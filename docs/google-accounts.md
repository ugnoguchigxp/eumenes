# Googleアカウント連携

設定アーティファクトの「Google連携」で、Googleアカウントを1件接続する。基本プロフィール（名前・画像）とメールアドレスだけを取得する。Calendar・Gmailの権限、同期、通知、AI操作は今回の対象に含めない。別アカウントへの切替は、現在の連携を解除してから接続する。

## 利用者の操作

Eumenesは本人のPCで起動する個人用アプリとして、Googleの「デスクトップ アプリ」用OAuthクライアントを使う。Eumenes配布元がクライアントを登録し、配布物へ設定を同梱する。設定済み配布版の利用者はGoogle Cloudのプロジェクト作成や認証情報の発行を行わない。

1. 設定 → Google連携 → Googleアカウントを接続。
2. 別タブのGoogle画面でアカウントを選び、アクセスを許可する。
3. 完了したタブを閉じると、元の設定画面に接続状態が反映される。別タブが開けない場合は「認証画面を開く」を使う。

ログイン済みのChromeプロファイルでEumenesを開けば、Googleのアカウント選択時にそのログイン状態を利用できる。Eumenesへのアクセス許可は別途必要。ChromeのCookieを取り出して使う方式ではない。埋め込みブラウザではなく、Chrome等の通常のブラウザで認証する。

## 配布元が一度行う設定

1. Google Cloudの「API とサービス」→「OAuth 同意画面」でEumenesのアプリ情報を設定する。個人のGoogleアカウントを対象にするので「外部」を選ぶ。開発中のテスト設定と一般配布の公開設定・必要なブランド確認を区別する。
2. OAuthクライアントを作成し、種類を **デスクトップ アプリ** にする。ウェブアプリケーションのクライアントは使わない。Google Cloudに利用者ごとのポート・リダイレクトURIを登録する作業はない。
3. ダウンロードしたクライアントJSONを、配布物内の `api/domains/google-accounts/distribution-client.json` に含める。これはGoogleの `installed` オブジェクトを含むJSON。認証エンドポイントはコード内の公式ライブラリを使い、JSON内のURLで変更しない。
4. 配布前に実アカウントで接続・解除を確認する。現時点では配布用クライアントは未同梱であり、実アカウント受入も未実施。

このファイルにはアプリの識別情報を入れる。利用者のパスワード・認証コード・アクセストークン・リフレッシュトークンは入れない。デスクトップアプリは配布先で秘密を保持できることを前提にせず、PKCEとstateを使う。配布用クライアントの情報は公開Gitリポジトリにコミットしない（既定ファイルはGit除外済み）。公式配布物へ同梱する作業と、公開ソースの管理は分ける。

開発・独自ビルドで別のクライアントを使う場合のみ、`EUMENES_GOOGLE_DESKTOP_CLIENT_FILE` にダウンロードしたデスクトップ用JSONのパスを指定できる。未指定なら同梱ファイルを読む。ソースだけを取得した環境には認証設定を含めないため、配布元の設定を別途配置するか、独自のデスクトップクライアントを用意する。従来の `EUMENES_GOOGLE_CLIENT_ID` / `EUMENES_GOOGLE_CLIENT_SECRET` は読み込まない。Web用JSONも拒否し、種類の混同を防ぐ。

## ローカルでの認証経路

既存のWeb待受とcallbackを再利用する。認証後の戻り先は `EUMENES_ORIGIN` ＋ `/oauth/google/callback`（標準では `http://127.0.0.1:5173/oauth/google/callback`）。`http` のループバックホスト（`127.0.0.1`、`localhost`、`[::1]`）に限定し、指定されたローカルのポートを使う。認証開始時とコード交換時に同じURIを使う。別サーバーへの設置や別PCのブラウザからの接続をこの方式で扱わない。

Webフロントは `/oauth/google/callback` と `/oauth/google/result` を同じローカルバックエンドへプロキシする。Viteの開発・プレビュー構成には登録済み。他の配信構成では同等の経路を用意し、この2経路へAPIのBearer認証を注入しない。URLの認証コードをアクセスログに記録しない。Viteのプロキシ障害ログは、既定のエラーハンドラーに渡る前に認証URLのクエリと例外本文を除去する。

参考: [Googleのインストール型アプリ認証](https://developers.google.com/identity/protocols/oauth2/native-app)、[OAuthポリシー](https://developers.google.com/identity/protocols/oauth2/policies)。

## 接続状態と保存

- 未接続・接続済み・再接続が必要・解除中を表示する。通常の設定の「保存」操作は不要。
- 許可するscopeは `openid email profile` のみ。追加のサービス権限は要求しない。
- IDトークンの署名・発行元・宛先・有効期限をGoogle公式ライブラリで検証し、nonce、メール確認済み状態、安定したアカウントID（`sub`）も検査する。再接続では同じ`sub`を必要とする。
- 認証要求は10分で失効。state、PKCE、認証要求ごとのHttpOnly/SameSite=Lax Cookieでブラウザと認証応答を対応付け、一度しか処理しない。取消・解除・新規認証後に古い結果が届いても採用しない。
- トークンと保留中の認証情報はsettingsの既存マスターキーから用途別に派生した鍵でAES-256-GCM暗号化し、専用テーブルに保存する。Webへの返却や共通操作台帳にはトークン・認証コードを含めない。DBと既存キーのバックアップは一組で管理する。
- バックエンド稼働中、60秒ごとに期限間近のトークンを更新する。Google側で許可が取り消された場合は、次の更新時に再接続状態へ移る。即時検出を保証するものではない。
- 解除は確認後にGoogleの許可を取り消し、保存情報を削除する。通信に失敗した場合は「解除中」で保存し、再起動後も再試行する。解除中は新しい接続を開始できない。進行中の認証応答を待ち、解除中に届いた認証情報も暗号化して取消対象に含める。自動処理と画面操作が重なっても取消は重複実行しない。
- Googleの取消APIは当該アプリに与えた許可に影響する。将来別ドメインで権限を増やす際は、OAuthクライアントの共有と解除の単位を改めて設計する。

## 実装と確認

`google-accounts` domainが認証・暗号化保存・失効管理を所有する。画面は `artifact:settings.google-accounts@1`、設定入口は `artifact:settings.hub@6`。既存の登録式アーティファクトとWeb adapterを使用する。DomainAdapterは公開状態の読み取りのみで、操作・AI用toolchain・packageは登録しない。

OAuthの開始・取消・解除は認証済みの専用API、GoogleからのcallbackはCookieとstateを検証する専用経路を使う。Googleのリダイレクトは共通APIのBearerを送信できず、トークン交換は外部通信を伴うため、同期transactionの共通操作台帳に入れない。

内部的なトークン更新では画面用revisionを変更しない。認証処理中も画面から取消でき、保存した接続状態が変わった際だけ操作の競合として扱う。保存情報を復号できない場合や状態取得が失敗した場合は、未接続と偽って表示せず読込エラーにする。

固定試験ではGoogle応答を置き換える。実Googleアカウントでの同意・取消はOAuthクライアントを設定して別途確認する。
