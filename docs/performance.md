# 性能予算と測定

代表条件の予算と、再実行可能な測定手順を定義する。予算は現行の実測（単回測定を含む）から置いた暫定値で、超過は直ちに失敗ではなく、再測定と原因の切り分けの合図とする。gate 化は測定が定常化してから別途決める。

## 予算（暫定）

| 条件 | 予算 | 根拠となった実測 |
| --- | --- | --- |
| 音声ターン: 確定 WAV 送信から認識表示まで | 1,500 ms 以内 | 873 ms（2026-10-08、合成 WAV・実 LARM、[acceptance.md](acceptance.md)） |
| 音声ターン: 最初の回答文字まで | 6,000 ms 以内 | 3,925 ms（同上） |
| 音声ターン: 最初の音声取得まで | 6,500 ms 以内 | 4,276 ms（同上） |
| 音声ターン: 回答完成まで | 9,000 ms 以内 | 5,783 ms（同上） |
| LARM 個別疎通: ASR / LLM / TTS | 各 5,000 ms 以内を目安 | ASR 897〜1,356 ms、LLM 3,334〜3,396 ms、TTS 978〜1,446 ms（各1回、[acceptance.md](acceptance.md)） |

文字ターンの初回表示、担当（toolchain）検索の所要には、まだ代表測定が無い。次回の live 測定で実測を取り、予算を追記してから採点対象にする。単回測定は予算の根拠にはするが、達成の証拠にはしない。

## 測定手順

1. LARM 個別疎通: 保存済み接続を使い `bun run verify:live -- --domain larm` を実行する（手順は [verification.md](verification.md)）。ASR・LLM・TTS の所要と出力サイズを記録する。
2. 音声ターン: 合成 WAV を公開 API へ送る既存の受入手順（[acceptance.md](acceptance.md) の streaming 記録と同じ条件）で、認識表示・最初の文字・最初の音声・完成までの ms を記録する。実機器での再生は含まない。
3. 記録は `spec/verification/` に、日付・対象コミット・条件（fixture/live/実機器）を分けて残す。過去の成功記録を現在の達成とは扱わない。

## 保存済みログから会話の基準値を取る

```sh
bun scripts/conversation-performance.ts --since 2026-11-21T08:17:49.629 --until 2026-11-21T08:29:37.567
```

期間は開始を含み、終了を含まない。タイムゾーン省略時は JST。既定の運用ログとローテーション分を読み、受付 `runId` と `jobId` で実行を結ぶ。指定した会話実行だけを集計するには `--run-id <ID>` を繰り返す。`--file` で保存済みのログを指定できる。

完了したジョブについて、受付、生成開始、過去のRouter、最初の `streamed` 本文、先頭音声データ準備、ジョブ終了の区間を集計する。`firstBodyToSettled` は最初の本文から同じジョブの終了まで。各区間は観測件数とミリ秒の p50・p90・最大値を返す。p50 は中央値、p90 は近順位法。取消や途中の実行はジョブ状態の件数に出る。回答の採用と実機器での音声再生は既存の実行記録と機器受入で確認する。[運用ログ](logging.md#応答開始までの時間を調べる2026-10-14追加)

`stageTimingMs` は、指定した会話実行に紐付く区間を component・phase・経路・用途・結果等ごとに p90 の降順で示す。例えば `tool_execution` の `kind=find_toolchain` を `query_embedding` と見比べると、検索のどこで待ったかを絞れる。`larmTimingMs` はLARMの送信後の初回本文と、Providerが報告したprefill・decodeの時間を示す。未観測の区間は集計に現れないか、観測件数0・値 `null` になる。区間には入れ子があるため、個別実行は `--run-id` と [JSONL の照合](logging.md#応答開始までの時間を調べる2026-10-14追加)で追う。

稼働中の API から利用量を照合する場合は `--with-usage` を付ける。既存の利用状況を読み取り、期間内に始まり終わった Codex の試行を `attemptId` で結ぶ。`reply` が回答生成、`background` が背景要求、`unlinked` がログで用途を確定できなかった試行。背景と用途未確定の集計は全期間を対象にする。キャッシュ率の分母は入力とキャッシュ読取の両方を観測できた試行。欠測値は `null` で、キャッシュ読取の報告値が0の場合も計数する。

Codex の `usageUpdates` は、運用ログで利用量の増加を観測した回数と試行数、同じ試行で複数回増えた件数を示す。ログを採取していない期間は `null`。個別のモデル応答の入力、キャッシュ読取、実効ウィンドウは `bun run logs -- --id <runId> --event inference.codex_usage_updated --json` で確認する。

## 扱い

- 予算超過が再現する場合は、まず `bun run logs -- --level warn` から runId で対象ターンを追い、入力長・接続状態・モデル側の所要を分ける（[logging.md](logging.md)）。
- 予算値の変更は実測の分布を見て行い、本書と根拠記録を同時に更新する。
