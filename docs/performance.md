# 性能予算と測定

代表条件の予算と、再実行可能な測定手順を定義する。予算は現行の実測（単回測定を含む）から置いた暫定値で、超過は直ちに失敗ではなく、再測定と原因の切り分けの合図とする。gate 化は測定が定常化してから別途決める。

## 予算（暫定）

| 条件 | 予算 | 根拠となった実測 |
| --- | --- | --- |
| 音声ターン: 確定 WAV 送信から認識表示まで | 1,500 ms 以内 | 873 ms（2026-10-08、合成 WAV・実 LARM、[acceptance.md](acceptance.md)） |
| 音声ターン: 最初の回答文字まで | 6,000 ms 以内 | 3,925 ms（同上） |
| 音声ターン: 最初の音声取得まで | 6,500 ms 以内 | 4,276 ms（同上） |
| 音声ターン: 回答完成まで | 9,000 ms 以内 | 5,783 ms（同上） |
| LARM 個別疎通: ASR / LLM / TTS | 各 5,000 ms 以内を目安 | ASR 897〜1,356 ms、LLM 3,334〜3,396 ms、TTS 978〜1,446 ms（各1回、[acceptance.md](acceptance.md)） |

文字ターンの初回表示、担当（toolchain）検索の所要には、まだ代表測定が無い。次回の live 測定で実測を取り、予算を追記してから採点対象にする。単回測定は予算の根拠にはするが、達成の証拠にはしない。

## 測定手順

1. LARM 個別疎通: 保存済み接続を使い `bun run verify:live -- --domain larm` を実行する（手順は [verification.md](verification.md)）。ASR・LLM・TTS の所要と出力サイズを記録する。
2. 音声ターン: 合成 WAV を公開 API へ送る既存の受入手順（[acceptance.md](acceptance.md) の streaming 記録と同じ条件）で、認識表示・最初の文字・最初の音声・完成までの ms を記録する。実機器での再生は含まない。
3. 記録は `spec/verification/` に、日付・対象コミット・条件（fixture/live/実機器）を分けて残す。過去の成功記録を現在の達成とは扱わない。

## 扱い

- 予算超過が再現する場合は、まず `bun run logs -- --level warn` から runId で対象ターンを追い、入力長・接続状態・モデル側の所要を分ける（[logging.md](logging.md)）。
- 予算値の変更は実測の分布を見て行い、本書と根拠記録を同時に更新する。
