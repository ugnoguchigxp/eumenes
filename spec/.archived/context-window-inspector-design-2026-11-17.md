# 会話 ContextWindow のライブ閲覧

2026-11-17。右上からのライブ閲覧、返答からの参照、デバッグモード中の一時保持を実装した。固定データを使った検証と実接続の状況は第7節に記録する。

関連資料は[会話の入力仕様](../conversation-input-spec-2026-10-26.md)、[デバッグモード専用の会話自己診断](../.todo/conversation-debug-diagnostics-implementation-plan-2026-11-15.md)、[Codex 経路の入力キャッシュ](codex-input-cache-structure-2026-11-12.md)、[運用ログ](../../docs/logging.md)。

## 1 利用場面と対象

11月17日の会話では、Eumenes が「通勤したのは昨日」という訂正を認めた後、開発の相談への返答で再び「今朝の通勤」を前提に質問した。実行記録には訂正発言への参照があった。参照には間接的な出典も含まれるため、訂正がどこに入り、Agency がどんな質問候補を添えたかは後から確認できなかった。

会話画面で、返答の生成中に入力の変化を追えるようにする。返答後は、その発言に対応する run と呼び出しを開き、送信時点の文面・順番・出典を確認できるようにする。正常終了した run も対象にする。

対象は `dialogue` の run に属する会話の回答生成と、同じ回答のためのツール結果を受けた呼び出し、接続先を切り替えた際の試行。音声認識を経て通常の会話 run を作る場合も同じ入口で扱う。記憶や Agency の背景処理が更新した内容は、会話の送信入力に採用された時点で表示する。表示する観測範囲は、Eumenes が接続先または SDK に渡した入力と、Eumenes が把握する持ち越し分までとする。

## 2 画面

既存の「設定 → 会話 → デバッグモード」に連動して、会話画面の右上の通知・アーティファクトの並びに **コンテキスト** ボタンを表示する。右パネルを開いた状態でも会話欄と入力欄を操作できる。ボタン、開閉時のフォーカス、キーボード操作には既存の DesignSystem を使う。パネル内の資料は開発用の表示として扱い、会話に渡す画面参照から除外する。[会話画面の配置](../../web/src/workspace/Workspace.tsx) · [デバッグモード](../../docs/settings.md#設定画面)

| 操作 | パネルの動作 |
| --- | --- |
| 右上の **コンテキスト** を開く | **最新を追う** で開く。進行中ならその run を、待機中ならこの会話の直近の run を選ぶ。進行中の run で最初の送信が始まるまでは「入力を準備中」と表示する。 |
| 入力が送信される | 時刻、呼び出し番号、段階を一覧に追加する。最新を追っているときは新しい入力を選ぶ。回答の文字が届く途中でも、選択した入力の文面は送信時のまま読める。 |
| 返答の **この返答の入力を見る** を開く | その返答の `runId` に固定し、採用された回答の入力を選ぶ。同じ回の他の呼び出しや失敗した試行も一覧から選べる。 |
| 一覧で過去の入力を選ぶ | 選択を固定する。新しい発言が始まっても開いている入力を保ち、**最新を追う** を選ぶと追従を再開する。 |
| **前の入力との差分** を開く | 直前の呼び出しと比較する。回の最初の呼び出しでは、同じ会話で保持されている前の回の入力を使う。追加・削除・変更を送信順に表示し、比較元の回と時刻を示す。 |

返答との対応には保存済みの `Message.runId` と run の回答メッセージ ID を使う。編集して送り直した回も、それぞれの返答につながる run を開く。採用試行は既存の推論の採用記録で示し、確認できない場合は時刻順に全試行を提示する。[会話履歴と実行表示](../../web/src/workspace/ConversationHistory.tsx) · [推論の採用記録](../../api/domains/inference/contracts/index.ts)

入力詳細の先頭には対象の返答、送信時刻、接続経路、呼び出し番号を表示する。本体は送信順のメッセージ列とし、各行で role、文面、資料の種類、利用できる出典 ID・版・時刻を読める。指示、過去の発言、記憶と状態、Agency が挿入した文、今回の発言、ツールの結果はそれぞれ実際の位置に置く。発言時刻と送信時刻は区別する。文面はプレーンテキストで表示し、長い区画を展開して読める。由来が分からない項目は「出典未特定」と表示する。

## 3 送信入力の取得

### 3.1 取得点と責務

1. `dialogue` が会話の回答用呼び出しを開始するときだけ、既存 run に紐づく採取先を渡す。判定には呼び出し側が持つ run と用途を使う。モデル名、接続名、利用者の発言から取得対象を推測する必要はない。
2. 既存の入力組立てで、どの位置がどの発言・記憶・ホストの資料に由来するかを採取用に対応づける。Agency による挿入、生成中の追加発言、ツール結果が加わった呼び出しも、実際の `request.messages` と対応させる。複数の資料が同じメッセージに収まる場合は、その中の位置を示す。既存の run の参照一覧は失効の依存元として利用できる。画面で示す各位置の由来は、挿入元と描画処理から得る。[入力組立て](../../api/domains/dialogue/service/generation-prepare.ts) · [回答の呼び出し](../../api/domains/dialogue/service/routed-turn.ts) · [Agency の挿入](../../api/application/agency/always-on-ports.ts)
3. `inference` と接続アダプタで、画像・ツール・予算の検査と入力変換を済ませた時点の入力を受け取る。既存呼び出しに任意の観測口を通し、下位 domain は `dialogue` の状態や設定を参照せず、確定した入力の必要項目だけを呼び出し元へ渡す。採取と差分の計算はプログラムで行い、診断のためにモデルを呼ぶ必要はない。
4. `dialogue` が採取した入力を会話と run に紐づけ、メモリ上の診断用領域に確定する。入力は採取時の内容で固定し、追跡中の更新は新しい呼び出しとして追加する。既存の run・推論記録から受付、失敗、中断、採用を対応づけ、保存した入力の有無と回答の結果をそれぞれ表示する。送信開始は Eumenes が要求を渡した時点を示す。利用者が回答を中止した場合は、送信した入力を中断状態とともに保持する。

### 3.2 接続経路ごとの観測境界

| 経路 | 「送信時点」として記録する位置 |
| --- | --- |
| LARM | 確定したメッセージとツールで正式計数・claim 検査を通過した後、生成要求を送る直前。計数が拒否した場合は「送信前に終了」とし、送信の行は作らない。[生成要求](../../api/domains/larm/service/answer-request.ts) |
| クラウドの HTTP 経路 | 予算に合わせた整形・検査を通過し、確定した生成要求を接続先へ渡す直前。[クラウド要求](../../api/domains/inference/service/cloud.ts) |
| Codex SDK | `turn/start` に渡す文面、ツール用に加えた指示を含む `baseInstructions`、`new`・`append`・`reset` の方式と、Eumenes 側で対応づけられる持ち越し範囲を記録する。`append` は今回足す文と保持済みの文を示す。SDK 内部で加わる項目や圧縮については、観測境界を「SDK への入力」と表示する。[Codex 入力の変換](../../api/domains/inference/adapters/cloud-agent-codex.ts) · [送信処理](../../api/domains/inference/adapters/codex-app-server.ts) |
| その他の SDK 経路 | ホストが実際に SDK に渡せた指示と入力を、その SDK の送信境界で記録する。観測口のない経路は「この経路の入力は取得できません」と表示し、正確に捕捉した範囲を明示する。 |

保存先には採取の識別子、`conversationId`、`runId`、`inferenceId`、`attemptId`、run 内の送信順、送信開始時刻、経路、メッセージと出典を持つ。フォールバックや同じ run の連続したモデル呼び出しにも個別の番号を付ける。予算による除外や縮約の情報を既存処理が確定できる場合は、理由と件数を添える。入力の比較はこの保存済みの版を使う。

保存する項目は送信されたテキスト、role、時刻・参照、提示されたツール定義、モデル入力に含まれたツール呼び出しと結果。添付は種類・位置・参照・サイズなどのメタデータを記録する。認証に関する値・HTTP ヘッダー・メディア本体・Provider の生応答はこの項目に含めず、本文は診断領域の取得 API からのみ提供する。記録可能な部分と、そもそも観測できなかった部分が画面で分かるようにする。

## 4 取得 API とライブ更新

取得 API は二つある。既存の `run` の取得と同じ認証を経て、run が閲覧可能な会話に属し、デバッグモードが有効であることを確認する。契約は dialogue の API と共通 client に定義する。

| 操作 | 応答 |
| --- | --- |
| `GET /api/runs/:id/context` | run の状態、取得できる入力の一覧、現在の版を返す。一覧は識別子、採取時刻、有効期限、経路、採用状態まで。 |
| `GET /api/runs/:id/context/:captureId` | 指定 run に属する指定版の入力を返す。取得時に期限、権限、失効を再確認する。 |

応答に `Cache-Control: no-store` を付ける。記録が空の場合は、送信待ち、送信前の終了、取得できる記録なしを、確認できた事実に応じて表示する。期限や容量で消えた理由が分かる場合はその理由を出す。

入力の採取と失効を既存の変更通知 SSE で届ける。パネルを開いた Web は、変更通知を受けて対象 run の一覧を読み、選択した版の本文だけを必要なときに取得する。回答の文字は既存の回答ストリームで更新する。切断中は更新が止まったことを表示し、再接続時に一覧と選択中の入力の有効性を取り直す。[既存の変更通知 client](../../client/events.ts) · [診断の更新方法](../.todo/conversation-debug-diagnostics-implementation-plan-2026-11-15.md#7-会話欄と詳細の表示)

CLI からは `bun run cli -- run <run-id> --context --json` で同じ API を読む。採取済みの一覧と、採用された回答の入力を返す。生成中や採用を確認できない回は、選んだ入力の状態を示したうえで最新のものを返す。`--call <番号>` を指定して、その回の別の入力も取得できる。[CLI 実行照会](../../docs/cli-chat.md#aiによる再現デバッグ)

## 5 保持と失効

デバッグモードが有効な間は、パネルを閉じているときも採取する。記録はサーバープロセス内で保持する。上限は採取から30分、会話ごとに最新20 run、1入力2 MiB、全会話で16 MiB。記録の容量には本文と一覧用の情報を含める。期限は既存の会話診断と揃え、期限到達で本文を破棄する。容量に達したら古い記録から除き、単体上限を超えた入力は「容量上限で本文を取得できません」と表示する。[既存診断の保持上限](../.todo/conversation-debug-diagnostics-implementation-plan-2026-11-15.md#6-コンテキストと長時間利用の上限)

設定をオフにしたときは採取を止め、同じ設定の世代に属する記録と画面上の本文を消す。会話削除、対象の訂正・忘却、権限失効でも対象の入力を消す。既存の参照検証を使い、依存元が確定しない記録は、その資料が変わり得る範囲の訂正・忘却時に記録全体を失効させる。本文を返す直前に有効性を検査し、設定や資料が変わる直前に始まった採取や取得も、古い世代の結果を表示へ戻さないようにする。Web はパネルを閉じたとき、接続先が変わったとき、または対象が失効したときに、取得済みの本文を破棄する。[既存の参照検証](../../api/domains/memory/service/reference-input.ts) · [診断の失効条件](../.todo/conversation-debug-diagnostics-implementation-plan-2026-11-15.md#8-例外と停止)

初版では訂正・撤回・忘却が起きると保持中の入力を全件破棄する。記憶や Agency の状態を通じて、同じ資料が別の会話の入力にも使われるため。取得時にも run と推論試行の権限、記録した参照の有効性を確認する。[一時保持と取得](../../api/domains/dialogue/service/context-inputs.ts)

初版で開ける過去の返答は、同じプロセスで記録し、保持上限に収まっているもの。再起動後はその回の記録がないと表示する。再起動を挟む調査にも広げる場合は、本文の期限付き保存と忘却・バックアップの扱いを設計時に決める。

## 6 実装順と受入条件

1. **取得と失効。** `dialogue` の一時保持と読み取り契約を作る。既存のデバッグ設定、run、出典検証、変更通知との接続を、固定データで確かめる。
2. **送信経路。** 回答 run から取得点を通し、まず LARM と今回の返答で使われた Codex SDK を固定試験で照合する。対応する HTTP・SDK 経路にも各境界の試験を置く。同じ入力で採取を有効にした場合の送信文・ツール定義・推論回数も、実装前に取った基準と比較する。
3. **Web と CLI。** 右上の入口、返答からの固定表示、最新追従と差分、CLI の取得を同じ API に接続する。対象 domain の部分試験から結合、通しの順に確認する。

| 検証 | 合格条件 |
| --- | --- |
| 送信の照合 | 通信先を fixture に差し替え、観測した実入力と表示の文面・role・順序が一致する。Codex の `append` では今回追加した入力と持ち越し範囲を照合する。送信前の拒否、再試行、接続切替で取り違えがない。 |
| 通勤のケース | 固定の会話で過去の「今朝の通勤」、本人の「通勤したのは昨日」、後続の「今朝は忙しかった」、話題の違う依頼を順に置く。既知の質問候補も入力に加え、最後の返答から開いたとき、訂正と候補が入った場所を送信の記録で示せる。 |
| ライブと過去 | ツールを1回使う返信で、送信ごとに一覧が増え、差分にツール結果が現れる。前の返答に固定したまま次の発言を送っても選択を維持し、追従再開で最新に戻る。パネルを後から開いても同じ入力を読める。再接続と CLI でも一致する。 |
| 失効と上限 | OFF のまま送った場合は追加の採取が0件。OFFへの切替、権限失効、訂正・忘却、期限切れ、再起動、サイズ上限では、対象の本文を API と画面から取り出せなくなる。別の run や会話の ID で同じ本文を取得できない。 |
| 通常の経路 | 採取を加える前後で同じ入力・出力制約・モデル呼出し回数を使う。採取の失敗時にも元の返答は処理される。入力の保持量と、返答の最初の表示までの時間を測る。 |

実装後は `bun run verify -- --domain dialogue --domain inference --domain larm --domain conversation --domain memory` を基準に、変更した利用側 domain も含める。ブラウザー E2E は追加する対象ファイルを明示して実行する。fixture、実接続、実機器を使う確認は実施状況を分けて記録する。

## 7 実装と検証の記録

- **Backend・CLI の固定試験 101件合格。** LARM とクラウド HTTP の送信文面、Codex の `turn/start` と持ち越し、Claude Agent SDK に渡す入力を照合した。通勤を訂正した発言と Agency の質問候補の位置、ツール使用後の入力、フォールバックの試行順、容量超過・期限切れ・設定 OFF・訂正・忘却、Web と CLI での記録の一致を確認した。[会話の入力取得試験](../../api/domains/dialogue/test/context-inputs.test.ts) · [CLI 結合試験](../../api/application/cli-chat-integration.test.ts)
- **Web の固定試験 12件合格。** 会話画面のボタンから最新入力を、過去の返答から対応する入力を開いた。ライブの通知後の追従、固定を維持してからの追従再開、差分、デバッグ設定 OFF と失効時の本文の消去を確認した。[画面の通し試験](../../web/src/App.smoke.test.tsx) · [パネル試験](../../web/src/workspace/ConversationContextPanel.test.tsx)
- **標準検証は未完了。** 作業ツリーにある過去の検証コピーが試験一覧の検査対象になり、最初の `inventory` で停止した。変更ファイルの lint・整形と差分の空白検査は合格した。全体の型検査には `packages/artifact-ui/src/markdown-components.tsx` のエラーが残る。
- **実接続の検証は未実施。** 実際のブラウザーでの表示・再接続、実サービス・実機器での受入、初回表示までの所要時間と長時間利用時のメモリ使用量の実測が残る。
