## 2. 実装した不具合修正

既存設計§5「同じ成果版に対する検査が不一致なら、未達の条件と実測を通常の判断へ戻す」と、提示した手段を実行できることを満たすための修正。判断方式・優先順位・フォールバックは追加していない。

| 変更 | 内容 |
| --- | --- |
| 文書照合の実行不能をなくす | 指定された証拠に読める文書がない条件と、文書の合計が48,000字を超える場合は、モデルを呼ばずに不合格の検査結果を返す。結果の `observation` に理由を残し、通常の判断へ戻す。条件の特定ができない場合だけ従来どおり実行不能とする |
| 止まった手をログに残す | `problem()` が待機に入れる前に `agency.goal_parked` を warn で出す。`reason`・`jobId`・`subjectId`（目標ID）・`kind`（選ばれていた手の種別）・`workRevision`（進行版）だけを記録し、本文は出さない |

不合格の結果として残る観測の例:

```json
{"observation":"指定された証拠に、照合できる保存済みの文書がありません。文書照合は文書IDの資料だけを照合します。","documents":[],"passed":false}
```

固定試験は `goal-capability-selection.test.ts` に2件を追加した。修正前のコードでは2件とも失敗し、1件目は待機に入ったまま5秒で時間切れになる。

| 試験 | 合格条件 |
| --- | --- |
| 文書でない証拠への文書照合 | 判断2回、照合のLLM呼出し0回、`goal_worker_unavailable` にならない、`root` は `open`、理由付きの不合格の証拠が残る |
| 上限を超える文書 | 照合のLLM呼出し0回、不合格、理由に上限の字数が入る |

この修正で目標1が行き止まりに入る経路は1つ減る。ただし§3の登録検査の提示がない限り、目標1は自力で検証へ進めない。

## 3. 合意を求める設計変更（未実装）

### 3.1 読取ポリシーの許可をコミットで失効させない

| 項目 | 現行 | 変更案 |
| --- | --- | --- |
| 読取ポリシーの構成世代 | `baselineCommit`（HEAD）を含む。コミットのたびに許可が失効・再発行される | 書込み0件の読取ポリシーでは `baselineCommit` を構成世代から外す。登録範囲・固定検査・bindingの版が同じなら同じ許可を保つ |
| 検査の提示条件の作業先照合 | 作業先の HEAD が許可の `baselineCommit` と一致すること | 読取ポリシーでは HEAD を照合しない。検査証拠の版は既存の `inputDigest`（読取対象ファイルの内容）で判定する |
| 本人の明示許可（書込みあり） | 基準版で固定 | 変更しない。第三者の変更を自分の変更として採用しない既存の照合も維持 |

理由: 本家の checkout を読み取り専用の作業先にすると、日常のコミットで許可IDが変わり続け、過去の読取を検査の根拠に数えられない。内容の変化は `inputDigest` で既に検出している。

### 3.2 登録検査の提示条件を「その作業先を実際に読んだ」に揃える

| 項目 | 現行 | 変更案 |
| --- | --- | --- |
| 読取ポリシーの検査が出る条件 | 同じ許可ID・版で `succeeded`、`resultRef` と証拠があり、対象条件を含む試行 | 同じ作業先の許可で行い、対象条件の証拠を残した試行。結果は問わない（`failed`・`partial` を含む） |
| 無関係な作業先の検査 | 提示しない | 変更しない（既存試験「Web文書の証拠しかない目標には無関係な作業先の検査を出さない」を維持） |

理由: 承認済みの設計差分の合格条件は「既存の実物を読み、対応する検査を選べること」。目標1は実物を4回読んでいるのに、監督が結論を返せなかったため検査を選べない。検査そのものは登録済みの固定コマンドを sandbox で実行するので、監督の結論には依存しない。

### 3.3 行き止まりの待機に再確認時刻を持たせる

| 項目 | 変更案 |
| --- | --- |
| 対象 | `problem()` が入れる構成変更待ち（`goal_worker_unavailable`・`goal_verification_unavailable`・`goal_decision_*` など） |
| 再確認 | `watch.dueAtMs` を入れる。初回1時間後、続けて止まるたびに倍、上限24時間。進行（新しい試行結果・構成変化・資料の到着）があれば1時間に戻す |
| 同じ入力の連打防止 | 時刻で起きたとき、判断の入力（`contextId`）が前回の判断と同じなら、LLMを呼ばずに次の時刻まで待機を延ばす |
| 停止・取下げ | 全停止・自発行動の無効化・取下げ・忘却の既存の制約をそのまま適用する |

理由: 一時的な原因（実行先の不在、推論のタイムアウト）で止まった目標が、再起動まで戻らない。入力が変わらないまま同じ判断を繰り返さないことも既存の方針（同じ入力で生成を連打しない）に合わせる。

### 3.4 止まったことを一度だけ伝える

| 項目 | 変更案 |
| --- | --- |
| 条件 | §3.3の待機が2回続き、本人に配送済みの質問もない |
| 内容 | 既存の質問配送を使い、元会話へ1回だけ届ける。同じ目標版・同じ理由では再送しない。発話休止・全停止・元会話が不明の場合の既存規則に従う |

### 3.5 再起動後に見つかった連続失敗（11月26日 09:27 起動）

§2の反映後、目標1は構成待ちから戻り、`agency.goal_parked` は0件だった。一方で、09:28〜09:39 の11分間に開発監督への試行を8件続けて行い、完了した7件はすべて `failed` になった。実行は止まっていない。

| 観測 | 内容 |
| --- | --- |
| 監督の判断が即時に失敗 | `claude-code.decide` が 1ms で失敗し、`decision.ts:132` の `claude_decision_input_limit` に当たる（入力が上限12,000を超える）。2回失敗すると「担当の判断を確定できず」で終わる |
| 登録検査は依然として出ない | 08:45 のコミット `c2fc0969` で読取許可が再び失効・再発行された（`c724a183`）。§3.1・§3.2が未実装のため、試行は監督経由のまま |
| 歯止めがない | 同じ条件で3回失敗すると `reviewRequired` が立つだけで、判断は新しい試行を出し続ける |

追加の変更案: 同じ条件で新しい証拠のない失敗が3回続いたら、新しい試行を受け付けずに§3.3の待機（再確認時刻つき）へ入れる。§3.4の通知の条件にもこれを含める。監督の入力上限は §3.6 の別調査に含める。
