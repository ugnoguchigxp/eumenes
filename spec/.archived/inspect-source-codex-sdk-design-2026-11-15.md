# 会話から Codex SDK に依頼するソース調査

2026-11-15 · 設計案

Eumenes の会話から登録済みのソースコードについて質問すると、Codex SDK が調査し、要約と根拠のファイル・行番号を同じ会話に返す。初期対象は Eumenes の Git リポジトリ１件とし、調査開始時のコミットを回答に明記する。結果は既存の会話・仕事結果として扱い、Markdown ファイルや Docling 文書の作成は行わない。

## 1. `inspect` の Web と Source

`inspect` は Codex SDK に調査を依頼する共通の実行機構とする。`inspect.web.note` と `inspect.source` は調査対象を表す。会話側の LLM が依頼内容から対象を選び、実行側は登録済みの binding で選択を確定する。会話本文の語句でモードを切り替える処理は追加しない。

| 調査対象 | 登録上の入口 | 対象と根拠 |
| --- | --- | --- |
| `inspect.web.note` | 現行の `web.note` / `web_note` を使用 | Codex の Web 検索。出典は URL |
| `inspect.source` | 新規の `inspect.source` / `inspect_source` | 登録済みの Git コミット。根拠はリポジトリ相対パスと行範囲 |

会話委任の既存契約は、登録済みの担当と依頼文を受け取る。モード引数を主会話の `delegate` に増やす必要はない。Source の bundle には profile・Skill・package・task binding・入出力契約を登録し、既存の検索と委任に載せる。初期版の Web 側は現行 ID・revision のまま利用し、`inspect.web.note` を別の候補として重複登録する作業は範囲外とする。 [Web 調査の現行設計](web-note-codex-search-2026-11-11.md) · [登録と拡張の手順](../../docs/toolchain-extension.md) · [会話の委任処理](../../api/domains/dialogue/service/routed-talk-work.ts)

Source の task は利用者の会話発言に結び付いた実行だけを受け付ける。登録 adapter に自律実行権限を宣言せず、受付時にも host が発行した実行元を検証する。`autonomous` と `workflow` の実行元は拒否する。既存の agency の調査先選択、ノート採用、文書保存を変更する作業は範囲外とする。 [task の自律実行判定](../../api/application/toolchain/task-autonomy.ts) · [agency の調査先選択](../../api/application/agency/always-on-flow.ts)

## 2. 実行と結果

1. 会話の LLM が登録済みの `inspect_source` を選び、利用者の質問を渡す。Eumenes が既存の仕事として受け付け、状態照会と取消を提供する。
2. 実行開始時に、host が登録済みの Eumenes のルートを解決し、`HEAD` をコミット ID に固定する。許可済みの通常テキストファイルを、そのコミットの Git オブジェクトから調査用の一時領域へ展開する。作業ツリーに未コミット変更があっても、回答対象は固定したコミットとする。ファイル取得は DB の書込みトランザクション外で行う。
3. Codex SDK の新規セッションに、質問、調査対象の版、返却形式を渡す。どのファイルを探すか、どこまで追えば答えられるかは Codex が判断する。Source 用の接続とモデル設定を host で解決し、`web.note` に固有の固定モデル指定をこの機能へ流用する作業は範囲外とする。設定・隔離・対象が揃ったときに Source を実行可能とする。
4. SDK は `outputSchema` を使って、短い要約と、主張に対応する候補のパス・開始行・終了行を返す。Eumenes が同じコミットの許可済みファイルに照合し、存在する行範囲だけを根拠として採用する。根拠をすべて失った主張は、確認済みの結果から外す。短い引用を付ける場合は host が該当する行から取得する。行の照合は参照先の検証であり、主張の解釈は Codex が担当する。
5. 既存の仕事結果に要約と、「`<repo>@<commit>` · `<path>:<start>–<end>`」形式の根拠を載せ、同じ会話に届ける。行番号は１始まりとし、絶対パスは結果に含めない。Source の構造化結果を表示用の `answer` へ変換し、Web URL 用の `sources` に代替 URL を作る作業は行わない。

根拠が取れた範囲を返し、確認できない箇所はその旨を記す。有効な根拠が一件も取れなければ、ソースから確認できなかった結果として扱う。SDK 起動失敗、応答形式の不一致、期限超過、取消は既存の状態で返す。終了時は実行元・binding・期限・取消状態を再検査し、失効後の結果を会話へ採用しない。

### 共用する実装と Source 固有の実装

| 共用 | Source 固有 |
| --- | --- |
| `web.note` の単発 SDK 呼び出し、取消・期限、使用量記録、登録 task の受付と会話への結果配送 | 許可されたコミットの取得、閲覧実行の隔離、結果 schema、ファイル・行の照合 |

既存の SDK helper には、呼出元が用意した調査領域と結果 schema を渡せる最小の拡張を加える。Web の空の作業場所と Web 用設定は回帰試験で保全する。

初期版は既存の task owner と `web_note_runs` の実行台帳を共用する。登録上は Source に専用の adapter ref を持たせ、既存 Web 用 adapter の自律実行可否と分ける。実行側は binding で決まったモードを保持し、Source では最初に取得したコミットも保存する。再開時に同じコミットを用意できなければ中断として扱う。既存の Web の記録は現行契約のまま読み取る。共用は同じ責務を持つ処理に限り、Web URL の抽出や Markdown メモの整形は Web 側に置く。 [SDK helper](../../packages/coding-runner/src/codex-turn.ts) · [現行の task owner](../../api/domains/web-note/service/index.ts) · [現行の結果配送](../../api/domains/web-note/service/lifecycle.ts)

## 3. 閲覧権限と保持

- `inspect.source` は閲覧専用とする。変更を含む依頼でも、ソースファイルの作成・編集・削除、パッチの適用、Git のステージング・コミット・push は行わない。原本のリポジトリと調査用のコピーの両方で、調査プロセスへのソース書込み権限を与えない。調査結果をきっかけに、編集権限を持つ別の担当へ自動で委任することも禁止する。
- 管理側がリポジトリと、Codex に渡してよいパスを登録する。Git 管理下かどうかだけで閲覧を許可せず、秘密を含む設定、データベース、ログ、バイナリ、symlink、submodule は調査用領域から除く。初期版では利用者やモデルから任意の実パス・リモート URL・ブランチを受け取る操作は設けない。
- Codex の作業場所に、許可済みの調査用領域を読み取り専用で見せる。SDK の `read-only` と `cwd` に加え、探索用の子プロセスから原本、ホーム、認証情報、他のリポジトリへ到達できないことを実行環境で強制する。探索用の外部通信・Web 検索・外部 MCP・プラグインや継承したプロジェクト指示を無効にする。認証と推論に必要な SDK 側の通信は探索用プロセスの権限と分ける。この実行境界を実環境で確認できることが公開条件となる。
- Codex に渡す質問と許可済みソースは設定された推論先で処理される。入力は調査に必要な依頼と対象情報に絞る。取得したコードやコメントは資料として扱い、そこに書かれた指示に実行権限を与えない。
- 調査用領域は実行終了・取消時に回収し、異常終了で残った領域も起動時の回収対象にする。既存の仕事台帳と会話に残るのは短い結果と根拠情報に限る。調査中の全文・生イベント・SDK の生応答を台帳や運用ログに保管する経路は設けない。

## 4. 実装順と受入条件

| 段階 | 確認すること |
| --- | --- |
| 部分 | 合成リポジトリで、未コミット変更を無視して固定コミットを読む。範囲外パス、symlink、submodule、存在しない行、異なる版の根拠を拒否する。ファイル数・入力・出力・実行時間に上限を設け、その超過を正常終了として扱わない |
| 結合 | 固定 SDK 応答を使い、会話の候補提示 → Source の委任 → SDK 呼出し → 行の照合 → 元会話への結果配送を通す。取消・期限後は結果を届けず、一時領域を回収する。文書保存が呼ばれず、自律実行元から受付できないことを確認する |
| 回帰 | `bun run toolchain:bundle -- check <bundle>` と、`bun run verify -- --domain capabilities --domain dialogue --domain agent-runtime --domain web-note` を使う。変更箇所に応じて SDK の利用側も追加する。Web の既存経路と agency の `web.note` 選択を変更前後で照合する |
| 実環境 | 合成リポジトリで閲覧と編集を一緒に依頼し、閲覧ができること、原本と調査用コピーへの書込みが拒否されること、別の編集担当が起動せず、ファイル内容・Git インデックス・HEAD が実行前後で一致することを確認する。対象外の読取りと探索用の外部通信も拒否されることを確認する。その後、登録済みリポジトリについて複数ファイルをまたぐ質問を会話から一件実行し、返った要約、コミット、ファイル、行を人が照合する |

実装時は、Source の実行境界と行の照合を先に確かめ、次に bundle・adapter と会話経路をつなぐ。最後に Web の回帰と実 Codex の受入を行う。実環境の隔離と根拠付き回答の両方が確認できた時点を公開の完了条件とする。 [ツールチェーンの検証手順](../../docs/toolchain-extension-verification.md)

## 5. 実装と確認記録

- `inspect.source` の初期対応は macOS。起動時に Codex の権限プロファイルで、許可したファイルの読取り、範囲外への読取り拒否、調査用の領域への書込み拒否、探索プロセスの通信拒否を確認してから登録する。Source は Codex の既定モデルを使う。
- 固定試験では、許可済みファイルをコミットから読み、無効な根拠を落とした結果が元の会話のアシスタントメッセージになることを確認した。
- 2026-11-15 に実 Codex SDK でサーバー初期化の経路を調べ、コミット `eebcc8d7` の複数ファイルと行範囲を元の試験用会話で確認した。本番稼働中のバックエンドへの反映は次回起動時となる。

## 6. 抜粋と差分の表示

以降の調査結果にはこの節の契約を適用する。変更の基準は開始時のコミット、現在のコードは調査開始時に取得した作業ツリーとする。取得した両方のコピーを読み取り専用で使い、差分はホストが実ファイルから作る。変更がないファイルは照合済みの範囲を抜粋する。エージェントは依頼から表示深度と読むファイルを選ぶ。指定がなければ中とし、ホストが重複を除いて小３・中４・大５ファイルに制限する。

利用者に見せるメッセージは概要に続けて、引用表示の「ソース：相対パス」と、変更前後を `-` / `+` で示す差分コードブロックか、コードの一部抜粋を含める。概要のみを通常の本文として記録し、画面専用のテキストを分離してメッセージ一覧に載せる。会話エージェント、会話検索、読み上げには通常本文を使う。コミットの識別子は実行台帳内で使う。

途中までの結果は「一部抜粋」と表示する。取消で結果が確定していないときは既存の取消を維持する。固定試験では、変更前後のコード、深度別上限、画面用テキストと読み上げ・会話入力の分離、ソースの変更が発生しないことを確認する。既に会話に表示された旧形式のメッセージはこの変更の対象外とする。

2026-11-16 に固定試験34件と型検査、bundle の登録検査を確認した。実 Codex SDK の試験では、結果が元の会話の画面用データに届いたことを確認した。標準検証は既存の `artifacts` 配下の退避コピーを試験として収集した時点で停止した。

## 7. 会話内での実行と折りたたみ

新しいソース調査は Web 検索と同じ会話内の読み取り操作として開始する。元の会話実行を結果採用まで進行中に保つため、既存の会話の進行中判定を自律側でも利用できる。既存の SDK・権限・差分生成を共用し、担当名の予告、別の仕事受付、完了通知を作らず、元の会話へ概要と表示専用の抜粋を一度だけ保存する。旧 task の登録版は既存実行を読み取るために残し、新規の候補から外す。

会話ログでは各ソースのコードブロックを初期状態で閉じる。ファイルパスと概要をそのまま表示し、各コードブロックはユーザーが個別に開けるようにする。表示専用データを読み上げと会話エージェントから分ける既存の契約を使う。

受入では SDK が返る前に会話が進行中で、予告・回答・完了通知が未出力であること、返却後に元の会話実行から回答が一件だけ採用されること、Web 検索の既存経路が通ることを確認する。表示はコードを開閉でき、一般の回答内のコード表示への影響がないことを確認する。

メモリー整理には既存の通常本文と発話イベントを渡し、概要は会話ノートの材料にできる。ファイルパス、コード、差分は会話画面専用の表示データに留める。受入では画面に実際の変更前後が届き、その回答を指す発話イベントとメモリー整理のメッセージ取得口には概要だけがあることを照合する。

2026-11-16 に、対象の固定試験と実 Codex SDK を使った会話の試験で、調査中の進行状態、回答１件、通常音声の要約１回、メモリー整理用の本文と発話イベントを確認した。Chromium ではパスを表示したまま２件の抜粋を初期状態で閉じ、クリックとキーボードで個別に開閉した。型検査、指示の生成結果、bundle、変更範囲のサイズ検査は成功した。標準検証は `artifacts/pursuit-integration-20261106/` の既存の退避コピーをテストとして収集した時点で停止した。

## 8. 会話を止めずに調査する

2026-11-17 の利用者の依頼により、§7 の会話内待機を既存の非同期タスクに戻す。会話のルーターと委任が選べるように `inspect.source` を再公開し、会話内で完了を待つソース調査のツールと指示を外す。調査を受け付けた会話は引き継ぎを伝えて終了する。継続の調査は `web-note.run` が担当し、既存の結果配送が元の会話に概要と表示専用の抜粋を一度届ける。抜粋の表示と通常本文の分離には §6 の契約を使う。

固定試験では調査の返却を保留し、その間に元の会話の次の音声入力を受け付け、返答の音声が用意されるまで確認する。保留を解いた後、元の会話のメッセージAPIで概要・抜粋を含む結果が一件だけ届くことを確認する。

`toolchain:inspect.source@4` を公開し、既存の `binding:inspect.source@2` を使用した。固定の調査応答と実 Codex SDK の両方で上記の通し試験が成功した。音声入出力は固定の認識・合成を使った。本番への反映と実機での再生は未実施。
