# タイマーの常設入口

目的: アーティファクト一覧にタイマーを常設し、未作成の状態でも時間を入力して開始できるようにする。

範囲: ランチャー、OpenUIの既存form表示とtimer APIの接続、開始後の既存時計表示。会話の担当指示・ツール・開始/取消API・DBは再利用する。新しい実行担当・ツールチェーン・Artifact種別は追加しない。

原因: 一覧がactiveTimersの結果だけからタイマー項目を作っており、0件では入口がない。未作成時には既存のtimerId必須画面を直接開けないため、登録済みform viewを使う。

依存順: 保存用のform JSON → 認証済みclient.startTimer → 保存済みreceipt → 既存時計タブ。フォームのボタン文言だけ共有FormResourceの任意項目で指定する。

完了条件: 空の一覧からタイマー画面を開き、開始・カウントダウン・取消・再オープンを確認する。入力拒否と開始失敗で架空の時計を開かない。部分試験、domain gate、ブラウザ結合、横断gate、差分点検を記録する。

開始時: 広範囲の既存未コミット変更あり。担当外は変更しない。既存時計とworkspace hookの部分試験をベースラインとして実行。

実装済み: 常設「タイマー」からOpenUI formの分・秒・名前を入力し、保存済みreceiptで既存時計へ切り替える。開始後と計測済みの再オープンは同じtimerタブを使用する。取消・通知・会話処理は既存経路のまま。

検証結果:

- 変更前の時計・workspace部分試験: 2件成功。
- 変更後の部分試験: 9件成功。90秒入力、0秒・負数・24時間超・小数の拒否、開始失敗で時計を開かないこと、タブの一意性を確認。
- timers gate: backend 14件、Web 32件成功。
- artifact gate: Web 49件成功。
- ブラウザ結合: 0件の状態からフォームを開く → 90秒の保存済み開始 → 時計 → 閉じる → 一覧から再オープン → 取消の保存確認 → 新規フォームの再表示まで成功。
- 全体gate: 境界・format・lint・型・build成功。backend等1,633件、Web335件、client317件、DesignSystem1,109件、ブラウザ46件成功・1件スキップ。タイマーの既存ブラウザ試験を含む8件すべて成功。全体所要553,406ms、検証中の入力変更なし。

修正した検証失敗: 初回の全体型検査で新規試験の配列要素がundefinedになり得る参照を検出し、optional accessへ修正。新規ブラウザ試験は共通CardTitleがheadingではないため、実際のタイトル表示を検査するよう修正。既存時計のボタン寸法取得は初回nullだったが、コード変更なしの個別再実行と最終全体検証で成功した。

差分点検: API・DB・LLMの指示・ツール定義に変更なし。発話や題材を判別する処理を追加していない。数値入力の変換・検査は既存APIの1〜86,400秒契約への接続に限定。既存の広範囲な差分は保持し、担当外へ編集していない。新規Artifact種別・専用render callback・ライブラリを追加していない。

証拠: [検証ログ](../verification/timer-launcher-2026-10-12)。live LLM・実機器は表示とAPI接続だけの変更なので未実施。ブラウザのAudioWorklet実マイク試験1件は既定のスキップで、実機器受入済みとはしない。

## 2026-10-13: 一覧のタイマー入口を一つに整理

目的: アーティファクト一覧の「タイマー」「タイマー: タイマー」の重複を解消し、新版の実装前に入口を一つにする。これから実装する新版の表示名を「タイマー（データドリブン）」と設計に指定する。

範囲・依存順: 既存ランチャーの保存済み項目追加を除去 → activeTimersQueryとuseOpenTimerを使い同じタイマー画面内へ保存済み選択を移す → 再表示の既存ブラウザ操作を更新 → 新版の設計へ入口・タブの名称を反映。完了条件は、保存済みタイマーが複数あっても入口とタブが一つで、開始・停止・再開・再読込み後の再表示が維持されること。今回はデータドリブン版本体の実装段階ではない。
