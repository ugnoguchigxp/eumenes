## 1. 目的と範囲

利用者が「これ」「いま開いているもの」と話したときに、会話エージェントが対象とその状態を把握できるようにする。内容の確認が必要なら、調査担当が表示対象やLARMの保存ライブラリを読み、根拠と確認範囲を伴う結果を返す。

二つの機能を独立した責務として実装する。

| 機能 | 入力と出力 | LLMの役割 |
| --- | --- | --- |
| A. 画面状態の共有 | 描画に使っている状態と操作状態から、表示対象・選択・処理状態・観測時点を取り出す | 収集・整形には使わない。通常の会話推論が状態を参考にする |
| B. リソース調査 | 質問、対象参照、必要ならAの観測を受け、保存物を探して内容を確認し、報告を返す | 検索語、読む対象・範囲・手段、内容の解釈、十分に調べたかを判断する |

対象は文書・PDF・画像・音楽・音声・動画・3Dモデル。初期受入はAと文書・画像のBを結合した経路とし、3D、音楽・音声、動画は媒体別の受入を追加する。初期受入の成功を全媒体の対応完了とは呼ばない。

以下は範囲に含めない。

- 保存物の編集・削除・生成、印刷や音声再生の自動実行。
- 画面変更のたびのLLM起動、全保存物の事前分析、全画面の常時撮影。
- 調査のための会話担当の交代、専用の新しいチャット、別のタスク実行基盤。
- 原本の複製ライブラリ、独自の文書版履歴、分析結果の長期Memoryへの自動登録。
- 現行の認証・承認方式の変更、モデル名による機能判定、未確認の接続先への自動転送。

## 3. A 画面状態の共有

### 3.1 収集と解釈の境界

表示に使うsource、登録された部品の状態、選択・編集中の位置から、共有を許可した項目だけを取り出す。既存の業務状態を正本とし、エージェント向けに別の業務状態を管理しない。ブラウザー内だけの選択・下書きは、その画面セッションの観測として扱う。

LLMを使わないものは、表示対象の識別、件数、処理中・完了・失敗、ページ・再生位置、選択範囲、未保存変更の有無、既に画面に出しているエラーである。題名から画像の中身を推測したり、生成完了から内容の正しさ・完成度を推測したりしない。

共通のフォーム・一覧・プレイヤーは共通部品から投影する。3Dや描画canvasなどの固有状態だけを所有domainのWeb adapterが補う。生成したUIにも登録部品とsourceの契約を適用し、任意のDOM全体、内部store全体、隠れた入力値を読み出す機構にはしない。

画面の状態は実ピクセルの検査結果ではない。崩れ・重なり・canvasの描画内容を確認する依頼には、必要な範囲の画像取得をBの調査手段として使う。通常の状態共有にPlaywrightや撮影を必須にしない。

### 3.2 観測の論理契約

以下は新契約に含める情報。項目名、APIパス、保存形式の最終形は実装準備で確定し、既存の`viewing`入力との互換を保つ。

| 情報 | 意味と正本 |
| --- | --- |
| 会話と画面セッション | 認証済みの会話と、送信元のブラウザー画面を識別する。別画面の観測を混ぜない |
| 観測参照・連番・時刻 | ホストが観測参照を発行する。画面内の連番、画面の観測時刻、ホストの受付時刻を区別する |
| アーティファクト | 登録の識別子・定義版・表示名・現在の表示モード。定義版と内容の版は別 |
| 対象参照 | 選択中・表示中のリソース、または未保存作業への参照。未選択なら未選択を表す |
| 公開状態 | 読込・処理・エラー、表示ページ、選択範囲、再生状態など、登録されたschemaで許可した値 |
| 内容の版 | 保存物の版、編集中の下書きの版。状態を読んだだけなら原本未取得とする |
| 取得可能な情報 | 本文、画像、音声区間、形状情報など、その対象から取得できる表現。対象のデータ種別と推論モデルの入力能力は別に示す |
| 確認範囲・鮮度 | 全体・一部、表示なし、未対応、取得失敗、期限切れを区別する。情報がない場合に空の正常状態を作らない |

通常会話には、表示対象、状態、観測時点、調査へ渡せる短い参照だけを渡す。長い本文、全行、全フォーム値、媒体bytesは自動で添えない。詳細な状態は同じ観測参照から調査担当へ引き継ぐ。秘匿項目は省略し、公開可否をLLMに判断させない。

文書の未保存部分を調べる場合は、保存済み原本を代わりに読ませない。既存の共有下書きに版付きで到達できればそれを使い、ブラウザーだけにある内容ならその時点の共有可能な範囲を固定して参照化する。固定できなければ「未保存部分は未取得」と返す。観測のために保存・上書き・公開しない。

### 3.3 発行、保持、会話への接続

1. 登録済み画面のmount・選択・処理状態などが変わったときに観測を更新する。再生時刻やスクロールは描画フレームごとの送信を避け、送信時に正確な位置を採る。意味の要約・重要度判定は行わない。
2. テキスト送信と音声の入力確定に、同じ収集口の観測を添える。送信前に別の推論やネットワーク往復を必須にしない。音声では発言を会話へ確定した時点の観測であることを保持する。
3. ホストは登録、型・容量、対象、接続bindingと参照権限を検査し、その入力に使う観測を固定する。文字列や画面由来の値は参考データとして置き、SystemContextへ混ぜない。
4. 振り分け、通常返答、委任で同じ観測を参照する。用途別に短く投影しても、対象や版を取り替えない。既存の`stateLines`全体を無制限に返答へ入れる変更にはしない。
5. 常駐エージェント向けの最新版は、画面セッション単位の期限付き状態として扱う。状態更新だけで推論や自発発話を起動しない。既存の判断時点で参照し、出所画面を特定できない場合は現在画面として採用しない。

発言に固定した観測と、その後に更新された最新版を分離する。利用者がAからBへ画面を切り替えても、Aを対象に開始した調査の対象をBへ置き換えない。更新順序の逆転は連番で拒否する。画面終了・再接続・期限切れを検出し、過去の観測を「今」として示さない。

最新状態の保持と、run・委任に固定した小さな観測の保持を分ける。後者は既存の実行入力・参照管理に接続し、元発言の撤回とともに利用を止める。新しい永続的な画面履歴は作らない。具体的な保存カラムやmigrationの要否はP0で既存の入力保存形式に照らして確定する。

### 3.4 Aの完了条件

- 状態を採取・検証・整形するための追加LLM呼出しが0回である。
- 観測の追加だけではProviderへの通信、生成処理、業務状態の更新が起きない。
- 表示対象がある場合と、未選択・読込中・エラー・作成途中を区別できる。
- テキスト、音声、通常返答、振り分け、委任へ同じ対象と観測版が届く。
- 別画面・古い連番・終了済みセッションの状態を現在の状態として採用しない。
- 旧`viewing`入力とCLIは継続利用できる。CLIにWebの現在画面を暗黙に混ぜない。

## 4. B サブエージェントによるリソース調査

### 4.1 担当の公開と実行

会話側の入口は一つの「リソース調査」ツールチェーンとする。bundleにprofile、実行用Skill、package、公開toolchain、binding、引数・結果schemaを登録し、applicationのadapterが所有domainの公開操作へ結ぶ。[登録手順](../../docs/toolchain-extension.md)に従い、旧固定runtime-mapへの個別追加は行わない。

実行は既存の作業台帳と選択済み担当の子実行へ接続する。会話の宛先を変更するsession型にはしない。検索・読取・分析の選択はこの担当が行い、同じ仕事を再計画する上位サブエージェントや媒体ごとの会話入口を初期段階で増やさない。

profileには調査担当の役割と責務、実行用Skillには検索・読取・根拠確認・報告の手順と停止条件を置く。SystemContextは既存の合成機構でこれらとツール契約を組み合わせる。画面観測、元依頼、取得した本文・媒体、実行状態は都度の入力として渡し、固定指示を重複させない。

| 接続 | 契約 |
| --- | --- |
| 会話から担当へ | 元依頼、具体化した質問、対象の短い参照からホストが解決した参照、必要な画面観測、既存の期限・取消と権限 |
| 担当から取得処理へ | 実行時に利用可能な検索・読取・媒体処理、型付き引数、有限の回数・容量・時間予算 |
| 担当からモデルへ | 固定指示と区別した依頼・資料・実内容。媒体入力は実際の接続能力を検査する |
| 結果から会話へ | 回答、根拠、確認範囲、不足、対象参照。既存の結果採用と報告通知を通す |

新しいtoolchainとschemaのID・初版、bindingの実行分類はP0で登録契約と照合して一覧化する。既存の`resource.read`を同名で二重登録せず、互換のtext投影を残した新版として扱う。公開済みrevisionは変更しない。ホストがactive版を自動提示する利用側もあるため、新版公開時には既存の担当が受ける版と出力を必ず検証する。

### 4.2 探す、読む、解釈する

担当には、以下の操作を必要な権限とともに提供する。これらは担当内部の操作であり、会話エージェントの固定ツールにはしない。

| 操作 | 再利用と拡張 |
| --- | --- |
| 検索・一覧 | 既存の種類登録と各domainの一覧を使う。LARMだけにある保存物も対象にできるよう接続する。結果に検索範囲、走査済み範囲、続き、部分失敗を含める |
| 対象の確認 | 参照、所有domain、接続binding、版、利用可能な表現を解決する。題名の一致だけで対象を同一視しない |
| 内容の読取 | 既存`resource.read`を拡張し、本文区間・画像・時間区間などを取得する。メタデータと実内容を区別する |
| 媒体処理 | 必要なページの画像化、画像の縮小、音声・動画の区間取得、3Dのレンダリング等。形式の変換はコード、意味解釈はLLMが担う |

表示中の対象が指定されていれば直接読み、未知の対象なら検索する。検索語、候補の比較、読む範囲、必要な分析と終了はLLMが選ぶ。コードは形式、認可、容量、期限などを検査する。発話の語句や個別の再現例に対応する専用分岐を追加しない。

`resource.read`の現在の短いtextは概要表示として維持するが、全文・実内容を読んだ証拠にしない。長い内容は区間と続きを返し、旧契約の600 tokenの先頭切出しだけで調査を終わらせない。全文が必要なら予算内で順に読み、不足すれば部分結果として返す。

### 4.3 LARMだけにある保存物の解決

原本の正本は所有する保存先に置く。文書、画像、音楽、動画、3Dの各domainが、その種類のLARM APIを読み、applicationが参照・読取portを調査へ接続する。下位domainからdialogueやagent-runtimeを参照しない。

現在の同期`resolveInTransaction`に、外部HTTP読取を追加してはならない。外部一覧・詳細をtransactionの外で読み、接続bindingと対象を照合してから、ホストが会話・実行に結び付いた参照を確定する。原本bytesの複製は不要で、参照に必要な識別・版・取得済み範囲だけを保持する。

参照の同一性には、所有domain、接続binding、外部IDを含める。接続を切り替えた後に同じ外部IDを持つ別の保存物を読ませない。既存の`eumenes://`と会話台帳へ接続し、未解決の外部URLや任意の文字列を取得権限として使わない。

検索は、まず既存の一覧とAPIが提供する絞込み・続き取得を使う。内容に関する質問は担当が候補本文を確認する。新しい全文検索・Embedding索引を初期実装の前提にせず、一覧で扱えない規模が実測された場合に別途設計する。未走査や一部の接続失敗を「保存物がない」という結果に変換しない。

### 4.4 媒体ごとの取得と推論

| 媒体 | 取得するもの | 担当の推論と報告の条件 |
| --- | --- | --- |
| 文書 | 原文・見出し・選択範囲・版 | 読んだ本文の位置を根拠にする。保存済み版と未保存下書きを区別する |
| PDF | 必要なページの本文、必要ならページ画像 | 本文抽出・OCR・ページ画像のどれを使ったか、対象ページと欠落を残す。既存scratch/文書処理で届かない部分だけ追加する |
| 画像 | 実画像または指定領域。寸法・変換情報 | 既存の画像正規化と推論adapterを担当へ接続する。生成依頼だけを見て描かれた内容を答えない |
| 音楽・音声 | 原音または時間区間。必要なら文字起こし | 発話内容と音楽的な特徴を区別する。音楽の印象を文字起こしだけで分析したとはしない。音声理解能力が未接続ならその範囲を未対応とする |
| 動画 | 時刻付きフレームと音声区間、または対応する動画入力 | 抽出時刻・間隔・未取得区間を残す。数フレームの確認から動画全体の連続動作を保証しない |
| 3D | 形状データ、検査結果、指定視点の画像 | レンダリング画像からの見た目の解釈と形状検査の結果を分ける。単位・寸法・印刷可能性を画像だけから確定しない |

媒体bytesは取得参照からホストが解決し、担当の次の推論へ入力する。URLやBase64を通常のtext資料へ埋め込んだだけでは入力完了としない。元の参照・版・変換・範囲と、実際に媒体を入力した推論要求・採用結果を対応付ける。

画像には既存の能力確認と送信経路を再利用するが、担当用の呼出しで同じ契約が有効かを検証する。現行の会話契約は文字と画像が中心である。音声・動画は、保存APIからbytesを取れることと推論が理解できることを別々に確認し、発見したサービスの契約に従って接続する。具体的な能力名や未提供のAPIを先に仮定しない。

複数の分析能力が必要な場合も、一つの調査担当の判断と既存の実行予算に収める。利用する接続は保存設定と実行時の能力情報から決め、モデル名の固定、対応不明時の無言の転送、主会話モデルの設定変更を行わない。

### 4.5 根拠と結果の返却

短い自由文の要約だけにせず、既存の根拠付き報告と`ExecutionResult`を拡張する。

| 返す情報 | 用途 |
| --- | --- |
| 回答と具体的な観測 | 主会話が利用者の質問へ答えるための内容。必要な原文抜粋や数値を含める |
| 根拠参照 | URI、所有者、接続binding、原本版またはdigest、取得時刻。ホストが発行し、モデルに創作させない |
| 根拠の位置と種類 | 本文区間・ページ、画像全体または領域、音声・動画の時間区間、3Dの検査・視点。メタデータ、原文、変換結果、モデルの解釈を区別する |
| 取得・入力の証跡 | 取得した資料と、担当の推論へ実際に渡した資料の対応。入力成功は内容の正しさの保証ではない |
| 確認範囲と制約 | 検索した範囲、読んだ範囲、残り、未対応、失敗、矛盾、予算到達 |
| 続行用の参照 | 対象、版、取得済み区間、報告への参照。追加質問で同じ対象を調べ直せる |

報告内の参照が実際の取得記録に存在し、範囲が記録と一致することをホストが検証する。原文引用は取得した区間と照合する。画像・音声の解釈を、textの引用照合だけで正しいと認定しない。資料中の命令や任意のURIを、新しい権限・上位指示へ昇格させない。

会話には回答に必要な報告を渡し、原本全体や全媒体を自動で再投入しない。会話エージェントが担当の報告を読んだことと、自分の推論で実媒体を見たことを区別する。後続会話でも対象と根拠を保持し、詳細が必要になれば同じツールチェーンへ追加調査を依頼する。完了した子プロセスが常駐していることを前提にしない。

資料を新たに作ったときの`finish.links`と、調査で参照した既存資料の根拠を区別する。読んだだけの原本を「今回作成した成果物」として登録しない。結果表示には既存の報告・リンク・リソース表示を使い、新しい専用Artifactは初期必須にしない。

### 4.6 版、失敗、予算と停止

- 発言時の画面観測と、読取時の原本版を保持する。期待した版を取得できなければ不一致を返し、黙って最新版へ差し替えない。旧版を保持する契約がない保存先に、旧版取得を要求し続けない。
- 調査中に新しい版ができても、取得済みの固定資料に対する観測を「最新版の内容」へ読み替えない。権限・元発言の撤回・取消・期限切れは、固定資料やキャッシュが残っていても既存の採用検査で拒否する。
- 検索で候補がない、検索範囲が一部、取得できない、入力能力がない、解析できない、予算が尽きた、を区別する。契約上の完了・部分・失敗へ対応付ける。空の正常結果で隠さない。
- 問いに必要な根拠が揃ったら報告する。無関係な全件分析、独立した評価担当の追加、意味検証の反復を自動で行わない。回数・容量・時間の上限はホストが強制する。
- 資料は原本版、範囲、変換条件をキーに必要な分だけ一時保持する。分析結果を再利用する場合は分析条件・入力能力の契約も識別し、読取と採用の双方で有効性を再確認する。寿命切れは明示し、無断の再生成で隠さない。
- LARM credentialはbackend内に留める。外部待ちでは不要な推論資源を保持しない。音声を解析・取得しても、backendや検証用ブラウザーから音を出さない。

| 所有箇所 | 変更する責務 | 既存機構だけで満たせない根拠 |
| --- | --- | --- |

| capabilitiesとapplicationの登録adapter | 調査担当のbundle、利用可能な操作と入出力の結線 | 会話から選べる保存リソースの調査担当が必要。既存の委任基盤を使う |

SQL・業務処理・試験は所有domainに置き、applicationは公開portの結線を担う。新しい汎用フレームワークや、UIごとの専用エージェントを追加しない。媒体差のコードは外部形式への接続と変換に限定する。

## 6. 実装の順序と依存関係

AはBの実装前に完成させて検証できる。Bの画面を使わない検索はAと独立に部分検証できるが、表示対象への質問の受入にはAが必要である。各段階は必要な接続と試験を揃えてから、部分、結合、通しの順に確認する。

| 段階 | 作業と依存 | 完了条件 |
| --- | --- | --- |
| P0 契約と基準 | 現行版と未コミット差分を確認。観測schema、共有項目、保存場所、寿命・容量・更新頻度、調査bundleのID・版・binding、媒体の対応表を確定。既存の失敗をfixture化 | A/Bの境界、変更する公開契約・migrationの要否、試験入口と予算がレビュー可能。推論能力の未確認箇所が明示されている |
| P1 Aの収集と受付 | 既存viewingを拡張。共通画面ホスト、文書・画像・3Dを代表に、選択・作成途中・エラーを収集。テキスト・音声の入力受付と観測固定を接続 | Aの部分・API結合試験が通る。追加LLM呼出し0、選択した対象と固定した版が一致 |
| P2 Aの利用 | 通常返答、振り分け、委任、常駐判断へ同じ観測の必要部分を渡す。期限切れ・複数画面・旧入力・CLIを確認 | 読取を呼ばなくても表示対象と客観状態を把握できる。画面変更だけで推論が増えない |
| P3 Bの文書経路 | 既存の委任へ調査bundleを接続。LARMの一覧・本文、外部参照、範囲と続き、根拠報告を実装。P0に依存し、画面連携はP2に依存 | 未表示のLARM文書と表示中の文書を調べ、主会話に根拠付きで返す。担当の交代、原本更新、専用の基本ツール追加がない |
| P4 Bの画像経路と初期受入 | 共通の媒体資料契約を通し、画像の実内容を担当の推論へ渡す。P3の根拠・採用を再利用。PDFの図表は必要なページ入力を確認 | A＋Bの文書・画像の通し試験と実LLM受入が成功。画像にだけある情報に答え、後続質問で再取得できる |
| P5 Bの3D経路 | 既存の保存モデル取得・viewerを再利用し、形状情報・レンダリング・検査結果を根拠へ結ぶ | 見た目の分析と形状の検査結果を分け、表示モデルと別の保存モデルを比較できる |
| P6 Bの音楽・音声・動画 | 保存物の参照、区間取得、実行時に確認した理解能力、時間付き根拠を接続。動画をresource-kindへ登録 | 媒体ごとの対応能力・未対応・部分取得が正しく報告され、必要な区間だけで依頼へ回答できる |
| P7 全体の受入と運用資料 | 対応した全媒体、利用側domain、取消・失効・容量・後続質問の回帰を確認。登録・読取・画面共有の追加手順をdocsへ反映 | 実装済み、fixture、live、実画面・実機器の確認範囲を区別した記録があり、残る未対応を列挙できる |

寿命や容量の具体値、サーバーへ保持する観測の方式はP0の決定事項であり、無制限の暫定実装を先行させない。意味判断・優先順位・新しいフォールバックが必要になった場合は、その時点で設計差分を示す。新規サービスやモデルの導入は、今回の方針合意だけで利用可能とみなさない。

## 7. 検証計画

### 7.1 Aの部分と結合

| 入力・状況 | 観測可能な合格条件 |
| --- | --- |
| 文書・画像・3Dの選択、対象なし、読込中、エラー | 登録された状態だけを出し、対象や成功を捏造しない。LLMとProviderの呼出し回数は0 |
| 選択範囲と未保存編集 | 保存版と下書き版が別に見える。固定した下書きがないときは原本で代用しない |
| テキスト送信と音声commit | 同じ収集口を通り、run・振り分け・返答・委任の観測参照が一致する |
| 送信直後のAからBへの切替、更新の逆転 | 送信済みの依頼はAのまま。古い連番で最新版を上書きしない |
| 画面終了、再接続、二つの画面セッション、期限切れ | 出所を混同せず、古い情報を現在表示中として渡さない |
| 設定・秘密入力を含む画面、不正参照、容量超過 | 公開項目だけを採用し、秘密・未許可参照を拒否する。省略範囲や失敗が分かる |
| 旧クライアントとCLI | 旧viewing契約が動き、観測がないことを正常に扱い、他の画面を勝手に参照しない |

### 7.2 Bの部分と結合

| 入力・状況 | 観測可能な合格条件 |
| --- | --- |
| ローカルworkspaceにないLARM文書 | 一覧から発見し、編集workspaceを作らず本文を読み、版・範囲付きで返す |
| 答えが先頭の短い概要より後ろにある文書 | 続きの取得が行われ、取得した範囲にある根拠だけで答える |
| 画像のメタデータと実画素で異なる情報 | 実画像が担当の入力に含まれ、画素にある情報を根拠にする。メタデータのみなら未確認を報告する |
| 音声・動画の一部区間だけを取得 | 根拠の時刻と取得範囲が一致し、未取得部分を確認済みにしない |
| 接続切替、同じIDの別保存物、読取中の版更新 | 期待したbinding・版を確認し、不一致を明示する。別物や別版に黙って置き換えない |
| 一つの保存先の失敗、未走査の続き、理解能力なし | 部分結果・取得不能・未対応を区別し、空の正常検索や推測の分析で埋めない |
| 原文・画像内の命令、不明なURI・根拠参照 | 資料を指示や権限に昇格させず、未取得の根拠を報告に採用しない |
| 取消・期限切れ・元発言撤回後に結果が到着 | 子・親・会話の既存採用検査で拒否し、成功通知や後続の自動発話へ混ぜない |
| 新版resource.readの公開 | 調査担当の新しい出力が使え、既存担当のtext読取・権限・回数制限も維持する |
| 後続質問 | 同じ対象と報告を参照し、必要な範囲だけ追加調査する。期限切れは明示する |

### 7.3 通しの受入

固定fixtureでは、Webの公開入力から、担当選択、参照引継ぎ、取得、担当への資料入力、報告採用、主会話の回答までを一続きで確認する。次を初期受入ケースとする。

1. 文書の途中を選択して質問し、その範囲を対象として回答する。
2. 画面に出していないLARM文書を探して質問に答え、後続質問で別の箇所も確認する。
3. 画像を選択して、題名や生成依頼に書かれていない内容を質問する。
4. 調査中に画面を切り替えても、元の対象の結果として戻る。
5. 調査取消・権限失効と遅い結果を組み合わせ、未採用の内容が回答に出ない。

実LLMでは、対象名・言い回し・配置・内容を変えたケースで同じ経路が選ばれることを確認する。モデル応答を固定したfixtureの成功を、実LLMの意味理解の成功とは扱わない。ログの「完了」だけでなく、実際に担当へ渡った媒体の識別・版・範囲と最終回答を対応付ける。検証用の非機密資料を使い、通常ログには本文・画像・音声・秘密を保存しない。

3D、音楽・音声、動画はP5・P6で同じ通し経路に追加する。音楽・動画の解析だけでは再生しない。再生機能への影響を検証する必要が生じた場合は、利用者が開いたEumenes Web画面での実機器受入を別に記録する。

### 7.4 実行入口と結果の扱い

実装時には下表の対象を試験ファイルとして先に用意し、部分試験とapplicationの結合試験を明示して実行する。新規の試験・bundleのファイル名はP0で確定する。以下は実行計画であり、本書作成時に製品試験を実行した記録ではない。

| 段階 | 実行入口と対象 | 期待結果 |
| --- | --- | --- |
| 部分 | `bun test ./api/domains/<owner>/test/<対象>.test.ts`、既存Web試験runnerの対象ファイル指定 | schema、参照、版、容量、状態遷移の正負ケースが成功 |
| 登録 | `bun run toolchain:bundle -- check <新規bundle>`、capabilitiesのfresh・旧版seed・再seed試験 | 依存・schema・版・公開条件が一致し、旧revisionを変更しない |
| 結合 | `bun test ./api/application/<対象>/<結合試験>.test.ts` | 公開入力から担当と主会話への返却まで成功・拒否・取消が一致 |
| Aのdomain検証 | `bun run verify -- --domain artifact --domain dialogue --domain conversation --domain voice-dialogue --domain resources`に、変更した表示側domainを追加 | 所有箇所と利用側の静的検査・試験が成功 |
| Bのdomain検証 | `bun run verify -- --domain capabilities --domain agent-runtime --domain tool-runtime --domain resources --domain dialogue --domain inference`に、文書なら`markdown`・`docling`、画像なら`image`・`larm`などを追加 | 調査の基盤と媒体側、既存の利用側に回帰がない |
| ブラウザーfixture | `bun x playwright test <対象の明示したspecファイル>`。Aの観測・文書選択・画像入力・媒体画面を段階別に選ぶ | 実clientと画面操作を通し、公開観測・選択・切替・エラーが一致 |
| 必要時の全体確認 | 全体の境界・型・build等の確認が必要なら、理由と対象を記録して`bun run verify:all`。横断変更だけを理由に必須にしない | 全体を確認した範囲と結果が明確。ブラウザーE2Eは別実行とし、成功に含むと誤記しない |
| live | 保存済み設定をbackendの読み取り専用操作から参照し、対象媒体の実LLM・実LARM読取を隔離した検証会話で実施 | 実際の取得、入力能力、判断、報告、回答の対応が確認できる |

各verifyは影響する利用側domainとapplication結合試験を自動で全て選ぶわけではないため、変更した接続から選択範囲を確定する。[検証手順](../../docs/toolchain-extension-verification.md)と[検証の共通規則](../../docs/verification.md)を使う。

サーバーの起動・停止・再起動は明示許可が必要であり、ブラウザー試験の設定による自動起動も含めて確認する。既存のfixture方式や起動済み環境を使える場合はそれを使う。fixture、live、利用者の実画面・実機器の結果を分け、省略は理由を記す。

検証中は入力ファイルを編集しない。失敗時は相関IDで原因を絞り、変更した条件を示してから再実行する。同じ目的の3ラウンド、または新しい根拠のない同一失敗では進め方を見直す。期待値を弱めて通さず、続行根拠がなければ差分・未解決事項・続行条件を報告する。

## 8. 完了判定と残作業

設計書の完了条件は、A/Bの境界、再利用と拡張の根拠、実装の依存順、段階別の合格条件が揃うこと。製品の完了判定はAの条件、Bの各媒体の受入、既存利用側の回帰、参照・取消・失効の検査を満たした範囲で行う。

実装時の記録では、基準commit・対象差分・登録版、実行した試験、入力の固定、成功・失敗・未実施、実内容を読めた媒体と範囲を残す。最後に無関係な差分も区別し、個別発話への依存やLLMの判断をコードで代替する処理が増えていないか確認する。

実装段階で更新する主な資料は[リソースURI](../../docs/resources.md)、[ツールチェーン](../../docs/toolchain.md)、[OpenUI Artifact](../../docs/openui-artifact.md)、[画像入力](../../docs/chat-images.md)、[登録手順](../../docs/toolchain-extension.md)と媒体別の検証記録とする。

## 9. 実装記録

発言時の経路では、登録済み画面から表示モード・表示段階を採り、文書・画像・3Dのadapterから選択や処理に関する状態を補う。文書はWebへ届いた下書きの版と未保存の印を共有する。共通の収集口で画面セッション、連番と観測時刻を付け、テキスト送信・音声入力確定の既存 `viewing` に添える。

ホストは既存runのJSON欄とリソース参照欄を使う。DB移行は不要。会話への投影時に公開済みの画面・表示モードを照合し、リソースの参照先と画面の登録adapterの対応を確かめる。通常返答と振り分けに同じ投影を使う。画面セッションと連番は発言に固定した観測の識別に使い、別の発言への採用条件にはしない。

今回の到達点は、通常の返答のモデル入力へ送信時の画面状態が届くこと。固定応答のAPI試験で、状態の有無にかかわらず通常返答のモデル呼出しが1回であることを確認した。常駐判断向けの最新版配信・期限制御、ブラウザー内だけにある編集位置と選択区間の共有、Bの調査担当への詳細な観測引継ぎは今後の実装範囲。

検証の基準は `8d900d77`。対象を指定したWebの固定試験73件とAPIの固定試験45件は成功し、最終差分の全体型検査は3,305ファイルで成功した。一括検証は元の作業フォルダーでは旧検証コピーの検出で停止し、固定コピーでは利用側の依存境界違反と既存Artifact UIのlint違反で停止した。別実行したドメイン試験は1,246件成功、2件失敗。自律調査の候補一覧が空になる失敗は変更前の登録経路でも再現し、他方はCLI結合試験のループバック待ち受けを開始できなかった。稼働環境のWeb画面、実LLM、実機器の受入は未実施。

## 10. LARM保存文書の調査

[`resource-research` bundle](../../api/domains/capabilities/bundles/resource-research.bundle.json)の `toolchain:resource.research@1` を、`package:resource.research@1`、`binding:resource.research@1`、`adapter:archive-research@1` に接続した。会話は既存の検索と委任で選択し、一つの調査担当が既存の子実行を使う。文書の検索語と読む箇所は担当が選ぶ。

担当の `archive.search@1` は保存先の一覧を取得し、指定された語を題名・名前空間・パスと照合する。結果に続きと省略件数を含める。同期でローカルの登録を引く `resource.read` の互換性を保つため、外部参照の発行と根拠付き区間取得には担当専用の `archive.read@1` を使う。参照は発行した実行とLARM接続に限り、検索で取得したETagと本文のETagが一致する場合に読取結果を採用する。原本取得は保存先のGETを使い、文書を開く操作や保存操作は発行しない。

根拠には原本の文書ID、題名、ETag、取得時刻と読取区間を持たせる。区間はCRLFをLFに揃えたMarkdownのUTF-16オフセットで、先頭を0、終端を区間外とする。本文の抜粋を既存の根拠照合に使い、完了通知と会話での結果確認へ版と範囲を渡す。通知には先頭の根拠を載せる。調査対象の全本文と接続の識別情報は会話へ転送しない。

基準 `309cede8` の作業差分で、一覧の2ページ目にだけある文書を発見し、本文の後半を読んで、版と範囲が通知と会話の入力に返ることを固定試験で確認した。未発行参照の拒否、版の不一致と接続の変更、編集workspaceを作らないことも確認した。登録チェック、関連固定試験50件、全体型検査が成功した。対象domainの一括検証は既存の `executionCommands` のサイズ制限で停止した。保存済み設定を使った実LARM読取は接続不可のため未確認。

この段階は保存文書の題名などから候補を探し、指定されたMarkdown区間を読む。全文索引、表示中の下書きからの直接読取、PDFのページ画像やその他の媒体は後続範囲。
