## 目的と根拠

発話中、認識待ち、送信済みを区別し、「止まって見えた後に突然送信される」挙動をなくす。既存ログでは発話終了待ち約1.5秒、ASR中央値1.37秒、最大34.67秒。途中表示57回に対し確定認識15回が別に実行されていた。遅い例ではローカル15秒タイムアウト後、クラウド約19.5秒。途中結果の消失と遅延した自動送信は表示・所有権・通信の問題でもある。

2026-11-15 に保存済み接続先の catalog と OpenAPI を読み取り確認。現在の ASR は `speech.stt` / `openai.audio-transcriptions.v1`、`POST /v1/audio/transcriptions`、JSON応答を公開。追加音声を受ける逐次セッション契約は公開されていない。ローカルに残る別の旧サービスには WebSocket があるが、現行接続先として採用しない。存在未確認のAPI、モデル名の固定、無断の接続先変更は行わない。

## 実装範囲

1. ブラウザーの入力状態を一元化。発話開始で即座に「聞き取り中」、録音確定で「文字起こし中」、10秒を超えた結果は「下書き」、受理後は「送信済み」。10秒は正常中央値を十分上回り、観測された15秒のフォールバックより前に自動送信を解除する操作上の期限。発話の意味や終了を判定する閾値ではない。
2. 旧preview API、累積録音の定期再送、preview専用状態を削除。現行Providerでは1つの録音に1つの論理認識を実行。既存の長音声分割、設定された経路、推論の権限・receipt検証は維持。音声を短く機械分割して意味・精度を犠牲にする代替方式は導入しない。
3. 認証済みSSEで認識結果を直接届ける。録音受付と結果購読を分離し、購読時には現在状態を必ず送る。購読の切断は自動再送・自動commitをせず、下書きとして結果を再取得する。取消・世代変更後のイベントは採用しない。画面全体のキャッシュ再取得を認識完了の条件にしない。
4. 手修正で自動送信権を失う。後続の認識結果が手入力を上書きしたり、修正前の発言を送信したりしない。手修正時はマイクを休止し、送信済み録音の受付を待って未送信の認識だけを取り消す。再生中の回答は維持する。短すぎて破棄した録音は結果を取得しに行かない。下書きの送信は既存の明示送信操作を使う。失敗・取消時に仮の文字を残さない。マイク休止時は確定済み結果を保持する。
5. 音声・途中状態はメモリに置く。確定認識と実行の権限記録のみ既存の永続化を使う。録音の滞留は、既存のブラウザー送信待ち上限に加え、backend受付でも同一セッション3件・全体16件に制限する。1件の既存上限は4 MB。重複受付を先に確認して冪等性を維持する。TTSの先行合成・順番再生、出力中の入力制御、Liveモードとの排他は維持。

## LARM側の追加仕様（未実装）

音声の追加と途中結果を同じ推論状態で扱う契約が必要。catalogから発見するセッション作成・追記・確定・取消、PCM形式とレート、単調な音声位置とイベント番号、全文を更新する暫定結果と最終結果、容量・期限・切断の契約を公開する。確定時に全録音を再認識する方式では終了待ちは消えないため、その区別も公開する。認証情報はEumenes backendに留める。仕様を確認してから専用の最小adapterを既存の推論受付・receipt検証に接続する。現行公開APIで話中の文字生成まで改善済みとは扱わない。
