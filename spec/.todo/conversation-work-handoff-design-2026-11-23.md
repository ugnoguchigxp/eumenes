## 2. 会話から担当へ渡す契約

### 2.1 担当の役割と画像

直接端末版の公開bundleの要約を「Claude Codeは対象プロジェクトのコードやファイルを読み、編集と試験を行う開発エージェントです。この担当を選ぶと依頼本文はClaude Code本人に届きます。対象・欲しい結果・利用者が指定した条件を書いてください。端末の選択と起動はEumenesが行います」とする。管理型には、専任担当がClaude Codeの実行・質問・結果を管理する旨を書く。共通の委任指示にも、選択した宛先を読者として本文を組み立てることを明記する。初回検索と後続ターンの要約に同じ役割を残す。[直接端末の登録](../../api/domains/capabilities/bundles/terminals-screen.bundle.json)・[管理型の登録](../../api/domains/capabilities/bundles/claude-code-task.bundle.json)・[委任指示](../../api/domains/dialogue/contexts/local/talk-delegate.context.toml)

利用者の指定が担当・改修対象・作業手段のどれかは会話LLMが文脈から解釈する。登録説明と履歴で決まらない関係を既存の `read_world`、必要に応じて `world.query` で読む。その間も選択済みの開発担当、素材、依頼の下書きを保持し、照会が終われば同じ依頼に戻る。Worldの記述は実行権限を与えない。名称を本文から機械的に消す処理は設けない。[担当候補の投影](../../api/domains/dialogue/service/routed-talk-work.ts)・[World照会](../../api/domains/capabilities/bundles/world-query.bundle.json)

会話内の画像番号を既存の生成画像参照から所有元のURI・ID・版に解決し、確認対象の仕事と一緒に保存する。ローカル端末への配送時は、ホストが既存の画像読取操作でその版を検証し、承認済みの仕事だけが使う読取用ファイルにして実行先から開けるパスを渡す。担当端末にAPI認証情報を渡さない。別ホストのrunnerでも、その実行先に素材を用意できた時だけ依頼を開始する。取得前に画像が削除・差替えされたら素材の再選択を求める。同名画像を選び直したり再生成したりしない。配置先が結果を左右し、履歴で決まっていればその条件を使い、未決ならその点だけ確認する。[生成画像と版](../../api/domains/dialogue/service/generated-images.ts)・[画像読取](../../api/domains/image/controller/index.ts)・[実行時の参照](../../api/domains/tool-runtime/contracts/task-execution.ts)

### 2.2 同意を届け、端末で続けた結果を戻す

1. **質問を保存してから尋ねる。** 直接端末の完了通知から固定4択を削除する。報告だけなら成果・残件で終える。判断が要る場合は、仕事ID・質問ID・設計版・次の操作・影響範囲を既存の仕事台帳に保存する。Webと音声は同じ版の質問を提示する。[現行の完了通知](../../api/application/work/claude-code-reports.ts)
2. **返答を操作に結び付ける。** 通常の確認に加え、担当の質問待ちも会話の返答処理へ渡す。LLMが了承・訂正・取消・別件を解釈し、ホストが未消費の質問と対象版を照合する。回答の消費と受付を単一writerで保存し、既存の回答操作で元の担当を再開する。二重回答や送信結果不明時は同じ操作IDを照会する。コミット、実装、再起動はそれぞれ提示した範囲にだけ同意が及ぶ。[確認への返答](../../api/domains/dialogue/service/confirmation-decision.ts)・[仕事への回答操作](../../api/domains/dialogue/service/talk-work-controls.ts)
3. **再開先を確保する。** 新規の継続案件は、登録作業場所で質問・回答・取消の実接続受入を通した管理型へ段階移行する。既存の直接端末では、元の仕事と端末セッションを参照する継続依頼を作り、回答を新しい操作IDで同じ端末へ1回送る。宛先消失時は元の仕事に「再開先なし」を残す。古い了承の再利用はしない。[管理型の契約](claude-code-managed-task-design-2026-11-15.md)・[端末への配送](../../api/application/work/terminals-adapter.ts)
4. **端末での続きも仕事に残す。** 元の依頼から開いた端末は「この仕事の続き」と仕事名を表示する。手入力の送信時に仕事・所有者・セッション・個々の入力ターンを対応付ける。通常入力への切替後は元の案件への共有を終了する。手入力を再送せず、既存の開始・終了hookを照合し、担当の最終報告と証拠参照をターンごとに一度保存する。未対応・重複・取消後・逆順のイベントで別の操作を完了させない。[端末hook](../../api/domains/terminals/service/hook-events.ts)・[端末の台帳](../../api/domains/terminals/service/ledger.ts)
5. **会話と担当の実行を独立させる。** 受付、開始、実装報告、コミット、実環境での確認を仕事の時系列に保持する。前の試験結果と残件を次の報告で消さない。別件への会話を受け付け、状態を尋ねられたら既存の状態表示と仕事照会で最新成果を渡す。通知を開くことや履歴に報告全文が残ることを前提にしない。管理型の結果を端末側から重複配送しない。[会話に渡す状態](../../api/domains/dialogue/service/state-text.ts)・[自律処理の待機判定](../../api/application/agency/always-on-host.ts)・[会話の実行状態との接続](../../api/application/agency/assembly.ts)

## 3. 計画を根拠にした自律調査の受付

計画をLLMへ提示した時点で、Continuityにある会話・計画ID・revisionと根拠発言・記憶を対応付ける。受付時と結果採用時に、提示時の版と根拠の可視性を所有元の公開操作で照合する。提示後に更新された場合は新しい版で再判断する。発言、記憶、メモの既存の検証を維持する。[現行の参照解決](../../api/application/agency/input.ts)・[計画と根拠](../../api/domains/continuity/contracts/plans.ts)

受付処理は不完全な入力を一律の拒否で返す箇所に、失効・未対応・権限不足・一時競合・受付結果不明を区別できる結果を返す。恒久拒否は同じ仕事・根拠版で終端にし、変更された根拠や権限が届いた時に再評価する。一時競合は既存の期限内で再試行、受付結果不明は元の操作を照会する。原因不明のまま同じ案件を再作成しない。自律活動の表示は同じ理由を1件にまとめる。意味の解釈と次の目的の選択は従来どおりLLMが行う。[受付と仕事の開始](../../api/application/agency/always-on-flow.ts)

## 4. TTSの実測・再現結果と実装方針

**実環境。** 11月23日朝の保存ログに残る音声入力13件を、発話IDで稼働中のAPIの状態と照合した。合成開始9件のうち8件は最終状態が `played`、1件は `interrupted / backend_restarted`。後者は6:32:28までに3句の再生終了報告があり、6:34:04にbackendが停止、6:35に復旧した。最後の報告と停止には約96秒ある。復旧理由から音が消えた瞬間までは断定できない。6:32:19の別の再生要求は同じHTTP要求内で推論取消と502が記録されている。文字入力側の3 runは生成11句に対して再生終了報告11件だった。

6:42の音声入力では計測された句間1,312 msのうち1,310 msが次の音声を取得し終わるまでの時間だった。2句目相当のTTS推論は6:42:34.949に成功し、1句目の終了報告受付は6:42:35.422。4句すべてで終了報告を受理した。ブラウザーの取得完了までの待ちには、公開、変更通知、取得開始、転送が含まれる。この値だけでネットワークや合成単体の責任とは決められない。[合成と公開](../../api/domains/voice-dialogue/service/synthesis.ts)・[句間の計測](../../web/src/domains/voice-dialogue/hooks/chunk-player.ts)

**障害を入れた再現。** 現行のWebの音声入力用再生処理に2句を渡し、同じ機械状態で1操作だけを失敗させた。音声と通信は代用品を使い、実際の端末には出力していない。

| 条件 | 再生開始 | 発話取消要求 |
| --- | ---: | ---: |
| 正常 | 2句 | 0件 |
| 2句目の音声取得だけ失敗 | 1句 | 1件 |
| 1句目を再生後、終了報告の通信だけ失敗 | 1句 | 1件 |

再生キューは取得と終了報告のエラーを同じ失敗処理に渡す。呼び出し元は出力停止と発話取消APIを実行するので、取得済みの次の句も止まる。これは申告の症状を起こすことを確認できた経路であり、当日の聞き取りがどの発話だったかは確定していない。[再生キュー](../../web/src/domains/voice-dialogue/hooks/chunk-player.ts)・[失敗時の発話取消](../../web/src/domains/voice-dialogue/hooks/playback.ts)

**変更内容。**

1. 取得待ち、再生中、自然終了、終了報告待ちを既存キュー内で区別する。終了報告の応答が失われたら、同一発話・生成・句番号の報告だけを既存の再生権と期限内で再送する。次の取得済み音声は順に再生する。報告が重複しても台帳を二重更新せず、音声を再生し直さない。[既存の終了報告処理](../../api/domains/voice-dialogue/service/playback.ts)
2. 音声の一時取得失敗では同じ版の公開済みの句を再取得し、後続句は順序を保って待つ。取得も報告も再試行は有界とし、回復しなければ最後に再生できた位置と失敗を表示する。自動再合成や全編の自動再読は行わない。利用者の停止、マイク割込み、画面の所有権・権限の喪失、生成の置換は即時停止とし、古い音声や遅れた返答を破棄する。
3. 音声入力の応答でも、句の公開直後に識別子・版・句番号をWebに知らせ、既存の音声GETと再生キューで先読みする。現行は画面共通の変更通知で複数の問い合わせをまとめて更新し、入力用SSEは認識終了で閉じる。既存の発話購読を応答中へ延長し、公開済み句の情報を当該発話だけに届ける。購読は当該画面の再生権に紐付け、切断時は同一発話の現在版を取得して未再生分だけを再開する。音声本文・生データをログに残さない。[現行入力SSE](../../api/domains/voice-dialogue/service/input-events.ts)・[既存の句単位再生設計](tts-async-clause-playback-2026-11-15.md)
4. 訂正時は旧世代の本文生成とTTSの両方に取消を伝播させ、旧結果を採用しない。再起動後の中断と明示停止を表示で区別する。前回の再生位置を確かめられない場合に全文を聞いた扱いにしない。[訂正時の回帰試験](../../api/domains/voice-dialogue/test/streaming-speech.test.ts)

**現行版の検証結果。** 現行の5ファイルを明示実行したbackend試験は45件成功・1件失敗。失敗は「元発言の訂正時、TTSは取消済みだが本文生成のsignalは発話失敗の観測時点で未取消」。Webの4ファイルは20件成功。実Web Audioを使う消音Chromiumは4件成功（順序、mute、失敗、世代置換）。消音試験は実機で音が聞こえたことの証拠には含めない。[ブラウザー試験](../../tests/browser/run-speech.spec.ts)
