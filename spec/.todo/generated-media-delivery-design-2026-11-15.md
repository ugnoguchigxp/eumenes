# 生成した画像と音楽を会話へ届ける設計

> **整理判断（2026-11-28）: 今後取り組む。** 一部実施。段階1・2は記録済み、音声ファイルの受口と音の分析（段階3・4）は計画。 実装済みの部分をやり直す指示ではない。未合意の設計は、着手時に現行方式と照合し必要な合意を得る。

2026-11-15。**段階1・2の実装と検証を記録。段階3・4は計画。**

画像や音楽の保存結果が採用された時点で、元の会話に成果物が届く。画像は続けて会話エージェントの推論へ実データを渡し、確認した内容を次の会話で使えるようにする。音楽は先に完成ファイルを扱えるようにし、音そのものの分析は入力能力の確認後に接続する。

この設計は、生成した成果物を元の会話へ戻す経路を定める。保存ライブラリ内の資料を探す依頼と、受領済みの画像や音楽を詳しく調べる依頼は、既存のリソース調査の担当へ委任する。[画面状態の共有とリソース調査](artifact-state-and-resource-research-design-2026-11-15.md)

## 1. 生成完了から元の会話への受け渡し

生成を開始するとき、元の会話と依頼、対象の仕事または画面操作の参照を既存の受付記録で固定する。生成の完了時には、所有する機能が保存済みの結果を返し、ホストが原本を識別できる参照を元の会話の台帳へ登録する。現在のタブや表示中の会話から行き先を推測しない。画面から始めた生成も、受付時に会話との対応が確認できる場合に同じ経路を使う。会話の出所を持たない生成物は、利用者が添付した時点で会話へ入る。

会話から依頼した生成では、保存結果の採用、仕事の完了、成果物の台帳と完了通知を使う。画面操作の結果に仕事がない場合は、操作の確定記録と同じ成果物台帳を結ぶ。台帳に入れるのは所有機能、原本の識別子、版または固定できる内容の識別情報、生成の出所。生成結果の採用を条件とし、保存中の仮ファイルは配信しない。[仕事の結果採用](../../api/domains/dialogue/service/work-ledger.ts) · [成果物の台帳登録](../../api/domains/dialogue/service/work-links.ts)

受け渡しの単位は、元の会話、生成結果の確定記録、成果物の組み合わせ。同じ結果が再通知されても、一つの成果物と一度の自動確認にまとまるようにする。受け渡しと確認の状態を再起動後に読める形で記録し、確定済みの生成物を取り直すときも生成要求は再実行しない。保存採用と会話参照を同じ書き込みで確定できる箇所はそれを使い、別工程では確定記録から配信を再開できるようにする。

完了通知で「成果物が届いた」ことを示す。確認結果は同じ成果物に紐づけ、会話に利用者の発言を代筆しない。画像の確認のために会話の応答先や再生状態を変更しない。生成の成功、ファイルの取得、推論への入力、確認結果の採用は別の段階として記録する。

## 2. 画像の実データを会話エージェントへ渡す

受領した画像について、元の会話エージェントによる確認を一度、既存の推論キューで行う。生成完了通知があれば確認を始められるため、次の発言や画面操作を待たない。完了通知の受付処理には現在、通常の会話推論を起動せず仕事を確定する経路がある。画像確認はその確定後に予約し、他の仕事の完了時に一律で会話推論を起動する変更は加えない。[完了通知の処理](../../api/domains/dialogue/service/generation-prepare.ts)

1. 確認の予約には、元の会話と確定した画像の参照を保存する。画像ごとの状態と実行の対応を保持し、画像が複数ある場合は、並び順と現行の入力上限に沿って一つの確認にまとめる。収まらない画像は未確認のまま受領済みとして残す。
2. 実行時に画像の所有機能から原本を読み、既存の画像変換・正規化・入力容量検査を通す。モデルへは判別できる実画像をネイティブ画像入力として渡す。保存時の指示、ファイル名、サムネイルの説明は由来を示すデータとして扱う。[保存画像の添付変換](../../api/application/media/attachment-file.ts) · [画像入力の契約](../../docs/chat-images.md)
3. 元の会話に適用される接続設定から、画像入力の可否と上限・保持条件を確認する。画像対応と送信権限が確認できる経路で実行し、対応不明、容量超過、取得不能、権限失効は区別する。別のサービスへの自動転送は既存の接続設定で許された経路に限る。画像を省いた回を画像確認の成功にはしない。
4. 採用前に、会話の出所、対象の版、取消・撤回と権限を再確認する。確認済みの記録には成果物の版、実際の入力画像の識別情報、変換、推論の実行・採用と確認内容を結び付ける。既存の画像入力の証跡が利用者の発言と添付IDを前提としているため、ホストが採用した生成物を出所にできるよう拡張する。[画像入力と回答の証跡](../../api/domains/dialogue/service/attachment-context.ts)

画像の確認内容は元の会話から参照できる。通常の履歴には小さな確認記録を残し、細部を再確認するときに同じ版の画像を取り直せるようにする。自動確認の出力は既存通知の更新に使い、別の発話や読み上げを自動で始めない。送達が不明な推論を自動で繰り返さず、確認結果を採用できなかった場合は受領済みの画像を保持する。

次の会話が画像確認より先に始まった場合は、受領済みの参照と確認中の状態を渡す。確認が終わったら、以後の会話で確認済みの記録を使える。キュー・通知・履歴に保持するのは参照と確認記録で、画像や音声の実データは実行時に取得する。保存先の切替や原本の削除で記録した版を確認できなくなった場合は、取得不能として扱う。

## 3. 音楽ファイルの受け口と音の分析

### 3.1 ファイルを受け取り、取得できるようにする

生成した曲、ボーカル、効果音は、音楽機能の確定結果から会話へ登録する。生成記録のIDとライブラリ上の曲のIDは区別し、所有機能が取得先を解決する。ブラウザーへの配信と既存プレイヤーはそのまま使える。生成物の音声を会話のために別途保存し直す必要はない。[生成音声の配信](../../api/domains/music/controller/index.ts) · [ライブラリの音声取得](../../api/domains/music/controller/library.ts)

端末の音声ファイルには、チャットの添付メニューに選択口を設ける。選択・取消・送信後の再取得は既存の添付操作に揃え、新たに音声の検証、保存、会話への関連付け、認証付き読み出しを用意する。原本を検査して、対応形式、容量、実際の再生時間を確認する。最初の対応形式と上限は、生成物の実形式、ブラウザーの再生、サーバーの検証方法を照合して実装前に決める。既存の一時ファイル機構も候補とするが、再起動後の再取得と会話単位の権限を満たせる保存経路を使う。[既存のチャット添付](../../docs/chat-images.md) · [一時ファイルの契約](../../docs/scratch.md)

この段階では、会話エージェントにファイルの存在、出所、形式、長さ、読み取り用の参照を渡せる。利用者は会話からファイルを開ける。音を出す操作は利用者が開いているEumenes Web画面で行い、完了時の受領や音の分析が再生を起動することはない。[可聴出力の責務](../.archived/music-audio-output-boundary-2026-10-31.md)

### 3.2 音の内容を調べる

音の分析には、保存済み設定から発見した接続の音声入力契約が必要になる。音声の形式と入力の長さ・容量・保持条件、出力が対象とする能力を確認する。現行のチャット入力は文字と画像を扱うため、音をモデルへ渡す処理と、その入力を結果に紐づける証跡を追加する。マイク入力の文字起こしは発言内容の確認に使えるが、曲調や楽器の判断には音を扱える入力経路が必要になる。[現行の推論入力契約](../../api/domains/larm/contracts/chat-input.ts)

利用者が内容の確認を求めた場合は、リソース調査の担当に、受領済みのファイルの参照を渡す。担当が必要な時間区間を選び、ホストが実際に取得して入力した音声と範囲を根拠として報告する。原音からの観測、文字起こし、生成時の指示・歌詞は出所を区別する。対応する接続が確認できない場合も、受け取ったファイルは使え、音の内容は未確認と分かる。

## 4. 実装と検証の順序

| 段階 | 再利用と拡張 | 合格条件 |
| --- | --- | --- |
| 0. 契約と基準 | 既存の生成結果、作品IDの寿命、会話と画面操作の出所、画像入力の能力・保持条件を確認する。受領・確認の識別、保持期間、容量、再開方法を決める。音声は既存の実ファイルで対応形式を調べておく。 | 生成結果から原本に到達できる範囲と、現行の固定試験の結果が記録されている。 |
| 1. 生成完了時の受け渡し | 画像・音楽の完了結果を既存台帳と通知へ接続する。原本の読み取り権限、再通知、取消、再開を検査する。 | 別画面を開いた状態で、元の会話にだけ一度届く。取消・撤回後の遅い結果、同じIDを持つ別の接続先のファイルを採用しない。 |
| 2. 画像を実データで確認 | 画像入力と既存の推論実行を再利用し、生成物を出所とする実入力と確認記録を追加する。段階1の確定結果に依存する。 | 生成指示と異なる特徴を持つ合成画像で、実画像がモデルの入力に入ったことを確認する。対応接続の実モデルでも画素にしかない特徴に答え、次の会話で結果を参照できる。 |
| 3. 音楽・音声ファイルの受け口 | 完成曲の参照と端末ファイル添付を、同じ会話内の取得口へ接続する。段階1の参照を再利用する。 | 生成曲と添付音声が送達され、再読み込み後に同じ内容を取得できる。破損・偽MIME・上限超過・別会話・再送を検査する。 |
| 4. 音の分析 | 対応するサービス契約を確認してから、調査担当に時間区間付きの音声入力と報告を追加する。段階3の後に進む。 | 実音にだけ含まれる特徴を確認でき、読んだ範囲と未確認区間を報告できる。未対応の接続ではファイルの受領までとし、音を分析した扱いにならない。 |

検証は部分、公開入口からの結合、通しの順で行う。段階1は [画像の会話結合試験](../../api/application/media/image-e2e.test.ts) と [音楽の会話結合試験](../../api/application/media/music-e2e.test.ts) を起点とする。段階2は [チャット画像添付試験](../../api/application/toolchain/chat-image-attachments.test.ts) を再利用し、生成完了からモデルに渡る入力までを追加する。段階3は [音楽の音声配信試験](../../api/application/media/music-audio-routing.test.ts) と添付の公開入口から確認する。既存の完了通知が維持され、重複した推論や発話を起こさないことも測る。

変更した機能と利用側は、段階に応じて `bun run verify -- --domain image --domain music --domain dialogue --domain resources` や `bun run verify -- --domain conversation --domain inference --domain larm --domain agent-runtime` から対象を選ぶ。ブラウザーの試験は対象ファイルを明示して別に行い、検証用ブラウザーは消音する。固定試験では接続・権限・採用結果を、liveでは実データとモデルの応答を、実機器では利用者のWeb画面からの再生を確認する。互いの結果は代用しない。[検証手順](../../docs/verification.md)

段階1と2を先に完了させる。段階3の完了は音声ファイルの受領・取得まで。音の理解を完了とするのは段階4の固定試験と実モデルでの受入が済んだ時点とする。

## 5. 実装と検証の記録（2026-11-15）

- 画像・音楽の成果物は、仕事の完了通知と元の会話のリソース台帳に登録する。生成した曲は音楽側が保存したファイルを既存の認証付きAPIで返す。画像は生成時に記録した接続先と原本のダイジェストを読み直した内容と照合する。確認は同じ仕事について最大1回。会話の画像入力上限を適用し、一度に最大8枚、150秒で打ち切る。確認用の入力・出力に会話の発言を追加しない。
- 固定試験では、元の会話への一度の送達、画像のネイティブ入力を復号した寸法と画素値、後続の会話での確認結果の参照を確認した。原本の差し替え、画像入力非対応、依頼を撤回した後の遅延応答も検査した。音楽は一度の送達と認証付きAPIから同一のバイト列を取得できることを検査した。
- 保存済みのLARM接続で、隔離環境の生成結果を緑一色の合成画像にして実モデルへ送った。夕焼けを指定した生成指示に対し、実モデルは画素から緑色を回答し、元の会話の完了通知に記録された。モデルは画像にない黒線も記述したため、この確認の合格条件は画像の実入力と緑色の識別まで。
- 保存済みの実曲1件を読み取り専用で取得し、ffprobeでOggコンテナのOpus（48 kHz、2チャンネル）と確認した。生成APIの既定形式はOpusで、現在のファイル保存・Web配信に使える。既存のマイク文字起こしは別経路で、WAVの16ビットPCM（通常16 kHz、モノラル）を使う。会話推論の現行契約はテキストと画像なので、どちらの音声形式で音を分析できるかは接続の音声入力仕様を確認する段階に残す。
- 生成画像・音楽の関連固定試験55件、対象ドメインの固定試験1,353件、型検査、指示カタログ検査は通過。総合検証は作業ツリーにある過去の検証用コピーの試験検出で停止し、そのコピーを含めない隔離環境でも既存の `MessageList.tsx` の依存境界違反で停止した。既存のチャット添付結合試験の失敗2件は変更前のmainでも再現した。
