作成日 2026-11-28 JST ｜ 状態 第6稿に基づくP0の事前検証と、P1のローカル実装・隔離受入を完了<br>
対象はEumenes本体、利用者が選んだ作品フォルダ、既存のClaude CodeおよびLARM接続。初版の対象OSはmacOS。

## 0. 用語

| 用語 | 意味 |
| --- | --- |
| 作品 | 利用者が登録した独立Gitリポジトリ一件。コード上の識別子は `prototype` とする。既存の `work` はClaude Code・Codexの仕事を指すため使わない。 |
| Works | 作品を並べる親フォルダの呼び名と、会話から作品を扱う入口の名前。 |
| 共有環境 | Eumenesが管理するWorks専用の依存宣言、ロックファイル、パッケージ本体、解決表、共通CLIのまとまり。 |
| 解決表 | 作品が書けるimport（パッケージ名と公開サブパス）から、実体のファイルと型への対応表。固定版ごとに一つ。 |
| 固定版・互換系列 | 固定版は共有環境の内容を特定する不変の版。互換系列は、既存作品の結果を変えずに追加だけを重ねられる範囲。§4.1。 |
| 共通CLI | 作品の `package.json` とEumenesの両方から呼ぶ、型検査・ビルド・単体起動の入口。実際のビルドは分離ビルダーで行う。 |
| 分離ビルダー | OSで読み書きとネットワークを絞った、ビルドと型検査のプロセス。§4.2。 |
| ランナー | 既存のClaude Code実行daemon。作品を作業場所にするものを試作用ランナーと呼ぶ。 |
| 登録世代 | 作品IDごとの番号。登録先のパスかGit共通ディレクトリを結び直すたびに進む。古い世代に結び付いた仕事とプレビューは採用しない。許可の変更では進めない。許可は素材の受け渡しと生成の受付のたびに照合し、取り消した許可はその時点から効く。 |
| 入力版 | ビルド対象のファイル内容、作品定義、固定版から作るダイジェスト。§4.3。 |

## 1. 目的と初版の完了条件

利用者とEumenesが、会話しながらソフトウェアを自由に試作できる環境を作る。利用者やCodexが直接編集するフォルダを、EumenesからClaude Codeへ制作を頼むときにも使う。作品ごとに独立したGitリポジトリを作り、Eumenes内から開くときも作品単体で起動するときも同じソースを使う。ソースと履歴は作品ごとのGitHubリポジトリで管理できる。ソースからの単体起動は、Eumenesの共有環境を用意した機器を対象とする。

作品の依存はすべてEumenes側に集約し、個々の作品に `node_modules` や依存のロックファイルを作らない。特定の一作品だけが必要とするパッケージもEumenes側の共有依存として追加する。同じ依存を作品ごとにインストールする処理と、作品専用の常駐サーバーを省く。共通の実行環境からReact、Canvas、three.js、cannon-esなどを使い、作品の機能として既存のLLMプロバイダーやLARMのモデルと素材を呼び出せるようにする。

初版の完了には次の結果が必要。

1. 独立した二つのGitリポジトリを登録し、各フォルダへの依存インストールと作品専用の常駐サーバーの起動なしで、Eumenesで両方を開ける。Eumenes本体のGit管理から両作品が独立していることを確認する。
2. Eumenesとの会話から作品Aを指定してClaude Codeへ制作を頼める。作業経過から使用可能なプレビューへ移れ、次の依頼で同じ作品を修正できる。作品Bは自分またはCodexで直接編集してプレビューに反映できる。
3. 一方の操作、再ビルド、失敗、取消が、もう一方の表示や実行を変更しない。対応ブラウザーで作品が応答しないときにもEumenesと別作品を操作できる。作品Bは保存素材の読込みと実LARMによる画像生成を同じ画面で実演できる。作品パネルからの生成は、主会話の発言や画像計画の推論を生じさせない。
4. 個別のインストールと開発サーバーを使う同等構成と比較し、ディスクとメモリの実測差を記録する。依存や常駐プロセスが増えない構造の確認と、節約量の確認をそれぞれ示す。
5. 既存のCodex作品を一件、Gitの作業ツリーとリモートを維持したままその場で試験導入できる。既存の実行方法に戻る手順も確認する。
6. 作品リポジトリを別の場所へcloneし、用意済みのEumenes共有環境を指定して、Eumenes本体のサーバーを起動せずに作品を開き、ビルドできる。両モードの型検査・素材読込み・作品内保存を確認し、作品別の `node_modules` とロックファイルが作られないことを確かめる。共有環境が未準備の機器では、不足する環境と用意する手順を表示する。

## 2. 作品フォルダと移行

最終的な配置例。親フォルダは整理用とし、Worksを本体リポジトリの外に置く。本体のGitとパッケージワークスペースの管理範囲はCoreに閉じ、Works直下の各作品を独立したGitルートにする。作品の通常のclone・commit・pushはその作品のリポジトリに対して行う。

```text
~/Code/Eumenes/
├── Core/                       Eumenes本体のGitリポジトリ
└── Works/
    ├── gravity-playground/     作品AのGitリポジトリ
    └── image-board/            作品BのGitリポジトリ
```

初版は現在の本体チェックアウトと既存作品のパスを維持し、Worksには本体のGitルート外のフォルダを指定する。Eumenesに「登録済みの作品を開く」「既存フォルダを登録する」「指定済みのWorks配下に新規作品を作る」を設ける。利用者が選んだ絶対パスをホストが正規化して作品IDに対応付ける。登録・新規作成・移設時は選択したパスの実体がGitのトップレベルに一致し、本体や別作品と管理範囲が重ならないことを確認する。正規化したGit共通ディレクトリも照合し、本体・別作品のlinked worktreeや別名経由の二重登録を拒否する。新規作成ではホストが `git init`、§2.3の雛形の配置、最初のコミットまでを行い、基準コミットのある状態で登録する。このコミットは利用者のGit設定の名前で作り、設定がなければ作成を止めて設定を案内する。登録時には履歴の起点コミットを記録し、§2.4の結び直しの照合に使う。 [Git共通ディレクトリの既存照会](../../packages/coding-runner/src/sdk-git-operations.ts)

| 保存先 | 持つもの |
| --- | --- |
| 作品フォルダ | §2.3のファイル。利用者・Codex・Claude Codeが共有するソースの正本。 |
| Eumenes | 作品ID、登録世代、登録先、利用を認めた機能・素材、実行と生成物の参照。全作品の依存宣言、ロックファイル、インストール済みパッケージ、ビルドキャッシュ、接続設定、資格情報をEumenes側で管理する。依存の正本の置き場は§4.1。 |
| GitHub | 作品ごとに利用者が選んだリモート。公開に必要なファイルを明示して保存する。既存リモートの変更や新規作成、pushは利用者のGit操作を起点にする。 |

初版はブラウザーで完結する試作を移行対象とする。入口、依存、サーバー処理、環境変数、外部接続を棚卸しし、互換性の不足は理由とともに示す。**試験導入**では暫定の入口・版・素材をEumenes側に登録してプレビューを試す。試験導入中は作品フォルダへ何も書き込まず、型検査の設定もEumenes側に生成する。依存は試験導入でも共有環境から解決し、不足や版の違いは棚卸しの結果として示す。既存の `package.json`、ロックファイル、作業中のソース、リモートと元の起動手順を維持し、試験登録の解除だけで従来手順へ戻れることを確認する。**正式移行**は利用者が選んだ作品で行い、必要な依存を共有側に追加した後に作品側の依存宣言とロックファイルを共通方式へ切り替える。Git履歴・リモートを引き継ぎ、従来の `node_modules` は運ばない。新パスは元の作品IDに結び、Gitルート・Git共通ディレクトリ・基準コミット・未コミット差分・リモートを照合する。

### 2.1 同じ作品を二通りで動かす

Works配下の作品は、制作中からGitHubでcloneして開発できる形で作る。作品単体での起動には、別の場所に一度用意したEumenes共有環境を使う。新規・既存のどちらの作品も `package.json` の開発・ビルドスクリプトから共通CLIを呼ぶ。Eumenes側に一度導入した共通CLIをPATHから呼び、利用者が指定した共有環境ルートと固定版を検証する。PATHに置くのは薄い起動口とし、実際の処理は作品が指定した固定版のものを使う。作品の標準スクリプトは `dev`、`typecheck`、`build`。READMEにはCLIの準備、共有環境の指定、対応する固定版、未指定・版不一致の対処を記載する。

| 実行方式 | 起動と依存 | 出力の置き場 | 素材・生成などの接続 |
| --- | --- | --- | --- |
| Eumenes内 | ホストが共通CLIと同じ処理を呼び、`prototype.json` の入口と固定版を検査して、共有依存でビルドする。プレビューは共通の配信口で開く。 | Eumenes側のビルドキャッシュ。作品フォルダへ書くのは `.eumenes/` の生成設定だけ。 | Eumenes用アダプターが、作品に認められた機能をホストの公開操作へ接続する。認証とLARMジョブの管理はホストが担う。 |
| リポジトリ単体 | READMEに沿って別の場所にある共有環境を指定し、作品の `package.json` のスクリプトから共通CLIを呼ぶ。共有依存でビルドし、単体用のブラウザービルドを開ける。`dev` は実行している間だけ配信口を開き、常駐させない。共有環境の準備は機器ごとに一度行う。 | `dev` は共有環境側のキャッシュ。`build` は分離ビルダーの専用出力先に作り、共通CLIの起動口が作品内のGit除外の `dist/` へ写す。 | 単体用アダプターが同梱素材と定義済みのサンプル応答を返す。実際に生成を行う作品は、別途設定した作品自身のバックエンドへ接続する。実接続の障害は失敗として表示する。サンプルの利用は単体のサンプルモードで明示する。 |

作品側の `package.json` はメタデータと起動スクリプトに使う。依存宣言・ロックファイル・パッケージ本体は、Eumenesが管理するWorks専用の共有環境に置く。ある作品だけが使うパッケージも同じ共有環境に追加する。両モードとも§4.1で指定された共有環境だけで依存を解決する。環境が未準備、指定版が利用不能、またはパッケージが未登録なら、不足する環境や依存と設定手順を表示する。READMEにはこの前提を記載する。CIでソースをビルドする場合は、macOSの実行環境に同じ共有環境を用意する。他のOSでのビルドは初版の対象外とし、共通CLIが対象外と表示する。

### 2.2 作品のアダプター

UIと作品の処理は共通の `src/` に置き、入口で型付きのアダプターを渡す。初版の契約は、利用可能な機能、選択済み素材の読込み、生成の入力案の提示、受付後の状態・取消・結果に絞る。生成の開始はホストのパネルの操作が受け、作品のコードからは始められない。作品内の設定保存は§4.3の作品オリジン内で行う。作品のUIはこの契約を使い、接続方式や資格情報には依存しない。Eumenes用の入口では§4.3の専用チャネルを使う。単体用の入口は最初から単体モードとして表示し、同梱素材と既知の応答によって、Eumenes本体サーバーやLARM接続がなくても、共有環境でビルドした画面の主な操作を試せるようにする。Eumenesのライブラリを参照する作品では、単体で同じ操作に必要な範囲の、配布できるサンプル素材をGitに含める。

アダプターの実装は共通CLIがモードに応じて差し替える。作品は共有の解決表に登録する公開入口 `eumenes-prototype/app` を使う。

```tsx
// src/main.tsx
import { mount } from "eumenes-prototype/app";
import { App } from "./App";

mount(({ adapter, root }) => root.render(<App adapter={adapter} />));
```

| アダプターの操作 | Eumenes内 | リポジトリ単体 |
| --- | --- | --- |
| 利用可能な機能の一覧 | 利用者がその作品に認めた機能 | `samples/` に応答を持つ機能 |
| 選択済み素材の読込み | 認可済みの保存素材（§5） | 同梱素材 |
| 生成の入力案の提示、受付後の状態・取消・結果 | ホストのパネルと既存の画像生成（§5） | サンプル応答。サンプルモードと明示する |

`.env.example` はリポジトリに置き、単体での初期モードと任意の接続設定を、空欄またはダミー値で示す。実値を入れる `.env` や `.env.local` はGitから除外する。ブラウザーへ渡す値はモードなど公開設定に限り、接続の資格情報は対応するバックエンドに留める。Eumenesモードは作品の環境ファイルを共通ビルドへ読み込まず、素材・推論・生成にはホストの設定を使う。単体で実LARMを使う場合は、作品側で管理するバックエンドと接続・認証の契約を別途定める。初版の単体受入は同梱素材・サンプル応答まで、実LARM生成はEumenesモードで確認する。

### 2.3 作品フォルダの中身

初版の共通CLIは `eumenes-prototype`、作品定義は `prototype.json` の `schema: 1` とする。アダプターで扱う機能は `library.image.read`（Eumenesの保存素材へのアクセス）と `media.image.generate`（LARMのcapability）。

```text
gravity-playground/
├── prototype.json     作品定義（追跡）
├── package.json       名前・版・共通CLIを呼ぶスクリプトだけ（追跡。依存欄を持たない）
├── tsconfig.json      生成設定を参照する入口（追跡）
├── README.md          共有環境の準備と起動手順（追跡）
├── .env.example       単体モードの公開設定の見本（追跡）
├── .gitignore         .eumenes/ dist/ node_modules/ .env* と、例外の !.env.example
├── src/main.tsx       入口。アダプターを受け取って画面を組む
├── assets/            同梱素材
├── samples/           単体モードのサンプル応答と、配布できるサンプル素材
├── .eumenes/          機器固有の生成物（Git除外）。型設定と共有環境の場所
└── dist/              単体モードの本番ビルド出力（Git除外）
```

```json
{
  "schema": 1,
  "name": "gravity-playground",
  "entry": "src/main.tsx",
  "environment": "1.4",
  "features": ["library.image.read", "media.image.generate"],
  "include": ["src", "assets", "samples"]
}
```

```json
{
  "name": "gravity-playground",
  "version": "0.1.0",
  "private": true,
  "scripts": {
    "dev": "eumenes-prototype dev",
    "typecheck": "eumenes-prototype typecheck",
    "build": "eumenes-prototype build"
  }
}
```

```json
{ "extends": "./.eumenes/tsconfig.generated.json", "include": ["src"] }
```

`.eumenes/` の生成設定は、分離の外で動く共通CLIの起動口が書く。書く契機は、Eumenesへの登録、固定版の変更、単体モードの準備の三つ。分離ビルダーは作品フォルダへ書かない。試験導入中の作品には生成しない（§2）。

| `prototype.json` の欄 | 意味 | ホストの検査 |
| --- | --- | --- |
| `schema` | 作品定義の形式の版 | 未対応の版は理由を表示して開かない |
| `entry` | ビルドの入口 | `include` の範囲内にある実ファイル |
| `environment` | 共有環境の固定版（互換系列.追加の通し番号） | 利用可能な固定版。無ければ版の不足と移行手順を表示 |
| `features` | 作品が求める機能。用途やcapabilityで書き、モデル名・profile名は書かない | 利用者が認めたものだけをアダプターに出す。生成はcatalogのcapabilityを使う |
| `include` | ビルドと配信の対象にするフォルダ | §4.3の収集規則と上限 |

### 2.4 登録の解除・移設・消失

Eumenesは作品フォルダを削除・移動しない。

| 操作 | 前提 | 作品フォルダとGit | Eumenes側 | ブラウザー側の保存データ |
| --- | --- | --- | --- | --- |
| 試験導入の解除 | なし | 変えない | 暫定の入口・版・素材の登録とビルド出力を消す | 残る。再登録しても引き継がない |
| 登録の解除 | 進行中のClaude Codeの仕事がない。停止を確認できない間は解除を保留し、保留中と表示する | 変えない | 登録、許可、監視、ビルド出力、プレビュー参照、待機中の試作用ランナーを消す。受付済みで未完了の生成は取り消す。保存済みの生成画像は画像ライブラリに残し、作品への関連付けだけを外す | 残る。再登録は新しい作品IDになり、引き継がない |
| 移設 | 進行中の仕事がない。利用者が対象の作品と新しいパスを指定する | 利用者が移動する | 登録時に記録した履歴の起点コミットが新パスのリポジトリにあり、§2の重複検査を通る場合に、新パスを同じ作品IDへ結び直して登録世代を進める。開いていたプレビューは新しい世代で作り直す。生成中の画像は作品IDに結び付いているので引き継ぐ | 引き継ぐ（作品IDが同じ） |
| フォルダの消失・Git共通ディレクトリの差し替え | 検出した時点 | — | 監視とその版の採用を止め、進行中の仕事に停止を求める。同じパスで起点コミットが一致すれば、利用者の操作で結び直す（移設と同じ扱い）。一致しなければ再登録を表示する | 結び直しでは引き継ぐ。再登録では引き継がない |

## 3. 責務と既存機構の再利用

| 部分 | 実装案と既存機構 |
| --- | --- |
| 会話と制作 | Eumenesが対象作品・目的・受入条件を整理し、既存の登録taskへ依頼する。質問、進捗、変更、取消、結果には既存の依頼処理を使う。複数工程の調整が必要な仕事は既存の開発監督を利用する。 [依頼の流れ](../../docs/assignments.md) · [開発監督](development-supervisor-design-2026-11-22.md) |
| 編集と検証 | 既存のClaudeランナーと作業場所の排他を再利用する。会話から作品制作を頼む仕事は、既存の監督付き経路で受け付け、受付した作品の作業場所と読み書きの範囲を渡す。作業場所の参照から遅延接続する方法を本体・登録目標・作品で共有する。経路の選択、検証、依存追加は§4.2で定める。 [Claude Code管理タスク](claude-code-managed-task-design-2026-11-15.md) · [現行ランナーの組立](../../api/application/work/claude-runners.ts) · [ランナーの選択と定期監視](../../api/domains/claude-code/index.ts) |
| ビルドと表示 | 初回利用時の準備、専用オリジン、短命なプレビュー参照、Artifact内での表示は既存Canvasを先例とする。複数ファイルのTypeScriptやReactは新しい作品契約で扱う。既存の単一スクリプトのCanvas作品は、現行の作品契約とWorker経路で開く。 [Canvas統合](canvas-app-integration-2026-11-12.md) · [初回利用時の起動](../.archived/toolchain-on-demand-startup-design-2026-11-26.md) |
| 素材・生成・推論 | ホストが所有domainの公開操作を接続する。生成済み画像・楽曲は既存ライブラリ、作品パネルの画像生成は§5で追加する直接受付を使う。既存の生成ジョブ、LARM接続、状態管理を再利用する。LLMは既存の保存済み推論設定を使う。 [画像生成](../../docs/images.md) · [LARM](../../docs/larm.md) · [リソース参照](../../docs/resources.md) |
| 作品の登録と操作 | 新しい作品のdomainは登録・設定・版の状態と実行参照を所有する案。各生成domainがジョブ本体と成果物を持つ。applicationが公開操作を組み合わせ、複数domainの保存は単一writerのtransactionで行う。Artifact・会話・リソースの入口はbundleと登録adapterで追加する。ホストパネルは既存DesignSystemの部品を使い、素材選択は画像の共通Grid・Pickerを候補とする。実装時は `scripts/domains.ts` と `docs/domains.md` に所有・依存境界を登録する。 [登録と拡張](../../docs/toolchain-extension.md) |

会話からの制作依頼は、受付時の作品ID、登録世代、正規の作業場所、排他枠を仕事に固定する。開始、回答、再開、取消、再起動後の復旧は同じ参照から解決し、タブ切替や対象不明時に本体の作業場所へ流す経路を設けない。停止未確認の仕事は対象作品の排他を保持する。別作品の枠は個別に管理する。

作品へのcommitとpushは利用者またはCodexの操作とし、初版のClaude Codeの仕事は変更を未コミットのまま残す。例外は新規作成時にホストが作る最初のコミットだけ（§2）。Claude Codeの仕事は作品のHEAD、インデックス、stashを変えない。監督付き経路ではBashが登録済みの検査コマンドに限られるため、commit・stash・restore・resetなどGitの状態を変える操作は通らない（§4.2）。仕事の開始時に基準コミットと既存の未コミット差分を記録し、今回の変更だけを結果として示す。取消は停止と成果の不採用を意味し、既に書いた変更は戻さない。これは既存の管理タスクと同じ扱い。 [取消と実行証跡の現行設計](claude-code-managed-task-design-2026-11-15.md)

現行の組立は起動時に接続をprobeし、定期監視も仕事の有無にかかわらず全ランナーをprobeする。daemonのprobeは起動を伴う。作品の登録・一覧表示ではランナーを起動せず、実際の受付・復旧で必要になった対象だけを開始する。現行契約には作品の待機daemonを終了する操作がない。待機期限は、実行の終了と排他の解放を確認してから初版60秒とする。期限時に同じ起動識別子に対し、処理中なら拒否する終了要求を出し、管理下の子プロセスの終了を確認してから接続を解放する。終了未確認の間は同じ作品の新しい受付を保留する。制御プロセスの再起動後は、未終端の仕事か終了未確認の起動識別子があるものだけを照会する。終了証跡または同じホストでの別のboot identityを確認するまで再割当てしない。定期確認は起動済み・復旧待ちの接続を対象とし、状態確認から新規起動が発生しないようにする。 [daemonの起動条件](../../packages/coding-runner/src/claude-daemon.ts)

## 4. 共有ビルドと実行境界

### 4.1 共有環境の実体と版

Eumenesの管理下にWorks専用の依存宣言、ロックファイル、解決表を置く。Core自身のWeb依存とロックとは分離する。初版は既に導入済みのTypeScript、React、three.js、cannon-esを足掛かりに、公開する入口・サブパス・型を決める。CoreとCanvasには異なるthree.jsが存在するため（0.186.1と0.187.0）、Worksで採用する依存は専用の正本に明示する。Canvas内部の推移依存から暗黙に拾う経路を設けない。同じパッケージの複数版が利用可能でも、作品の指定版の解決表から実体を一つに決める。共有環境はCoreのワークスペースの自動解決と切り離す。作品内の相対パスと解決表に登録したパッケージだけを使用する。`node_modules` のないフォルダからは、Bunの既定の解決でパッケージに届かないことを確認済みで、解決は解決表による明示の対応付けで行う。

- **正本と発行。** CoreのcheckoutとDBのあるデータ領域の外に、Works専用の独立Gitリポジトリを置く。ホストの承認済み操作で依存宣言・Bun設定・ロック・解決表・共通CLI・アダプターを検証してコミットし、`works-v<系列>.<通し番号>` タグを発行する。管理側の版一覧にはタグ名、コミットID、発行対象ファイルの内容SHA-256を記録する。発行済みの版名は再利用しない。別機器・CIは管理側で指定されたリポジトリを取得し、タグと内容を記録と照合した上で、ロックの変更とインストールスクリプトの実行を禁止して一時領域に導入し、検証後に利用可能とする。 [保護パスの現行組立](../../api/application/work/claude-runners.ts)
- **導入時のガード。** 公開から7日未満の版を入れない本体の設定（`bunfig.toml` の `minimumReleaseAge`）と同じ規則を共有環境にも適用する。依存のライフサイクルスクリプトは実行しない。ネイティブビルドを要するもの、ブラウザー向けの入口を持たないものは対象外とし、理由を返す。
- **互換系列と固定版。** 下の表に従う。固定版はWorks専用ロック、解決表、共通CLI（ビルドと型検査の処理）、アダプターの内容から識別し、一度発行した内容を書き換えない。Bunの版は固定版の識別に含めず、固定版ごとの検証記録に持つ。`prototype.json` は固定版を指定し、共有・単体の両モードで同じ固定版を使う。新しい依存を使う作品だけが承認済みの版へ更新する。
- **ホストとの互換。** ホストは、保持している固定版すべてのアダプターとの専用チャネルの契約を受け付ける。チャネルの契約を変えるときは、古い固定版の作品が動く間は旧契約の受付を残す。
- **保持と容量。** 確定済みのローカル導入は同時に最大2版とし、一つのBunキャッシュを使う。初版の管理上限は、キャッシュを一回と各導入済みディレクトリを合計した論理サイズ512 MiBとする。準備中の一時領域によるピークとAPFSの実消費は別に測る。ビルド・登録済み検査・開いているプレビューが参照する版は解放まで保持する。上限に達した場合は未使用で最後の参照が最も古い版から導入済みデータを外す。全候補が使用中か、上限に収まらない場合は理由を表示する。発行記録とタグは保持する。外した版は指定時に同じ発行記録から再準備し、復元できない場合は版の不足と明示的な移行手順を表示する。
- **回帰の確認。** 作品C専用の依存追加と、Core Webの依存更新を別々に行い、変更前に固定した作品A・Bを同じBunの版・同条件で再ビルドする。各モード内でJS・CSS・静的素材の内容ハッシュが一致することを確かめる。古い固定版でビルドした作品が、現行ホストの専用チャネルで素材の読込みと生成の状態取得まで動くことも確かめる。別の場所へcloneした旧コミットも同じ固定版から依存を解決できることを確認する。異なる固定版の作品を二件同時に開けることと、廃止版の不足を表示できることも試験する。

| 変更 | 版の扱い（例） | 既存の作品 |
| --- | --- | --- |
| 新しいパッケージの追加で、既存の推移依存・公開入口・型・出力が変わらない | 同じ互換系列に固定版を一つ発行する（1.4 → 1.5） | 何もしない。使う作品だけが `environment` を1.5へ進める |
| 追加によって既存パッケージの解決結果が変わる | 互換系列を上げる（1.x → 2.0） | 1.x指定のまま動く。移行は作品ごとに行う |
| 既存パッケージの更新・削除、解決表・型検査・アダプター契約の変更 | 互換系列を上げる | 同上 |
| ビルダー本体であるBunの更新 | 固定版は発行も書換えもしない。Bunは機器に一つで旧版を保持しない。保持中の固定版ごとに受入作品を再ビルド・再検査し、結果をその固定版の検証記録に追記する | 出力が変わった作品を表示する。旧版のBunでの再現は保証しない |

### 4.2 ビルド・型検査・Claude Codeの検証

- **ビルドを分離する。** ビルドと型検査は、Eumenes本体およびClaude Codeの編集プロセスと分け、OSで読み書き範囲を制限した分離ビルダーで実行する。分離は両モード共通とし、初版の対象OSはmacOS。既存の検証sandbox（`sandbox-exec`、ネットワーク拒否、書込みは専用領域のみ）を先例にする。初版の対応はTS・TSX・CSS・静的素材に絞り、Vite固有の `import.meta.glob`、`?raw`・`?url`、環境変数の展開、Tailwind/PostCSSプラグイン、パスエイリアスは互換性を確認したものだけを登録する。未対応の既存作品には原因と対象箇所を出す。許可した入力スナップショット、共有依存の読み取り、専用出力先への書込みに絞る。環境変数は必要な公開値だけにし、入力と出力を固定した作業ディレクトリでネットワークを閉じる。作品の `bunfig.toml`、`tsconfig` の `paths`、プラグイン、インストールスクリプトをホストの解決に使わない。Bunのマクロを無効にし、検査でマクロ指定を見つけたビルドは失敗にする。分離を適用できる環境だけでビルドを受け付ける。共通CLIの起動口も、作品フォルダを作業ディレクトリにして起動したときに作品の `bunfig.toml`（preloadなど）と `.env*` を読み込まないようにする。保存の検知と表示のためにホストが動かすビルドと型検査は、機器全体で同時実行の上限を設け（初版は各1件を案とする）、待ちは作品ごとに最新の入力版だけを残す。Claude Codeが頼む検査はこの待ち行列に入れず、その仕事の検査sandboxで動かす。作品ごとの排他により、同時に動くのは作業中の作品の数までとなる。 [Bun公式のマクロ仕様](https://bun.com/docs/bundler/macros) · [既存の検証sandbox](../../packages/coding-runner/src/claude-supervised-tools.ts)
- **型検査を共通化する。** 両モードの共通CLIに型検査コマンドを設ける。固定版の解決表から、絶対パスを含む機器固有のTypeScript設定を作品内のGit除外領域に生成する。作品の追跡対象に置く設定はその生成ファイルを参照する入口とし、CodexやエディターでReact・three.jsと公開サブパスの型が解決できるようにする。共通CLIも同じ解決表から検査し、作品側の独自 `paths` を権限や依存解決の根拠にしない。型診断は現在の入力版に結び付ける。
- **型エラーと表示の更新。** 保存に伴うプレビューの更新は、ビルドが通った完全な出力で行う。型診断は同じ入力版の結果としてパネルに並べて出し、型エラーだけでは表示の更新を止めない。Claude Codeの完了報告と、共通CLIの `build`（単体の本番ビルド）は型検査の合格を条件にする。ビルドの失敗時は版を明記して前回成功のプレビューと診断を表示する。
- **Claude Codeは監督付き経路で動かす。** 作品の制作は、既存の監督付き経路（lease、authorization、登録済み検査）に載せる。通常経路は作業場所内でBashを自由に使え、書込み前照合を持たないため、作品には使わない。監督付き経路では、読取りを作品フォルダ（`.git` と `.env*` を除く）、書込みを `include` のフォルダと `prototype.json`・READMEに限る。EditとWriteは読取り時の内容と照合され、Bashは登録済みの検査コマンドと一致するものだけが検査sandboxで動く。パッケージマネージャーの実行、Gitの状態を変える操作、本体・別作品への読取り・検索・書込みはこの経路を通らない。会話からの依頼を監督付き経路で受け付ける接続点はP0で確認する。 [通常経路の作業制限](../../packages/coding-runner/src/claude-policy.ts) · [監督付き経路の範囲と検査](../../packages/coding-runner/src/claude-supervised-tools.ts)
- **既存契約への変更は三つ。** 一つ目は、作業場所の外にある作業中の固定版のパッケージと型を、質問なしの読取り専用の範囲として認めること。現行は作業場所の外を指す範囲を `claude_scope_invalid` で拒否する。二つ目は、検査sandboxの読取り拒否に、本体のデータ領域・別作品・`.env*` を指定すること。現行の検査sandboxは読取りを既定で全て許す。三つ目は、登録済み検査として共通CLIの `typecheck` と `build` を登録し、出力を検査sandboxの一時領域に置くこと。Claude Codeに共有キャッシュや本体への書込みを許す必要がなく、結果は検査の出力として診断が返る。現行のランナーにはホストの操作を足す口がないため、検証をホストの公開操作として渡す方式は採らない。検査の実行中に作品の入力が変わった場合は、既存の `workspace_inputs_changed` として返し、Claude Codeが読み直して再検査する。
- **依存追加はホストが扱う。** 未登録依存が必要なとき、検査は不足する依存を診断として返す。Claude Codeは用途、候補の名前・版、使う箇所を報告し、既存の質問の経路（担当の `ask_user`）で利用者へ届ける。ランナーに新しい操作口は足さない。ホストは承認を操作・対象・世代に結び付けて受付し、利用者が承認した追加だけをWorks専用の依存宣言とロックに反映する。固定版の発行と確認後、対象作品と入力を再照合し、同じ仕事を再開する。再開した仕事が作品の `prototype.json` の `environment` を新しい固定版へ進める。否認・取消・入力の競合は該当する状態を返す。試作用ランナーの指示にも、作品内でインストールしないことを書く。インストールが必要な処理は、承認を照合したホストの依存追加操作に限定する。作品ソースの通常編集に伴う差分は作品リポジトリだけに現れ、承認済み依存追加の宣言とロックの差分はWorks共有環境側だけに現れる。
- **同時編集を検出する。** 受付・再ビルド時に登録ルートを再検査し、ルート外や別の場所へのシンボリックリンクを拒否する。Claude Codeの管理下の書込みは、既存の書込み前照合をもとに、読取り時の内容と書込み適用時の内容を照合する。並行更新がある場合は利用者の現ファイルを保ち、Claude Codeの案を未適用差分として示す。この照合を通らない書込みの経路は、監督付き経路の制限により存在しない。排他はランナーの仕事を調整し、ビルダーの版照合は古い出力の採用を止める。 [既存の書込み前照合](../../packages/coding-runner/src/claude-supervised-tools.ts)

**監督付き開始と検査の接続。** 登録済みWorks担当は、認可した作品の作業場所参照・登録世代・固定版から、開発監督が使う監督付き開始と同じlease・authorizationを組み立てる。検査は登録コマンドとの完全一致を確認し、信頼済みの起動側が作った一つのOSプロファイルで共通CLIの処理を走らせる。外部の読取りは検証済みの固定版一つに限り、書込みは専用の一時領域に限る。現行の `withExitStatus` と `toolEvidence` で実際の終了状態と入力ダイジェストを記録する。macOSでは現行の検査プロファイルを重ねて起動すると失敗する。P0では一つのプロファイルで登録済みの `typecheck` と `build` を通し、型エラーと入力更新で合格しないことを確認した。 [現行の監督付き開始](../../api/application/work/development-supervision-host.ts) · [登録済み検査の試験](../verification/instant-project-sandbox-2026-11-28/registered-check-probe.ts)

### 4.3 プレビュー・素材・更新

共通の配信口を初回利用時に準備し、Eumenes本体とは異なるサイトで、作品ごとに分かれた安定したオリジンを同じリスナーから配信する案をP0で確認する。オリジンの案は `http://p-<作品ID>.localhost:<配信口のポート>` で、作品IDごとに固定する。作品のCSS、テクスチャ、GLTFなどは登録済みの静的素材経路から配信し、作品オリジン内で `localStorage` を使えるようにする。共有・単体で保存操作の契約をそろえる。保存データは各モードの作品オリジンに属する。作品からのService Worker登録は受け付けず、入口の文書はキャッシュさせない。古い出力が配信口の照合を通らずに残る経路を作らない。初版はEumenesと同じ機器のループバック経由に絞る。LAN・別の実機器では起動前に対象外であることを表示する。対応ブラウザー、安定した作品別オリジンの割当て、iframe権限とCSP、同一リスナーでの配信が成立することをP0で実測する。 同一リスナーでの実配信と停止操作は、macOSのGoogle Chromeでは確認済み。Playwright Headless Shellの試験ではサイト分離を明示する。 [P0の配信証跡](../verification/instant-project-sandbox-2026-11-28/README.md#4-実ループバック配信)

親とプレビューは、親が確認したフレーム専用のチャネルで作品ID・ビルド版・セッションを照合する。遷移や再読込みで古いチャネルを失効させる。認証情報と本体の保存領域は本体に留め、作品へ渡す素材はその作品への利用を認めた範囲に限る。CanvasのDOMモードで判明しているブラウザー停止や外向き通信の限界も確認し、対応ブラウザーで本体と別作品の操作が続けられ、作品の配信条件を満たす場合に起動する。親の停止操作か監視で応答不能と判定したらiframeを切り離し、作品コードを動かさない復旧画面へ戻す。同じ入力版の自動再表示を抑止し、入力が変わった後または利用者の明示操作で再試行する。一般の未信頼コードと秘密データの処理は初版の対象外とする。 [Canvas統合の実行境界](canvas-app-integration-2026-11-12.md)

**権限と音。** 初版はiframeへ自動再生・マイク・カメラ・画面取得の権限を委譲しない。作品が鳴らす音と、会話の読み上げ・聞き取りとの調停は初版の対象外とし、受入作品は音を出さない。音を扱う拡張では、利用者が開いたEumenesのWeb画面内で再生し、検証ブラウザーは消音する。

**更新の方式。** 表示の更新は、新しい出力へのページ全体の読み直しで行う。物理シミュレーションの途中経過など実行中の状態は引き継がず、作品オリジンに保存した設定は残る。モジュール単位の差し替え（HMR）は初版に含めない。見えなくなった作品（別のArtifactへの切替、パネルを閉じる）のフレームは破棄し、再表示で同じ入力版の出力を読み直す。フレームを保持する方式へ変えるかは、P4の計測（表示中と破棄後の待機メモリの差、開き直しの待ち時間）を見て判断する。

| プレビューの状態 | 入る条件 | 画面に出すもの | 次の状態 |
| --- | --- | --- | --- |
| 対象外 | macOS以外、分離ビルダーを起動できない、対応外のブラウザー、ループバック以外からの表示 | 対象外の理由。作品コードは動かさない | 条件が変わるまで留まる |
| 待ち | 同時実行の上限による順番待ち | 前回成功した版があればその出力と、待ちの表示。無ければ待ちの表示だけ | 順番が来たら準備中 |
| 準備中 | ビルドの実行中（初回と再ビルド） | 前回成功した版があればその出力と、進行の表示。無ければ進行の表示だけ | 成功で表示中、失敗で失敗 |
| 表示中 | ビルドの成功 | 現在の入力版の出力。型診断があれば件数と位置をパネルに出す | 保存の検知で待ち。見えなくなれば非表示。応答不能の判定で応答不能 |
| 失敗 | ビルドの失敗、作品定義の誤り（`schema` の未対応、`entry` が `include` の外）、収集の拒否（上限の超過、ルート外へのリンク）、マクロ指定の検出 | 前回成功した版があればその出力。失敗した入力版と診断を明記する。無ければ診断だけ | 入力が変わる、または利用者の再試行で待ち |
| 応答不能 | 親の停止操作、または監視による判定 | フレームを切り離した復旧画面 | 入力が変わる、または利用者の再試行で待ち |
| 非表示 | 別のArtifactへの切替、パネルを閉じる | なし。フレームを破棄し、監視を解除する | 再表示のとき、入力版が同じなら既存の出力で表示中、変わっていれば待ち |
| 環境の不足 | 固定版の不足、未登録の依存 | 不足しているものと対処の手順 | 承認済みの依存追加、または固定版の移行で待ち |
| 登録先の異常 | フォルダの移動・削除、Git共通ディレクトリの差し替えの検出 | 異常の内容と、結び直し・移設・再登録の操作 | 結び直し・移設で待ち。再登録は別の作品になる（§2.4） |

**収集と入力版。** スナップショットは `prototype.json`、登録された入口、`include` で許可した `src/`・`assets/` 等に限る。`.git`、`.env*`、`node_modules`、生成設定、キャッシュ、出力は除外し、ルート外を指すリンクを拒否する。生成設定（`.eumenes/`）はスナップショットに含めず、分離ビルダーには同じ固定版の解決表から作った型設定を外から渡す。読み込み前にファイル数・個別サイズ・総量の上限を適用する。入力版は、対象ファイルの正規化パスと内容、作品定義、共有環境の固定版から作るダイジェストとし、未コミットの変更も含む。ビルド、配信、Claude実行の前後で照合する。作品フォルダの移動・削除・Git共通ディレクトリの差し替えを検出した場合は監視とその版の採用を止め、§2.4の結び直し・移設・再登録の操作を表示する。

収集の初期上限は1,024ファイル、個別16 MiB、合計64 MiB。読取り中にも上限を適用する。ルートからディレクトリを辿る間もリンクを追わず、収集前後の登録ルートとファイルの同一性を照合して、変更を検出したスナップショットを破棄する。入力版のハッシュでは、正規化した相対パス順で各項目のバイト長と内容を含めてSHA-256を計算する。

**保存検知。** 開いているプレビューのソースと素材だけを一つのホスト側処理で監視する。Codexまたは人の連続保存は最後の変更から100 msの安定待ちでまとめ、同一入力版のビルドを重複させない。閉じた作品の監視は直ちに解除し、古い入力版の出力は新しいプレビューへ反映しない。

事前確認では、`node_modules` のない一時フォルダに置いたTypeScript二ファイルを、Canvasに同梱されたthree.jsとcannon-esでビルドし、消音したChromiumで重力と3D描画を確認した。cannon-esはパッケージのESM入口でビルドに成功した。Fableレビューは、Bun 1.4.4の既定のビルドで作品のマクロがビルダープロセス内で動くこと、`bun build --no-macros` では同じ入力が `Macros are disabled` で失敗することを実測した。分離ビルダー、複数作品、実LARM、資源の節約はこの計画の検証対象とする。

**保存素材の受け渡し。** 本体パネルが既存の認証付き画像APIから取得し、作品・版・プレビューセッションで許可を照合した上で、専用チャネルから容量を制限したバイト列を渡す。フレームは作品内のBlob URLで表示し、差し替え・閉じる操作でURLと参照を解放する。取得不能や上限超過は状態として返す。作品のCSPは既定拒否とし、スクリプト・スタイル・接続は作品自身のオリジン、画像は作品自身のオリジンとBlobだけを許す。Workerを禁止し、埋め込み元は登録済みの親に絞る。iframeにはスクリプト実行と作品自身のオリジンを許す。 [保存画像の配信](../../api/domains/image/controller/index.ts)

**作品パネルからの画像生成。** Eumenesが描画するパネルの操作を起点に、型を検査した生成パラメータと論理操作IDで `image` domainの直接受付を新設する案とする。現行の会話由来入口は会話run・子実行を必要とし、`image.plan` から `image.generate` へ進む。作品の受付は主会話発言や画像計画の推論を起こさず、既存の生成キュー、容量待ち、LARM接続、保存を利用できる接続点をP0で固定する。実行履歴は作品パネルが作品参照で扱い、通常会話の画像生成履歴へは配信しない。完成画像は既存ライブラリに保存し、作品に関連付けた参照から利用する。 [画像の現行受付](../../api/domains/image/service/index.ts) · [計画と生成のジョブ](../../api/domains/image/service/handlers.ts)

- **既存行の移行。** `image_generations` をimage domainの単一writerのtransactionで作り直し、既存行を `origin='conversation'` として移す。rowid、実行ID、会話ID、キューID、内容、成果物版を保持する。作品由来は `origin='prototype'` と作品ID・論理操作ID・許可の改訂番号・絶対期限を持ち、会話IDとrun IDは空にする。作品IDと操作IDの組を一意にする。会話向けの一覧・完了一覧・活動・会話成果物の照会は会話由来に絞る。完成画像は双方とも既存ライブラリに保存する。 [現行の表と照会](../../api/domains/image/repository/index.ts) · [移行試験](../verification/instant-project-sandbox-2026-11-28/image-migration-probe.ts)
- **期限。** 受付または再試行の開始から各回に5分の処理枠を取り、現行のキューと同じく末尾の15秒を確定処理に確保する。既存の規則で再送可能と判定された容量不足だけを空き待ちに回す。最初の容量不足から30分以内で、再試行に5分を確保できる場合に限る。操作の絶対期限は受付から35分とし、呼出元がより早い期限を指定した場合はそちらを使う。最初の処理枠もその期限で切り詰める。再送・再読込み・作品のリビルドで絶対期限を延ばさない。 [現行の容量待ち](../../api/domains/larm/contracts/capacity.ts)
- **権限。** 受付・送信前・結果の確定・照会・取消・取得時に、その作品の許可と受付時に保存した許可の改訂番号を照合する。受付と結果の確定では状態と期限も単一writerのtransactionで照合する。取消や許可の失効後は結果を採用しない。同じ作品IDを保つ移設や入力変更では、許可が有効な限り操作を継続する。

ホストは作品・操作ID・入力を画像実行IDに、単一writerのtransactionで結び付ける。開始時の入力版は記録として持ち、結果の採否には使わない。生成中に作品を保存して再ビルドしても、再読込み後のページがアダプターから同じ操作IDの状態と結果を取り直す。同じ操作の再配送はその受付を返し、新しい操作だけが別の実行になる。状態・取消・再接続・成果物の参照はこの対応から行う。LARMへの生成POSTの応答が失われた場合は既存の復旧規則を使う。画面を開く、再ビルドする、通信が切れるといった操作で生成を増やさない。取消済み・権限失効済みの結果は採用しない。 [現行画面の取消対象](../../web/src/domains/image/use-image-creation.ts) · [LARM画像の復旧規則](../../docs/images.md)

部分試験、公開入口の結合試験、対象ファイルを指定したブラウザーE2E、実Claude Code・実LARMの順に確認する。対象と利用側のdomainを確定し、`bun run verify -- --domain <name>` を使う。固定・live・実画面／実機器の結果は区別し、稼働サーバーの操作が必要な検証は明示の許可を得て行う。 [検証手順](../../docs/verification.md) · [ツールチェーン検証](../../docs/toolchain-extension-verification.md)

- **P1の独立性。** Eumenesのチェックアウト外のcloneを明示した共有環境で起動・ビルド・型検査する。共有環境なしでは不足する前提と準備手順を表示する。各作品と本体のGitルート・共通ディレクトリ・リモートを照合し、作品のソース編集に伴う本体のGit差分がないことを確認する。素材を読み、設定を再読込みで復元する。A・Bのストレージ（localStorage・IndexedDB）とBroadcastChannelが分かれ、作品コードから親の画面や本体の設定・画像一覧に到達できないことを検査する。応答不能になった作品は親から閉じ、他作品を操作しながら復旧画面を表示できる。巨大ファイル・ルート外リンク・`.env` を含む入力の収集と配信、登録フォルダの削除・差し替えに対する失敗表示も確認する。全部閉じれば監視対象とハンドルは0。二件を表示しても監視プロセスは増えず、Codexの連続保存はまとまって該当作品だけに反映される。登録の解除後に作品フォルダとGitの状態が変わらず、Eumenes側の登録・出力・監視が残らないことを確認する。移設では同じ作品IDのまま登録世代が進み、`localStorage` の内容が残り、旧世代の出力が採用されない。
- **P2の競合と解放。** 通常会話からAを編集し、本体とBのソース差分がゼロであることを確認する。Aの制作タスク中に、本体・B・`.env*` への範囲外操作と、作品内の依存インストールを拒否できることを確認する。Claude Codeが読んだ後にCodexで同じファイルを保存し、利用者の修正とClaude Codeの未適用差分を両方確認する。停止未確認時はAの再着手だけを保留し、別作品の操作を続けられる。停止確認後に複数の監視周期を経過しても終了したランナーが再起動しないことを確認する。依存の承認時に差分が出るのはWorks共有環境の依存宣言とロックであり、作品側で固定版を更新する場合はそのメタデータ差分を作品に記録する。仕事の前後で作品のHEAD、インデックス、stashの一覧が変わらず、作業ツリーの差分は今回の編集分だけであることを確認する。Codexが残していた未コミットの編集は、仕事の後も同じ内容で残る。停止を確認できない仕事がある間の登録解除は、保留と表示される。

## 7. ストレージとメモリの判定方法

同じ二つのソース、依存の版、機器、表示条件で「個別インストールと開発サーバー」と「Eumenesの共有環境」を比較する。P0で従来方式のディスクの基準値を測り、P4で共有環境の実測を並べる。作品0件・1件・2件の増分を取り、空キャッシュの初回と通常の追加時を分けて複数回測る。Eumenes側の追加費用も含め、中央値とばらつきを記録する。従来方式のパッケージマネージャー・キャッシュ状態をP0で固定し、開発サーバーは一件ずつ起動する場合と二件同時に常駐させる場合を分ける。LARMの実行とブラウザーの描画は別欄に記録する。

| 指標 | 比較の取り方 |
| --- | --- |
| ディスク実消費 | Worksの外に用意した比較環境で、個別インストール前後の実消費を測る。対象ファイルシステムとBunのインストール方式を記録し、見かけ上の容量と実消費を区別する。macOSのBunにはコピーオンライトの方式があるため、ディレクトリ容量の合算で節約を判定しない。P4では共有依存、キャッシュ、作品別ビルド出力を計上する。作品固有依存を追加したときは旧版の保持中と掃除後を両方測る。 [Bun公式のインストール方式](https://bun.com/docs/pm/cli/install) |
| プロセス・待機メモリ | 常駐サーバー、ビルダー、監視、Claudeランナーの数・PID・待受を記録する。登録直後、二件の表示が落ち着いた時点、A・Bで順にClaudeの制作を実行した後に両方を閉じた時点を測る。終了確認・待機解放期限・複数の監視周期の後に、0件時のメモリと比較する。ビルドと型検査の実行中のピークは待機と分けて記録する。二件を表示中の時点と、フレームを破棄した後の差を出し、フレーム保持へ変えるかの判断に使う。共有ページを二重に数えるRSSの合算だけで判定しない。 |
| 操作の待ち時間 | 新規・二件目の追加から初回表示までをインストール時間込みで測る。ソース保存の完了から表示の更新までと、作品の開き直しも測る。従来の開発サーバーはモジュール単位の差し替え、共有環境はページ全体の読み直しである点を並記する。共有環境の一度だけの準備時間は内訳に示す。 |

構造上は、作品を増やしても個別の `node_modules` や常駐プロセスが生じないことを合格条件とする。ディスクと待機メモリの改善は、従来構成からの差が測定のばらつきを超えた項目について報告する。効果を確認できない構成は、原因と適用条件を見直し、移行範囲を決める。
