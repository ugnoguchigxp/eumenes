# Eumenesの試作環境（Instant Project Sandbox）実装計画書

作成日 2026-11-28 JST ｜ 状態 レビュー用初稿・実装前<br>
対象はEumenes本体、利用者が選んだ作品フォルダ、既存のClaude CodeおよびLARM接続。

## 1. 目的と初版の完了条件

利用者とEumenesが、会話しながらソフトウェアを自由に試作できる環境を作る。利用者やCodexが直接編集するフォルダを、EumenesからClaude Codeへ制作を頼むときにも使う。作品は独立したGitリポジトリにでき、作業の継続や公開に既存のGitHubリポジトリを使える。

作品が増えても依存のインストールと常駐サーバーが作品数に比例して増えない構成にする。共通の実行環境からReact、Canvas、three.js、cannon-esなどを使い、作品の機能として既存のLLMプロバイダーやLARMのモデルと素材を呼び出せるようにする。

初版の完了には次の結果が必要。

1. 独立した二つのフォルダを登録し、各フォルダへの依存のインストールと専用サーバーの起動なしで、Eumenesで両方を開ける。
2. Eumenesとの会話から作品Aを指定してClaude Codeへ制作を頼める。作業経過から使用可能なプレビューへ移れ、次の依頼で同じ作品を修正できる。作品Bは自分またはCodexで直接編集してプレビューに反映できる。
3. 一方の操作、再ビルド、失敗、取消が、もう一方の表示や実行を変更しない。作品Bは既存の保存素材の読込みと実LARMによる画像生成を同じ画面で実演できる。
4. 個別のインストールと開発サーバーを使う同等構成と比較し、ディスクとメモリの実測差を記録する。依存や常駐プロセスが増えない構造の確認と、節約量の確認をそれぞれ示す。
5. 既存のCodex作品を一件、Gitの作業ツリーとリモートを維持したままその場で試験導入できる。既存の実行方法に戻る手順も確認する。

## 2. 作品フォルダと移行

最終的な配置例。親フォルダは整理用とし、本体と各作品に独立したGitのルートを持たせる。

```text
~/Code/Eumenes/
├── Core/                       Eumenes本体のGitリポジトリ
└── Works/
    ├── gravity-playground/     作品AのGitリポジトリ
    └── image-board/            作品BのGitリポジトリ
```

初版は現在の本体チェックアウトと既存作品のパスを維持する。Eumenesに「登録済みの作品を開く」「既存フォルダを登録する」「指定済みのWorks配下に新規作品を作る」を設ける。利用者が選んだ絶対パスをホストが正規化して作品IDに対応付ける。同じ実体の二重登録を防ぎ、同じ実体を別名やシンボリックリンク経由で新たな作業枠にできないようにする。

| 保存先 | 持つもの |
| --- | --- |
| 作品フォルダ | `prototype.json`（スキーマ版、入口、実行環境の版、利用ライブラリ、要求する機能）、`src/`、必要に応じて `assets/` とREADME。利用者・Codex・Claude Codeが共有するソースの正本。 |
| Eumenes | 作品ID、登録先、利用を認めた機能・素材、実行と生成物の参照。依存の実体、ビルドキャッシュ、接続設定、資格情報もホスト側で管理する。 |
| GitHub | 作品ごとに利用者が選んだリモート。公開に必要なファイルを明示して保存する。既存リモートの変更や新規作成、pushは利用者のGit操作を起点にする。 |

初版はブラウザーで完結する試作を移行対象とする。既存作品では入口、依存、サーバー処理、環境変数、外部接続を棚卸しし、共通環境で動く範囲を確かめる。互換性の不足は理由とともに示す。既存のロックファイル、独自サーバー、依存は受入が終わるまで元の運用に使える状態を維持する。移動は別の操作とし、移動後は元の作品IDを新パスに結び、Gitルート・HEAD・未コミット差分・リモートを移動前後で照合する。

## 4. 共有ビルドと実行境界

- **依存の解決。** Eumenesに導入済みのブラウザー向け依存から登録リストを作る。初版はTypeScriptとReact、three.js、cannon-esを候補とする。ホストに複数版がある場合は実行環境の版ごとに使う実体を一つに決める。試作の import は登録されたパッケージ、公開されたサブパス、作品内の相対パスだけを解決する。依存が足りなければ利用できる版を示す。追加や版更新は共有環境の変更として扱う。
- **ビルド。** 最初は既存Bunを使う共通ビルダーを候補とする。許可されたソースと素材をスナップショットに固定し、内容、依存セット、ビルド条件からキャッシュを識別する。更新時に同じビルドをまとめ、完全な出力だけを配信へ切り替える。ビルドに失敗したときは旧版を表示中と明示してエラーを出す。作品側のVite設定、プラグイン、インストールスクリプト、サーバー用モジュールをビルド用ホストに読み込ませる機能は後続扱いとする。
- **ファイルと編集。** ホストは受付・再ビルド・実行先変更で登録ルートを再確認する。パスの逸脱、別の場所を指すシンボリックリンク、本体のDB・設定・鍵へのアクセスを拒否する。Claude Codeの仕事を受け付けた時点で作品の作業場所を解決し、ランナー側で作業場所と書込み範囲を検査する。編集枠を使う管理下の仕事は既存の排他を利用する。Codexや手編集との同時更新は編集枠で強制できないため、入力版とビルド差分を照合して古い出力の採用を防ぐ。
- **プレビュー。** Eumenesが管理する共通の配信口を、初回利用時に準備する。作品の追加に伴う聴取ポート、監視プロセス、常駐ビルダーの増加を避ける。別オリジンでsandbox付きiframeを使い、プレビューごとに短命の参照を発行する。iframeに親の認証状態や同一オリジン権限を与えず、親が確認したフレームに結び付く専用チャネルを用いる。受け付けるメッセージは作品ID・ビルド版・プレビューセッションと照合し、再読み込みやフレームの遷移で古いチャネルを無効にする。本体APIの資格情報、Cookie、DB、任意のURLやファイル取得を渡せる汎用口は用意しない。CSPとiframeで制御できる外部通信と、描画の暴走が本体や他作品に及ぼす影響をP0から検証する。一般の未信頼コードや秘密データを処理する用途は初版の対象外とする。
- **キャッシュと版。** 生成物とビルド出力は作品ソースから分け、容量・保持上限と再生成の方法を定める。開いているプレビューと利用中の版を保護して掃除する。ホスト更新後に旧作品の指定版を扱えない場合は、その状態を表示して利用者が版を移行できるようにする。

事前確認では、`node_modules` のない一時フォルダに置いたTypeScript二ファイルを、Eumenesに導入済みのCanvas側のthree.jsとcannon-esでブラウザー向けにビルドし、消音したChromiumで重力と3D描画を確認した。cannon-esをサーバー向けのCommonJS入口から解決した場合はビルドが失敗し、パッケージのESM入口を使うと成功した。この結果は共有依存の実行可能性を示す。Eumenesに組み込んだプレビュー、作品間の境界、実LARM、資源の節約は今後の検証対象。

## 5. LARMと複数LLMの利用契約

| 用途 | 初版・拡張の扱い |
| --- | --- |
| 素材を使う | 初版は作品に選択した保存済み画像を紐付け、既存の認証付き経路から必要な内容を受け渡す。取得不能や参照失効は画面に出す。楽曲・効果音の素材は同じ参照の考え方で拡張する。 |
| 新しく生成する | 初版は作品パネルの「画像を生成」操作をホストで受け、既存の画像生成へ接続する。受付、空き待ち、完了、失敗、取消、結果参照を返す。音楽・効果音と動画などは、所有domainの入出力を確認して順次登録する。 |
| **作品内で**LLMを使う | 型の決まった文章生成などをホストに要求する。機能ごとにEumenes側で利用先を選ぶ設計とし、接続設定を作品ごとにコピーしない。初版は画像で共有機能の経路を検証し、推論は次の機能として追加する。 |
| 計算を使う | 短時間のCPU計算は既存契約を候補にする。利用者が用意したPyTorch環境は場所・起動・入力・出力が確認できた時点で投入口を設計する。2026-11-28に保存済み接続先から取得したCPU計算の公開パッケージ一覧には、PyTorchの掲載がなかった。 [CPU計算の契約](../../docs/compute.md) |

作品の宣言は必要な能力を表す。利用者が与えた許可、ホスト発行の認可済み素材参照、スキーマ、予算、版をホストが受付時に検査する。プロバイダーの資格情報はバックエンドに留め、LARMの接続とモデルは保存設定やcatalogから実行時に解決する。画像は `media.image.generate` と `larm.image-generation.v1` を使う既存経路に接続する。

初版の生成ボタンはEumenesが描画する作品パネルに置く。試作からは入力案を渡せるようにし、ボタンの操作をホストが受けて生成を開始する。生成の受付は、作品・実行版・論理操作IDと入力を結び付ける。同じ操作の再配送は同じ受付を参照し、利用者がさらに生成した回は新しい操作とする。画面を開く、再ビルドする、通信が切れるといった操作で生成を再投入しない。同じ版を開き直したときは、認可を照合したうえで受付済みのジョブに再接続する。取消済み、権限失効済み、あるいは旧版に紐付く結果は現在のプレビューに採用しない。所有domainに保存された成果物は履歴として扱う。音声を追加するときは、利用者が開いたEumenesのWeb画面内で再生する。検証ブラウザーは消音する。

## 6. 実装順と検証

| 段階 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| P0 契約と計測準備 | 現在の依存の実体、画像・LLM・Claudeの公開口、作業場所の排他、Canvasの分離方式を確認する。作品形式、共有実行環境の版、使用する二つの比較用作品を固定する。 | レビューで対象、分離の保証、計測方法、既存機構との接続点を合意する。 |
| P1 ローカル試作 | 登録・作成、共有ビルド、プレビューの共通配信、エラー表示を接続する。新規の3D積み木と、既存フォルダを登録した画像一覧の二件を使う。 | 依存の追加インストールや作品専用サーバーなしで二件が開き、保存・失敗・再試行・切替を相互に影響なく行える。 |
| P2 会話からの制作 | 作品IDを既存Claude Codeタスクとランナーへ渡す。結果の参照から作品のプレビューを開き、同じ作品へ追加依頼を届ける。 | 依頼・編集・検証・使用可能なプレビュー・追加修正までの一連の流れを実Claude Codeで確認。別作品や本体への書込み、二重着手、取消失効を試験する。 |
| P3 LARM | 認可済み素材の読込みと、既存画像生成を一つの作品から使う。接続不可と空き待ちを表示し、完了した同じジョブを照会する。 | 登録済み素材と実LARM画像を同じ画面で使い、画面再読込み・作品切替・取消で再生成や旧結果の採用が起きないことを確認する。 |
| P4 試験移行 | 従来構成との資源計測、Codexでの既存作品の編集、Gitリモートの維持、元の開発手順への復帰を確認する。 | §7の比較と適用範囲を記録し、利用者が次に移す作品を判断できる。 |

順序は部分試験、公開入口の結合試験、指定ファイルのブラウザーE2E、実Claude Code・実LARMでの受入。対象と利用側のdomainを確定して `bun run verify -- --domain <name>` で検証する。プレビューではA/Bの入替え、古い版の応答、ホストへの未許可操作、範囲外ファイル、プレビューを閉じた後の資源解放、壊れた作品からの復帰を確認する。固定・live・実画面／実機器の結果は区別して残し、稼働サーバーの操作が必要な受入は明示の許可を得て行う。 [検証手順](../../docs/verification.md) · [ツールチェーン検証](../../docs/toolchain-extension-verification.md)

## 7. ストレージとメモリの判定方法

同じ二つのソース、依存の版、機器、表示条件で「作品ごとのインストールと開発サーバー」と「Eumenesの共有環境」を比較する。共通のEumenes本体・ブラウザーの起動前提をそろえ、作品0件・1件・2件の増分を取る。依存キャッシュが空の初回と、既存キャッシュを使う追加時は別に測る。測定は各条件で複数回行い、中央値とばらつきを残す。初回だけ必要なEumenes側の追加コストも含める。LARMの生成を伴わない比較を基準とし、生成時の負荷は別に測る。

| 指標 | 比較の取り方 |
| --- | --- |
| ディスク増分 | 依存実体、共通キャッシュ、作品別のビルド出力を計上する。ディレクトリの見かけ上の容量と、ファイルシステム側の実消費を区別する。ファイルの共有やクローンで実消費を帰属できない場合は、その制約を記録する。 |
| プロセス・待機メモリ | 常駐サーバー・ビルダー・監視・Claudeランナーの数とメモリを記録する。作品2件を登録して閉じた状態と、2件を表示してビルドが落ち着いた状態を測る。ブラウザーとLARMは別欄に記録する。共有ページを二重に数えるRSS単純合計だけで節約を判定しない。 |
| 操作の待ち時間 | 初回表示、ソース保存から表示更新、開き直しを測る。資源の節約と引き換えに普段の編集サイクルがどれだけ変わるかを記録する。 |

2件目を登録して編集しても作品ごとの `node_modules` と常駐プロセスが増えないことを構造上の合格条件とする。ディスクと待機メモリの削減を主張するのは、従来構成より実測値が改善し、測定のばらつきを超える場合に限る。改善を確認できない構成は、原因と適用条件を明らかにするまで移行対象を広げない。

## 8. Astra・Fable・hydrogenへのレビュー論点

1. **既存実装との接続。** Claude Code管理タスク、開発監督、Canvas、素材・生成のownerに重複する責務があるか。作品登録時にランナーが常駐する設計へ戻らず、登録ルートに限定した編集を実現できるか。
2. **作品間の分離と状態遷移。** プレビュー、ビルド、素材参照、Claudeの作業場所に同じ作品IDと版を一貫して適用できるか。取消、タブ切替、失効、再試行、外部編集との競合に抜けがあるか。
3. **使い方と移行効果。** 新規作品と既存Codex作品を同じ会話・プレビューで扱えるか。先に切るべき範囲、Gitと依存の移行リスク、メモリ・ディスク比較の不足があるか。

レビューでは重要度、該当箇所、成立しないシナリオ、最小の修正案、追加すべき受入条件を返してもらう。版の保持方針、実行境界、オンデマンド起動と停止、計測条件をレビュー後に確定し、利用者の合意を得てから実装に進む。
