## 3. 未達の目標に次の手を残す

目標の進行は `principal + goalId + goalRevision` に属する。未達の行は、実行可能な仕事、受け取るべき結果・解除条件、本人に確認する具体的な一点のいずれかを持つ。

| 状態 | 保存する内容 | 次に起こすもの |
| --- | --- | --- |
| 判断・実行待ち | 未達の条件、確定した証拠、直前の結果、処理すべき進行の版 | 登録・改訂・許可・新しい結果、またはすでに予約されている背景ジョブ |
| 実行・照会中 | 一手の目的、確認方法、許可参照、受付操作ID、実行先、取得済みの作業ID | 実行先の状態更新。通知できない実行先は期限付きの状態照会 |
| 条件待ち | 待つ対象のIDと版、成立条件、該当する場合は再確認時刻 | 資料の到着、作業先の解放、利用者指定の時刻など。到着済みの条件も登録時に照合 |
| 本人の判断待ち | 質問ID、必要な事実または広げる許可、試した内容、対象版 | 同じ質問への返答。進められる独立部分は先に進める |
| 検証中 | 当初の各達成条件、成果物の版、検証手段と観測値 | 全条件の成立で完了。部分達成・不一致なら未達の条件と理由を次の判断へ渡す |
| 完了・取下げ | 終了した版と結果。完了には証拠参照と一意の報告ID | 結果の閲覧、許可された宛先への未配送の報告 |

保存形式は既存の `goalMigrations` に追加する。1目標版につき1行の進行レコードに、実行方式、進行版、状態、未達条件と依存、再開条件、未投入の印を置く。`goal_preparations` は設計の参照、`goal_permits` は許可、`goal_work` は各試行、`goal_reports` は配送の正本とする。既存の許可行と仕事・報告の payload は旧形式として読み、新形式には種別・形式版を付ける。外部の本文は所有元に保ち、試行から作業ID・成果物ID／版・digest でたどる。同じ目標内に質問待ちと着手可能な小目標があれば、全体は実行待ちのままにする。

- 会話の登録・改訂と状態の更新は、目標を保存する同じ writer で行う。進行の版を進めて再開の必要を永続化し、同じ transaction で `enqueueInTransaction` に渡す。キュー満杯なら未投入の印を保存したうえで、空きができた時と起動時に回収する。モデル呼び出しと外部実行は transaction の外で行い、採用時に読んだ版を再照合する。
- 完了・失敗・調査メモには元の目標／待機対象と結果の版を付ける。判断ジョブの重複キーは所有者・目標ID・目標版・進行版、同じ目標の同時判断を防ぐキーは所有者・目標IDとする。同一結果の重複は一度にまとめ、逆順の旧結果では状態を巻き戻さない。期限より先に資料が届けば、古い予約を取り消して直ちに再評価する。依存関係のない目標を一斉に再計画しない。
- 資料不足でも、許可内の手段で取りに行ける間は取得を次の一手にする。別経路で作られた文書を待つ場合は、閲覧可能な区画と対象を待機条件に保存する。文書の保存時に一致する待機先へ版付き候補を渡し、内容の関連性は Agency が判断する。無関係と判断した文書版は処理済みとして記録する。
- 受付・照会中は同じ操作IDを使う。受付の成否が不明なら先に実行先に照会し、未受付が確定したときだけ同じIDで再送する。照会と重複排除を保証できる実行先だけを自動再送の対象にする。新しい方法には新しい試行IDを割り当てる。起動時には未投入の仕事、受付済みの仕事、期限が来た待ち、未配送の報告を台帳から回収する。
- 初回は現在の実作業の同時枠を使い、実行枠が空けば既存の優先度を使う。質問待ちや将来の資料待ちは枠を返す。利用者の「発話を控えて」は配送に、「すべて停止」と自発行動の無効化は新たな自律実行にも適用する。停止の対象と解除条件を保存し、復帰時に照合する。取消や実行済み操作の状態照会は可能にする。

## 4. 許可された実作業をどう接続するか

**利用者が渡す許可。** 現在の目標ツールを拡張し、本人の明示発言、対象目標・版、隔離作業先・基準版、操作の影響、読める範囲・書けるファイル・実施できる検査、適用する期限／上限を保存する。目標登録と明示許可は一つの発話で扱える。登録だけの目標は、既存ポリシーで認められた分析・読み取りから進める。追加許可は既存の質問に結び付けて一度求める。`authorize_mock` は従来の模擬作業に限定する。[既存の許可操作](../../api/application/agency/always-on-goal-reply.ts)・[監督が照合する作業範囲](../../api/domains/development-supervision/contracts.ts)

**実行先に渡す許可。** ホスト発行の「目標を起点とする依頼」を実行契約に加える。所有者・スコープ・目標ID／版・試行ID・許可ID／版・選ばれた能力と binding の版を照合する。LLM から受け取るのは提示済みの参照と依頼内容。予約、実行直前、再開、結果採用で検査する。根拠の `goal` は Goals、`plan` は発行元の計画、`note` は文書の保存元に、型と版を付けて解決する。会話のメッセージIDには実在する発言だけを渡す。[現在の参照解決](../../api/application/agency/input.ts)・[実行元の検証](../../api/application/toolchain/task-execution-sources.ts)

**初回の実行先。** 登録済みの開発監督に目標起点の親仕事を受ける入口を加える。現在の通常入口は `source.origin` のある依頼を拒否し、利用者発言を必須としている。新入口が台帳の許可を照合し、監督が各子作業向けに設計版・操作・実行先を絞った既存の子許可を発行する。目標側は未達条件を選び、監督は一つの依頼の実行と子作業の回収を担う。両方で同じ試行を起こさない。計画変更が当初の許可内なら子許可を発行し直せる。基準版・操作範囲の拡大は新たな本人判断になる。[監督の通常入口](../../api/domains/development-supervision/task.ts)・[子許可](../../api/domains/development-supervision/authority.ts)・[実行と照会](../../api/domains/claude-code/supervised-task.ts)

親仕事と子仕事の出所は、既存の会話起点と目標起点を識別できる形にする。後者は親仕事ID・試行IDで照合し、会話IDが必須の型・照会・通知を境界で分ける。申請元会話が記録されていれば配送先にできる。配送先がなくても作業と検証を完了し、報告を所有者の目標台帳から取得できる。前景の会話が切り替わっても、別の会話に書き込まない。[子仕事の型](../../api/domains/tool-runtime/contracts/task-execution.ts)・[現在の報告経路](../../api/application/agency/goal-agenda.ts)

初回のファイル変更には既存の設計書と初回分析期間（既定5分）の条件を引き継ぐ。期間中も分析・許可内の資料収集を行い、満了時に当該目標を起こす。同じ目標版の再計画で初回の時計は戻さない。作業先は本人が許可した隔離 checkout に固定する。続きの編集では前の試行が所有する差分を、基準版・対象ファイル・前後の digest で再照合する。他の作業による変更を検知した場合はその対象を保留する。[初回分析の既存条件](../../../eumenes_agency/spec/user-goals-verification-plan-2026-11-21.md)・[作業先の検証](../../api/application/work/supervision-workspace.ts)

## 5. 結果の採用・中断・報告

- 担当の「完了」は検証開始の合図。条件ごとに成果物ID／版、作業先、期待値、実測値、検証の作業IDを対応付ける。機械で判定できる条件は再読取・再実行し、意味の判定が必要な条件はモデルに実物と出典を渡す。現在も有効な合格条件は保持する。依存するファイルや資料が変わった条件だけ再検査する。
- 成果を返す能力が成功し、その条件に対応する独立検査があるときは、次の判断に `verificationRequired` と受付・対象条件を渡す。この段階では新たな作業を提示せず、モデルが条件・検査・根拠を選んで独立検証へ渡す。同じ成果版に対する検査が不一致なら、未達の条件と実測を通常の判断へ戻す。
- 一時的な障害には既存キューの有界な再試行を使う。手段の失敗、恒久的な受付拒否、検証の不一致は次の判断に戻す。同じ目的で3回試すか、新しい根拠なしに失敗が続いた時点で、試した手段・結果・見直した方針を進捗に残す。許可内の代案があれば続行し、本人にしか解けない点が残ればその一点を質問する。
- 改訂、取下げ、すべての作業の停止、許可の取消、出典の忘却は、実行待ちの仕事にも受付済みの仕事にも反映する。取消可能な外部作業に停止を送り、結果の遅着を照会・記録する。旧版・旧許可の結果を現行目標の証拠や報告へ採用しない。忘却に含まれる証拠本文・参照・未配送の報告は既存 purge と同じ writer で除外する。
- 全条件の合格時は、実行前の目標版を照合して Goals を完了にし、同じ transaction で完了報告を一つ予約する。報告には試行対象の版と完了後の版を対応付ける。配送の再試行は同じ報告IDで既存の履歴を照会する。`list_goals` は現在状態、最後の試行と観測、未達条件、次の手または待機理由、開ける証拠参照を返す。進捗更新はこの一覧に蓄積する。

## 6. 実装順と移行

実装手順書の段1・2で Agency の判断と台帳を作り、段3で配布物を本家のキューに接続する。段4で一発話の登録・許可、段5で監督・実作業の受付と照会、段6で検証・報告・忘却を接続する。段7で §7 の離席試験を通す。各段の変更先・試験ファイル・合格値は手順書 §1 に置いた。実行先を追加するときにも、受付の一意性・結果照会・許可・実物の検証を契約試験で確認する。[段ごとの引き渡し条件](registered-goal-autonomy-implementation-2026-11-23.md)

移行は追加形式とし、実行方式を目標版ごとに永続化する。旧モックで受付済みの仕事は元のIDと所有元で収束させる。既存の完了記録は履歴に残し、過去の模擬成果と実成果の区別を表示できるようにする。既存の未完了目標は元の枠・スコープ・版を照合して進行を再構成し、実作業には実作業用の許可を結び付ける。移行中は旧担当と新担当の双方が所有区分を照合する。切戻し時は新規の実作業受付を止め、受付済みの照会・取消・結果回収を所有元で終える。旧方式へ戻すバージョンにもこの所有区分の読取が必要。[migration の登録](../../api/application/migrations.ts)・[配布物の取込](../../vendor/agency/README.md)
