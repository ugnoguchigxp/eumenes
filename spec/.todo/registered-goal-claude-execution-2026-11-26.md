利用者が作業を進めるために登録した目標では、Eumenes が通常の作業先を選び、Claude Code に調査・改修・検証を依頼する。目標の達成条件と必要な製品判断を利用者と共有し、作業先や個々のファイル、テストへのアクセスはホストと runner が扱う。受付は会話画面の有無から独立させる。

現行では、調査を始めるにも登録目標専用の作業先と読取範囲が要る。Live2D の目標では、通常の Claude Code と同じリポジトリを使いながら、古いアバター用の読取範囲に設定画面と保存処理が含まれず、利用者への質問になった。旧検査も設定画面を対象にしていない。通常の会話依頼には、既定の checkout と既存のツール規則で読み書きとコマンド実行を扱う経路がすでにある。 [停止の調査](../.archived/goal-idle-stall-repair-2026-11-26.md) · [通常依頼の実行規則](../.archived/claude-code-completion-improvement-2026-11-23.md#1-目的と合意事項)

## 1. 作業先と通常操作

- ホストが、会話からの Claude Code 依頼に渡す checkout の実パスと `workspaceRef` を共通の正本として解決する。現在の本家では、Eumenes の手動 Claude Code 端末と同じ backend の起動ディレクトリにある `eumenes` checkout を使う。目標の判断には利用可能な開発能力を提示し、実行時の作業先はホストが補う。 [runner の組立](../../api/application/server-wiring.ts#L493) · [端末の作業先](../../api/application/work/kanban-sdk-host.ts#L47)
- 利用者による現行版の登録と既存の自発行動設定を開始の根拠にする。明示的な登録の出典を照合し、登録済みの実作業モードで起動する。目標候補は、本人による登録を経て対象になる。
- 新しい通常実行では `EUMENES_GOAL_WORKSPACES` への追加、ファイル一覧、目標専用の登録検査を開始条件から外す。調査と改修には通常 runner のツール、sandbox、保護パスの規則を使う。新規ファイルの作成も、通常依頼と同じく依頼の範囲内で行える。 [既存のファイル・コマンド規則](../../packages/coding-runner/src/claude-policy.ts#L108)
- 通常依頼と同じ作業指示を Claude Code に渡し、着手時に checkout 内の作業規則を読む。利用者の未コミット変更を引き継ぎ、設計変更の合意やサーバー操作の明示許可が必要な場合はその規則に従う。従来一律に課していた目標専用の設計書生成と初回5分の待機は、通常改修の開始条件から外す。改修の必要性と影響は、待機中の思考プランで見積もる。 [従来の実行条件](registered-goal-autonomy-2026-11-23.md#4-許可された実作業をどう接続するか) · [作業規則](../../AGENTS.md)

作業先の占有は通常依頼・手動端末・Kanban と同じ `workspace-guard` で調整する。手動端末が保持している間は目標を空き待ちにし、既存の解放を確認した時点で受付を再開する。runner の停止や接続不良も、既存の待機・見直しに理由を残す。目標の変更先として明示された対象がホストの作業先と一致しない場合は、対象を取り違えないよう、その作業を保留する。 [通常依頼の排他](../../api/application/work/claude-code-task-adapter.ts#L63) · [手動端末の排他](../../api/application/work/terminal-workspace.ts#L60)

## 2. 調査から検証までの受付

待機の起点、振り返り、方法と影響の判断は、待機中の思考プランに従う。計画の一手ごとに、ホストが登録目標・対象の達成条件・作業の種類を Claude Code の受付または検証へ渡す。方法の選択は目標本文と観測に基づくモデルの判断とし、各手の実行可否をホストが照合する。 [待機中の思考プラン](goal-idle-deliberation-redesign-2026-11-26.md#2-新しい流れ)

| 手 | 使う経路と結果 |
| --- | --- |
| 調査 | 通常 runner の読取モード。実装やリポジトリの検証手順を確認し、対象条件に関係する箇所と観測を返す。 |
| 改修 | 通常 runner の作業モード。必要な差分を作り、既存のプロジェクト手順で担当内の確認を行う。観測と差分を次の判断へ返す。 |
| 検証 | 登録目標の検証工程から別の実行を受け付ける。調査済みの現物や改修後の版に対し、達成条件に対応する既存の検査や操作を再実行する。 |

調査で既存実装を見つけた場合は、次の手を検証にできる。検証で不足が見つかった場合は、その実測を振り返りに戻す。実行上の不足は、待機や手段の見直しの理由にする。利用者へ届ける質問は、目標を満たすために本人の判断が必要な要件と、プロジェクトの規則上本人が決める操作に限る。作業先やファイル範囲、通常の検査に関する許可待ちが生じたら、ホストが作業先と runner の状態を照合して、再開または実行不能として記録する。思考プランの採用処理は、この理由を待機や手段の見直しに渡す。

### 受付の根拠と再開

`GoalExecutionSource` と既存の目標試行の受付 ID を使う。本家のホストが登録目標の所有者・版、現在の試行、起動元の出典、通常の作業先と binding の版、実行種別を照合して、Claude Code domain の内部受付に渡す。起動元は目標の記録に基づき、会話起点の受付は引き続き実在する利用者発言を照合する。Claude Code domain では、この入口を会話起点の入口と同じ作業の生成・照会・停止処理につなぐ。会話への報告先は目標側の出典から解決する。 [目標の実行元](../../api/application/agency/goal-execution-source.ts) · [Claude Code の受付](../../api/domains/claude-code/task.ts)

実行元の認可は、既存の `goal_permits` 台帳に作業先単位の版付き scope として保持する。ホストが発行し、通常 runner の workspace と利用可能な操作に結び付ける。従来のファイル範囲と基準コミットを持つ scope は互換用の形式として読む。通常実行の scope は作業先・binding・目標の出典を根拠にし、コミットの変化は検証対象の版として扱う。台帳とキューへの予約は、既存の単一 writer で確定する。 [目標の試行と受付](../../api/application/agency/goal-receipts.ts) · [従来の許可台帳](registered-goal-capability-selection-2026-11-23.md#3-保存と公開操作)

受付前、実行・再開前、観測の採用前に現行性を照合する。受付が不明なら同じ受付 ID で照会し、再起動後も同じ作業を回収する。目標の改訂・取消・全停止・忘却では既存の停止経路を通し、停止確認まで利用枠を保持する。完了判定には現行の受付による証拠を使う。忘却では、由来する作業・証拠・未配送の報告を既存の経路で取り除く。 [復旧処理](../../api/application/agency/goal-recovery.ts) · [結果と報告の既存契約](registered-goal-autonomy-2026-11-23.md#5-結果の採用中断報告)

## 3. 検証結果で目標を閉じる

検証担当は、元の達成条件、調査・改修の記録、検証する成果の版を入力に受ける。検査手順はリポジトリの作業指示、`package.json` の検査スクリプト、対象ソースの既存テストから選ぶ。本家では対象 domain の `bun run verify` と、必要な対象ファイルの試験を使う。足りない試験を追加する場合は、改修の手で扱い、検証では元の達成条件に対応する期待値を照合する。 [本家の検証手順](../../docs/verification.md)

検証担当が選んだコマンドは、実行ファイル・引数・作業ディレクトリの組として検査の受付に渡す。runner が検証対象の作業先に結び付け、通常の保護パスの規則に加えて、検査サンドボックスと終了コードの記録を適用する。ビルドやレポートを作る検査は、成果の版を固定した一時領域で実行する。一時領域には検証に必要なソース、未コミットの成果、依存関係を用意し、製品 DB・設定・秘密は入力から除外する。検査が書き込む範囲は一時領域までとし、試験用サーバーなどが必要な場合はリポジトリの手順と既存の許可に従う。検証の開始・終了時に既存の検証入力 digest で版を照合し、対象の入力が変われば再検証する。 [検査の再実行](../../api/application/agency/goal-verification.ts) · [runner の検査サンドボックス](../../packages/coding-runner/src/claude-supervised-tools.ts#L61) · [検証入力の照合](../../scripts/verification-inputs.ts)

検証記録には、対象の条件、ソースの版と入力 digest、実行した検査、終了状態、実行されたテストと観測を結び付ける。既存の検査結果レポートがある場合はその結果を使い、検査が途中で停止した場合や、条件に対応する試験が実行されなかった場合は未確認とする。条件への適合は検証担当が観測をもとに判断し、ホストは実行記録と版を照合する。全条件の合格が揃った時点で目標を完了し、元の会話へ報告を一件届ける。 [検証と完了](registered-goal-autonomy-2026-11-23.md#5-結果の採用中断報告) · [報告の配送](../../api/application/agency/goal-report-delivery.ts)

## 4. 既存の目標を移す

1. 受付済みの試行と未配送の報告は元の所有元と受付 ID で回収する。旧試行の終了を確認してから、同じ目標の通常実行を受け付ける。
2. 現行版で未達の通常目標には、作業先単位の scope が利用可能になった事実を構成変更として一度渡す。同じ目標 ID・版のもとで過去の観測と未達条件を読み直し、旧範囲を理由に出ていた質問は既存の質問解消処理で扱う。過去の質問を解消できるかの判断には、質問時の不足と今回使える能力を渡す。停止中・取下げ済み・忘却済みの目標と、本人が明示的に取り消した実行権限の扱いを引き継ぐ。
3. 新しい通常の登録・更新と `list_goals` の案内では、目標の内容と進行を扱う。 `workPermission` と `authorize_work` は互換用の扱いに移す。旧形式の受付照会・取消には旧 scope を残す。明示的に作業対象を限定された依頼は、その限定に従って回収・継続可否を判定する。

この設計は、従来の登録目標設計の §4 と、能力選択設計のうち通常 checkout を扱う部分を改訂する。待機中の思考プランでは、段5に通常作業の能力を提示し、段6は本書の受付と検証につなぐ。コミットによる読取許可の失効と登録検査の候補提示の補修は、旧形式の試行を扱う間に適用する。 [登録目標の従来設計](registered-goal-autonomy-2026-11-23.md) · [能力選択](registered-goal-capability-selection-2026-11-23.md) · [思考プランとの接続](goal-idle-deliberation-redesign-2026-11-26.md#5-責務の分け方と置き換えるもの)

## 5. 実装と受入の順序

| 段階 | 合格条件 |
| --- | --- |
| 部分 | ホストの標準 checkout と通常の Claude Code binding から三つの手を提示できる。登録目標専用のファイル・検査設定が空でも、repo 内の複数のディレクトリを読み、新規ファイルを含む必要な改修と検査ができる。通常のツール規則が保護パスと操作境界に適用され、範囲外のファイル要求は作業の失敗として記録される。 |
| 結合 | 会話なしで、受付が同じ作業 ID に戻る。手動端末または Kanban の占有中に別の編集は開始せず、解放後に続く。受付後の再起動、取消、改訂、忘却で重複起動と失効結果の採用が各0件。旧質問の再送0件、切替後の初回判断は1回。runner が不在の場合は再開条件付きの待機になり、作業先やファイル一覧を尋ねる質問は0件。 |
| 通し・改修が要る場合 | 隔離したリポジトリで、公開手順と実装を読み、不足する機能を改修し、独立した検査で元の条件を満たすことを確認する。対象ファイルの事前登録、登録後の利用者発話、作業先・ファイル許可を求める質問は各0件。 |
| 通し・Live2D の既存目標 | 同じ目標 ID と版で、設定「表示」の色選択、設定 API での2色の保存と再読込、背景への反映と既定色への復帰を実測する。ソース修正、追加発話、ファイルや検査の登録、旧質問の再送を各0件とし、全条件の合格で完了報告を一件だけ届ける。 |
| 検証の不成立 | 指定試験が削除済み、実行された試験が0件、条件に対応する試験が未実行、または保存値が期待と不一致の場合は未達とし、観測を次の判断へ戻す。 |

目標側の受付・移行と Claude Code 側の通常実行は、対象の `goals`、`claude-code`、`coding`、`tool-runtime`、`dialogue`、`kanban` の domain 検証で確認する。Live2D の受入では `settings` と `avatar` の試験も用い、固定試験、実 runner、稼働環境での結果をそれぞれ記録する。
