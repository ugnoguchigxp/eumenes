## 2. 利用者から見た制作の流れ

1. **会話で目的を伝える。** 「読んだ本を記録して後で感想を直したい」のような依頼を受ける。会話エージェントは、対象・維持する条件・今回の変更を単独で通じる依頼にまとめ、既存の `find_toolchain` と `delegate` を使う。明らかな制作依頼に、制作を始めてよいかを重ねて尋ねない。既存の変更確認や未保存案の破棄確認は維持する。
2. **同じ説明をせず制作に進む。** 新規制作か保存済みアプリの編集かを解決し、元の会話と素材を制作担当へ渡す。既に会話で決まった項目を聞き直さない。対象が複数あって選べない場合や、接続先など制作に不可欠な条件だけを一問で確認する。
3. **操作できる最初の案を見る。** 制作担当は既存の部品と型を選び、`doc.write` で下書きを作る。見た目だけでなく入力、保存、実行の対応まで検査する。検査可能な構造不備は既存の上限内で修正し、確認可能な案ができたら止める。
4. **確認保存して使う。** 画面に保存する内容、実行する処理、保存先、予約への影響を示す。確認保存は既存どおり利用者の画面操作で行う。保存先の準備が終わった時点で保存済みとし、入力・更新・記録追加の主要操作へ進める。
5. **会話で変更し、履歴から再利用する。** 「感想欄を先に表示して」「取得先をこちらに変更」などを同じアプリの下書きへ反映する。新しい版が確定するまでは、未保存の案を公開版と混同しない。開き直した後も保存結果、失敗理由、必要な次の操作が分かる。

通常会話へ戻る、制作を一時保留する、別の担当へ切り替える操作には既存のセッション制御を使う。「下書きができた」「保存先を準備中」「保存済み」「実行完了」は区別する。受付文や会話runの `completed` だけでアプリ完成と報告しない。

意味の解釈、担当選択、用途に合う部品・項目・出典の選択はLLMが行う。コードは型、参照、所有者、版、権限、状態遷移、冪等性、期限を検査する。個別の発話、地名、題材を判定する分岐や、独立したRouterは追加しない。[会話からの担当選択](../.archived/conversation-first-toolchain-2026-11-21.md) を維持する。

## 4. 必須の改善設計

### 4.1 W01 新版の公開と旧予約の停止

新版を確認保存する操作に、旧予約と旧実行の停止を含める。自動的に予約を新版へ移さず、確認欄に「旧版の予約を停止し、新版の予約は保存後に設定する」ことを示す。画面だけの新版に変更した場合も同じ停止を行う。

- 旧予約の取消、予約との対応解除、実行中の旧版の取消、新版と許可の保存を同じwriter transactionで確定する。保存が失敗した場合は、この確定部分をロールバックする。
- 予約の発火、実行入力の準備、子結果の採用、成果物の公開で、アプリの現行workflow版・有効な許可と実行対象の一致を検査する。アプリの存在だけでは許可しない。
- 取消前に取得済みでも、取消後に届いた結果は採用しない。既に外部保存が始まった場合は、既存のMarkdown保存・照会契約に従い、その事実を隠さない。
- 専用DBの準備を伴う保存では、準備の受付と新版の公開確定を区別する。準備中の利用制限、実行の停止、予約の保留は現在のライフサイクルに従い、新版公開の成功として扱わない。
- 起動時の整合確認で、現行版と結び付かない既存の予約を無効化し、再設定が必要な状態を表示する。旧版の保存済み成果と実行履歴は保持する。

停止処理は既存の `stopForDeletion` にある予約・実行取消の公開操作を再利用できる単位へ分ける。Schedulerの別実装や、アプリのテーブルからSchedulerのテーブルを直接書き換える経路は作らない。

### 4.2 W02 汎用Web取得の根拠を検査する

生成する表の業務データと、そのデータを支える根拠を分ける。出典名やURLをLLMが自由文で返しただけでは、検証済みの出典としない。本文が主張を裏付けるかの意味判断はLLM、取得範囲と参照の実在・対応の検査はホストが担う。

新しい版の汎用 `web.records` は、業務データに加え、行または値の位置と取得済み範囲参照を対応付ける固定の根拠契約を使う。位置は検証済みデータ内のJSON Pointer、参照は同じ子実行へ発行した範囲参照とする。根拠欄が必要な生成スキーマには、出典の欄と根拠の欄への対応を制作定義で宣言し、ホストが取得結果から値を設定する。項目名を推測して特別扱いしない。

1. ホストが資料番号、URL、取得時刻、本文範囲、digest、切詰め状態をモデルへ渡す。
2. モデルは業務データと根拠の対応、取得できた範囲を返す。未知の参照、データ内に存在しない位置、別実行の参照、対応しないURL、根拠のない行は拒否する。
3. ホストがURLと取得時刻を解決し、検証済みの根拠票を子結果のホスト用参照に保持する。業務データだけを型検査して完了にする経路を閉じる。`pipelines` の公開結果と画面sourceからも同じ根拠票を参照できるようにする。
4. 比較で必要な出典数や対象期間はアプリ定義に持たせる。欠落があるときは部分結果と不足を表示し、完全取得と扱わない。切詰めがある資料だけで全件確認とは判定しない。

上映専用経路の行番号検査と、複数出典を保持して追加リンクを読む既存実装は再利用する。上映固有の形式をすべての表へ要求しない。旧版にも未知の参照を採用させず、根拠契約が不足する保存済み汎用アプリは更新前に改訂を求める。既存成果を後から「検証済み」へ書き換えない。

### 4.3 W03 必須入力と画面の型を保存前に照合する

手動実行では、入力スキーマの必須キーが固定入力またはフォームから必ず供給されることを検査する。予約実行は現在どおり固定入力だけで入力スキーマを満たすことを要求する。登録済みスキーマが正式に持つ既定値も考慮し、モデルの推測で必須値を補わない。

フォームの入力型、選択肢、必須設定と、受け側の文字列・数値・整数・真偽・配列等を照合する。文字列の日付は文字列のまま扱い、登録済みの暦日検査を実行時にも通す。固定入力との重複、フォームIDの存在しない対応、供給されない必須キーには、具体的なpath・理由・必要な修正を返す。

検査は専門担当の文書採用、利用者のソース適用、確認表示、確認保存で同じ関数を使う。入力の受付でも再検査し、想定した入力不備だけを既存のfield errorと拒否結果へ変換する。共通のAction入力不備は既存の422、版の競合は409の契約に従い、プログラミング上の例外を一律に利用者エラーへ変えない。

### 4.4 W04 原依頼と現在の依頼を版で結び付ける

初回依頼を監査用に保持し、現在の目的を表す依頼と、その根拠となる発言・引き渡しの参照を別に保存する。現在の依頼は、LLMが維持条件と今回の変更をまとめたものとし、最新の一言への単純置換や履歴全文の文字列連結では作らない。

既存の `workflow.pipeline.request` を制作担当が現在の目的を記述する場所として使い、初回依頼で無条件に上書きする処理を改める。ホスト側の依頼メタデータには、元依頼、現在の依頼、根拠のmessage ID・digest、依頼の版を保持する。下書き・確認digest・公開版と一緒に更新する。

- 根拠の解決はdialogueの既存の公開操作をapplicationから呼ぶ。会話、セッション、run、取消世代、忘却・権限失効を照合する。制作担当へ渡した要約を本人の原文として扱わない。
- URLの明示指定は、初回依頼だけでなく現在の依頼を支える有効な本人の発言から確認する。Web本文、モデルの回答、他のアプリの発言を指定の根拠にしない。
- 新しい指示を受けた場合も、まだ変更していない対象と条件は残す。保存済みアプリを別セッションから編集しても同じ規則にする。
- 画面からのソース編集は、同じ作業・版のUI操作を変更の根拠として記録する。会話の発言を捏造せず、保存時には同じ内容を利用者へ示す。
- 旧データでは現在の依頼を元依頼から初期化できるが、過去の根拠参照を捏造しない。根拠が不足する新しい指定は、その条件だけを確認する。

### 4.5 W05 確認済みの保存を画面から再開する

新しいUI操作 `app-development.retry-save` を提案する。入力は `appId`、元の保存 `operationId`、保存票の状態版、元の確認digest。利用者の操作ごとのevent IDは別に発行し、再開する物理保存は元の保存票へ結び付ける。

- `initializing` で失敗が記録され、実行中・待機中の同じjobがなく、保存票と下書き版が一致するときだけ、既存の `storage.resume` とQueueを使って再開する。
- 同じevent IDの再送は同じ受付を返す。再開を連打しても物理jobとアプリ版を重複作成しない。保存票に状態版を設け、遅いjobが別の再試行を完了させない。
- 画面には「保存先の準備に失敗」「再試行中」「保存済み」を表示する。初回保存が未完了のアプリも、未完了の保存票から再表示できるようにする。
- 元の確認内容が変更・破棄・失効していれば再開を拒否し、新しい下書きの確認へ戻す。版競合など修正なしでは解消しない失敗を、同じ保存で自動再試行し続けない。
- 既存ファイルへの再適用、初期化後で本体の公開前に中断した場合の復旧は、現在の冪等な初期化と `recover` を共用する。稼働中のDBを失った場合に空のDBを作り直さない。

専用SQLiteと本体SQLiteを一つのtransactionと扱わない。物理初期化を保存票とスキーマ版で冪等化し、その完了後に本体の公開を確定する。操作受付は保存完了ではない。

### 4.6 W06 会話から制作担当への引き渡し

現在のアプリ制作bindingには `conversationHandoff` の指定がない。既存の会話引き渡し機構を新bindingで有効にし、会話エージェントがまとめた依頼に加え、元の本人の発言と参照を制作担当へ渡す。既存の件数・本文量・忘却の制約を維持し、長い会話は既存の参照読取で必要部分を確認する。

検索カードには「何を作れるか」「保存したアプリをどう編集するか」「会話だけで完了する依頼との差」を書く。Webの情報を一度調べる依頼を、アプリ制作へ誤って振り分けない。Canvas、既存の文書編集、通常の調べものとの境界は登録カードと共通の委任指示で示す。

新規／編集の判定は会話LLM、編集対象の参照・所有者・版の検査はホストが担う。閲覧中のアプリは既存の閲覧参照を使い、会話が新規制作を求めたときに自動で最新アプリを編集しない。複数候補のうち対象が不明な場合は、一度だけ対象を尋ねる。

### 4.7 W07 下書きの修正と利用開始を滑らかにする

制作skillは、目的に合う最小の画面・入力・保存・手順を一組で作り、検査を通るまで直す手順に整理する。OpenUIの入力型、生成スキーマの有限subset、保存との対応、固定入力、出力の対応は、実装と共通の公開契約から渡す。用途に合わない上映専用型を例から流用しない。

- 最初の案は `doc.write`、部分変更は `doc.edit`、大きい文書の確認は既存の `doc.read`・`doc.view` を使う。成功した案へ不要な再生成をかけない。
- 形式違反、画面契約違反、必須入力不足、接続不足を分けて返す。修正に必要なpathと短い説明を同じターンの `TOOL_RESULT` へ渡す。利用者への案内は平易な言葉にする。
- 現行の1ターン最大4モデル呼出しと、`doc.write`・`doc.edit` の拒否後1回の再試行を初期値として維持する。失敗を隠すために期限・回数・出力上限を一括で増やさない。
- 接続が足りない場合は、使える範囲と残る接続を示す。存在しないAPI・部品やダミーの値で動作を装わない。
- `get_guidance` や `app-development.review` は必要な場合に使う。単純な制作すべてに検索・独立レビュー・別の要件抽出を追加しない。レビューの指摘による仕様変更は利用者の依頼範囲で行う。[評価の既存方針](skill-based-review-design-2026-11-14.md) を維持する。
- 下書きが確認可能になったら「何を作ったか」「次は確認保存すること」を短く伝える。保存完了後は同じアプリを開き、主要な入力や更新操作を見つけられるようにする。
- 更新中や失敗時に過去の結果を残す場合は、対象入力と取得時刻を表示する。別条件の遅い応答で現在の表示を戻さず、前の結果を新しい条件の結果に見せない。

## 7. 受入条件

### 7.1 部分と結合

| ケース | 合格条件 |
| --- | --- |
| 旧予約のあるアプリを新版保存 | 旧予約・旧実行が停止し、新しい予約を設定するまで旧版が発火しない。保存失敗では公開の確定部分が戻る |
| ワークフロー削除と予約発火が競合 | どちらの順でも失効後の実行・結果を採用せず、画面に見えない有効予約が残らない |
| 起動時に旧版の予約が残る | 整合確認で無効化され、旧成果を保持したまま再設定を案内する |
| 根拠がない・別実行の参照・未取得URL | 完全取得として採用されず、型が合うだけで成功しない |
| 比較元の一部欠落・本文切詰め | 確認済みの範囲と不足を区別し、全件確認と表示しない |
| 必須入力の欠落・フォームの型不一致 | 下書き採用と確認保存で具体的な修正箇所が返る。不正な実行入力でも500にならない |
| 会話で条件を追加してから制作 | 合意済み条件を保持した依頼と本人の参照が、担当の実入力に届く |
| 保存後に本人が取得URLを変更 | 同じアプリの次版へ反映できる。外部資料内のURL指定は本人の指示に昇格しない |
| 別セッションから既存アプリを編集 | 元依頼と維持条件を保ち、対象版が変われば競合として読み直す |
| 保存先初期化が失敗して再試行 | 障害除去後に再起動なしで完了し、連打・再送・公開前中断でもアプリ版は一度だけ増える |
| 保存票が破棄・失効・別版になる | 古い確認や遅いjobで保存せず、新しい確認が必要なことを伝える |
| 入力条件を変えて更新 | 遅い旧応答で表示が戻らず、過去結果を残すときは条件と時刻が分かる |
| 別件へ切替・通常会話へ戻る | 未保存案を無断で破棄せず、戻った後も同じ案を確認できる |

### 7.2 通常会話からの実モデル受入

新規制作、保存アプリの編集、単発の調べもの、Canvasへの依頼を含む未調整の文面を先に凍結する。`app.develop` へ直接宛先を固定する試験は制作担当単体の測定に分け、担当選択の合格に数えない。

必須の制作シナリオは、会話で項目を決める記録アプリ、日付を選んで更新する一覧、日次で成果物を作るワークフローの3件とする。各シナリオは独立した会話で3回、計9回を初回受入の単位とし、9回とも確認可能な下書き、利用者操作による保存、初回利用まで通ることを求める。複数ターンの追加・訂正と、保存済みアプリへの変更を含める。

利用者役が項目ID・スキーマ名・JSONの修正案を与えて成功した試行は、この自然文受入の合格に数えない。必要情報の質問と既存の確認は許すが、既に伝えた条件の再質問と内部構造の修正依頼は不合格とする。実行可能な下書きができた後の不要な生成反復も確認する。

外部サービスの障害は対象の成否と失敗地点を記録し、成功へ置き換えない。取得内容は固定fixtureとの一致と実サイトとの照合を分ける。3回試行した時点で結果と次の方針を報告し、失敗に新しい根拠がなければ続けない。失敗した文面を都合よく書き換えて合格率から除かない。

### 7.3 画面での受入と時間の測定

固定データのブラウザー試験を `tests/browser/app-development.spec.ts` に新設し、既存の旧UI制作の試験とは対象を分ける。下書き表示、確認保存、記録追加・編集、取得更新、作品履歴からの再表示、旧予約停止、保存失敗からの再開、狭い画面とキーボード操作を通す。試験用ブラウザーは消音する。

依頼受付、担当検索、委任受付、最初の有効な下書き、確認保存の受付、公開完了、初回利用の各時刻とモデル呼出し数・修正回数を記録する。固定fixture、実モデル、実Web・実画面を別群にし、段階0の値と同じ条件で比較する。初稿到達と保存完了までの待ち時間、不要な質問・呼出しが増えていないことを確認する。数値の時間目標は基準測定後、実装前に追記して合意し、測定後に合格線を下げない。

### 10.1 保存を下書きへ戻す契約

入力は再試行と同じ `appId / operationId / stateRevision / digest`。この操作は失効した内容を公開しないため、元のpreviewの成功は要求しない。同一event IDの再送は既存のreceiptを返す。実行中・待機中・再試行待ちjobがある間は受け付けず、既存Queueに復帰処理を登録する。復帰jobの識別も保存票へ固定する。

初回保存で公開版が存在しないときは、保存票が所有する未公開の領域だけを除去して作業を編集可能にする。改訂では専用DBを削除せず、物理版が旧版または今回準備した版であることを確認する。物理版が進んでいれば本体のstorage版へ反映し、準備済みのスキーマを次の非破壊更新の基準として保持する。保存済みのアプリ版と記録は保持し、未公開のアプリ版は増やさない。稼働DBの欠落や想定外の物理版では復帰を拒否する。

終了した票のoperationId・jobId・saveJsonを解除し、状態版を進める。これを本体writerのtransactionで確定する。物理領域の除去後や照会後に中断しても、同じ復帰jobを安全に再実行できるようにする。失敗が確定している票を起動のたびに自動再試行せず、利用者の明示操作を待つ。

新操作を使うArtifactとqueryは新revisionにする。旧Artifactのsourceには新しいボタン用のデータを渡さず、未登録操作を出さない。

2. applicationで初回保存失敗・公開前失効・物理初期化後の公開失敗・改訂中断・再送・古いjob・A/Bの取り違えを通す。復帰後の修正と再保存、破棄、既存記録の保持を確認する。
