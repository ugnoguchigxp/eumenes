# always-on の Eumenes 取り込み実装計画

作成日: 2026-11-08。状態: **利用者の実装開始指示に基づき、上流修正・Eumenes接続・固定検証を実施。稼働設定とサーバーは未変更。P5のLive実配送対応、P6の全体検証合格、P7の実モデル・利用者受入は未完了。**

利用者の「評価で的確と思える部分を実装計画書にし、周辺実装から見つかる課題も追記する」という依頼に基づく。当初は計画案として作成し、その後の「では実装開始してください」で§7の推奨案を採用した。元の引き継ぎ資料の誤認指摘・訂正は今回の作業対象に含めない。

## 1. 目的と完了条件

会話ごとの背景判断を F runtime から always-on の heartbeat / think へ置き換える。利用者の発言がない間も、会話・記憶・自身の関心から、準備と発話の価値・間合いを LLM が判断する。通常応答にも準備中の仕事・確定した成果を伝え、同じエージェントとして応答できるようにする。

判断以外の部分は、既存の公開操作・保存・権限・実行・配送を再利用する。ホスト側の変更は always-on の入力・票・保存形式を既存契約へ接続するためのものに限定し、語句別の行動分岐、意味分類器、別の記憶管理、別のジョブ実行基盤を追加しない。

実装完了の条件は次のとおり。

- 背景判断は会話ごとに一方の runtime だけが所有し、旧 timer・wake との二重起動がない。
- think と準備の実行は通常応答・steward・専門担当と独立して進む。利用者の新規入力だけを理由に think を中断せず、古い行動は受付・配送前に拒否する。
- 自発実行できるのは、現在の登録と権限が許す読み取り・独立成果物の作成だけ。既存の受付・照会・取消・確定処理を通る。
- 原観測、記憶、過去の作業メモ、準備、結果、通常応答にわたる出典と版が追跡でき、忘却・訂正・期限・権限変更後の再利用と遅延採用がない。
- checkpoint、feed cursor、実行票、結果採用が一貫して保存され、再起動・切り戻し・再送で重複実行や古い発話が起きない。
- 部分→結合→通しの固定検証と、実モデル・利用者 Web での受入を区別して記録する。音声の完成は実機器3往復の受入後に判断する。

## 3. 維持する前提と変更範囲

### 3.1 元依頼から維持する前提

- 利用者についての事実の正本は steward の Memory State。always-on には読み取りの `known` を渡す。自身の仮説、知りたいこと、準備材料は作業状態として区別する。
- 記憶の統合・訂正・停止は steward の責務のまま。always-on に整理目的の自律ジョブを追加しない。
- think ループには呼出回数・費用の上限を設けない。実際の準備実行には既存ホストの同時数・日次回数・冷却・能力別制限を適用する。費用は既存台帳で記録し、欠測をゼロと扱わない。この適用範囲を元依頼の「思考と準備に上限を入れない」の具体化案として、実装前に確定する。
- busy による新規 tick の抑止を維持する。発話の確定時には最新の会話・入力・再生状態を再検査する。
- 旧 runtime へ切り戻せるようにする。異常時に自動で旧 runtime を起動するフォールバックは追加しない。
- 初期の準備は元依頼の A 案を使い、読み取り1種と独立成果物の作成1種程度から始める。能力名・profile・モデル名を製品コードの振分けに固定しない。

## 6. 接続設計案

### 6.1 runtimeの所有と保存

ホストで旧 F / always-on の構成を選ぶ。両方を同じ会話に起動しない。共通にするのは公開操作・票の検証・出典・実行・配送の接続に必要な最小範囲だけで、二つの状態モデルを一つの巨大runtimeへ統合しない。

保存envelopeは少なくともruntime種別、ホスト形式版、scope、epoch、状態の変更番号、snapshot、scheduler checkpoint、設定digest、入力manifest参照を区別する。既存のAgencyStatePortと単一writerを拡張して使う。旧snapshotを型castして新runtimeへ渡さない。schema変更は新migrationとし、適用済みSQLを書き換えない。

観測本文はMemory Recordsに置き、ホストcheckpointにはID・版・digest・出典を残す。always-on本体のrestoreに本文が必要なら、現行の公開Memory読取り境界から検証して組み立てる。原文をDB内外へ別保存する専用経路は作らない。

### 6.2 発行・受付・結果の境界

LLMが行動を選ぶ→coreが形式・参照・自発可否を検査する→ホストが票と入力版を保存する→現在の権限・予算・出典を再検査する→既存のexecutionを受付、の順にする。実装方法は既存domainの公開操作を拡張する形で確定する。

同じ票・同じ入力は同じ実行を照会し、別入力なら競合として拒否する。結果不明では新しい仕事を作り直さない。受付拒否と受付後の実行失敗を区別し、受付成功を成果の成功として伝えない。返却は現在の実行元を検証してから結果同期・core反映・checkpointを一つのwriterで確定する。rollback時はメモリー上のcore変更を破棄または復元し、次回の再採用を可能にする。

選ばれた能力の引数schemaとeffect・承認条件は既存registryから取得する。A案の公開集合もデータで決め、能力名のコード分岐を作らない。`AlwaysOnTool`は引数schema欄を持たないため、既存カードの引数契約を説明へ渡し、受付時は元schemaで検査する。効果が引数や実行先で変わる能力は静的な`read`表示だけで許可しない。

### 6.3 指示と通常応答

まず既存TOML資産・`systemContext`・`conversationPersona`・ネイティブschema経路を再利用する。think向けのframe・safety・動機付け・公開出力契約をEumenes所有の指示へ移し、通常応答と同じ人格で構成する。取り込み元のCLI全体や固定モデル設定は移植しない。短縮する場合は能動性の同条件比較を行う。

通常応答には、現在時刻、正本のknown、準備中の状態、確定成果、必要な作業メモを既存の動的State区画へ渡す。仮説と確定結果を区別し、作業メモを外界の事実の証拠にしない。実際に表示した入力manifestを回答の出典へ継承する。動的状態をsystemへ入れてcacheを毎回無効化しない。

通常依頼は既存delegate/実行元を第一候補として再利用する。`start_preparation`の追加が必要な場合も、同じ依頼を通常delegateと二重実行しないこと、元のrun/発言の同一性、AO-N4、既存承認経路との境界を先に固定する。通常応答で成果を共有した場合の共有済み記録も、実配送後の既存記録と照合する。 実装では、通常応答の確定観測を次のthinkへ渡し、既存の`stock.drop`で共有済み材料を整理する。`usedAt`は票に対応する実配送receiptだけで更新し、通常応答の本文からホストが共有内容を分類しない。stateを読んだだけで共有済みにしない。

### 6.4 独立推論とbusy

保存済みの接続とruntime catalogを正本とし、think専用のresource参照はsettingsの新しい契約で選ぶ案とする。選択不能時は準備・思考の利用不能を明示し、通常応答の接続へ無断で戻さない。既存の独立接続・helper機構で分離できるかを先に確認する。共通poolで要件を満たせない場合だけ、測定・再現根拠を添えて接続所有範囲の最小拡張を決める。

reasoningの努力度は保存済み設定から渡し、独立接続にした結果既定のlowへ落ちないよう検証する。thinkのsystem・schema・期限・出力上限は技術契約として検証し、モデルやprofileの文字列で分岐しない。cacheは固定指示の再利用と既存provider契約を使い、特定providerの1時間指定を全経路へ一律に要求しない。

新しい利用者入力では進行中thinkの行動だけを無効化し、通常応答は待たせない。忘却・取消・権限失効・ホスト停止・runtime切替では対象結果を採用しない。取消済みの推論結果も内側のstateへ保存しない契約を確認する。busyの開始・終了は重なりを扱い、heartbeat自身の実行中カウントを利用者busyと混同しない。

### 6.5 複数会話・再起動・切り戻し

初期案は、既存attentionで選ばれた表示中または最後に話した1会話でheartbeatを回し、非選択会話では新しいthinkを始めない。受付済みの準備は既存executionとして進め、結果を元の会話へ保存する。別会話へ発話を転送せず、戻った会話で新しい入力・間合いを見て話す。これは設計選択であり、非表示会話でもthinkを継続するかは実装前に合意する。

現行の非表示30分・追跡20会話の整理はruntimeのメモリー解放として再利用し、受付済みジョブや必要な返却対応を消さない。古い結果のためにruntimeを再作成するときも、保存された種別・世代を確認する。

再起動では新しいtickの前にjournal照合・出典検査・実ジョブ照会を完了する。未配送発話を再送しない一方、既に確定した文字配送・実字幕の証拠は復旧し、発話回数と共有済み状態を失わない。coreのsnapshotに未配送票がないことだけで復旧が完了したと扱わない。

切替は新規tick停止→旧世代の行動失効→進行中の受付・結果状態の保存→所有runtime切替、の順にする。新規scope/epochまたは同等の永続境界で古い票を拒否する。切替前の仕事の取消・結果保管を明示し、別runtimeへ再委譲しない。切り戻し後も、旧保存を新しいknown・忘却・現行権限で再検査する。

取り込み元のS1〜S10は維持するが、それだけではホストの配送・権限・保存・推論の受入にならない。事例専用の製品条件分岐を追加しない。試験の入力名や対象を変えた場合も同じ契約を通す。

### 9.2 結合

1. 通常応答と背景thinkが並行し、user入力で旧行動だけが失効する。steward・専門担当の実行も互いにpreemptせず、共有接続待ちに直列化されていないことを偽providerの開始・終了順で確認する。
2. think→prepare票→既存capability/adapter→execution→確定結果→stock→自然な共有→既存成果物表示を通す。外部I/OとLLM応答だけをfixture化し、製品の実行経路を別のmock実行器に置き換えない。
3. 通常依頼と自発準備が同時にある会話で、発言・run・権限・入力版・通知の所有を混同しない。
4. Memory訂正・忘却・期限、再起動、runtime切替を受付・返却・配送の各境界へ差し込み、古い採用がなく独立したBの会話・仕事は継続できることを確認する。

### 9.3 通しと実受入

実装で変更した所有domainとその利用側を `bun run verify -- --domain <name>` で選ぶ。現時点の候補は dialogue、inference、larm、settings、memory、conversation、delivery、tool-runtime、agent-runtime、capabilities、live-voice、voice-dialogue。全候補を無条件実行せず、実際の差分・domain依存を確認して選定し、理由を記録する。Agencyはapplication配下なので、独立した`agency` domainがあると仮定せず、登録済み結合と必要なファイル指定試験を使う。

```sh
bun run verify -- --domain dialogue --domain inference --domain memory --domain tool-runtime
bun test api/application/agency/llm-port.test.ts api/application/agency/connection.test.ts api/application/agency/continuity.test.ts api/application/agency/continuity-actions.test.ts api/application/agency/archive-recovery.test.ts api/application/agency/checkpoint-sources.test.ts
bun run context:check
```

上記は入口の例であり、新設した結合試験のinventory登録と他の変更domainの選定を省略する指示ではない。E2Eは変更した画面・音声・Artifactの試験ファイルを明示し、headlessは消音する。`verify:all`へブラウザE2Eを混ぜない。既存の保管コピーや並行差分で標準入口が停止した場合は成功扱いせず、阻害箇所と代替した同等検査を別記録にする。

実モデルは採用版・同一努力度・同一シナリオで複数回比較する。tick内LLM時間だけでなく、出来事→tick開始、待ち時間、実行受付、結果返却、利用者への配送までを分けて測る。結果を作った数に加えて、実際に有用だった準備、共有の遅れ、反復、静穏希望・作業中・睡眠中の抑制、紛れた指示への耐性、通常応答の遅延を確認する。費用の上限追加はせず、実モデルを実行する範囲・接続・料金条件は事前に合意する。

最後は利用者がEumenes Webで会話し、未依頼の準備が役立つこと、良い間合いで共有すること、止めてほしいときに引くことを確かめる。HTTP正常応答やモデルの発話件数だけを完了条件にしない。
