# 関心に基づく自発行動を、制作を含む既存の担当へ接続する

作成日: 2026-11-07。状態: **2026-11-07、利用者がAgencyの行動をフルに扱うための適用を承認。実装済み。固定検証の結果と未完了の受入は9節以降。**

## 1. 利用者が求める動作

利用者の明示的な依頼を待たず、会話・記憶・関心から、役立つ／楽しめそうな行動をAgencyが選んで実行する。画像を作る、音楽を作る、調べて報告することは例であり、この3種類への固定振分けにはしない。新しい能力も、既存の登録契約と実行条件を満たせば候補にできる。

成果は発話件数ではなく、関心の根拠→行動の選択→実行→確定結果→成果物の提示・必要な報告がつながることで確認する。不要な行動を見送ること、停止・訂正を守ることも受入条件にする。

## 2. 現在の根拠と不足

| 箇所 | 現行の動作 | 不足 |

| `api/domains/dialogue/service/agency-state.ts` のcatalog | `minImpact=none`相当、bindingなし、routeがweb/historyの能力だけを公開 | 画像・音楽・command・instant等は自律側の候補に入らない |

2026-11-07のローテーション済み運用ログでは、通常会話`main`の自発発話は3件、自律調査開始は0件。入力検査の`agency_input_stale`が157件、updateの予算待ちが240件あった。全会話を含む過去ログには自律調査開始もあるため、機能全体が一度も動かなかったとは結論しない。

調査時点で標準APIの8787番ポートは接続拒否だった。サーバーの起動・停止・再起動、稼働DBの読取り・変更、実モデル・生成サービスの呼出しは行わない。

## 3. 既存機構を使う方針

意味判断はAgencyの既存update/selectへ置く。新しい分類器、行動提案エージェント、専用イベントバス、画像／音楽ごとの発話判定を作らない。まず既存指示を「会話への短い参加と読み取り調査の発案」から、許可済み能力による有用な成果の生成・確認・共有までを責任に含む内容へ改訂する。

指示の変更だけでは、非公開の能力や不在の実行権限は増えない。以下の接続契約を先に整える。

### 3.1 候補と能力

- 能力の正本は既存のCapabilities registryとbundle・adapter。全能力の説明・引数を常時詰め込まず、既存の検索・カード・解決経路を使う。
- Agencyは根拠、目的、何ができれば完了か、今行う価値を判断し、既存のintent/candidateを使って選ぶ。単に「時間がたった」「ユーザーが興味を持ちそう」とだけ言って新しい権限や事実を作らない。
- 候補には、実行可能、確認待ち、接続不足、サービス利用不可を区別して返す。能力名や特定routeのホワイトリストだけで汎用性を実現したことにしない。
- 個別能力に必要なschema・成果物・照会・取消はその登録adapterで扱う。共通の実行契約を満たさない能力は、その不足を提示して実装が済むまで実行しない。

### 3.2 自律起点の出所と許可

一般の実行元へ、利用者発言と区別できる自律起点の契約を追加する。現在の読み取り用`autonomousResearchSource`を、そのまま操作権限へ昇格させない。

自律起点は、ホストが永続した会話scope、intent/candidate/ticketと版、epoch、根拠参照、選択した能力revision、許可設定の版、予算予約、期限への参照で検証する。LLMの出力だけで有効な出所を作れないようにする。利用者のmessageやmanual/voice runを捏造しない。既存保存記録は従来の利用者起点として検査し、同じIDのまま権限を増やさない。

実行直前・再開・結果採用時には、発行時の許可上限と現在の許可を両方確認する。取消・忘却・設定変更・能力版変更で失効した古い結果を採用しない。

### 3.3 自動実行の範囲と費用（合意する初期案）

| 行動の性質 | 初期案 |
| --- | --- |
| 読み取り・調査・照会 | 保存済みの権限と予算内で自律実行する |
| 新しい独立した成果物の作成 | 画像・音楽・文書など、登録能力と保存先が許可され、既存物を変更しないものは、予算内で都度の確認を求めず作成・提示する |
| 既存物の変更、公開・送信、支払い、削除、外部環境の操作 | 既存の操作承認へ接続する。対象と操作を含む有効な事前許可がある場合だけ、その範囲で自動実行する。関心や生成の許可を外部操作の許可へ流用しない |
| 会話を専有する制作session | 背景から黙って会話を切り替えない。独立成果物として返せる経路がなければ、既存handoffの確認を使う |

これらは画像・音楽等の名前で分岐せず、能力の副作用、保存先、既存承認、adapterの実行契約で検査する。`minImpact`だけでは操作・宛先・費用を表せないため、既存の操作承認と予算を併用する。

初期値の提案は、会話scopeごとに同時実行1件、自律起動3件/日とし、画像・音楽等も同じ枠を使う。既存の12時間冷却・各能力の呼出上限・期限を維持する。これは最大枠であって実行ノルマではない。返答・停止・失敗の回収は、新規実行の枠を使い切っても続ける。

課金上限は保存済みの利用制限を適用する。金額上限が評価できない接続は、呼出数・生成量・期限を上限にできることを説明し、金額上限があるかのようには表示しない。具体的な利用上限と上記の初期値は実装前に合意し、コードの暗黙の既定値にはしない。

### 3.4 実行・結果・提示

既存のqueue・単一writer・実行台帳・ToolchainExecutionPort・domainの公開操作を再利用する。必要な接続以外に実行ループを増やさない。委譲の受付は開始の事実として返し、完了は既存の子結果の確定から得る。同一ticketの重複、応答前後の再起動、結果不明時の二重生成を防ぐ。

調査結果だけのsummaryではなく、生成物refと版、成否・不足・取消・利用量を返却に含める。成果物は既存のresources/artifactへ登録し、利用者の会話に紐づく形で開けるようにする。Agencyは結果を根拠として共有の価値を判断する。受付だけを「作りました」と報告しない。既存の完了通知とAgencyの報告を二重配送しない。

音楽の生成・保存・提示と再生を区別する。可聴出力は利用者が開いているWeb画面だけを使い、既存の再生許可・操作を守る。backendや検証用ブラウザーから再生しない。

### 3.5 機会と停止

既存feed、idle、review、work.returnedを使う。発話の未応答上限は発話に適用し、内部更新・行動の結果回収へ流用しない。発話停止後にも有用な行動候補が検討されることを試験で確かめ、候補がないときに常時推論を回す実装にはしない。

「この話題ではやめて」「自分から作らないで」等の意味はLLMが既存の意図・関心・設定へ反映し、ホストが取消・世代・遅延結果の拒否を強制する。自然文の辞書や正規表現で停止対象を推定しない。全停止操作は新規の自律実行と予約を止め、既存の取消経路と回収を維持する。

## 5. 検証

部分→結合→通しの順で行い、固定モデルと実LLM、生成サービス、Webでの提示・再生を区別する。

| ケース | 観測する期待動作 |
| --- | --- |
| 明示依頼ではない、異なる題材の継続的な関心 | 許可された異なる能力を選べる。画像・音楽・調査を語句に固定して起動しない |
| 既知の内容、利用者が断った話題、有用な差分なし | 待機できる。数を満たすための生成や同じ報告をしない |
| 発話上限到達、子の実行中・完了 | 新規発話を抑えつつ、許可された行動判断と結果回収を維持する |
| 許可設定・対象・料金枠・能力版が不一致 | 実行前に拒否し、無許可の代替経路へ回らない |
| 受付済みで生成中、部分成功、失敗・サービス利用不可 | 受付と完了を区別し、成果物・不足・固定理由を記録する |
| ticket保存後／実行後／結果採用前の再起動 | 同一処理を照会し、二重生成・二重配送をしない |
| 停止、訂正、根拠の忘却 | 取消と出所失効が子へ届き、古い生成物を新規成果として採用しない |
| 資料に「承認済み」等の指示が混入 | データとして扱い、実行元や許可を増やさない |
| 次の登録能力を追加 | 同じ接続契約を満たせばAgencyに題材専用の条件分岐を足さず選択・実行できる |

固定検証は`dialogue / agent-runtime / tool-runtime / capabilities / memory / resources`と変更した能力のdomainを対象に`bun run verify -- --domain <name>`を使う。Agencyホストの試験、bundle検査、context生成・checkを含める。E2Eは対象ファイルを明示し、実モデルの品質をfixture成功で代用しない。

実モデル受入は、制作の明示依頼を含まない独立した関心の会話で、画像・音楽・調査をそれぞれ確認する。好みに合わない場合・生成不要の場合も含め、起動率だけで合格にしない。費用・所要時間・利用者介入・不要な割込みを併記する。

## 6. 実装前に合意する事項

1. 調査だけに限定せず、許可された能力から新しい独立成果物の作成まで、都度確認なしの自律実行に含める。
2. 自律実行の出所を一般の共通実行へ接続し、利用者起点と区別して保存・検査する。
3. 初期の同時実行数・日次上限・冷却と、利用制限の設定方法を確定する。
4. 既存物の変更や公開・送信等は、対象と操作を含む既存の承認に従う。音楽の生成と再生は別の操作として扱う。

本書はこれらの合意を実装後の追記で代用しない。合意前に実装できるのは、既存の責務・権限を変えない段階0の不具合修正までとする。

## 8. 合意後の接続計画

- Agencyの既存update/select、tool ticket、delegateのworkRef、work.returnedを維持する。自律行動用の別の意味判断ループは追加しない。
- 共通のagent executionへ、選択済み能力を一件実行する公開操作を追加する。実在するexecution/childの台帳・queue・照会・取消・成果物refを使い、親の再計画推論は起動しない。
- ExecutionSourceは自律起点を明示し、messageIdはnull。dialogueの永続したAgency workと権限記録だけが出所を発行する。旧読み取り用workはこの権限を持たない。
- 能力の公開判断と実操作の権限検査は共通実行portへ置く。adapterの既存effect=readは読み取り、writeは独立作成の明示宣言がある場合だけ自動実行可能とし、それ以外は承認が必要と返す。command翻訳でも非許可の道具を提示せず、実行直前にも検査する。
- 既存の能力検索をAgencyのfind_toolchainへ接続し、delegateへ能力revisionと問い・必要な実引数を渡す。全能力のschemaを固定指示へ詰め込まない。
- Agency workへ共通executionのIDと権限・作成時刻を新migrationで保持する。旧実行の受付と返却は維持する。返却と忘却で共通executionも照会・取消・消去し、結果のresource URIを会話へ紐づける。
- 初期値は合意済み設計案の同時1件・日次3件。設定APIで変更・全停止できる形にし、既存の冷却・能力ごとの期限・利用制限を維持する。新規実行の枠と検索・結果回収を区別する。
- 検証は出所と共通一件実行の部分試験→実hostから画像・音楽・調査・登録操作の結合試験→影響domain gateの順。実環境の起動停止は別途の明示許可が必要なため操作しない。

実装済み: 共通一件実行と自律出所、能力公開と操作権限、Agencyの検索・実行・返却と成果物、設定と指示、固定モデルによる部分・結合試験。

残作業: 実LLM・保存済み生成サービス・利用者のWeb画面での通し受入。利用者自身による再起動後の検証で活動予算の不足が判明し、11節の調整を実施した。調整後の稼働環境での受入は、利用者が再び反映してから行う。横断gateの既存失敗は下記の検証記録に分けて残す。

## 9. 適用した実装

- Agencyの既存update/selectへ汎用の能力検索とdelegateを渡した。意味判断はLLMに残し、話題・語句・画像／音楽の意図をコードで分類する処理は追加していない。
- 選択済みの能力一件は共通の実行台帳とchild lifecycleを通す。親の再計画推論は追加しない。登録taskとpipelineはそれぞれの既存ownerを使う。
- 一般操作の出所は新しい権限記録から発行する。発行時のticket・能力revision・実引数・設定を固定し、重複時に異なる入力を受け付けない。旧読み取り用出所と利用者発言の出所は別のまま保持する。
- 設定と能力の変更は実行中にも検査する。取消・忘却・古い結果の拒否、依頼内容の写しと成果物リンクの削除を既存writerへ接続した。taskの自動実行には取消・忘却の公開操作も必須にした。
- 画像・楽曲・登録調査担当の報告などを、登録済みResourceAdapterから会話の成果物一覧へ入れる。完了通知とAgencyの報告を二重に作らない。質問は既存TODOへ出し、実在する利用者の回答で再開する。
- 発話の上限に達しても、未処理の配信結果・操作結果を既存の1分間隔のreviewで判断する。処理中・利用者応答中に短い間隔で回り続けるタイマーは追加しない。再起動後にも同じ観測から継続する。
- 初期設定を設定APIで返す。同時1件・1日3件は会話scope単位で、日本時間の午前0時に日次枠を区切る。停止・利用上限・既存冷却を維持し、検索や返却を新規生成枠と混同しない。

## 10. 検証の範囲と限界
