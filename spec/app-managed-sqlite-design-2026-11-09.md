# Webアプリ開発で作るアプリの専用SQLite

2026-11-09。実装と検証の記録は末尾に記載する。

Webアプリ開発で、利用者が入力した記録を次回も開けるアプリを作れるようにする。保存が必要なアプリには専用のSQLiteファイルを割り当て、アプリの削除操作でそのファイルと補助ファイルを削除する。確認対象は読書メモのような記録アプリとする。上映一覧の取得先は既存の取得手順キャッシュ側で扱う。 [既存のアプリ設計](reusable-content-workflows-design-2026-11-09.md#webの取得手順)

## 現状と追加する責務

| 責務 | 現状と追加案 |
| --- | --- |
| `app-development` | 現在は下書きと確定版を本体SQLiteに保存する。専用DBの有無、保存先の識別子、スキーマ版、作成・更新・削除の状態を管理し、作品履歴から削除できるようにする。 |
| SQLite基盤 | 既存の接続管理、単一writer、排他を利用する。アプリ専用ディレクトリとファイルの作成・終了・削除をbackendが行う。 |
| OpenUIとワークフロー | 保存済みのアプリ版が許可した操作を、既存のArtifactとワークフローの入口から実行する。予約の停止と実行の取消には各domainの公開操作を使う。 |

既存の下書きには画面、ワークフロー、生成スキーマがある。保存済みアプリの削除操作と、アプリデータ用の物理ファイルは今回追加する。 [アプリの保存形式](../api/domains/app-development/index.ts) · [アプリの操作](../api/application/app-development/app-development-adapter.ts) · [SQLite基盤](../api/infrastructure/sqlite/index.ts)

## 制作時の定義

LLMは、依頼にデータの永続保存が必要か判断し、必要なら下書きに `storage` を追加する。記録の項目・型・許可する操作を宣言する。確認画面にはコレクション、項目、読み書きの範囲、アプリ削除時に記録も消えることを表示する。保存を確定した時点でbackendが専用DBを用意する。

読書メモの下書きに追加する `storage` の例。

```json
{
  "storage": {
    "version": 1,
    "collections": [
      {
        "id": "reading_notes",
        "schema": "reading-note",
        "operations": ["list", "get", "create", "update", "delete"]
      }
    ]
  }
}
```

`schema` は同じ下書きの `schemas` にある行スキーマの名前を指す。`reading-note` なら書名、読了日、感想を定義する。既存の有限JSON SchemaからZodへの変換を使い、画面だけの保存型アプリもスキーマを参照できるようにする。項目名・型・件数とサイズを検証し、許可した型からbackendがSQLiteの列定義を生成する。レコードID、更新版、作成・更新時刻はbackendが発行する。 [既存のスキーマ変換](../api/domains/capabilities/service/json-schema-subset.ts)

実行時は、画面やワークフローがコレクション名と登録済み操作を指定する。backendは利用者のscope、保存済みアプリのIDと版、操作の許可を照合してから、値をパラメータとしてSQLに渡す。SQLiteファイルのパス、SQL文、移行スクリプトはbackendが所有する。初版の一覧はページ単位で読み、必要な検索・並べ替えは許可済みの項目に絞る。画面の読み取りはAPIで返し、ワークフローが永続的に保持する受け渡し値には専用DB内の参照を使う。台帳と運用ログはID・状態・件数を扱う。

画面の `screen.storage` は、表示する `collection` とフォーム項目IDから列名への `inputs` を指定する。入力・編集には既存のOpenUIフォームを使い、記録一覧には同じコレクションで許可した操作を表示する。一覧は25件ずつ取得する。ワークフローの `storage.records` は、許可された一覧・個別参照・削除を扱い、結果には記録IDと版を残す。記録の新規作成と本文の更新は画面のフォームから行う。

## ファイルと保存の整合

- 本体SQLiteの台帳で `(scope, appId)` と専用の `storageId` を対応させる。ファイルはbackendが選ぶローカル領域の `<storageId>/app.sqlite` に置く。タイトルを変更しても保存先は同じ。
- 保存確認後、本体SQLiteに初期化の受付とQueueの仕事を同じtransactionで登録する。専用DBでスキーマとその版を確定し、読めることを確認してから、確定版とストレージの対応を公開する。同じ確認の再送は既存の受付を返す。
- ファイルの初期化と本体SQLiteの確定の間で停止した場合、再起動時に台帳とファイル内のスキーマ版を照合し、続きから処理する。稼働中のアプリのファイルが見つからない場合は、異常として表示し、空のDBで既存の記録を置き換える操作を拒否する。
- 同じアプリ内の記録更新は専用DBのtransactionで行う。更新と削除はレコードの版を検査する。同じ操作IDと入力の再送は同じ受付を返し、同じIDで異なる入力が来た場合は競合を返す。受付記録も専用DBの同じtransactionに置く。
- アプリ版の更新ではデータを引き継ぐ。初版の自動移行は任意項目と新しいコレクションの追加に限る。移行中はアプリを一時停止し、専用DBでスキーマ更新を確定してから新しいアプリ版を公開する。中断時は台帳と専用DBのスキーマ版を照合して再開する。

本体SQLiteの台帳と専用DBの確定は、Queueと状態記録でつなぐ。WALでは、`ATTACH` した複数DBの変更をクラッシュ時も一括で確定できる保証がない。 [SQLiteの複数DB transaction](https://sqlite.org/lang_attach.html)

## アプリの削除

作品履歴の「アプリを削除」から実行する。確認画面に対象名と「このアプリに保存した記録も削除されます」を表示し、アプリID、現在の版、確認digest、操作IDを照合する。保存やスキーマ更新と削除は、アプリ単位で同時に一件だけ受け付ける。

1. 本体SQLiteのwriterで `deleting` を記録し、削除の仕事を登録する。以後の読み書き、実行、予約設定を閉じ、既存の予約を停止して実行中の処理を取り消す。古いタブからの操作と遅れて届いた結果も、アプリの状態を照合して拒否する。
2. 受け付け済みのDB操作を収束させ、専用DBの全接続を閉じる。その後で管理下のアプリ専用ディレクトリを消す。対象には `app.sqlite`、`-wal`、`-shm` などのSQLite補助ファイルと、同じ領域に作った初期化・移行用ファイルを含める。削除先は台帳から解決し、管理ルート外やシンボリックリンク経由の削除を拒否する。 [SQLiteのWALファイル](https://sqlite.org/wal.html#the_wal_file) · [開いているDBファイルの扱い](https://sqlite.org/howtocorrupt.html)
3. ディレクトリが存在しないことを確認してから、本体SQLiteのwriterで `deleted` を確定し、作品履歴と保存済みアプリの参照から全版を除く。再送の照会と古い参照の拒否に使う削除受付を保持する。これを画面上の削除完了とする。

途中でbackendが終了した場合は、再起動後に `deleting` から再開する。すでに対象が消えていれば手順3へ進む。権限やI/Oの失敗でファイルが残る場合は、作品履歴に削除待ちと理由を表示する。作品履歴での操作受付と、ファイル削除の完了を区別する。

削除範囲はEumenesが管理するアプリと専用DBの領域。確認画面にその範囲を示す。別途取得した運用バックアップや外部の保存先では、それぞれの保持・削除規則を適用する。

## 実装順と受入条件

1. **ファイルの管理と削除**。台帳、専用DBの作成、接続の閉鎖、削除受付と再開を実装する。初期化中、接続を閉じた後、ファイル削除後から本体の確定前で停止を注入する。再起動で処理が完了し、対象外のアプリのDBが読めることを確認する。
2. **制作と型付き操作**。`storage` をアプリ定義と確認画面に追加する。読書メモの依頼からEumenes自身が下書きを作り、確認保存後に記録を追加・編集・一覧表示する。再起動後も記録が読めることと、型違反、scope違反、古い版、二重送信が拒否または同じ受付として処理されることを確認する。
3. **作品履歴からの通し試験**。2つのアプリにそれぞれ記録を入れ、片方だけを削除する。予約・実行・別タブがある場合も、削除完了後に対象アプリを開けず、専用DBと補助ファイルが消え、もう片方の記録が残ることを確認する。ファイル削除に失敗する試験では、完了表示より先に障害が見えることを確認する。

部分・結合試験は `bun run verify -- --domain app-development --domain ui-compositions --domain pipelines --domain scheduler` を起点にする。画面からの受入は、固定データのブラウザー試験と、Eumenesが自然文から制作する実モデル試験を分けて記録する。

## 実装と検証

- ランチャーと制作担当の表示名を「Webアプリ開発」に更新した。アプリ、履歴、担当の内部識別子を継続して使う。
- 固定試験では二つのアプリに記録を追加し、入力の型、記録の版、同じ操作IDの再送、共通の操作履歴に記録本文が残らないことを確認した。片方の削除でSQLiteと補助ファイルが消え、もう片方の記録は読めた。シンボリックリンクで削除を失敗させると、履歴に削除待ちが残り、リンクを除いた後の再試行で完了した。
- 永続キューと本体SQLiteを開き直し、初期化前、ファイルへの移行を確定した後、ファイルを消した後の中断から再開した。任意項目を追加しても既存の記録は読めた。稼働状態のファイルを失った場合、空のDBを作り直さずエラーにした。
- ワークフローは記録のIDと版だけを結果に保持した。アプリの削除で予約と実行を取り消した。上映アプリの固定試験では、公式ページの取得・表示・再更新に専用DBの領域が作られなかった。
- 隔離Chromiumで、フォームからの記録追加と編集、削除確認、履歴とSQLiteの消失を確認した。実モデルの試行ではスキーマ名の不一致と `screen.storage` の欠落を検出し、下書きを修正する欄と対応関係を返すようにした。修正後は実モデルが自然文から読書メモを作り、確認保存、記録の追加・編集、アプリと専用SQLiteの削除まで25.8秒で通った。
- 標準検証は既存のPursuit試験スナップショットの列挙で停止したため、バックエンドと画面の対象試験を指定して実行した。画面78件と、最終変更後のアプリ開発・初期登録の15件が通過した。稼働中のEumenesへの反映はサーバーの再起動後に確認する。
