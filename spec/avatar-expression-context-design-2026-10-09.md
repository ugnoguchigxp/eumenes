# アバター表情とTTS感情制御の現状調査と改善設計

調査日：2026-10-09。対象：現在のEumenes作業ツリーとgnosis上のRyzen AI MAX+ 395。状態：**調査・小規模評価・設計まで。製品実装は未変更、実装は承認後。**

## 判断と推奨方針

**文脈は必要だが、Layaに文脈を追加するだけでは改善を保証できない。** 実機の小規模比較では、チャンク単独の一致率48%に対し、ユーザー文脈追加・直前チャンク追加はいずれも44%だった。まず判断対象を「文章に含まれる感情」から「現在のチャンクをアシスタントがどう話すか」に揃え、評価データと確率の校正を整える。そのうえで、文脈を使う条件と遷移制御を選ぶ。

重要な現状差がある。依頼文の「ストリーミング中に各チャンクを判定」と異なり、現在の作業ツリーは**回答全体の完成を待ち、回答単位の判断をすべての音声チャンクに再利用する**。直近の会話情報もすでに入力している。今回の条件を満たすには、全文待ちを外し、判断単位をチャンクに戻す設計変更が必要である。

推奨順は次のとおり。

1. 現行Layaで、固定した日本語の発話目的・A/B/C入力・候補絞り込み・校正の効果を切り分ける。
2. 採用可能な精度が得られた場合だけ、因果的なチャンク処理と軽いヒステリシスを実装する。
3. 改善が限定的なら、Ruri-v3-30m＋分類ヘッドとVerdict Smallを同じデータで比較する。
4. 小さな分類ヘッドで不足する場合だけ、37M程度のEncoderの追加学習を検討する。

追加のLLM呼び出し、英訳、表情判断用の文章生成は不要。5種類の表情と通常状態を維持する。**通常を含めると評価・分類は6クラス**になる。

### 表情と音声の対応

| 判定 | アバター動作 | TTSの調整 | 回答名横の表示 |
| --- | --- | --- | --- |
| none | neutral | natural | なし |
| warmth | agreeing | bright | 🙂 |
| joy | joyful | bright | 😊 |
| empathy | listening | gentle | 🤍 |
| curiosity | curious | natural | 🧐 |
| surprise | surprised | bright | 😮 |

音声はVOICEVOXの話者・スタイルIDを感情別に切り替える実装ではない。`speed`・`pitchScale`・`intonationScale`への小さな補正である。brightは順に+0.05・+0.02・+0.15、gentleは−0.06・−0.01・−0.10を基本値に加える。ユーザー設定の強さと範囲制限もある。**判定が合っていても、望む感情が聞き取れるとは限らない**ため、判断と音声表現の評価を分ける。

### 判断ミスにつながる要因

- **目的の違い**：現在の指示は文章の感情分類。求めるのはアシスタントの発話態度。相手の悲しみや、説明中の「失敗」をそのまま表情に移してはいけない。
- **全文の単一判断**：祝福から手順説明へ移る回答でも、全チャンクが同じ表情になる。全文待ちは初回発話を遅らせる。
- **候補の取りこぼしと偏り**：語句にない自然な共感はモデルへ届かない一方、候補を狭めると確率が高く見えやすい。通常が多い原因を「モデル」「事前の候補除外」「閾値」に分けて測る必要がある。
- **前処理の情報損失**：引用・コード・定義的な文を除く処理がある。技術説明の誤判定を抑える反面、引用された名前など発話意図に必要な内容まで落とし得る。600文字の先頭・末尾だけでは回答の中間も失う。
- **未校正の確率**：実機設定の温度は既定値の1。`0.6`は「60%正しい」の保証ではなく、候補内の出力スコアの閾値である。公式モデルカードも未校正・過信とタスク依存の限界を説明している。[Laya公式仕様](https://huggingface.co/convaiinnovations/laya-multilingual)
- **短い読点チャンク**：音声として早く出したい単位と、意味判断に十分な単位が一致しない。未来の文を待たず、すでに生成済みの直前部分を補助に使う必要がある。
- **経路の準備時間**：[LARMのwithProvider](/Users/y.noguchi/Code/eumenes/api/domains/larm/service/index.ts:865)は`system-one`にもLLM・ASR・TTSを含む接続を要求する。判断だけのための接続準備が発話開始の経路に入る可能性がある。native推論時間だけを見てはいけない。

## 文脈付き判断の具体設計

### 入力は役割と対象を固定する

安定した指示は日本語で固定し、変動する会話はデータとして分ける。モデルに与える対象は常に`current_response`。例：

```json
{
  "user": "最近ようやく体調がよくなったんです。",
  "previous_response": "それは大変でしたね。",
  "current_response": "少しずつ回復されているようで安心しました。"
}
```

質問の意図は「CURRENTを話す時のアシスタントの表情・声色を選ぶ。ユーザーの感情をコピーしない。過去の返答を分類しない。技術的なエラー説明は通常。安心・気遣いは穏やかな寄り添い」。これは固定設定であり、LLMに新たに生成させる文章ではない。モデルの短い指示への適合を実測し、長大な禁止事項を足し続けない。

表情の意味を発話目的で定義する：warmth＝親しみの声かけ、joy＝一緒に祝う、empathy＝落ち着いて寄り添う・安心させる、curiosity＝相手の続きを知りたい、surprise＝アシスタント自身の驚き、none＝説明・事実・通常の確認。悲しみ・怒りの模倣を標準にしない。単なる聞き返しを興味にしない。

初期案は直前1チャンクのみ。最新ユーザー発言は160〜240文字、直前は120〜180文字を仮の目安とし、実際は**token数で上限を管理**する。Layaではまずstate約256＋head約256、合計512 tokens以内を比較する。現在チャンクを優先し、過去から削る。否定や現在の対象を無言で落とさず、必要なら通常へ戻す。入力中の日本語は原文を使用する。

引用を一律に消すより、発話対象と参照データを分ける。コード読み上げの除外は音声仕様として維持し、個人の話に含まれる引用語の削除とは別に扱う。直前2チャンクや以前の会話は、1チャンク方式より改善することを確認してから追加する。

**前の表情はまずモデル入力に入れず、外側の遷移制御で使う。** 入力すると過去の表情に引っ張られる循環を作り得るため、モデル入力へ追加する方式は独立した追加実験にする。

### A B Cの選択と候補絞り込み

最初から全チャンクにCを強制しない。A/B/Cを同じ発話目的・同じ候補で比較し、文脈による改善を確認する。今回の小規模結果では、Cを本番の既定値にする根拠は不足している。

評価では現行の語句ゲートも別因子として比較する。曖昧な短文で候補を落とす、技術語から感情を決める、といったハードな除外は縮小する候補。明確な説明文の安価な通常判定は、誤って共感を消さないことを検証できれば残す。選択肢を可変にする場合は候補数ごとの校正も必要になる。

### ストリーミングと同期を維持する

```text
すでに生成されたprefixを受信
  → 既存SpeechSentencesで現在チャンクを確定
  → runに紐づく質問＋直前チャンク＋現在を固定
  → 期限付き判断 → 遷移制御 → このchunkのdeliveryを確定
  → 確定deliveryでTTS合成
  → 音声＋deliveryを一緒に採用
  → 実際の再生開始でそのdeliveryをアバターへ反映
```

LLMは次の文章の生成を続ける。判断は現在チャンクが確定した時点の情報だけを使い、次チャンク・全文完成を待たない。元の質問は進行中runを扱うdialogueの公開操作から取得し、グローバルな「最新メッセージ」を使わない。

`createSpeech`内に、runの世代、チャンク番号と本文範囲、直前テキスト、直前の確定済みdeliveryを保持する。合成待ちの計画状態と実際の再生状態を分ける。先読み音声があるため、判定に使うのは**前の計画済みdelivery**、表示の開始時刻に使うのは**実際の再生開始**。混同すると再生速度によって判断が変わる。

進捗取得には既存の`dialogue.subscribeProgress`を使える。voice経路ではLLM完成時の全文Laya判断を重ねず、回答名横の表示も確定済みchunk計画から集約する。テキストのみの回答への表示は別経路として残せるが、その判断で音声chunkのworkerを塞がない。

判断workerは順序を守る1本とし、現在のLARMの同時判断禁止を尊重する。準備済み音声3チャンクの上限と取消・世代チェックを維持する。再試行では同じチャンク入力・deliveryを使い、失敗で別の感情に変えない。

仮の判断期限は**warm経路150ms以内**を起点に、実際のLARM往復と初回発話を測って決める。現在の2秒は音声の開始待ちには長い。未準備・期限超過時はそのチャンクを通常で確定し、遅れて返った判断は破棄する。TTSを通常で先に合成してからアバターだけ感情を変更すると同期が壊れるため、行わない。

モデル・音声providerの準備は会話開始時のvoice準備で行い、最初のチャンクの判断中にフルprofileを起動しない。テキストのみの場合にASR/TTSまで準備する現在の接続結合も、必要な範囲で整理する候補。credentialの所在やprofile設定をWebへ移す必要はない。

Layaが期限を過ぎてもCPU計算が直ちに止まる保証はない。1本の判断が残っている間は追加要求を積まず通常で流し、queueを増やさない。モデル置換後もこの制御を共通にする。

合成後のdeliveryは不変にして、音声と同じreceiptで採用する。実際の再生開始で既存hookがmotionを発火する構造は維持する。同じ表情の連続チャンクでは動作を毎回先頭から再開せず、既存の待機・話しかける動作と表情の補間を継続させる案が自然である。

生成途中の発話は、最終回答の確定前に聞こえる。取消や生成失敗では後続を止め、未確定の回答本文を会話の正本に保存しない。すでに再生した内容は取り消せないため、単調に増えるprefixのみを処理し、全文の書き換えを検知したら中断する既存の制約を維持する。

### 遷移制御の推奨

| 方法 | 効果・今回の観察 | 方針 |
| --- | --- | --- |
| 低信頼時に通常 | 不適切な強い表情を抑えられるが、寄り添いも取りこぼす | 校正後に閾値を決定。非通常の出現率だけで調整しない |
| 直近多数決 | 短い正しい変化を過去で消し得る。今回改善なし | 既定にはしない |
| 確率EMA | 切替は減ったが一致率・再現率が悪化 | 主分類への強い適用を避ける |
| ヒステリシス | 今回はCと同じ。曖昧な競合だけを保留できる | 校正済み上位候補と旧候補の差を使う第一候補 |
| 最小継続時間 | ちらつきを減らすが内容変化に遅れる。2チャンク保持は悪化 | まず視覚補間に限定。分類保持を採るなら強い新候補・通常への復帰を優先し、実時間で評価 |

基本は「今回の有力な候補が明確なら即切替、競合が僅差なら短く保持、低信頼は通常」。前の表情を長く残して通常の説明を喜びで話さない。具体的な確率・差・保持時間は校正用データで選び、評価用データで調整しない。

この制御は**TTS合成前**に適用する。アバターだけ旧表情を保持して声色だけ変更しない。視覚的な補間は、現在の確定した目標表情へなめらかに移す別処理として扱う。今回は音声を聴いた自然さや実時間の最小継続を検証していない。

### 保存と回答アイコンと読み直し

生のチャンク判断はdelivery domain、runとの対応と公開操作はdialogue、永続化はconversationが所有する。下位domainからdialogueやDBへ直接依存しない。

モデル置換時は`SpeechDelivery.source`の`laya`限定、`acceptedEmotion`、音声補正の採用条件、Webのsource表示も対象になる。成功したモデル判断とfallbackを区別する意味を保ちつつ、engine名・revisionを別に記録し、旧v2の読み込みを維持する。別モデルの結果をLayaと偽って保存しない。

試験実装ではチャンク計画をメモリに持てる。ただし採用版で読み直しを同じ表情・声色にするには、回答単位の保存だけでは足りない。`runId＋本文範囲／チャンク番号＋delivery version＋policy version`ごとに保存し、単一writerのtransactionで音声採用と整合させる。再生時も保存済み範囲を使い、全文の単一判断を戻さない。

名前横のemojiは回答の代表表情として維持できる。チャンクのたびに文章のemojiをちらつかせず、確定済みの主な非通常表情から決定する。再生中の表情と回答全体の代表表示は別の意味であることを明確にする。代表値の集約に新たなLLM判断は不要。

### Ruriと専用分類器

最初はEncoderを固定し、日本語の役割タグ付き入力を1回だけ埋め込み、小さな線形ヘッドを学習する。6クラス×256次元の線形ヘッドは約1,542パラメータであり、計算の大半はEncoderになる。独立したユーザー・前・現在の3回のEncoder呼び出しを標準にしない。

全文平均のembeddingでは文脈が現在の対象を覆う可能性がある。必要なら同じ1回のEncoder出力から「現在チャンクのtokenだけをpoolingする」方式と全文poolingを比較する。分類用の`トピック: `prefixと役割タグは固定入力であり、翻訳やLLM生成は不要。Ruriはembedding性能の良いモデルであって、配布状態のまま表情を正しく選べるモデルではない。[Ruriの用途・prefix](https://huggingface.co/cl-nagoya/ruri-v3-30m)

重みだけの理論目安は、37MならFP32約148 MB・INT8約37 MB、70Mなら約280 MB・70 MB。ただし量子化対象外の重み、tokenizer、runtime、作業領域が増えるため、常駐メモリの予測値として扱わない。ONNX export・pooling・日本語tokenizerの一致、量子化前後の分類差を確認する。

### Verdict Small

正式な公開先は`Manav2op/verdict-small`。モデルカードは118Mのdecision用途追加学習とINT8 ONNX約118 MBを示す。一方、公開評価でも全タスクが元のEncoderより改善しているわけではなく、日本語のアシスタント発話表現の検証ではない。[モデルカード](https://huggingface.co/Manav2op/verdict-small)

選択肢のembeddingは事前計算できる。判定ごとに必要なのは文脈付き日本語入力のembeddingで、既存のstate/questionsに合わせるadapterを作れる。ただし質問対象を理解するjoint classifierとは仕組みが違い、文脈の平均化で対象を取り違える可能性は検証が必要。

公式実装には入力embeddingのcacheがあるため、**同じ例を繰り返す速度評価では入力cacheを無効化**する。固定した選択肢cacheは許可して条件を記録する。ONNX経路はCPUExecutionProvider・512 tokensの切り捨てで、PyTorchの長文分割経路と同じではない。[embedding実装](https://raw.githubusercontent.com/Manavarya09/verdict/main/src/verdict/engines/embed.py)、[ONNX実装](https://raw.githubusercontent.com/Manavarya09/verdict/main/src/verdict/engines/onnx.py)

日本語は基盤モデルと学習コードの対象に含まれる。配布ライセンスとは別に、学習mixには研究用途限定のデータを組み込める実装がある。採用前に配布checkpointのデータ来歴・条件を確認する。`--commercial`で再学習できることだけでは、配布checkpointの来歴確認にならない。[学習データ定義](https://raw.githubusercontent.com/Manavarya09/verdict/main/train/data.py)、[基盤モデル](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md)

### Ryzenでの実行方式

まずCPU ONNX INT8・1/4/8スレッドを比較する。現在のCPU推論より速く、少ないメモリで済むかを実測する。LLMと同じGPUに小さな判断処理を載せると、転送・待ち・メモリ競合で不利になる場合もある。

Radeon 8060SはAMDの対応情報に載るが、現在のPyTorch wheelはCPU版である。ROCmは対応OS・version・operatorを確認して別条件で試す。CUDA向け最適化やFlashAttentionの案内だけでAMD上の高速動作を保証しない。NPUもONNXのoperator対応とCPU fallbackを確認してから扱う。[AMD GPU仕様](https://rocm.docs.amd.com/en/latest/reference/gpu-specs.html)、[Ryzenの対応情報](https://rocm.docs.amd.com/projects/radeon-ryzen/en/latest/)、[Ryzen AIのモデル実行](https://ryzenai.docs.amd.com/en/latest/modelrun.html)

## 本評価の方法と採用基準

### データと正解

初期比較は100〜150会話・400〜600チャンクを目安にする。現行APIの実ログと、同じ返答が文脈で変わる対照例を混ぜる。短文、技術説明、回復への安心、喪失への寄り添い、祝福、驚き、聞き返し、興味、否定、引用、皮肉、チャンク境界での転換を含める。実データはユーザー・会話単位で分け、同じテンプレートの言い換えを学習・評価へ跨がせない。

二人が「望ましい主表情」「許容できる表情」「避けるべき表情」「声色」を付け、不一致を調整する。通常も許容するケースと、温かさが必要なケースを区別する。調査者一人の好みを正解に固定しない。LLMで判断用テキストや正解を増産しない。

まず現行の全文・候補ゲート込みの基準も測定する。未来の全文を使う現行基準はストリーミング方式と同条件ではないため、品質の参考と、初回発話までの待ち時間を別に示す。A/B/Cは同じ指示と固定候補で比較し、候補ゲートと指示の変更は別の比較にする。

### 品質と校正と遷移

| 指標 | 測り方 |
| --- | --- |
| 一致率・Macro F1 | 通常を含む6クラス。混同行列とクラス別precision/recall/F1を併記 |
| 不自然な表情 | 許容外の選択率と、人が実再生を見て不自然と付けた率を別に集計 |
| 表情の出現と取りこぼし | 非通常が必要な例のrecallと、技術説明・通常例の非通常誤判定率を同時に見る |
| 不要な切替 | 人が同じ態度を望む隣接チャンクでの切替率。必要な変化を見逃す率・切替遅延も測る |
| 確率 | held-out校正データでtemperatureを調整。ECE・Brier・信頼度別の誤り、上位2候補の差を確認 |
| 声と表情の整合性 | 同じdelivery IDの対応確認に加え、音声＋アバターの盲検評価。bright/gentle等の聞き分けと過剰表現を確認 |

確率vectorはnative APIにあるので、内部スキーマで安全に保持できる。閾値・ヒステリシスを校正セットで決めて固定し、別の会話を含む評価セットで比較する。反復回数でデータ数を水増しせず、会話単位のpaired bootstrapで差の不確実性を示す。

温度による校正は確率の過信と棄却の調整であり、クラスの順位そのものを改善する方法ではない。文脈で驚きや喜びを取り違える問題が残るなら、指示・入力・分類ヘッドを変更する必要がある。

**暫定の採用目標**：Macro F1 0.80以上、必要表情のrecall 80%以上、明らかに不自然な表情と通常説明への誤表情を各2%以下。不必要な切替を減らしつつ、必要な転換のrecallを落とさない。数値は製品の体験目標であり、現モデルが達成済みという意味ではない。許容ラベルと利用場面を確定してから調整する。

### 実行性能

同じ395、モデルrevision、入力、token上限、バッチ1、seed、接続条件を固定する。thread数・CPU affinity・電源設定・温度・同居プロセスを記録する。warmとcold、判断単体とLLM/ASR/TTS同居を分ける。入力cacheは無効化し、選択肢cacheの有無は明記する。

計測時刻を分ける：`chunk_ready → decision_start → decision_end → synthesis_start → audio_ready → playback_start`。判断単体のP50/P95、queue待ち、LARM準備、最初の音声再生への追加遅延、後続音声の欠けを測る。判定から合成前までの時間を「発話開始遅延」と取り違えない。

メモリは孤立processの起動前後・warm推論後のRSS/PSS/USS/Swapとpeakを測る。冷間ロードは既存稼働サービスを止めず、評価用の隔離processでreadyになるまでを計測する。重みcacheが温かい起動と初回読み込みも分ける。CPU process時間とwall、GPU利用率・共有メモリ、NPUを使う場合のfallbackも記録する。

性能目標の起点はwarmの判断P95 100ms以内、最初の発話への追加待ち150ms以内。超過時は通常へfallbackする。150ms内に返る率と表情の取りこぼしを一緒に評価する。モデル置換は、同条件で品質改善・速度非劣化・実メモリ削減を確認した場合に採用する。今回未測定なのはcold load、製品経路全体の初回TTS遅延、GPU/NPU使用量、代替モデルの性能である。

### 小型ヘッドの学習コスト

最初は各クラス50〜100例程度の学習例を目安に、例えば学習600・校正200・評価300の計1,100チャンクを会話単位で分ける。16/50/100例／クラスの学習曲線を見て増やす。希少クラスを増やしても、評価側は実際の通常表情の割合を残す。

Encoder固定の分類ヘッドは小さく、学習よりembedding作成・人のラベル付けが主な費用になる。1例20〜45秒を二人で付ける場合、1,100例で約12〜28人時＋不一致調整が目安。これは見積もりであり、実測ではない。Encoder推論時間・head学習時間は最初の100例で測る。

Encoderまで追加学習する場合は2,000〜5,000例を検討し、通常・共感・興味の混同や対象範囲の取り違えが改善するかを確認する。まず100〜300例の試験で学習時間とpeakメモリを測り、epoch数と複数seedを含めて費用を見積もる。今回、GPU学習・外部送信はしていない。精度向上幅は未検証であり、ラベル品質や入力設計が悪ければ追加学習でも改善しない。
