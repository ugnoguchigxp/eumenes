# ブラウザアーティファクトの実行Script・進捗と接続承認省略の設計

作成日: 2026-10-20

状態: **UI・保存契約・登録・固定試験まで実装済み。実Brave/Bridge・実LLM・音声による受入は未実施。** ユーザーの実装依頼に基づき着手した。製品設定の変更とサーバーの停止・起動・再起動は行っていない。実装と検証の範囲は[実装記録](verification/browser-script-progress-2026-10-20/README.md)を参照。レビューで確認した修正と最新の検証結果は[レビュー記録](verification/browser-script-progress-2026-10-20/review.md)にまとめた。

既存の[ブラウザ設計](browser-tabs-toolchain-design-2026-10-18.md)への追加・変更を定義する。未実施の受入条件を、固定試験の成功だけで満たしたとは扱わない。

## 1. 目的と合意した方向

利用者がチャットで依頼したことについて、「どういう行動と解釈したか」「これから何をするか」「どこまで実行・確認できたか」をブラウザアーティファクトで確認できるようにする。

- 音声認識（ASR）とテキストの依頼入力は、既存のチャット欄に統一する。
- ブラウザアーティファクトは**実行Scriptと進捗を主体**とする。プロンプト欄、マイク、音声入力、送信ボタンを追加しない。
- 接続・タブ・撮影画像は残すが、補助タブへまとめる。
- Braveの場所やBridgeの設定は、既存の設定アーティファクトから開く「ブラウザ」セクションへ移す。
- Bridgeの初回トークン登録により、次回以降の接続の手動承認を省略できるようにする。
- プレビューは実タブのライブ映像をPiPで表示できる場合だけ別途検討する。静止画をライブ表示の代わりにしない。依頼された撮影画像の閲覧は維持する。

### 今回の設計に含めないもの

- 独立した設定アプリ、ブラウザアプリ、全画面の管理ダッシュボード。
- 任意JavaScriptや固定クリック列を生成・実行するコードエディター。
- 自作のブラウザ拡張、専用ブラウザ・プロファイル、MCP内部実装への直接接続。
- ブラウザ接続のための常駐別サービス、接続を失わないことの保証。
- 再起動前に実行中だった操作の自動再開・自動再送。
- 語句・サイト名の辞書による依頼の分類や操作手順の固定化。
- LARMへの画像保存、画像圧縮条件の変更。

## 2. 現状と、再利用する仕組み

| 現在の仕組み | 再利用・変更の方針 |
| --- | --- |
| 会話の `browser_operate`、`browser_capture` とcommand担当 | 入力経路を維持する。依頼の意味理解と担当選択をLLMに委ねる |
| 単発型の共通エージェント核、1ジョブ1推論、`invoke / finish / clarify` | 維持する。Scriptのためだけの別plannerや別実行ループを作らない |
| browser domainのtask・operation・approval・capture台帳 | 進捗の正本として使う。Scriptと手順への関連付けだけを追加する |
| 実行前の予告・commit後の通知・会話への結果通知 | 公開と実行の順序、確認待ち・終了の通知に再利用する |
| 登録済みArtifact、source、actionBindings、Web adapter | 新revisionで画面と契約を改訂する。Workspaceへのブラウザ専用分岐を増やさない |
| browserの実行ファイル設定・標準パス提案・OSファイル選択 | 設定画面へ移設して使う。値の正本や保存前検査を二重化しない |
| settingsの秘密情報の暗号化・鍵管理 | 公開操作を追加してBridge credentialに利用する。browserからsettingsのSQLや内部関数を直接参照しない |

現状では、ブラウザ画面に接続・URL入力・タブ・作業・撮影画像が縦に並ぶ。taskの状態と短い結果は表示できるが、事前の行動Scriptと手順単位の進捗はない。backendの失敗理由等もWebのsource変換で一部落ちている。

現在の共通核は、`invoke`に説明用`text`を併記する出力を許さない。指示文を変えるだけでScriptや進捗を保存できるわけではない。本書では、既存核の登録ツールとbrowser domainの表示契約を拡張して対応する。

検討した代替案と判断:

| 案 | 判断・トレードオフ |
| --- | --- |
| LLM指示だけでScriptの文章を返す | 保存・公開順序・進捗との照合を保証できないため、単独の解決策にはしない |
| Script用の別plannerと別ループ | 解釈・状態・予算の管理が二重になる。既存核の登録ツールで満たせるため追加しない |
| 既存核と操作台帳にScriptを接続する | 採用案。責務を維持できるが、登録・保存契約と初期化の拡張、および推論予算の実測が必要 |
| MCPを別サービスとして常駐させる | 承認省略に加えて接続寿命の設計が必要になる。今回の要件には公式token経路を先に検証する |

## 3. 画面構成

### 3.1 アーティファクトとしての枠組み

既存の可変幅ArtifactPanelの内側に表示する。アプリ全体のヘッダー、独立したサイドバー、別のウィンドウ枠を追加しない。外側のアーティファクトタブがタイトルと閉じる操作を担い、内側は内容と必要な操作だけを持つ。

390px程度の狭い枠でも一列で読めることを基本にする。幅が広い場合も情報の優先順位を変えず、全画面を前提とした余白や二列の固定配置にしない。

外側タブの余白0、内容欄の全周余白などは[OpenUI Artifact](../docs/openui-artifact.md)の現行規約を使う。参考画像の余白・テーマを固定値の新仕様として採用しない。

### 3.2 ブラウザアーティファクト

| ローカルタブ | 表示・操作 |
| --- | --- |
| **操作（初期表示）** | 実行Script、実行中の手順、完了・確認待ち・失敗、折り畳んだ実行履歴、中止 |
| 接続・タブ | 接続・切断、操作対象の選択、URLを開く、タブを閉じる、必要な接続案内 |
| 撮影画像 | 保存済み画像の一覧・選択・拡大・取得、撮影の状態・失敗理由・取消 |

小さな接続状態、現在の操作対象のタブ名、設定へのリンクは、どのローカルタブでも確認できる位置に置く。設定リンクは既存のアーティファクト間ナビゲーションで設定を開く。

「操作」の優先順位は、実行Script → 現在の手順と状態 → 小さな依頼の参照表示とする。元の依頼は読み取り専用とし、入力欄に見える枠や編集操作を置かない。未依頼なら「チャットでブラウザへの依頼を伝えてください」と案内する。

- 読み込み中、Script準備中、接続中を区別する。Scriptがない間に架空の手順を表示しない。
- 確認待ちは止まった手順と確認内容を表示し、回答先はチャットとする。ここに第二の回答欄を作らない。
- 「実行を中止」は既存の取消操作へ接続する。押下だけで取消完了とせず、台帳の確定結果を反映する。
- 閲覧中の履歴を更新で勝手に切り替えない。現在の会話・依頼に関連するtaskを識別し、複数あれば表示対象を選べるようにする。表示選択は新しい操作依頼や実行対象の変更にならない。
- 関連付けは既存のconversationId・requestId・taskIdを使う。別の会話の最新taskを推測で今回の依頼として表示しない。
- 「撮影画像」の閲覧は維持するが、「操作」の中央へ撮影画像を自動表示しない。画面からの撮影開始の追加は今回の必須条件にしない。

### 3.3 設定アーティファクトの「ブラウザ」

既存の設定ハブに「ブラウザ」を追加し、同じアーティファクトの開き方・見た目・保存結果の表示に合わせる。独立した設定サイトを作らない。

| 項目 | 内容 |
| --- | --- |
| Braveの場所 | 保存済みの実行ファイル、未設定時の標準パス提案、対応OSの「参照…」、保存・設定解除 |
| 拡張機能 | Playwright MCP Bridgeの導入とトークンの取得手順への案内 |
| 接続の承認 | 省略の有効・無効、トークンの初回登録・更新・削除、登録済みかと利用可否の表示 |
| 戻り先 | 「ブラウザを開く」。接続・タブ操作はそちらで行う |

パスの保存とBridge credentialの登録は明示的な設定操作であり、§1の「操作依頼はチャットに統一する」とは区別する。トークンをチャットへ貼り付けるよう案内しない。登録後は入力欄を空にし、保存済み値は返さない。

現行のパス設定は即時保存のAPIを持つ。移設だけを理由に別の保存台帳や、保存後にもう一度適用を要求する経路を作らない。保存操作が何を確定するかを画面内で明示する。

## 4. チャットからScript、実行への流れ

1. 利用者が既存チャット欄から音声またはテキストで依頼する。原文・認識結果の扱いは既存の会話受付を維持する。
2. 通常担当が依頼を解釈し、既存のブラウザ担当へ渡す。曖昧な対象や不足条件はチャットで質問する。
3. ブラウザ担当が、依頼の解釈、対象、予定手順、各手順で何を確認するかをScriptとして保存する。必要な接続も予定に含める。
4. 保存を確定し、アーティファクトのsourceと既存の会話予告経路へ公開する。必要なら同じブラウザアーティファクトを開く。既に開いていれば重複して増やさない。
5. 公開が確定した後に、次のqueue段階で実際の操作へ進む。操作対象は観測後に決め、一手ずつ検証・実行する。
6. 操作の結果と観測に従って進捗を保存する。必要な計画変更・確認待ち・結果を同じ画面へ返す。

Scriptの公開は、これから行うことの予告である。**画面を見たこと・承認したこと・操作が成功したことの証拠にはしない。** 全依頼に新しい「Scriptを承認して実行」ボタンや追加確認を必須化しない。従来の送信・購入・公開・削除・保存等の個別承認は維持し、チャットで受け取る。

「公開済み」は保存と通知が確定したことを指し、利用者の既読やWeb描画完了を意味しない。既存の音声入力・自動読み上げで予告の再生完了を待つ条件が適用される場合は、その順序を維持する。Script全文を毎手順読み上げず、音声には短い予告と要点だけを渡す。

### 4.1 例: 「なんか面白い動画見せて」

| 種類 | 表示例 |
| --- | --- |
| 原文（小さく参照表示） | なんか面白い動画見せて |
| 解釈と予定 | YouTubeのおすすめから、面白そうな動画を1本選んで再生します |
| 手順 | YouTubeを開く → おすすめを確認する → 動画を選ぶ → 再生を確認する |
| 実行中 | 「動画を選ぶ」実行中。前の二手順は完了、再生確認は未着手 |
| 確認できない場合 | 再生を開始する操作は行ったが、再生中とは確認できていない |

これは会話で挙がった表示例であり、サイトや順位、動画名、選定方法をコードへ固定しない。どの方法を選ぶかは現在の依頼・タブ・観測に基づくLLMの判断とする。観測前に特定動画を選定済みと表示しない。

## 5. 実行Scriptと進捗の契約

### 5.1 Scriptの意味

Scriptは利用者が読める行動計画であり、実行コード、内部の思考過程、DOMセレクター一覧ではない。予定は画面の状況で変わり得るため、初版と更新を区別して残す。

保存する最小情報は次のとおり。

| 単位 | 必要情報 |
| --- | --- |
| Script | taskとの関連、改訂番号、解釈の短文、対象の参照、作成・更新日時 |
| 手順 | 安定した手順ID、順序、短い行動名、確認する到達条件、現在状態 |
| 進捗の記録 | 単調な順序番号、taskのepoch、Scriptの版・手順ID、関連する操作・観測の参照、発生日時 |
| 計画の更新 | 変更前後の版、変更箇所と短い説明。過去の実行記録との対応は維持する |
| 続きの作業 | 承認後に作るtaskと前taskの関連。古い承認や実行中状態を新taskにコピーしない |

ID・版・順序はhostが発行・検証し、モデルが任意のtaskや他者の手順を書き換えることを許さない。行動の意味、手順のまとまり、到達条件、状況に応じた更新はLLMが判断する。ページ本文を命令として採用せず、表示は常に非実行のテキストとして描画する。

### 5.2 状態と、事実として示せる範囲

| 状態 | 意味 |
| --- | --- |
| 未着手 | 予定として保存したが実行を開始していない |
| 実行中 | 対応する推論・操作・観測が進行中 |
| 確認待ち | 必要な入力・承認・対象指定を利用者に求めている |
| 完了 | 到達条件について、観測した根拠を実行担当が確認した |
| 失敗・結果未確認 | 処理の失敗、または外部操作が実行されたか確定できない |
| 中止・期限切れ | taskの取消または期限によって終了した |
| 変更・省略 | 新しい計画で置き換え・省略した。完了とは扱わない |

画面用の状態は既存taskの終端やoperationの状態を壊さず、必要な表示へ対応付ける。Scriptの全手順の完了と、taskの処理が終了したことは区別する。taskが終了しても未確認の手順を一括で完了にしない。

- operationの `prepared → dispatched → observed` は、操作の準備・送出・応答確認の事実である。業務上の到達条件の成立を自動では意味しない。
- 「検索結果が表示された」「再生が始まった」等の意味判断はLLMが最新の観測から行う。特定サイトの文言・ボタン名の辞書で判定しない。
- hostは根拠の参照がそのtask・対象・有効な観測に属することを検査する。検査しただけでモデルの意味判断の正しさを保証したとはしない。
- 観測で確認できる手段がない場合は「確認できない」と残す。音が鳴っていると観測できない構成で、再生ボタンのクリックだけから音声再生を断言しない。
- LLM推論中、ツール実行中、接続待ち、確認待ちを区別する。時間経過だけで進捗を増やさず、根拠のない割合や残り時間を表示しない。

### 5.3 既存実行核への接続

初版・改訂・到達条件の確認結果を保存する**browser所有の登録ツール**を追加し、既存の `invoke` 形式で呼ぶ。共通核に「説明を付けた任意ツール出力」を別形式で増やさない。具体的なtool/schema IDと上限値は、実装時に既存bundleの登録状況とサイズ検査に合わせて確定する。

必要時接続のために、現在の二つの前提を明示的に変更する。

- 現行のtask受付は接続済みを必須としている。承認省略が有効で接続準備が整っている場合は、未接続でも新しい依頼とScript準備を受け付けられる契約へ拡張する。「依頼を受け付けられる」と「ページを操作できる」を可用性・画面状態で区別し、ページ操作の接続済み検査は維持する。
- 現行runnerは初回推論前に対象タブと観測を必須としている。未接続時は対象・観測なしを明示したREFERENCEでScript準備を行い、公開後に接続・対象確定・観測へ進む。接続・対象が揃う前のページ操作はhostで拒否する。接続済みの安全な読み取り観測は、初版の準備に使える。

Script保存操作はブラウザ接続を要求せず、task・版・epoch・権限を検査する。これにより「Scriptを作るために先に接続が必要」という循環を作らない。未登録の手動接続経路は既存の案内を維持する。

ページ操作には対応するScriptの版と手順参照を結び付ける。hostは実行前に、そのtaskのScriptが公開済みで参照が現行であることを検査し、operation記録と同じ公開操作・writerの境界で記録する。Script未公開や未保存の計画変更を先に実行しない。

操作の実行開始・拒否・結果未確定・取消・期限はhostの台帳から反映する。到達条件の完了申告は観測根拠を検査して保存する。Scriptの書込みが失敗したとき、表示だけを成功にせず、その計画に対応する次の操作も行わない。

Script公開・更新の推論も、現行の最大12回の予算に含める。表示のための無制限な追加推論を設けない。初期観測・公開・更新で予算不足になる場合は実測結果を示して設計を見直し、黙って上限を増やさない。

### 5.4 チャットからの修正と確認への回答

追加発言が訂正・中止・別依頼のどれかは既存の会話担当が判断する。画面側の語句判定や、別のチャット入力経路を作らない。

同じ対象の実行中taskを修正する必要がある場合、旧taskを取り消してから新しい依頼を受け付け、旧taskのScriptを新taskの予定へ読み替えない。既に外部へ送出された操作の完了を取り消したとは表示せず、既存の不確定操作の停止規則を適用する。

既存の承認待ちへの同意は、`continueFrom / approvePending` と期限・一回限りの承認契約を維持する。画面に出ているScriptやタブを選んだ事実だけで同意と解釈しない。

### 5.5 保存・取得・復元

- Scriptと手順・進捗の追加情報はbrowser domainが保存する。Webのstateや汎用ログを実行状況の正本にしない。
- 現行のworkspace sourceを拡張し、Script、進捗、関連task、既存のerrorCode・errorLabelを返す。Web schema・resource・DesignSystemのpropsまで接続する。
- まず既存のquery invalidationとポーリングを使う。表示だけのために新しい配信サービスを導入しない。通信断では最後に取得した情報と更新不能を示し、完了を推測しない。
- sourceのrevision、進捗順序、taskのepochで古い応答を識別する。連番の進捗が欠けた場合はsourceを読み直し、外部操作を再送しない。
- 初版・変更履歴は保存された順に再表示する。利用者が履歴を見ている間は、新しい進捗でその閲覧位置を奪わない。
- taskをまたぐ続行は関連を表示するが、task ID・epoch・承認の境界を保つ。
- 終了済みtask等の現行7日保持と削除へ追加情報を含め、孤立したScript履歴を残さない。
- 保存するのは短い行動名と確認結果、参照、状態に限定する。観測本文、入力値、認証情報、URLのクエリ等をScriptに複製しない。通常ログにも出さない。
- 再起動後は保存済みScriptを閲覧できる。以前の「実行中」を現在も動いている表示にせず、既存の終了処理に従って中断・結果未確認を反映する。

## 6. 接続承認の省略

### 6.1 公式仕様と現在の制約

Playwright MCP Bridgeには、プロファイル固有の `PLAYWRIGHT_MCP_EXTENSION_TOKEN` をMCP子プロセスへ渡すと、接続時の手動承認を省略する公式経路がある。初回だけ、利用者が拡張機能の画面でトークンを取得し、Eumenesの設定へ登録する。

一方、承認省略は「以前のタブに復帰する」「接続ページを一切開かない」「以前の実行状態を再開する」という契約ではない。公式試験では、承認省略時に `connect.html` 自体が最初の接続タブになる。現行のEumenesはこのschemeを一般の操作対象として許可していない。

公式情報を確認した日: 2026-10-20。

- [Bridgeの承認省略とプロファイルの説明](https://github.com/microsoft/playwright/blob/main/packages/extension/README.md#bypassing-the-connection-approval-dialog)
- [Bridgeの試験: token bypassと接続ページ](https://github.com/microsoft/playwright/blob/main/tests/extension/extension.spec.ts)
- [接続ページからの遷移についての調査記録](https://github.com/microsoft/playwright/issues/43230): 初期報告はtoken経路を疑っていたが、後続で別の拡張が挿入するiframeを原因として訂正されている。token固有の障害と扱わない。

確認対象の製品依存は `@playwright/mcp@0.0.83`。公式のmainの挙動を、インストール済みの版や利用者のBraveで確認済みとは扱わない。

### 6.2 設定と秘密情報

- 未登録時は現行の手動承認を維持する。省略を有効にするには、有効な登録と利用者の設定操作を必要とする。
- トークンはsettings domainの公開credential操作で暗号化してSQLiteに保存し、既存の鍵管理を使う。暗号化方式や鍵ファイルを新たに二重管理しない。
- browser側は設定と接続状態を所有し、applicationの構成で必要最小限のcredential取得・失効通知を接続する。下位domainから上位domainへの参照、他domainのSQL直接操作を追加しない。
- credentialと省略設定を同時に変更する場合は、単一writer transactionと各domainの公開操作を使う。OSのファイル検査やMCP通信はtransaction外とする。
- Webへの読取り応答は登録有無・省略設定・安全な状態・revisionのみ。トークン自体は返さない。書込みは認証済みの設定操作に限り、登録後はブラウザメモリの入力を消す。
- トークンを汎用Artifact outbox、receiptのpayload、チャット履歴、LLMのsnapshot・REFERENCE、診断・通常ログに保存しない。既存の秘密設定と同様、専用の認証済み設定APIへ渡す。
- MCP子プロセスには既存の限定環境に、このBridge credentialだけを追加する。backendの認証tokenやLARM credentialは渡さず、利用者に環境変数の設定を要求しない。
- 更新・削除・省略無効化時はcredentialの版を進め、旧credentialで接続中のsessionを切断する。実行中taskは既存の切断規則で終了し、古い接続結果を採用しない。
- 「削除」はEumenesに保存したcredentialと使用許可を削除する意味であり、Bridge側のトークンを再発行したとは表示しない。

### 6.3 接続のタイミング

| 場面 | 動作 |
| --- | --- |
| 承認省略が有効で、新しいブラウザ操作依頼を受けた | 必要な接続を予告し、保存設定で接続する。利用可能な操作対象が確定してから進む |
| backendを再起動しただけ | 自動でブラウザ操作を再開しない。次の新しい依頼、または明示的な接続操作で接続する |
| 利用者が切断した | バックグラウンドで勝手に再接続しない。次の明示依頼・接続操作を待つ |
| 同じ依頼の操作中に接続を失った | 接続して同じ外部操作を再送しない。既存の中断・結果未確定として止める |
| トークン不正・失効・プロファイル不一致 | 省略接続の失敗と設定への案内を表示する。別プロファイルや手動承認方式へ黙って切り替えない |
| 未登録・省略無効 | 現行の手動接続を案内する。接続待ちを操作完了と表示しない |

接続要求は接続全体で直列化・重複抑止し、同時の依頼でMCP子プロセスや接続画面を複数作らない。接続の失敗は同じ理由で無限再試行しない。現行の接続待ち上限2分を維持する。

### 6.4 接続対象の扱いと実機での採用条件

**この部分は実機確認前のため、実装方法を確定したとは扱わない。**

1. token経路で接続した直後に、実際のタブ一覧と接続状態を読む。操作可能なページが得られたこととMCPへの接続成立を区別する。
2. 接続ページ・空タブを、前回の対象や現在の利用者のタブだと扱わない。接続URLにcredentialが含まれる可能性を考慮し、LLM・通常ログ・UIのsourceへそのURLを渡さない。credentialを受け取るadapter境界で除外する。
3. 利用者の依頼に開くURLが明示されている場合は、承認済みの新規タブ操作を再利用できるか検証する。接続ページが対象でも、一般のページ操作にそのschemeを許可して迂回しない。
4. 既存タブを対象にする依頼では、再接続後に参照できる範囲で対象を確定する。旧tabRef、同じタイトル、同じURLだけで元タブの同一性を保証しない。対象を確定できなければチャットで選択・手動接続を案内する。
5. 複数のBraveプロファイルがある場合、credentialが対応するプロファイルと実際の接続先を照合する。公式のprofile指定が必要なら、実機で確認して設定へ追加する。自動で別プロファイルへ移らない。
6. 固定版MCPと現在のBridge・Braveで、接続ページの後始末、Eumenesから開いたタブの扱い、切断・再接続時の範囲を記録する。

承認省略と新規ページの操作が成功しても、「以前から開いていた任意のタブへ自動復帰できる」とは宣言しない。要件を満たせない場合は、確かめた範囲と追加の選択が必要な場面を報告する。一般のURL安全境界を弱めたり、MCPの非公開内部実装へ接続したりして解決しない。

### 6.5 外部操作の承認との区別

Bridgeトークンが省略するのは**接続時の手動承認だけ**である。送信・購入・公開・削除・保存、入力値、対象と世代、有効期限、一回限りの操作承認は従来どおりhostで検査する。Scriptが公開済みであることや、接続が承認不要であることを外部操作の許可として使わない。

## 7. PiPと撮影画像

実行Scriptと進捗の改修は、映像機能に依存させない。PiPは別の調査・採用判断に分ける。

候補は、利用者が選択した実タブのMediaStreamを取得し、PiPへ表示する方式。画面共有・PiPのAPIの仕様上、利用者のクリックや対象選択・共有許可が必要で、ASR依頼だけによる無操作の開始は前提にできない。

- 実際の対象タブが動く映像を映せること、共有終了を検出すること、対象の不一致を誤表示しないことを実機で確かめる。
- 別タブへ移ったときの自動追従や、PiP上でのページ操作ができることを保証しない。
- 録画・保存・サーバーへの映像送信はこの候補に含めない。
- 不成立・未対応のときは映像機能を出さず、静止画や撮影の自動反復へ置き換えない。

依頼による撮影・保存済み画像の閲覧・ダウンロードは既存機能として「撮影画像」に残す。ライブプレビューとは混同しない。

仕様: [画面共有](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia#security)、[Document PiP](https://developer.chrome.com/docs/web-platform/document-picture-in-picture)。

### 10.2 部分試験

- Script未公開では実操作を送出しない。公開transactionの失敗、取消・失効直後、旧Script版・別taskの手順参照を拒否する。

- 確認待ち、同意による続き、承認失効、取消・期限切れ・切断で実状態に合った表示となり、同じ外部操作を再送しない。
- credentialの保存・更新・削除・復号不能、旧接続の失効、読み取りAPI・source・receipt・LLM文脈・ログへの非露出を確認する。

- 設定からパス提案・OSファイル選択・保存・解除ができ、保存前の候補を接続に使わない。
