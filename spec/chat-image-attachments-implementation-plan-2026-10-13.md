# ornith1.5 チャット画像添付の実装計画

作成日: 2026-10-13。状態: 計画。製品実装と実モデル受入は未着手。

チャット領域全体でJPG・PNG・BMPを受け取り、プロンプト入力欄でサムネイルを確認してから、本文と画像をornith1.5に送信する。画像はユーザー発言にひも付く資料として保存し、後続の質問でも参照する。既存の会話保存・推論・ジョブ・取消機構を拡張する。

## 対象と完了条件

- JPG（拡張子JPEGを含む）・PNG・BMPを、貼り付け、ドラッグ＆ドロップ、添付ボタンから追加できる。
- 会話履歴から入力欄までのチャット領域を受付範囲とする。設定、Artifact、他の入力欄への貼り付けは捕捉しない。
- 入力枠内にサムネイル、準備状態、削除操作を表示し、拡大して確認できる。
- 本文だけ、本文と画像、画像だけを送信できる。本文も画像もない入力は拒否する。
- 通信失敗で草稿を失わず、再送しても発言・回答ジョブ・画像が重複しない。
- 送信済み画像を履歴で表示し、少なくとも直後の質問では同じ画像を参照できる。再読み込み・backend再起動後も表示できる。
- 画像対応を確認した推論先にだけ画像を送る。画像を落として文字だけで続行したり、別モデルへ無断転送したりしない。
- 固定試験、ブラウザ試験、実ornithでのJPG・PNG・BMP受入をそれぞれ記録し、必要なgateと差分点検を完了する。

動画、カメラ撮影、画像編集、生成画像ライブラリの改修、物体検出APIの呼び出し、全クラウドモデルの画像対応、画像の長期記憶・World取り込み、CLIの添付操作は今回の対象外。文字だけの既存CLI/API入力は互換性を維持する。認証方式やLARMの接続設定は変更しない。

## 画面と操作

入力枠の上段に64〜80pxを目安とするサムネイル列、下段に本文と送信操作を配置する。画像は全体が見える表示とし、複数枚は横スクロールで確認する。各画像に名前、準備状態、削除ボタンを設ける。拡大表示には既存Modalを使う。狭幅と暗色でも操作を維持する。

ドラッグでチャットに入った間だけ「画像を追加」を表示し、入れ子の要素への移動で表示が点滅しないようにする。対応する画像ファイルのdropだけを消費し、画像URLやHTML内の画像を自動取得しない。

キーボード貼り付けにはブラウザ内のフォーカスが必要である。チャット内にフォーカスがある場合と、他の操作対象がなくチャットがアクティブな場合に受け付ける。設定入力・Artifact・Modalが操作対象なら受け付けない。textareaではキャレット位置を維持し、画像と文字が混在する貼り付けでも文字を失わない。同じイベントを枠と入力欄で二重処理しない。ファイル選択も同じ添付受付に集約する。

追加直後はFileと一時URLをブラウザ内で保持し、送信操作で初めてアップロードする。読み込み中や送信中は状態を表示する。準備に失敗した画像は理由を表示し、その画像を削除するか再試行するまで送信を止める。解除した一時URLは破棄する。

送信時の本文と添付一覧をsnapshotに固定する。成功後はそのsnapshotの草稿だけを除去し、送信待ちに入力された本文や追加された別画像は保持する。失敗時は本文・画像・取得済み添付IDを保持する。送信中の対象画像の差し替えは行わない。

音声の自動送信は手動添付を消費しない。入力欄で「添付画像は送信ボタンで送ります」と状態を示す。音声入力による本文変更と手動草稿の既存制御を確認し、添付がある場合の本文の所有を明確にして回帰試験にする。

## 保存とAPI

添付の原本とメタデータは`conversation`が所有する。初期実装は容量制限付きSQLite BLOB保存を基本案とする。ファイル保存とDB確定の二重管理を避け、同一writerで保存・関連付けを検証できるためである。原本は変えず、表示用の縮小画像は資料の原本と区別する。BMPの表示変換が必要な場合も、原本と変換結果の関係を保持する。

保存する項目は添付ID、所有者、conversationId、元のファイル名、検査済みMIME、bytes、幅・高さ、SHA-256 digest、作成時刻、未関連時の期限、メッセージとの関連と表示順。所有者は認証済みbackend contextから決め、client申告を信用しない。確定した添付は不変とする。

新規migrationは`conversation`の現行連番を確認し、`after`付きで追加する。配布済みmigrationと文字資料の`textRevision`は変更しない。画像digestと関連順序を含む資料snapshotを別に持ち、元資料の同一性と回答採用時の有効性を確認する。

以下はEumenes側のAPI案であり、LARMへの外部契約ではない。

| API案 | 入出力と責務 |
| --- | --- |
| `POST /api/conversations/:id/attachments` | 単一画像のmultipartとupload requestIdを受け、検査後に添付IDとメタデータを返す。同じID・同じ内容は再利用し、異なる内容は競合とする。 |
| `GET /api/conversations/:id/attachments/:attachmentId/content` | 所有者と会話の一致を検査して画像を取得する。MIMEを固定し、`nosniff`と`no-store`を使う。 |
| `DELETE /api/conversations/:id/attachments/:attachmentId` | 未関連のアップロードの破棄に使う。送信済みの添付は発言の撤回規則で扱う。 |
| `POST /api/runs` | 既存の`requestId`・`conversationId`・`text`に順序付き`attachmentIds`を加える。省略時は従来どおり。本文空欄は有効な添付がある場合だけ許可する。 |
| 会話履歴取得 | 各Messageに添付メタデータを返す。原本やBase64を履歴JSONに埋め込まない。 |

受付transactionで全添付の所有者・会話・有効期限・未関連状態を確認し、発言との関連・run・queue jobをまとめて確定する。queue満杯などの失敗では全てrollbackし、画像は再送に使える未関連状態へ戻る。requestId競合判定には正規化本文と順序付き添付IDを含める。

複数画像のアップロードの一部だけが成功した場合、成功済みIDを保持して残りだけ再試行する。未関連の画像は、確認済みの保持期限と保存容量上限に従い、既存queueまたはschedulerで回収する。関連付けと回収は同一writerで競合を防ぐ。撤回された発言の画像は取得・新規推論利用を拒否し、進行中の回答も既存の取消と採用検査に従って不採用にする。

拡張子やFile.typeだけで判定せず、backendで実データ、寸法、デコード可能性を検証する。受信bytes、画像枚数、画素数、会話全体の保存容量に有限の上限を設ける。画像decoderは既存依存で実現できるかを調査し、足りなければJPG・PNG・BMPの検証に必要な最小依存を選び、その理由を記録する。手作りの不完全なヘッダー検査だけで破損画像を受理しない。

## 推論と資料の扱い

内部メッセージは、systemとassistantの文字入力を維持し、userに本文と順序付き画像参照を持てる型を導入する。DBやqueue payload、検索queryにBase64を混ぜず、非同期実行段階で`conversation`の公開読取操作から原本を解決する。LARMには確認済みのwire形式で変換して送る。

会話の主モデルはツール選択前から実画像を受け取る。`prepareRouting`などの文字検索には本文を渡し、画像データを文字列化しない。画像だけの入力でも候補検索の空文字を扱え、主モデルが回答または必要なツールを選べるようにする。画像内容からの検索語や依頼文の作成が必要ならLLMが行う。画像の有無や語句で用途を決める専用分岐は追加しない。

commandや委譲先に画像が必要な場合、主モデルの説明と資料IDを渡し、画像入力対応が確認された経路だけで原本を解決する。文字専用の委譲先に添付名だけを渡して「画像を見た」と扱わない。今回の完成条件は主会話での画像利用であり、全委譲先の画像対応を先行実装しない。

主モデルへの指示に、添付をユーザー提供資料として扱うこと、画像内の文字や命令によって権限を増やさないこと、不鮮明・不足なら確認すること、画像だけの入力では内容に応じて応答することを追加する。対象や用途の判定はLLMに委ねる。固定の画像説明文や題材別処理は追加しない。

最近の会話windowに残る画像は、元のユーザー発言に付けて再送する。本文・添付・回答を同じ会話単位で扱い、予算削減で本文だけ残して画像を見た扱いにしない。現在の入力と直近の画像を黙って落とさず、収まらない場合は明示的に失敗させる。古い画像がwindow外なら、その制約をモデルと利用者に伝え、履歴の「入力欄に追加」操作で原本を再添付できるようにする。履歴取得権限を検査して新しい未関連添付参照を作り、過去の関連を移動しない。

文字のMemory処理には原本やBase64を送らない。既存の文字契約を維持し、画像だけの発言を空文字エラーや解析済み資料と扱わない。画像内容を永続的な記憶に変換する仕組みは別計画とする。画像付き回答の有効性は資料snapshotと会話revisionで検査する。

`fitContext`の現行JSON bytes推定は画像の入力token推定に使えない。転送bytes上限と、文字・画像を含むモデル入力token予算を別に検査する。Base64膨張は転送容量に含める。画像token計算・事前計数・画像前処理はLARMの回答に従い、計数できない場合の契約も確定させる。数字を推測してlive利用を開始しない。

選択profileの能力情報を発見・claimと結び付けて保持し、lease更新や再claimで更新する。モデル名に`ornith`が含まれるだけでは画像対応と判定しない。対応能力が不明または文字専用ならUIとbackendの両方で画像送信を止める。backend credential、claimされたURL、保存済み設定は既存経路を使う。

## 検証手順

新規試験は各domainの所有場所に置く。API横断試験は`api/application/`、ブラウザは`tests/browser/chat-image-attachments.spec.ts`を予定する。以下のコマンドは実装後の実行計画であり、今回の文書作成で実行した結果ではない。

| 段階 | 方法 | 期待結果 |
| --- | --- | --- |
| 部分 | `bun run test:domain -- conversation`、`dialogue`、`inference`、`larm`を順に実行。追加DS部品はpackageの既存試験手順を使う。 | JPG・PNG・BMPの正常系、破損・偽MIME・画素数・容量境界、添付付き契約、画像予算、取消検査が通る。 |
| 結合 | 追加したAPI fixture試験を`bun test <追加した試験ファイル>`で実行。clientとWebの所有試験も実行する。 | 一部upload失敗、受付応答の消失と再送、requestId競合、他会話参照、期限回収、queue満杯、再起動後取得を確認する。 |
| domain gate | `bun run verify -- --domain conversation`、`dialogue`、`inference`、`larm`。変更時は`memory`、`agent-runtime`、`artifact`等の利用側も追加する。 | format、lint、型依存閉包、domain境界、所有試験が成功する。 |
| buildとブラウザ | `bun run build:web`後、既存のPlaywright設定で上記ブラウザ試験を実行する。 | チャット各位置へのdrop/paste、混在貼付、二重受付防止、送信snapshot、添付削除・拡大、狭幅・暗色、音声自動送信からの分離が通る。 |
| 横断 | `bun run verify:all`。 | 全体gate成功。担当外の失敗なら証拠・影響・続行条件を記録し、その部分は修正しない。 |
| live | backend settings domainの読取専用操作で保存済みLARM設定を使い、隔離した確認会話から実ornithへ送る。 | JPG・PNG・BMP各1件以上、複数画像の比較、画像だけの送信、直後の質問での再参照を実モデルで確認する。 |

実画像が送られた証拠としてfixtureで添付順・MIME・digest・bytes一致を確認し、liveでは検査用画像の内容に依存する質問で応答を確認する。画像は合成した非機密資料を使用する。固定試験成功をlive成功と同一視しない。

転送時間、初回応答までの時間、画像入力token、保存増分を、仕様上限付近を含む代表画像で測る。受信・表示・推論で不同の上限を設ける場合は利用者への説明も確認する。通常ログはrequestId・runId・jobId・HTTPのX-Request-Id、件数、容量、経過時間、分類したエラーだけとし、画像・本文・ファイル名・秘密・provider生応答は入れない。

失敗時は再現条件と証拠を保存し、担当範囲の原因が絞れた場合にだけ修正する。同じ失敗に新しい根拠がなければ再実行を止め、計画を見直す。期待値や上限検査を弱めて通さない。途中の通し試験は未完成箇所の想定内失敗と製品不具合を区別する。

## LARMに確認する事項

問い合わせ用Prompt: [LARMの画像入力契約確認](larm-multimodal-contract-inquiry-prompt-2026-10-13.md)。送信・上流設定変更はこの計画に含めない。

確認するのは、配備版の送信形式、主・補助profileの画像対応と能力フィールド、3形式の対応範囲、枚数・容量・寸法上限、画像tokenの計数、画像履歴の再送、画像とstream/tool/JSON出力の組合せ、lease・取消・データ保持の条件。回答は現行仕様・実測・未確認を分け、秘密を含めず最小要求例と根拠を添える。
