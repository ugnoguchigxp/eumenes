# CLIからの対話モード（2026-10-31）

状態: 実装・固定試験・CLI実接続2往復を確認済み。既存のAPIクライアントに入力・表示の入口を追加する。会話の設計・判断方式は変えない。

## 目的・範囲

`bun run cli -- chat`で文字の会話を続け、自然言語で制作を依頼できるようにする。既定のconversationIdはWebと同じ`main`。CLIも`POST /api/runs`で送信し、既存の担当選択・協働セッション・確認・制作・完了通知を使う。CLIからDBは開かない。

- 起動時に会話APIの履歴を表示する（既存APIの上限200件。古い発言は既存history-search/history-readで読む）。表示する発言の本文を省略しない。
- 送信は毎回UUIDを付け、通常の会話として保存する。確認質問への返答も同じ送信経路を使う。特定の依頼文の判別や固定応答をCLIに追加しない。
- 既存の変更通知`subscribeChanges`を購読し、会話APIを読み直す。Webからの発言・非同期の完了通知も表示する。既存Webは同じ通知とAPIからCLIの発言・返事を取得する。Webが閉じていても会話は保存される。
- Webの`RunDetails`と同様、会話のruns APIから、各入力に対応する最新runの`announcement`も本文の後に表示する。制作依頼の受付文は会話メッセージとは別に保存されるため、会話APIだけでは表示が欠ける（タイマー作成の結合試験で再現）。CLI内の表示用IDを付け、JSON出力では`type: announcement`で通常の発言と区別する。
- 発言IDと表示内容で重複を抑え、変更された発言は更新と明記する。artifact presentationの入力はWebと同様に会話表示から除く。
- 自分の送信の応答待ちは既存`watchRun`を使い、確定後に会話を再取得する。標準入力を行単位で読み、EOFでは送信済みの応答待ちを終えて終了する。
- `/exit`・`/quit`で終了。Ctrl+CはCLIの購読・待機だけを終了する。受付済みの仕事はbackendに残り、Webで継続できる。取消は既存`cancel`を利用する。
- 通常は発言者と本文を表示し、`--json`は発言ごとのJSON行。端末ではプロンプトを出す。APIの失敗はstderrに出し、送信結果が不明ならrequest IDを残し、自動再送しない。

アーティファクトはCLIで描画・操作しない。保存される制作の依頼・実行は既存経路に流し、画面操作が必要な工程はWebで行う。CLIから表示中のWebアーティファクトを参照しているとは申告しない。

DBスキーマ、公開API、認証、LLMへの指示、モデル・Profileの選択、ツールチェーンの登録、Web表示の責務は変更しない。新しい依存ライブラリは追加しない。既存の未コミット差分はこの作業の変更に含めない。

## 手順・依存関係・完了条件

1. CLIコマンドを追加し、会話の読取り・通知の購読・送信・応答待ち・終了を接続する。
2. サーバー不要の固定試験で、履歴、全文、双方向の変更、再接続時の重複、制作依頼の通常送信、エラー、購読解除を確認する。
3. 一時的な試験サーバーの操作が許可されたらCLIプロセスと既存APIを結合して、連続送信とWebと同じ会話の取得を確認する。
4. `bun run verify -- --domain conversation --domain dialogue`を実行し、CLIはdomain所有外のため対象試験と静的検査を別途確認する。サーバーを使う試験は許可後に行う。
5. 差分から個別の依頼への分岐・判断の複製・無関係の変更がないことを確認し、利用手順と実施済み・未実施の検証を記録する。

## レビューとデバッグ導線の改善（2026-10-31）

目的は今回のCLI対話モードの欠陥を直し、AIがREADME・AGENTS・利用手順から再現と追跡の入口を見つけられるようにすること。既存のLLM指示、会話API、SSE、run照会、ログ・エラーレポートを使い、DB・担当の判断・実行方式は変えない。

レビューで確認した対象:

- 対話中の例外を単なる文字列にしており、APIの追跡IDと既存CLIの終了コードが失われる。既存入口のエラー表示を共通化して再利用する。
- パイプ入力では送信・応答の失敗後も次の行を送る。非対話入力は最初の失敗で停止し、結果不明の要求に依存した後続入力を送信しない。端末での会話はエラーを表示して継続できる。
- 待機中のCtrl+Cを処理失敗扱いし、backend側の取消も処理失敗3としている。CLIだけの終了は0、backend取消は既存CLIと同じ4に揃える。
- 応答待機の例外が、その後の再取得の例外に置き換わり得る。最初の失敗の原因・追跡先を保持し、表示更新の失敗も確認可能にする。
- 別のコマンド用の履歴・件数オプションを黙って無視していた。文書で示した`--conversation`・`--json`以外は送信前に拒否する。
- 入力契約違反も処理失敗3としていた。既存のsubmit schemaによる入力検査の違反を2にし、サーバー応答の契約違反とは区別する。
- 表示直後、再取得Promiseが完了する直前の変更通知が失われる。読み取り処理の終了時に待機中の印を先に解放し、その直後の通知が再取得を始められるようにする。マイクロタスクで通知を挟む固定試験で再現した。

手順: 既存12件の基準結果と追加の失敗再現を確認 → 最小修正 → CLI単体と実API/SSE結合 → 関連domainのverify → 差分の再レビュー。3ラウンドごとに証拠と残件を整理する。完了条件は対象の指摘に回帰試験があり、試験・静的検査が通り、差分の再レビューで新たな未解決の欠陥がないこと。製品サーバーの操作や無関係の既存差分は対象外。
