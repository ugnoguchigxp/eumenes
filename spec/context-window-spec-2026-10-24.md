## 1. 目的と範囲

会話エージェントがLLMへ渡す文脈（ContextWindow）の、内容・形式・並び・予算・保持・更新・忘却・キャッシュの扱いを定める。

満たす要件:

| # | 要件 |
| --- | --- |
| G1 | エージェントが常に作業できる空間（出力・思考・作業領域）を確保する |
| G2 | 記憶をinput cacheとして扱えるよう、変わりにくいものを先頭に置き、先頭を毎回変えない |
| G3 | 指示（プロンプト）と資料（記憶・記録・結果）を取り違えない |
| G4 | 普段の入力を小さく保ち、待ち時間（prefill・生成・思考）を抑える |
| G5 | 忘却・訂正をキャッシュより優先し、保存した複製まで消す |
| G6 | 会話を往復（依頼→完了報告、質問→回答）に単純化しない。自発的な発言・連続した発言・割込み・仕事の状態の変化を、時刻順の出来事として扱う |

範囲外: サブエージェント（toolchainの担当）の文脈、記憶担当（steward）の各stepの文脈、Agencyの内部の文脈、初期判断以外の補助LLM呼出し。ただし、それらから会話エージェントの文脈へ入るものの形は本書で定める。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 生成 | 会話エージェントのLLM呼出し1回（tool結果を受けて続ける呼出しを含む一連） |
| きっかけ | 生成を始める理由。利用者の新しい発言、TODOの変化、通知 |
| 出来事 | 利用者の発言、エージェントの発言（返事・自発・報告）、エージェントの行動、利用者に提示した通知 |
| 資料のJSON文書 | 記憶・記録・状態を入れる一つのJSON文書（§5） |
| 計画窓C | 予算の計算に使う窓の大きさ（§7） |
| 再構成 | 保留していた書換えをまとめて反映し、新しい窓の版を作ること（§12） |
| 準備 | 再構成で使う要約・統合を、LLMで背景で作ること（§12） |
| 凍結した文字列 | 窓に入れた項目の、描画済みのJSON文字列。再構成まで変えない（§11） |
| 長期記憶 | 本人について長く保つ記憶（制約・好み・事実・習慣・傾向）。`memory` domainが持つ（§5.6） |
| アクティブな短期記憶 | 今の会話で動いている情報（出来事の流れ・経緯・仕事の結果・短期メモ）。`continuity` domainが持つ（§5.6） |

本書は「ターン」を単位にしない。

## 3. 原則

1. **正本は各domainの台帳、ContextWindowは投影。** 会話の発言・実行台帳・記憶は、それぞれのdomainが正本を持つ。窓の文字列を正本として扱わない。
2. **変わりにくい順に前から並べる。** 毎回変わるものは末尾に置く。
3. **普段の変化は末尾への追加だけ。** 途中の書換え・削除・要約への置換えは、再構成のときにまとめて行う。
4. **指示の形をしているものを限る。** 指示の権限を持つのはsystemと、利用者の新しい発言（なければhostの固定文）だけ。それ以外はすべて出所付きの資料にする。
5. **同じ内容を二重に作らない。** 結果や出来事は一つの形で持ち、短縮版や一文要約を別に作らない。
6. **小さく保つ。** 窓の上限は使い切る量ではない。大きい資料はサブエージェントの文脈で扱い、会話エージェントには短い結果だけを渡す。
7. **正確さはキャッシュより優先する。** 忘却・訂正のためなら先頭が崩れることを許す。
8. **プロファイル名・モデル名を書かない。** 窓の大きさや思考の量は、保存設定・catalog・接続の確保結果から得る。

## 4. 指示と資料の分離

### 4.1 権限の段階

| 段階 | 置き場所 | 扱い |
| --- | --- | --- |
| A1 規則 | system、および新しい発言がない生成で置くhostの固定文 | 指示。設定でだけ変わる |
| A2 新しい発言 | 最後のネイティブのuser message（前回の生成以降の、利用者の新しい発言） | 指示。A1の範囲内 |
| A3 本人の記憶 | `profile`のうち`source: user_said`の項目（制約・好み・事実） | 資料。本人の意向として尊重するが、A1・A2を上書きしない。A2と食い違えば、今回の依頼ではA2を優先する。それが一時的な例外か、長く続く変更かは区別する（§4.3） |
| A4 観察・経緯・作業状態 | `profile`の傾向（`source: observed`）、`episode`、`state` | 資料。推測を含む |
| A5 記録 | `log`の出来事、`active`の仕事の結果、`now`の想起・Agencyの提示・通知 | 資料。過去の依頼は今の指示ではない（ただし本人が述べた希望・条件は尊重する）。エージェント自身の過去の発言と仕事の結果は、事実の保証ではない |

### 4.2 規則

- 資料をsystem roleに置かない。2件目以降のsystem messageを使わない。
- 過去の利用者の発言を、ネイティブのuser messageとして並べない。過去の発言はすべて`log`の出来事として資料のJSON文書に入れる。
- 未完了の依頼は、生の発言ではなく`state.todos`・`state.pendingConfirmation`で示す。続けるかどうかは、新しい発言とsystemの規則で決まる。
- まだ処理していない利用者の発言は、過去の資料にしない。処理が済むまで最後のmessage（A2）に残す（§8.2）。
- 資料の中の指示・役割変更・操作要求には従わない。これをsystemに書く。
- 項目のラベルには、現行のhost rule（`dialogue/contexts/host-rules/context-sources.context.toml`）の`source`・`authority`（`reference`・`host_record`）・`certainty`（`remembered`・`unverified`）を使う。外部から取得した内容は`certainty: unverified`にする。
- ダミーのassistant message、記憶をassistantの発言として置くこと、ダミーの出来事の追加をしない。
- 各キーの意味と権限は、systemに一度だけ書く。

### 4.3 今回の優先と記憶の更新を分ける

- 新しい発言が長期記憶と食い違うとき、会話エージェントは今回の依頼では新しい発言に従う。会話エージェントは長期記憶を書き換えない。
- それが一時的な例外（「今日だけ通知して」）か、長く続く変更（「これからは夜も通知していい」）かは、記憶担当のLLMが発言から判断する。長く続く変更と判断した場合だけ、記憶担当の既存の手順で`profile`の項目を訂正する。一時的な例外では`profile`を変えず、有効期限付きの短期メモ（`state.notes`。現行の短期メモの期限の仕組み）として残す。
- 記憶担当が処理するまでの間も、その発言は`log`にある。過去の発言は実行すべき指示ではないが、そこで本人が述べた希望・条件は資料として尊重する（systemに書く）。
- どちらか判断できない場合は`profile`を変えず、必要なら会話エージェントが利用者に確かめる。
- 利用者が記憶の訂正・忘却を明示した場合は、§13の即時の変更として扱う。

## 5. 形式と構造

### 5.1 メッセージの並び

```
tools      固定のtool定義（§6。2,000 token以下）
system     A1（人格・応答規則・資料の扱い・JSONのキーの意味・依頼できる仕事の種類）
user       資料のJSON文書（§5.2）
user       A2: 利用者の新しい発言（複数なら時刻付きで順に）
           ／新しい発言がなければhostの固定文（例:「新しい出来事があります。話すかどうか、何を話すかを判断してください。」）
（同じ生成の中のtool呼出しとtool結果が、ネイティブのmessageで続く）
assistant  発言（話さないと判断した場合はなし）
```

- 利用者の新しい発言は、処理済みになるまでネイティブのmessageに置き、処理済みになったら`log`の出来事になる（§8.2）。添付の画像は、その発言が未処理の間は最後のmessageに付けて送る（§7.3）。
- 新しい発言が複数たまり、作業領域`W`の半分を超える場合は、古いものから先頭と参照IDに縮める（落とさない）。
- hostの固定文は常に同じ文字列にする。

### 5.2 資料のJSON文書

キーは次の順に固定する。

| キー | 内容 | 権限 | 変わるとき |
| --- | --- | --- | --- |
| `profile` | 本人の長期記憶（制約・好み・事実・習慣）と傾向 | A3・A4 | 再構成のとき、即時の変更（§13） |
| `episode` | `log`から外れた会話の経緯。区切りの配列で、各要素は`kind: summary`（要約）か`kind: unsummarized`（未要約の印、§8.3）と時間の範囲を持つ | A4 | 再構成のとき |
| `log` | 出来事の流れ（§8） | A5 | 末尾への追加。途中の書換えは再構成のとき |
| `active` | アクティブな短期記憶にある仕事の結果。TODOごとに1枠。枠の順は最初に入った順で、上書きしても位置は変えない（§9.3） | A5 | TODOが`done`・`waiting`になったとき、確認したとき（同じTODOは上書き）、アーカイブの確定のとき（枠を削除） |
| `state` | `todos`（archivedを除くTODOの一覧）、`pendingConfirmation`（hostが発行した実行前の確認、§6.7）、`retained`（最近使ったtoolchain）、`decisions`・`askedUser`・`goals`（記憶担当、§10.2）、`newMemories`（長期記憶へ反映待ち）、`notes`（短期メモ） | A4 | 毎回 |
| `now` | 現在日時（日付・時刻を聞かれたらこれで答える）、`trigger`（この生成のきっかけの配列、§8.2）、`speaking`（配信中のエージェントの発言、§8.1）、通知、自動想起、Agencyの提示 | A5 | 毎回 |
| `work` | この生成に必要な資料の全文（利用者が資料の中身を求めた場合だけ） | A5 | 毎回 |

### 5.3 書き方

- キーの順・配列の項目の順・項目内のキーの順を固定し、字下げなしで出力する。同じ窓の版からは同じ文字列が出る。
- 日本語は`\uXXXX`に変換せずに出力する。エスケープするのは`<`・`>`・`&`と行区切り文字（U+2028・U+2029）だけとする（現行の`memory/service/turn-recall.ts`の`safeJson`と同じ）。
- キーは短く読める英語にする。
- 時刻はすべてISO 8601の秒までの値に`+09:00`の時差を付ける。日付の境は`Asia/Tokyo`で判定する。

### 5.4 長期記憶の規則

- `profile`の項目に、相対的な時刻、現在日時、アクセス回数、関連度の点数を入れない。日付は絶対値で持つ。時刻で変わる情報は`now`に置く。
- `profile`の種類内の順は、公開済みの順を保ち、新しい項目を末尾に足す。全体の並べ直しは再構成のときだけ行う。予算不足のときに残す順は、描画順とは別に持つ。
- 長期記憶へ反映待ちの新しい記憶は`state.newMemories`に置き、再構成のときに`profile`へ統合する。

### 5.6 長期記憶とアクティブな短期記憶

長期記憶と、今の会話で動いている情報は、保存先も寿命も分ける。両者を一つの保存先に混ぜない。

| 層 | 中身 | 窓のキー | 保存先 | 寿命 |
| --- | --- | --- | --- | --- |
| 長期記憶 | 本人の制約・好み・事実・習慣、傾向、長期へ反映待ちの新しい記憶 | `profile`、`state.newMemories` | `memory` domain（現行の`eumenes-memory`のState・傾向） | 忘却・撤回・期限切れまで |
| アクティブな短期記憶 | 出来事の流れ、経緯の要約、仕事の結果、短期メモ（決定事項・利用者への問い・一時的な例外） | `log`、`episode`、`active`、`state.decisions`・`askedUser`・`notes` | `continuity` domain（現行の短期メモを拡張） | 会話の中で手放すまで（§8.3・§9.3）。台帳の原文は会話側に残る |
| 窓の外の正本 | TODO（仕事の状態）、目標、実行前の確認、最近使ったtoolchain | `state.todos`・`goals`・`pendingConfirmation`・`retained` | 実行台帳（tool-runtime・agent-runtime）、`goals`、dialogue、tool-runtime | 各domainの規則 |

- `continuity`は最下層（`docs/domains.md`のlevel 0）で、`memory`（level 3）は`continuity`を参照できる。長期記憶の忘却を短期記憶へ届けるときは、`memory`が`continuity`の公開操作を呼ぶ（§13）。
- 記憶担当は両方を扱うが、書き込み先は層ごとに分ける。経緯の要約・短期メモは`continuity`へ、長期記憶の統合は`memory`へ書く。
- 記憶ツール（§14）が読むのは長期記憶だけである。アクティブな短期記憶はすでに窓にあり、窓から外れた会話の原文は会話履歴（§14）で読む。
- 現行は往復の台帳・要約・窓の保管を`memory` domainが持っている。これらはアクティブな短期記憶として`continuity`へ移す（§17）。

## 6. tool定義と生成

### 6.1 tool定義

tool定義は全生成・全段階で同じ一組とし、推定2,000 token以下にする（§23）。

| tool | 引数 | 動作 |
| --- | --- | --- |
| 記憶ツール | 操作（読取り・依頼）。読取りは探したい内容または項目ID。依頼は種類（`forget`・`remember`・`correct`）・対象・詳細 | 読取りは長期記憶（State・傾向・反映待ち）だけを返す（§14）。依頼は現行の`memory_request`と同じく記憶担当の依頼キューへ入れ、受付を返す（§13） |
| 担当の検索 | 最初に行う作業の用途を表す検索文 | 現行の`find_toolchain`と同じ検索を行い、候補（最大4件）の説明をtool結果で返す。実行はしない |
| 依頼 | 方式（`execute`・`confirm`・`approve`）。`execute`・`confirm`はtoolchainのID、依頼文、予告または確認文（80字以内、§6.5・§6.7）、影響（`none`・`create`・`modify_existing`・`irreversible`）、パイプラインなら入力、session型なら対象と未保存の作業の扱い（現行の`target`・`resolveUnsaved`）。`approve`は確認の参照だけ | `execute`は選んだtoolchainへ仕事を渡しTODOを作る。即答できるtoolchainはTODOを作らず、答えをtool結果で返す。`confirm`は実行せず、実行前の確認を発行する。`approve`は確認に保存した依頼をそのまま実行する（§6.7） |
| 仕事の操作 | TODOのID、操作（確認・質問への回答・依頼の訂正・取消・アーカイブ）、期待する依頼の版（`state.todos`または`active`の`revision`）、質問への回答なら質問ID、本文、アーカイブなら伝えた根拠（§9.4） | 確認はTODOの現在の状態・版・結果を返す（§9.3）。確認・回答・訂正・取消は現行の`executionControl`（`workRef`・`expectedRevision`・`action: status/answer/amend/cancel`・`questionRef`）に対応する。版が古い操作は実行せず、最新の状態と版を返す。訂正で版が進んだら新しい版を返す。アーカイブは新しい操作で、要求として記録し、§9.4の条件で確定する |

- toolchainのIDは列挙値にしない。hostは、そのIDがこの生成の検索結果または`state.retained`に示したものかを検査する。
- 影響の値は§6.7の確認の要否に使う。実行直前の失効検査は既存の`dialogue/service/operation-authority.ts`で行う（§6.7）。
- 合うtoolchainがない・できない場合は、本文で利用者にそう伝え、発話の`unavailable: true`を付ける（§6.3）。
- systemには、依頼できる仕事の大まかな種類（調べ物・操作・画像・楽曲・コード作業など）だけを数行で書く。
- 1回の生成のtool呼出しの回数・合計token・時間の上限はhostが強制する（初期値は§20）。担当の検索は1回の生成で1回までとする。
- tool定義・出力の説明は、判断の区別に必要な説明を削らない。分類・承認の引数（§6.3）の説明を共通指示へ移す・短くする比較では、実モデルで分類と承認の誤りが増えた（§22）。分析の4値の説明だけで推定約430 tokenある。
- モデルへ送るtool定義は、tool一つにつき一つのobjectとし（方式ごとの`oneOf`に分けない）、idの長さの範囲は書かない。意味のある上限（予告の80字など）だけを説明文に書き、`impact`の説明は依頼toolに置く。方式ごとの必須項目と、すべての長さ・件数の範囲はhostの検査が保ち、違反は理由をtool結果で返す（§6.6）。
- LARMへ送るschemaに文字列長の範囲（`maxLength`等）を入れると、HTTP 500になる場合がある（§22）。LARMへ送るgrammarでは長さの範囲を説明文へ移し、hostの検査では元の制限を保つ。制限そのものを外さない。

### 6.2 toolchainの情報

| 情報 | 置き場所 | 寿命 |
| --- | --- | --- |
| 最近使ったtoolchain（最大4件。ID・一行の説明・前回の使い方の要点） | `state.retained` | 毎回変わってよい |
| 担当の検索で得た候補の説明（現行の候補カードの内容。1件の上限を決め、4件で約1,000〜2,000 token） | その生成のtool結果 | その生成だけ。`log`には候補のIDと名前だけを残す |
| toolの使い方・schema・SKILL | サブエージェントの文脈 | 会話エージェントには入れない |

仕事を引き受ける前に、会話エージェントは候補を見てこなせるかを評価する。合う候補がなければ依頼せずに断る。

### 6.3 生成の形

- 会話エージェントは eumenes-agency である（[会話エージェントを agency に置き換える設計](agency-conversation-agent-design-2026-10-25.md)、2026-10-25 合意）。返答は agency の `runRespond` が行い、hostはモデルの呼出し（`executeStream`）と固定のtoolの実行を渡す。
- 1回の生成で、話す・記憶を読む・担当を検索する・依頼する・仕事を操作する、を組み合わせて選べる。toolを呼んだ場合は、tool結果を受けて続ける。同じ先頭なので、続きの呼出しはキャッシュが効く。
- タスクの依頼かどうかを判断する回を設けない。会話の流れでツールが必要と判断したら、その返答の中で担当を使う。発言の分類（`kind`・`freshness`・`impact`・`approved`）は出させず、分類と行動の突き合わせ（根拠のない回答の検査）もしない。
- 断りは本文で話す。承認は依頼toolの`approve`、影響は依頼toolの`impact`で表す（§6.7）。

### 6.4 発話の契約

- 発話は音声向けに短くする。通常は1文、補足を含めても2文、音声用の整形後で300字以内（`SPOKEN_REPLY_MAX_CHARS`・`SPOKEN_REPLY_MAX_SENTENCES`）。予告は80字以内。
- 発話の長さは agency の文体の規則（音声向けの話し言葉、1〜3文）で保つ。hostは書き直させない。
- 検査前の発話を配信しない。表示用の成果物、操作の引数、制作の要件にはこの契約を適用しない。出典URLは発話の長さに数えない。
- 提示されたtool名を本文に書いた出力を、正式な呼出しとして採用しない。

### 6.5 依頼の前の予告

- TODOを作る依頼（`execute`・`approve`）には、これから行うことを伝える短い予告（例: 「お調べします」）を必ず付ける。toolchainと予告の固定文の対応表は作らない。担当が決まる前に予告しない。
- 即答できるtoolchainは予告を付けず、答えをtool結果で受けてそのまま話す。即答できなかった場合はtool結果がそれを返し、会話エージェントが改めて予告付きの`execute`を選ぶ（現行の、即答できないときに同じrunで別のtoolchainへ自動で回す動作は廃止する）。
- hostは予告を検査し、`said`（`origin: announcement`）として確定し、委譲より先に配信する。音声の自動読み上げが有効なら、予告の配信結果（§8.1の`delivered`）を待ってから委譲を確定する。
  - `heard: full`、または`heard: partial`（利用者の割込み）なら委譲を確定する。割込みの発言は次の生成で扱い、取消なら仕事の操作で取り消す。
  - `heard: none`（再生の失敗）・取消・期限・権限失効なら委譲しない。
- 生成のやり直しで、予告を再配信せず、委譲も重複させない（§8.2の二重実行の防止）。
- 予告は完了や成功の証拠ではない。

### 6.6 受け付けない呼出し

- 不正な引数・未知のtool・回数の上限・担当の検索の2回目は、hostが受け付けず、その理由（`refused`・`issues`・`fields`）をtool結果として返す。会話エージェントは結果を見て直して呼び直すか、できないと伝える。生成を失敗にしない。
- 提示されたtool名や制御構文を本文に書いた出力（`control_text_in_body`）は採用しない。
- 主会話の生成の呼出しの出力は1,024tokenまでとする。toolを渡していても温度を固定しない（`speaks`）。停止文字列（`stop`）は付けない（本文の後の空行で`respond`の呼出しの前に切れた run `6839d520`）。
- 生成が失敗で終わったrunでは、その生成が受け取った発言を処理済みにする（run `3f369993`）。利用者の中止で終わったrunの発言は未処理のまま残す（[止めて編集](prompt-edit-design-2026-10-24.md) Q5）。
- 2026-10-25 までの`respond`・分類・根拠の検査・構造の修正（`respond_required`・`answer_without_basis`・`speech_required`・`spoken_reply_too_long`、`tool_choice: required`）は廃止した。ただの会話が返答なしで失敗した（run `6839d520`・`5145885e`）。

### 6.7 実行してよいか

- 実行できる依頼は、提案して返事を待たない（「画像を作りましょうか？」で止めない）。依頼し、予告して、そのまま実行する。
- 既存のものを変える依頼（`modify_existing`）と、取り消せない操作（`irreversible`）は、実行の前に確認する。保証は次の三つに分け、それぞれ担当を決める。

| 保証 | 内容 | 担当 |
| --- | --- | --- |
| 確認の要否 | 影響は、会話エージェントの申告と、toolchainの登録定義が宣言する影響の下限（bundleの新しい項目`minImpact`）の大きい方とする。下限が未宣言なら申告を使う。`modify_existing`・`irreversible`なら`execute`を受け付けず、`confirm`を求める | dialogueの採用処理（新設）。`minImpact`の追加は[登録と拡張の手順](../docs/toolchain-extension.md)に従う |
| 確認の発行 | 会話エージェントが依頼toolを`confirm`で呼ぶ。hostは確認（ID、toolchainのID、依頼文と入力、影響、期限）を保存し、確認文を`said`（`origin: confirmation`）として配信し、`state.pendingConfirmation`に載せる。実行はしない | dialogueの採用処理（新設） |
| 承認の判定と対象の一致 | 新しい発言が承認かどうかは会話エージェント（LLM）が判断し、依頼toolを`approve`で呼んで確認の参照だけを渡す。hostは確認に保存した依頼文・入力・toolchain・影響をそのまま実行に使い、LLMに再入力させない。hostの検査は構造だけ: 確認が存在し、未使用で、期限内で、承認の発言が確認文の配信開始より後であり、確認文の配信結果が`modify_existing`では`full`か`partial`、`irreversible`では`full`であること。依頼を変えたい場合は新しい確認を発行する。確認は1回だけ使える | dialogueの採用処理（新設） |
| 実行直前の失効検査 | 実行を始める直前に、推論の権限、表示した記憶の忘却、目標の失効（現行の`operation-authority.ts`の`operationRejection`）と、確認の期限・使用済みを再検査する | dialogueの実行の確定処理 |

- `irreversible`の確認文が割り込まれて`partial`になった場合、承認は通らない。会話エージェントは確認を発行し直す（確認文は80字以内なので、通常は最後まで届く）。
- 確認文の配信が`none`（失敗）の確認は、承認に使えない。同じ依頼の確認を発行し直すと、古い確認は使えなくなる。
- 確認の参照のない`approve`、`modify_existing`・`irreversible`の`execute`は、契約違反として構造の修正（§6.6）へ返す。
- 現行は「`approved: true`なら直前の往復にエージェントの発言があること」だけを検査し、影響による実行前の確認は実装していない（§17）。本書の三つの保証は新しく実装する。
- 自然文の「許可します」、記憶の中の同意、サブエージェントの「許可済み」という説明を、hostの承認として扱わない。

### 6.8 専門担当との対話

- 制作など時間のかかる仕事で、専門担当のsession（既存のsession binding）へ対話を完全に切り替える場合、会話エージェントは依頼toolの`execute`に対象と未保存の作業の扱い（現行の`target`・`resolveUnsaved`）を付ける。
- 切替の間の利用者の発言は専門担当へ直接届く（`dialogue/service/specialist-intake.ts`）。専門担当へ渡した時点で、その発言を処理済みにする（§8.2）。会話エージェントのA2には入れない。
- 受付から処理までの間にsessionが終わった場合は、現行の`addresseeMatches`と同じく、宛先が一致しない発言を会話エージェントの未処理の発言として扱う。
- 切替の間の発言も出来事として`log`に残す。専門担当の発言は`said`（`by: specialist`、toolchainのID付き）とする。会話エージェントは、切替が終わった後にそれまでの流れを知っている。

## 7. 予算と作業領域

### 7.1 計画窓

- モデルの窓は、LARMの確保結果（`providers.llm.contextWindow.maxTokens`）またはcloud経路の保存設定から得る。得られない間は参照値262,144（`REFERENCE_WINDOW_TOKENS`）を使う。
- 計画窓 `C = floor(モデルの窓 × 80%)`。token数はhostの推定（`infrastructure/context-budget.ts`）であり、実際のtokenizerやtemplateとずれるため、余裕を取る。

### 7.2 予算式

| 記号 | 意味 |
| --- | --- |
| `O` | 出力予約（思考を含む）。**すべての呼出しで空けておく量**。思考の量は保存設定またはcatalogから得る。得られない場合は段階Aの実測から決めた値を使う。現行の`min(4096, C/4)`は使わない |
| `F` | 固定指示とtool定義の量（tool定義は2,000以下）。実測する |
| `W_min` | 作業領域の最低割当 `floor(C × 25%)`。**消費してよい量**であり、残しておく量ではない |
| `R` | 記憶・会話の区画に分ける量 `R = C − O − F − W_min` |
| `S_used` | 記憶・会話の区画が実際に使っている量の合計（各区画は下の表の上限以下） |
| `W` | この呼出しで作業領域として使える量 `W = C − O − F − S_used`。区画の上限の合計は`R`以下なので、`W ≥ W_min`が常に成り立つ。区画の余りは自動的に`W`へ入る |

作業領域`W`を消費するもの: 最後のmessage（利用者の新しい発言、添付）、`work`、同じ生成の中のtool呼出しの引数（assistant message）とtool結果。

区画の上限は `min(割合 × R, 絶対上限)` とする。

区画の割合と絶対上限:

| 区画 | Rに対する割合 | 上限（推定token） |
| --- | ---: | ---: |
| `profile` | 25% | 12,000 |
| `episode` | 8% | 2,000 |
| `log` | 40% | 16,000 |
| `active` | 8% | 4,000 |
| `state` | 8% | 2,000 |
| `now` | 11% | 3,000（Agencyの提示を含む） |

256kの窓での試算（`O`は仮に8,192、`F`は3,000）: C = 209,715、`W_min` = 52,428、R = 146,095。区画はすべて絶対上限が効き、`S_used`は最大39,000、`W`は最小でも約159,500。

区画の上限の合計は常に`R`以下なので、`W ≥ W_min`が成り立つ。`R`が最小値（初期値8,000、§20）に満たない窓（`C`が小さい、または`O`・`F`が大きい）の接続は会話に使わない。設定画面と運用ログに、窓が足りないことを示す。

`state.todos`だけは区画の上限で落とさない（仕事を見失わないため）。`state`の上限を超える分は、`state`の他の項目（`notes`・`retained`）を先に縮め、それでも超える分は`W`から使う。

### 7.3 同じ生成の中で増える分

- 呼出しのたびに、hostは `F + S_used + 作業領域の使用量 + O ≤ C` を検査する。空けておくのは`O`だけである。
- tool結果を足すとこの式を満たさなくなる場合、hostはその結果を参照IDと要点に縮めて渡し、続きを読めることを示す。
- 記憶ツールの結果には1回の上限を設け、超える分は続き用のcursorで分けて読む。
- 添付の画像は、その発言が未処理で最後のmessageにある間だけ送り（取消・失敗で未処理に戻った場合も送る）、1枚1,600（`TOKEN_ESTIMATE.imageTokens`）として`W`に数える。`log`に移った後は参照だけを残し、画像は再送しない（§19）。
- 利用者の新しい発言が長い場合も`W`に数える。`log`へ移るときに1件の上限（§8.3）を適用する。

### 7.4 普段の入力の目標

- 普段の入力は約20,000〜30,000を目安にする。区画の上限は超えてはならない量であり、目標ではない。
- **入力の目標値**（初期値30,000）は `F + S_used` に対する値とする（最後のmessage・`work`・tool結果は含めない）。これを超えたら、次の沈黙の待機中に再構成する（§12）。
- 文脈が長いほど、キャッシュ済みでも生成と思考は遅くなる。計画窓は使い切る量ではない。

## 8. 出来事の流れ（`log`）

### 8.1 出来事の種類

| `type` | `by` | 内容 |
| --- | --- | --- |
| `said` | `user` | 発言（音声・文字）、添付の参照 |
| `said` | `agent` | 発言、`origin`（`reply`・`spontaneous`・`report`・`announcement`・`confirmation`）、任意の`todoRefs`（agency の自発発話が報告したTODOのID） |
| `said` | `specialist` | 専門担当のsessionでの発言（toolchainのID付き、§6.8） |
| `delivered` | host | エージェント・専門担当の発言の配信結果。`ref`（発言の出来事ID）、`heard`（`full`・`partial`・`none`）、`partial`なら`deliveredText`（届いた部分） |
| `acted` | `agent` | 担当の検索（検索文と候補のIDと名前）、依頼（方式・toolchain・依頼文・影響・TODOのID・確認の参照）、仕事の操作（確認・回答・訂正・取消・アーカイブの要求と確定）、記憶の読取り（問合せと結果）、記憶への依頼（種類と受付） |
| `notice` | host | 利用者に提示した通知（タイマー等） |

- `log`の順は**追記した順**である。`at`は実際の時刻を表す。処理済みになって後から`log`へ移った利用者の発言は、`at`がそれより前でも追記した位置に置く。時間の前後は`at`で判断する（systemに書く）。
- 同じtransactionで追記する場合は、利用者の発言（処理済みにしたもの）→ `acted` → `said`（agent）の順にする。
- 出来事は対を作らない。`about`は関係を示す任意の参照であり、質問と回答の対ではない。
- **発言と配信結果を分ける。** エージェントの発言は、発話を確定した時点（配信を始める時点）で`said`として追記する。配信結果は、配信が終わった時点で別の`delivered`として追記する。凍結した文字列を後から書き換えない。配信中の発言は`now.speaking`に出来事IDで示す。
- `heard`の決め方:
  - 音声: 全句を再生したら`full`。一部の句だけ再生し、割込み・停止・句の再生失敗（現行の`audioSkipped`を含む）があれば`partial`で、`deliveredText`は再生できた句をつないだもの。1句も再生できなければ`none`。
  - 文字だけの画面: 既存のdeliveryで配信が完了したら`full`、失敗したら`none`。
  - 句ごとの再生の完了を報告する経路は現行にない（`voice_turns`は発話単位の`played`・`interrupted`だけ）。音声の配信処理に句ごとの再生結果を返す契約を新設する（段階C）。
- 仕事の確認の結果の本文は`log`に入れない（`active`だけに置く）。
- 出来事にしないもの: 話さないと判断した生成、Agencyの内部の判断、モデルの思考の文章、判断の理由の文章、構造の修正のやり直し、採用されなかった発言（構造の検査に落ちた発言、生成が採用されなかった場合の発言）、サブエージェント内部のtool呼出しと生の結果、失敗の内部詳細（outcomeの分類だけ残す）。

### 8.2 きっかけと処理済みの印

| きっかけ | 最後のmessage |
| --- | --- |
| 利用者の新しい発言（話しかけ、連続した発言、割込み） | その発言（A2） |
| TODOの変化（`done`になった、`waiting`になった） | hostの固定文 |
| 通知 | hostの固定文 |
| 前回の生成が、行動の確定後に採用されなかった（§13） | hostの固定文 |

- `now.trigger`はきっかけの配列とし、関係する出来事・TODOのIDを持つ。同時に起きたきっかけはまとめて1回の生成にする。利用者の新しい発言があれば、それが最後のmessageになり、他のきっかけは`now.trigger`にだけ載る。
- TODOの変化のきっかけには結果の中身を入れない。中身は会話エージェントが確認して得る（§9）。会話エージェント自身の操作（取消・訂正）による変化は、きっかけにしない。
- `done`のTODOはアーカイブが確定するまで`state.todos`に残るので、ある生成が話さないと判断しても、以後の生成で常に見える。
- Agencyの自発的な発言は、Agencyの経路（発話後・沈黙後の判断）で作られる。発話を確定した時点で`said`（`origin: spontaneous`）、配信が終わった時点で`delivered`を追記する。

位置と印:

- **閲覧位置**: その生成の文脈に入った最後の出来事。診断と`now.trigger`のためだけに使う。生成の間に追記された出来事は、次の生成で通常どおり`log`に見える。
- **処理済みの印**: 利用者の発言ごとに付ける。発言は、それを含む生成の**最初の採用**（発話の確定、または行動の確定）で処理済みになる。話さないと判断した生成が採用された場合も処理済みになる。専門担当へ渡した発言は渡した時点で処理済みになる（§6.8）。
- 処理済みでない利用者の発言は、何度生成に入っても最後のmessage（A2）に時刻順で置き、`log`には入れない。処理済みになった時点で`log`へ追記する。
- 生成が最初の採用の前に取り消された・失敗した場合、その生成が入れていた発言は処理済みにならず、次の生成で再びA2になる。生成中に新しい発言が来て生成が打ち切られた場合も、未処理の発言は新しい発言と合わせてA2になる。

二重実行の防止:

- 副作用のある行動（依頼、仕事の操作、記憶への依頼）は、生成の途中で呼ばれた時点で確定する。
- 構造の修正（§6.6）や生成のやり直しで同じ行動がもう一度呼ばれても、同じ発言に対する同じ行動は一度しか実行しない。既に確定していれば、確定済みの結果（TODOのIDなど）を返す。重複の判定は、処理する発言と行動の対象（依頼先のtoolchain、TODO）で行う。
- 依頼は予告の配信結果（§6.5）の後に確定する。予告が確定する前に生成が止まった場合は、発言は未処理のまま残る。

### 8.3 保持の単位

- 目安は接続ごとの予算から決める。`log`の上限を`L_cap = min(40% × R, 16,000)`として、上側の目安 `L_hi = min(10,000, L_cap)`、下側の目安 `L_lo = floor(L_hi / 2)`、残す量 `L_keep = min(4,000, L_lo)` とする。発話の上限300字（§6.4）では1往復が推定約370 tokenなので、最大の窓で再構成までに約27往復、再構成の後も直近約10往復が残る。どの窓でも `L_keep ≤ L_lo < L_hi ≤ L_cap` が成り立つ（`R`の最小値8,000では`L_cap` = `L_hi` = 3,200、`L_lo` = 1,600、`L_keep` = 1,600）。
- `log`が`L_hi`を超えたら、次の再構成で古い出来事を`episode`へ移し、`L_lo`まで減らす。
- 切る位置は、範囲内で最も新しい沈黙の区切り（出来事のない間。初期値2分）とする。区切りがなければ出来事の境で切る。
- **会話の再開**（出来事のない間が再開の基準時間（初期値30分）を超えた後の最初の出来事、会話を開き直した、`Asia/Tokyo`で日付が変わった）では、その間より前の出来事を`episode`へ移し、直前の`L_keep`だけを残す。
- 移す出来事の要約は準備（§12）で作る。準備ができるまで、原文を`log`に残す。
- ただし、**区画の上限は要約の完成より優先する**。`log`が上限を超えそうで要約が準備できていない場合（連続した発言で準備が進まない、記憶担当が止まっている等）、hostは次の再構成で、LLMを使わずに古い出来事を`L_lo`まで窓の外へ出す。`episode`の配列の末尾に、その範囲を示す**未要約の印**（`kind: unsummarized`、時間の範囲、件数、「会話履歴ツールで読める」）を置く。続けて未要約が出た場合は、末尾の未要約の印の範囲を広げる（印は連続する範囲ごとに一つ）。
- 未要約の範囲は、後で準備ができたときの再構成で`kind: summary`に置き換える。範囲の一部だけ要約できた場合は、要約した部分を`summary`に、残りを`unsummarized`のまま分ける。`episode`が上限を超える場合は、まず記憶担当が隣り合う`summary`を統合する（準備）。準備がない場合や統合しても超える場合は、hostがLLMを使わずに次の規則で上限内に収める。
  1. 古い側から順に、要素を「範囲だけの`unsummarized`」に置き換える（要約の本文を落とし、時間の範囲と件数と「会話履歴ツールで読める」だけを残す）。
  2. 隣り合う`unsummarized`は一つにまとめる。
  3. それでも超える場合は、最も古い要素から順に、`episode`の先頭の一つの`unsummarized`（「この時刻より前は会話履歴ツールで読める」）に吸収する。
  範囲だけの`unsummarized`は数十tokenの固定に近い大きさなので、`episode`の上限が最小の窓（`8% × 8,000` = 640）でも収まる。記憶担当の長期記憶の抽出は、窓から出たかどうかに関係なく台帳の出来事に対して行う。
- 1件の上限は`L_cap`の10%とする。長い発言は、追加時に先頭と参照IDにして凍結し、全文は台帳に置く。
- 移した出来事の事実は、記憶担当の既存の抽出で長期記憶の候補になる。原文は台帳に残り、会話履歴ツールで読める（§14）。

### 8.4 再構成で縮める部分

出来事は一つの形で保存する。再構成のときに縮めるのは、hostが機械的に決められる部分だけとする。

| 種類 | 縮め方 |
| --- | --- |
| 記憶の読取り | 直近`L_keep`より古いものは、結果を項目IDだけにする |
| 発言・担当の検索・依頼・仕事の操作・通知 | 縮めない |

## 9. 仕事の結果

### 9.1 TODOへの一本化

- 仕事のやりとりはTODOに一本化する。会話エージェントが依頼して起動し、状態・質問・結果はTODOから得る。
- 完了報告を会話へ届ける中継（現行の報告の保留・解放`heldEventId`）は使わない。

### 9.2 サブエージェントの結果

- 結果は一つの形とし、LLM同士が十分わかる量に限る。利用者向けの文章ではなく、会話エージェントが判断・発言するための材料にする。
- 内容: outcome（成功・一部・失敗）、`asOf`、主張と出典ID、制限事項（分からなかったこと・条件）。出典の本文・URL・取得資料は実行台帳に置き、出典IDで参照する。
- 上限は1件600 token（推定）。超えた結果は受け付けず、サブエージェントに縮めさせる。hostは切り詰めない。
- hostやLLMが、結果の短縮版・一文要約を別に作らない。

### 9.3 仕事の結果はアクティブな短期記憶に置く（`active`）

- TODOが`done`になったとき、hostはその結果を、`waiting`になったときはその質問を、アクティブな短期記憶の`active`のそのTODOの枠に入れる。会話エージェントが先に確認しなくても、結果は窓にある。
- 会話エージェントは、仕事の操作の「確認」で、TODOの現在の状態・版（`revision`）・質問ID・結果を読み直せる。確認の結果も同じ枠に入る。
- 同じTODOの枠は、次に入るとき（状態の変化・確認）に位置を変えずに上書きする。古い内容は残さない。
- `log`には確認したこと（`acted`、TODOのIDと時刻）だけを残す。結果の本文は`active`だけに置く。
- アーカイブが確定したTODOの枠は削除する。
- `active`が上限を超えそうな場合は、内容が入った時刻が最も古い`done`の枠から外す。外したTODOは、確認すれば再び入る。
- 結果をいつ話すかは会話エージェントが判断する。

### 9.4 TODOの報告とアーカイブ

- TODOが`done`・`waiting`になったrunは生成せずに完了し（サブエージェントの答えはここで消費）、agency の`result_received`の機会を開く。agency は機会（TODOの変化・発話後・沈黙後）に`done`を一言で報告し、`waiting`の質問を利用者に聞く。
- agency の発話が`done`のTODO（`todo:<id>`）を引用していれば、保存時に報告待ちとして発話へ紐づけ、実際の音声再生が最後まで完了した通知で`archived`にする（2026-10-27変更）。文字の保存・表示だけでは確定しない。
- 利用者の発言への返答がTODOの結果を伝えたかは、agency の背景の update が照合する。伝えた返答の音声が最後まで再生されていれば`archived`、まだなら音声配信の結果を待つ（文字の配信とは区別）。`heard: partial`・`none`なら`done`のまま残り、次の機会で再び見える。
- 完了TODOを引用する報告は雑談の自発発話上限を消費しない。雑談が上限に達していても未報告の完了TODOには報告の機会を作る。音声配信待ちの同じ報告は重ねず、中断・失敗で未報告候補へ戻す。詳細は[todo-spoken-report-delivery-design-2026-10-27.md](todo-spoken-report-delivery-design-2026-10-27.md)。
- 会話エージェントのアーカイブの操作（仕事の操作の`archive`・`told`）は廃止した。利用者が不要と言ったTODOの扱いは後の課題。

## 10. 作業状態（`state`）

### 10.1 TODO

- TODOは実行台帳の仕事から作る投影であり、別の表を持たない。TODOのIDは実行台帳の仕事のID（`executionControl`の`workRef`、UUID）である。現行の`api/application/agency/work.ts`の`hostTodoOf`は、報告の保留（`heldEventId`）の有無で`todo`・`done`を決めている。報告の中継を廃止するため（§9.1）、導出を下の対応表に改め、アーカイブの印を実行台帳に加える。
- 状態と、実行台帳の`ExecutionStatus`との対応:

| TODOの状態 | `ExecutionStatus` | outcome |
| --- | --- | --- |
| `todo` | `queued`・`deciding`・`waiting_child` | ― |
| `waiting` | `waiting_user` | ― |
| `done` | `completed`・`partial`・`failed`・`cancelled`・`interrupted` | `succeeded`・`partial`・`failed`・`cancelled`・`interrupted` |
| `archived` | 終了状態でアーカイブの印がある | 終了時のもの |
- `state.todos`は`archived`を除いた一覧とし、各TODOはID・タイトル・状態・outcome・依頼の版（`revision`）・更新日時・質問ID と質問文（`waiting`のとき）だけを持つ。結果の本文は載せない。仕事の操作に必要な識別情報（TODOのID・版・質問ID）は、この一覧で常に得られる。
- **`archived`のTODOは一切読まない。** 一覧・確認・想起のどれにも出さない。

| 操作 | 担当 |
| --- | --- |
| 追加 | 依頼を受け付けた時点で実行台帳に登録される。サブエージェントの内部の手順は、サブエージェント自身の文脈と実行台帳の子の記録で扱い、`state.todos`には載せない |
| `waiting`・`done` | 実行台帳の状態の遷移による（サブエージェントの質問・終了、取消） |
| 応答のない・期限切れ・取消の仕事を失敗にする | host |
| `archived` | 会話エージェントだけ。確定の条件は§9.4 |

会話エージェントと記憶担当は、TODOの追加や`done`への変更をしない。会話上の発言から完了を推測しない。

### 10.2 記憶担当が更新する項目

- `decisions`（決定事項）・`askedUser`（会話エージェントが利用者に尋ねて答えを待っていること。実行前の確認とTODOの`waiting`の質問は除く。現行コードの`openQuestions`（操作担当の質問）とは別のもの）・`goals`（目標）を、新しい出来事を処理するたびに、構造化した操作（追加・更新・完了）で更新する。自由文で書き換えない。
- 実行前の確認（`pendingConfirmation`）はhostが発行・管理する（§6.7）。記憶担当は書かない。
- 各項目にID、元の出来事のID、参照ID、更新日時を付ける。完了・取下げた項目は外す。
- 仕事の進行は書かない（正本は実行台帳）。

### 10.3 その他

- `retained`は最近使ったtoolchain（§6.2）。
- `newMemories`と`notes`は、memoryが短期層から作る。

## 11. 記録と保持

### 11.1 凍結

- 窓に入れた出来事・`active`の枠は、追加時に描画済みのJSON文字列とtoken数を保存し、再構成まで同じ文字列を使う。台帳から毎回描き直さない。
- 窓の組立ては、窓の版が指す凍結した文字列を順に並べるだけにする。窓の版が同じなら出力は同じ文字列になる。
- 凍結した文字列は、`log`から外れたら消す。以後は台帳から読む。

### 11.2 保持するデータ

| データ | 内容 | 保存先 | 寿命 |
| --- | --- | --- | --- |
| 窓の出来事（現行の`memory_exchange`を置き換える） | 会話ID、連番、時刻、種類、元の参照（発言・run・TODOのID）、凍結した文字列とtoken数（記憶の読取りは縮めた形も）、表示中の形、`episode`への統合の準備状態、忘却の印 | `continuity` | `log`にある間。外れたら文字列を消し、参照と統合済みの印だけを残す |
| `active`の枠 | TODOのID、入った時刻、凍結した文字列とtoken数 | `continuity` | 上書き、アーカイブで削除 |
| `episode`（現行の`memory_conversation_summary`を移す） | 表示中の版と準備済みの版、それぞれが統合した出来事の範囲と時間の範囲 | `continuity` | 表示中と準備中の二つだけ |
| 短期メモ（決定事項・利用者への問い・一時的な例外） | 現行の短期メモ | `continuity` | 完了・取下げ・期限で削除 |
| 窓の版（現行の`memory_context_window`を移す） | 版番号、`profile`と`episode`の版、`log`の範囲、各出来事の形、最後の再構成の時刻と理由、生成ごとに見た最後の出来事 | `continuity` | 最新と、実行中の生成が参照する版だけ |
| 長期記憶と`profile`の公開版 | State・傾向・反映待ち、`profile`として公開した版 | `memory` | 現行どおり |
| 実行前の確認 | ID、toolchainのID、依頼文と入力、影響、期限、確認文の出来事ID、使用済みの印 | dialogue（現行の未回答の質問を拡張） | 使用または期限切れまで |

現行の往復（exchange）の管理と処分（`keep`・`summarize`・`drop`）は廃止する。

### 11.3 書き込み

各domainの既存の処理の単一writerのtransactionの中で、保存先のdomain（アクティブな短期記憶は`continuity`、長期記憶は`memory`）の公開操作を呼ぶ。保存先は上位のdomainを参照せず、内容は呼び出す側が渡す。

| 出来事 | 書き込み | 呼び出す側 |
| --- | --- | --- |
| 利用者の発言を受け付けた | `said`（user、未処理） | conversationの受付処理 |
| エージェントの発話を確定した | `said`（agent・specialist） | dialogueの採用処理、Agencyの発話の受領処理、専門担当の採用処理 |
| 発言の配信が終わった | `delivered`。アーカイブの確定（§9.4）・予告の後の委譲の確定（§6.5） | deliveryの配信処理 |
| エージェントが行動した | `acted`（§8.2の二重実行の防止） | dialogueの行動の確定処理 |
| 実行前の確認を発行・使用した | `pendingConfirmation`の追加・使用済み | dialogueの採用処理 |
| 利用者の発言を処理した | 処理済みの印、`said`（user）を`log`へ | dialogueの採用処理・行動の確定処理 |
| TODOが`done`・`waiting`になった | `active`の枠の上書き | 実行台帳の状態の遷移 |
| TODOを確認した | `acted`と`active`の枠の上書き | dialogueの採用処理 |
| TODOのアーカイブを要求した・確定した | `acted`（要求・確定・未確定）、確定時に`active`の枠の削除と実行台帳のアーカイブの印 | dialogueの行動の確定処理、deliveryの配信処理（§9.4） |
| 通知を提示した | `notice` | 通知の提示処理 |
| 準備した | `episode`・短期メモの準備済みの版（`continuity`）、`profile`の統合の準備済みの版（`memory`） | steward |
| 再構成 | 新しい窓の版、外れた出来事の文字列の削除、形の切替え | `continuity`（`profile`の再公開は`memory`） |
| 忘却・撤回 | 長期記憶の項目の削除（`memory`）、対象を含む凍結した文字列の消去と置換え・窓の版の更新（`memory`の忘却処理が`continuity`の公開操作を呼ぶ） | `memory`の忘却処理 |

## 12. キャッシュと再構成

### 12.1 書換えの時期

| 区画 | 書き換えてよいとき | 書き換えたときに読み直す範囲 |
| --- | --- | --- |
| 最後のmessage・`work`・`now`・`state` | 毎回 | 末尾だけ |
| `active` | 確認・アーカイブのとき | `active`から後ろ |
| `log` | 普段は末尾への追加だけ。途中の書換えは再構成のときだけ | 書き換えた位置から後ろ |
| `episode` | 再構成のときだけ | `episode`から後ろ |
| `profile` | 再構成のとき、または即時の変更 | `profile`から後ろ |
| system・tool定義 | 設定・指示の変更時だけ | 全部 |

cacheの区切りは、system末尾・`profile`末尾・`episode`末尾・`log`末尾・`active`末尾に置く。

### 12.2 準備と再構成

- **準備**（LLMを使う）: `episode`へ移す出来事の要約、長期記憶の統合、`state`の統合。新しい出来事の後に記憶担当が背景で作り、未適用の版として保存する。前景の処理（発言の生成・ASR・TTS）の間は止め、利用者が話し始めたら中断する。元の版・revisionが変わっていたら作り直す。
- **再構成**（LLMを使わない）: 準備済みの版と§8.4の規則をまとめて反映し、新しい窓の版を公開する。保留中の書換えを一度にまとめる。
- 生成は準備の完了を待たない。準備ができていない分は原文のまま残す。
- 制約が両立しないときの優先順は、(1) 出力予約と計画窓、(2) 区画の上限、(3) 要約の完成、(4) キャッシュの維持、とする。上限を超えそうで準備がない場合は§8.3の未要約の印を使う。
- 準備は前景の処理がない間なら実行してよい（長い沈黙を待たない）。利用者が話し始めたら中断し、次の空いた間に続きから行う。

### 12.3 起動条件

| 理由 | 条件 | タイミング |
| --- | --- | --- |
| キャッシュが既に失われた | 最後の要求から接続の無操作解放の目安（初期値6分）を超えた。接続の再確保、backend再起動、モデル・設定の変更。直前の生成で、キャッシュ再利用の割合が見込みより大きく低かった（他の要求によるKVの上書き。§22）。割合は同じ尺度どうしで比べる: 実際の割合はProviderの正式計数どうし（`providerCachedTokens` ÷ その要求の正式入力数）、見込みの割合はhostの推定どうし（前回と共通の先頭の推定量 ÷ その要求の推定入力量）。実際の割合が見込みの割合の半分（初期値）を下回ったら失われたとみなす。Providerがキャッシュ再利用量を返さない場合は、この条件を使わない | 次の生成の準備時。保留中の書換えをすべて適用する |
| 会話の再開 | §8.3の会話の再開 | 同上 |
| `log`の量 | `L_hi`を超えた | 沈黙の待機中 |
| 入力の目標超過 | 区画の合計が入力の目標値を超えた | 沈黙の待機中 |
| 区画の上限超過 | いずれかの区画が上限を超えそう（追記で超える） | 沈黙の待機中。間に合わなければ次の生成の準備時に、準備済みの範囲と規則だけで適用する（LLMを待たない） |
| 即時の変更 | §13 | 即時。保留中の書換えも一緒に適用する |

- 沈黙の待機中とは、発言の配信が終わり、新しい出来事がない状態が沈黙の待機の基準時間（初期値10秒、§20）続いたことをいう。Agencyの沈黙後の判断を妨げない順序にする。
- 先読み（§15）が使えない間は、`log`の量・入力の目標超過による再構成は、区画の上限を守る範囲で、キャッシュが失われる機会まで保留してよい。

### 12.4 期待される動き（推定。段階Aで実測する）

`active`は`log`の後ろにあるため、`log`に追記するたびに`active`も読み直す。`active`は確認した仕事の結果だけで、普段は数百〜千数百tokenである。`log`の前に置くと、確認のたびに`log`全体（最大16,000）を読み直すことになるため、後ろに置く。

| 場面 | 読み直す範囲 |
| --- | --- |
| 普段の生成 | 前回以降に増えた出来事、`active`の全体、`state`・`now`・`work`・最後のmessage（`active`と`work`を除いて約1,000〜3,000） |
| 再構成の後 | `episode`から後ろ（上限の合計で最大27,000＋`state`・`now`の外の部分） |
| 長期記憶の再公開の後 | `profile`から後ろ（上限の合計で最大39,000） |
| キャッシュが失われた後の最初の生成 | 全部（普段は約20,000〜30,000） |

## 13. 忘却・即時の変更

- 忘却・撤回: 対象を含む出来事・`active`の枠・`episode`・`state`の項目・記憶ツールの結果を、即時に表示しない。長期記憶（`memory`）とアクティブな短期記憶（`continuity`）の両方に届かせる。凍結した文字列も消去し、本文のない置換えに作り直す。`episode`が忘却対象に依存する場合は空にし、記憶担当が作り直す。
- 会話メッセージの訂正（書き起こしの修正など）: そのメッセージを示した`said`の凍結した文字列を、訂正後の本文（1件の上限、§8.3）に作り直し、窓の版を進める。`acted`など、エージェント自身の行動の記録は書き換えない。`episode`の要約がそのメッセージに依存する場合は、未要約の印にする。`log`から外れた出来事は本文を持たないので対象外。
- 長期記憶の訂正、権限・設定の変更、有効期間の境界: `immediateSeq`・`policyRevision`・`boundaryCrossed`による再描画を行う。
- 実行中の生成は採用検査で不採用にする。採用検査は、窓に表示した`episode`の版で判定する。表示していない要約の更新では不採用にしない。
- 不採用の時点で既に確定した行動（§8.2）は取り消さない。行動は確定時に自分の失効検査（§6.7）を通っている。不採用になった生成の発話は捨て、きっかけ「前回の生成が採用されなかった」（§8.2）で新しい生成を始める。新しい生成は、`log`の`acted`と`state.todos`から行動済みであることを知り、改めて話す。
- 記憶の訂正・忘却を利用者が会話で頼んだ場合、会話エージェントは記憶ツールの依頼（`forget`・`correct`）で記憶担当の依頼キューへ入れる（現行の`memory_request`と同じ）。記憶担当がそれを適用した時点で、上の即時の変更が起きる。
- 記憶への依頼は、行動として確定した時点で記憶担当の依頼キューに入る（§8.2）。**生成の取消（割込み・失敗・不採用・利用者による発話の停止）では、確定済みの記憶への依頼を破棄しない。** 発話を止めることと、依頼を取り消すことは別である。
- 利用者が依頼そのものを取り消した場合（「やっぱり忘れないで」）は、新しい発言として扱い、会話エージェントが記憶ツールの依頼で取下げを入れる。記憶担当は、まだ適用していない依頼を取り下げる。適用済みの忘却は戻さない（忘れた内容は復元できない）。
- 行動として確定する前に生成が止まった場合は、依頼は入らず、発言は未処理のまま残る（§8.2）。現行の「生成が取り消されたら`forget`・`correct`を破棄する」扱いは廃止する（§17）。
- キャッシュを守るために、訂正前の記憶や忘却対象を残さない。

## 14. 想起

- **記憶ツール**: 会話エージェントの基本ツール。hostが同じ要求の中で直接実行する。
  - 返す: 現在有効な長期記憶・傾向・反映待ちの項目（ID・revision・種類・更新日時・有効期間付き）。`profile`にある項目は本文を繰り返さない。アクティブな短期記憶は返さない（すでに窓にある）。
  - 返さない: 忘却・撤回・期限切れ・blockedの項目、旧revision、設定・認証情報、Agencyの内部メモ。
  - 読んだことは`acted`として`log`に残る。組立てのたびに有効性を検査し、忘却・訂正された項目の本文は表示しない。
  - 読んだだけで記憶を追加・強化・並べ替えしない。memoryが不健全、または記憶が無効のときは渡さない。
- **会話履歴**: 複数の利用者は当面想定しない。既存の会話履歴の担当（`history.search`/`history.read`）の検索範囲を全会話とする。結果は元の会話ID・日時付き。
- **自動想起**（`turn-recall`）: 現行どおり`now.recall`に置く。
- 想起の結果は資料（A5）として示す。見つからない場合に「保存されていない」と断定しない。運用ログに本文を出さない。

## 15. 先読み

- 会話を開いた時点と再構成の直後に、`state`の直前までを準備する。
- 生成時は同じ先頭と最新の末尾から通常の要求を作り、KVが残っている前提で本文を省かない。
- 先読み中の発言・会話の変更・失効では対話を優先し、古い先読みを採用しない。利用者が使っている会話のKVを追い出さない。ダミーの出来事を追加しない。
- 無出力のprefill・保持期限・取消・解放の操作はLARM側の契約が必要であり、契約が確定するまで先読みは実装しない（§19）。

## 16. Agency

- 会話エージェントは agency（eumenes-agency）である。利用者の発言への返答（`runRespond`）、自発発話（発話後・沈黙後の`decide`）、TODOの報告はすべて agency が行う（[設計](agency-conversation-agent-design-2026-10-25.md)）。agency は常に動き、ON/OFFの設定はない。推論はすべて Eumenes に設定された会話のLLMで行う。
- 返答の system の先頭は agency の`respondSystem`（自然な会話の基本・人格・音声の文体・感情・ツールの使い方。設定で決まる）。agency の変わる状態（意図・候補・関心の要約）は`now.agency`に置く。
- Agencyの自発的な発言は`log`の出来事（`said`、`origin: spontaneous`）にする（§8.2）。
- 本人の記憶と、エージェント自身の関心を混ぜない。Agencyの内部メモは記憶ツールで返さない。

## 21. 検証

### 21.1 部分（fixture）

- tool定義が全段階・全生成で同じで、推定2,000以下。
- ネイティブのuser messageは新しい発言か固定文だけ。過去の発言はすべて資料のJSON文書の中にある。資料がsystem roleに入らない。
- 同じ窓の版で同じ文字列。日本語が`\uXXXX`にならない。`<`・`>`・`&`・行区切り文字がエスケープされる。
- 出来事が時刻順に並び、自発的な発言・連続した発言・割込み（`heard: partial`と届いた部分）が同じ流れに入る。
- 再構成の間は、前回の文字列が`log`の末尾まで次の生成の先頭にそのまま含まれる。
- `L_hi`を超えた後の再構成で、沈黙の区切りで`L_lo`まで移る。会話の再開で沈黙より前が移り、直前`L_keep`が残る。`R`が最小値の窓でも`L_lo`まで減らした後は`log`の上限内に収まる。準備が済むまで原文が残る。準備中に利用者が話すと準備が中断し、生成は待たない。
- キャッシュ失効の条件の後の最初の生成で、保留中の書換えがまとめて適用される。
- 作業領域の最低と出力予約が、同じ生成の中でtool結果が増えても守られる。区画の余りは作業領域へ回る。
- 出来事に残すもの・残さないもの（§8.1）のとおりになる。外れた出来事の凍結した文字列が消える。忘却で凍結した文字列が消去される。
- 担当の検索で合う候補がなければ依頼しない。検索結果・`state.retained`にないIDへの依頼をhostが拒否する。
- TODO: 受付で`todo`、サブエージェントが`waiting`・`done`にする、期限切れ・取消はhostが失敗にする。会話エージェントは`archived`にすることだけができる。`archived`は一覧・確認・想起に出ない。
- 仕事の結果: 600を超える結果は受け付けられない。確認の結果は`active`の枠にだけあり、再確認で上書き、アーカイブで削除される。TODOの変化のきっかけに中身が入らない。
- 忘却・訂正が即時に反映される。表示していない要約の更新で不採用にならない。
- 記憶ツール: 外れた項目を取り出せる。忘却済み・旧revisionが返らない。読んだだけで記憶が変わらない。
- `episode`の上限: `episode`が既に上限に達した状態から未要約の範囲を追加しても、記憶担当を止めたまま、§8.3の規則で上限内に収まる。`summary`と`unsummarized`が交互に並ぶ場合も収まる。
- 根拠のない回答の検査は廃止した（§6.3、2026-10-25）。
- 記憶への依頼: 確定した後に生成を取り消しても依頼はキューに残る。確定前に止まった場合は依頼が入らず、発言は未処理に戻る。
- キャッシュ喪失の判定: 推定と正式計数の尺度が大きく違っても（推定約14,000・正式2,682のような場合）、全量を再利用できていれば失効とみなさない。
- 上限と準備: 記憶担当を止めた状態・連続した発言で準備が進まない状態で`log`が上限を超えそうになると、未要約の印を置いて上限内に収まる。範囲の一部だけ要約できた場合は`summary`と`unsummarized`に分かれる。後で準備ができると印が要約に置き換わる。区画の上限・出力予約は破られない。
- 未処理の発言: 生成を採用前に取り消す・失敗させる・新しい発言で打ち切ると、その発言は次の生成でA2に残り、`log`には入らない。依頼を確定した後に生成が失敗しても、同じ依頼は二度実行されず、次の生成で行動済みが分かる。予告の前に止まった依頼は確定しない。
- アーカイブ: agency の発話が引用した`done`も、通常返答が伝えたと照合された`done`も、音声が最後まで再生されたときに`archived`になる。文字の保存・表示、`partial`・`none`・不採用では確定しない（§9.4、2026-10-27変更）。
- 実行前の確認: `confirm`で実行されない。確認の参照のない`approve`、期限切れ・使用済みの確認、確認文の配信開始より前の承認、`none`で届かなかった確認文への承認は実行されない。実行直前に記憶の忘却・権限失効があれば実行されない。
- TODOの操作: `state.todos`の版と質問IDで確認・回答でき、古い版の操作は拒否される。
- 予算式: 新しい発言・添付・tool呼出しの引数・tool結果を`W`に数え、`F + S_used + 作業領域の使用量 + O ≤ C`が常に成り立つ。`W_min`を超えて作業領域を使える。区画の上限は`min(割合 × R, 絶対上限)`。`R`が最小値に満たない接続は使われない。`state.todos`は落ちない。
- 配信結果: 発言は確定時に`said`、配信の終了時に`delivered`として追記され、凍結した文字列は書き換わらない。句の一部だけ再生されたら`partial`と届いた部分、1句も再生されなければ`none`。配信中は`now.speaking`に出る。
- `log`の順: 後から処理済みになった発言が追記順の位置に入り、`at`は実時刻のまま。同じtransactionでは発言→`acted`→`said`の順。
- 二重実行の防止: 構造の修正・生成のやり直しで、同じ発言に対する同じ依頼が二度確定しない。修正の呼出しに確定済みの行動が引き継がれる。予告が再配信されない。
- 層の分離: `memory`にアクティブな短期記憶のデータが入らず、`continuity`に長期記憶が入らない。記憶ツールは長期記憶だけを返す。長期記憶の忘却が`continuity`の出来事・経緯・仕事の結果にも届く。
- 仕事の結果: TODOが`done`になると確認しなくても`active`に入り、`waiting`では質問が入る。
- 日付: 日付・時刻そのものを聞かれたら`now.at`で答え、委譲しない。
- 承認: `approve`は確認に保存した依頼をそのまま実行し、LLMが依頼文を再入力しない。`minImpact`が`modify_existing`のtoolchainは、申告が`none`でも確認が要る。`irreversible`は確認文が`full`で届いた後だけ承認できる。
- 予告: 即答できるtoolchainは予告なしで答える。予告が`partial`なら委譲し、`none`なら委譲しない。
- 不採用: 行動の確定後に生成が不採用になっても行動は取り消されず、新しい生成が始まり、二重に依頼しない。
- 専門担当: 切替中の発言は専門担当へ渡した時点で処理済みになり、会話エージェントのA2に入らない。sessionが終わった後の発言は会話エージェントへ届く。
- TODO: `ExecutionStatus`の各状態が対応表のとおりに投影される。版が古い操作は最新の状態と版を返す。

## 23. 決定の記録

2026-10-24、利用者との検討で次を決めた。

- 文脈をJSONで構造化する。ネイティブのuser messageは新しい発言（なければhostの固定文）だけにする。
- 会話をターンで扱わず、出来事の流れにする。会話エージェントは自発的にも話す。
- 計画窓をモデルの窓の80%（256kなら約200k）とし、作業領域と出力（思考込み）を先に確保する。

- 会話メッセージの訂正は`log`の凍結した文字列まで届かせる（G5、§13）。
- 発話の上限を300字（2文は維持）とする。160字では足りない場合がある。これに合わせ、`log`の目安を`L_hi = min(10,000, L_cap)`・`L_keep = min(4,000, L_lo)`に引き上げた（§6.4・§8.3）。
