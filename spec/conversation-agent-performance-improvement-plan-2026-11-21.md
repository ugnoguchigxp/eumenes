# 会話エージェントの性能改善計画

2026-11-21 合意。会話を受け付けてから最初の本文が出るまでを短くし、背景処理が消費する入力トークンを減らす。ユーザーの訂正、忘却、確認、委任が正しく扱われることを採用条件にする。

最初の実装候補は、既存の計測から同条件の比較を作ることと、Codex の `append` が直前の応答を取り違える不具合の修正。入力キャッシュの再利用率はすでに高いため、速度の改善は毎回供給する入力の量と、本文が出るまでの直列呼び出しを中心に検証する。

計測準備と Codex の追記の固定試験を実施した。[初回の検証記録](verification/conversation-agent-performance-first-stage-2026-11-21.md)

## 基準値と採用条件

11月21日 08:17〜08:29 JST の運用記録。Codex SDK を使った音声会話の完了12件、回答生成13回、回答以外の成功87回を集計した。再現用の基準は工程0で作る。時刻の起点はサーバー受付、音声は先頭データの準備時点。[計数方法](../docs/usage.md) · [既存の性能予算](../docs/performance.md)

| 観測項目 | 運用記録 |
| --- | ---: |
| 受付から最初の本文までの中央値 | 6.96秒 |
| 受付から最初の音声データまでの中央値 | 7.63秒 |
| Router の判断 / 回答試行開始から最初の本文までの中央値 | 1.14秒 / 5.29秒 |
| 回答生成の入力中央値 / 保存済み `contextWindow` | 15,850 / 272,000トークン |
| 回答生成のキャッシュ読取 | 153,088 / 206,010トークン（74.3%）。`reset` は11回すべてヒット |
| 回答以外の未キャッシュ入力 | 637,474トークン。集計対象の未キャッシュ入力の92% |

比較の目標案は、ウォーム状態の通常会話で受付から最初の本文までの p50 を25%、p90 を15%短縮し、同じ発話・待機・作業の流れで背景の未キャッシュ入力を30%削減すること。いずれも工程0の基準に対する相対値とする。完了時間、初回音声、失敗・取消、呼び出し数、入力総量も併記する。

キャッシュは既存の live 受入条件を使う。同じ会話で2分以内に5発話し、2回目以降の呼び出しの8割以上で入力の6割以上がキャッシュ読取になること、ツール後の呼び出しでそのターンの1回目の入力の9割以上が読取になることを確認する。消費はキャッシュ率に加え、キャッシュされなかったトークンの総数で判定する。[既存の live 受入条件](codex-input-cache-structure-2026-11-12.md#6-検証)

## 工程0　復旧条件と計測を確定する

1. 08:35 JST の終了後に生じた `migration_unknown_applied:dialogue/0040-specialist-parked` は運用復旧として扱う。既存ログと起動に使われる成果物の migration 登録を照合し、適用済みの migration を認識する版を特定する。サーバー操作は明示許可を得た時点で行う。live の着手条件は `server.ready`、公開 API の読み取り成功、保存済み接続経路の確認。[起動と復元の規則](../docs/operations.md#バックアップからの復元)
2. `runId` で `dialogue.accepted`、`dialogue.router_selection`、`dialogue.first_delta`、音声の準備をつなぎ、`jobId` で `queue.settled` を照合する。`attemptId` で採用した推論、利用状況、`new`・`reset`・`append` を照合する。回答生成と背景処理の呼び出し数を数える。計測に不足があれば、Router の直接呼び出しの回数・使用量と、入力区画ごとの概算・経路が報告する実測を既存の診断口に追加する。ログに保存するのは数値、固定の分類、相関ID。計数が報告されない場合は欠測を明示する。[運用ログ](../docs/logging.md) · [入力の観測範囲](context-window-inspector-design-2026-11-17.md#32-接続経路ごとの観測境界)
3. 復旧後、稼働版と比較に使うコードのコミットを記録する。検証用会話IDと固定した開始状態を使い、変更前の結果を保存する。通常会話のウォーム比較は案ごとに有効30件を目安とし、ウォームアップ回、初回のコールド測定、ツールを使った回も記録する。モデル・経路・音声条件を揃え、基準と候補を交互に測る。正式な比較の分母は固定条件の測定で確定する。[CLI の再現手順](../docs/cli-chat.md#aiによる再現デバッグ)
4. 標準 `verify` の既存停止箇所は `createCodexProcesses` の336行超過。検証再開に必要なら、これを独立した差分で責務ごとに整理し、常駐・再利用・取消・終了の現在の試験を通す。判定は現行の300行上限で行う。[対象関数](../api/domains/inference/adapters/codex-transport.ts)

完了条件は、同じIDでターン時間、各モデル呼び出し、採用結果と利用量を再集計でき、欠測箇所を説明できること。復旧待ちの間も、工程1の固定試験と評価データの準備は進められる。

## 工程1　Codex の追記を正しく結び付ける

- `inference` の既存スレッドプールで `append` の条件を詰める。本文の先頭一致に加え、同一の会話と推論要求の続きで、直前の試行が返した回答・ツール選択に対応することを条件にする。照合には既存の実行IDと呼び出しの対応を使う。対応を確認できない場合は既存の `reset` または `new` で、その回の入力を渡す。[スレッド選択の実装](../api/domains/inference/adapters/codex-threads.ts)
- 固定試験は、同一実行の正しいツール後続で `append`、先頭が同じで直前の回答が異なる場合や別会話では `reset` または `new`、取消・訂正・忘却後の古い内容の再採用が0件、を確認する。送信した差分と診断が示す持ち越し範囲も照合する。[既存の追記試験](../api/domains/inference/test/codex-threads.test.ts) · [忘却の結合試験](../api/application/agency/forgotten-context.test.ts)

完了条件は、再現済みの取り違えを修正し、同じターンのツール結果が正しく続き、工程0の基準と比べて通常会話のキャッシュ読取が既存の受入条件を満たすこと。固定試験の合否は復旧前に確定できる。

## 工程2　初回応答までの待ちを減らす

1. Codex に渡る入力のうち、11件で共通だった指示とツール定義が約10,695、毎回変わる Agency の状態が中央値約2,294トークン相当だった。最初の候補は、同じ規則を記す指示とツール説明の重複を整理し、Agency の状態から会話で使われる情報を既存の読み取り口で参照できるようにすること。現在の話題・保留中の事項と出典を利用できる条件を先に固定し、区画を一つずつ変えて比較する。[SystemContext の組み立て](../api/domains/dialogue/service/context-system.ts) · [Agency の状態挿入](../api/application/agency/always-on-ports.ts)
2. Router の所要を構造判断・候補照会・回答試行に分け、通常会話と、確認・取消・複数依頼を含む回を比較する。判断方式の候補は既存の `routeWithSelection` とホスト側の実行契約から組み立て、選択方式を変える場合は採択根拠を設計に記載して合意を得る。[Router の現行方式](router-package-integration-2026-11-04.md#2026-11-14-選択方式への切替)
3. 会話の思考量は既存の `high` を比較の基準にする。代替を試す場合は検証用の実行で同じ入力とツールを与える。`low`・`medium` で記憶ツールを選ばなかった過去の実測を踏まえ、速度改善とツール選択の品質を同時に採点する。採用する値と適用条件は結果を添えて合意を得る。[思考量の検証記録](memory-integration-2026-11-05.md)

完了条件は、同条件の比較で初回本文の p50・p90 の目標を満たし、記憶の読み取り、後続の訂正、確認・取消、複数依頼の判断、ツール実行前の予告が既存の品質基準を満たすこと。

## 工程3　Agency と記憶担当の入力消費を減らす

1. 同じ集計時間帯の Agency 52回、記憶担当32回を、起動理由、処理対象の版、処理の役割、採用の有無で照合する。各担当の既存のキューと採用記録から、同じ状態に対して重なった呼び出しと、新しい入力があった呼び出しを識別する。[Agency の運用記録](../api/application/agency/always-on-cycle.ts) · [記憶担当の準備](../api/domains/steward/service/unit-prepare.ts)
2. 実測で重複した処理から、既存の待機・再開・版照合を使ってまとめる。重複が少ない工程では、変化した資料と必要な参照を担当に渡し、入力を縮める案を比較する。記憶の更新や話題の判断は既存の LLM に委ねる。期限のある仕事、訂正・忘却、回答中の取消は既存の権限と採用処理で検証する。

完了条件は、同じ発話・待機・作業の流れで背景の未キャッシュ入力が目標まで減り、必要な作業・記憶更新が一度ずつ採用され、明示された訂正・忘却が後続の応答に正しく反映されること。

## 工程4　長い入力に対する ContextWindow の契約を揃える

- 工程0の計数と工程1の継続条件に基づく。送信前に、経路が宣言する容量、設定上の出力予約、実際に送るメッセージ・ツール・構造化出力・添付の内訳を既存の予算計算と照合する。LARM では同じボディの正式計数、Codex では SDK に渡る入力の推定と SDK が報告する利用量・利用可能な容量を根拠とする。送信APIに出力上限を指定できる場合はその値を確認し、経路の制約で指定できない場合は見積もりの予約量として記録する。[クラウドの予算処理](../api/domains/inference/service/cloud.ts) · [LARM の送信境界](../api/domains/larm/service/answer-request.ts) · [Codex の送信パラメーター](../api/domains/inference/adapters/codex-app-server.ts)
- 上限に近づいた回で保護する対象は、現在の依頼、訂正と権限に関わる指示、進行中の操作に必要な参照。どの履歴・資料を落とせるかは出所と用途を確認して設計で決め、既存の ContextWindow の区切り・読取の機構を使う。超過時の動作は、保護対象を保持した送信か、既存の超過エラーで明示する案を経路ごとに決める。[会話の入力仕様](conversation-input-spec-2026-10-26.md)

完了条件は、長い日本語入力・添付・大きなツール結果・小さいモデル窓を含む fixture で、予算と送信結果が対応し、保護対象と出典が追跡できること。工程2・3の速度・消費の評価とは独立に着手できる。
