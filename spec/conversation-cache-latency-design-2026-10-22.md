# 会話の応答時間とキャッシュの設計（2026-10-22）

状態: **案・合意待ち。** 計測（§2）は実施済み。§4 の変更はどれも未実装。LARM の prompt キャッシュが直った後（[修正依頼](larm-prompt-cache-request-prompt-2026-10-22.md)）を前提にする。

関連: [ContextWindow 設計](conversation-context-window-design-2026-10-17.md)（原則・区画 S/P/H/W/V/R・C1〜C3 実装済み）、[2段の初期判断](conversation-two-round-initial-analysis-design-2026-10-17.md)（R1/R2、H1・H2）、[Agency 統合スパイク](agency-integration-spike-design-2026-10-22.md)。

## 1. 目的

音声で雑談が成り立つ応答時間にする。目安は、挨拶・相づちの最初の音声まで 3 秒以内、通常の質問で 5 秒以内（今は挨拶 1 回に 11〜20 秒）。そのために、LARM の KV prefix 再利用が効く呼出しの形にそろえる。判断の質を落とさないことを、live の比較で確かめる。

## 2. 計測（2026-10-22、保存済み LARM 接続、プロセス内の隔離ホスト、サーバー起動なし）

### 2.1 LARM

| 項目 | 値 |
| --- | --- |
| 入力の読込み（prefill） | 約 1.0〜1.2 ms/token（約 800〜1,000 token/s） |
| 出力 | 約 71 token/s |
| 同じ接続・同じ要求を 2 回 | 2 回とも `cache_n` 0、`prompt_n` 3040。`cache_prompt: true` を明示しても同じ |
| 本番の呼出し | すべて `cached_tokens` 0。1 呼出し 3,000〜5,500 token、返答段は 75KB・最初の token まで 22 秒の例あり |
| 文字と token の比 | 会話の入力でおよそ 2.3 文字/token |

### 2.2 1ターンの呼出しと共通先頭

雑談 5 往復と「計算依頼 → こんばんは」の軌跡で、関数定義＋メッセージ列を比べた。

| 比較 | 共通先頭 / 長さ（文字） | 理由 |
| --- | --- | --- |
| 返答段 → 次のターンの返答段 | 5,051〜5,289 / 5,400〜5,700（93〜97%） | 原則（S 不変・履歴は末尾に追加）が効いている |
| R1 → 次のターンの R1 | 3,749 / 5,500〜6,100（約 65%） | 関数定義と役割文までは同じ。直前の1往復から先が変わる |
| R1 → 次のターンの R1（初回・失敗の直後） | 941 | 承認の参照元がない回は `approved` の schema が `const:false` に変わる（`initial-decision.ts` の安全上の制約） |
| R1 → R2（担当選び） | 40 | 関数定義が違い、メッセージ列も別物 |
| R1 → 返答段 | 0〜1 | 別のメッセージ列。R1 は役割文だけ、返答段は S P H W |
| 修正（repair）の回 | 32〜40 | 修正指示を system の先頭に足すため全体が不一致（ContextWindow 設計 §2.3 で既知） |

### 2.3 session と接続

- R1・R2 は `sessionRole: "auxiliary"` で、呼出しのたびに新しい LARM 接続（client `eumenes-helper-<uuid>`）を作り、終わると解放する（`larm/service/index.ts:154-180`）。KV は接続ごとなので、LARM が直っても R1・R2 は再利用できない。接続の作成と ready の確認で 1 呼出しあたり約 0.25 秒、正式な token 計数で約 0.05 秒かかる。
- 返答段は `main` の接続で、ターンをまたいで同じ接続を使う。

### 2.4 失敗と修正の頻度（ローカル LLM）

| 事象 | 観測 |
| --- | --- |
| R1 が関数を呼ばず本文を書く（`analysis_call_required`） | 挨拶で 1/3〜1/2。修正の回は上のとおり全体が不一致になり、さらに約 6 秒 |
| 回答のない依頼が直前にあると、修正の回でそれを再実行する | プロンプト調整（2026-10-22）で 0/3 → 3/6 まで改善、根治していない |
| 返答段の `spoken_reply_too_long` が 2 回続いて run が失敗 | 「温かい飲み物でおすすめはある？」で発生 |
| LARM に `tool_choice: "required"` を送る | 8 回中 6 回、本文を書いたまま止まらず約 66 秒で `chat_stream_too_large`。R1 に入れる試験は取り消した。**既存の `completion-check.ts:268` と `trial-selection.ts:43` も LARM に required を送っており、同じ暴走が起きうる** |

計測スクリプトは scratchpad（揮発）にあり、本書の数値が正。

## 3. 現状の 1 ターン（挨拶の例）

```
R1   aux 新規接続 0.25s + 計数 + prefill 2.4k token ≈ 2.4s + 出力 ≈ 1.2s   （失敗時は修正でもう 1 回）
返答 main       計数 + prefill 2.4〜5k token ≈ 2.5〜6s + 出力 ≈ 1s
```

## 4. 提案

### P1 判断用の持続 session（R1・R2）

`sessionRole` に `decision` を足す。会話ごとではなく backend に 1 本、R1・R2 を順番に流す接続とし、ターンをまたいで同じ client 識別子を使う（`main` と同じ扱いで、解放は終了時と失効時）。completion-check と trial-selection も同じ session に載せるかは D1 で決める。

- 効果: 接続作成の約 0.25 秒が毎回なくなる。LARM が直れば、R1 の共通先頭（§2.2 の 65%）がキャッシュに当たる。
- 代償: LARM の同時接続を 1 本常に使う。2026-10-12 に確認した構成（主 1＋補助 3）では、補助の枠が 2 になる。

### P2 修正の材料を末尾へ（既存の原則の実装）

修正指示を system の先頭に足すのをやめ、`UNTRUSTED_REJECTED_OUTPUT` と同じく今回の依頼の直前に置く。R1・R2・返答段の共通処理（`conversation-generation.ts`）で行う。ContextWindow 設計の原則 3（system は変えない）と区画 V（修復の材料）の実装。ただし同書は「V には規則を置かない」としているので、修正指示を host 規則として扱う位置づけを D2 で決める。

### P3 R1 のメッセージ列を「変わらないものが先」に

今は `[役割][背景][作業][直前の1往復][使用記録][R1の指示][今回]`。指示は「直前の返答の形にこの呼出しを引きずらせない」ため今回の依頼の直前に置いている（`request-analysis.ts`）。キャッシュのためには `[役割][R1の指示][背景][作業][直前の1往復][使用記録][今回]` が有利だが、指示が遠くなることでローカル LLM の判断が変わりうる。live で比べて決める（D3）。関数定義は、固定のもの（`find_toolchain`・`answer`・`report_unavailable`）を先に、保持中の担当を後に並べる案も同時に比べる（位置の偏りで選択が変わりうるため、比較なしには変えない）。

### P4 R1・R2 を構造化出力（json_schema）にする

LARM は control 要求で `response_format: json_schema`（strict）を受け付け、文法で出力を縛れる（`docs/larm.md`）。R1・R2 の「関数を一つ呼ぶ」を `{"function": <名前の enum>, "arguments": …}` の構造化出力にすれば、次のようになる。

- 本文だけ書く失敗（§2.4 の 1 行目）が文法上起きない。修正の回と、その回で過去の依頼を再実行する経路がなくなる。
- 関数定義が要求の先頭（chat template の tools 欄）に入らなくなり、関数の説明はメッセージ列の中に置ける。P5 の共通化ができるようになる。
- 代償: 判断の方式（native tool calling → 構造化出力）が変わる。cloud 経路（OpenAI 互換・Claude Agent SDK・Codex）の対応、`anyOf` の schema での品質、出力の長さ（`execute_task` の request は最大 8000 字）を live で確かめる必要がある。
- `tool_choice: "required"` は §2.4 のとおり使えない。

### P5 R1 と返答段の先頭を共有する（ContextWindow の拡張）

R1 を、返答段と同じ `S P H W` の後に R1 の指示と今回の依頼を付ける形にする。H2（R1 に長期記憶・履歴を渡さない、利用者指示）の見直しになる。

- 効果: キャッシュが効けば、R1 の追加読込みは R1 の指示と今回の依頼だけ（数百 token）になり、返答段も R1 と先頭を共有する。R1 が履歴を見られるので「それは？」「うん、楽しかった」のような続きや、agency の自発発言への返事を取り違えにくくなる。
- 代償: キャッシュに当たらない回（初回・memory の工程の後）は R1 の読込みが今の 2〜3 倍になる。履歴に引きずられて R1 の分類が変わる恐れがある（H2 を決めた理由）。
- 前提: P4（関数定義を先頭から外す）。P4 なしでは、関数定義が R1 と返答段で違うため共有できない。

### P6 runless の発言を履歴に入れる

agency の自発発言・計算やタイマーの通知（runless の assistant message）を、会話の逐語台帳に単独のターンとして入れ、R1 の直前の1往復と返答段の履歴に出す。2026-10-22 の「こんばんは → 計算再実行」は、計算結果の通知が履歴に入らず、回答のない依頼だけが残ったことで起きた。memory の台帳の変更を伴うので、Agency 統合スパイクの非目的（memory を改修しない）を見直す（D6）。

### P7 短い返答の 2 回目の失敗

返答段の `spoken_reply_too_long` が 2 回続くと run が失敗し、利用者には失敗が返る。選択肢は D7 に置く。新しい扱い（切り詰め・別の返答）を足すことになるので、合意なしには入れない。

### P8 計測

LARM の修正を確かめた後に、§2 と同じ軌跡で各段の `cache_n`・最初の token までの時間・判断の一致を記録する。fixture、live、実機器の結果は分けて記録する。

## 5. 見込み（LARM が直り、P1〜P3 を入れた場合の概算）

| 段 | 今 | 見込み |
| --- | --- | --- |
| R1（挨拶） | 0.25s ＋ prefill 約 2.4s ＋ 出力 約 1.2s | prefill 約 0.3〜1.0s ＋ 出力 約 1.2s |
| 返答（挨拶） | prefill 約 2.5〜6s ＋ 出力 約 1s | prefill 約 0.2s ＋ 出力 約 1s |
| 修正の回 | 全体の読み直し ＋ 約 6s | 末尾だけの読み直し ＋ 出力（P4 なら発生しない） |

挨拶 1 ターンでおよそ 11 秒 → 3〜4 秒。P4・P5 まで入れると、R1 の出力を短くできるかで決まる。ここでの数値は §2 の実測からの推定で、未検証。

## 6. 決めること（推奨つき）

| # | 事項 | 推奨 |
| --- | --- | --- |
| D1 | P1 の判断用 session を入れるか。completion-check・trial-selection も載せるか | 入れる。R1・R2 だけを載せ、ほかは今のまま |
| D2 | P2 の修正指示の位置づけ | 今回の依頼の直前に、host 規則の system メッセージとして置く（固定文だけから作り、外部由来の本文を含めない） |
| D3 | P3 の R1 の並び替え | live で今の並びと比べ、判断の一致が下がらなければ採る |
| D4 | P4 の構造化出力 | 採る方向で、まず R1 だけを live で比べる。cloud 経路は adapter で native tools に戻せる形にする |
| D5 | P5 の先頭共有（H2 の見直し） | P4 の結果を見てから決める |
| D6 | P6 の runless 発言の台帳入り | 入れる。別に memory の設計書を書いて合意を得る |
| D7 | P7 の 2 回目の失敗 | (a) 2 文・160 字で切り詰めて返す / (b) 今のまま失敗にする / (c) 長い返答を許し、読み上げだけ 2 文にする。決めるのは利用者 |
| D8 | 既存の `toolChoice: "required"`（completion-check・trial-selection） | LARM 経路では送らない調整を入れ、live で確かめる |

## 7. 対象外

- LARM 側の修正そのもの（修正依頼 Prompt で依頼）。
- memory・World の構造の変更（P6 は台帳に入れる範囲だけ）。
- 専門担当・agent-runtime の ContextWindow。
