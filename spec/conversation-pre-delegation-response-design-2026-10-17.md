# 会話AIの自力回答判断と委譲前の一時回答

作成日: 2026-10-17

状態: 2026-10-17、利用者が基本案に合意。「一部はサブエージェントと完全に入れ替わる」という補足を反映して実装済み。対象fixture検証済み。live・実機器検証は未実施。

## 1. 目的と変更範囲

会話AIは最初に、現在の依頼を手元の情報と自身の回答だけで満たせるか判断する。満たせなければ必要なツールチェーンを選び、これから行うことを短く利用者へ伝えてからサブエージェントへ依頼する。SystemContextに個別ツールの手順や定型応答を増やさない。

今回の設計対象は通常会話の初動、委譲前の一時回答、その通知と実行順序。既存の専門担当との継続対話、各担当の作業手順、権限、結果採用、保存ルールは維持する。新しいライブラリやエージェント基盤は導入しない。

ここで会話AIが確定する「使うツール」は、会話に公開されたツールチェーンの関数とする。内部の検索手段、API、具体的な引数は、既存設計どおり委譲先が判断する。内部ツールまで通常会話AIが選ぶ変更は含めない。

## 2. 現状と再利用する機構

確認した設計は[ツールチェーンの定形セット](.archived/toolchain-set-routing-design-2026-10-12.md)、[専門担当との対話編集](toolchain-specialist-dialogue-implementation-plan-2026-10-17.md)、[ツールチェーンの運用](../docs/toolchain.md)、[通知](../docs/realtime.md)。

| 現状の根拠 | 変更案 |
| --- | --- |
| `selection-trace.ts` の `prepareDecision` が回答判断より先に候補検索と関数提示を行う | 自力回答の可否を先に判断し、委譲が必要な場合に既存の候補検索を使う。会話の参照情報・記憶の準備は独立して維持する |
| `conversation-policy.context.toml` は「呼ぶときは関数呼出しだけ」を要求する | 選定した依頼と一時回答を共通の出力契約に含める |
| `conversation-generation.ts` は関数呼出しに付いた前置きを破棄する | 任意の前置きをそのまま表示せず、選定と一体で検査した一時回答を採用する |
| `generation-handler.ts` は自然文のみの出力を `reviewConversationAnswer` で再判定する | 初段の明示的な判断を使い、旧経路の意味的な再判定を重ねない。構造不正の修復は既存の上限を再利用する |
| `generation-operation.ts` は採用検査後、各担当のjob・task・sessionを開始する | 共通の通知段階を通った依頼だけを既存の委譲処理へ渡す |
| `progress.ts` は未確定の本文と完了回答を扱い、委譲時には途中本文が消える | 一時回答を最終回答とは別の採用済み通知として扱い、既存SSEとAPIへ接続する |

共通契約の拡張が必要な根拠は、現在の関数引数と通知契約に一時回答の居場所がなく、実装が前置きを明示的に破棄していること。プロンプトだけを変えても順序・再接続・取消を保証できない。

## 3. 提案する流れ

1. **自力回答の可否を判断する。** 現在の依頼と必要な会話情報を受けたLLMが「直接回答」「必要な確認」「ツールチェーンが必要」を選ぶ。直接回答・確認の場合は、その応答も同じ推論で生成する。推論過程は利用者へ表示しない。
2. **必要なツールチェーンを確定する。** 委譲が必要な場合だけ既存の候補検索を行い、登録定義から生成した関数を提示する。LLMが一つ選び、担当へ渡す依頼と短い一時回答を同じ推論で生成する。
3. **一時回答を採用して通知する。** hostが選定した関数、版、依頼、通知の形、取消・権限・参照情報の有効性を検査する。検査済みの通知を保存し、既存の配信経路へ渡す。
4. **登録された方式で引き継ぐ。** 通知の配信処理後、結果返却型は既存の委譲処理で担当を起動する。完全切替型（session）は会話相手を専門担当へ変更し、初回の依頼を渡す。方式は登録済みbindingから解決し、発話による判定や新しい選択フラグは追加しない。
5. **担当に応じて応答する。** 結果返却型は通常会話AIが結果を伝える。完全切替型は専門担当が直接回答し、続く発言も直接受ける。通常会話AIの選定や回答の言い直しを毎ターン挟まない。通常担当への復帰は既存の返却・保存後終了・破棄の契約に従う。

自力回答とは、文章を作れるかではなく、依頼を満たせるかを指す。最新情報の確認や画像の生成など、外部情報・実操作が必要な依頼を知識だけの説明で完了扱いしない。判断基準は短い共通方針とし、語句による分岐を作らない。

候補が見つからない、または候補に依頼を満たす能力がない場合は、LLMが不足を説明するか必要な確認を返す。実行先が未確定なのに作業開始を予告しない。

## 4. 一時回答と責務の分離

一時回答は「これから何をするか」を伝える短い一文とする。例えばWeb検索なら「お調べします」、画像生成なら「画像作成の準備をしています」。これらは受入例であり、ツール名と固定文の対応表にはしない。実行前なので完了や担当切替の成功は断言しない。

| 層 | 担当すること |
| --- | --- |
| 会話AIの共通方針 | 自力回答の可否、必要時の委譲、実行前の短い予告 |
| 登録定義・関数schema | 担当の能力、使う場面、依頼と一時回答の入力契約 |
| 今回の入力 | 現在の依頼、会話情報、利用可能な候補と対象 |
| host | 契約検査、通知保存、通知と委譲の順序、重複防止、取消と失効 |
| サブエージェントのSKILL・ツール | 分野ごとの手順、内部のツール選択、実行と結果確認 |

引数は既存の平坦な共通形式を拡張する案とし、`request` に加えて必須の `announcement` を持たせる。`questionRef`、`target`、`resolveUnsaved` の既存の適用条件は維持する。一時回答の意味と長さの制約はschemaで一度だけ説明し、SystemContextへ重複して書かない。登録・契約の改訂は[登録手順](../docs/toolchain-extension.md)に従う。

一時回答は作業結果でも新たな操作権限でもない。最終回答のreceiptやMemory/Worldの成果取り込みに混ぜない。最終回答が来ても、何を予告したかは当該ターンの表示で確認できるようにする。

## 5. 通知、失敗、取消

- dialogueがrunと選定に紐づく一時回答・通知状態を所有する。フロントエンドに別の正本を作らない。保存形式の具体化は実装の最初に既存の永続化機構へ合わせる。
- 通知前の採用検査に失敗した場合は委譲しない。空の一時回答や未知の関数を固定文で補って進めない。既存の構造修復上限を超えたら失敗として返す。
- 同じ依頼の再配送・再接続で通知や委譲を重複させない。保存済み通知は再取得できるが、再取得は再実行の契機にしない。
- 通知の配信処理を委譲より先に行う。ブラウザの受信確認や音声の再生完了を待つ新しい通信プロトコルは設けない。この案で保証するのはサーバー側の配信順序であり、端末上の表示・聴取完了後の実行ではない。
- 音声入力時も自動読み上げ設定に従って既存deliveryへ通知を渡す案とする。通常の回答との順序と重複防止、取消を共通化し、最終回答を上書きしない。
- 通知後に取消・権限失効が起きた場合は委譲を止める。既に開始した処理には既存の取消と古い結果の拒否を適用する。通知済みの予告を成功の証拠にしない。
- session型の開始予告と、開始成立後の担当切替通知は意味を分ける。未保存作業の解決が必要な場合は既存の確認手順で待ち、専門担当を開始済みと表示しない。
- 完全切替の予告は「制作担当に引き継ぎます」など、対話相手が変わることを説明する。対応関数の説明へ登録由来の切替方式を渡す。切替成立後は今回追加する通常会話の初段判断を通らず、既存の専門対話へ直接配送する。

### 実装時の具体化

初段の判断は、通常回答と、担当の探索が必要なときだけ選ぶ内部関数の二択で表す。自然文の返答はそのまま回答に採用でき、構造不正の修復は既存の生成処理を再利用する。探索は実操作・担当起動を行わない。記憶の参照準備は候補検索から分離して初段でも維持する。

一時回答は選定attemptのキー付きでdialogueのrunに保存し、run一覧・progressから取得できるようにする。生成jobのexecute内で選定と権限・版を検査して保存・通知し、その後の既存settleで再検査して委譲する。通知だけが保存された状態で停止しても、既存のjob中断処理に従い、通知を根拠に委譲を再実行しない。同じrunで専門担当が範囲外の依頼を通常担当へ返した後に別の担当を選ぶ場合も、予告は既存のものに続けて保存する。同じ選定attemptの再配送は追加しない。各予告は200文字以内、合計は既存の回答容量65,536文字以内とする。会話の通常メッセージには追加せず、参照履歴・Memory/Worldへの混入を避ける。

## 6. 実装順序と完了条件

| 段階 | 必要作業・依存 | 完了条件 |
| --- | --- | --- |
| 設計 | 現状調査、変更案と検証条件の作成、利用者との合意 | 本案の対象・順序・一時回答の扱いが合意済み |
| 契約 | 初段の判断、選定時の一時回答、通知状態の最小契約を確定 | 既存の版・権限・結果採用との整合が取れ、型とfixtureで検査できる |
| 応答と委譲 | 自力回答先行、既存候補検索、共通の予告・委譲順序を接続 | 語句やツール種別ごとの意味判定・固定応答を追加せず全委譲経路に適用 |
| 表示・音声 | API/SSE、会話表示、deliveryへ接続 | 再接続・取消・最終回答で通知が欠落・重複・上書きされない |
| 検証 | 下記の部分→結合→通し検証、差分点検 | fixture、live、実機器の結果と未実施項目を分けて記録 |

部分検証はdialogueの判断・契約・通知、Webのprogress、必要なdeliveryの試験。`bun run verify -- --domain dialogue` を起点に、実際に変更したcapabilities・conversation・deliveryと利用側domainを追加する。結合検証は既存の `api/application/toolchain/` のrouting・出力・委譲・専門担当の試験に順序の確認を加える。ブラウザの通し検証は `tests/browser/toolchain.spec.ts` と音声に影響する対象ファイルを明示して個別に実行する。

| 受入場面 | 観測する合格条件 |
| --- | --- |
| 手元の情報で答えられる質問 | 直接回答し、委譲用の候補検索・予告・担当起動を行わない |
| 最新情報の調査依頼 | 自力回答判断→選定→短い予告の配信→担当開始→根拠付き結果の順になる |
| 画像生成依頼 | 生成の準備を伝えてから担当を開始し、生成前に完成を断言しない |
| 登録済みの別分野・言い換え | ツール別の固定応答や追加分岐なしに同じ契約を通る |
| 必須情報不足・利用可能な担当なし | 必要な確認または制約の説明を返し、実行できない処理を予告しない |
| 通知直後の取消、再接続、重複配送 | 通知を再取得でき、委譲が重複せず、取消後の結果を採用しない |
| 通知の構造不正、担当の起動失敗 | 無言の委譲や偽の完了をせず、失敗状態を表示する |
| 専門対話の開始・未保存作業の確認 | 予告を成功通知にせず、既存の確認と切替の条件を守る |
| 完全切替後の追加入力・通常担当への復帰 | 専門担当へ直接届き、通常担当の初段判断・候補検索・言い直しが走らない。既存の復帰条件で通常会話へ戻れる |

実モデルでは直接回答と各委譲の成否に加え、初回応答・予告・最終回答までの時間と推論回数を変更前後で記録する。自力回答を先に置くことで委譲時の判断工程が増えるため、速度改善を事前に断言しない。liveで使う接続先は保存済み設定を読み取る。サーバーの起動・停止が必要な検証は明示許可を得て実施する。音声の実機器受入は3往復で別記録とする。

## 7. 今回の実施記録と残作業

### 実装済み

- 初段の自力回答／探索判断、必要時だけの候補検索、選定した関数の必須 `announcement` を実装。自然文回答の後に行っていた旧経路再判定は削除した。
