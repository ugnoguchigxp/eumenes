# 会話エージェントの自己診断と Claude Code への修正依頼

2026-11-12 合意。スケジューラーの診断と、承認した診断を Claude Code の分析依頼に添えるところまで実装済み。

Eumenes の会話エージェントが、利用者の相談を受けて、この会話に関係する予約の有無と実行結果を直接確かめる。修正が必要と考えられる場合は、確認した事実と未確認の点を示し、利用者の依頼と既存の承認を経て Claude Code に渡す。

## 1. 今回の会話で必要だったこと

毎朝10時に曲を届ける相談で、会話エージェントは ChatGPT Scheduled をブラウザで調べる担当に渡した。利用者の訂正後も、自発応答で Hermes Agent の情報を自分の機能として案内した。会話の実行記録が `completed` でも、予約の登録、作曲、配信のいずれが行われたかは、その値から判定できない。当時の会話ログだけでは該当する予約の登録有無は未確認だった。

会話エージェントには `read_history`、`read_runs`、`read_agents` が提示されていた。`read_runs` は最近の会話実行と関連する警告を、`read_agents` は担当の作業を読める。Scheduler は予約と各回の実行履歴を持ち、実行履歴から Queue のジョブと会話またはワークフローの実行をたどれる。既存の Claude Code の「エラー修正」は、失敗した会話実行のエラーレポートを起点に、分析と実装を二段階で依頼する。 [会話の読み取りツール](conversation-read-tools-design-2026-10-31.md) · [Scheduler の契約](../api/domains/scheduler/contracts/index.ts) · [Claude Code への依頼](../docs/terminals.md)

## 2. 会話から予約を確認する

1. 会話エージェントは、利用者の直近の発言と訂正、ホストが示す機能の説明から調べる対象を選ぶ。「自分の機能」の稼働状況には Eumenes 内の記録を優先する。通常の応答と自発応答の指示に同じ原則を置き、Web で取得した情報は出典のある外部情報として扱う。
2. 既存の `read_runs` に `target` を追加する。指定のない呼び出しは従来どおり最近の会話実行を返す。初版の `target` は `kind: "schedule"` と、必要に応じて予約 ID `id`、確認したい予定時刻 `at`（オフセット付き ISO 8601）を取る。予約 ID がなければ現在の会話から確認できる予約の候補を返し、ID があれば該当する予約と直近の実行結果を返す。`at` は履歴で確認する予定時刻に使う。既存の `count` は会話実行の読み取り専用とし、`target` との併用は入力エラーとする。
3. モデルは候補の種別・時刻・繰り返しと会話の文脈から該当する予約を判断する。候補が一意に定まる場合はその結果を伝える。複数残る場合は、利用者が区別できる候補を示して一つ確認する。対象を推測して他の予約の結果を報告することを防ぐため、予約 ID はホスト側でも照合する。

1回の会話で使う既存の読み取り枠は維持する。予約、発火、後続の結果をホストが一度の読み取りにまとめる。直近の訂正の確認に `read_history` が必要な場合や、誤った担当への引き渡しを確認する場合は、既存の `read_history` と `read_agents` を使う。読み取り先が利用できない場合は、その時点で確認できない旨を伝える。 [読み取りの実装](../api/domains/dialogue/service/executor-read.ts) · [会話から担当に頼む経路](../docs/agency.md#会話の返事から担当に頼む)

自発応答では、利用者がこの会話で確認を求めた対象について、同じホストの読み取り結果を参照できるようにする。予定や権限が変わった場合は再確認し、取得できなければ稼働状況は未確認として扱う。発話前に利用者が対象を訂正した場合は、既存の入力の世代管理で古い結果の報告を止める。内部診断の代わりにバックグラウンドの Web 調査を起動する経路を作らない。Claude Code への引き渡しは利用者の発言を起点とする既存の委任経路に限る。 [自発応答と調査の設計](agency-agenda-integration-2026-11-11.md)

### Scheduler が返す記録

| 確認事項 | 根拠と回答に使う情報 |
| --- | --- |
| 予約の有無と現在の状態 | Scheduler の予約 ID、種類、状態、繰り返し間隔、次回予定、延期理由。取消済み・完了済みの予約も対象に含める。 |
| 予定時刻の処理 | 該当回の予定時刻、実行履歴 ID、`dispatched` または `skipped`、記録された理由。延期は予約側の `deferReason` から読む。履歴がなければ、確認した時刻の実行記録がないことを示す。 |
| 後続の処理 | 実行履歴の `jobId` と `subjectRef` から、Queue の状態・失敗コードと、会話実行またはワークフロー実行の確定状態を読む。会話実行に別の後続ジョブがあれば、それぞれの状態を保持する。 |
| 結果が届いたか | 同じ実行に紐づく保存済みの回答や成果物を、権限と記録で確認できた場合に示す。ブラウザでの表示・読み上げ・利用者の受領は、それを裏づける記録がある範囲で答える。 |

`dispatched` はジョブの登録を示す。会話実行の `completed` はその回の処理完了を示す。いずれも成果物の生成や配信の証拠として使わない。初版の取得上限は予約候補5件、候補ごとの実行履歴は直近3件。時刻指定時は該当回を先に探す。現行の読み取り結果と同じ3,000字以内に収め、検索範囲と、上限・記録の欠落・読み取り障害で確認できなかった部分を示す。空の結果は、対象範囲を確認できた場合の「該当なし」、一部だけ確認できた場合の「確認範囲では該当なし」、読み取り自体ができない場合の「未確認」で区別する。 [Scheduler の読み取り](../api/domains/scheduler/service/index.ts) · [会話予約の実行](../api/domains/dialogue/service/intake.ts) · [ワークフロー予約の実行](../api/application/app-development/workflow-controls.ts)

会話予約は現在の会話に属するものを読む。ワークフロー予約は、現在の会話に紐づく参照から既存のアプリの閲覧権限と予約との結び付きを検証できるものを読む。その経路で範囲を確認できなければ、ワークフロー予約は未確認と伝える。予約 ID やプロジェクト共通の `scope` が一致するだけでは参照を許可しない。タイマーの内部予約は対象外とする。通常の会話予約が扱うのはその会話での回答であり、毎朝の作曲は実行可能なワークフローの登録状況と実行結果を確認する。 [実行予約の設計](toolchain-search-choice-design-2026-10-30.md#現行の会話予約と一覧)

### 回答の例

> この会話には、毎朝10時に文章で知らせる予約が1件あります。今日10時の回答は保存されています。作曲するワークフローの予約は、この会話から確認できる範囲では見つかりませんでした。

## 3. Claude Code に同じ根拠を渡す

1. 会話エージェントは確認した事実、まだ分からない点、調査対象を短く伝える。正常な状態や単なる登録待ちを、コードの不具合と断定しない。利用者が原因調査や修正を頼んだ場合は、既存の「エラー修正」担当 `claude-code.repair` への依頼を組み立てる。
2. 依頼には、ホストが確認した機能・対象の参照、確認範囲と時刻、段階ごとの状態と固定の理由コード、再現時に期待する結果を添える。対象となる失敗した会話実行があれば既存のエラーレポートを参照する。予約が見つからない場合や会話実行が完了している場合は、確認した範囲と観測事実を添える。予約 ID や失敗 run を必須にすると、登録に至らなかった不具合を引き継げないため、確認した会話実行または予約を探した範囲も根拠にできるようにする。
3. ホストは既存の承認待ちの依頼に対象と根拠の参照を結び付ける。承認時に会話・対象・権限を再確認し、登録された Eumenes プロジェクト宛てに既存の `claude-code.request` で送る。対象の訂正、忘却、権限の変更で根拠が失効した場合は再診断する。状態が進んで問題が解消した場合は、その事実を示してから、以前の問題をなお調べるか利用者の意図を確認する。同じ承認の再送は既存の依頼 ID に合流する。
4. 1回目は再現・原因分析と改善案の報告まで。再現できなければ、確認した範囲を報告して止める。利用者が改善案を承認して改めて依頼した場合に、承認された範囲の修正と検証を別の依頼として実行する。受付・作業開始・分析結果・修正と検証の完了は、既存の端末依頼記録と会話への結果通知で伝える。

Claude Code に渡す事実は、許可された ID・時刻・状態・理由コードと、利用者に示した短い再現条件に絞る。会話全文・音声・予約本文・認証情報・設定値・生ログは対象外とする。LLM が作る依頼の文と、ホストが検証して添える事実を分け、事実の参照先をモデルの自由記述から解決しない。既存の承認・委任が保持する参照と依頼内容を利用し、診断結果専用の保存先を増やさない。 [エラー修正の手順](../api/domains/capabilities/bundles/terminals-screen.bundle.json) · [承認時の参照の再確認](../api/domains/dialogue/service/executor-delegation.ts) · [端末の依頼記録と会話通知](../docs/terminals.md)

## 4. 他の機能に広げる境界

| 担当 | 責務 |
| --- | --- |
| 会話エージェントと既存の読み取りツール | 利用者の意図と参照先を選び、読み取った事実から何が分かるかを説明する。必要なら利用者に尋ね、修正依頼を組み立てる。 |
| 機能を所有する domain とアプリケーションの接続部 | 既存の公開読み取り操作で対象と状態を取得する。会話との結び付き、閲覧権限、参照の有効性を検証し、出してよい項目だけを返す。Scheduler 側の履歴や Queue の状態を会話側の SQL で直接参照しない。 |
| 既存の委任・承認と Claude Code | 対象、根拠、依頼した作業範囲を一緒に引き渡す。受付と実行結果の追跡には端末依頼の台帳を使う。 |

共通化するのは、読み取りツールの呼び出し経路と、結果に付ける確認時刻・範囲・参照・取得の完全性である。会話への返却と承認時の引き渡しは、同じ型付きの結果からそれぞれに必要な情報を取り出す。各機能の状態や失敗コードは所有 domain の意味を保つ。将来、タイマーなら作成・満了・通知、画像生成なら依頼・生成・保存を、それぞれの公開操作から読む。同じ `read_runs` と承認経路に接続できる。初版で追加する読み取り先は Scheduler のみとし、対象を選ぶ判断はツールの説明と会話の文脈を使う LLM に委ねる。

## 5. 実装順と受入条件

| 順序 | 作業と完了条件 |
| --- | --- |
| 1. 予約の読み取り | Scheduler の既存の予約・実行履歴の読み取りを使い、必要な絞り込みが現行の公開操作で足りない場合に限り Scheduler 側へ最小の読み取りを足す。`read_runs` の既存の呼び方を維持し、未登録、実行待ち、一時停止、スキップ、延期、後続失敗、結果確認、記録欠落、上限超過を区別できる。別会話の ID、権限が失効したワークフロー、忘却した発言由来の記録を出さない。 |
| 2. 会話での診断 | 通常の応答で内部記録を参照し、自発応答でも訂正後に他製品の情報を Eumenes の診断として報告しない。該当する予約が複数ある場合、作曲と会話回答を区別する必要がある場合、読み取り先に接続できない場合を確認する。 |
| 3. 修正依頼 | 失敗した会話実行がある場合と、予約登録に至らず失敗 run がない場合の双方で、同じ根拠を既存の承認に結び付ける。拒否・取消・期限切れ・対象の訂正・参照失効では送信されず、承認の再送でも Claude Code への送信は1件。分析後に修正の承認を受けた場合だけ、2回目の依頼が作られる。 |

部分検証は読み取りと端末依頼の固定データ試験から始める。結合検証では既存の予約試験と読み取りツール試験にケースを追加し、会話から予約の結果を答え、確認待ちの修正依頼まで進むことを確かめる。続けて `bun run verify -- --domain scheduler --domain dialogue --domain capabilities --domain terminals --domain tool-runtime` で、変更の影響がある domain を検証する。 [予約の結合試験](../api/application/scheduler/scheduler-toolchain.test.ts) · [会話の読み取り試験](../api/domains/dialogue/test/read-tools.test.ts) · [検証手順](../docs/verification.md)

通し検証は隔離した検証環境で行う。実際の会話と同じく「毎朝10時に曲を届けたい」から始め、登録の有無と根拠が返ること、会話予約とワークフロー予約を区別すること、対象を訂正した後も Eumenes の診断を続けること、明示の依頼と承認後にのみ Claude Code に分析が届くことを確認する。固定応答での成功、実モデルが読み取りを選んだ結果、実際の端末依頼の受付・通知は分けて記録する。失敗した場合は対応する会話実行・ジョブ・端末依頼の ID から記録を追い、原因を絞ってから該当する検証を再実行する。

## 6. 実装と検証の記録

`read_runs` の検索版を `host:read_runs@2` に更新した。予約の読み取り結果には会話内の `e<n>` を返す。承認と端末依頼の保存時に、その参照が指す観測と元の発言を再確認する。エラー修正は `toolchain:claude-code.repair@3` から `binding:claude-code.repair@3` と既存の `claude-code.request` を通る。端末へ送る診断はホストが組み立て、会話で提示した観測を添える。

| 検証 | 結果 |
| --- | --- |
| 会話から端末の受付まで | 隔離した固定モデルの試験で、予約なしと実行済みの両方を確認。承認前の送信なし、承認後の観測の一致、承認の再送で重複なし、元発言の訂正後の送信なしを確認した。 [通し試験](../api/application/work/claude-code-toolchain.test.ts) |
| ワークフロー予約 | 登録したアプリの予約を実行し、現在開いているアプリに紐づく場合に保存済み結果まで取得した。アプリへの参照を渡さない場合は未確認になった。 [ワークフロー試験](../api/application/app-development/app-development.test.ts) |
| 実際の会話モデル | 初回は ID を指定しない質問で会話実行の一覧を読んだ。予約台帳を選ぶ引数と、ID の省略が可能なことを明示した後、同じ質問で予約を読み、登録済みで実行履歴が空の観測を得た。 [実モデル試験](../api/application/scheduler/scheduler-toolchain.test.ts) |
| 実際の Claude Code | 承認された合成の診断を、プロジェクトにアクセスできない検証用の Claude Code に渡した。応答から診断の参照、予約 ID、実行履歴の状態が一致することを確認した。 [通し試験](../api/application/work/claude-code-toolchain.test.ts) |

実サービスを使う試験は次のコマンドで個別に再実行できる。

```sh
EUMENES_VERIFY_SCHEDULER_LLM=1 bun test ./api/application/scheduler/scheduler-toolchain.test.ts -t 'live model reads'
EUMENES_VERIFY_DIAGNOSTIC_CLAUDE=1 bun test ./api/application/work/claude-code-toolchain.test.ts -t 'schedule diagnostics reach.*completed'
```

隔離コピーの6 domain 標準検証では静的検査を通過し、Bun 試験は1,093件成功、3件スキップ、1件失敗。失敗した Canvas の初期登録試験は変更前の `b59dda83` でも同じ結果だった。実モデルでの確認を反映した最終版は、`scheduler` と `pipelines` の標準検証で69件成功、4件スキップ、会話の読み取りと Claude Code 連携の固定回帰試験で33件成功した。稼働環境への反映と Claude Code による製品コードの修正は検証範囲に含めていない。
