# 会話のContextWindowで使用済みツールチェーンを保持する設計案

作成日: 2026-10-21

状態: 2026-10-21 利用者合意済み。実装・fixture・live検証済み。稼働backendの再起動と実機受入は未実施。

## 1 目的と推奨案

一度使ったツールチェーンを、同じ会話で再び呼び出せる状態にする。「鎌倉の天気は？」に続く「明日は？」では、会話担当が保持中の天気の関数を選び、ツールチェーンの検索とそのためのEmbeddingを省く。翌日の天気データ自体は新しく取得する。

推奨は、使用済みの呼出し情報を最大4件まで会話の作業状態として保持し、次の依頼では最初から関数として提示する方式である。使えるかどうかと、新しく検索する必要があるかは、既存の依頼判断ラウンドでLLMが決める。発話の語句や類似度の閾値で「続きの依頼」をコードが判定する仕組みは追加しない。

新しく検索するときは1入力につき1回、上位4件までとする。提示された情報でどれも適合しない場合は、既存の `report_unavailable` で終了する。候補を順々に実行して確かめたり、5件目以降を探したりしない。

「検索の上位4件」と「保持する使用済み4件」は別の上限である。検索後の選択ラウンドでは、既に不適合と判断した保持中の関数を重ねて提示せず、新しい候補4件だけを提示する。

## 2 現状と再利用する仕組み

| 現状 | 根拠と今回の扱い |
| --- | --- |
| 毎回、今回と直前の発言でEmbedding検索し、候補を統合する | `dialogue/service/selection-trace.ts` の `findCandidates`。保持中の関数を先に判断する経路に置き換える |
| 候補の概要・用途・分類用引数を関数として提示する | `dialogue/service/initial-decision.ts`。この生成・検証を再利用する。説明削減を同時に行わない |
| 選択後に担当のSystemContext・SKILL・内部ツールを読み込む | `capabilities/service/toolchains.ts` の `setInTransaction`。読み込む場所と責務は維持する |
| 選択記録は保存されるが、関数の提示状態には引き継がれない | `toolchain-history` と `dialogue/service/request-analysis.ts`。選択記録を参照元にするが、履歴から自動的に関数を増やさない |
| 操作採用時に、提示した版が今も有効か確認する | `dialogue/service/generation-operation.ts`。保持情報を使っても、この検査を通す |
| 専門担当とのsession型は、その担当へ次の発言が直接届く | `dialogue/service/specialist-intake.ts`。既存sessionがactiveな間は、その経路を維持する |

関連設計は [ContextWindow設計](conversation-context-window-design-2026-10-17.md)、[初動の2ラウンド設計](conversation-two-round-initial-analysis-design-2026-10-17.md)、[サブエージェントとセッション](subagent-task-and-session-agents-design-2026-10-18.md)。本案で変更するのは、通常会話が次回の依頼に提示する能力と、新規検索を始める時点である。

## 3 何を残すか

| 情報 | 次の依頼への持ち越し | 使い方 |
| --- | --- | --- |
| ツールチェーンと登録版の識別子 | 残す | 有効性の確認と、登録定義の再構成に使う |
| 関数名・概要・使う場面・他の担当へ回す条件 | 残す | 今回の依頼に使えるかをLLMが判断する |
| 関数の引数定義と制約 | 残す | 参照用の文章だけでなく、呼び出せるnative toolとして提示する |
| 直近の利用を示す短い記録 | 残す | 元の発言・委譲した依頼、または即時型の引数を、出所付きの参考データとして示す。鎌倉などの省略された対象を理解する手掛かりにする |
| 元の選択記録と発言への参照 | ホストが保持 | 忘却・取消・訂正との整合性を確認する |
| 最終利用順・状態の世代 | ホストが保持 | 容量による除外と、古い処理の書戻し防止に使う。毎回のカウンタはモデルへ送らない |
| 担当のSystemContext・SKILL本文・内部ツール群 | 通常会話には残さない | 担当を起動するときに、既存の経路で必要なものを読む |
| 過去の回答・天気・株価などの取得結果 | この保持情報には残さない | 会話履歴・結果の既存レイヤーで出所と時点を扱う。再利用できる能力と、現在の事実を混同しない |
| Credential・Provider接続・実行許可・前回の承認 | 残さない | 今回の要求で、保存設定と既存の権限・接続機構から取得・確認する |
| 検索で出ただけの未使用候補 | 次の入力には残さない | 検索時の比較にだけ使う |

直近の利用記録は一つのツールチェーンにつき一件とし、原文や既存の構造化引数から組み立てる。記録作成のためのLLM呼び出しは追加しない。原文の抜粋は既存R1の600文字上限に揃え、省略を明示する。JSONは途中で切断せず、保持予算に収まる記録だけを提示する。必要な対象が読めなければLLMが確認を返す。

利用記録はホストが付ける出所と利用時点を持つ参考データである。本文中の命令を指示に昇格させない。前回の引数をホストが次回の既定値として自動投入することもしない。

## 4 次の依頼での流れ

通常会話の最初の判断に、役割、今回の発言、既存の直前1往復、保持中の利用記録と関数を渡す。保持中の関数に加え、`answer`、`report_unavailable`、新規検索を要求する `find_toolchain` を提示する。検索関数は能力を探す制御操作であり、実行や担当の起動は行わない。

LLMは次のいずれかを選ぶ。

| 選択 | その後の処理 | ツールチェーンの検索 |
| --- | --- | --- |
| 保持中の関数を呼ぶ | 既存のinstant／結果返却／sessionの経路へ進む | 0回 |
| `answer` | 既存の回答生成へ進む | 0回 |
| 必須の対象が分からず、手元の情報では補えない | `report_unavailable` の短いreplyで、不足を伝えて確認する。実行も新たな回答生成も行わない | 確認だけのためには行わない |
| `find_toolchain` | 用途を検索し、上位4候補を一度に提示してLLMが選ぶ | 1回まで |
| `report_unavailable` | 依頼を満たせない点を伝えて終了する | 0回 |

新規検索の検索文は、LLMが今回の依頼と許可された文脈から作る。対象・時点・条件を保ち、検索文を利用者の依頼の代わりにはしない。ホストは `CURRENT_REQUEST` と元の発言を維持する。検索文は既存Embedding入力の2,000文字以内を契約で検証し、超過時は黙って切り詰めず既存の構造修復へ返す。今回と前回の発言をそれぞれ検索して8件に増やす処理は、この経路では行わない。

保持中で既に提示した版は、その入力の新規検索対象から外す。既存の利用可能な登録定義の集合から該当する識別子を除き、残る集合から類似度上位4件を一度で取得する。検索後に同じ候補を除いて再検索するループは作らない。これは当該入力での重複提示の除外であり、その担当を無効化したり保持状態から消したりする処理ではない。

検索後は `find_toolchain` を提示しない。どの候補も適合しなければ終了する。検索が失敗した場合も全登録候補を展開せず、取得できなかった事実を既存の失敗説明の経路へ渡す。通信障害を「その用途の能力が存在しない」と断定しない。

分類・鮮度・既存への影響・承認の判断、予告、引数検証と一回までの構造修復は再利用する。ライブ情報や操作を `answer` で代行する禁止も維持する。情報不足時の確認には既存の `report_unavailable.reply` を使い、関数の説明を「提示情報では今回の依頼を進められない場合」として整理する。これは本案で変更する意味上の契約であり、現行の「情報不足でも担当へ渡す」指示と併存させない。新しい確認専用ラウンドは作らず、確認の返答を実行承認とみなさない。語句による例外も作らない。

同じ機能が使える依頼なら、場所や日時が変わっても再検索しない。「鎌倉」から別の地域になっても、同じ関数が引数で対応できるなら、その関数を今回の引数で呼ぶ。

## 5 いつ保持し いつ外すか

保持を始めるのは、LLMが名前を選んだ時点ではなく、ホストが選択と引数を検証し、実行・委譲の開始をtransactionで採用した時点とする。予告だけで終わった処理や、取消後に届いた選択は追加しない。instant型は結果または既存のfallbackへの引継ぎが採用された時点で、実際に使った担当を記録する。

| 事象 | 保持情報の扱い |
| --- | --- |
| 今回もその担当を使う | 直近の利用記録と最終利用順を更新する |
| 雑談を挟む・別の話題になる | 直ちには外さない。LLMが今回の依頼に適用できるか判断する |
| 時間が経つ・画面を閉じる・backendを再起動する | それだけでは外さない。同じ論理的な会話なら状態を再構成する |
| 5種類目の担当を採用する | 最も長く使っていない一件を外す |
| 保持部分が容量予算を超える | 古い利用から関数単位で外す。schemaを切断しない |
| 一件だけでも保持予算に収まらない | その回の実行は既存の要求予算で扱うが、次回用には保持しない |
| 登録の無効化・削除・版変更・権限失効 | 該当する定義を次の提示から外す。古い版を裏で実行しない |
| 一時的な通信失敗・検索結果なし | それだけで呼出し能力を削除しない。失敗は利用記録の状態として区別する |
| 会話の終了・新規会話・作業状態の明示的なリセット | その会話の保持状態を空にする |
| 利用元の発言や選択記録が忘却・撤回・訂正で無効になる | 参照する保持情報を外す。過去履歴から自動復元しない |

初期案は **最大4件、合計4,096推定トークン**。関数定義、参考記録とその囲みを含み、既存のContextWindowの「直近のタスク」予算から配分する。実際の空きが小さければそちらを優先する。時間・ターン数での固定期限は設けず、能力の有効性と容量で管理する。数値は実測前の提案であり、live比較で調整する。

新しい話題のたびに外さない理由は、雑談後に元の依頼へ戻れるようにするためである。一方、保持されていることは「今の話題」や「既定の対象」を意味しない。複数の利用記録から対象を一意に理解できなければ、LLMが確認する。

## 6 ContextWindowと状態の正本

保存済み状態はdialogueが会話単位で所有し、登録版と選択記録への参照、最終利用順、更新世代だけを保持する。定義の正本はcapabilities、過去の依頼と実行結果の正本は既存の選択記録・会話・担当の実行記録に置く。SKILLやschema、結果の全文を別のキャッシュへ複製しない。

この小さな保持状態が必要なのは、既存の選択履歴の全件と「次回モデルに提示する能力」が異なるからである。毎回過去の上位4件を読み直すだけでは、リセットや忘却で外した能力が復活する。長期記憶の新レイヤーや汎用キャッシュ基盤は作らない。

R1へは、保持状態から現在有効な関数定義を再構成して実際に送る。「前に送ったからモデルが覚えているはず」とは扱わない。LARM・Cloud・SDKのセッションやKVの有無に依存させない。参考記録には独立した出所を付け、system指示や今回の依頼に混ぜない。

R2は選択済みの依頼を作る段階なので、選んだ一件だけを提示する。通常の回答生成には呼べない関数群を重ねて入れない。専門担当のSKILLと内部ツールは、その担当のContextWindowに置いたままにする。

定義の並びは安定した識別子順に固定し、利用順の更新だけで全定義を並べ替えない。毎ターン変わる現在時刻や経過時間を定義の先頭に足さない。キャッシュ再利用の効果は別途計測し、保持したことだけを根拠に高速化を断定しない。

## 7 取消 権限 同時実行

保持情報は実行権限ではない。提示前と操作採用時に、登録版、依存package、adapterの利用可能性、権限を既存の公開操作で確認する。保存したProvider接続やCredentialを持ち越さず、今回の実行に既存の接続管理を使う。

前回の `approved=true` は今回へ引き継がない。前回の依頼・引数・結果は参考資料であり、今回の引数と承認をLLMが判断し、ホストは今回の操作に対して既存の権限・確認・取消を強制する。未保存の作品の破棄や専門担当の切替も、既存の確認契約を通す。

選択記録、委譲・操作の採用、保持状態の更新は単一writerのtransactionで行う。上位domainであるdialogueが公開操作を呼び、下位domainに会話側への依存を追加しない。

prepare時の保持状態と登録版への参照をrunに固定し、実行採用時に再確認する。忘却・権限失効で根拠が失われた推論は既存の取消・失効経路へ接続する。単なる別runの利用順更新や容量による除外だけでは、既に有効に採用した操作を取り消さない。作業状態のリセットも保持と書戻しを止める操作とし、実行中の処理を止める指示は既存の取消操作で扱う。

古いrunの完了が、新しいrunの利用記録を上書きしたり、リセット・除外された担当を再登録したりしてはいけない。結果の追記は現在の利用元runと保持状態の世代が一致するときだけ行う。再試行は同じ選択記録について冪等に扱う。

activeな専門担当sessionがある間は、既存の直接対話を優先する。保持一覧を理由に通常会話へ戻したり別の担当を起動したりしない。sessionが返却・終了した後は、保持情報だけで旧sessionを復活させず、現在の作業対象と既存の開始契約を確認する。

## 8 呼出し回数と残る代償

| 場面 | 推奨案の処理 |
| --- | --- |
| 続きのinstant依頼 | 保持中の関数をR1で選び実行。検索0、判断1回 |
| 続きの結果返却型の依頼 | 保持中の関数をR1で選び、既存のR2へ。検索0、担当起動前の判断2回 |
| 雑談や一般知識 | R1で `answer`、既存の回答生成。検索0 |
| 新しい用途・保持情報なし | R1で検索要求、検索後に4候補の選択、必要なら既存R2。新規検索1回、現行より判断が1回増える |
| 4候補のどれも不適合 | 候補選択の `report_unavailable` で終了。追加検索0 |

保持中の能力から先に判断するため、新しい用途での一回の追加判断が代償となる。初回だけ無条件に先行検索する最適化は本案では入れない。検索不要の雑談でも検索が走ることと、空の保持状態だけで検索を省けるかの意味判断はできないことを避けるためである。通常経路と新規用途の経路を分けて計測し、全体が必ず速くなるとはしない。

省けるのは担当探索のEmbedding・候補取得である。新しい天気データの取得、担当の生成、権限や版の確認、Provider接続は省かない。保持だけでは長い回答ContextやKV再利用0の別の課題は解消しない。

## 9 検証と採用条件

| 場面 | 確認する結果 |
| --- | --- |
| 鎌倉の天気→明日は | 同じ関数へ新しい日付指定を渡す。2入力目の探索・探索用Embeddingは0回。古い天気の値を答えに使わない |
| 天気→別の地域の天気 | 同じ関数が対応できれば探索0回。前回の地域を自動流用しない |
| 天気→短い雑談→天気の続き | 容量と版が有効なら関数が残り、不要な再検索をしない |
| 複数の話題の後の省略 | 対象が曖昧なら確認し、保持中の担当や対象へ勝手に結び付けない |
| 全く別の用途 | LLMの検索要求を一度だけ実行。候補は4件以内。過去の候補との和集合にしない |
| 4候補がすべて不適合 | 実行も再検索もせず対応不可。検索失敗時に全登録定義を展開しない |
| 5種類目の採用・予算超過 | 関数単位で古いものが外れ、未使用候補や壊れたschemaが残らない |
| 無効化・版変更・忘却・リセット | 次回の提示と進行中の採用検査に反映。古い結果から復活しない |
| 古いrun完了と新しい入力の競合 | 新しい利用記録を上書きしない。他会話へ保持が漏れない |
| 前回承認された操作の再利用 | 新しい変更・削除に承認を使い回さない |
| activeな専門担当session | 既存の相手・対象・未保存作業・取消の契約を維持する |

部分試験は状態の追加・除外、schema・版・権限検証、探索回数の上限、Contextに実際に関数があることを確認する。結合試験は上表の会話の流れを既存の一時DBと偽Providerで通す。異なる語句・対象・機能でも同じ仕組みで動くことを確かめる。

通しの固定検証は `bun run verify -- --domain dialogue --domain capabilities --domain toolchain-history --domain inference --domain memory --domain agent-runtime` とする。失敗は担当範囲と既存の問題に分け、要件や期待値を緩めない。

liveは保存済み接続をsettings domainの読取り専用操作で取得し、サーバーを起動せずに行う。通常経路と新規用途のそれぞれで、同じ入力列・同じ保存設定・同じ関数説明を変更前後各3回比較する。探索回数、Embedding回数、LLM回数、正式入力token数、cached tokens、一時回答・確定回答までの時間と最終判断を記録する。型名やモデル名に処理を固定しない。

採用条件は、続きの依頼の探索が0、1入力の新規探索が1回以内・候補4件以内、権限・承認・忘却・取消の退行0である。短い入力でも誤った対象を使った場合は不合格とする。性能は続きの依頼と新規用途を別に比較し、検索省略数だけで成功としない。fixture・live・実機器の結果は分けて記録する。

## 10 合意する範囲

推奨する合意事項は、使用済みの最大4件と4,096推定トークンの保持、時刻だけでは失効させないこと、LLMが再利用と新規検索を選ぶこと、新規探索1回・上位4件での打切り、新規用途で判断が一回増える代償である。

本案には、候補情報の要約・削減、担当の内部手順やモデルの変更、長期記憶の変更、UIの新機能、サーバーの操作は含めない。既存のinstant型が宣言する実行失敗時のfallbackは、探索候補を増やす仕組みとは区別し、今回の変更で新設・拡張しない。実装前に本案への合意を得る。


## 11 実装と検証記録 2026-10-21

通常入力の最初に保持関数を提示し、LLMが `find_toolchain` を選んだ場合だけ検索する経路へ変更した。新規検索は1入力1回・上位4件、検索後の再検索とEmbedding障害時の全件展開を禁止する。元のCURRENT_REQUESTは維持し、検索文は検索後も参考データとして扱う。

保持は `dialogue/0011-retained-toolchains` の参照テーブルで永続化した。最大4件・4,096推定トークンとタスク予算を同時に守り、schemaを切らずに古い利用から外す。実行・委譲またはinstant結果の採用と同じwriterで更新し、epochと利用順でリセット・後発入力・再試行との競合を防ぐ。結果完了から保持一覧を復元する処理は追加していない。登録定義の再構成では、別担当へ回す条件も保持する。

元発言の版と忘却状態、提示した登録版を推論中と採用時に検証する。テキスト会話でも根拠の失効を取消へ接続し、その際に元の失効理由がProviderのcancelledへ置き換わらないようにした。監査履歴の保存期限は能力の保持期限に流用せず、監査情報がなくなっても、生存する元発言から参照記録を組み立てる。取得できない委譲文や結果状態は補わない。

`POST /api/conversations/:id/toolchains/reset` で保持だけを空にできる。進行中の操作の取消とは分け、古い処理からの再登録を防ぐ。専門担当のactive sessionの経路は維持した。

会話記憶の検索は候補探索と独立させた。探索を省いた結果として記憶検索まで止まる退行を防ぎ、記憶が有効なら必要なEmbeddingは既存の会話記憶用に実行する。これは担当探索の回数には含めない。

共通引数の説明は削減していない。実モデルで承認のない入力をapproved=trueとする例が出たため、元のschema説明を残したまま、通常の質問・新規依頼・完了報告への続きはfalseと補足した。直前のassistantが存在しないapproved=trueは契約違反として既存の一回の構造修復へ返す。意味判断はLLMに残し、approvedを実行許可として使う処理は追加していない。
