# 作成アシストエージェントの独立サブプロジェクト開発計画

作成日: 2026-11-03

状態: 計画案・実装前。利用者の依頼に基づく計画書の作成であり、リポジトリ新設、既存コードの移動、実行権限の拡張への合意とは区別する。

調査時のEumenes HEAD: `9e17160bf9e7cac14c89548daf49ceea524cdd49`。本書作成前から、4役割の設計書とその索引変更、別件の調査文書が作業ツリーにある。それらの内容は変更せず、本書と索引の一行だけを追加する。

計画書の作成中に別作業のコード差分が増えているため、実装着手時にはHEADと関連する実装の対応を再確認する。今回の文書検査は対象を限定し、他作業のコードを修正・検証する作業へ広げない。

## 1. 目的と対象

作成アシストを、利用者とのやり取りから意図・条件・未決事項を具体化し、JSON等の構造や外部エージェントへの作業依頼へ落とし込む担当として、独立して開発・検証する。

UI自由制作に限らず、入力フォームの回答整理、構造化文書の編集、Pipeline制作、Claude Codeへの依頼・追加回答・結果確認を対象にする。共通する仕事は「利用者と、実行・利用できる形まで内容を詰めること」である。成果物を常に画面やファイルにする必要はなく、構造化した要求や確認待ちの案も成果に含む。

本計画では既存の呼称「作成アシスト」を使う。サブプロジェクトの仮称は`eumenes-collaboration`とし、正式名と作成先はP0で決める。名前を理由に対象をUI生成へ限定しない。

### 1.1 期待する成果

- 複数ターンの対話から、明示された条件、仮定、未決事項、変更理由を区別した構造を作れる。
- 利用者の修正や手編集を受けても、関係のない条件や成果物を壊さず更新できる。
- 対象ごとのschema・検査・観測を使い、表示や実行結果を確認して対話を進められる。
- 必要に応じてClaude Code等へ正確な依頼を渡し、質問・進行・結果不明・終了を区別して扱える。
- UI、Pipeline、外部作業という異なる対象で同じ対話の核を使い、対象固有の処理を追加しても核の発話別分岐を増やさない。

### 1.2 今回行わないこと

今回は計画書だけを作成する。製品コード、依存、bundle、DB、設定、サーバー、外部エージェントへの送信は変更しない。新しい自律実行権限、任意の端末入力、commit/pushの代行を追加しない。

サブプロジェクトの開発でも、Eumenesの会話・queue・DB・認証・描画・端末管理を一式複製しない。すべての専門Subエージェントを新しい核へ移すこと、Pursuitや汎用のコーディング監督を作り直すことは対象外とする。

## 3. 必要な能力

| ID | 能力 | 観測できる成功条件 |
| --- | --- | --- |
| A1 | 意図と条件の具体化 | 目的・対象・制約を原発言と対応づけ、推測を利用者の決定として保存しない |
| A2 | 対話から構造への変換 | 対象schemaに合わせてJSON・設定・要求定義等を作り、必要な値が未決なら欠落を示す。schemaを通すための捏造をしない |
| A3 | 確認・仮置きの選択 | 後で容易に直せる案は提示して進み、実行に必要な未決事項は尋ねる。分かっていることを繰り返し質問しない |
| A4 | 変更意図と既存内容の保持 | 最新の訂正を反映し、変更対象外の条件・利用者の手編集・採用済みの構成を保つ |
| A5 | 参照対象の理解 | 「この項目」「前の案」を現在の作品・選択対象・版・履歴と結びつける。根拠がないときは対象を確認する |
| A6 | 構成の提案 | 内容の優先順位、見せ方、手順、外部作業の依頼を組み立て、案と確定事項を区別して提示する |
| A7 | 結果の観測と修正 | 対象の検査・表示・操作・試験結果から、案を直すか、追加情報を求めるかを判断する |
| A8 | 作業中の記憶 | 合意した点・却下した案・変更理由を出所付きで保持し、中断や再開でも復元する。自分の提案を同意へ昇格させない |
| A9 | 外部エージェントとの協働 | 許された作業を依頼し、追加質問を対応する利用者へ戻し、確定した回答と対象を結んで渡す |
| A10 | 終了・保留・引渡し | 作成、反映、観測済み、保存、公開、実行完了を区別し、未確認を残したまま達成したと言わない |

意味の理解、対象の選択、質問の必要性、構成・修正方針はLLMが判断する。コードはschema、参照、版、同一性、権限、予算などを検査する。発話の語句、題材、特定の再現例を辞書や正規表現で処理する製品分岐は追加しない。

## 5. サブプロジェクトの範囲と接続案

### 5.1 配布する核

coreはhostから渡された入力を使い、モデルへ送る要求を構成し、モデル出力を版付きの提案として返す。実モデル呼出しと操作の実行はhostが行う。プロセス内の長いPromiseや独自の常駐ループを核に持たせず、一手ずつ保存・再開できる接点にする。

coreはEumenesのdomainやSQL、Bunのprocess・filesystem・networkを直接参照しない。時計、参照、上限、既に確保された操作と結果は入力として渡す。独立実行でも同じcoreを使い、I/Oだけをテスト用hostへ差し替える。

外部へ出す単位は、まず次の三つに絞る。正確なAPI名とschemaはP0で確定する。

1. **入力・出力の契約**: 現在の利用者の依頼、対象のschemaと状態、観測、利用可能な操作、返却する提案。
2. **共同作業の判断処理**: 文脈の組立て、出力の解釈、根拠付きの状態更新提案。初版は現行のaction契約を保つ。
3. **評価可能な固定指示と版情報**: 共通の共同作業規則。UIの部品一覧や特定の実行手順は対象adapterの文脈に置く。

hostは提案を検査して実行し、receipt・現在版・拒否理由を観測として返す。coreが「反映した」と出力しても、hostの確定結果がなければ版や進捗を更新しない。

### 5.2 最小のプロジェクト構成案

| 場所 | 内容 | 製品への配布 |
| --- | --- | --- |
| `src/contracts/` | hostとcoreの版付き入力・出力、状態の構造 | 含む |
| `src/agent/` | 固定指示、文脈構築、提案の解釈 | 含む |
| `test/` | 契約・資料の分離・状態更新等の固定試験 | 含めない |
| `eval/` | 複数ターン課題、対象adapter、評価器、集計と分析 | 含めない |
| `standalone/` | 個別実行・再現用host。テスト用の保存と接続 | 含めない |
| `spec/` | host契約、研究仮説、評価条件、結果の限界 | 配布物には不要 |

UI、Pipeline、外部コード作業の違いをcoreのswitchへ置かない。実在する各対象のschema・説明・観測を渡すadapterで接続する。汎用のプラグイン市場や追加のDSLは作らない。

配布は既存の独立packageと同様、確定ソース、版、checksum、manifestを持つtgzを案とする。EumenesのAPIキー・接続先・モデル設定・製品DBをサブプロジェクトへコピーしない。standaloneの設定はテスト用に分離し、モデル名やprofile名を製品コード・ファイル名へ固定しない。

### 6.2 抽出と能力追加を別工程にする

最初に現行の入力、action、編集結果、返答、修正回数、取消時の扱いを記録し、固定モデルで同じ振る舞いを再現できる形で抽出する。ここでは最大推論回数・再試行・`no_change`の扱いを変更しない。

その後、意図の状態、観測、追加質問、外部協働を一つずつ比較する。例えば現行`no_change`は固定文で終了するが、「既に要求を満たしている」「表示中の項目と内部名を取り違えた」などの判断をモデルへ戻す案は、独立した振る舞い変更として検証する。

移行中の旧実装は比較用の凍結スナップショットに限定する。新しい核を製品採用した後は、同じ役割の固定指示・解析・判断処理を旧経路へ重複して残さない。共通の単発型runtimeや他domainは、この移行のために作り直さない。

切り出す共通固定指示の正本は配布core側に一つだけ持つ。Eumenes固有の規則は既存のSystemContext管理とbundleに残し、入力データと分離して合成する。TOMLの移動・削除やimport方式はP0で決め、既存のcontext lint/build/checkと生成物の整合を確認する。両側に同じ本文を手作業で複製しない。

## 7. 対話からJSON等へ具体化する状態と操作

### 7.1 状態の最小要素

状態はhostが保存する。coreは根拠付きの更新案を返し、確認できた版・イベントに基づくものだけをhostが採用する。

| 要素 | 持つ情報 | 区別するもの |
| --- | --- | --- |
| 今回の依頼 | 利用者の原文、現在の目的、依頼の版 | 過去の依頼、外部資料、hostの通知 |
| 条件・判断 | 値、対象、利用者発言または観測のref、変更・撤回の関係 | 利用者が述べた条件とエージェントの提案 |
| 仮定・候補 | 仮置きの値・理由・代替案、採否 | 仮置きと確定、却下済みと未検討 |
| 未決事項 | 不足、問い、回答の参照、どの構造の値に関係するか | 回答待ちと単なる検討候補 |
| 作業対象 | schemaの版、文書ref・版・digest、必要な範囲の本文 | 編集対象、表示中の対象、別作品 |
| 観測 | 検査、プレビュー、操作・外部作業の結果と対象版 | 反映済み、観測済み、未確認、古い観測 |
| 実行・権限の参照 | hostが発行したoperation・質問・承認のref | モデルの同意解釈とhostによる実行許可 |

出所refはhostが発行・検査する。値が利用者の発言の意味に合うかはLLMが判断する。参照が存在するだけで内容が正しいと保証せず、評価では条件ごとの意味の一致も確認する。モデルが`approved:true`を出して権限を作る形にはしない。

### 7.2 構造化の例

「社内向けの申込を受けたい。部署は必須で、メールはいらない」という依頼なら、部署必須・メール不要を出所付きの条件へ落とし、対象schemaに従う案を作る。申込内容や保存先がまだ決まらなければ、未決として保持する。画面の初稿は仮定を示して作れるが、値を整理しただけで実際の申込データの送信や公開を開始しない。

次に「部署は任意で」と訂正されたら、その条件を更新し、他の条件は維持する。利用者がまだ決めていない保存先を、以前のエージェント案から確定済みとして補わない。例文を製品の専用分岐にせず、言い方・対象・schemaを変えた課題でも同じ契約で扱う。

構造はJSONに限定しない。JSONのschema、表形式の入力、作業依頼書、既存domainの構造化引数へ同じ意図を投影できることを目指す。内部の共同作業状態と、実行先が要求する業務JSONは別にする。業務schemaへ独自の未決フラグを混ぜず、必要な値が決まるまでは実行候補として保持する。

### 7.3 要件変更と忘却

利用者との対話で要件は具体化・変更される。Pursuitのように全条件を最初から固定することは必須にしない。一方、外部へ渡す依頼や編集を実行するときは、その時点の条件・対象・入力の版を凍結する。変更後は古い提案・照合・承認を新しい実行へ流用しない。

採用済み状態にも、訂正・撤回・忘却を反映する。参照が消えたのに値だけが残ることを防ぎ、保存した抜粋・外部へ渡す予定の依頼・保留中の候補も追跡する。coreに独自の長期記憶DBを作らず、作業状態を丸ごとWorldやMemoryへ登録しない。

## 8. ターン・観測・待機の契約

標準の流れは、利用者の発言または対応するhostイベント→現状と必要な資料の取得→coreによる提案→hostの検査・操作→確定した結果の返却、である。続けて考えるか、短く答えるか、質問して待つかはcoreが提案する。回数・時間・権限はhostが強制する。

- 小さな修正は既存の短い経路を維持できる。毎ターンの計画書、画像確認、反省を必須にしない。
- 表示や操作の観測は、`workRef/revision/digest`と観測時点を持つ。別版の画像や操作結果を現在版の成功根拠にしない。
- 現行の`viewing`は主に保存作品の参照である。画面上の選択部品や座標まで扱うには、hostが発行する対象refと現在版への対応を追加する。モデルがDOMのIDや対象refを発明しない。
- 画像がない場合は構造・検査結果から判断できる範囲を示す。実画面を見たとは答えない。必要な観測を得られなければ、その点を未確認として残す。
- 人の回答や外部の長い仕事を待つ間は、状態とpending operationを保存してターンを終える。推論枠やプロセス内Promiseを保持しない。
- 再開イベントは、session・epoch・対象版・operation／質問IDを照合する。receipt保存前後のクラッシュ、重複イベント、取消後の遅延を固定試験にする。
- 実行済みの操作と返答の失敗は区別し、返答のために操作を再実行しない。

外部待機への対応は、現在の短いsessionターンの単なる時間上限延長で実装しない。必要なlifecycleの追加をEumenes側の接続契約として設計する。

## 9. UI自由制作での開発・検証

### 9.1 接続するもの

現在のUI定義schema、正規化・検査、`WorkDocumentAdapter`、実際のartifact rendererを使う。rendererの代用品だけで画面品質を評価しない。独立評価では、確定版に対応する実rendererをテスト用hostから読み、必要な観測だけをcoreへ渡す。

実画面の画像、アクセシビリティ情報、表示範囲、選択対象、入力後の値を、観測として返せる接点を追加する案とする。スクリーンショット単独では数式や全状態の正しさを保証しないため、操作と構造の検査を併用する。

### 9.2 複数ターン課題

見た目の唯一の正解画像を全課題に要求しない。指定された値・保全すべき情報・操作は機械検査し、構成と使いやすさは手順を揃えた人の評価を別に記録する。

## 11. Claude Code等を操作する担当への拡張

### 11.1 役割と依頼の構造

利用者と対象、目的、制約、完了条件、未決事項を整理し、実行可能な依頼へ具体化する。外部エージェントが返す質問や結果を受けて、その仕事の範囲で対話を続ける。実装の探索を長期に監督する機能を、無条件にこの担当へ重ねない。必要ならPursuitとの責務を別途合意する。

依頼は、原依頼のref、具体化した作業、対象projectのhost発行ref、許された変更範囲、検証方法、未決事項、実行に対応する権限refを持つ案とする。外部へ送る本文はこの版付きの依頼から作る。利用者の条件を省略した短い指示へ潰さず、長さ制限に収まらないときは許可された参照の読取り方法を設計する。全文を黙って切らない。

### 11.2 現行との接続と不足

| 操作 | 再利用するもの | 追加で必要な契約 |
| --- | --- | --- |
| 作業を依頼する | `terminal_requests`、`enqueueInTransaction`、既存の送信器 | 協働sessionを出所とする依頼、対象sessionとの固定した対応、実行前の権限・対象照合 |
| 進捗と結果を読む | フック、依頼状態、`lastReport/files`、非同期operationの追跡 | 作成アシストへ返す有界な観測。報告された変更と実際の差分・検証を区別する |
| 続く作業を頼む | hostが知る`claudeSessionId`と既存の継続対象 | 指定した依頼・外部sessionに結びつく追加指示。無関係な最新`current`へ送らない |
| 作業中の質問へ答える | 現行の`waiting`という活動状態 | 質問本文・種類・ID・対象世代・回答結果。通常の質問、実行許可、認証要求を区別する接点 |
| 取消・停止する | 未送信取消、`stop`と停止確認 | 作成アシストのpending operationと結ぶ。停止未確認を停止済みにしない |

現在の通常依頼キューは、作業中・質問待ちのPTYへ直ちに貼り付ける仕組みではない。そこへ回答を追加しただけでは、作業中の質問には答えられない。回答できる正式な接点を確認し、必要ならterminals側に最小の版付き操作を追加する。確認できるまでは「対応可能」と表示せず、利用者に画面で回答してもらう。

外部操作の方式は、既存の正式な構造化接点・フックを優先し、raw PTYへの任意入力をcoreへ公開しない。TUIしか扱えない項目は、入力可能な状態・対象・世代と操作確認を先に定義する。外部画面の表示文字列を見て固定キー列や無条件の`yes`を送る方式を既定にしない。

### 11.3 権限・所有・完了

- coreは実在するhost発行refだけを使い、`owner:direct`や利用者の発言を捏造して既存の型を通さない。現行のowner/originの契約で表せない場合は、最小の拡張を先に設計する。
- 作成アシストの発言、外部エージェントの要求、構造化JSON内のフラグを実行許可にしない。許可が必要な操作はEumenesの確認とhostの検査へ戻す。
- 依頼を直したら古い依頼と承認の対応を失効させる。必要な承認の対象を具体化し、同じ権限を別session・別プロジェクトへ持ち越さない。
- `mode:work`だけで全経路にcommit/push制限があるとは仮定しない。現行の制限はowner等による違いがあるため、採用する経路で実効性を確認する。
- 利用者の手入力と自動入力は、同じ外部sessionの入力所有権をhostで調整する。対象が変わった／応答が不明な場合は自動入力を止める。
- `queued/delivered/started/completed`は異なる。外部エージェントの完了報告は「報告」であり、利用者の受入条件を満たした証拠とは分ける。テストや成果物の確認ができない部分は未確認にする。
- 再起動や`unknown`を成功扱いせず、自動再送しない。外部の会話履歴が残ることと、実行を安全に再開できることを区別する。

### 11.4 評価課題

まず偽の外部agentで、依頼の忠実性、質問→利用者回答→同一質問への返却、許可要求の転送、手入力との競合、対象sessionの変更、送信途中の中断、重複イベント、停止未確認を試す。

その後、許可された隔離プロジェクトで実Claude Codeを使い、依頼→作業開始→質問／追加指示→結果→独立した差分・試験の確認を通す。最初はcommit/pushや外部送信を含めない。既存sessionへの送信、外部プロセスの起動・停止、製品サーバーの操作を、この計画書の作成依頼だけで実施しない。

## 12. 評価の設計

### 12.1 データと比較条件

初期課題は、一般の対話→構造化、UI自由制作、Pipeline制作、外部agent協働の4群とする。各群8課題、計32課題を最低構成の案とし、各群4課題を開発用、4課題を保留評価用へ開始前に分ける。通常は5〜12発話、一部に20発話以上の条件保持・中断・再開を含める。数は初期計画の提案で、P0で実行可能な予算とともに固定する。

評価者が保持すべき条件・許された変更・禁止された操作・質問の必要な点を事前に定義する。エージェント自身に全期待値を作らせない。言い換え、条件の訂正、単位・対象schemaの変更、途中の手編集を含めるが、その例だけの製品分岐は追加しない。

利用者役のLLMは補助評価とし、答えを不自然に誘導する、何度でも同じ質問に答える、曖昧な操作でも同意する、といった偏りを確認する。実利用者の共同作業を代用したと報告しない。固定脚本、人による受入、自由対話の結果を分ける。

比較は次の順で行う。

1. 現行実装と、振る舞いを保った抽出版。固定モデルでは出力・副作用・状態の一致を確認する。
2. 同じ核で、従来の文脈と、意図・未決事項を明示した文脈を比較する。
3. 観測なし／検査結果のみ／必要な表示・操作の観測ありを比較する。
4. 個別の改善が確認できた後に、組合せを保留課題と人の受入で確かめる。

現行が対応していない能力には、架空の「現行自動実行」の基準線を置かない。外部agentの作業中の質問回答なら、現在の依頼投入と利用者による手動回答を比較対象にし、人の介入と操作時間を含める。未対応の機能を全件失敗として加点効果を作らず、既存機能の回帰と新能力の達成を別に示す。

モデル・資料・能力・対象schema・総予算・打切り条件を揃える。観測や評価用のモデル呼出しも費用へ含める。コード・固定指示・データ・renderer・依存・フラグ・モデルの実行時識別値を記録し、測定中に変更しない。

公開できる合成課題と、実利用の会話・画面・コードを使う非公開の受入記録を分ける。製品の会話や外部agentの生出力を、独立プロジェクトの公開データや通常ログへ自動転記しない。記録には対象版、結果、使用量、必要な参照を残し、秘密や本文の保持範囲はhostの規則に従う。

### 12.2 指標と合否

| 指標 | 測り方 | 合否の考え方 |
| --- | --- | --- |
| 意図・条件の一致 | 事前の条件と最終構造・依頼を照合する | schema合格だけで通過させない |
| 要件の保持と訂正 | 複数ターンの条件の残存・撤回を検査する | 却下・訂正された条件を復活させない |
| 意図しない変更 | 対象外の構造・値・外部操作を比較する | 許された変更範囲を超えない |
| 質問と利用者負担 | 必要な質問の見落し、不要な質問、修正介入を数える | 質問ゼロを目的にしない。未決値の捏造で減らさない |
| 表示・操作・実行 | 実renderer、固定入力、独立検査で確かめる | 表示・fixture・live・受入の保証を区別する |
| 説明と事実の一致 | 発話とreceipt・版・観測を照合する | 未実行・未保存・未検証を成功と伝えない |
| 安全な継続 | 取消・競合・忘却・重複・再開の故障注入 | 不変条件の違反0件を製品採用の必須条件とする |
| 時間・資源 | ターンp50/p95、総tokens・費用、呼出し・検査回数 | P0で取得した現行値と、測定前に定める予算で判定する |

意味品質や見た目は単一の総合点へ潰さない。対象ごとの達成率とばらつき、保留課題の成績、利用者の介入回数を併記する。少数試行では優位性を断定しない。数値の採用基準は、現行の基準線を採取した後、改善版の結果を見る前に固定する。

### 12.3 部分→結合→通し

| 段階 | 実行するもの | 証明できる範囲 |
| --- | --- | --- |
| 部分・fixture | coreの出力契約、現在版・出所、保持・訂正、拒否・中断の再現 | 契約とhostが提案を正しく処理すること。実モデルの意味判断は含まない |
| 結合・fixture | 実writer・registry・domain・queueと固定モデル。UI/Pipeline/偽端末の操作 | 実際の接続、失効、保存、重複防止。実外部agentの操作品質は含まない |
| 独立live評価 | 明示された予算とテスト接続による複数ターン比較 | 実モデルの判断・構造化・観測利用。製品UI全体の受入とは別 |
| 製品Web受入 | 利用者の対話、実renderer、手編集、復帰、許可された実外部agent | Eumenesでの共同作業。音声の実機確認は別記 |

新サブプロジェクトには`verify`と、費用が発生するlive評価を分ける入口を用意する。Eumenesでは変更したdomainの`bun run verify -- --domain <name>`と利用側を選ぶ。初期候補は`dialogue / inference / tool-runtime / capabilities / ui-compositions / pipelines`、外部協働を接続する段階で`terminals`等を加える。正確な依存先と試験ファイルは各段階の変更前に確定する。

既存の部分・結合試験は、`api/domains/dialogue/test/specialist*.test.ts`、`api/application/pipelines/`、UIとPipelineのdomain試験を再利用する。Webは`tests/browser/ui-compositions.spec.ts`、`ui-composition-parts.spec.ts`、`pipeline-handoff.spec.ts`を影響に合わせて個別指定し、新しい意味判断の試験を台本E2Eの成功だけで済ませない。Claude Codeではterminalsの依頼・送信・lifecycleとapplicationのadapter試験を選ぶ。

サーバーを起動するfixture/E2Eも、既存のサーバー操作の許可規則に従う。検証用ブラウザは消音し、音声受入は利用者が開いたWeb画面だけで行う。

| C-2 | host非依存の判断部分だけを抽出し、I/Oと権限はEumenesに残す | 公開契約と現在の核との分割位置 |

| C-6 | 保存・公開・承認・停止の確定をhostへ残す | 既存の公開操作と新しい入力操作の境界 |
| C-7 | 検証した範囲だけを新revisionで製品採用し、同じ判断処理の二重保守を終える | 配布・切戻しと旧処理の削除対象 |

### 14.2 主要リスクと対処

| リスク | 対処・受入条件 |
| --- | --- |
| UI生成の都合が核へ入り、一般の構造化や外部依頼で使えない | P2の一般課題とP4の非UI課題で検査。部品名・画面の語句でcoreを分岐させない |
| 合意状態が新しい「正本」になり、原発言や現在文書とずれる | 出所付きの更新提案と、hostが確定した版を分離し、訂正・忘却で失効させる |
| 観測と修正を増やし、応答・費用が悪化する | 全ターンに観測を強制せず、同じ予算の比較で必要性を測る |
| 外部agentへ質問回答や許可を取り違えて送る | 質問ID・種類・世代とhostの権限refを検査し、未対応の操作を公開しない |
| 人の手編集・端末入力と競合する | 編集版と入力所有権をhostで照合。競合時は旧提案を適用しない |
| 自作のfixtureだけ通り、実作品や実行が壊れる | 独立検査、保留課題、実renderer、実外部agent、人の受入を分けて実施する |
| 独立化で同じruntimeと固定指示が二重になる | 抽出範囲を限定し、採用時に旧判断処理を削除する。host共通機構は移さない |

同じ仮説で3ラウンド進めても新しい根拠が増えない、測定中に実装・課題が変わる、計画外の権限や公開操作が必要になる場合は、次の編集・再実行の前に進め方を見直す。正常に進む長時間の仕事を、経過時間だけで再起動しない。担当外の失敗は証拠と影響を報告し、期待値・要件を弱めて通さない。
