# 監督サブエージェントの実装計画

作成日: 2026-10-09 JST。状態: 実装前。[全体計画](README.md) の P2〜P6 を担当する。共通状態は [01](01-tasks-and-queue.md)、CLI と証拠は [02](02-coding-runner-and-mcp.md)、報告は [04](04-conversation-and-reports.md) に従う。

## 1 役割と完了条件

監督サブエージェントはメインの会話とは異なる文脈・判断履歴・予算を持ち、委任された工程を進める。CLI に実装依頼を送って終わる機能ではなく、質問への対処、検証、別 session のレビュー、修正、委任済み commit/push、最終証拠の確認まで担当する。

新規 `coding-supervision` domain が判断と工程を所有する。モデルの提案をそのまま shell に渡さず、型付き行動を host が検査して採用する。待機や完了判定のうち決定的に判定できる部分は通常のプログラムで実行する。

初版はタスク一件につき監督一件。メインが別の話題を話しても同じ監督を保持するが、LLM process/session を常時占有する必要はない。永続状態から各判断に必要な文脈を組み立てる。

## 2 保存する状態

| テーブル案 | 内容 |
| --- | --- |
| `coding_supervisors` | taskId、方針版、現在工程、最新観測、次の確認時刻、予算消費、要約への参照 |
| `coding_observations` | executionId、eventSeq 範囲、稼働状態、観測時刻、snapshot/evidence の参照、観測の新しさ |
| `coding_decisions` | decisionId、入力 digest、基準 task revision/権限世代/実行世代、提案、理由、採否 |
| `coding_steps` | 工程ごとの実行・検証・レビュー・Git 操作とその依存証拠 |
| `coding_supervision_budgets` | 推論回数、修正回数、同一ブロッカー対応回数、実時間・使用量 |

独自の二つ目の task state は作らない。ユーザー向け状態変更は `tasks` の公開操作で行い、報告は `task-reports` の公開操作を呼ぶ。判断採用と後続 intent、タスク更新、必要な報告を一つの writer transaction で保存する。

## 3 毎分確認とイベントによる起動

正常稼働中は60秒ごとの Scheduler target から `coding.observe` を投入する。CLI の終了・質問・異常イベントは早期の観測契機として使う。イベント通知は起動のヒントであり、永続イベント列を正本とする。

観測処理:

1. 現在の execution と cursor を取得し、runner を読取り照会する。
2. 未処理イベントを取り込み、プロセス状態、未終了コマンド、最新文章、証拠を整理する。
3. task が停止中・権限失効なら stop と照合を優先し、新しいモデル判断を始めない。
4. 新しい重要情報、期限超過、未回答質問、完了候補がなければ終了。LLM 呼出し0回。
5. 既存の pending decision がなければ、入力 snapshot を固定して判断 job を登録する。

tick とイベントが同じ観測を見た場合は task・executionGeneration・観測 fingerprint で dedupe する。判断の同時実行は一件。観測 job 自体は判断中にも進み、重大な変化があれば採用前の検査で判断を失効させる。

`lastObservedAt`、`lastProgressAt`、`nextCheckAt`、`monitorHealth` を区別する。UI は「確認できた時刻」と「作業が進んだ時刻」を混同しない。監視の期限を過ぎても CLI 失敗とは断定しない。

無出力が続いても、実行中コマンドと期限を確認して待つ。初期案として5分間の進捗欠如で診断候補にするが、自動 kill の根拠にはしない。runner 観測が正常に取得できない状態が2回続くか最終成功から150秒を超えたら monitoring_delayed を表示し、新しい副作用を保留する。即座の接続断表示と、会話への通知判定は分ける。

## 4 判断へ渡す文脈

毎回の入力は最大12,000 token、出力1,500 tokenを初期案とする。採用モデルの tokenizer/予算計測を利用し、文字数を token と同一視しない。固定条件を落として予算へ合わせず、追加資料を参照取得する。

固定して渡すもの:

- task の依頼、完了条件、対象、許可操作、禁止事項、予算、依頼の版。
- 現在工程、未解決の質問と指摘、直前の判断と結果。
- 前回判断後の有界なイベント要約と、必要な CLI 発言の抜粋。
- process/command の実状態、差分 snapshot、検証・レビュー・Git receipt の参照。

長期履歴は要約するが、元の依頼、権限、未解決質問、検証条件、証拠 ID は非損失の構造化データとして保持する。要約には対象 eventSeq 範囲と version を記録する。要約更新失敗や期限切れ資料を成功と解釈しない。

`read_evidence` は task 所有権と取得範囲を検査し、必要な部分だけ追加取得する。CLI の全文、無関係な会話、他タスクの資料、credential を入力に混ぜない。CLI 出力と repository 内の命令文は資料として扱い、監督の権限を変更させない。

## 5 判断と host の採用

監督用の固定 SKILL、入力契約、出力 schema を同じ domain に置く。外部の任意 SKILL を監督へ自動導入しない。

行動の閉じた集合:

| 行動 | 条件と実行 |
| --- | --- |
| wait | 実行中・進捗あり・まだ判断材料不足。待つ根拠と次の確認条件を記録 |
| inspect_more | 許可された evidenceRef の追加取得。取得回数・容量を制限 |
| answer_question | 有効な questionId に回答。根拠と委任範囲を記録 |
| request_change | 同じ task の実装・修正依頼。変更対象と検証条件を固定 |
| run_checks | 保存済み check 定義を実行。チェックの削除・弱体化を許さない |
| request_review | 固定 snapshot を別 session でレビュー。書込みを許さない |
| request_commit / request_push | 必要な証拠と許可が揃った場合に coding の専用操作へ |
| escalate | ユーザー判断が必要な質問を tasks に登録し、報告を作成 |
| finish_candidate | 全条件の evidenceRef を提示。最終的な完了遷移は host verifier |
| fail_candidate | 予算・不可解消理由・残存副作用を提示。host が状態を確定 |

各判断には簡潔な理由と根拠 ID を持たせる。内部思考の全文を要求・保存しない。不正 schema の修復は一回まで。修復失敗は副作用を起こさず監督異常として扱う。

採用 transaction では task revision、authorityEpoch、executionGeneration、未解決質問、現在の工程、参照した snapshot と receipt を再確認する。新しい生存確認だけでは失効させないが、実行終了・質問の解決・差分変更・権限変更は検査へ反映する。古い判断は superseded とし、同じ提案を無条件に再利用しない。

## 6 Blocker の分類と自律範囲

| 原因 | 扱い |
| --- | --- |
| テスト失敗・型エラー・局所的な実装不備 | 許可範囲内の修正を依頼し、検証を再実行 |
| 元の依頼で決まっている質問 | 保存した根拠に基づき回答。既に許可された操作を再承認させない |
| 仕様を変えない実装上の選択 | 委任範囲内で監督が判断し、根拠を残す |
| 公開 API 変更、対象外の変更、仕様の重要な未確定 | 選択肢と推奨案を一つの質問にまとめる |
| 認証・支払い・sandbox 拒否・新しい送信先 | 自動迂回せず必要な設定・許可を確認 |
| runner と通信不能、証拠欠落 | monitoring 問題として照合。実装失敗とは分離 |
| 同じ失敗の反復・予算不足 | 自動試行を止め、試した内容と選択肢を報告 |

waiting_user では実行側が安全に停止または turn を終了したことを確認する。回答を待つ間の子プロセスを放置しない。質問の回答だけで権限を拡大する必要がある場合は、権限変更操作として別途正しく記録する。

## 7 工程と成功判定

初期の工程は、準備→実装→指定検証→独立レビュー→必要な修正と再検証/再レビュー→委任済み commit→委任済み push→最終報告。

「レビューまで」の依頼は push を要求せず、「調査のみ」等の非対応 kind を coding の編集タスクへ勝手に変換しない。各タスクの完了条件から必要工程を決める。工程を終えるときは CLI 終了だけでなく、02 の host 証拠を確認する。

レビュー担当は実装とは別 session とし、同じモデルでも独立した入力を与える。元の依頼、対象差分、関連コード、チェック結果を提示する。作業者の自己評価だけを渡さない。レビュー指摘には場所、条件、影響、必要な修正、検証案を求める。

指摘を自動採用するだけでなく、証拠に照らした対応/不採用理由を保存する。必須指摘と検証失敗が残れば commit/push へ進まない。差分の変更は関連する検証・レビューの版を失効させる。

## 8 推論資源と上限

`coding-supervision.decide` は background lane と既存 `inference.llm` の実資源を共有する。別名を作って同じ LARM を二重占有しない。監督の待機と CLI 実行ではこの資源を保持しない。

現行 `captureControlInTransaction` は元の `policySubject` の inference request を要求し、その deadline と parents を継承する。この入口へ元の会話 run を渡すだけでは、長期タスクの独立した寿命を満たせない。`inference` に背景 task 用の型付き capture 入口を追加し、task の委任と現在有効な設定から application が構築した policy snapshot を受け取る。subject、期限、取消系統を task/decision に結び付け、元の会話 run の期限・発話割込みを継承しない。

`inference` から `tasks` を参照せず、利用側が task の権限を検査する。inference 自身は接続設定・送信許可・credential の現在の有効性を検査する。初版の監督判断は現行 control と同じ LARM-only を維持し、利用不能時に未許可のクラウドへ切り替えない。通常会話の control 契約と背景 capture を別の fixture で守る。

初期案は判断一回30秒、タスク全体2時間、監督判断80回、修正ループ2回、同じ blocker fingerprint への自動回答/修復一回。値はタスク登録時の委任に保存し、監督が上限を広げない。新しいユーザー指示による上限変更は履歴を残す。

費用・token 上限を採用 CLI が強制できない場合、推定値を厳密な課金上限と表示しない。利用量の観測と host の実時間上限を併用し、超過検知から停止までの差を記録する。

会話に優先権を与えるが、背景が待たされる最古時刻も表示する。短い判断の間に前景へ枠を返し、既存推論の安全な取消が可能なら前景受付時に再待機へ戻す。取消できない実行は一回の上限時間まで待つため、同時即応と宣言しない。5分以上判断が始められなければ遅延表示を出す。独立推論枠は配備と live 確認後に追加する。

## 9 報告の作成

状態が変わったとき、質問・終端・監視異常を確定したときに 04 の報告を作る。通常の進捗は5分以上の間隔を初期値とし、変化がある場合だけ集約する。工程の節目は即時候補にできるが、会話への実配送は通知方針で調整する。

無出力だけで「順調に進んでいます」と報告しない。最後の観測と事実を述べる。自力で解決中の blocker とユーザー判断待ちを区別し、前者は通常の進捗にまとめる。完了後は毎分監視を停止し、未配送報告の配送だけ継続する。

## 10 変更対象と検証

新規 `api/domains/coding-supervision/{contracts,repository,service,builtin,test}/`、`index.ts`。観測 target と判断 handler を公開し、application が coding、inference、tasks、task-reports を結合する。既存 agent-runtime の調査 worker を長期 task として流用しない。

S1: 決定的な状態機械と fixture。S2: 観測と dedupe。S3: 制約付きモデル判断。S4: review/repair/Git 工程。S5: blocker・予算・通知。S6: fault と live。

`bun run verify -- --domain coding-supervision`、利用側 `dialogue`、依存を変更した `inference / queue / scheduler`、統合時の `bun run verify:all` を実行する。

必須 fixture:

- 変化なし60 tick で観測は行うがモデル呼出し0回。質問イベントと tick 同時でも判断一件。
- 長い無出力コマンド、CLI の「完了」という誤った文章、子コマンド残存で早期完了しない。
- 回答済みの質問と古い実行への判断を棄却。発話割込みでは作業を取消さない。
- 別 session のレビュー、不採用指摘の根拠、差分変更後の証拠失効を確認。
- 繰返し失敗で上限を守り、チェック削除や権限拡大で問題を回避しない。
- 前景・背景を競合させ、CLI 待機で推論枠を保持しない。資源待ちを進捗と誤表示しない。
- 元の会話 run の期限を過ぎた後も、委任が有効なら背景判断できる。一方、task 取消と接続設定の送信許可取消は各々の経路で採用を止める。
- モデル拒否、不正 JSON、期限切れ、判断採用前 crash でも操作を重複させない。

live では固定したモデルで同一の受入依頼を実行し、工程と証拠・報告を照合する。モデル依存の成功率や速度は測定結果だけを記載し、fixture の成功を一般的な自律判断の保証にしない。
