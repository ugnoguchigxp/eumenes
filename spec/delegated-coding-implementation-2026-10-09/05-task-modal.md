# 会話画面のタスクモーダル実装計画

作成日: 2026-10-09 JST。状態: 実装前。[全体計画](README.md) の P1、P3、P5、P6 を担当する。状態と API は [01](01-tasks-and-queue.md)、報告と回答は [04](04-conversation-and-reports.md) を正本とする。

## 1 目的と画面の位置

会話を主画面のまま維持し、既存の設定ボタンの近くに「タスク」ボタンを追加する。ボタンから大きめのモーダルを開き、Kanban と一件の詳細を見られるようにする。常設の管理画面や別の会話への移動を必須にしない。

会話で登録された task と手動登録した task を同じ一覧に表示する。初版は現在の単一利用者のタスク全体を対象にし、カード/詳細に元の会話を示す。内部 agent task、Queue job、音声処理 job はカードとして列挙しない。

前の検討で作成した操作可能な画面案は、メニュー、4列、詳細、質問回答、登録、閉じる操作の参考。サンプル表示は製品実装ではなく、本書の状態・API・権限・アクセシビリティ契約を実装時の正本にする。

## 2 Kanban の状態投影

| 列 | task state | 表示上の区別 |
| --- | --- | --- |
| 待機 | registered、queued | 登録済み/開始待ち/実行枠待ち/前提待ち |
| 進行中 | active、stopping | 実装中、検証中、レビュー中、commit中、push中、停止要求中 |
| 確認・保留 | waiting_user、paused、reconciling | 回答待ち、一時停止、実行結果を確認中 |
| 終了 | completed、failed、cancelled | 完了、失敗、取消を別 badge と文言で表示 |

監視遅延・接続断は、元の作業状態に重ねた表示とし、failed へ勝手に移さない。観測の古さが分かる最終確認時刻を付ける。状態不明なのに「実装中」と断定する表示は避け、「最終確認時は実装中」とする。

カードはタイトル、対象プロジェクト、現在工程、最新の意味のある変化、最終確認時刻、質問の有無を持つ。根拠のない進捗パーセントや残り時間は表示しない。

初版は状態をドラッグで変更しない。特に「完了」へ手動移動して検証を省略できないようにする。優先順変更が必要になったら、別の業務操作と API として追加する。

終了列は最新の少数件と続きを取得する操作にし、全履歴を一度に読まない。列の総件数は server の集計 DTO を使い、取得済みページ数から全件数を推定しない。カード順は待機が受付順、進行中・保留が重要な更新順、終了が終了時刻順を初期案とする。

## 3 メニューと通知

「タスク」ボタンには未解決のユーザー判断待ち件数を表示する。未読の完了報告は別の印で区別し、すべての更新を一つの未読件数に混ぜない。メニューを開いただけで質問を解決済みにしない。

タスク完了や blocker は会話にも 04 の規則で届く。会話メッセージの task 参照から該当カードの詳細を直接開ける。会話とモーダルで別の質問状態を持たない。

モーダルを閉じる操作は閲覧を終えるだけで、実行・監督・Schedule を停止しない。停止は詳細の明示操作として用意する。

## 4 タスク詳細

モーダルの中で一覧から詳細へ切り替え、さらに別のモーダルを重ねない。「一覧へ」で元の選択・位置へ戻る。

詳細は以下の順序を基本とする。

1. タイトル、状態、対象プロジェクト、現在の工程、最終確認時刻。
2. ユーザーへの質問があれば最上部に質問と回答欄。
3. 元の依頼、完了条件、任せた範囲、実行先 branch/remote の安全な表示。
4. 監督担当の最新説明と次の予定。メイン会話へ届けた内容との区別。
5. 実装、試験、レビュー、修正、commit、push の作業履歴。
6. 変更ファイル、差分、試験・レビューの結果、成果への参照。
7. 必要な場合だけ開く CLI 出力の抜粋と、追加読取り。

「監督担当」と「作業担当」はユーザー向けの名前で表示し、jobId、MCP、lease 等の内部用語を通常操作へ露出させない。診断用 ID はコピー操作等の詳細領域へまとめる。

履歴は cursor で追加取得する。生出力は常時描画せず、有界な範囲を読む。ANSI・制御文字・HTML を無害化し、リンクの実行や shell の自動実行を許さない。秘密を UI で隠すだけにせず backend から除去する。

試験結果には未実施・成功・失敗・中断を明示する。レビュー済みでも現在の差分が変わっていれば失効を示す。push 結果不明なら commit 済みと区別する。

## 5 登録と着手

「登録」から同じモーダル内のフォームを開く。必須は依頼内容、対象プロジェクト、完了条件、実行範囲。タイトルは補助し、登録のみと着手を分ける。

実行範囲は「実装・検証・レビューまで」「commit まで」「指定ブランチへの push まで」のように業務上の区切りを示す。push を含む場合は remote と branch を明示し、登録済み候補から選ぶ。CLI executable、任意 path、shell flags の入力欄はここに設けない。

workspace の登録・CLI の準備は別の設定領域で管理する。ブラウザーのファイル選択だけで runner の filesystem 権限が得られるようには扱わない。未準備なら理由と設定への導線を示し、作業を開始しない。

フォームからの再送は一つの requestId を維持する。通信 timeout では ID で照会し、「失敗」と決めつけて新規 task を追加しない。受付成功後に server の taskId と状態へ切り替える。

会話からの委任も同じ API を使う。登録済みの task を会話に表示するとき、UI が独自にもう一件作らない。会話で明確に着手を頼まれた task に、モーダルで再度開始させる手順を追加しない。

## 6 回答と制御

回答は taskId、questionId、expectedRevision、requestId を送り、server が受理した結果を表示する。自由文と選択式は質問 schema に従う。送信中は二重クリックを抑えるが、正しさは server 側の冪等性で保証する。

会話で先に回答済みなら、モーダルは「既に回答済み」と最新状態へ更新する。古い質問への回答を新しい質問へ転用しない。権限拡大が必要な回答は変更内容を明示し、通常の質問回答と取り違えない。

停止操作は「一時停止」と「取消」を区別する。一時停止は実行停止確認後に paused、取消は確認後に cancelled。押した直後は「停止要求中」とし、結果不明なら「停止を確認できていません」と表示する。いずれも変更ファイルを元へ戻す操作ではない。

再開は server が返す利用可能操作に従う。result unknown の task に通常の「もう一度実行」を出さず、照合や確認を優先する。停止・再開・範囲変更は画面上だけで状態を確定しない。

## 7 データ取得と UI 状態

TanStack Query は task API の表示 cache、ローカル UI state は開閉・選択 task・フォーム下書きだけを保持する。業務状態を Zustand 等へ別の正本として複製しない。

既存の共有 SSE を使い、保存確定後の変更で一覧・badge・選択中詳細を再取得する。毎分の CLI 監視をブラウザーの timer に置かない。モーダルを閉じたら詳細の購読を外し、会話側で必要な badge の軽量更新は共有接続で続ける。

heartbeat だけで全件再取得しない。大量出力の一行ごとに画面を更新せず、backend の更新通知と query invalidation をまとめる。再接続/reset 時には最新 snapshot を読み直す。401/403 は既存規則に従い自動再試行を停止する。

操作結果の古い HTTP 応答が新しい SSE の状態を上書きしないよう revision と実行世代を検査する。該当 task の資料が削除・期限切れなら、カードを消して成功扱いにせず説明を残す。

## 8 レイアウトとアクセシビリティ

既存 design-system の Button、Badge、Input 等を使用し、modal が不足する場合はアプリ内のアクセス可能な共通 primitive を追加する。汎用 design-system package の不要な全面改修はしない。

desktop は4列を基本とし、狭幅では2列または状態別の縦一覧へ変える。長いタイトル、日本語、長い branch 名でも横にはみ出さない。モーダル内の高さとスクロールを管理し、会話側のスクロールを固定する。

dialog 名、aria-modal、focus trap、背景 inert、Escape、元ボタンへの focus 復帰を実装する。質問と送信結果は aria-live で伝えるが、毎分の時刻更新を読み上げ続けない。色だけで状態を区別しない。

編集中のフォームを閉じる場合は下書きを保持する。閉じただけで task を作成しない。音声入力中であることは見える状態にし、モーダルの回答欄と通常の会話入力へ同じ発話を二重送信しない。モーダルを開いたことを実行承認として扱わない。

## 9 変更対象と工程

- 新規 `web/src/domains/tasks/{index,api,hooks,TaskModal,TaskBoard,TaskDetail,TaskRegistration,TaskQuestion}.tsx/ts` と近接する試験。実装時は機能単位で過度な巨大ファイルを避ける。
- `web/src/App.tsx` のタスクメニュー、既存設定ボタンとの配置、会話内 task receipt/report 表示。
- `client/tasks.ts`、`web/src/queryKeys.ts`、SSE の query 更新、UI エラー文言。
- 必要な登録 workspace/CLI 設定 UI、`tests/browser/tasks.spec.ts`。

U1: fixture DTO で一覧・詳細。U2: API と SSE。U3: 登録・質問回答・停止。U4: 会話からの直接表示・badge。U5: 狭幅・accessibility・音声。U6: live 受入。

## 10 検証と完了条件

Web 所有パスを `tasks` domain に登録し、`bun run verify -- --domain tasks` と、変更した `settings / dialogue / voice-dialogue` を実行する。ブラウザー fixture を `verify:all` の gate へ追加する。

- メニュー→Kanban→詳細→一覧→閉じる→再表示で選択と状態が整合する。
- registered/queued/active/waiting_user/paused/reconciling/stopping/各終端が正しい表示になり、終了列の失敗と完了を区別する。
- Queue の観測 job が終了してもカードが完了列へ移らない。
- 登録の二重クリック・timeout・再読込みで重複 task が作られない。
- 会話と UI の同時回答、停止中の完了、古い API 応答と新しい SSE を競合させる。
- モーダルを閉じても task が進み、再接続で最新状態へ追いつく。停止未確認を cancelled と表示しない。
- 320px、tablet、desktop、light/dark、キーボードのみ、スクリーンリーダー向け名前を確認する。
- 長い出力、切詰め、期限切れ、HTML/制御文字、秘密の fixture を表示し、安全性と可読性を確認する。
- 実ブラウザーで別の会話を続けながら、進捗・質問・完了を確認し、モーダルからの返答で監督が再開する。

画面案の操作確認は製品 API・実 CLI の受入とは別に記録する。見た目だけの完成でタスク機能を有効化しない。
