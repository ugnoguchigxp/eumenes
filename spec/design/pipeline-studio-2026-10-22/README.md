## 採用した画像と生成指示

- [制作画面](creation-concept.png) — [生成指示全文](creation.prompt.txt)。入力、4つの手順、完了時の回答を縦に表示。②の取り出し方を展開。青いラベルで入力・前の手順の結果を示す。
- [試験画面](trial-v2-concept.png) — [生成指示全文](trial-v2.prompt.txt)。言い方による選択の確認と、疑似データでの手順確認。11〜12分から11分を取り出し、タイマーの依頼へ渡す。

いずれも768×1152pxのPNG。この寸法は画像案の基準であり、製品の固定幅ではない。暗色の背景とカード、青いアクセント、細い境界線、小さなタブを既存のEumenesに合わせた。

## 意図と既存機能との関係

- 通常は「手順」「試す」を開き、JSONの直接編集は詳細メニューから開く想定。
- 手順の意味を変える編集は既存の対話と作業文書の仕組みを使う。カード上での直接編集は今回の画像に含めない。
- 灰色の接続線は実行順、青いラベルはデータ参照。曲の雰囲気は利用者の入力から受け取り、タイマーの出力からは受け取らない。
- 数値を取り出す処理も独立した手順として確認できる。
- 試験画面の合格・値は説明用のサンプル。実際の検索、タイマーの起動、楽曲生成を実施した結果ではない。
- 「公開」は既存の操作を示す。今回の作業でパイプラインを公開していない。

## 生成・確認記録

プロジェクトの指示に従い、保存済みLARM設定をbackendのsettings domainの読み取り専用操作で取得。catalogからcapability `media.image.generate`、protocol `larm.image-generation.v1` を持つサービスを発見し、発見・確保応答のURLとdescriptionを確認して既存の生成機構を使用した。Profile名・モデル名は固定していない。参照画像の編集には対応していないため、既存画像を目視し、テーマと構図を文章で指定して新規生成した。

- 制作画面1回、試験画面2回の計3回。各回、生成HTTP200、取得成功、接続解放HTTP204を確認。
- 試験画面初稿の `trial-concept.png` と `trial.prompt.txt` は検討履歴。カードが明色になり、ローカルタブと入力参照の描写も不十分だったため、最終成果物には使用しない。
- 再生成では暗色カード、独立したローカルタブ、入力参照の指定を強化。配色とタブの改善を目視確認した。
- 3ラウンド後の見直しでは、アーティファクトの枠、4手順、値の受け渡し、疑似データの明記が揃ったため追加生成を終了した。
- 両採用画像を目視し、768×1152pxであることを確認。小さな文字やラベル内の字形・アイコンには生成の揺れがある。曲の雰囲気の参照元は元の入力であり、画像内のラベルの細かな描写を内部参照の仕様として採用しない。
- 今回追加の `context_compile` は0回、`compile_eval` は0回。前ラウンドの調査と承認済みの画面案を使用した。

今回の差分はこのフォルダ内の画像・生成指示・記録のみ。製品コード・設定・DBの変更とサーバー操作は行っていない。製品の挙動を変更しない画像案のため、domain verify・結合試験・ブラウザE2Eは省略した。
