# Eumenes 開発監督の設計案

2026-11-22 ｜ **第4稿・利用者承認済み。初版の実装と隔離環境での検証結果を §7 に記録**

「集計処理の試験を走らせる間に、入力処理と既存テストを読んで、どの条件で行が欠けるか調べて」と頼む。集計の試験は編集枠を使う検証専用の子が、入力処理の静的読解は読取り枠の子が受け持つ。後者にも再現試験が必要になれば、Eumenes は「該当箇所は特定済み。再現は編集枠待ち」と答えられる。その間も利用者は別の話を続けられる。

**これまでの合意**は、会話の人格を一つに保つこと、Memory・World・Goals の正本を共有すること、Git worktree を作らず同じチェックアウトで作業の重なりを減らすこと、Claude Code への実装依頼に先立って調査と設計を行うこと。初版の同時実行は、同じ作業場所で編集枠一件と静的読解一件までとする。利用者は、子仕事の枠解放と実際のソース修正の受入条件を明記した上での実装を承認した。

## 2. 誰が何を決めるか

| 担当 | 判断・操作 |
| --- | --- |
| 会話エージェント／Agenda | 利用者との対話、日常の調べ物、興味、目標、目標間の優先順位を担う。開発依頼を既存の能力検索から委任し、進捗照会・条件変更・停止を元の仕事へ届ける。利用者に話しかける窓口もここに置く |
| 開発監督 | タスクを分け、設計書の受入条件を定め、結果がその条件を満たすかと、他タスクへの影響を判断する。判定済みの試験結果は参照し、設計変更・証跡不足・タスク間の競合があれば介入する |
| Claude Code の既存担当と runner | 一件の依頼書に沿って実行し、経過・質問・停止を扱う。既存の担当 LLM が追加実行・質問・終了を選び、終了時に実行済みであることと証跡参照を照合する。その判断と証跡を監督に返す |
| 本体の台帳とキュー | 参照・権限・世代の検証、依存待ち、実行枠の予約、再配送、取消、状態保存を行う。どの資料が有用か、重なりをどう解くか、成果が依頼を満たすかは担当 LLM が判断する |

監督には依頼、受入条件、関係する共有情報、同じ作業場所の進行中タスク、利用可能な操作だけを渡す。Memory は過去の決定と理由、World は対象間の関係、Goals は利用者が採用した目標と版を返す。各 domain の公開操作で、元依頼に許された参照だけを解決する。監督の調査結果・仮説はまず仕事の記録に置き、永続記憶や World への採用は既存の担当に渡す。短い開発依頼は仕事として直接受け付け、登録目標の枠を消費しない。[会話からの委任](conversation-first-toolchain-2026-11-21.md) · [Memory の責務](../docs/memory.md) · [World の照会契約](../api/domains/world/contracts/query.ts) · [Claude Code の判断と証跡照合](../api/domains/claude-code/lifecycle.ts)

## 3. 下調べから Claude Code への引き渡し

1. **設計を左右する問いを決める。** 依頼と共有 Memory を読み、現行コードの入口、既存の機構・公開契約、代表的な試験、他タスクの変更予定を調べる。「どこに組み込み、何を再利用し、何で達成を確かめるか」を根拠付きで説明できたら設計に進む。静的読解で決着しない問いは未確認と記す。再現が設計の前提なら、先に検証項目を記した短い調査依頼書を確定し、許可されたコマンドを編集枠で実行する。
2. **共用の調査能力を使う。** 外部仕様や実践例は会話と同じ Codex 検索 `web.note`、過去の判断は Memory、リポジトリの事実は `inspect.source` に照会する。SkillSmith の接続は実装段階②に置き、接続後は設計書を確定する前に適合する手順を問い合わせる。独立した問いは並行に扱う。出典と適用条件が今も有効なメモは再利用する。
3. **根拠を短いメモにする。** Web は出典・取得時点、SkillSmith は採用した手順・版または digest・適用理由、コードはパス・関数・基準コミットと根拠箇所の内容 digest を残す。コード調査は未コミット変更を含む取得時の内容を読む。外部検索に渡す問いは公開情報に絞り、ローカル差分はソース調査で扱う。[Codex 検索](web-note-codex-search-2026-11-11.md) · [ソース調査の実装](../api/application/web-note/codex-source-inspect.ts) · [SkillSmith の既存接続](../api/application/knowledge/specialist-guidance.ts)
4. **一つの設計書を保存する。** Agency の公開契約で生成・検証し、本体の文書ストアに保存する。会話で閲覧する Markdown と Claude Code に渡す Markdown は、同じ文書 ID と本文 digest を使う。コード・World・SkillSmith の資料は原典へ戻れる調査メモにし、設計に渡した資料すべての出典と版を保存する。
5. **Claude Code は着手時に現物を確かめる。** 起点と関係する差分を読み、実装方法、呼び出し元、例外処理、必要な追加試験を詰める。設計後に別タスクが動いていても、前提と許可が有効なら続行する。変更範囲や受入条件に影響する差は監督に返す。

### 設計の生成・検証と保存の契約

| 境界 | 現状 | 提案する契約 |
| --- | --- | --- |
| Agency の入力と出力 | `GoalDesignInput` は `StoredGoal`、`workspace`、`analysis`、目標計画型に結び付く `brief`、Memory、メモを必須とする。`validateDesign` は現行の公開入口に含まれない | `eumenes-agency/agenda/runtime` から目標に依存しない `DesignInput`、その型を受ける生成関数、`validateDesign(input, output)` を公開する。入力項目は `purpose, workspace, analysis, brief, memory, notes`。依頼は作業名・本文を持ち、既存の目標用関数は `StoredGoal` をこの入力に変換する。検証は入力中の `note:`・`memory:` だけを許し、`ready` は本文必須・不足理由なし、`blocked` は不足理由必須・本文なしとする。本文上限 4,000 字と推論の注入を保つ。[配布版の入力・検証・公開範囲](../vendor/agency/goal-runtime-adoption-source.patch) |
| 本体の保存と閲覧 | 目標経路は会話の空きを判定し、進行中の会話で文書を開始して目標ストアに登録する | 本体の組立時に監督用の Markdown 生成文書 owner を一度登録する。保存時は元依頼の会話 ID・親仕事 ID に設計版と根拠参照を結び、同じ writer で `generated.startInTransaction` に版ごとの文書 ID と本文を渡す。閲覧可能な保存結果を確認して委任可能にする。閲覧・委任の双方で本文 digest・出典・忘却を検査する。登録目標がなく会話中でも進められる。[現行の目標保存](../api/application/agency/goal-agenda.ts) · [本体の生成文書ストア](../api/domains/markdown/service/generated.ts) |

この公開契約を備えた Agency の新配布版を本体に取り込むことが段階①の前提になる。旧版のまま仮の登録目標を作る運用は採らない。長い資料は版付きの参照にし、受入条件だけで本文上限を超える場合は仕事を分ける。[配布版の照合方法](../vendor/agency/manifest.json)

**Claude Code が受け取る依頼書**

| 項目 | 記載内容 |
| --- | --- |
| 目的・受入条件 | 利用者が得たい結果、観測方法、成功と判断する条件 |
| 現状・方針 | 確認済みの挙動、採用理由、読むべきファイルと関数、版付きの根拠 |
| 作業範囲 | 編集を認めた範囲、関係する他タスク、順番を合わせる箇所 |
| 検証・裁量 | 必要な試験・成果物、実装担当に委ねる選択、監督に戻す未確定事項 |

冒頭の例なら、集計の依頼書には試験コマンド、固定入力と期待件数を書く。入力処理の担当は、調べた分岐・該当テストと、実行しないと判定できない条件を分けて返す。

## 4. 仕事の正本と Kanban

会話の `dialogue_work` は元依頼につき一行で、状態は `todo / waiting / done`。親子関係の列はない。既存の `sourceRef` が指す監督 owner に、タスク ID、任意の Goals 参照、設計版・対象範囲、子の仕事／実行 ID、受入証跡と判断理由を持つ。初版の先行指定は同じ親の登録順で前のタスクを一件までとし、作成時に固定する。これで相互待ちを構成できず、汎用の循環探索は要らない。CLI の状態は子の owner の公開操作で読む。[仕事台帳の行と結果型](../api/domains/dialogue/repository/work.ts) · [登録 task の参照](../api/domains/dialogue/service/work-dispatch.ts) · [台帳の報告契約](../api/domains/dialogue/service/work-ledger.ts)

会話の進捗照会とボードは、監督の同じ公開ビュー（タスク ID・版・状態・理由・結果・証跡参照）をそれぞれ一回の読取りトランザクションで取得する。同じ版なら両方に同じ状態と理由が出る。下表の台帳列は**親一件への報告**、ボード列は**個々のタスクの表示**である。[Claude の状態型](../api/domains/tool-runtime/contracts/task-execution.ts)

| 監督の状態と理由 | 子の Claude 担当の状態・監督の観測 | 会話台帳への対応 | Kanban の監督行 |
| --- | --- | --- | --- |
| 待機 | 子なし／`queued`。先行の受入待ち・編集枠待ちなど、理由がある | `todo` | 未着手列に「編集枠待ち」等 |
| 実行中 | `deciding`、または `waiting_child` で実行を観測。子が `completed` でも受入前なら「受入確認中」 | `todo` | 進行列に実施中の工程 |
| 保留 | `waiting_user` の有効な質問（提示待ち／回答待ち）、検証失敗後の再計画、依存失敗、`stopping`、自分の停止未確認、または新規起動を妨げる「他タスクの停止未確認」 | 親に提示中の質問が一件あれば `waiting`。内部調整・停止確認だけなら `todo` | 進行列に対象・理由・再開条件 |
| 終了 | 子の `completed` と受入成功で「完了」。`partial / failed / cancelled / interrupted` は監督が再開・停止確認の要否を確かめて該当結果を確定 | 親全体を確定した時だけ `done` と `succeeded / partial / failed / cancelled / interrupted` | 終了列に「完了」「一部達成」「失敗」「取消」「中断」のいずれか |

親が開いている間は、いずれかの子の質問を提示中なら `waiting`、それ以外は `todo` とする。一方の試験が失敗し、その実行の停止を確認できた場合、両画面に「A は検証失敗・再計画中、B は静的読解中」と表示できる。停止を確認できず、兄弟の次の起動が保留になる場合は §5 の理由を表示する。全件受入なら親は `done/succeeded`、一部だけ受入で終了なら `done/partial`。親全体の取消・中断には該当する結果を使い、すべて失敗で終了なら `done/failed` とする。

現行の `query:kanban.board@1` は手動カードの終了ラベルに `done / blocker` を持つ。ボード照会の次版に監督の `supervisedRows` を追加する。既存の `cards[].label` はそのまま読み、Web は監督行も同じ三列に描く。監督行の終了時には `outcome` を必須とし、上表の五つの結果名に対応させる。[ボードとカードの現行契約](../api/domains/kanban/contracts/index.ts)

| ボード上の対象 | 報告先と操作 |
| --- | --- |
| 監督の行 | 重要な進展・質問・最終結果は元の会話へ一度配送する。照会・条件変更・取消は親仕事と対象タスクの ID・期待版で同じ owner に届く。監督行から commit／push を起動する操作は設けない |
| 手動カード | 既存の Kanban owner が扱い、完了報告は通知センターに届く。commit／push は対象カードで人が既存の確認操作を行う。監督行の表示に伴うカード作成や再投入は行わない。[既存ボードの契約](../docs/kanban.md) |

### 二つの子が同時に質問したとき

親台帳にある `question_id` は一件分。監督は子の質問を受けた順に永続化し、先頭の一件だけを親に提示する。質問には親・タスク・子仕事・両世代・子質問 ID と、runner からの質問なら実行 ID を結び付ける。受付順は同じ writer が採番し、同じ子質問の再配送は同じ受付に戻す。会話で受理した回答は、提示中の親質問 ID からその一件にだけ配送する。回答受理・失効・取下げ時に次の有効な質問を選ぶ。親取消時は全件、条件変更時は旧世代の該当分を閉じる。[親台帳](../api/domains/dialogue/repository/work.ts) · [子の回答の照合](../api/domains/claude-code/task.ts)

現在は Claude 担当の `ask_user` も SDK の `AskUserQuestion` も、質問の発生時から最長15分で失効する。監督配下では両経路に「提示待ち」と「提示中」を設ける。提示待ちの間も仕事・許可・実行の絶対期限と中止信号は有効。**15分の回答時間は親台帳に質問を提示した時刻から**とし、絶対期限との早い方で締め切る。子担当の期限検査と runner の待機タイマーを両方この契約に合わせる。[担当が作る質問](../api/domains/claude-code/lifecycle.ts) · [期限の検査](../api/domains/claude-code/index.ts) · [SDK の質問](../packages/coding-runner/src/claude-engine.ts) · [runner のタイマーと返信](../packages/coding-runner/src/claude-service.ts)

提示時刻・締切・親質問 ID と子への提示通知を同じ取引に保存する。runner の通信契約に子質問 ID と締切を指定する提示操作を加え、提示通知、回答の順で再配送できるようにする。同一 ID の再送で締切は延びない。backend 再起動時は有効な質問と締切に再接続する。絶対期限切れや runner 停止で失われた回答先は閉じて次へ進む。配送を確認できなかった回答はその旨を親に記録し、再質問が必要なら、停止確認と現行許可の照合後、新しい質問 ID で受け付ける。[runner の現行通信契約](../packages/coding-runner/src/claude-contracts.ts)

## 5. 共有チェックアウトでどこまで並行にするか

監督は開始前に同じ作業場所のタスクを読み、編集予定のファイル・シンボル、公開契約、生成物、共有するテスト資源を見比べる。同じ domain に属するだけなら進められる。たとえば同じ型定義の変更を前提とする二件なら、型の変更を一方に寄せ、その型に依存する工程だけを待たせる。実行中に予定範囲が広がれば、判明した時点で調整する。全タスクの読取り範囲にロックを掛ける必要はない。

初版で同居できる組合せは **静的読解一件と、検証または編集一件**。枠は同時に走れる仕事を決め、操作許可は各子が使えるツールと対象を決める。再現・計測・試験・ビルドは編集枠を使う。

静的読解から検証へ移るときは、同じ監督タスク ID に読取りの証跡を保存する。Claude 担当は実行の停止を確認して**読取りの子仕事を終了し、その保持者・epoch の読取り枠を解放する**。監督は終了と解放の両方を確認してから、**新しい子仕事 ID** で検証工程を登録する。検証の許可を照合して編集枠を取り、新しい実行 ID で開始する。編集枠待ちの間、読取り枠は空いている。停止未確認なら元の保持行を残し、§5 の回復手順を使う。工程を再配送しても同じ後続の子仕事が一件だけ作られる。[子仕事の終了と枠解放](../api/domains/claude-code/lifecycle.ts)

| 実行経路 | 現状 | 初版の変更 |
| --- | --- | --- |
| workspace guard | `kanban_workspace_guards` は `workspace_ref` が主キーで一場所一行。`held / releasing / unknown` を保存する | **同じ台帳**を保持者単位（作業場所・owner・executor・epoch）にし、`read / edit / exclusive` を記録する。予約時に全保持者を同一 writer で照合する。照会・解放・回復は保持者を指定する。既存行は状態と epoch を保ち `exclusive` に移す。[スキーマ](../api/domains/kanban/repository/migrations.ts) · [予約と解放](../api/domains/kanban/repository/workspace-guard.ts) |
| Claude の task と runner | `hold` に枠の区別がなく、runner は実行中一件で次の開始を拒否する。`readOnly` で選ぶツールの上限は、読取り三種か、それに `Write / Edit / Bash` を足したもの | ホストが許可から決めた操作区分・枠・保持者・epoch を開始要求と受付証に結ぶ。操作区分は `read`（読取り三種、読取り枠）、`verify`（読取り三種と指定の Bash、編集枠）、`edit`（許可した編集・検証ツール、編集枠）。runner は実行ごとに枠の組合せ・ツールの上限を強制し、再送・セッション継続時にも操作区分と許可範囲を照合する。旧形式の直接依頼は `exclusive` として扱う。[task の接続](../api/application/work/claude-code-task-adapter.ts) · [runner の受付とツール上限](../packages/coding-runner/src/claude-service.ts) |
| 手動端末 | 起動・送信・修復が一件の guard を参照する | 従来の全面排他として、起動・送信前に全保持者と照合する。読取り中の新規起動は busy、停止・修復は自分の保持者だけを対象にする。[端末の予約と修復](../api/application/work/terminal-workspace.ts) |
| Kanban の手動カード | 担当別に一件を配送し、作業場所の guard とカードの所有者を照合する | 担当別キューを維持し、受付・配送・再照合は `exclusive` で同じ予約 API を使う。監督行は表示だけでは予約しない。[配送判定](../api/domains/kanban/service/queue.ts) · [実行の予約](../api/application/work/kanban-executors.ts) |
| Codex SDK の開発実行 | ホストの guard と SDK runner の作業場所ロック・受付証を使う | ホスト側は `exclusive` の保持者・epoch で予約と回復を照合する。SDK runner の作業場所排他は維持する。会話と共用する Web 検索はこの開発実行枠を使わない。[ホスト側の照合](../api/application/work/codex-task-port.ts) · [SDK runner](../packages/coding-runner/src/sdk-service.ts) |

**検証専用の実行。** 読取り三種は `Read / Glob / Grep`。各区分に共通する質問は §4 の経路で扱う。`verify` には `Write / Edit` を渡さない。ホストが許可した検証ごとに実行ファイル・引数・作業ディレクトリを確定し、既存の `PreToolUse` で、それに対応する固定の Bash 呼出しだけを許す。[現在の Bash 隔離条件](../packages/coding-runner/src/claude-service.ts) · [実行前の認可フック](../packages/coding-runner/src/claude-engine.ts)

シェルとその子孫には OS のサンドボックスを適用し、チェックアウト全体（追跡外のパス・`.git` を含む）を読取り専用にする。書込み先はチェックアウト外の実行 ID 専用の一時ディレクトリに限り、必要なキャッシュと成果物もそこへ向ける。許可済みの試験自身が行うソース書込みも実行時に拒否する。開始前にこの隔離を強制できない場合や、試験自体が作業場所への書込みを必須とする場合は、理由を添えて保留する。

同じ保持者・epoch・枠の再送は同じ予約を返す。保持中の枠変更・古い epoch からの解放は拒否する。異なる保持者間では `read + edit` だけが共存でき、取得順は問わない。`exclusive` は全枠が空いたときだけ取得できる。`releasing`・`unknown` が残る間はその作業場所の新規予約を保留する。全呼出し元の移行と runner の対応確認を終えてから並行モードを有効にする。排他の正本は改訂した既存 guard 一つ。runner のロックは実プロセスの二重起動を防ぐ。[11月15日設計の作業場所の排他](claude-code-managed-task-design-2026-11-15.md)

**他タスクの停止未確認。** 現行の Claude runner は、読取りを含む一件でも停止を確認できなければ runner 全体を隔離する。初版もこの範囲を採用する。子 A の停止が不明なら、同じ作業場所の枠を待つ B は「他タスクの停止未確認」と A の参照・再開条件を会話とボードに出す。すでに稼働を確認できている B は実行を続けられ、必要に応じて照会・停止できる。B に追加実行が必要になった時点でその起動を保留する。[runner 起動時・実行終了時の隔離](../packages/coding-runner/src/claude-service.ts)

回復には、該当する実行 ID・保持者・epoch に対して管理プロセス群の終了を確認した記録、または開始時に記録した同じホストの OS 起動識別子が変わった証拠を使う。runner にこの証拠を照合して受付証を停止確認済みにする操作を加え、ホストは同じ証拠で該当する `unknown` 保持行だけを解放する。再送で途中から完了できるようにし、未知の実行結果は「中断」として扱う。対象の未確認が全件解消し runner の受付が復旧した後、B の世代・期限・枠を再照合して一度だけ起動する。時間経過や backend の再起動だけでは解除しない。[guard の解放契約](../api/domains/kanban/repository/workspace-guard.ts) · [手動端末での OS 再起動の照合例](../api/application/work/terminal-workspace.ts)

未コミット差分には利用者の手作業も含まれる。開始時に対象箇所の状態を控え、編集直前と検証後に関係する入力の版を照合する。静的読解中に参照したソースが変わったら、その根拠だけを読み直す。同じ箇所を誰が変えたか判別できない場合は、その箇所の成果の採用を保留し、既存差分を残す。

## 6. 権限、再起動、完了判断

### 子を起動する権限

現行の Claude task は開始時に `messageId` を必須とし、`origin` 付きは拒否する。`inspect.source` も会話の出所を要求する。会話の条件変更・回答は実際の発言を照合する一方、内部の取消は会話 ID と仕事 ID を取る。どちらも背景の監督の権限を表す型ではない。[共通の型](../api/domains/tool-runtime/contracts/task-execution.ts) · [出所の検証](../api/application/toolchain/task-execution-sources.ts) · [Claude の受付と制御](../api/domains/claude-code/task.ts) · [ソース調査の受付](../api/domains/web-note/service/index.ts)

提案は `ExecutionSource` に、ホストだけが発行する次の判別可能な型を足すこと。親は元の発言・許可を保持し、子の `messageId` は `null` にする。呼出し先はホスト提供の専用検証を通し、会話、Agency 自律、workflow の既存判定を引き続きそれぞれの出所に適用する。

```ts
type SupervisedSource = {
  origin: "supervised"
  conversationId: string
  messageId: null
  runId: string
  request: string
  digest: string
  delegation: {
    grantRef: string
    parentWorkId: string
    taskId: string
    parentGeneration: number
    taskGeneration: number
  }
}
```

| ホストが照合する項目 | 正本と条件 |
| --- | --- |
| 親仕事・子の宛先 | `grantRef` から親、対象タスク、元の利用者・会話・許可、workspace、実行先の登録版を引く。呼出元がその親 owner に結び付く内部 port であることを検査する。子の受理後は発行済みの子 ID とも照合する |
| 依頼・設計 digest | 子の依頼本文の digest を照合する。設計前の参照調査はその依頼版と読取り操作にだけ許可を出す。設計後の実行は文書 ID・承認範囲にある本文 digest・現行版が一致するときだけ許す。設計のない許可で再現コマンドを起動しない |
| 許可操作 | 元依頼の許可から、子に必要な操作と対象を選ぶ。検証だけの許可には §5 の `verify`、許可したコマンド・引数・作業ディレクトリと対象版を結ぶ。worker の開始・継続時とツール呼出し時に範囲を検査し、隔離を適用できなければ「検証用の書込み制限を適用できない」と保留する。編集が必要と判明したら、監督が現行の許可を調べ直す |
| 世代・期限 | 親・対象タスクの保存世代、許可と子実行の期限、参照元の有効性を照合する。変更操作は期待版も検査する。親取消は全子、単一タスクの条件変更は当該タスクの許可を失効させる。兄弟タスクの通常進捗では世代を進めない。破壊的変更・本番適用・公開は該当する明示許可が必要 |

### `supervised` を受け付ける経路

段階①の最初に、`ExecutionSource` の出所を判定する全分岐を移行する。現行の `web.note` は `autonomous` だけを背景キューに入れ、他の出所は対話キューに入れる。実行参照の SQL にも `workflow` 以外をまとめて候補にする箇所がある。ホストの共通入口で、出所省略（会話・専門セッション）、`autonomous`、`workflow`、`supervised` を発行元と照合する。各受付では `supervised` を明示的に扱い、専用検証を持たない操作は拒否する。未知の値や、監督用の委任参照を持ちながら出所が欠落した入力も拒否する。[出所検証](../api/application/toolchain/task-execution-sources.ts) · [Web 調査のキュー選択](../api/domains/web-note/service/index.ts) · [実行参照の検索・閲覧](../api/domains/agent-runtime/service/execution-access.ts)

| 境界 | `supervised` の扱い |
| --- | --- |
| 登録能力の受付・配送 | 段階①は `web.note` と `inspect.source` の参照調査、②からは管理下の Claude task を、親の許可に対応する専用入口で受け付ける。登録版・操作・対象の照合を、共通 dispatcher と owner の直接入口でも通す。その他の task、command、instant、研究 worker、専門セッション、pipeline／workflow への引き渡しは、専用契約があるものだけを通す。[能力の解決](../api/application/toolchain/task-execution-catalog.ts) · [実行の振分け](../api/application/toolchain/task-execution-dispatch.ts) · [pipeline の受付](../api/domains/agent-runtime/service/execution-pipeline.ts) |
| 参照・保存済みの仕事・配送先 | 照会、参照検索（SQL を含む）、再読込み・再配送でも同じ出所と親・世代を照合する。子の調査と Claude の判断ジョブは背景キューに入れ、進捗・質問・結果は親へ返す。通常の会話履歴や他の仕事へ子の参照を流さない。専用検証がない経路は、仕事の作成・外部実行・結果公開の前に拒否する。[task の照会と配送](../api/application/toolchain/task-execution-port.ts) · [Claude の判断ジョブ](../api/domains/claude-code/index.ts) |

### 制御と回復

利用者の操作は親で受理する。会話なら実際の発言、ボードなら認証済みの利用者・会話・対象・操作・期待版をホストが記録した操作 ID を出所にする。監督は親子関係と操作 ID・期待版を検証する内部制御 port で子 owner を呼ぶ。監督配下の子 ID を会話の既存制御入口に直接指定した場合は拒否する。親子の開始・制御は SQLite の単一 writer で記録し、runner への通信はコミット後に行う。

| 操作 | 照合と効果 |
| --- | --- |
| 開始・再送 | 親・宛先、依頼・設計 digest、許可操作、世代・期限に加え、先行の受入と空き枠を照合し、起動要求と一意な操作 ID を保存する。子 owner の受付と親子 ID の対応を同じ取引で確定する。外部実行の配送直前にも世代を検査する。同一 ID・同一内容の再送は既存の受付、異なる内容は競合とする |
| 質問・回答 | §4 の順に一件ずつ提示する。親質問 ID・子仕事・子質問 ID・世代・締切と実際の回答発言を照合し、同じ操作 ID でその子に一度だけ渡す。期限切れ・取消・旧世代・未提示の質問への回答は拒否する |
| 条件変更 | 会話の変更・ボードに記録した利用者操作の出所と親の期待版を照合する。監督が範囲内で再計画する場合も理由を記録する。影響する世代を進め、未配送要求を無効化し、旧実行を停止する。新しい依頼・設計版・操作を再照合し、必要な許可と停止確認がそろってから新世代で開始する |
| 取消・期限切れ・忘却 | 親側で新規開始と結果採用を失効させ、保存済みの子 ID・世代に限定した停止要求を同じ取引に記録する。停止・停止確認には所有関係と対象 ID を照合し続けるため、開始許可の失効後も後始末できる。配送済みの開始と競合した場合、先に届いた停止を runner が記録し、先に開始済みなら停止を追跡する。確認前は「停止確認中」とし枠を保持する。[runner の開始前取消](../packages/coding-runner/src/claude-service.ts) |
| 再起動・応答喪失 | 保存済みの子 ID、runner 受付 ID、観測位置から照会する。現行の親子・設計版・世代・操作・期限が一致する場合だけ続行と結果採用を許す。失効済みなら既存 ID の停止確認だけを行う。停止未確認なら §5 の隔離・証拠照合を通す。照会と停止確認は隔離中も受け付ける。[既存の回復設計](claude-code-managed-task-design-2026-11-15.md) |

設計書の閲覧・レビューだけの依頼は提出で待機する。SkillSmith は段階②で、上の調査許可を仕事の世代に合わせて照合する接続を追加する。現行の専門セッション用の認可は、そのセッション経由で使う。[SkillSmith の出所検証](../api/application/knowledge/specialist-guidance.ts)

### 証跡と報告

Claude 担当が依頼の実行終了と証跡参照を確かめ、監督は設計の受入条件と照合する。静的読解なら対象ファイル・版・根拠箇所と答えを照合する。「再現した」「短縮した」「試験が通った」と判定するには、編集枠で得た実行 ID・対象版・測定値または試験結果が必要になる。実行後に対象が変われば、影響した条件だけを再検証する。[子の完了判断](../api/domains/claude-code/lifecycle.ts) · [runner の証跡](../packages/coding-runner/src/claude-engine.ts)

通常の進捗は台帳へ集約する。質問・失敗・競合・完了候補など判断を変える観測で監督を起こし、利用者には重要な進展・判断待ち・最終結果を届ける。同じイベントは同じ報告 ID に集約する。失敗の再試行は新しい根拠か条件の変更を記録してから行い、呼出し枠や期限に達したら残件と再開条件を保存する。

## 7. 実装順と MVP の受入

実装は次の順に接続する。自発的な新規開発の提案と優先度変更は MVP の評価後に検討する。[登録手順](../docs/toolchain-extension.md) · [検証手順](../docs/toolchain-extension-verification.md)

1. **Agency 更新を前提に、下調べから設計書閲覧まで。** §3 の型・生成・検証を公開した配布版を固定する。§6 の全出所分岐を移行・検査してから参照調査を有効にし、本体の登録 task と Markdown ストアを接続する。会話中に登録目標なしで保存・閲覧できることを確かめる。
2. **SkillSmith を設計前に接続し、一件を実委任する。** 手順が適合すれば版付きメモを設計入力に加える。検証専用の隔離、質問の提示と期限、隔離中の照会・停止と回復を実装する。子の起動・条件変更・取消・再接続と、実 runner での検証を確認する。
3. **共有チェックアウトでの並行実行と Kanban。** §5 の全経路の予約を移行した後に、監督下の Claude 二件で静的読解と検証または編集を重ねる。二件の質問を順に届け、会話と新しいボード照会が同じ理由・結果を返すことを確認する。

| 検証段階 | 試験と合格条件 |
| --- | --- |
| 部分・設計契約 | 本体が取り込む配布版の公開入口から生成・検証を呼び、登録目標なしで生成できる。既存の登録目標でも同じ検証を通る。設計書を見た利用者と子が同じ本文 digest を取得する。入力にない出典、忘却された資料、別仕事の証跡を拒否する。レビューだけの依頼から編集開始は 0 件 |
| 部分・権限 | 設計 digest・許可操作・親子関係・世代・期限を一つずつ違えて起動と採用を拒否する。親取消後の未配送要求から子起動は 0 件、旧世代の条件変更・回答も拒否する |
| 結合・検証専用 | `verify` の子で許可済みの試験が成功し、実行 ID・対象版・試験結果を得る。同じ子の `Edit / Write` 要求と未指定の Bash は実行前に拒否する。書込みを試みる試験を許可した場合も、その子プロセスによるソース上書き・新規ファイル作成は OS が拒否し、チェックアウトの内容が一致する。隔離を用意できない場合は理由付き保留で、実行は 0 件 |
