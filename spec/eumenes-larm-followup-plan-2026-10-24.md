# EumenesのLARM接続復旧と応答遅延の修正計画

作成日: 2026-10-24。状態: 利用者合意済み。A〜Cの修正とDの切り分けを完了。通常配置の受入と接続寿命の追加設計は保留。[実装と検証結果](verification/eumenes-larm-followup-2026-10-24.md)。

コードレビュー後の追加修正と検証は[レビュー記録](verification/eumenes-larm-followup-review-2026-10-24.md)に記載した。レビュー中に配備されたLARM新版では、後方systemを含む5配置の可視性試験が成功した。通常配置の大きな文脈・会話全体の受入と、判断用接続の寿命の追加設計は引き続き別に確認する。

LARM新版でキャッシュ保持の改善を確認した後に残った問題を扱う。先にEumenesだけで接続復旧と測定の不備を直し、初期判断の遅さを切り分ける。後方systemの配置変更や判断用接続の常駐化は、LARMの契約確認と追加の設計判断を経て扱う。

既存の[応答時間短縮計画](eumenes-response-latency-plan-2026-10-23.md)、[接続保持設計](larm-connection-retention-design-2026-10-18.md)、[新版の再検証記録](verification/larm-revalidation-retry-2026-10-24.md)を前提とする。構造化出力候補は未採用であり、本計画で自動採用しない。

## 目的と分担

| 対象 | 観測と問題 | LARM待ちの有無 |
| --- | --- | --- |
| 旧接続の410 | 接続状態の照会が410でも旧leaseを保持し、更新処理で再確保に進めない | Eumenes側の修正・fixtureは待たずに可能。配備切替のlive再現は後段 |
| 失敗理由の記録 | 出力上限、content filter、終端欠落、空出力が同じ`chat_stream_incomplete`になる | 待たずに可能 |
| 比較結果の欠測 | ログのバッファを排出する前にrunnerが集計し、末尾のtimingが結果から欠ける | 待たずに可能 |
| cache受入の精度 | 通常配置の推定約14,000 tokenが正式2,682 tokenでも、実行自体は続く。資料内の値の読取りをcache runnerで検査していない | runnerの修正・失敗検知は待たずに可能。通常配置の合格はrole互換性解決後 |
| 初期判断の6.46〜7.20秒 | 短命な補助接続で全件cache 0。新規接続だけが原因とは未確定 | 接続・入力差分・時間の計測と対照試験は先行可能。寿命契約の変更は結果とLARM回答次第 |
| 後方systemの情報欠落 | 送信済みの資料が正式計数と読取りから欠落 | Eumenes側の回帰試験は準備可能。role配置の変更は保留 |

通常入力のまま全情報をモデルへ渡すこと、失効した接続から復旧すること、未完了出力や取消後の結果を採用しないことを優先する。情報欠落による短縮を性能改善と扱わない。

## 既存機構を使う方針

LLMへの指示・候補schema・情報の組立てと、実行機構を確認した。初期判断は`request-analysis.ts`から`generateConversation`へ渡され、`sessionRole: auxiliary`として1回限りの接続を使う。補助接続の寿命は`larm/service/index.ts`、接続状態はlease manager、生成結果の採用はinferenceとdialogueが担う。

今回先に扱う不具合は接続寿命と観測の問題なので、LLMへの追加指示で補わない。既存のlease更新・解放・接続確保、共通ストリームreader、構造化ログ、比較runnerを修正・再利用する。新しい判断器や接続poolは作らない。後段の入力最適化も、既存の固定指示・参考情報の境界と共通validatorを維持した候補比較を先に行う。

## A 旧接続の410から復旧する

最初の製品修正。対象は`api/domains/larm/service/lease-manager.ts`、`refresh.ts`と、必要に応じた既存のlease状態管理。既存の`with-provider.ts`は401後の状態照会で404/410を終端と扱い、解放処理も410を受け付けている。この共通の寿命管理に、接続更新時の状態照会410をそろえる。

1. 接続状態のGETで確認した410を、その旧接続が利用不能になった事実として処理する。全API・全Providerの410を一括で再試行対象にしない。
2. 旧leaseを新規利用から外し、既存の利用数管理・解放処理を通して新規接続を確保する。KV保持を目的に、有効な接続を定期的に作り直さない。
3. 同時の更新・送信・画面保持要求は既存の`connecting`へまとめる。復旧中や復旧失敗時に無効と判明した旧接続をreadyとして残さない。
4. 取消・port終了・設定変更で復旧を止め、遅れて完了した確保結果を採用せず解放する。再確保も既存の期限内で行い、同一呼出し内の無制限ループを追加しない。
5. 接続確保前の失効回復と、生成POSTの再送を分離する。推論が始まったか不明な要求や公開済みstreamを、410だけを理由に再送しない。

既存の「410後も旧接続を保持する」試験は、新しい復旧仕様に合わせて改訂する。診断用のconnectionId記録・秘密情報非記録の検査は残す。

完了条件: 接続照会410→新規確保→生成成功をfixtureで確認し、同時呼出しで確保が増殖しない。旧接続利用中、復旧失敗、401/403、通信断、取消、close、設定変更も検査する。最後にliveで新規接続の生成成功を確認する。実サービスの切替再現は、利用者が行う配備・再起動の機会に別枠で確認する。

## B ストリーム失敗の診断を分ける

対象は`api/infrastructure/chat-stream.ts`、`api/domains/larm/service/llm-timing.ts`、安全なエラー・ログの既存境界。

現行readerは`finish_reason: length`または`content_filter`、`[DONE]`なし、空の結果を同じエラーへまとめている。したがって、前回の`chat_stream_incomplete`をネットワーク断やLARMの終端欠落と断定できない。

共通readerが観測した固定の終了分類、終端受信の有無、受信済みの許可されたusage/timingsを、失敗時も安全に診断へ渡す。外向きのエラーと採用判定は保ち、成功を増やすために不完全な本文・引数を受け入れない。任意のProvider文字列や出力本文は記録しない。既存のrunId・attemptId・connectionId等と対応させる。

完了条件: 正常stream、上限到達、content filter、終端欠落、空出力、不完全なtool call、取消をfixtureで区別でき、失敗時の本文・引数が採用されない。終了理由やusageが届かなかった場合は不明のまま記録し、0で補わない。128 tokenの試験失敗を通すための上限引上げや自動再送は行わない。

## C 比較runnerの欠測と誤った受入を防ぐ

対象は`scripts/response-decision/`と既存loggerの排出境界。通常の生成処理へ追加推論を入れない。

1. 検証接続の終了とログの排出を終えてからJSONLを集計する。既存sinkのflushを再利用し、固定sleepで末尾イベントを待たない。
2. 全呼出しをsubjectIdで正式計数・timingと対応させる。成功・失敗・取消の行を残し、末尾欠測や重複を検出する。情報不足やboot/config混在は比較不能と判定する。
3. 通常配置と、全資料を先頭systemに置く合成対照入力を別の試験として管理する。再検証で使った対照runnerは、本文・秘密を保存しない形で再実行可能な管理対象へ整理する。
4. 対照入力は正式約14,000 tokenへ校正する。通常配置は、推定値だけでその規模の受入を通さない。資料の欠落で正式計数が小さくなった場合は、合格とせず理由を記録する。
5. 合成資料内の値の読取りも確認し、要求が成功しただけで情報がモデルへ渡ったとは判定しない。後方systemなどの配置別の可視性試験と組み合わせる。

同じ入力の再送、user差分、背景更新、元の要求、補助4要求後をテキスト・JSONで確認する。新規接続をcold、同一接続をwarmとは呼ばず、Providerの実際のcache数を基準にする。

完了条件: runnerのfixtureで欠測・重複・revision混在・資料欠落を検出できる。liveの全呼出しが成否と対応し、通常配置の失敗を対照試験の成功で上書きしない。通常配置の可視性が失敗している間は、該当する大きな文脈の受入を保留する。

## D 初期判断の遅延を切り分ける

A〜Cの後、既存の計測を使って初期判断の時間を分ける。対象はdialogueの生成・入力計測、inferenceのattempt、LARMの接続・計数・生成計測と比較runner。

- 呼出し元の`initial_decision`と論理sessionRoleを保ち、helper内部でmainへ置換された値だけで分類しない。
- 接続確保、主接続の利用待ち、正式計数、生成送信、最初の本文、完了の区間を対応させる。既存の入れ子の時間を合計して二重計上しない。
- 同じ合成入力の「同じ接続で再送」と「短命な補助接続で再送」を比較する。次に候補・依頼・背景の変更を分け、共通prefixの変化とcache数を観測する。生入力の比較はrunnerのメモリ内だけで行う。
- 接続条件の比較では出力方式を固定する。nativeとschemaの比較は別軸にし、接続変更の効果に混ぜない。

この対照試験は製品の寿命契約を変更しない。現在のLARMへ小規模な計測は可能だが、新版反映などでrevisionが変わった比較を混ぜない。

結果に応じて次を選ぶ。

| 測定結果 | 次の対応 |
| --- | --- |
| 同一接続ではヒット、新規接続ではヒットしない | LARMの所有・解放契約を確認し、判断用接続を保持する必要性と資源費用を追加設計にする |
| 同一接続でも実入力prefixが変わりヒットしない | 既存E4の配置候補を使い、同じ情報・権限を保った比較を行う |
| 同じprefix・同じ接続でもヒットしない | LARM側へ条件と計数を渡す。Eumenesへ専用キャッシュやslot制御を追加しない |
| prefill以外の待ちが支配的 | Eumenes内の不要な重複処理を実測で特定する。Provider内部の差分はLARM側に確認する |

完了条件: cache 0の原因について、接続寿命・入力差分・Provider動作のどこまで確認できたかを示し、次の修正の根拠を残す。6件のsmokeだけで方式採用や速度改善を宣言しない。新しい常駐接続や所有範囲の変更は本計画から直接実装せず、追加設計の合意対象とする。

## LARMの回答を待つ変更と受入

後方systemが処理される契約をLARM側で修正する場合は、Eumenesの通常配置を維持したまま、5配置の可視性、正式約14,000 token、補助4要求後の保持を再検証する。

LARM側が後方systemを非対応と定める場合は、Providerへの直列化方式を追加設計する。参考情報・偽の承認・外部出力をsystemの命令へ昇格させず、履歴の順序、現在依頼、画像、忘却、token予算、他Providerとの整合を扱う。systemをuserへ一括置換する暫定処理は導入しない。

既存E2/E3の構造化出力候補、E4の配置候補は、情報が欠落しない条件で既存の品質・時間基準を満たしてから採用を判断する。判断用接続の常駐化・共有範囲の変更も、LARMの契約とDの測定結果がそろうまで保留する。

## 検証の順序と完了条件

部分→domain結合→通しの順で行う。

1. A〜Cのfixtureを先行する。410復旧、取消・同時実行、streamの終了分類、ログ排出と集計、可視性の不合格を個別に確認する。
2. `bun run verify -- --domain larm --domain inference --domain dialogue`で確認する。共通stream変更の利用側を検索し、影響があれば対象domainの検証を追加する。logger変更時は既存logger試験も確認する。
3. 公開APIのfixtureで「旧接続失効→新規確保→判断→回答」と「途中取消→古い結果を不採用」を確認する。通常動作にschema候補を混ぜない。
4. 保存済みLARM設定の読取り専用取得でliveを行う。Aの復旧、Cの対照試験、Dの比較を記録する。製品の通常会話については、role互換性と旧接続の復旧を確認した後に通し検証する。
5. ブラウザE2Eは`tests/browser/toolchain.spec.ts`など影響するファイルを明示する。サーバー操作が必要な試験は許可を得てから実施する。音声を評価する場合は実機器3往復を別途行う。

LARM待ちの間の完了はA〜Cの実装・fixture・domain検証とDの切り分けまでとする。後方systemの可視性、配備切替のlive回復、通常会話の速度、音声の受入は別々に未完了として残す。LARMの回答前でも、根拠のあるEumenes内の不具合修正は進められる。
