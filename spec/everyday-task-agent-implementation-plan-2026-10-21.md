# 日常の複数操作エージェント 実装計画

作成日: 2026年10月21日

状態: 利用者の実装指示を受け、P0〜P5の実装・固定試験を実施済み。P6の実モデル受入は不合格、実ブラウザー再生は未達で、全体は未完成。製品DBでは新担当だけを無効にし、既存担当とサーバーを復帰した。改訂後の最新の成否と残作業は[進行契約の検証記録](verification/everyday-task-agent/progress-contract-verification-2026-10-21.md)を正本とする。

本書の `task` は新しいbindingの実行型を指す。既存の単発処理用の `TaskState`、調査の `agent_tasks`、browserのtaskとは区別する。以下、複数操作全体を「親実行」、一つの能力への依頼を「子呼出し」と呼ぶ。

追記: [実装レビューと改善記録](verification/everyday-task-agent/implementation-review-2026-10-21.md)の実モデル受入は未達。2026-10-21に[進行契約の改訂案](everyday-task-agent-progress-contract-proposal-2026-10-21.md)への利用者合意を受領した。以後の進行契約は同改訂を適用した。現行bundleはskill@8 / package@8 / toolchain@9。計画欄・改訂条件・失敗依存の改訂後、二操作は改訂条件の追加後の15件で12件成功（失敗3件は推論時間・通信）。複数能力の組合せシナリオは未達のため無効を維持する。

## 1 目的と完了の定義

会話エージェントから一つの依頼を受け、既存の能力を必要に応じて探し、結果を使って次の能力を選び、日常の複数操作を完結する担当を追加する。例えば「おすすめの動画を別タブで再生して」は、検索結果の取得で終了せず、選択・ブラウザ操作・結果確認までを同じ担当が進める。動画・サイト・語句に依存する専用手順は実装しない。

会話エージェントは依頼の理解、MemoryやWorldの記録を踏まえた委譲、利用者との質問・訂正・取消、最終説明を担当する。実行担当は委譲された目的内のツール探索・操作・観測を担当し、利用者の新しい目的や許可を自分で作らない。

初版の完了条件は、公開入口から既存の検索・command・instant・生成系の実行を使い、質問と非同期完了をまたいで要求を満たすこと、取消・失効・重複の検査を維持すること、固定試験と実モデルの記録を分けて揃えることである。Web検索とブラウザだけの成功で全能力への接続完了とはしない。session型は利用者との直接対話へ引き継ぐ境界までを対象とする。

## 2 対象と対象外

| 対象 | 今回の扱い |
| --- | --- |
| 実装の場所 | Eumenes本体。外部ライブラリ・別リポジトリへ切り出さない |
| 新しい担当 | bundleと登録adapterを持つ `task` 実行型として追加する |
| 日常の複数操作 | 一手ずつの探索・実行・観測。子処理は初版では直列 |
| 既存の単純な依頼 | instantや個別担当へ直接渡す経路を保つ |
| 既存能力との接続 | 型ごとの公開操作を共通の呼出し口へ接続する。業務判断は各domainに残す |
| 質問・訂正・取消 | 作業IDと版を確定して会話から配送する |
| 表示 | 既存チャットの受付・作業状況・質問・最終回答と、既存の成果物Artifactを使う |
| Pursuit | 別の長期リサーチ担当。本書では取込・自動昇格・起動を実装しない |
| Harness2 | Context分離と実行記録に基づく改善の参考に限る。自己改良・比較のための本番反復実行は入れない |
| その他の対象外 | 常駐監視、日をまたぐ自律試行、並列計画、任意コードの実行、新しい権限体系、Memory・Worldの保存仕様変更、既存全ツールチェーンのデータ移行、専用の新画面 |

長期化が必要なら、理由・確認済みの事実・残作業を会話へ返す。未実装のPursuitを起動したことにせず、時間切れだけで別担当へ自動移行しない。

## 3 既存実装の根拠と再利用先

| 現在の接続 | 根拠 | 計画への反映 |
| --- | --- | --- |
| bindingはcommand・session・instant | `api/domains/capabilities/contracts/bindings.ts` | 長く続く担当の契約を `task` として追加。既存revisionは変更しない |
| commandは一操作を採用して回答へ戻す | `dialogue/service/toolchain-command.ts`、`command-apply.ts`、`agent-runtime/service/action-operation.ts` | commandの受付を複数操作全体の完了として使わない |
| 調査完了は会話回答を起こす | `agent-runtime/service/task-ops.ts`、`dialogue/service/agent-sync.ts` | 子処理の完了先を親の実行担当へ向けられるようにする |
| 根のcoordinatorと選択履歴はrun単位で一意 | `agent-runtime/repository/index.ts`、`toolchain-history/repository/index.ts` | 会話のrun、実行全体、各呼出しを別のIDで保持。既存の履歴を上書きしない |
| 一手ごとの核とQueueがある | `inference/contracts/agent-core.ts`、`agent-task.ts`、`queue` | 契約検査・修復・予算・prepare/execute/settleを再利用する |
| 共通核は開始時のツールと履歴を固定する | `inference/contracts/agent-task.ts` | 動的な能力提示を扱う部分だけ拡張。固定型の既存利用者を一括移行しない |
| 非instantの選択関数は分類と予告だけを受ける | `dialogue/service/initial-decision.ts` の `analysisTools` | この引数を子依頼のschemaと誤認しない。選択情報を共用し、子依頼の契約を追加する |
| 共通結果型は確認待ちも持ち、Artifactを必須にしている | `tool-runtime/contracts/adapters.ts` の `ExecutionResultV1` | 終了専用型として扱わず、Artifactのない親実行を既存UI結果型へ押し込まない |
| ブラウザは受付後に別のtaskで動く | `application/browser/browser-adapter.ts`、`browser/service/tasks.ts` | 受付IDと終了結果を区別。既存の承認・安全検査・操作ループを使う |
| ブラウザ完了は会話へ直接通知する | `browser/service/lifecycle.ts`、`application/browser/browser-composition.ts` | 親がいる処理は親へ返し、親の最終回答と二重通知しない |
| ブラウザのneeds_inputはそのtaskの終了で、承認後は別taskを作る | `browser/service/tasks.ts`、`approvals.ts` | 同じtaskを単純に再開する前提を置かず、論理的な子呼出しと再開先taskを結ぶ |
| ブラウザへ渡す原文が長いと現在は引継ぎ文へ置き換わる | `application/browser/browser-adapter.ts` の `TASK_REQUEST_CHARS` と `said / brief` | 引継ぎ文を許可の原文へ昇格させない参照経路を追加し、長文の回帰試験を置く |
| 生成系はrunごとに一件の保存がある | `image`、`music`、`excalidraw` のrepository・公開service | 呼出しIDを分離し、同じ依頼内で二回生成しても衝突しない |
| 判断段階によってContextが異なる | `dialogue/service/request-analysis.ts`、`selection-trace.ts` | 委譲判断と委譲情報の選択に、会話のContextを使う |

新しいruntimeの中核は `agent-runtime` に置く。下位domainからdialogueを呼ばず、所有者・元発言の検査、能力の実行、質問の会話配送は注入portとapplicationの組立てで接続する。`tasks` domainは現在coding等の長期委任を管理しているため、日常の短い実行をそのschemaへ無理に追加しない。

## 4 担当の選択と登録契約

### 4.1 会話側の判断

依頼の意味と担当の選択は会話LLMが判断する。難易度の数値、発話の正規表現、動画などの題材別の分岐は作らない。雑談・説明は会話で答え、一能力で済む依頼は既存担当、結果に応じて複数の能力を使う必要がある依頼は日常実行担当へ渡す。判断できない詳細を最初から完全に計画することは要求しない。

`execute_task` を登録済みの小さい委譲入口として最初の会話判断に提示する。全ツール一覧は提示しない。この入口は用途別検索で見つかることに依存させない。そうしないと検索担当だけが上位候補に入り「探して再生」の後半が失われるためである。既存の使用済み4件・4,096推定トークンとは別の制御入口だが、実際の要求予算には定義・引数・参考資料を含めて計上する。

委譲を選ぶ判断は、既存のContext組立てから今回の原文・直前の会話・Memory・現在の作業参照を受ける。Worldの本文は従来どおり取得したものだけを使う。現在の「R1はMemoryを読まない」制約はこの判断では変更する。分類結果を得る前に、その発話だけMemoryを足す分岐は作れないため、変更は通常入力のR1に適用する。既存のContext予算内のMemory・直前会話・作業projectionを使い、会話履歴や全Memoryを新たに全件取得しない。候補探索後の再判断にも同じ入力を使う。委譲内容と参照の選択を同じ呼出しで返し、そのためだけの追加planner・分類LLM・command翻訳LLMは作らない。既存の個別担当の実行手順は維持する。単純依頼にも生じる入力tokenの増加は§12で比較する。

`execute_task` の引数は既存の依頼分析・予告に、委譲する目的と提示済み `contextRefs` を加える。原文・元発言ID・版・許可・期限・実行IDはhostが確定する。R1の関数生成・結果解析・契約検査へtask分岐を追加し、この入口だけを既存R2の依頼翻訳から外す。可用な公開revisionを一つだけ提示し、保持一覧に同じ担当があっても関数を重複生成しない。探索候補からはこの制御入口と再帰起動を除外する。

### 4.2 登録するもの

以下は新規IDの計画値。実装前に重複を検査し、以後は凍結したrevisionを使う。

| 登録 | IDまたは内容 |
| --- | --- |
| bundle | `api/domains/capabilities/bundles/task-execution.bundle.json` |
| profileとSkill | `profile:task.executor@1`、`skill:task.executor@1` |
| packageとtoolchain | `package:task.execute@1`、`toolchain:task.execute@1` |
| functionとbinding | `execute_task`、`binding:task.execute@1`、`execution:task` |
| adapter | `adapter:task-execution@1`。起動・状態・回答・取消をagent-runtimeの公開操作へ接続 |
| 出力 | 後述の構造化結果projection。調査報告schemaへ操作結果を押し込まない |
| 画面 | 初版は専用Artifactなし。成果物の既存Artifactと既存チャットを使う |

`task` bindingはprofile・Skill・制御tool・入力/結果schema・登録adapter・可用性・推論/探索/実行予算・timeLimitsを持つ。task用のadapter契約は開始、状態取得、回答、訂正、取消、参照検証を公開する。新しいexecution値は登録検査・bundle検査・runtime解決で明示的に対応し、未知の型は従来どおり拒否する。モデルに任意のadapter名・操作名・SQL・APIパスを選ばせない。

### 4.3 作業を続ける会話の入口

会話R1には、同じ会話で参照可能な作業の小さいprojectionを提示する。作業ref、依頼版、現在状態、短い目的、未回答の質問ref、終了した結果の参照を含める。本文・全手順・全能力は載せない。保存と提示の件数/容量上限はP0の契約で確定する。

作業参照がある場合だけ小さい `task_control` 関数を提示する。引数は `workRef`、`expectedRevision`、`action:status|answer|amend|cancel` と、actionに必要な質問ref/回答または訂正内容とする。expectedRevisionは依頼の版であり、通常の進捗更新だけで回答や取消を競合させない。意味上の選択は会話LLMが行い、hostは提示したref、状態、版、必要フィールドだけを検査する。質問回答は元の質問schemaでも検査し、訂正は§9の更新へ接続する。statusは保存済み状態を返し、実行担当を再起動しない。この関数を選ぶための追加分類や能力検索は行わない。

完了した結果を使う新しい依頼は、新しい `execute_task` または既存の個別担当へ、選択した結果refを渡す。終了した親実行を復活させない。現在進行中の作業への訂正とはLLMが区別する。複数の参照から対象を決められない場合は、操作せず会話で確認する。

## 5 一手ずつの実行

実行担当は原依頼、必要な背景、過去の確定結果、現在提示中の能力を読み、一回の推論で一つを選ぶ。

| 選択 | ホストが行うこと |
| --- | --- |
| `find_toolchain` | 用途を検索し、実行可能な上位4件を返す |
| 提示されたtoolchain関数 | 正確なschemaで引数を検査し、一つの子実行を開始する |
| `read_reference` | 提示済みの有効な背景・結果参照の指定範囲を返す。新規検索ではない |
| `ask_user` | 必要な質問を保存して会話へ配送し、待つ |
| `complete_task` | 満たした内容・根拠・実行済み操作・成果物を検証して終了する |
| `report_partial` | 達成済みと不足・実行不能・長期調査の必要性を区別して終了する |

能力の選択・引数・対象の解釈はLLMに残す。各能力のprofile・Skill・内部toolはその担当のContextへ渡し、日常実行担当には展開しない。用途説明・登録schemaの解決・native functionの生成/検証を共通化する。既存 `analysisTools` の非instant引数は分類と予告だけなので、そのまま子呼出しへ使わない。親の能力関数は、非instantでは `stepRequest` と提示済み `contextRefs` を受ける。instantでは `arguments` に登録schemaそのものを入れ、`contextRefs` と分けて引数名の衝突を防ぐ。操作・対象・入力値が必要なcommandは既存の担当が翻訳する。schemaを文章から再構成せず、固定JSONを使う既存サブエージェントの出力契約も変えない。

全体の原依頼と、今回の子が達成する `stepRequest` を別々に渡す。子は選んだ能力と今回の目的だけを扱い、全体の原依頼を根拠に別の能力を起動しない。親が原依頼の条件を省いてもhostは原文と参照を保持する。検索文・要約・子依頼から新しい許可を生成しない。

親用の状態はversion付きで、依頼版、提示した関数のrevision/schema digest、使用量、未確定呼出し、背景と確定結果のrefを保存する。固定JSON核の `TaskState` をnative function対応へ無条件に変更しない。共通の予算・拒否・修復検査を再利用し、親用handlerで一回一関数の呼出しを検証する。複数関数の同時呼出しや未提示関数は実行せず、残予算内の構造修復へ返す。

各判断のContextは固定profile/Skillとこの状態から組み立てる。過去の未使用候補の定義・失効した版・長い結果を履歴へappendし続けない。現在の関数、使用済みの短い結果projection、参照を提示し、詳細は `read_reference` で読む。確定済みの操作と不足を保持したまま提示量を制限し、全文履歴を短縮しただけで未確認の完了を作らない。

能力を持っていなければ検索する。検索で得た4件が不適合なら、その検索の選び直しループは終了する。先の結果から別の能力が必要になった場合は、残り予算内で新しい探索を選べる。用途が変わったかの意味判断を文字列比較で代替せず、依頼・観測・使用量をLLMへ渡し、ホストは回数上限を強制する。

検索直後は新しい4候補だけを能力として提示し、保持中の4件との和集合にしない。`find_toolchain` を提示せず、最終的には候補の実行か不足の報告を選ぶ。必要な `read_reference` / `ask_user` は使えるが、同じ候補と探索済み状態を保持し、それだけで探索枠を復活させない。選んだ能力の結果を受けた次の判断から、残りの探索を選べる。依頼の訂正で条件が変わる場合は§9の版更新を通す。

一度使った能力は実行内で再利用する。実行内の保持も最大4件・4,096推定トークンと要求予算の小さい方を上限にする。未使用候補、廃止された版、古い承認は保持しない。会話の保持一覧には日常実行担当を残し、内部で使った全能力を会話へ自動展開しない。

## 6 既存能力を使う共通接続

applicationに `ToolchainExecutionPort` を組み立て、開始・現在状態・取消・質問への回答・根拠検証を公開する。実行分類と所有domainの公開操作を接続するportであり、依頼の意味から手順を決めるdispatcherにはしない。各呼出しは凍結したtoolchain/package/binding版、実行ID、元依頼への参照、許可の世代を持つ。

開始応答は呼出し参照、状態、受付receipt、確定結果への参照を区別する共通envelopeとする。既存の `ExecutionResultV1` は `needs_input` を含むUI向けの結果型として保ち、非同期処理の `accepted` / `running` / `waiting_input` を `completed` に読み替えない。新しい親実行の結果はArtifact参照を任意の配列とし、既存型の必須 `artifactRevisionId` を満たすためのダミーArtifactを作らない。照会・通知・再配送は同じ呼出し参照へ結び、domainの状態から決まる変換だけをadapterに置く。

| 既存の実行型 | 接続するものと受入条件 |
| --- | --- |
| research | Web・会話履歴・Worldの既存worker。親の子として開始し、検証済みprojection・sources・失敗を親へ戻す。既存の検索/取得の安全検査を省かない |
| bound command | 選んだpackageのcommand担当と登録adapter。LLMが操作・入力を作り、既存schema・対象snapshot・権限を検査する。起動受付なら後続の完了まで追う |
| instant | 既存schema・choices・adapterをそのまま使用。文と根拠を親の結果へ返し、会話へ即時回答する経路とは区別。既存fallbackも子実行として追跡する |
| image・music・excalidraw | 各所有domainの開始・状態・取消・成果物参照。呼出し単位のIDと元の会話runを分離し、二回の呼出しが同じ保存行へ合流しない |
| object-recognition等の旧command | 現在の公開操作を接続する。利用者のカメラ・画像・画面等への同意と現在の添付参照を維持し、直接対話が必要なら確認へ戻す |
| browser等の非同期command | domainのtask/capture IDを保存して待つ。受付receiptと最終結果を別々に扱い、needs_input・failed・indeterminateも親へ戻す |
| session | 隠れた子として操作しない。対象と未保存作業を既存契約で検査して会話側へ引継ぎ要求を返す。session開始は会話側が既存の相手切替で行う。親は `partial` と `interactive_handoff` の理由・引継ぎ参照で終了し、成果物完成とは報告しない。sessionを隠れて進めたり、終了した親を自動復活させたりしない |
| dots・外部coding等の長期委任 | 既存の権限と開始/照会/停止契約を使用。今回の要求が「委任する」なら受付が目的の完了になり得る。「結果を使う」なら完了を待ち、期限に収まらなければ未完了として戻す |

hostの実行対応・現在の可用性・利用者の許可の積集合だけを探索候補にする。未公開操作を直接呼んだり、権限の拒否を別の担当で迂回したりしない。公開された別の能力で目的を満たせるかはLLMが判断するが、適合性を調べるためだけの試行実行は行わない。再帰的な `task.execute` の起動、会話の委譲入口を子から呼ぶことは初版では許可しない。

既存domainへの拡張は、実行単位・入力の由来・結果参照・取消・完了配送・予算/期限をつなぐ公開契約に限る。新しいAPIの内部処理や業務SQLをapplicationへ移さない。既存の直接呼出しも共通化できる部分を共用し、同じcommand翻訳・承認検査を二実装にしない。

browserは現在、原文を4,000文字に収められない場合に引継ぎ文を `request` として使う。日常担当からの新しい起動経路ではこのfallbackを使わず、hostが束縛した元発言ref・版と、実行目的のbriefを別に保持する。入力grantの引用は所有domainの公開portを通じて元発言から検証する。必要な原文を参照で渡せない場合は開始を拒否し、briefだけを原文にしない。長文の後半にある条件や、短い同意の継続元も同じ規則で扱う。

## 7 保存と非同期処理

agent-runtimeが以下を所有する。表名は計画値で、既存のmigration列の末尾へ追加する。

| 台帳 | 保存するもの |
| --- | --- |
| `agent_executions` | 実行ID、会話ID、元run・元発言と版、原依頼参照、依頼の版、状態、期限、取消/権限世代、凍結した予算、現在の子呼出し、最終結果 |
| `agent_execution_steps` | 単調な手順番号、判断の種類、提示した能力と選択、送信前に検証した子依頼/入力とdigest、呼出しID、実行先と再開先のID、受付と終了状態、結果/receipt/成果物参照、使用量。入力本文は通常ログに出さず、終了後に回収する |
| `agent_execution_refs` | 所有者・出所・版/digest・有効状態を持つ背景情報と結果の参照、表示順、取得範囲。本文の正本を複製しない |
| `agent_execution_questions` と配送 | 親が出した質問と回答を実行ID・手順・依頼版へ結ぶ。子の質問は所有domainの質問参照へ結ぶ。配送は一意なイベントIDで重複を防ぐ |

会話のrunは一回の会話応答、実行IDは依頼された作業全体、呼出しIDは一つの能力の実行を表す。元runを新しい実行IDで偽装しない。`agent_tasks`等の呼出し契約に実行所有者と完了配送先を追加し、既存のdialogue所有者は互換の既定値として維持する。run単位の一意制約を無条件に削除せず、新しい所有者では実行・呼出し単位の一意性を検査する。

親の開始キーは元発言のID/版と採用した委譲操作、子の開始キーは親実行ID/依頼版/手順番号へ結ぶ。キーと入力digestを送信前に保存し、同じキー・同じ入力は同じ結果、同じキー・異なる入力は競合として返す。別の発言や別手順で同じ内容を依頼した場合は別実行である。内容の類似度や本文hashで利用者の新規依頼を重複扱いしない。

既存の `command_interactions` は会話runを再開する契約であり、親実行の状態機械へ流用しない。質問のschema・表示・回答検査は再利用し、applicationで質問の所有先を解決して各domainの公開操作へ配送する。会話runの再開を返す既存応答と、作業の再開を返す応答を型で区別する。下位domainからdialogueのserviceやrepositoryを参照しない。

元会話runの完了・通常の次入力・UI切断と、実行所有者の取消を区別する。現在のrun単位の取消・回収処理を新しい所有者へ無条件に適用せず、作業の依頼版・所有者・期限と明示的な取消で生存を判定する。元発言の削除・忘却や権限失効は引き続き検査する。

現行の `readActionOriginInTransaction` は会話runがqueued/runningでなければ拒否するため、実行所有者を新たに検証する経路が必要である。会話originの偽装や `manual` runの捏造で回避しない。所有者契約をadapter origin、capabilityの検証、推論要求のcapture/採用、取消、結果参照まで通して接続し、既存の会話originの検査を緩めない。

一ジョブは一推論または一つの外部結果の採用で終了する。子を開始したら `waiting_child` を保存して推論資源を解放する。結果到着は保存済みの呼出しID・依頼版・取消世代と照合し、同じwriter transactionで結果採用と次ジョブの登録を行う。commit後に起床・表示更新する。LLMにstatusのポーリングを繰り返させない。

外部通信より先に呼出し行・入力・開始キーとdispatch用Queueジョブを同じwriterでcommitする。既存domainの開始操作が同じDBで完結する場合は公開transaction操作で原子的に開始し、ネットワーク通信をwriter内で待たない。受付後に親への結果保存だけが失敗した場合は、既存receiptの照会・冪等な再配送で照合する。成否不明の書込みを新しいキーで再送しない。

子結果と最終通知は保存済みの配送イベントを正本とし、宛先・イベントID・採用済みrevisionで重複を防ぐ。外部通知の送信済みフラグだけで配送完了とせず、親の結果採用または会話メッセージ採用を確認して消し込む。会話への通知ジョブは元runを再利用せず、作業参照から既存のホスト通知入口へ接続する。子の完了を会話へ直接返す従来経路は、dialogue所有の呼出しでは維持する。

主な状態は `queued → deciding → waiting_child / waiting_user → deciding → completed / partial / failed / cancelled / interrupted`。完了不能な未確定操作は `indeterminate` として別に記録し、自動再送しない。権限が失われた子を別の担当で迂回しない。

実行中のジョブがない `waiting_child` / `waiting_user` にも期限判定を行う。既存のagent-runtimeの期限reconcilerへ親実行を追加し、期限で新規採用を止め、子へ停止要求を送り、確定した範囲を保存・通知する。最終推論の時間が残っていない、またはモデルが応答しない場合は、hostが期限/予算と確定済み参照だけから不足を返す。親の終了後に届いた副作用の結果は照合記録へ残すが、依頼の達成や再開へは採用しない。

保存量・質問の期限・終了後の回収もP0の契約へ含める。手順数は実行予算で制限し、結果本文は所有domainに残す。元資料の失効で再読取りを止め、回収後も重複防止に必要な最小receiptを保持する期間を明示する。台帳の削除で未確定操作を新規操作として再送しない。

再起動時は初版では全ての未終了実行を `interrupted` にする。runningだけでなくqueued・質問待ち・子待ちを起動前の回収で対象にし、epoch更新、未実行dispatchの取消、子への停止要求、結果照合を行う。保存済みのreceiptと子の状態は照会可能にし、副作用を自動再実行しない。中断通知は同じイベントを再配送する。単なる画面切断や音声の読上げ停止は、採用済みの実行の取消にはしない。会話runと作業の寿命を分けること自体を回帰試験に含める。

## 8 Contextと結果参照

委譲入口は原依頼、今回の目的、明示条件、関連する参照を受け取る。元発言・Memory・World・添付・前回結果はhostが発行した参照だけを使い、LLMが選んだ範囲を所有者と版で検査する。会話側の言い換えだけを唯一の根拠にせず、原依頼を実行担当と子担当へ渡す。

現行の `ContextAssembly` は表示用ブロック、Memoryの `PreparedWindow` は会話一回の検証用であり、任意の部分を子へ渡す参照APIではない。P0で所有domainの公開読取りprojectionを定義し、元発言はIDとdigest、長期Memoryはitem ID/版と根拠、World・成果物・検索結果は所有domainの版付きrefへ結ぶ。R1には、渡せる部分にhost発行refを付ける。参照で再取得・検証できない集約本文を、再読取り可能な資料であるかのように委譲しない。Memoryの保存方式や別の記憶層は追加しない。

会話Window全体のversion/buildIdを、長く続く作業の生存条件に流用しない。通常の会話によるWindow更新と、選択した元資料の変更・削除・忘却を区別する。実行前と結果採用前には、実際に使用したitem/元発言/結果の版・digestと権限を検査する。失効した資料は黙って最新版へ差し替えず、不足として返すか、新しい会話判断で有効なrefを選び直す。

実行担当には固定の役割/Skill、今回の依頼、背景参照、現在の実行状態、提示中の能力、確定した結果と必要な詳細を分けて渡す。好みは推薦に利用できるが、過去の依頼・Worldの仮説・検索ページ本文は新しい実行指示や許可にならない。記憶の全コピー、実行担当独自の長期Memory、未取得のWorld本文は追加しない。

候補一覧は提示順とタイトル・URL・出典参照を保つ。`2番目`等の解釈はLLMが行い、hostは選択されたrefを正本へ解決する。URLは要約から作り直さず、動画ID等を含む完全な参照先を既存の遷移検査へ渡す。候補の短い一覧と要約、詳細の範囲読取りを分け、長い本文を全件再送しない。省略表示は原物の欠落と区別する。

最終回答や次の依頼で使う参照は、元domainの保持期限内で有効性を再検査する。結果の要約だけではタイトルとURLの対応を保証できない場合、所有domainへ短い構造化projectionを追加する。削除・忘却・期限切れから本文を復元する独自キャッシュは作らない。

`complete_task` / `report_partial` は短い結果、満たした内容、不足、根拠ref、操作receipt、成果物refを構造化して返す。操作receiptは `confirmed` / `unknown` と取消・停止要求の状態を別に持ち、未確定を成功へまとめない。hostは提示済み参照と確定状態を検証し、要求全体の意味上の達成判断はLLMに残す。調査の `coverage:complete` や子taskの `completed` を、親依頼全体の完了へ機械的に置き換えない。会話へは親の状態・理由とこのprojectionを渡し、子の生応答や独自の成功判定を足さない。

## 9 質問 承認 訂正 取消

質問は親実行と該当する子のどちらが必要としているかを保持する。会話へは質問・対象・必要な選択肢だけを返し、会話エージェントが説明と回答の配送を担当する。回答を受け付けたら対応する質問ID・依頼版・所有者を検査して一度だけ再開する。

質問の期限は親の絶対期限と所有domainの承認期限の短い方にする。期限内の回答でも対象や値・依頼版が変わっていれば再開しない。期限後の返答で自動的に新しい作業を作らず、既発生の操作を確認した上で会話LLMが継続依頼かどうか判断する。

ブラウザの操作承認・入力値承認は既存の対象・タブ・origin・値・期限・一回限りの検査を維持する。自然文の `approved`、Memoryの同意、実行担当の「許可済み」という説明はhostの承認tokenにしない。検索由来のURLを開くことと、外部データをフォームへ入力して送信することは既存の別契約で扱う。

browserが `needs_input` で終了した場合は、親を `waiting_user` にし、その子呼出しに質問と旧browser taskを結ぶ。正しい質問への回答から、既存の承認移送契約で新browser taskを開始する。これは同じ論理的な子呼出しの再開として記録し、親の期限・総予算をリセットしない。旧taskの終了したcoreをそのまま復元せず、実行済みreceipt・Scriptの確認結果・現在の対象観測から再開する。既実行の書込みを再送しないことを結合試験で確認する。

会話には作業ID・現在状態・最新の確認待ちを小さく提示する。新しい発言が進捗確認・訂正・取消・別の依頼のどれかは会話LLMが判断する。複数作業から対象を一意に決められなければ確認する。通常の雑談や次の音声入力を、作業の取消へ自動変換しない。

訂正は依頼版を進め、未実行の提案を失効させる。実行中の子を停止し、停止と既発生の副作用を照会してから新しい条件で再開する。取消は即時に新しい推論/操作の採用を止め、子の停止が未確認なら停止要求中と表示する。遅い完了通知を新しい依頼の成功として採用しない。取消でも既発生の操作は巻き戻したことにしない。

訂正時に停止の成否が未確定なら、新条件の書込みを始めず、確認待ちまたは不足を返す。取消が止めるのは以後の操作であり、既に再生中の動画、作成した物、送信済みの内容を自動で元に戻す意味ではない。停止・削除・巻戻しが必要なら、その目的と許可を別に受ける。対象の排他やtab leaseは所有domainの既存検査を使い、別の作業や利用者の操作を勝手に取り消さない。

## 10 予算と会話への返却

初期の試験値は親の推論12回、論理的な子呼出し6回、能力探索3回、一回の探索は4候補、親子合計の推論48回とする。48回の対象はEumenesが発行する推論であり、command翻訳・子の推論・修復・拒否後の判断・fallbackを含む。会話R1と受付/最終説明の推論は別に計測し、各会話runの既存予算で制限する。Embeddingは推論回数とは別に探索予算で制限する。外部coding担当などの内部推論は観測も制限も保証せず、既存の外部実行契約の予算・期限・照会・停止を使う。それが不足するものは「外部へ委任した受付」より後の自律的な継続を公開しない。

親の最後の一回は結果・不足の返却に予約し、`complete_task` / `report_partial` だけを提示する。予算のない質問待ちや子起動を作らない。親子の再開・承認後のbrowser task作成・質問・訂正で予算をリセットしない。最後の推論で契約違反が起き、修復枠がなければhostが確定状態と失敗理由を返す。以上は通常の実行回数を増やす指示ではなく上限である。

子の開始時に残予算から上限を予約し、所有domainが実際の推論・修復を消費する公開契約へ接続する。既存bindingの上限より増やさず、親の最終返却分を子へ配らない。単なる終了時の集計を上限制御の代わりにしない。消費量や上限を伝えられない実行型はP0で不足を明記し、接続ができるまで日常担当の候補へ公開しない。

予約は同じwriterで行い、一つの推論request IDの消費を一度だけ計上する。送信された失敗・取消・修復の試行も消費し、未使用予約だけを確定後に返す。browser再開で子内部の回数が初期化されても、この台帳の残量を引き継ぐ。外部担当への開始操作についても、Eumenes側の翻訳・受付の推論は同じ上限に含める。

期限はtask bindingの `timeLimits` と利用者の許可の短い方を開始時に固定する。初期案はrun/turn 300秒、親の一推論45秒。runは親全体の絶対期限、turnは確認への返却までの区間の上限とし、質問や訂正でrun期限は更新しない。子の期限は既存の能力別上限と、親の期限から最終推論用45秒を差し引いた時刻の短い方とする。余白がなければ子を開始しない。会話の最終説明は別の会話runの予算で行い、利用者が回答を受け取るまでの時間にはそこも含めて計測する。以上の数値は暫定値であり、P0で比較入力と既存経路の基準を凍結し、P6の固定試験・実モデル比較で過不足を記録する。変更する場合は本書の採用値と理由を明示して更新する。

親が保持する能力は4,096推定トークン以内とする。検索直後の新規4候補は保持枠と区別し、制御関数・原依頼・背景情報・結果・schemaを含む要求全体に既存の入力計数と予算検査を適用する。schemaを途中で切断せず、長い結果本文は範囲読取りへ移す。必要な定義が収まらなければ予算拒否として返し、候補不適合と区別する。事前推定とProviderのusage実測は別に記録する。モデル名・Provider profile名を固定せず、保存済みのサブエージェント接続とcatalogを使う。

会話は親実行の永続化後に受付を短く返し、採用済みの作業参照を保持する。受付段階では作業を達成したと説明・記録しない。子の途中結果を毎回会話LLMへ戻さず、進捗・確認待ち・最終結果だけを配送する。statusの表示は保存済み状態から行い、変化のない進捗ごとに会話推論や音声割込みを起こさない。完了・部分完了の通知は既存の通知経路から会話LLMへ渡し、実行済み/未確認を保って説明する。利用者が別の会話を開いていても通知先は元会話に固定する。読み上げや画面表示は既存の制約に従う。

操作全体の成功と、その後の回答生成やTTSの失敗は別々に記録する。返答の失敗を理由に実操作をやり直さない。ログは実行・手順・子task・job・HTTP requestのID、状態、既知の理由、容量、時間だけを残す。

## 11 実装順序と各段階の終了条件

各段階は製品コード・回帰試験・固定fixture・予定する記録を揃えてから検証する。途中の段階を全体完成と呼ばない。新しい契約の不足が見つかった場合は本書へ理由と影響を先に反映し、範囲拡大が必要なら合意を得る。

| 段階 | 必要作業と主な変更先 | 依存 | 終了条件 |
| --- | --- | --- | --- |
| P0 契約と基準 | 有効catalogの実行型と公開操作を一覧化。既存の直接実行・保持・取消の固定入力を凍結。task binding、所有者、R1/子入力、背景/結果参照、子完了先、総予算、保存上限をschemaと試験ケースにする。`capabilities/contracts`、`agent-runtime/contracts`、`tool-runtime/contracts`と所有domainの公開読取り | 本書の合意 | 後述の契約表を確定。対象catalogの全件について開始・結果・質問・取消・参照検証・予算の対応を記載し、未対応を隠さず候補から除外できる |

## 12 検証計画

### 12.1 固定試験の受入ケース

| 入力・条件 | 観測する合格条件 |
| --- | --- |
| おすすめ動画を探して別タブで再生 | 一つの親実行で検索とbrowserを使用。取得済みの動画URLを開き、再生の観測に基づいて返す |
| 候補提示→2番目を再生 | 保存した表示順とrefから解釈し、不要なWeb再検索をせず別の候補を開かない |
| 検索だけを依頼 | 検索結果で終了し、browserや再生を勝手に起動しない |
| 天気等の単純依頼 | 既存の直接/instant経路を維持。日常担当を常に経由させない |
| 同じ生成型を二回使用 | 二つの呼出し・成果物が残る。通知と保存が一方に上書きされない |
| 検索4候補が不適合・Embedding障害 | 全catalog展開や同じ探索の無制限反復をしない。別の能力の必要性と検索障害を区別する |
| commandの確認・browserの操作/値承認 | 正しい質問へ回答し、元の操作・値・対象だけを一度再開する。過去承認は再利用しない |
| 長い原文、短い同意、原文にない入力値 | 後半の条件と引用元を保つ。briefを原文にせず、同意の対象を検証して承認済みの範囲だけ再開する |
| 受付後に失敗・未確定・時間切れ | 完了とは言わず、既知の実行状態を保持する。未確定の書込みを自動再送しない |
| Memoryの好みと今回の明示条件が不一致 | 今回の条件を変えない。好みやWorld仮説を操作許可や今回の観測にしない |
| 原文にない情報が必要 | 許可された参照を読むか質問する。委譲文に事実や入力値を捏造しない |
| 検索/ページ本文の命令混入 | 結果を資料として扱い、担当・権限・完了条件を変更しない |
| 雑談・音声割込み・画面切断 | 採用済み作業を無条件に取消しない。会話応答は続けられる |
| 訂正・取消と遅い子結果の競合 | 依頼版・epochで古い結果を拒否。訂正前の条件で次の操作を始めない |
| 別会話・別実行・忘却・登録失効 | 候補・承認・結果参照を横流しせず、失効した根拠を採用しない |
| 会話Window更新、未使用候補の履歴、参照の版変更 | 雑談だけで作業を失効させず、選択した元資料の変更は拒否。現在の定義だけを提示し、古い候補の全文が蓄積しない |
| sessionへの切替 | 未保存作業の既存確認を通し、実行担当が利用者の代わりにsessionへ回答しない |
| 再起動・イベント再配送・HTTP再送 | 初版の復旧規則どおり中断。副作用・最終通知・使用量を重複させない |
| dispatch前後・子終了後・会話への採用前後のクラッシュ | 元の開始キーで照合し、外部操作と会話メッセージを重複させない。queued/子待ち/質問待ちも再起動で回収する |
| 待機中の期限、最後の推論の失敗、同時実行の上限 | LLMのポーリングなしで停止・不足を返し、新しい子を始めない。収容不能なら保存前に拒否し受付成功を返さない |
| 同じ入力の再送と、別発言からの同じ依頼 | 再送は同一作業。別の明示依頼は別作業。同じキーで異なる引数は競合 |
| 中止と、実行済み状態の変更 | 後続操作の取消と、既実行の操作を変える新しい依頼をLLMが区別。未依頼の巻戻しや別作業の停止をしない |
| 子の成功後に回答/TTSが失敗 | 実行済みを維持し、同じ実操作を再実行しない |
| 予算到達・Pursuit未接続 | 元の要求を弱めず部分完了/不足を返す。未実装の背景試行を約束しない |

固定モデルの成功を、LLMによる依頼理解の正しさの証明にはしない。別の語句・対象・ツール組合せでも同じ仕組みが通るケースを含める。

### 12.2 コマンドと段階

次の新規試験名は予定パスである。実装段階で作成してから実行する。検証対象のファイルは実行中に編集しない。

```sh
# 部分: 登録、状態、予算、既存型ごとの呼出し契約
bun run toolchain:bundle -- check api/domains/capabilities/bundles/task-execution.bundle.json
bun test api/domains/agent-runtime/test/task-execution.test.ts api/domains/capabilities/test/task-binding.test.ts
bun test api/domains/inference/test/task-execution-state.test.ts api/domains/dialogue/test/task-delegation.test.ts

# 結合: 本物の公開入口・登録adapterを固定Provider/driverと接続する
bun test api/application/toolchain/task-execution.test.ts api/application/toolchain/task-execution-tools.test.ts api/application/browser/browser-toolchain.test.ts
bun test api/application/toolchain/task-execution-recovery.test.ts

# 通し: 新担当の所有先と直接の利用側
bun run verify -- --domain agent-runtime --domain capabilities --domain tool-runtime --domain inference --domain dialogue --domain toolchain-history --domain browser --domain memory --domain voice-dialogue
bun run verify -- --domain queue --domain conversation --domain web-research --domain world

# P4で変更・接続した生成系の利用側
bun run verify -- --domain image --domain music --domain excalidraw --domain object-recognition

# 既存チャット・質問・Artifactの接続を変更した場合のブラウザ試験
bunx playwright test tests/browser/task-execution.spec.ts tests/browser/browser-workspace.spec.ts
```

各段階は対応ケースと静的gateが成功することを合格条件とする。新規migrationは新規DB、直前の正本seed、二回のseed、未対応adapter、古いrevisionの保持を検査する。Web/clientの変更が発生した場合はartifact等の影響domainも追加する。最終gateも変更したdomain・利用側・application結合を明示して選ぶ。全体の型・境界・buildの確認が必要と判断した場合は理由を記録して `bun run verify:all` を追加できる。ブラウザE2Eは含まれないため上記の対象ファイルを別実行する。

ブラウザE2Eで製品サーバーの起動・再起動が必要なら、その直前に利用者の許可を得る。in-processの固定試験と実サーバーの受入を混同しない。UI変更がなくブラウザE2Eを省略できる場合も、P5の質問・進捗の表示経路が既存と同じである根拠を記録する。

### 12.3 実モデルと実機の受入

実モデルは保存済みLARM設定をsettings domainの読取り専用操作で取得し、同じ設定と凍結した入力で各3回を初期の比較単位とする。単純依頼、検索だけ、検索→再生、曖昧な指示語、Memoryとの不一致、途中訂正を含める。外部応答を固定した試験と、本物の検索・Brave/Bridgeを使う試験を別に記録する。

計測は受付まで/最終結果までの時間、親子別のLLM回数とProviderが報告した入力/出力token、cached tokens、探索回数、子起動回数、修復、対象の誤り、不要な質問、誤った完了を含める。未報告のusageは不明とし、0や事前推定値で埋めない。各3回では中央値と範囲を報告し、p95等の十分な試行数が必要な値は主張しない。短いContextにしたことだけで高速化を主張しない。初回の冷たい能力探索と継続時の再利用を分ける。

性能の採用条件は、単純/既存担当への依頼に追加plannerや分類の往復がなく、保持済みの続きで不要な能力探索やWeb再検索が増えず、子ごとの会話への往復がないこととする。入力・応答時間の基準と許容増分はP0の記録と比較し、採用上限が未設定または超過した場合は公開gateを未達とする。現行で目的を完遂できない複数操作は、途中で終了した旧応答の速さだけと比較せず、達成範囲と各段階の時間を示す。

実ブラウザでは別タブ・対象URL・再生状態、取消後の新規操作停止と既発生の副作用を観測する。再生状態を観測できなければそのケースは再生成功として数えない。取消で自動的に再生が止まるとは期待しない。実スピーカーでの聴取と音声3往復は別の実機器受入であり、今回のfixtureやブラウザ成功から音声MVP完成を宣言しない。

## 13 公開 切戻し 停止条件

新しいtask bindingに対応したコードとmigrationを先に用意し、固定試験・受入後に登録公開する。新担当の可用性がfalseなら `execute_task` は提示しない。公開ポインタと実行中の凍結revisionを分ける。新revisionの登録や既存定義の上書きで過去の実行を変更しない。

切戻しは新担当の公開を外して新規受付を止め、進行中の作業は停止・照合して確定済み操作を残す。既存の個別担当への経路は維持する。追加migrationを削除して製品DBを巻き戻さず、同一revisionの上書きやDBの削除で登録衝突を回避しない。

担当外の検証失敗は証拠と影響を記録して修正しない。上限や試験期待値を弱めて成功にしない。同じ仮説の試行が3ラウンド続く、同じ失敗に新しい根拠がない、検証中の編集で結果を無効にした場合は、次の編集前に進め方を見直して利用者へ短く報告する。正常な長時間処理は時間だけで止めない。

本計画にない新しい判断方式、権限、長期背景実行、sessionの自動操作が必要になった場合は、その部分の実装を止めて設計を先に改訂する。main上の既存差分と他作業の変更を保持し、新ブランチ・サーバー操作・別チャットへのメッセージ送信を無断で行わない。

## 14 作業管理と実装開始前の確認

| 段階 | 現在の状態 |
| --- | --- |
| P0 | 契約、容量、性能の基準を確定・記録済み |
| P1〜P2 | 登録、移行、台帳、動的native schema、一手ループ、参照、予算、復旧を実装・固定試験済み |
| P3〜P4 | 型ごとの既存公開操作に接続。検索とbrowser、同型二回生成、再送、session引継ぎを固定試験済み |
| P5 | 公開会話入口の委譲、質問回答、通知の採用と失効を実装・固定試験済み |
| P6 | 主13領域と後続修正の正式検証成功。実モデルの重複・誤完了・不要な委譲が残り、再生も未達。公開を取り下げ、[検証記録](verification/everyday-task-agent/implementation-verification-2026-10-21.md)へ再開条件を記載 |

当初のP5実装時に登録したtaskの旧revisionを保持するため、その時点の登録版は `skill:task.executor@4`、`package:task.execute@4`、`toolchain:task.execute@5`、`binding:task.execute@2`、結果schema@2。§4.2の初期計画値を同一revisionで上書きしてはいない。公開の可否はP6の受入と[検証記録](verification/everyday-task-agent/implementation-verification-2026-10-21.md)に従う。

利用者は2026-10-21に以後の必要なサーバー再起動を許可済み。同時作業の稼働と実行中ジョブを確認して操作し、別チャットへのメッセージ送信は行わない。実モデル・実機の成功を固定試験の成功で代替しない。

本書で明示的に追加する仕様は、task実行型、会話で使える委譲/作業操作の入口、通常R1でのMemory利用、背景情報の参照projection、会話runと作業の寿命分離、子完了の配送先、別能力への再探索、呼出し単位の保存、既存の承認と質問の引継ぎ、親子の予算強制である。必要なバリエーションの追加は許可済みだが、これらを含む計画全体の合意を確認して製品実装へ進む。

計画作成時の変更は本書とspec索引だけ。既存の保持実装・Web担当の報告量調整等の差分は編集していない。製品試験・live・サーバー操作は計画作成の段階では実施していない。

初回作成では関連するローカル参照9件、索引の重複、空白と文書構造を検査した。今回の文書レビューは[レビュー記録](verification/everyday-task-agent/document-review-2026-10-21.md)に根拠・修正・再確認を残す。製品試験を行っていないことと、計画の契約レビュー完了を区別する。
