# GPT-Live音声会話・チャット記録・専用設定の設計案

作成日: 2026-10-31。状態: **基本方針と実装開始は合意済み。製品実装済み。固定検証は[実装・検証記録](verification/live-voice-2026-10-31/results.md)を参照。実API接続・本人の機器での3往復受入は未実施のため、音声MVPの受入完了とはしない。** [実装前レビュー](live-voice-design-review-2026-10-31.md)の指摘と具体化は§14に記録。

利用者の要求: GPT-Liveを現在のプロンプト入力の代わりに使い、利用者とAIの発話を正確にチャット欄へ残す。既存toolchainを使い続ける。APIキーの保存方法を設計する。開始用アイコンボタンを入力欄の近くに置き、専用設定画面を設ける。

レビュー中の追加要求: 利用者「会話ログはでるのですがASRやTTSは軒並みOFFの吹き出しにしないとですね」。Live中は、既存ASR/TTSを実行せず、状態の吹き出しにもOFFを明示する（§3.1）。

モデル名の確認: 最初の「live 1.1」は、利用者が「GPT-Liveの音声会話を想定している」と回答。公式資料で確認できた製品はGPT-Live 1。実装・ファイル名にはモデルIDを固定せず、保存済みの選択を使う。

## 1 目的・範囲・完了条件

本案の目的は、音声の会話窓口をGPT-Liveにし、Eumenesの会話台帳・記憶・toolchain・承認・仕事の状態を引き継ぐこと。GPT-LiveにEumenesとは別のツール実行ループを作らない。

対象は、開始・終了とマイク操作、専用設定、秘密情報の保存、Live接続、字幕の永続化、既存dialogueへの委任、音声出力の排他、検証。既存の文字入力は残し、音声会話中も補足を送れる。

本案では、既存toolchainの検索順位・担当の判断方式・権限・承認条件・非同期完了通知の方針は変更しない。既存のASR→会話→TTS経路の削除や自動フォールバック、音声録音の長期保存、全体リファクタリング、他チャットへの連絡は含めない。サーバーの起動・停止・再起動は別途明示許可が必要。

今回の完了条件は、公式仕様と既存実装に基づく設計、画面案、変更範囲、実装順序と受入条件を提示すること。実装の完了は§10の条件を満たした時点とする。

| 話した内容と配信状態 | `api/domains/dialogue/service/delivery-record.ts`、`api/domains/voice-dialogue/service/playback.ts` | 発話と配信状態を分ける既存責務を再利用・拡張 |
| 音声機器と再生の共有 | `web/src/domains/audio/`、`voice-dialogue/` | マイク・スピーカーの共有、通常TTSとの排他 |

会話ハーネスは[一本化の設計](single-harness-plan-2026-10-31.md)が最新。GPT-Live向けに廃止したcloudハーネスを復活させない。同日進行中の[会話から読む道具](conversation-read-tools-design-2026-10-31.md)とも競合させず、合意済みの公開口を利用する。[TODOの完了通知](todo-completion-notice-design-2026-10-29.md)は通知センターのままにする。

**基本方針:** 設定・会話台帳・routedハーネス・toolchainを再利用する。Liveの接続adapterに加え、連続PCMの入出力、字幕の一時保存と履歴への公開、委任の入力参照、案内・承認の配信、発話所有者の接続が必要。既存のASR/TTSへ音声を流すだけでは、GPT-Liveの同時に聞く・話す会話を実現できない。レビュー前の「接続adapterと受け渡しだけ」という記述は変更規模を過小に見積もっていたため訂正した。

## 3 入力欄のボタンと操作

通常の文字入力欄を維持する。送信ボタンの左側に、波形アイコンの正方形ボタンを置く。既存DesignSystemのiconサイズを使い、タッチ領域は約44px、キーボード操作・名前読み上げ・ツールチップを備える。

| 状態 | ボタンと表示 | 操作 |
| --- | --- | --- |
| 未設定 | 波形、「音声会話を設定」 | 専用設定へ移動。マイクや課金接続は開始しない |
| 停止中 | 波形、「音声会話を開始」 | 保存済み設定の確認後、マイク権限と接続を開始 |
| 接続中 | 進行表示、「接続を中止」 | 再クリックで中止。連打で複数接続を作らない |
| 会話中 | 停止アイコン、「音声会話を終了」 | 入力を止めて終了処理。欄の直上に「音声会話中」と経過時間 |
| マイク休止 | 会話中の表示と「マイク休止中」 | 別のマイクアイコンで再開。出力停止とは区別 |
| 終了処理中 | 進行表示、「終了処理中」 | 新たな入力を受け付けず、終端通知を待つ |
| 切断・保存停止 | 理由と「再接続」 | 明示操作で新しいセッションを開始。自動で課金接続を作り直さない |

会話中だけ、主ボタンの近くにマイク休止と設定への入口を出す。開始操作だけで話しかけられるようにし、通常の文字入力の下書きは消さない。既存の音声入力とLiveは同時にマイクを所有しない。Liveの発話を通常TTSでも再生する二重出力を止める。

音声会話の終了はバックエンドの仕事の取消とは別。既存の仕事は既存方針で継続し、完了は通知センターへ出す。利用者が仕事自体の取消を求めた場合は、LLMと既存の取消操作で処理する。

### 3.1 Live中のASR・TTSと状態の吹き出し

| 表示・経路 | Live中の状態 |
| --- | --- |
| 既存ASR | **OFF（Live使用中）**。LARM・クラウドのどちらにも認識要求を出さない |
| 既存TTS | **OFF（Live使用中）**。自動読み上げ・読み上げ直し・案内文・試用を含め、この会話のための合成要求と待機中の再生を止める |
| GPT-Live | 接続・マイクON/休止・再生中/待機を実際の状態から表示 |
| 会話ログ | 入力字幕と出力字幕をLiveの原文から継続表示・保存 |
| toolchain・記憶・仕事 | 実際の利用状態を表示。ASR/TTSのOFFを理由に必要なbackendの推論や仕事を停止しない |

「OFF」はこの会話が既存音声経路を使っていない意味であり、モデルの未設定・故障・サーバー停止とは区別する。Liveの再生を、既存の `phase === "playing"` だけでTTS利用中と表示しない。従来の「音声再生」は出力全体の状態、TTSはサービスの利用状態として分ける。

ASR/TTSの保存設定やモデル選択は変更せず、会話の実行経路で排他を保証する。Live開始時には既存音声受付、合成・再生の待機、Live対象の準備要求を停止・失効させ、後着した結果も再生しない。Live停止後も旧マイクを勝手に再開せず、次の通常音声開始操作で保存設定を使う。

画面上のOFFだけで済ませず、backendの要求台帳とProvider呼出しが増えないことを試験する。設定画面の従来ASR/TTSの試用も同一機器・会話でのLive実行と排他にする。別の仕事やconsumerの音声資源を一括解放したり、LARMサーバーを停止したりする指示ではない。既存の自発発話・担当からの質問の扱いは、OFFにより失われないようレビューR5の共通配信契約を先に定める。

## 4 専用設定画面「音声会話」

既存の設定アーティファクトに独立した「音声会話」を追加する。「音声と入力」の機器設定を再利用し、デバイスごとの異なる設定の写しを作らない。開始ボタン付近と設定一覧の両方から同じページを開く。

| まとまり | 項目・動作 |
| --- | --- |
| 接続とAPIキー | 既存のOpenAI公式接続を選択、または同じ画面から新規登録。キー欄はパスワード入力。保存後は「登録済み」のみ。更新・削除が可能 |
| モデルと声 | 保存済み資格情報で取得した利用可能モデルから選択。モデルID・profile名の固定値や名称判定は置かない。モデル一覧だけでLive対応・利用権限を保証せず、明示的な接続テストで確認。声は実行時に確認した公式契約の候補または検証可能な指定値を使い、モデルIDから推測しない |
| 話し方 | Eumenesの保存済み人格・言語方針を基に短い会話指示を組み立てる。話し方の補足を入力可能。業務指示・toolchainの規則はここへ複製しない |
| マイクと再生 | 共通のマイク・出力先への設定入口。「開始時にマイクを有効にする」（初期ON）。初期OFFなら、音声送信前に休止が有効であることを確認 |
| 記録 | 「文字起こしをチャットに保存」は必須ONの説明表示。保存対象と精度の限界を短く示す。音声ファイルは保存しない |
| クラウド送信 | 音声と会話に必要な文脈がOpenAIへ送られることを示し、既存のクラウド送信許可も検証。取消時は即時停止 |
| 動作確認 | 「接続を確認・モデル一覧を更新」と「音声会話を試す」を分ける。後者はマイク・発話・字幕を確認できる別のテストセッション。通常の会話・記憶には追加しない。課金が発生する旨をボタン付近に示す |
| 保存 | 既存の共通下書き・変更一覧・「設定の変更をすべて保存」を使う。保存失敗は入力を保持。秘密情報を変更一覧へ出さない |

未保存の接続・キー・モデル変更がある間は、保存済み設定との取り違えを防ぐためテストを開始しない。画面を開いただけでモデルや音声セッションへ接続しない。

モデル・声・開始時指示の変更は次の音声セッションから適用し、画面にその旨を出す。キーの更新・削除、接続無効化、送信許可取消は現在のセッションにも即時反映する。

追加する保存設定の案は `live.enabled`、`live.connectionId`、`live.model`、`live.voice`、`live.startWithMicrophone`、`live.instructions`。モデルと声は未設定を許し、モデル名のコード既定値は置かない。会話保存のON/OFF設定は追加しない。

## 5 APIキーの保存

専用の平文ファイル、ブラウザのlocalStorage、独自のキー保存庫は作らず、settingsの既存接続・資格情報を使う。対応するOpenAI公式接続があれば同じキーを参照する。画面から新規登録しても秘密情報の保存経路は一つにする。

1. キーは認証済みの設定保存APIへ一度送信し、backendがAES-256-GCMで暗号化する。既存の接続IDとepochに結び付いた認証付き暗号を使い、暗号文は `settings_credentials` に保存する。
2. 暗号鍵は既存の `EUMENES_SECRET_KEY` またはDBの隣の `keys/settings.key`。鍵ファイル0600・親ディレクトリ0700を維持する。暗号文が残って鍵が無い場合は新しい鍵を生成して上書きせず、利用不能とする。
3. 設定取得はキーの有無だけを返す。保存後のキー全文の再表示機能は設けない。キーを会話・指示・診断・ログ・画面の永続下書きへ含めない。入力中の秘密も、保存後や画面を閉じた後はメモリーから除く。
4. バックアップ・復旧は既存手順に従い、DBと暗号鍵を管理する。同じホストを完全に読める攻撃者から守る機構ではないことを運用上区別する。
5. 環境変数参照を使う既存接続も利用可能。利用者へ環境変数を必須として要求しない。
6. backendだけがOpenAI接続に資格情報を使う。最初の対応先はOpenAI公式originに限定し、既存接続のURLが別originなら採用しない。SDKログやProviderの生のエラー本文もログへ渡さない。
7. 開始時に接続epoch・設定revision・送信許可を捕捉し、送信・結果反映前にも確認する。失効時は送信・再生・結果反映を止める。資格情報の失効によって、既に保存した正当な過去の会話まで削除しない。

## 6 接続と既存toolchainへの委任

### 6.1 接続の提案

初版の提案は、ブラウザ→Eumenes backend→GPT-Liveの**主WebSocket接続**。音声とイベントをbackendの一つの受信経路で扱い、会話本文の受領・保存・委任の所有者を一つにする。APIキーはbackendから出さない。

OpenAIの推奨はWebRTCで、WebSocketも正式対応している。本案でWebSocketを選ぶ理由は、記録をbackendで開始から受信し、ブラウザとsidebandの二系統のイベントの照合を初版に持ち込まないため。音声の中継・再標本化が必要になるため、遅延と負荷は§10のG0で測定する。高速化したという主張はしない。許容できない場合はWebRTC＋sideband案を再設計し、合意なしに切り替えない。

主接続は `wss://api.openai.com/v1/live/sessions`、最初のメッセージは `session.start`。保存済みモデル・声・短い会話指示と `delegation.type: client` を指定する。`session.started` の後から音声を送る。PCM等の形式・サンプル境界・順序・送信の速度は公式プロトコルに合わせる。既存のWAV区切りをそのまま転送しない。

ブラウザとbackendの接続には既存の本人認証・会話への権限検査を適用し、Origin、セッションの所有権、短命な接続券を確認する。資格情報をURLへ埋めない。sessionIdだけを知っている状態では接続できない。音声キューとイベントの上限を定め、過負荷や保存失敗は新しい操作の受付を止めて表示する。

### 6.2 委任の流れ

1. Liveは短い会話指示で雑談・聞き取り・話す役割を持つ。外部の情報・実行・記憶の参照・保留中の質問や承認への返答が必要な場合はEumenesへ委任するよう指示する。語句の条件分岐で依頼を判定しない。
2. `session.input_transcript.delta` と `session.output_transcript.delta` を保存し、`session.delegation.created` を受信する。委任イベントには利用者の発言本文が無いので、`offset_ms`、保存した会話、現在の担当・確認待ち・仕事の状態からLLMが依頼を解釈する。
3. 断片不足・曖昧な対象・訂正の可能性がある場合は、LLMが追加発言を待つか確認する。字幕の無通信を発言の確定や実行許可にしない。字幕だけを契機に同じ依頼を先行実行する仕組みは初版に入れない。
4. 既存のroutedハーネスに依頼を渡す。検索・選択・読む道具・担当実行・transaction・権限・承認はEumenesが所有する。利用者の実際の原文は会話に一度だけ保存し、LLMが整えた依頼文を利用者の原文として追加しない。
5. 委任経路には「既存の利用者メッセージを参照し、返答はLiveへ返す」配信先を追加する。現在の `accept` を無条件に呼ぶとメッセージと回答の二重保存になるため、既存受付を分けて再利用する。これは明示的な契約変更として試験する。
6. その場の返答・質問・検証済み結果は `session.commentary.append`、会話に必要な事実は `session.thinking.append`。元の `delegation.id` を付け、各appendは500 token以下。backendの文をLiveが言い換えた場合、チャットにはLiveが実際に出した字幕を記録する。ツールの生データと内部推論は送らない。
7. 非同期の仕事は、受付と状態を既存の仕組みで扱い、完了は既存の通知センターへ出す。Liveのために自動読み上げを復活させない。利用者が結果を尋ねた場合は既存の参照操作で答える。

委任ID・Eumenesのoperation/run ID・依頼revisionを対応付ける。同一イベントの再処理で既存runを再利用し、新しい仕事を二重に作らない。ブラウザはtoolchainを実行しない。GPT-Liveの音声と文字入力が同じ依頼を補足する場合は、LLMが現在の依頼と関連付け、ホストはrevisionで古い結果を拒否する。

### 6.3 文字入力・承認・中断

会話中の文字入力は原文をそのまま既存台帳へ保存し、Eumenesへ渡す。Liveには必要な事実だけを反映し、独立した通常TTSは起動しない。画像添付は既存の画像対応backendへ渡し、Liveへ直接画像を送らない。

Liveの「わかりました」やappendへのACKを、既存の確認が利用者に届いた証拠にしない。正確な文言・対象提示と配信確認が必要な操作は、必要条件を満たすまで実行しない。Live経由の短い「はい」だけで、確認ID・対象・revisionの検査を省略しない。**レビューで訂正:** Eumenesの会話の確認を扱う汎用の画面承認口は、調査した会話UI・dialogue controllerでは確認できなかった。個別Artifactの承認と同一視せず、画面確認を追加する場合の契約と既存の案内配信条件をレビューR2で詰める。これを「既存画面の再利用で解決済み」とは扱わない。

発話への割込みと仕事の取消を分ける。取消・訂正の意味はLLMが解釈し、ホストが既存の権限と世代で取消・古い結果の不採用を保証する。声の無音や特定語句の一致だけで仕事を取り消さない。

## 7 「正確にチャットへ残す」の契約

### 7.1 保証することとAPIの限界

| 対象 | 保存・表示の契約 |
| --- | --- |
| キーボード入力 | 入力原文を保存。依頼文への書換えや要約で置き換えない |
| 利用者の音声 | APIの入力字幕を、空白・反復語を含め受信どおりに保存。「文字起こし」と表示し、音声認識が完全に正しいとは保証しない |
| AIの音声 | APIの出力字幕を受信どおりに保存。backendの返答やtool出力で代用しない |
| 同時発話 | 双方の字幕を独立して更新。到着順で擬似的な交互会話にせず、元のセッション時間も保持 |
| 再生 | 再生キューで追跡する。字幕の到着・appendのACKは、再生完了の証拠にしない |
| 途切れた会話 | 保存済みの断片を残し、未受信・再生不明を表示。欠けた文をLLMで補完しない |

公式仕様では字幕イベントにitem IDも発言完了イベントも無い。`start_ms`・`end_ms` は概算の区間で、単語ごとの正確な境界ではない。主WebSocketの出力音声には時刻とaudio-doneも無い。したがって、割込み時に「どの文字まで耳に届いたか」を一文字単位で保証する設計にはしない。**レビューで訂正:** 音声を保存するだけでも、字幕との正確な対応や利用者の実際の聴取を保証できるわけではない。厳密な照合を求めるなら、別の照合方式と精度評価が必要になる。録音の保存は今回の範囲に追加しない。

### 7.2 保存の形

Live接続と字幕断片を扱う小さな `live-voice` domainを設ける案。会話の表示本文の正本はconversationのままにし、二つの独立した会話履歴を持たせない。

- セッション: EumenesのID、会話ID、ProviderのopaqueなID、接続epoch、設定revision、状態、開始・終了時刻、終了usageの確認状態。
- 断片: ローカルで割り当てた受信連番、話者、元のdelta、`start_ms`・`end_ms`、受信時刻、表示メッセージ参照。連番をProviderのevent IDと偽らない。
- 委任: Providerの委任ID、offset、参照する字幕範囲とメッセージ、Eumenesのrun/operation、依頼revision、結果の状態。
- 配信: ローカル音声キューの再生・破棄・中断・不明、対応を確認できる範囲。字幕との正確な対応が無い場合は不明のままにする。

字幕の保存は認証情報やProvider全応答を保存するデバッグログではなく、利用者向けの会話データ。必要なフィールドだけを保管し、通常のログにはID・状態・理由コードのみを出す。

同じ受信経路のイベントへ受信連番を割り当て、保存後に表示へ通知する。再配信はローカル連番で排除し、原文の一致では排除しない（同じ言葉を二回話すことは正当）。Provider接続断の前後でexactly-onceを保証する材料が無ければ、新セッションとして扱い、欠落可能性を示す。

表示の吹き出しは原文断片から組み立てる。話者ごとに進行中の吹き出しを持ち、表示上の無音・時間・操作による区切りを意味的な発言確定と混同しない。遅れた断片は元の時間区間の吹き出しを更新する。数値の区切りはG0の実測後に決め、依頼の実行や承認の根拠に使わない。

conversationには受信済み本文とLive由来・記録状態を関連付ける契約を追加し、保存するたびに単一writerのtransactionで断片と表示用本文を更新する。暫定の断片をそのまま記憶担当の確定ソースへ流さず、既存outboxへ公開する時点を明示する。会話中の文脈は受信台帳から読み、通常の履歴・記憶へ渡す区切りはLLMが判断する。明示終了や保存確認で断片の保存自体は完了できるが、発言が意味的に完結したとは扱わない。

「再生済み」「中断」「再生範囲不明」を本文と分けて残す。聞かれていない範囲を次の会話で既知の事実として扱わない。既存の `heard: full/partial/none` に根拠なく写さず、不明を表せる共通配信契約の拡張を設計・試験する。

訂正・取り下げ・忘却は、表示本文と関連する原文断片、委任に保存した本文の写し、派生した記憶へ同じ公開操作で反映する。参照だけのrun/operation IDを残す場合も、忘却した本文を復元できないようにする。Live内部の文脈を消した証拠が取れない場合は接続を終え、忘却後の許可済み履歴から新しいセッションを開始する。

## 8 状態管理と障害時

セッションの状態はbackendの永続台帳を正本にし、Webは通知を受けて描画する。Live接続に必要な双方向音声以外の設定・履歴は既存APIを使い、定期pollingを追加しない。

- 終了: ローカル録音と新規委任を止め、`session.close` を送り、受信を継続して `session.closed` のusageを保存してから解放。待機上限後は「終了確認不明」。切断しただけで正常終了としない。
- 再接続: 利用者の操作で新セッション。許可済みの保存履歴と現行の仕事だけを渡す。Provider側の会話永続化には依存せず、`store: false` を指定する（データ保持全般が無効になるという意味ではない）。既存の仕事を再実行しない。
- キー更新・許可取消: 古い接続の音声送信・再生・委任を止め、古い世代の後着結果を採用しない。
- 保存失敗: 「会話を保存できないため停止」と表示し、新しい外部操作を始めない。受信済みなのに未保存の内容を保存済みとして表示しない。
- ページ離脱・プロセス異常: 音声資源を解放し、次回の復旧時に未終了セッションを「中断・終了usage不明」とする。再接続には新しい明示操作が必要。

## 10 実装順序・検証・受入

| 段階 | 内容 | 通過条件 |
| --- | --- | --- |
| G0 公式契約と成立性 | 検証用セッションで権限・字幕・日本語・同時発話・PCM再生・中継遅延を測定。許容する遅延目標を利用者と決める | 表示用の区切り、字幕と再生の対応限界を記録。要件を満たさなければ実装を広げず設計を再検討 |
| G1 設定と秘密 | 共通設定の追加と専用画面、接続とmodel/voiceの保存、キーの失効 | 秘密の非露出、鍵欠落、競合、キー変更、未保存テスト拒否のfixtureが通る |
| G2 接続と記録 | 開始・休止・終了、原文保存、重複防止、同時発話、訂正・忘却 | 再読込で本文が一致。保存失敗・切断・再接続でも二重記録や欠落の隠蔽がない |
| G3 toolchain結合 | 委任と既存run、短い返答・質問・承認・非同期仕事、文字補足 | 同じ依頼で同じ担当・権限・承認を使い、二重実行・二重発話・架空の完了報告がない |
| G4 通しと実機器 | ブラウザE2E、実API、本人のマイクとスピーカーで3往復以上 | 下記の受入を満たし、fixture・実API・実機器の記録を分ける |

G0でも最初は資格情報なしのプロトコルfixtureを通す。実接続は保存済みの資格情報と送信許可がそろってから行い、未登録ならG1の設定保存を先に用意する。キーをこのチャットへ貼るよう求めたり、検証専用の平文設定を作ったりしない。

検証は部分→結合→通し。実装前の対象fixtureを採取して変更前後を比較する。関連domainは `bun run verify -- --domain settings --domain live-voice --domain conversation --domain dialogue --domain voice-dialogue --domain inference --domain continuity --domain delivery --domain capabilities` を基本に、依存が実際に変わる利用側を追加する。新規domain登録前は存在する対象だけを検証する。結合試験の対象ファイルは実装時に明示し、domain verifyだけで通ったことにしない。

Webの設定・Composer・共有音声と既存文字入力を検証し、E2Eは新設するLive用ファイルと影響する既存の設定・会話ファイルを個別に指定する。実際の試験パスはG1開始時に確定する。文書だけの本タスクでは、製品のverify・課金接続・サーバー操作は行わず、参照と差分を点検する。

実機器受入には、通常の3往復に加え、相づち、同時発話、途中での訂正、音声からtoolchain実行、確認が必要な操作、担当からの質問への短い返答、文字補足、割込み、マイク休止、キー失効、保存失敗、切断と再接続、終了後の履歴再表示を含める。同一語句の反復を落とさないことも確認する。

Live開始から終了まで、双方の会話ログは増え、既存ASR/TTSはOFFの吹き出しとなり、通常の認識・合成要求件数は増えないことを追加受入条件とする。開始直前から継続していた要求の取消、失効後の後着結果、通常音声へ戻す明示操作もfixtureで検証する。

担当外の失敗は調査結果と影響を記録し、要求・試験を弱めたり無断で修正したりしない。同じ仮説の再試行が3ラウンド続く場合は作業規則に従って俯瞰し、次の編集前に方針を通知する。

## 14 実装に先立つ契約の具体化（2026-10-31）

利用者「では実装開始してください。最後までやりきってください」を受け、レビューの必要事項を以下で具体化してから実装する。基本方針を維持し、承認条件や担当の判断方式を弱めない。

- R1: 連続PCMの入力と出力キューを共有音声機器に接続する。ブラウザとbackend間は既存のBearer認証付きHTTP操作とSSEを使い、backendとProvider間の主WebSocketだけを新設する。音声は短い連続区間を順序付きで送り、遅延・キューの上限で停止する。通常ASR/TTSとLiveは同時に動かさない。
- R2: 正確な案内・確認はLive画面のホスト通知にも提示する。通常の案内は実際の画面描画を配信確認とし、確認文には利用者が内容を確認する操作を設ける。画面への配信と音声聴取を別の証拠として記録する。LiveのACKで既聴を捏造せず、既存の配信条件はこの画面配信の証拠で満たす。操作の承認自体は既存のLLMと確認ID・対象・版の検査を通す。
- R3: 進行中の字幕はLive台帳からチャットに表示し、通常のmessagesには途中の追記をしない。受信範囲を閉じた時に原文のまま一度だけ通常履歴へ公開する。表示上の無通信・容量・委任時のスナップショット・明示終了は受信範囲の境界としてのみ使い、発話の意味的完結や実行許可の判断には使わない。未完の断片も原文を失わず、LLMの解釈には途中である可能性を知らせる。
- R4: 委任は入力の受信範囲と版を固定してから既存のroutedハーネスへ渡す。文脈が無い通知は保持し、字幕の更新で再評価する。同じ入力範囲の複数通知は同じrunを参照する。後続の入力がある場合は古いrunの実行前に版を確認し、未引渡しの古い実行を不採用にする。引渡し済みの仕事は音声の割込みだけで取り消さず、訂正・取消の意味は既存のLLMと仕事の操作に委ねる。
- R5: 主会話と専門担当の返答、agencyが話す提案の出力先をLiveへ接続する。backendの案文は利用者へ実際に話した文として会話に重複保存せず、Liveの出力字幕だけを発話として記録する。ホスト通知は話者の発話と区別する。提案の受付と実際の配信も区別する。
- R6: fixture→設定→最小音声接続→その製品経路での実接続測定→保存・委任結合→通しの順に進める。サーバー操作は本依頼でも許可されていないため実施しない。
- R7: Liveには独立したクラウド送信許可を保存する。モデルは保存済み接続の一覧から取得し、名前で適性を分類せず接続テストで確認する。声は任意の指定値を保存し、空欄ならProviderの既定を使う。接続epoch・送信許可・無効化だけを即時失効とし、モデル・声・人格の変更は次回に適用する。

残作業は設定と専用画面、Live台帳・接続、連続音声、既存会話の配信先接続、OFF表示と排他、回帰・結合・通し検証。実API権限・日本語品質・実機器3往復は結果が得られるまで未検証として記録する。


## 15 実装結果

設定は `settings.live@1` と `settings.hub@9` をbundleで登録し、既存の共通下書き・資格情報・設定adapterを使う。開始・休止・終了は新設live-voice domainが管理し、API認証、連続PCM、SSE、字幕原文の台帳、既存messagesへの一度だけの公開を接続した。モデルは保存値だけを使用する。

既存dialogueの受付・選択・実行・承認を公開portで再利用した。文字入力はLiveへthinkingとして伝え、同一入力版の委任で既存runを再利用する。案内は画面描画、確認文は明示操作を配信証拠とし、音声を既に聞いた記録へ置き換えない。主返答・専門担当・agencyの案文をLiveへ返し、通常の発話履歴には出力字幕を保存する。会話の訂正・削除はrawの複製にも反映し、Liveを中断する。

通常ASR/TTSの受付・試聴・自動読み上げ・replayを抑止し、設定のサービス試用も音声の種類だけを停止・拒否する。他の種類のサービス試用は維持する。Liveの接続中状態を保存してから従来音声を停止し、新しい通常要求が入り込まない順序とした。OFF表示はComposerとStatusBarへ反映した。接続終了状態はSSE切断・設定パネル離脱後にも状態照会で追従する。試用字幕は終了時・異常終了時の復旧で削除する。

これらは§14の共通契約の実装であり、担当の検索順位・承認条件・意味判断を変更していない。連続PCMと主WebSocketは公式外部契約のための専用部分、入力版・epoch・容量・順序の分岐は契約と失効の強制である。特定の利用者発話、題材、モデル名に対応した製品分岐は追加していない。

利用手順は[音声会話](../docs/live-voice.md)、試験結果・失敗原因・残作業は[実装・検証記録](verification/live-voice-2026-10-31/results.md)に記録する。稼働中の設定APIの読み取りではLiveは無効、送信許可OFF、接続・モデル未選択だった。設定とAPIキーは変更せず、サーバー操作・実APIの課金接続は実施していない。
