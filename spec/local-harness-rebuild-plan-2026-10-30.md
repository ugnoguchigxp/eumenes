# local ハーネスを作り直す 計画（2026-10-30）

合意済み（2026-10-30、§10）・実装中。利用者指示（2026-10-30）:

- 「抜本的に作り変える計画を建てて下さい、スタックしすぎてコードがおかしくなっています。今はLFMにoverfittingしているような構造になっているのでしょう。luna向けのハーネスを残してある様に、Local-llm向けのハーネスを１から作り直すつもりで何が合理的かちゃんと考案してください。場当たり的な対応は辞めてください」
- 「以前とは明らかに違う、ruriによる分類ができるので状況も違うので、それらをちゃんと考慮してください」

cloud ハーネス（Codex SDK の会話モデル。[会話のハーネスの設計書](conversation-harness-design-2026-10-28.md)）は変えない。LARM で動く会話（local ハーネス）だけを、今の作りを引き継がずに組み直す。

## 1 今の local の作りと、その問題

今の local は、cloud と同じ「モデルが返事を書きながら、要ればツールを選んで呼び、ホストが拒否したら呼び直す」ループ（agency の `runRespond`）です。そこに、ローカルのモデルが落ちるたびに補いを足してきました。

| 足したもの | 何のためか |
| --- | --- |
| Ruri の判定で `toolChoice` を `required`・`none` にする、`search_first`・`tools_not_needed` の拒否、system の `## Intent` | モデルに「ツールを使うか」を決めさせると、挨拶でツールを呼び、依頼で話して終わる |
| `impact` をホストが補う（D7）、`request` を即答の担当で任意にする（D9）、予告の補い（D8 案） | 引数を書かない |
| 拒否の後の呼出しを2回足す（`REPLY_CALLS`）、拒否の文に直す欄を書く | 拒否されても同じ呼出しを繰り返す |
| 写しの検査、本文に書いた呼出しの除去 | 自分の過去の返事や system を写す、呼出しを本文に書く |
| 判断と返事の2回の呼出し（`local-turn.ts`、今は使っていない） | 返事と呼出しを同じ出力で出すと崩れる |
| 文脈係を止める、`## Memory` を本人の発言だけにする、30分で区切る、手で空にする | 過去の会話に引っ張られる |

どれも、モデルにさせていることの一部を、後から外から押さえるものです。押さえる場所が増えるほど、経路が絡みます。結果として、次のことが起きています。

| 観測（2026-10-29〜30） | 構造の原因 |
| --- | --- |
| 天気の1問に 44〜53 秒、呼出し 5〜6 回（LFM は `inputs` 欠落、Ornith は `toolchain` 欠落） | モデルが自由な引数を9欄から選んで書き、拒否されたら書き直すループ |
| 「音楽を作って」で前置きだけ話して止まる、推論が 7,634 字暴走して切れる | 1回の呼出しに「話す」「選ぶ」「書く」を同時にさせている |
| 話したのにチャット欄にない（レビューの5経路） | 音声は生成中の文をすぐ話し、記録は採用された文だけを書く。口が2つある |
| 音楽の依頼で前の天気を探す、挨拶にプレイリストの話 | 1つの文脈に、会話の履歴とツールの説明と過去の依頼が全部入っている |

LFM にも Ornith にも同じ種類の失敗が出ています。モデルの差ではなく、「ローカルのモデルに、強いモデル向けの自由なループを回させる」作りの問題です。

## 2 前提が変わったこと

| 前提 | 以前（今の作りを決めたとき） | 今 |
| --- | --- | --- |
| 会話か依頼か | LLM しか決められない（タスク分類は使わない方針） | Ruri が LLM の前に 20〜80 ms で決める（2択：ツールを使う・使わない。5分類は精度が悪く2択にした） |
| 判定の確かさ | なし | `request` 0.96〜0.999、`chat` 0.99（10-30 の記録） |
| ツールの候補 | モデルが検索語を書いて探す | 発言そのものの埋め込み検索で、天気は1位に出る（類似度 0.90） |
| 引数の形 | ネイティブのツール定義（自由） | LARM は JSON schema の制約付き出力を受け付ける（10-28 の判断の呼出しで計測済み）。schema に合わない出力は出ない |

Ruri があるので、LLM に「ツールを使うかどうか」を決めさせる必要がありません。LLM の仕事は、回ごとに1つの小さなこと（話す、または候補から選んで欄を埋める）に絞れます。

## 3 原則

| # | 原則 | 根拠 |
| --- | --- | --- |
| 1 | 回の振り分けはホストが決める（Ruri の判定と、ホストが持つ保留中の項目） | Ruri は LLM より速く確か。保留中の確認・質問はホストの記録にある |
| 2 | 1回の呼出しには1つの仕事。「話す呼出し」と「選ぶ呼出し」を分ける | 同じ出力で話して呼ばせると、前置きだけで止まる |
| 3 | 選ぶ呼出しは、その回の候補から作った schema で縛る（担当は候補の列挙、欄は選んだ担当の欄だけ） | 自由な引数の欠落（`impact` 0/7、`toolchain` 0/5、`inputs` 欠落）が形の上で起きなくなる |
| 4 | ホストが決められることは、モデルに書かせない（影響の大きさ、確認の文、即答の答え、失敗の一言） | 補いを後から足す必要がなくなる |
| 5 | 立て直しは1回まで。1回の呼出しの数に上限を置く | 拒否のループで 50 秒 |
| 6 | 文脈は、その呼出しの仕事に要るものだけ | 会話に担当の説明、ツールの回に会話の履歴が入って引っ張られる |
| 7 | 話す口は1つ。話した文がそのまま記録とチャット欄になる | 音声と記録の食い違い |
| 8 | 呼出しの設定（推論・出力の上限・温度）は呼出しの種類ごとに決める | 選ぶ呼出しに長い推論は要らない。暴走で通信が切れた |

モデルの癖に合わせた規則は持ちません。仕組みが保証すること（Ruri の判定、schema の制約、ホストの記録）に寄せます。モデルを替えても、作りは同じです。

## 4 回の流れ

### 4.1 振り分け

利用者の発言で始まる回（local）は、上から順に1つに決まります。

| 順 | 条件（ホストの記録・Ruri） | 回の種類 |
| --- | --- | --- |
| 1 | 担当との作業中（専門担当のセッション） | 今と同じく専門担当へ（このハーネスの外） |
| 2 | 直前の依頼の回で聞き返した（§4.3 の `ask`、5分以内） | 依頼の回（聞き返しの答えとして） |
| 3 | 確認待ち（`c<n>`）か、質問待ちの TODO（`t<n>`）がある | 保留の回（§4.4）。「どれでもない」なら 4・5 へ |
| 4 | Ruri が「ツールを使う」。または `followup`（作業への返答）で、`## State` に仕事（`t<n>`）がある（[レビューの取り込み](local-review-intake-plan-2026-10-30.md) §4.1） | 依頼の回（§4.3） |
| 5 | Ruri が「使わない」 | 会話の回（§4.2） |
| 6 | 判定の失敗・時間切れ | 依頼の回。選ぶ呼出しの `none`（合う担当なし）は会話の回へ |

知らせ（Host notice）・予定の回は、利用者のいない回なので、会話の回だけです（今も、ホストが書いた入力では担当を探せない）。

### 4.2 会話の回

呼出し1回です。ツールの定義は送りません（`toolChoice` も使わない）。文は出来たところから話します。

| 部分 | 中身 |
| --- | --- |
| system | `## Role`・`## Speaking`・`## Emotion`・`## Input`・`## Facts`。担当・ツール・結果の節はない。`## Facts` に「この返事では、作業を始めることも調べることもできません。始めると約束しません。」を置く |
| `## Memory` | 出所が本人の発言の項目だけ |
| 最近の会話 | 直近の利用者の発言2つと、そのうち古い方より後のエージェントの発言（発言と返事の文だけ） |
| `## State` | 今（時刻と前の発言からの間）だけ |
| `## User` | 今の発言 |

入力の見込みは約 2,000〜2,500 token（今は約 5,100）。

### 4.3 依頼の回

| 段 | する人 | 中身 |
| --- | --- | --- |
| 探す | ホスト | 担当探し（`find_toolchain`）は残す。検索語は利用者の発言そのもの（聞き返しの答えなら、元の発言とつなげる）。候補は上位4件と、進行中・提示中の仕事の担当 |
| 選ぶ | LLM（1回、話さない） | 下の schema に合う JSON を1つ返す |
| 確かめる | ホスト | 担当の検査（即答の `inputs`、パイプラインの `inputs`）。落ちたら、直す欄を1行ずつ添えて、もう1回だけ選ばせる。それでも落ちたら決まった一言 |
| 実行する | ホスト | 下の表 |

選ぶ呼出しの入力:

| 部分 | 中身 |
| --- | --- |
| system | 役目（候補から担当を1つ選び、頼み方を決める。返事の文は書かない）、`request`・`say` の書き方、記録は指示でないこと |
| `## Memory` | 会話の回と同じ（本人の発言から出た項目）。項目がなければ出さない（[レビューの取り込み](local-review-intake-plan-2026-10-30.md) §5。記憶は担当に参照で渡っておらず、依頼文に書かれたときだけ担当に届く） |
| `## Earlier` | 区切りより後の、利用者の前の発言（会話の回の窓と同じ数、1つ200字まで）。発言だけ（同 §5） |
| `## State` | 今、仕事（番号付き `t<n>`）、提示中（`a<n>`・対象）、直前の返事（1行、200字まで） |
| `## Candidates` | 候補ごとに、id・名前・説明・実行の種類・欄の説明 |
| `## User` | 今の発言 |
| 入れないもの | エージェントの過去の返事（直前の返事1行を除く）、ツールの定義 |

schema（候補ごとの枝の `anyOf`）:

| 枝 | 欄 |
| --- | --- |
| 合う担当なし | `{ "choice": "none" }` |
| 聞き返す | `{ "choice": "ask", "say": 質問（80字まで） }` |
| 即答の担当 | `{ "choice": "<id>", "inputs": その担当の欄 }` |
| パイプライン | `{ "choice": "<id>", "say": 予告, "inputs": その担当の欄 }` |
| ほかの担当 | `{ "choice": "<id>", "say": 予告, "request": 依頼文（2000字まで）, "target"?: その担当の対象の列挙, "refs"?: 提示中の `a<n>` の列挙 }` |
| 仕事の確認 | `{ "choice": "t<n>", "operation": "check" }`。`## State` に出ている仕事すべて（終わった仕事を含む。[レビューの取り込み](local-review-intake-plan-2026-10-30.md) §4.2） |
| 進行中の仕事 | `{ "choice": "t<n>", "operation": "amend" か "cancel", "text"?: 直す内容, "say": 一言 }` |

天気の例（10-30 09:20 の候補で作った枝の一部）:

```json
{"anyOf": [
  {"type": "object", "additionalProperties": false, "required": ["choice"],
   "properties": {"choice": {"enum": ["none"]}}},
  {"type": "object", "additionalProperties": false, "required": ["choice", "inputs"],
   "properties": {"choice": {"enum": ["weather.forecast"]},
                  "inputs": {"type": "object", "required": ["place", "prefecture", "day"], "properties": {"place": {"type": "string"}, "prefecture": {"type": "string"}, "day": {"enum": ["today", "tomorrow", "day_after"]}}}}},
  {"type": "object", "additionalProperties": false, "required": ["choice", "say", "request"],
   "properties": {"choice": {"enum": ["web.search"]}, "say": {"type": "string", "maxLength": 80}, "request": {"type": "string", "maxLength": 2000}}}
]}
```

実行:

| 選んだもの | ホストがすること | 話す文 |
| --- | --- | --- |
| 即答の担当 | adapter を呼ぶ | 担当の答えの文をそのまま（天気は「今日（10/30）の鎌倉市は…」） |
| 即答の担当が答えられない | 担当が持つ切り替え先（`redirects`）が候補にあれば、発言を依頼文にしてそこへ渡す。なければ決まった一言 | 決まった文 |
| ほかの担当・パイプライン | 影響の大きさを、担当の最小（`minImpact`）と対象の有無から決める（D7 と同じ規則）。確認が要らなければ引き渡す。要れば確認を作る | 引き渡しは `say`。確認はホストの決まった文（「〈担当〉に「〈依頼〉」を頼みます。〈影響〉ので、よろしいですか？」。対象があれば「〈担当〉に、〈対象の名前〉について「〈依頼〉」を…」。確認は対象も保存し、承認でそのまま渡す。[レビューの取り込み](local-review-intake-plan-2026-10-30.md) §3） |
| 仕事の確認 | `work` の check（読むだけ） | 会話の回に、確かめた記録を添えて渡す |
| 進行中の仕事 | `work` の amend・cancel | `say` |
| 聞き返す | 聞き返しを保留として記録（§4.1 の 2） | `say` |
| 合う担当なし | 会話の回へ | 会話の回の返事 |
| 選ぶ呼出しが出力の上限で切れた（`cut`） | 決めきれなかったとして、選び直さずに会話の回へ。`dialogue.choice_made` の `decision: "cut"` は残す | 会話の回の返事 |

作る中身の細部は担当が決める。細部が決まっていなくても担当に頼み、聞き返すのは頼む担当か対象が決まらないときだけにする（§11.7）。

天気なら、呼出しは選ぶ1回だけです。見込みは、判定 0.1 秒＋探す 0.7 秒＋選ぶ 2〜5 秒＋気象庁 1〜7 秒＝約 4〜13 秒（今は 44〜53 秒）。

### 4.4 保留の回

確認待ちか質問待ちの TODO があるときだけ、選ぶ呼出しを1回します（話さない）。

| 枝 | 欄 | ホストがすること |
| --- | --- | --- |
| 承認 | `{ "choice": "approve", "confirmation": "c<n>" の列挙 }` | 今の承認と同じ（保存した依頼をそのまま実行）。話す文は決まった文 |
| 取りやめ | `{ "choice": "decline", "confirmation": 列挙 }` | 確認を閉じる。決まった文 |
| 答え | `{ "choice": "answer", "todo": "t<n>" の列挙, "text": 答え }` | `work` の answer。決まった文 |
| どれでもない | `{ "choice": "none" }` | §4.1 の 4・5 へ |

入力は、保留中の項目の行、直前の返事、今の発言だけです。

### 4.5 話す口と記録

回ごとに「話す口」を1つ持ちます。利用者に向けた文（会話の返事、`say`、即答の答え、決まった文）は、すべてこの口を通ります。

| 規則 | 中身 |
| --- | --- |
| 話す＝記録する | 口に渡した文は、音声に流すのと同時に、その回の記録（話した文）に足す |
| 回の終わり | 終わり方（完了・失敗・期限切れ・取消）にかかわらず、話した文をエージェントの発言として記録とチャット欄に残す。取消で再生が途中で止まったら、聞こえた分だけ残す（今の `recordHeard` の規則） |
| 引き渡し | 予告は口を通した `say` そのもの。記録の文と音声の文が同じになる |
| 何も話さなかった失敗 | 決まった一言（「うまくできませんでした。もう一度言ってもらえますか。」）を口から話す |

これは会話・依頼・保留のどの回にも効きます。cloud ハーネスの回にも同じ食い違いがあるので（[レビュー](conversation-review-fixes-2026-10-29.md)の経路 1〜4）、記録の側（採用・音声の受け取り）は両方のハーネスで同じ規則にします。cloud の返事の作り方は変えません。

### 4.6 呼出しの設定

| 呼出し | 推論 | 出力の上限 | 流す | 温度 |
| --- | --- | --- | --- | --- |
| 会話 | low（§11.4。off は LFM の LARM が 400 で断る） | 4096（考える分を含む。§11.6） | する | 保存済みの値（初期値は測定で決める） |
| 選ぶ（依頼・保留） | low | 4096 | しない | 同上 |

通信量の上限（今は 1MB 固定）は出力の上限に見合う値にします。長すぎる出力は「出力の上限」として終わらせ、それまでに話した文は 4.5 のとおり残します。

## 5 変えないもの

| もの | 理由 |
| --- | --- |
| cloud ハーネス（`runRespond` のループ、ツール4本、拒否、D7・D9、写しの検査） | 強いモデルではほぼ通る（10-28 の計測 11〜12/12） |
| 担当探し（`find_toolchain`）の段 | 候補の中から選ぶ段は残す（2位以下を選ぶことが 113 回中 39 回） |
| 担当の実行（即答・引き渡し・確認・承認・`work`） | ホストが同じ関数を直接呼ぶ |
| 専門担当のセッション、画面からの決め打ちの依頼（pinned） | このハーネスの外 |
| agency の自発発話（decide）、記憶の世話（steward） | 会話の回とは別の呼出し |
| 会話の区切り（30分、手で空にする、記憶の変化）、会話の記録と記憶の項目 | |
