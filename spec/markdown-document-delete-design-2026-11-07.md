# Markdown文書の削除

後続の利用者提示仕様に従い、[ライブラリ拡張への対応](markdown-library-api-design-2026-11-07.md)へ統合した。本書は事前調査の記録として保持する。以下の単件削除案を配備済み仕様や実装完了の根拠としては使わない。

2026-11-07。利用者の追加依頼「mdファイルを作るだけではなく、削除する方法も提供」に対応する設計。削除を対象外とした従来の一覧・保存設計に対する追加であり、実装済みではない。

## 目的と完了条件

文書一覧の各Markdown行から削除を選び、文書名・保存場所を確認して削除する。成功後はDoclingの正本がなくなり、一覧と対応する作業用文書から除かれる。未保存の作業用文書は、その下書きだけを削除できる。フォルダ・一括削除・ごみ箱・版履歴は追加しない。

## 確認した既存機構と不足

既存のlibrary/open/select、一覧・編集ビュー、DesignSystemの削除・確認部品、backendの文書ID・ETag・接続binding・revision検証、単一writer、保存queueを再利用する。文書の意味分類やLLMの判断方式は変更しない。専用処理は外部削除操作と対象・状態・権限の検証に限る。

本番の保存済み接続先をsettings domainのreadonly操作で取得し、2026-11-07 18:27 JSTにGETで確認した。`/v1/docling/capabilities`は`methods:["GET","PUT"]`、`/openapi.json`の`/v1/docling/documents/{id}`も`get`と`put`だけだった。[確認記録](verification/markdown-document-delete-2026-11-07/discovery.json)。文書は変更していない。

EumenesのDocling client、Markdown公開操作・API・Artifactにも文書削除はない。既存のHTTP接続を拡張できるが、保存先に削除を実行する公開契約が不足している。空のMarkdownで上書きする、一覧から隠す、保存先のDB・ファイルを直接操作する方式では代替しない。

## 追加する保存先の契約案

LARM側への[依頼内容](reference/larm-document-delete-proposal-2026-11-07.md)は提案であり、配備済み仕様ではない。LARM側の実装・公開OpenAPI・capabilities確認を、Eumenesの正本削除の実装と実接続試験の前提とする。Codexの登録情報と既存参照資料から、作業場所はgnosis上の`/srv/ai/apps/local-LLM-harness`と確認できた。現行のDocling作業指示はSSH・配備変更を対象外としているため、保存先側まで変更範囲に含める合意の前に遠隔操作・実装は行わない。

## Eumenesの削除導線

1. 保存文書の行に削除アイコンを置く。対象の文書名と場所、Doclingの保存文書と対応する作業用文書を削除すること、未保存入力を失うことを確認ダイアログで示す。取り消した場合は何も変えない。
2. 一覧で確認した対象IDと正確なETagをbackendへ渡す。対象は最新の保存先bindingで検証し、GETで取得した新しいETagへ黙って載せ替えて削除しない。
3. 保存処理中・保存結果不明・共同編集で使用中は削除を拒否し、状態を解消してから操作する。文書単位の共通実行制御で保存と削除が競合しないようにする。
4. LARMの削除成功を確認してから、同じ保存先・外部IDに対応するEumenesの作業用状態を単一writerで整理する。遅れて届いた保存・編集の結果が文書を再作成しないよう、既存revision・存在・bindingの検証を通す。
5. 一覧を更新し、対象を開いていた場合はファイル一覧へ戻す。該当するブラウザー下書きは成功後に削除する。失敗時は一覧と入力を残す。
6. 作業用文書の一覧では「作業用文書を削除」と明示する。Doclingに対応する正本を消す操作とは分ける。保存・共同編集中の扱いは上と同じとする。

412は更新競合として保持し、再確認するまで削除しない。403は削除不可を表示する。通信断・5xxでは結果不明とし、DELETEを自動再送しない。読取りで現在の不存在を確認できた場合も、操作履歴の証明とは表示しない。結果が確定するまで手元の文書を破棄しない。

既存SSD cacheは一時ファイルのままで、共通の整理・貸出・寿命ルールに従う。削除機能のためにscratch storeや削除APIを新設せず、ごみ箱や復元可能な正本として扱わない。

## 実装順と検証

1. 保存先の追加契約について合意し、LARM側で実装・検証・配備する。正確なレスポンス、ETag、失敗時の契約を確認する。
2. 既存Markdown・Docling・Artifact試験をbaselineにする。Docling clientとbackend削除操作を追加する。SQL・業務検証・試験はMarkdown domain、外部接続はDocling domainに置く。
3. 登録手順に従い、必要なArtifact action/binding/schemaの新revisionを追加する。既存revisionを上書きしない。一覧の削除アイコン・確認・失敗表示・選択解除へ接続する。
4. 部分試験では正確な対象・ETag、取り消し、失敗時の入力保持、保存中の拒否、遅い応答、重複実行防止を確認する。結合では実queue/writerと公開API、保存文書・作業用文書の違い、別文書不変を確認する。
5. `bun run verify -- --domain markdown --domain docling --domain capabilities --domain artifact`で利用側も確認する。既存のinventory問題で停止した場合はその結果と個別検査を区別する。
6. 利用者によるEumenes再起動後、検証専用文書を使って確認ダイアログ、削除後の一覧・GET、編集中文書と別文書への影響を実画面で確認する。既存の利用者文書を検証で削除しない。サーバー操作は行わない。

現在の残作業: 保存先側の契約・変更範囲の合意、LARM側の実装と配備、Eumenesの実装、部分・結合・通し検証。今回実施済みなのは既存実装と本番公開契約のreadonly調査、変更前baseline、作業場所の確認、およびこの追加設計まで。
