## 0. 要点

| 分かったこと | 中身 |
| --- | --- |
| 不合格の大半は「書いたが読めない」 | 78 件のうち、確認の問いで `read_history` を別の会話で引いて空だったものが 23 件、`read_memory` の照合が外れたものが約 10 件、`read_memory` を語なしで呼び新しい順 16 件に入らなかったものが約 10 件、道具を呼ばずに「記録にない」と答えたものが約 13 件 |

提案の柱は 3 つ。(a) 件数の上限をなくし、文脈に載せる量だけを測って決める（§4）。(b) 読む側を直す: 照合の修正と、関係する記録をホストが選んで載せる方式（§5）。(c) 評価を本番の記憶から切り離す（§6）。

## 1. 目的と、やらないこと

| 項目 | 内容 |
| --- | --- |
| 目的 | live 評価の低い区分（音声認識の誤り・再学習・時間推論・統合の劣化・複数会話の推論・能動的利用・更新・抽出・保持）の失敗の原因を特定し、改善案と優先順位を決める。記憶が増えたときの保存・検索・文脈への載せ方を、件数の上限を前提にせず決め直す |
| やらないこと | 実装。評価の実行。睡眠の層の規則の変更（深い整理の中身）。目標の二区画の一本化。記憶のためのツールの追加（作り直し設計 §0 の決定を保つ） |
| 守る規則 | プロンプトに例文を入れて挙動を固定しない。モデル名・profile 名を書かない。domain の判断・SQL は各 domain に置き、下位 domain は上位を参照しない |

### 2.6 評価の仕組みが原因のもの

| 事象 | 根拠 | 影響 |
| --- | --- | --- |
| 全ケースが本番の利用者の記憶 1 つ（`profile:owner`）を共有する | 記憶の一覧に、ケースの値（恵子・ミル・掛川・ハスラー・久保田）と利用者本人の記録（開発・研究の関心）が混ざっている。`extraction-002` の返事は別ケースの「札幌の円山」 | 後のケースの発言が前のケースの記録と食い違い、L2 に入らない（`open_question` 62 件の多くは「不動産会社の記録に対し印刷会社と述べている」の類）。注入 3・迎合 2・更新 1 は混入だけで不合格。上限の 100 件にも評価の途中で達した |

## 3. 改善の構成

| 層 | 今 | 変えた後 | 節 |
| --- | --- | --- | --- |
| 保存 | 有効な記憶 100 件まで。背景のパスは超えると L1 へ | 件数の上限なし。重複と食い違いは件数ではなく照合で抑える | §4.1 |

## 4. 記憶の量が増えたときの設計（件数とトークンの上限の見直し）

### 4.1 保存: 件数の上限を置かない

| 項目 | 内容 |
| --- | --- |
| 今の上限の理由 | `curation-shared.ts` のコメントは「Keeps the fixed view inside its byte budget」。記憶の全件を 1 つの固定の表示に入れていた頃の都合で、保存の都合ではない。今は全件を入力に入れる処理は無い（記憶担当の全件一覧は作り直しで廃止） |
| 上限が起こしたこと | 上限は記憶の質を守らず、101 件目以降の本人の言葉を黙って読めない場所へ回した（§2.4）。重複 3 件を残したまま新しい事実を落とす |
| 変えること | 件数で書き込みを拒否しない。`explicit.ts` の `limit_reached` の分岐と、`always-on-records.ts` の「満杯なら L1 へ」の分岐を消す。L1 は推定・観測だけの場所に戻す |
| 件数の使い道 | 拒否の壁ではなく、整理のきっかけにする。有効な記憶の件数と、同じ事柄の重なりの件数を睡眠の層の起動の条件（作り直し設計 §6.1 の「一定量以上」）に足す |
| 残す上限と理由 | 1 件の本文 500 文字（`MAX_TEXT_CHARS`）: 1 件が区画の枠を食い尽くさないため。引用 1,024 バイト・根拠 8 件: 記憶ライブラリの保存の形 |
| 件数が増えても遅くしない | 書き込みのたびの全件の読み出し（`explicit.ts` の `listed`、`always-on-recall.ts` の `currentItems`、`context-window.ts` の `itemsNow`）を、鍵での照会と全文索引（`memory_state_fts`、3 文字組。`semanticKey` と本文と属性が入っている）に置き換える。数百件までは今のままで足り、置き換えは件数が 1,000 件を超える前に行う |

`limit_reached` はほかにも使われている（`curation-state.ts:84`、`candidates.ts:188`、`exclusion.ts:64`、`tendency-write.ts:101`、`curation-tendencies.ts:68`、`curation.ts:24`、`seeds.ts:42`、`maintenance.ts:113`）。件数の上限によるものと別の上限（傾向・除外）によるものが混ざっているので、実装の前に 1 つずつ分ける（未確認）。

### 4.2 文脈への載せ方: 3 つの区画

| 区画 | 置き場所 | 入るもの | 変わる頻度 | 量の決め方 |
| --- | --- | --- | --- | --- |
| 常時 | `## Memory`（固定の指示の次、履歴の前） | 本人の言葉の記録（`source=user_said`）。まず応答のしかたに関わる制約・好み、次に習慣、次に本人の事実 | 会話の区切りと、載っている記録の訂正・忘却・抑制のとき | 枠に収まる限り全部。枠は §4.3 で測って決める |
| その回 | 末尾（`## State` の隣） | その回の発言に関係する記録（常時に載っていないもの）。§5.2 | 毎回 | 件数と枠。毎回キャッシュされずに読まれるので小さく保つ |
| 検索 | 道具（`read_memory`・`read_history`） | 残り全部。推定・傾向は「推測」と付く | 呼んだとき | 1 回の結果 3,000 文字（今のまま）。関係の強い順 |

常時の区画に全部を載せる理由: 今の規模（本人の言葉の記録 73 件、本文の合計は 2,664 文字の内数）なら全部が載り、選ぶ処理も道具の呼出しも要らない。不合格 78 件のうち 46 件は「道具の選び方・語の選び方・呼ばない」で落ちており、これは載っていれば起きない。検索は、枠からあふれた分の受け皿として働かせる。

枠を超えたときの選び方（今の `keepOrder` を保つ: 出所 → 種類の順 → 新しい順）。あふれた記録は消えず、その回の区画と道具で読める。あふれが続くことを整理のきっかけにする（§4.1）。

本人の事実（`personal_fact`）を常時の区画に入れるのは、入力の仕様 §5.1（`## Memory` は好み・習慣・傾向・制約だけ）の変更に当たる。決定 C4（本人の言葉だけ。推定と過去の会話記録を載せない）は変えない。

### 4.3 枠の根拠

固定の数ではなく、測れる 3 つの量から決める。

| 量 | 今分かっていること | 決め方 |
| --- | --- | --- |
| 記憶の実際の大きさ | 有効 124 件で本文 2,664 文字。1 行は参照と出所の注記を足して 35 文字前後 | `estimateTextTokens` で、本人の言葉の記録を全部並べた大きさを測る。これが「選ばずに済む枠」の下限 |
| 1 回の入力の固定部分 | 実行ログ（`inference.input_sections`）の値は、ツール定義 4,760・system 3,045・入力 492〜553（単位は未確認） | 常時の区画がこの固定部分に対して何割増しになるかで見る |
| 区切りの後の最初の返事の遅れ | 未計測 | 常時の区画を 1,000・2,000・4,000 トークンにして、区切り直後の返事の最初の音までの時間を比べる。許す増分を利用者が決める（§9） |

推奨の初期値: 常時の区画 2,000 トークン（今の本人の言葉の記録が全部載る大きさ。計測で確かめてから確定）、その回の区画 400 トークン・8 件まで。値は SQLite の設定に置き、コードの定数にしない。

その回の区画を小さくする理由: 末尾は毎回キャッシュの外で読まれる。常時の区画は先頭側にあり、区切りまで同じ並びなので、2 回目以降はキャッシュから読まれる。大きくしてよいのは常時の側だけ。

### 4.4 上限をなくしたときに守ること

| 守ること | 危ないこと | 守り方 |
| --- | --- | --- |
| 文脈の大きさ | 記憶が増えるほど入力が膨らむ | 載せる量は枠で決め、件数では決めない。枠を超えた分は検索に回る。1 件 500 文字の上限を保つ |
| KV キャッシュ（先頭の一致） | 常時の区画が変わると、その後ろの履歴が全部読み直しになる | 常時の区画は区切りでだけ並べ直す（今の仕組み: 追加は次の区切りまで末尾の「新しい記憶」に出す）。並びは決定的にする（同じ記録なら同じ順・同じ文）。載っている記録の訂正・忘却・抑制だけは即時に区切る（今と同じ）。事実まで載せると区切りが増えるので、`dialogue.input_cut` の理由ごとの回数を記録して確かめる |
| 遅延 | 検索のために推論や通信が増える | その回の区画の検索は SQLite の中だけで行い、LLM も埋め込みの呼出しも足さない。道具の往復が 1 回減る（確認の問いの遅延は、道具を呼んだ回が 12〜20 秒、呼ばない回が 7〜9 秒） |
| プライバシー: 声に出る | 常時に載る記録が増えるほど、関係のない場面で口にしやすい。音声は周りの人にも聞こえる | 機微な情報（健康・宗教・信条など。作り直し設計 §2）と、ほかの人についての記録は常時の区画に載せない。本人がその話題を自分から出した回の、その回の区画と道具でだけ読める。抑制された記録は載せない（今と同じ）。機微かどうかの印が記録にあるかは未確認で、無ければ背景のパスの出力と `memory` ツールの引数に足す |
| プライバシー: 外に送る量 | 常時の区画は毎回の入力として推論の提供元に送られる | 常時に載せる範囲（応答の好みだけ／好み・習慣・制約／本人の事実まで）を設定で選べるようにする（§9） |
| プライバシー: 忘却 | 記憶の文が残る場所が増える | その回の区画は履歴に保存しない（毎回作り直す）。窓の保存（`memory_context_window`）は今の `purgeInTransaction` で消える。忘却の閉包の検査（作り直し設計 §9.2 の「対象の語が出ないこと」）に、その回の区画を足す |
| 質 | 上限が無いと重複と古い値がたまる | 書くときに似た記録を見つけて同じ事柄として扱う（§5.5）。重複の統合は深い整理（作り直し設計 §6.2「片方を失効させる」） |

## 10. 危ない点と、確かめられなかったこと

| 項目 | 内容 |
| --- | --- |
| 型の件数 | 主因 1 つで数えた目安。1 回の試行（3 回中 2 回の判定ではない）で、混入の影響を受けている。分離した後に測り直すと内訳は変わる |
| 道具を呼ばない 13 件 | 原因は確かめられていない（モデルの判断）。常時の区画とその回の区画で、呼ばなくても見えるようにする以外の手は出していない |
| 実行ログの入力の大きさの単位 | `inference.input_sections` の 4,760・3,045 がトークンか文字かは未確認 |
| 機微な情報の印 | 記録に印があるかは未確認。無ければ常時の区画から外す規則を実装できない |
| 語が違う問い | 常時の区画の枠を超える規模では、§5.1 の照合では当たらない。話題の語を書くときに付ける方式と、記録の埋め込み（発言の埋め込み `memory_turn_vector` は既にある）を使う方式の比較が要る。埋め込みの呼出しが返事の前に入ると遅延が増える |
| 区切りの回数 | 本人の事実を常時の区画に載せると、訂正のたびに区切りが入り、履歴が読み直される。回数は計測していない |
| `limit_reached` のほかの使い道 | §4.1 の 8 か所は中身を 1 つずつ確かめていない |
| `withdraw-003` | 前の返事の `applied` の ref が、次の回の入力から見えていたかは確かめていない |
| 会話の種別 | 検証用の会話を、会話をまたぐ検索から外す手段があるかは未確認 |
| 音声認識の誤り | 想起が直った後でないと、誤認識の扱いの設計（作り直し設計 §14 の「確信度を出所に含めるか」）に進めない |
| 遅延 | 4 件並行の実行の遅延は待ち行列を含む。遅延の比較は順に流した実行どうしで行う |
