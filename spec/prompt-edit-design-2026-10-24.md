# 直前のプロンプトを止めて編集する機能の設計

- 日付: 2026-10-24
- 状態: 合意済み（2026-10-24、§9 は推奨どおり）。実装済み（fixture 検証済み）
- 関連: [context-window-spec-2026-10-24.md](context-window-spec-2026-10-24.md)（§8.2 未処理の発言・行動の確定、§13 会話メッセージの訂正）

## 1 目的

送った直後に「言い間違えた」「条件を足したい」と気づいたとき、応答を止めて、その発言を直して送り直せるようにする。対象は**会話の直前の利用者の発言だけ**とする。過去の任意の地点まで会話を戻す機能（巻き戻し）は対象外。

## 2 範囲

対象:

- Web の会話画面での、直前の利用者の発言の本文の編集と再送信。
- 入力元は手入力と音声のどちらでもよい（音声の発言も本文は会話メッセージなので、同じ操作で直せる）。

対象外:

- 2件以上前の発言の編集、会話の巻き戻し。
- 添付の追加・削除（初版は本文だけ。添付はそのまま引き継ぐ。§9 Q3）。
- 専門担当の対話中に専門担当へ渡った発言、定期実行・通知の run（利用者のプロンプトではない）。
- 音声での「さっきのは無しで」などの操作（§9 Q4）。

## 3 編集できる条件

次をすべて満たすときだけ編集できる。判定は再送信の書き込みトランザクションの中で行う。

1. 対象のメッセージが、その会話の最新の利用者メッセージである。後に Agency の自発発話や通知があってもよい。後に別の利用者メッセージがあれば編集できない。
2. その発言の出来事（`said`、`by: user`）がまだ未処理（`pending`）である（ContextWindow §8.2）。生成が行動を確定すると発言は処理済みになるので、委譲・確認・仕事の操作・記憶への依頼が確定した後は編集できない。
3. その発言を元にした確定した行動の記録がない。つまり、そのメッセージを `messageIds` に含む `acted` のうち、確定した行動（`memory.request`・`delegate`・`confirm`・`work.*`。不採用時の再生成と同じ基準）がない。道具を探す（`find_toolchain`）・記憶を読む（`memory.read`）・即答（instant）は何も確定しないので数えない。2 と重ねて判定し、競合を防ぐ。
4. その発言の run が `queued`・`running`・`cancelled`（利用者の中止による）のいずれかである。応答が採用されて `completed` になった後は編集できない（直前の発言でも、既に答えた発言を変えるのは巻き戻しにあたる）。
5. 専門担当へ渡った発言（`to: specialist`）ではなく、run が利用者の入力（手入力・音声）である。

条件 2・3 の理由: 確定した行動（予告して委譲した仕事、記憶への依頼など）は、発言を直しても取り消せない（ContextWindow §13）。元の発言のまま実行が進んでいるのに発言だけ書き換えると、記録と実行が食い違う。そのため、行動が確定する前だけ編集を許す。

## 4 サーバーの処理

### 4.1 再送信 API

`POST /api/conversations/:conversationId/messages/:messageId/resubmit`

```json
{ "requestId": "<uuid>", "text": "直した本文" }
```

- `requestId` で冪等にする（同じ requestId の再送は同じ結果を返す）。
- 成功: `200 { "run": <新しい run> }`。
- 失敗（409、本文なし）: `not_latest`（後に利用者の発言がある）、`already_acted`（行動が確定した・応答が採用された）、`specialist_turn`、`not_editable`（定期実行・通知など）。空の本文は 400 `empty_text`。

### 4.2 一つの書き込みトランザクションで行うこと

1. §3 の条件を判定する。満たさなければ何も変えずに拒否する。
2. 元の run がまだ `queued`・`running` なら、中止と同じ扱いで終える（`endRun(..., "cancelled", "edited")`、キューのジョブの取消、エージェントタスクの取消）。推論の取消（`cancelSubject`）は書き込みの後に行う。発言は未処理のまま残る（§8.2、現行の中止と同じ）。
3. 本文が変わっていれば、会話メッセージを訂正する（`conversation.correctInTransaction`）。訂正のフックで、`log` にある未処理の `said` の文字列も訂正後に作り直され、窓の版が進む（ContextWindow §13、実装済み）。メッセージの ID は変えない。
4. 同じメッセージを入力とする新しい run と生成ジョブを作る（intake に「既存の未処理の発言の run を作り直す」公開操作を追加する。メッセージの追加はしない）。新しい run の生成は、その未処理の発言を最新の発言として読む。

本文が同じなら 3 を省き、送り直しとして 4 だけ行う。

新しい run について:

- 入力メッセージの run は新しい run に付け替える（`conversation.moveToRunInTransaction`）。記憶は run の入力と回答を一組として扱うため。
- 編集は手入力なので、新しい run は音声の発言からでも `manual` とし、`utteranceId` は持たない（音声の発話 ID は元の run に残る）。回答は手入力の回答と同じく、画面の自動読み上げの設定に従う。
- 同じ requestId の再送で本文が違えば `request_conflict` で拒否する。
- 元の生成が読み取り系の道具で残した `acted` は、起きたこととしてログに残る。

### 4.3 競合

- 生成が行動を確定する書き込みと再送信の書き込みは、同じ writer で順に並ぶ。先に行動が確定していれば、再送信は `already_acted` で拒否される。このとき元の run は止まっていない。画面は「実行が始まっていたため編集できませんでした」と出し、中止の操作を残す。
- 先に再送信が確定していれば、元の生成は採用検査（run の状態・版、窓の版）で不採用になり、行動の確定も run の状態の検査で失敗する。
- 元の生成が既に読んだ本文は訂正前のものだが、その生成は採用されないので記録に残らない。

### 4.4 記録と記憶

- 会話メッセージには訂正の出来事（`corrected`）が残る。記憶担当は訂正後の本文を読む（未処理の発言はまだキュレーションされていない）。
- ログ（JSONL）には runId・messageId・結果コードだけを出し、本文は出さない。

## 5 UI

### 5.1 入口

- **応答中の表示（「回答を作成中」と中止ボタンの行）に「止めて編集」を足す。** 押すと、その run を止め（中止と同じ操作）、読み上げも止め、直前の発言を入力欄に入れて編集の状態にする。
- **直前の利用者の発言の吹き出し**に、編集できる間だけ鉛筆のボタン（ラベル「編集」）を出す。中止した後もここから編集できる。中止した後に別の run が応答を終えた場合（その発言も一緒に処理された）は出さない。
- 入力欄が空でフォーカスがあるとき、↑キーで直前の発言の編集に入る（チャットツールでよくある操作）。

### 5.2 編集の状態

- 入力欄の上に帯を出す: 「直前の発言を編集中」と「やめる」ボタン。
- 送信ボタンのラベルは「更新して送信」。送信のキーは通常の送信と同じ（Ctrl/⌘+Enter）、Esc でやめる。
- 対象の吹き出しは薄く表示し、編集中であることを示す。
- 添付があれば帯に「添付はそのまま送ります」と添える（§9 Q3 で変える場合あり）。
- 編集中は画像の添付と音声入力の開始を出さない（添付を足しても送られないため、音声の認識結果で本文が上書きされないため）。
- 「やめる」を押すと入力欄を元に戻す。止めた run は止まったままで、発言は未処理のまま残る（現行の中止と同じ。次に送った発言と一緒に答えられる）。

### 5.3 送信の後

- 吹き出しの本文を訂正後の本文に置き換え、小さく「編集済み」と表示する（同じメッセージに run が二つ以上あれば編集済みとする）。
- 新しい run の応答中の表示に戻る。
- 拒否されたときは、帯の中に理由を出して編集の状態を保つ:
  - `already_acted`: 「実行が始まっていたため編集できませんでした。」
  - `not_latest`: 「新しい発言があるため、この発言は編集できません。」
  - その他: 「この発言は編集できません。」

### 5.4 音声

- 音声の発言でも、吹き出しの「編集」から本文を直せる。止めたときは読み上げも止める（現行の音声の中止と同じ）。
- 音声入力中（録音中）は編集の入口を出さない。

## 6 層と責務

- `dialogue`: 条件の判定、run の終了と作り直し、再送信の公開操作と HTTP ルート。業務判断と SQL は dialogue に置く。
- `conversation`: 訂正（既存）。新しい API は追加しない。
- `continuity`: 訂正の反映（実装済みの `correctMessageInTransaction`）。
- Web: `web/src/domains/dialogue`（API とフック）、`web/src/workspace`（会話画面と入力欄の編集の状態）。DesignSystem の既存の Button・アイコンを使う。

## 7 検証

- dialogue domain:
  - 応答中に再送信すると、元の run は `cancelled`（`edited`）、メッセージは訂正され、`said` も訂正後の本文になり、新しい run が同じメッセージで作られる。
  - 本文が同じなら訂正せず送り直す。
  - 行動が確定した後（委譲の確定、記憶への依頼など）は `already_acted` で拒否し、何も変えない。
  - 後に利用者の発言があれば `not_latest`。専門担当への発言は `specialist_turn`。
  - 同じ requestId の二重送信は一つの run になる。
  - 再送信の後、元の生成の結果は採用されない。
- Web: 「止めて編集」で入力欄に本文が入る、Esc でやめる、送信で吹き出しが置き換わる、拒否の理由が帯に出る。
- ブラウザ E2E は対象の試験ファイルを明示して個別に実行する。fixture・live・実機器の結果は分けて記録する。

## 9 決定事項（2026-10-24 合意、すべて推奨どおり）

- **Q1 行動が確定した後の扱い。** 推奨: 編集できない（§3）。代案: 編集は許し、確定済みの行動はそのまま残して「○○は実行済みです」と伝える。代案は記録と実行が食い違うので推奨しない。
- **Q2 応答が終わった後（`completed`）の直前の発言。** 推奨: 編集できない（巻き戻しになる）。
- **Q3 添付。** 推奨: 初版は本文だけ直し、添付はそのまま引き継ぐ。添付の差し替えは別途。
- **Q4 音声での操作（「今のなし、〜にして」）。** 推奨: 初版は対象外。必要なら会話エージェントの新しい操作として別に設計する。
- **Q5 「やめる」後の止めた発言。** 推奨: 現行の中止と同じく未処理のまま残す。代案: やめたら元の本文のまま自動で送り直す。
