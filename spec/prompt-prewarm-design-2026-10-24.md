# 先行キャッシュ（キャッシュがないときの記憶の先読み）の設計

- 日付: 2026-10-24
- 状態: 案・合意待ち（§9）。実装前
- 関連: [context-window-spec-2026-10-24.md](context-window-spec-2026-10-24.md)（§12.3 キャッシュが失われた機会、§15 先読み）、[larm-preload-recheck-2026-10-24.md](verification/larm-preload-recheck-2026-10-24.md)

## 1 目的

会話の入力の先頭（system・tool定義・記憶と会話の文書）が LARM のキャッシュにないとき、利用者が話す前に、返答を作らずにその先頭を LARM に読ませておく。初回や沈黙の後の最初の応答で、約1.4万tokenの読込み（約19秒）を待たないようにする。

2026-10-24 20:15 の「こんにちは」では、キャッシュが0で、最初の本文まで21秒かかった（run `405849d7`、入力13,785token、prefill 19.2秒）。同じ先頭がキャッシュにあれば、読込みは約0.03秒になる（同日の再検証）。

## 2 LARM の現状（2026-10-24 20:30 に確認）

保存済みの接続で、公開 OpenAPI（113操作）と `GET /v1/activity` を読み取り専用で確認した。

- **無出力の先読みの操作はない。** prefill・preload・warm・slot・KV を扱う操作は公開されていない。§15 が前提にした契約は、まだない。
- **プロンプトの保持（`larm-prompt-cache.v1`）がある。** runtime の設定項目として、保持の上限（全体8GiB・利用者ごと4GiB・16件）、使われない間の失効（`idleTtlMs`、初期値5分）、最大の保持時間（`maxAgeMs`、初期値30分）がある。実際の値は inspection の権限がなく読めなかった（初期値で見積もる）。
- **補助の要求4件の後でも保持される**（同日 12:08 の再検証で13,953/13,957token再利用）。10-23 の「補助4件で0になる」は解消している。
- **チャット要求は `prompt_cache_key` を受け付ける。** Eumenes は今は送っていない。要求の項目は開いており、`max_tokens` も渡せる（token計数の公開仕様は出力1以上を要求する）。
- **キャッシュがあるかを問う操作はない。** 分かるのは、要求の後の `cached_tokens` だけ。
- `GET /v1/activity` で、LARM が空いているか（`idle`/`active`）と、`bootEpoch`・`configRevision` が分かる。

## 3 方式の要点

1. Eumenes が、キャッシュがない見込みかを、自分の記録から判定する（§4）。
2. ない見込みなら、主会話と同じ先頭に固定の短い末尾を付けた通常の要求を、出力1tokenで送る。返答は捨てる（§5）。
3. 送るきっかけは、会話画面の表示・話し始め・再構成の直後・保持の延長に限る（§6）。
4. 本物の生成を常に優先する（§7）。

LARM が無出力の先読みを公開したら、§5 の要求だけを差し替える。

## 4 キャッシュがない見込みの判定

会話ごとに、主会話の要求を最後に送った記録（メモリ上、再起動で消える）を持つ:

- 送った時刻、その保持が始まった時刻
- 先頭の digest（`generation-prepare` の `prefixDigest`。system と tool定義から作る）
- LARM の `bootEpoch`・`configRevision`
- その要求の入力token数と `cached_tokens`

次のどれかなら「ない見込み」とする:

- 記録がない（起動後の初回）。
- 最後の送信から `idleTtlMs`（初期値5分）から余裕30秒を引いた時間が過ぎた。
- 保持の開始から `maxAgeMs`（初期値30分）から余裕1分を引いた時間が過ぎた。
- `bootEpoch` か `configRevision` が変わった（LARM の再起動・設定変更）。
- 今の先頭の digest が記録と違う（再構成・設定・tool定義の変更）。
- 最後の要求の `cached_tokens` が入力の半分に満たなかった（見積もりが外れた）。

判定は推定であり、外れても正しさには影響しない（遅いか、無駄な先読みが1回増えるだけ）。

## 5 先読みの要求

- 主会話の profile へ、通常のチャット要求を送る。中身は次のとおり。
  - 主会話と同じ system と tool定義、同じ先頭の message（生成の `messages` の、最新の発言より前の部分）。
  - 末尾に固定の短い user の文。
  - `max_tokens: 1`、`stream: false`。
  - 主会話と同じ `prompt_cache_key`（会話ごとに固定の値。本物の生成にも付ける）。
- 末尾の固定文は要求の中だけのもので、会話・`log`・出来事には入れない（§15 の「ダミーの出来事を追加しない」を守る）。返答の1tokenは捨てる。
- 中身は、生成の準備（`generation-prepare`）と同じ組み立てを、**読み取りだけ**で作る。再構成・記憶の採用・digest の保存・run の作成はしない。今の窓が再構成を要する状態なら先読みしない（再構成は次の生成で行い、§6 の再構成の直後の先読みで読ませる）。
- 推論の使用量は `purpose: llm`、種類 `prewarm` として記録する。ログには理由・入力token数・`cached_tokens`・所要時間だけを出し、本文は出さない。
- 会話の版や窓の版が変わった（発言・再構成）後の先読みの結果は、記録の更新に使わない。

## 6 先読みを送るきっかけ

いずれも §4 で「ない見込み」のときだけ送る。

| きっかけ | 理由 |
| --- | --- |
| 会話画面が表示された（画面の在席、`/api/inference/screen`） | 初回や久しぶりに開いたとき、話し始める前に読ませる |
| 音声入力を始めた・話し始めた・入力欄に打ち始めた | 文字起こしや入力の間に読込みを進める |
| 再構成の直後（§12.3） | 先頭が変わった直後に、次の発言の前に読ませる（§15） |
| 保持の延長 | 画面に在席している間、使われない時間が `idleTtlMs` に近づいたら送る。キャッシュが残っていれば読込みは約0.03秒で済み、失効を防げる。在席していなければ送らない |

`maxAgeMs`（30分）で保持が切れる分は、在席中の沈黙の間に読み直す（1回約19秒の計算）。

## 7 本物の生成を優先する

- 会話ごとに、先読みは同時に1件だけとする。
- run が動いている間、音声の読み上げ中、LARM が `active` の間は、新しい先読みを始めない（保持の延長も同じ）。
- 先読みの途中で本物の生成が始まった場合:
  - 先頭の digest が同じなら、生成は先読みの完了を待ってから送る。同じ先頭を2回読むより早い。待つ上限は、先読みの残りの見込み時間とする。
  - 違うなら、先読みを取り消して生成を送る。
- 利用者が使っている会話のキャッシュを追い出さない。先読みは主会話の先頭だけとし、補助の要求の先頭は読ませない。

## 8 検証

- fixture:
  - 判定の各条件（初回、失効、`bootEpoch` の変化、digest の変化、`cached_tokens` の不足）。
  - 先読みが1件だけ動くこと。
  - 生成が先読みを待つ場合と、先読みを取り消す場合。
  - 先読みが会話・`log`・出来事を変えないこと。
  - run の動作中と読み上げ中は送らないこと。
- live（実行には事前の許可を取る）:
  - キャッシュ0の状態で先読みし、続く本物の生成の `cached_tokens` が入力の95%以上になる。
  - 5分の沈黙の後に、保持の延長の有無で比べる。
  - 補助の要求が挟まっても保持されることを、もう一度確認する。
  - fixture・live・実機器の結果は分けて記録する。

## 9 決定事項（合意待ち）

- **Q1 出力1tokenの通常の要求で代用してよいか。** 推奨: 代用する。LARM が無出力の先読みを公開したら差し替える。§15 の「LARM の契約が確定するまで先読みは実装しない」を、この方式に改める。
- **Q2 保持の延長（在席中、失効の前に送る）を入れるか。** 推奨: 入れる。キャッシュが残っていれば、1回の計算はごく小さい。
- **Q3 きっかけ（§6）の範囲。** 推奨: 4つすべて。最も効くのは、画面の表示と話し始め。
- **Q4 先読みの途中で発言が来たとき、生成が先読みを待つか。** 推奨: 先頭が同じなら待つ。
- **Q5 `idleTtlMs`・`maxAgeMs` の実際の値。** 推奨: LARM の担当者に確認し、確認できるまでは初期値（5分・30分）で見積もる。inspection を読む権限の付与を頼んでもよい。
