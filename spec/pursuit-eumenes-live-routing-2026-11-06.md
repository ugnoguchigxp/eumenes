# Eumenesの実会話から検索・長考調査を確認する

利用者の依頼は、実際のEumenesから短いWeb検索と長考リサーチを使い分け、問題を修正すること。前提は `pursuit-web-research-integration-2026-11-06.md` と `router-package-integration-2026-11-04.md`。mainで作業し、CIは実行しない。Claude/OpenAI APIの累計上限は既存キャンペーンの15ドルを引き継ぐ。

## 観測と修正範囲

事前固定したSQLite公式資料の単一事実確認と2資料比較を、実行中のEumenesへ通常のCLI会話から送った。担当の指定・判定の差替えはしていない。両方とも最終選択が会話となり、「公式Web資料を確認できない」と返した。再順位づけでは適切なWeb担当が最上位だったが、既存best-v2の最終順位で会話が上回った。取得障害やタイムアウトではない。

既存の `routeStructured` も比較したが、短い依頼を3依頼へ分解してPipelineへ回した。作業完了を確認し、入口と時間枠は元の `route` / 8,000msへ復元した。この設定は採用しない。

まず既存の担当説明・利用場面・例の情報を改善する。短い検索は公式資料の単一項目の確認と短い出典付き回答、長考調査は複数本文の照合、条件・制約・限界、関連する論点の検証を説明する。SQLiteやWALを選択条件や例に追加しない。キーワード分岐、順位補正、モデル・閾値・記憶の変更、新しい判断方式は追加しない。

この案を保存済みLARMの埋め込み・文脈判定と変更しないrouterパッケージで比較した。隔離したカード索引で、場所・関数・指定ページ・防災計画・技術仕様・研究比較・雑談の7件が4/7から7/7へ改善した。説明の調整に使わなかった元の2件も期待する担当へ分かれた。この試験は全登録カードを利用可としており、実会話の完全な再現ではない。通し成功の代用にはしない。

公開済み定義は不変とし、`toolchain:web.search@9` と `toolchain:web.research@5` を追加する。接続先、skill、package、実行枠は既存のまま。新しい起動・判定の機構は不要である。

## 実会話の再試験で判明したSDK接続の不備

明示的な許可後に一度再起動し、検索@9・調査@5の有効登録を確認した。元の2件は通常の会話から期待する担当へ分かれた。短い検索は公式本文を取得し、リンク付きの完了通知と報告リソースを生成した。完了結果を履歴本文へ追加せず通知へ出すのは現行のTODO通知設計に従う動作であり、変更しない。

長考調査は本文取得前に停止した。モデルがホストの`web_read`や`report_draft`を自分の実行環境の関数と取り違え、Codex側の道具を探索した。提案された外部の道具名はcoreの契約検査で拒否され、未取得の内容を完了とはしなかった。

読み取り専用の診断で、CLIの`mcp_servers={}`はユーザー設定のMCP登録を消さず、5つの登録が有効なまま残ることを確認した。また現行CLIでは旧`js_repl`フラグは廃止済みで、`code_mode_host`が別に存在する。これが「native tools・MCPを無効にする」という既存adapterの契約を満たさない根拠である。

既存のapp-server JSON-RPC機構を再利用する。`config/read`で有効設定を一度読み、登録名だけから各MCPの`enabled:false`を構成し、全ての無効featureとともに新しい推論threadの`config`へ渡す。ユーザー設定は書き換えず、認証・model・接続先は維持する。設定取得や形の検査が失敗した場合には推論を開始しない。固定のMCP名や題材による分岐は追加しない。この設定の隔離診断では全MCPの道具数が0になった。

これは新しい担当選択方式ではなく、推論だけを行い道具実行はホストが所有する既存契約の修正である。外部仕様は[app-serverのconfig/read](https://learn.chatgpt.com/docs/app-server)と、稼働CLIが生成した`ThreadStartParams.config`のJSON Schemaを確認した。偽SDKによる設定継承の回帰、実SDKでのホスト道具のJSON提案、関連する推論・Pursuitの検査を部分から順に実施した後、必要な再起動の許可を得て通常会話の長考試験をやり直す。

MCP隔離後の再試験では、Codexのglobal `AGENTS.md`にある初期化をモデルが研究の前提と誤認し、利用者へ実行環境の変更を相談した。自身のWeb操作・回答案保存にはまだ進んでいない。試験用の仕事だけを登録済みTODO画面のaction APIで取消し、再試験の入力は変更していない。

推論を送らない`debug prompt-input`と`thread/start.instructionSources`で、`project_doc_max_bytes=0`、空の`instructions`、空の`developer_instructions`でも個人用の指示が読まれることを確認した。これらの設定変更だけを繰り返さない。認証を複製した別のCodex homeは作らず、既存のfunctions選択用指示と同じ方法で、構造化したモデル応答の役割を明記する。入力の道具一覧はホストが後で実行する操作の記述であり、モデルは要求されたJSONを返す。作業場所の初期化はこのモデル応答の前提ではなく、Codex自身の道具の利用可否からホスト道具の欠如を推測しない。これは`outputSchema`の既存契約に対する説明であり、題材や発話による担当判断は増やさない。まず小さい実SDK検査でこの境界を確かめ、成功してから通常会話の調査を再実行する。

## 完了した報告を開く接続

この修正後、元の比較依頼は通常会話からPursuitを選び、公式本文2件、仮説4件、モデル要求34回で完了した。独立検証2件にも合格した。しかし通知は200文字の要約だけで、Pursuitが所有する全文へのリソース登録がなく、報告リンクが空だった。受付・計算・通知の成功だけではこの不足を完了扱いにしない。

既存の`report` resource kindの複数owner登録と、既存の`work-result`表示を再利用する。Pursuitの保存済み結果を`eumenes://report/pursuit:<id>`で解決し、ホスト生成の完了結果にその参照を付ける。登録済みの読み取り専用queryで、全文・出典・不明点を既存表示へ渡す。新しい専用React画面や調査・採点ロジックは増やさない。producerの登録が必要な部分は公開済み版を保った次版にする。未完了・忘却済み・存在しない結果を報告として返さない。取消・忘却・本文の安全な表示と既存の短い検索の報告が維持されることを部分・結合で確認し、実サーバーから報告の解決・本文取得を確認する。通知のリンクまで通す新しい実会話も実施する。

完了結果のJSON schemaは拡張せず、既存の`fromResultInTransaction`とproducer登録で通知のリンクを作る。結果本文は元のまま照合する。launcherを持たない報告画面が`artifact_not_found`になることを結合試験で再現した。task bindingへ任意の画面参照を追加する案も検査したが、「taskはartifactを持たない」という既存契約の試験に抵触したため取り下げた。試験の期待値は変えず、既存のlauncherを持つ独立artifactとして登録する。通知リンクは対象IDを指定して正しい全文を開き、launcherは「最新の調査報告」として直近の完了・一部完了の結果を開く。明示したIDが存在しない・忘却済みの場合は別の結果へ置き換えない。結果がまだない場合は未作成と表示する。bindingと調査担当の版は@2と@5を維持し、調査の時間・回数・指示は変えない。

既存結果表示のSession欄は、ownerが`sessions`を渡した場合だけ表示する。調査報告に対して「実作業Sessionの開始は未確認」と表示しないための共通の表示修正であり、渡された空配列・記録済みSessionの表示は維持する。

公開APIでは全文一致を確認したが、実ブラウザーでは共通adapterが結果sourceを読まず、表示できなかった。共通adapterは登録された設定field・collectionを扱い、`work-result`の直接sourceを扱わないことを確認した。共同作業画面と同じ既存の登録方式で、Pursuitに読み取り専用の薄いWeb adapterを追加する。query取得・形の検査・既存部品への受渡しに限定し、専用画面や意味判断は追加しない。対象IDと表示中の状態をquery keyに含め、未指定時の空表示・対象変更・取得失敗・本文のHTMLエスケープを実際のrendererで回帰試験する。サーバー側の調査処理に変更はないため、ここは画面の部分試験とdomain検査の後、稼働ブラウザーで再確認し、それから新しい通しリサーチを行う。

## 長考の応答時間枠の受渡し

報告接続後の通常会話`research-r5`は両本文を取得し34回のモデル要求まで進んだが、最後の要求が60,003msで`local_timeout`となった。Pursuitは120秒の期限を指定していた一方、`captureUserControlInTransaction`に試行時間を渡す欄がなく、保存された`attempt_ms`はnullだった。既存の共通推論機構は、明示された試行時間がないcloud要求に60秒の既定を適用する。120秒の既存契約が実際の試行へ届かない不具合である。

既存の親付きcontrolと同じ任意の`attemptMs`を独立したuser controlにも受け渡し、Pursuitが保存済みbindingの時間枠を渡す。独立controlの既存の最大期限120秒と同じ範囲に検査し、実際の試行も元の依頼期限を超えない。未指定の呼出しは従来の既定を維持する。時間・回数の上限を増やしたり、タイムアウト時の自動再送や新しいfallbackを追加したりしない。保存・試行への反映・期限と不正値の拒否を部分、Pursuitとの受渡しを結合で検査してから再試験する。同じ操作を繰り返す際の変更条件は「120秒の宣言に対して60秒で切断」から「宣言した120秒を既存実行機構へ渡す」ことである。途中結果と通知リンクを失敗履歴へ残す。
