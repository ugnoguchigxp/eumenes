# 登録目標へ実際の参照先と検査を渡す設計差分

2026年11月23日策定、11月24日更新。**利用者が実装を承認済み。実装・正式検証を完了し、補修版の実稼働再受入を待っている。** 質問配送・質問待ちの分離・改訂後の読取許可は既存設計に対する補修として実装した。本書は、単一許可・単一専用runnerという従来の実装契約を変更する部分を定める。承認には利用者が起動したサーバーの操作を含めない。[既存設計](registered-goal-autonomy-2026-11-23.md)・[補修版の検証記録](verification/goal-autonomy-2026-11-23/operational-repair.md)

## 1. 目的・範囲・完了条件

利用者が登録した目標について、ホストが認めたローカル参照、公開Web調査、独立検査を同時に提示し、LLMが必要な手段を選べるようにする。実際の作業先が追加された場合には、既に待機している目標にもその変化を一度渡す。元の目標本文と達成条件は変更しない。

今回の実目標は「Live2Dの背景を設定でさまざまな色に変更できるようにすること。達成条件は、設定から背景色を変更できること。」。現ソースには背景色の選択・保存・復元が存在する。したがって、追加実装を前提に編集許可を求める前に、既存の実物を読み、対応する検査を選べることが必要になる。

合格には、同じ実目標ID・版を保持し、参照先の登録反映後、追加の催促なしで参照・独立検査・結果採用へ進むことを確認する。既存成果が条件に足りない場合には不足を保存し、許可内の別の手か具体的な質問を選ぶ。unit/component試験だけで実画面・実機器の確認を済ませたと扱わない。

対象は、許可の複数保持、能力と許可の対応、作業先別runner、構成変更時の再評価、登録された独立検査。外部公開、別のCodexチャットへの送信、利用者の無許可の書込み、サーバーの自動操作は対象外。

## 2. 許可を一つの優先順位で選ばない

現在は新しい許可の発行で同じ目標版の全許可を失効させ、最後の一行だけを能力提示に使う。さらに作業先が一つなら、その読取許可をWeb調査より優先する。この選択を廃止し、次の二種類を別に保持する。

| 種類 | 発行元・共存・取消 |
| --- | --- |
| ポリシーによる参照・検査 | ホストの登録と現在のbindingに基づく。Webと各登録作業先について一件ずつ共存できる。書込み対象は常に0件。 |
| 本人の明示許可 | 現在の発言、目標版、登録作業先・基準版・読書範囲・検査に限定する。新しい明示許可は従来どおり旧明示許可を置き換え、ポリシーによる別の参照先は消さない。 |

取消は許可ID・版を照合する。ポリシー許可を本人が明示取消した場合、同じ目標版では構成変更や再起動で自動再発行しない。構成変更による旧ポリシーの失効と、本人の取消を区別して保存する。目標を改訂した場合は旧版の全許可を失効させ、新版の読取ポリシーを適用する。編集許可は新版へ持ち越さない。

実行済み・受付不明の仕事は、その試行が保存した許可ID・版で照会・取消・回収する。別の許可が追加されたことを理由に、元の仕事を別の許可や別の作業先へ付け替えない。

## 3. 保存と公開操作

Agencyの既存`goal_permits`と`scope_json`を引き続き正本にする。過去のmigrationを書き換えず、新しいmigrationでポリシーの論理キー、構成世代、失効理由を追加する。旧行は追加情報なしで読める形を保つ。

- 論理キーは、Web読取または登録`workspaceRef`に属するポリシーを識別する。モデル名・目標本文・会話の表示状態を含めない。
- 構成世代は、登録範囲、基準コミット、固定検査、toolchain/bindingの版の正規化digest。論理キーは同じで内容が変わった場合に旧行を構成失効させ、新しい行を発行する。
- 失効理由は、本人の取消、構成置換、目標版の終了、忘却を区別する。本人取消は新しい構成世代でも同じ目標版の自動発行を止める。
- 同一目標版・論理キーの有効なポリシー行は最大一件。発行操作の重複キーには所有者、目標ID・版、論理キー、構成世代を含める。同じキーで違う内容ならconflict。

追加する操作は、`goalPermitsInTransaction(key)`、`authorizeReadPolicyInTransaction(key, configuredPolicy)`、`reconcileReadPoliciesInTransaction(key, policies)`。単一の`goalPermitInTransaction(key, id)`は、保存済みの試行の照会と旧ホスト互換のため維持する。新規試行の許可選択に「最後の一行」を使わない。

目標版ごとに適用済み構成fingerprintも永続化する。ポリシーの追加・置換・取消の照合と、進行版の更新、背景キューへの投入は同じwriterで行う。構成が同じなら更新・再判断予約は0件。

## 4. 能力の提示とLLMの選択

`GoalCapability`の内部情報へ`permitId / permitRevision`を加える。スナップショット生成時に全許可の現行性・期限・出典・停止条件を確認し、それぞれのownerが提供するsurfaceを合成する。

同じownerのローカル読取が複数あっても識別できる不透明な`capabilityRef`を発行する。ホスト側の対応表は、その参照を許可ID・版、workspace、ownerの操作、binding版へ一意に結び付ける。モデルに渡す説明と許可範囲には、どの作業先・資料・検査を扱えるかを記す。モデルは既存の`GoalStep.act.capabilityRef`を選ぶ。発話や目標本文のキーワードでコードが作業先を選ばない。

予約直前・開始直前・再開・観測採用で、その参照に結び付いた許可を再照合する。実担当に渡す契約は選ばれた一件の範囲に限定する。内部の対応を失った参照や旧スナップショットからの予約は拒否する。

検査にも同じ対応が必要である。`checkRef`は作業先と許可に結び付け、機械検証が後から別の許可の同名検査を選ばないようにする。既存受付の古い参照は、その保存済み試行の照会・取消に限り互換で読めること。

## 5. 登録検査と実作業先

作業先の登録へ`policyCheckRefs?: string[]`を追加する。省略時は空配列で、既存登録の検査権限を広げない。指定できるのは同じ登録内の`acceptance: true`の検査だけ。未知の参照、重複、非acceptance検査は構成エラーとする。

ポリシーで実施できる検査は既存の`runGoalCheck / createCheckSandbox`を使う。固定の実行ファイル・引数・cwdを保持し、ネットワーク禁止・作業先の書込み禁止・期限・出力量の制約を維持する。sandboxが利用不可なら検査不能を保存する。sandboxを外して実行しない。本人の編集許可と、登録検査の実施を分ける。

Live2D用には[登録した作業先・検査](verification/goal-autonomy-2026-11-23/workspace-proposal.json)の参照範囲と、`policyCheckRefs: ["avatar-background-behavior"]`を設定した。書込み対象は0件。11月23日23:30 JSTに既存の別作業先を保持して稼働設定へ反映した。設定済みであることと、補修版の起動・実目標の受入が済んだことは区別する。[sandboxでの検査結果](verification/goal-autonomy-2026-11-23/existing-avatar-verification.json)

作業先の実パス・HEAD・入力digestは既存の検査を再利用する。第三者による変更を自分の変更として採用しない。実物を読む・検査する前に、既存の機能がないと推定して新たな編集を始めない。

## 6. 作業先別runnerと既存目標の復帰

`buildClaudeRunners`は通常会話のrunnerを維持し、登録作業先ごとのrunnerを解決する。キーはcanonical path。物理的に同じcheckoutは共有し、異なるcheckoutは既存の専用daemon方式で分離する。明示ソケットの対応範囲を超える作業先は利用不可として返し、通常の作業先へ送らない。監督のworkspace解決も単一登録へのフォールバックを廃止し、保存済みの`workspaceRef`を使う。

起動復旧と構成変更時には、未完了・採用中の目標版だけを照合する。fingerprintが変わり、停止・取下げ・忘却・本人取消に抵触しない場合は、許可の差と利用可能能力を更新し、同じ目標版へ背景判断を一件予約する。追加能力の内容が同じなら、再起動を繰り返しても同じ質問を再推論しない。

本人待ちの質問は本人が回答したことにしない。実担当の未回答条件を再実行しない制約も維持する。ホスト構成が変わったという新しい観測を判断へ渡し、LLMが、以前足りなかった手段で進めるか、まだ本人の判断が必要かを選ぶ。不要になった質問の解消は、現行質問ID・目標版に対する明示的な判断として記録し、未配送の古い質問を後で提示しない。

このため、次段では次の追加契約も実装する。単に`needs_user`を`ready`へ変えるだけでは完了としない。

- `GoalStepContext.openQuestions`へ、その質問を新しい構成観測によって再評価できるかを示す`canResolve`を追加する。実担当が返答を待つ質問には常にfalseを渡す。解消可能な理由と構成観測の参照もデータとして渡す。
- `GoalStep`の共通部へ`resolvedQuestionRefs?: string[]`を追加する。省略した旧応答は空配列として読む。提示された解消可能な質問だけを指定でき、解消と新たな`act / wait / ask / verify`を同じ判断で返す。意味の判定はLLMが行い、コードが「能力が増えたので解消済み」と決めない。
- `GoalQuestion`へ、作成時の構成世代と任意の`resolution`を保存する。解消記録は、今回の構成観測・contextId・進行版・理由と結び付ける。`answeredBy`は本人の実在する返答にだけ使う。旧質問も新しい構成観測を受けたときだけ一度再評価できる。
- 採用writerで質問ID・目標版・進行版・構成世代と`canResolve`を再照合する。実担当の質問、別目標の質問、未提示の質問、古い観測での解消は拒否する。解消済み質問への返答を新規実行に使わず、未配送の質問を後から提示しない。配送済みの履歴は既存の出典・忘却規則を維持する。

| 2 | Hostの`goal-permission / registered-goals / goal-progress-context / goal-progress` | 一つの判断に全ての有効な候補が見え、選択参照と予約した許可ID・版が一致。古い版・偽参照・取消後の実行0件。 |

| 4 | `goal-verification`と構成復旧 | 登録検査だけをsandboxで実施。選択した作業先・検査・入力digestを保持。構成変更の一度の再評価、同一構成の更新0件。 |

追加の通し試験では、既に動く機能と、その現物を読む登録先、失敗する検査条件を用意する。最初は登録先なしで質問待ちにし、構成を追加して一度だけ復帰させる。コードの再実装をせず既存成果へ到達するケースと、検査が不一致で次の手へ進むケースの双方を確認する。サンプルREADMEの成功を実目標の成功に代用しない。

サーバーの起動・停止・再起動は本家の作業規則と利用者の指示に従う。本書の合意だけを、利用者が起動したサーバーへの操作許可と解釈しない。

## 8. 実稼働で確認した設計生成の停止点

23:37の利用者による再起動後、元会話への追加発話0件で既存目標の背景ジョブは始まった。しかし設計の原文引用が初稿と一度の訂正でも検査に通らず、23:39に`goal_criterion_source_invalid`で停止した。これは実稼働受入の不合格であり、固定試験の成功をもって完了とはしない。

既存設計§4が設計書と初回分析期間を要求する対象はファイル変更である。読み取り専用の目標にも詳細設計を先行させ、引用失敗で参照・検査まで無期限に止めた実装を補修する。元のroot達成条件と引用検査を維持し、書込みには引き続き有効な設計・許可・分析期限を要求する。同一入力で失敗した設計準備は記録して再生成を連打せず、許可内の参照と独立検証は続ける。既にこの引用失敗で待機した行も、現在使える手段を照合して同じ目標ID・版のまま一度復帰させる。

発話を投入せずに実稼働状態を確認できるよう、既存`list_goals`と同じ登録目標の投影を`GET /api/agency/goals`へ接続する。既存API認証を維持し、会話の生成・選択・attend、LLM呼出し、台帳更新、キュー投入を行わない。反復GETでもwriter呼出し・進行版・会話・受付が増えないことを固定試験で確認する。

受入中に共有配布物は`74981c957258…`から`5228ee16a86e…`へ更新された。採用ソースの違いは`src/agenda/extract.ts`と`src/agenda/index.ts`で、目標処理のソースは同一だった。引用停止をこの差分のせいにはしない。現在の配布物を保全してホストの補修を進め、再度の実稼働確認を別の受入として記録する。

同じ質問の一回配送では、質問IDも不変でなければならない。従来のdigestは渡された進行行全体を含め、キューID・進行版の更新でも別質問になり得た。所有者・目標ID・目標版・重複を除き整列した条件ID・前後の空白を除いた不足理由だけで照合し、旧形式の未回答質問にも同じ意味の照合を行って既存IDと本文を再利用する。本人の回答済み・構成変更による解消済みの質問は復活させない。この補修を含む配布物は`794a0c03481a…`で、直前の別作業による変更を維持する。
