# 依頼文の URL 境界の判定

作成日: 2026-10-17

状態: 設計（未合意・未実装）

## 1. 問題

`api/domains/agent-runtime/service/request-urls.ts` の `requestUrls` は、依頼文から URL を最大3件抜き出す。抜き出した URL は、サブエージェントの `web.read` が読める URL の許可リストになる（`urlScope: "request_or_observed"`、`tool-runtime/service/read-invocation.ts` で href の完全一致を検査）。

`4fe373ce` で、日本語のパス（`https://example.org/日本語`）を扱えるよう、非 ASCII 文字を URL の一部として受け入れるようにした。その結果、空白を挟まずに日本語が続くと、URL の境界を誤る。

| 依頼文 | 現在の抽出結果 | 利用者の意図 |
| --- | --- | --- |
| `https://example.com/pageを読んで` | `https://example.com/page%E3%82%92…`（「を読んで」まで含む） | `https://example.com/page` |
| `https://example.com/a、https://example.com/b` | 1件に結合される | 2件 |

日本語の依頼では、URL の直後に空白を入れないのが普通である。そのため、次の失敗が起きる。
- モデルが正しい URL を `web.read` に渡しても、許可リストと一致せず `tool_url_out_of_scope` になる。
- 誤った URL が、3件の上限の枠を使ってしまう。

会話側の LLM が関数引数 `urls` で URL を渡した場合は、そちらが先に入るので問題は起きない。問題になるのは、LLM が `urls` を省略し、ホストの抽出だけに頼る場合である。

## 2. 方針

依頼文の字面だけで判断し、意味の判定は加えない。境界があいまいなときは、どちらか一方を選ばず、ありうる候補を両方とも許可リストに入れる。許可リストは、利用者が書いた文字列から導いた候補だけで構成する。そのため、範囲が広がるのは、同じ文字列の中で境界の位置が違う URL だけである。

1. **区切り文字の追加。** 読点「、」と句点「。」は、URL の途中でも区切りとして扱う。現状は、末尾にあるときだけ取り除いている。
2. **境界があいまいな場合の候補。** URL の中で、ASCII 文字の直後に非 ASCII 文字が続く位置を「境界候補」とする。次の2つを、1つの参照の候補として両方とも許可リストに入れる。
   - 境界候補より前の部分
   - 全体
3. **候補の数え方。** 候補は、元の参照1件につき最大2件とする。3件の上限は、候補の数ではなく参照の数で数える。許可リストの件数の上限は、6件（3参照 × 2候補）に変える。
4. **変えないもの。**
   - 括弧の内側（`（…）`、`「…」` など）は、括弧を区切りとする。この規則は今のまま。
   - パーセントエンコード済みのパスと、日本語ドメインの扱い。
   - 会話側の LLM が渡した `urls` を先に入れること。

境界候補が複数ある場合（`https://example.com/日本語ページを読んで` など）は、最初の境界候補だけを使う。この例では、`https://example.com/` と全体の2候補になり、意図した `…/日本語ページ` は候補に入らない。日本語のパスに助詞が直接続く書き方は、字面だけでは分けられない。この場合は、会話側の LLM が `urls` で渡すか、利用者が空白か括弧で区切る必要がある。この限界は、本設計の範囲外とする。

## 3. 影響

- 許可リストに入るのは、利用者が書いた文字列の接頭辞だけ。新たなホストやパスは加わらない。
- 3件の上限の意味（参照の数）は変わらない。
- 変更するのは `request-urls.ts` だけ。戻り値の型を、参照ごとの候補のまとまりにするか、平坦な配列のままにするかは、実装時に `start-task.ts` と `tool-selection.ts` の利用箇所に合わせて決める。

## 4. 検証

- `api/domains/agent-runtime/test/request-urls.test.ts` に、次の場合を加える。
  - 助詞が続く場合（`…/pageを読んで`）
  - 読点で2件を並べた場合
  - 句点で終わる場合
  - 日本語のパスを括弧で囲んだ場合（既存）
  - 日本語のパスの直後に空白がある場合
- 許可リストの照合試験に、次の2つを加える。
  - 境界候補の前の部分を `web.read` で読めること
  - 別のパスは引き続き `tool_url_out_of_scope` になること
- 検証は `bun run verify -- --domain agent-runtime --domain tool-runtime` で行う。

## 5. 要合意事項

| ID | 論点 | 選択肢 |
| --- | --- | --- |
| U1 | 境界があいまいなときの扱い | (a) 両方の候補を許可リストに入れる（本設計） / (b) ASCII の直後の非 ASCII で常に切る（日本語パスは括弧か空白で区切る必要がある） |
| U2 | 「、」「。」を URL の途中でも区切りとして扱う | (a) 扱う / (b) 末尾だけ取り除く（現状） |
