# 検索エージェントと会話履歴参照ツールの実装計画

作成日: 2026-10-10 Asia/Tokyo

状態: P0〜P5を実装し、固定応答の受入試験・利用側10domain・全体検証を通過。P6の実モデル3ケースはSQLiteの保存済み接続先で実行し、発見した入力契約の問題を修正して再受入中。実機器受入も未実施。実装と検証の詳細は[受入記録](verification/research-and-history-tools/README.md)に記す。

検索で取得した資料を必要な位置から読み直し、目的の情報がなければ別資料や別の検索語へ進めるようにする。もう一つは、保存済みの会話原文から必要な発言を探し、前後の文脈を取得するツールを追加する。どちらも、少量の候補から必要な原文へ進み、実際に提示した根拠に基づいて回答する。

会話を要約して置き換える圧縮処理は導入しない。会話記録とMemoryの役割・正本を変えない。履歴画面のページ分割や描画の最適化も今回の対象外とする。

## 1 実装範囲と前提

| 領域 | 今回実装するもの | 今回含めないもの |
| --- | --- | --- |
| 検索エージェント | 取得結果のタスク内一時保存、本文内検索、範囲読取り、不足項目に応じた再検索、有限の探索制御 | 自動巡回、無制限の再検索、新しい検索Provider、ブラウザ操作基盤 |
| 会話履歴参照 | キーワード・日時による候補検索、前後の発言と長文の部分取得、発言版の検証、回答への接続 | 会話の圧縮、原文の複製保存、Memoryへの自動登録、ベクトル検索、履歴管理画面 |
| 検証 | 二つの機能の固定シナリオと、モデル応答を固定する小さな再生fixture | 全製品を対象とする汎用録画・再生基盤、通常会話やProvider生応答の運用ログ保存 |

初版の取得結果の「保存」は、backendメモリー内の期限付き保管とする。タスク中に読み返す用途であり、別の依頼で古い検索結果を再利用する永続キャッシュではない。backend再起動後の継続読取りは提供せず、参照期限切れを明示する。既存の安定資料キャッシュの利用条件は維持する。

既存設計との関係は、[Web取得の計画](web-research-cache-implementation-plan-2026-10-09.md)、[取得経路の学習計画](research-route-learning-implementation-plan-2026-10-09.md)、[Memory接続計画](memory-system-incremental-adoption-concept.md)、[domain境界](../docs/domains.md)に従う。本書は検索中の読取り操作と会話原文への参照を追加する差分計画である。別リポジトリのMemory本体の変更は前提にしない。

基準はEumenesの `bc8cc6c` と作成時点の作業ツリー。関連箇所には進行中の未コミット変更があるため、実装着手時に最新コードと差分を読み直し、本書の関数名・契約との対応を更新する。他の変更を巻き戻さない。

## 2 現在の実装と不足

| 現在の実装 | 今回の差分 |
| --- | --- |
| `web-research` は取得結果をメモリーに15分保持する。公開結果は本文・全体サイズが制限される | 表示用結果と、再読取り用の取得本文を分ける。本文を外へ丸ごと返さない |
| `llm-fetch` adapterは本文取得を最大12,000文字に制限する | 取得可能量と一回のモデル提示量を別々に制限する |
| `workerContext` は各資料の先頭最大4,800文字、観測全体を20,000 byte以内に短縮する | 先頭以外も選択できる読取り結果を追加し、資料の版と読取り範囲を識別する |
| `web.read` のモデル入力はURLだけ | 保存済み本文内を検索する `web.find` と、範囲を読む `web.read_saved` を追加する |
| 調査workerは検索2回、本文読取り3回、総tool操作5回、モデル8回が上限。別候補・再検索・報告修復の経路がある | 既存の探索を再実装せず、不足項目、同一操作の反復防止、ローカル読取り用予算を加える |
| 抜粋番号は資料とモデルstepに対してローカル。報告時に原文から引用を確定する | 範囲変更後に同じ番号が別の文章を指さないよう、提示版を加えて引用を検証する |
| `conversation` は原文、訂正・撤回、発言のrevision/digest、変更outboxを所有する | その公開操作に、検索・周辺取得・範囲取得を追加する |
| 会話APIは全件取得が中心。`sourceInTransaction` は原文の現行状態を取得できる | モデル向けに件数・文字量を制限し、回答採用時に同じ原文が有効か照合する |

現在の本文短縮、引用検証、取消、権限付き実行参照は維持する。容量制限を単純に大きくする変更では完了としない。

会話原文を読むportは検索の `ToolResult.documents[].url` に無理に合わせない。結果を `web_source` と `conversation_source` で識別し、各種類の検証と親への報告変換を小さな実装に分ける。架空のWeb URLを会話発言に付けない。

## 4 検索結果を読み直す設計

### 4.1 取得本文と表示用結果を分ける

検索結果はURL・タイトル・snippet・検索条件・取得時刻を保持する。本文取得は、ガード後の正規化本文と、URL、取得時刻、本文digest、取得段階の省略有無を保持する。検索snippetと本文は別種類の根拠のまま扱う。

`llm-fetch` の結果を公開schemaへ落とす前に、内部用の取得本文を受け取る。現在の `ResearchResult` の本文上限と32 KiBの公開結果上限はそのまま維持し、内部本文用の型・容量検査を別に用意する。生HTML、認証header、cookie、Provider生応答は保存しない。取得のsecurity判定と送信・取得先制約を通る前の内容は公開しない。

一時本文の正本は `web-research` の一箇所に置き、tool-runtimeには参照と提示済み抜粋を置く。既存のresults bufferとの重複保管を避ける。取得完了のtransaction後に、現在のjob/generationが採用可能なことを再確認して参照を公開する。失敗したtransactionから本文参照だけが利用可能にならないようにする。

再fetchした資料には新しい `sourceRevision` と参照を発行する。同じURLという理由で、古い抜粋の中身を差し替えない。取得段階で省略された本文を、保存しただけで「全文」と表示しない。内部契約に `acquisitionTruncated` と `previewTruncated` を分ける。

### 4.2 追加tool

以下は新規契約案である。tool入力の `sourceRef` はホストがそのタスクに発行した不透明な参照とし、OSのファイルパスは公開しない。

| Tool | 入力 | 出力と用途 |
| --- | --- | --- |
| `web.find` | `sourceRef`、検索語、任意の続きcursor | 保存本文内の一致箇所と短い前後、読取り用cursor、`hasMore`、省略状態 |
| `web.read_saved` | `sourceRef`、ホスト発行の位置cursorまたは先頭指定、希望量 | 指定箇所の抜粋、前後のcursor、`viewId`、`sourceRevision`、省略状態 |

初版の本文内検索はNFKC・大小文字などを検索専用に正規化した文字列一致とする。正規表現・任意コードは受け取らない。一致箇所を原文位置へ戻す対応を持ち、引用する文字列は原文から切り出す。位置単位をAPI内で固定し、サロゲートペアを分断しない。cursorは本文版・位置に結び付け、異なる本文へ転用できなくする。

`web.find` と `web.read_saved` は外部通信を起こさない。期限切れ、取消、所有者違い、版の不一致は理由付きの失敗として返す。本文がない場合に、読取り操作から勝手にfetchしない。

最初のプレビューは冒頭と末尾を予算内に収める。両者が連続した文章に見えないよう位置と省略を明記する。本文内検索で見つかった中間部分も同じ引用経路で使えるようにする。

### 4.3 引用の識別と寿命

現在の `sourceId + excerptId` に `viewId` を加え、報告根拠を `{ sourceId, viewId, excerptId }` で参照する新revisionを作る。viewは本文版、範囲、抜粋本文digestに結び付く不変の提示記録とする。過去stepの `e0` を、新しい範囲の `e0` と取り違えない。

モデルの最終報告に使わせる抜粋は、その最終stepの入力に実際に含めたviewに限定する。以前読んだが予算から外れた箇所は、保存済み参照から再提示する。引用対象として残す有用な抜粋と、新しく読む抜粋に上限を設け、後から大きなページを取得しても以前の根拠を一括で押し出さない。

ホストが抜粋原文を確定し、報告受理時と親回答の採用時に、owner、cancelEpoch、本文版、参照期限、根拠の有効性を再検証する。別タスクの参照、未提示のview、存在しない番号は拒否する。失敗した修復で新たな探索予算を付与しない。

子の報告完了と親回答の採用は別の段階として扱う。本文の保管寿命はroot runに結び付け、子の読取り権限だけを子の期限・完了で閉じる。子の報告を受理するtransactionで、採用する根拠への検証専用参照を親ticketに結び付ける。親に全文読取り権限は渡さず、rootの期限・取消まで検証材料を保持する。子終了時のメモリー回収で親の採用検査が必ず失敗する設計にしない。

### 4.4 初期上限案

数値は本計画の初期値として実装した。すべてホストが検証し、モデルは拡張できない。

| 項目 | 初期値 |
| --- | --- |
| 新revisionの担当期限 | 最大150秒。親runの既存180秒以内で、親回答に30秒を残す |
| 新revisionのmodel step | 最大45秒、担当期限を超えない。残り60秒以下は最終報告に進む |
| 取得本文1件 | 64,000文字かつUTF-8で256 KiB以下。先に達した方で止め、省略を明示 |
| 一時本文の総量 | 1タスク1 MiB、backend全体16 MiB、最大64本文 |
| 有効期限 | 本文保管は開始から15分とroot期限の短い方。子の読取り権限は子期限・完了で終了 |
| 一回の範囲読取り | 最大2,400文字かつエンコード後8 KiB以内 |
| 本文内検索 | 一回最大5箇所、結果全体8 KiB以内 |
| モデルに渡す観測全体 | 既存の20,000 byteを維持。必須指示・元依頼を削らない |

本文の取得上限を広げる前に、採用中のllm-fetchのサイズ制限・ガード処理が内部の大きな本文でも維持されることを隔離試験で確認する。保証できない取得先では現行取得上限を維持し、取得できた範囲だけを再読取り可能にする。

容量不足では、期限切れまたは所有者のいない本文を先に回収する。現に使っている本文を黙って追い出さない。なお確保できない場合は既存の小さなプレビューを返し、`body_unavailable` を観測に載せる。以降は別候補または部分回答を選べるようにする。全量をモデルへ戻す回避はしない。

同じ物理本文を既存の取得共有で使う場合でも参照はownerごとに分ける。一人の取消で他の有効な参照を壊さず、最後の所有者解放で回収する。取消の権限失効はtransaction内、メモリー回収はcommit後に行う。

## 5 目的に届くまで調べ直す制御

### 5.1 次の操作を選ぶための情報

既存のworkerに、現在の依頼、必要項目、確認済み項目、不足項目、操作履歴、残り予算を渡す。必要項目は対象・日付・地域・単位などを含む有界な構造化データとして初回のworker判断で作る。別LLM呼出しは増やさず、各項目に原文の依頼との対応を持たせる。ホストは件数・文字量・参照の存在を検査するが、意味の充足を機械的に完全検証できたとは扱わない。

| 観測した状態 | 次に許可する選択 |
| --- | --- |
| 同じ資料に目的の項目がありそうだがプレビュー外 | 本文内検索、該当範囲の読取り |
| 資料の対象・時点が違う、本文に項目がない | 取得済みの未読候補を読む |
| 適切な未読候補が残っていない | 不足項目を反映した検索語で再検索 |
| 対象を特定できず、資料を増やしても決められない | 明確化が必要な点を報告する |
| 項目が揃った | 根拠付きで終了する |
| 予算・期限が尽きた、または進展がない | 確認済みの内容と不足を分けて終了する |

単純な質問に全手順を強制しない。追加の探索は不足がある場合だけ行う。取得失敗、目的との不一致、本文の省略、資料間の矛盾は別の理由として扱う。明示URLだけを調べる依頼など、ユーザーが限定した範囲は再検索で広げない。

終了報告は `answered`、`partial`、`not_found`、`clarification_required`、`failed` を区別する新revisionにする。現在のreportが要求する最低1件のclaimを、根拠0件の終了へ流用しない。根拠がある報告だけclaimを要求し、未発見・明確化・失敗は探索範囲と理由を返せるようにする。履歴報告も同じ終了種別を使い、出典型は会話用に分ける。

### 5.2 回数と時間をホストで止める

外部取得は既存の合計5回、内訳は検索2回・fetch3回を維持する。保存本文の検索・範囲読取りは合計4回を別枠にする。workerモデル呼出しは現在の8回から最大12回へ変更し、通常操作9回、最終報告1回、修復最大2回を収める。Coordinatorの上限は変更しない。最終報告に必要なモデル1回分と時間を確保し、残りがなければ追加操作を公開しない。

期限は現在のroot/child期限を引き継ぎ、再検索・経路変更・JSON修復・新しい参照の発行で延長しない。既存の直接取得経路は最初の単一tool権限を維持し、検索への切替時は既存の再発見と権限再発行を通す。継続・切替の前後で予算がリセットされない台帳にする。

正規化した検索条件、取得URL、本文版と範囲を操作指紋として保存する。日本語の空白・大小文字程度を揃えるが、異なる地名・日付・URL queryは同一視しない。同じ成功済み操作を繰り返しても新しい観測が増えない場合は実行せず、その理由をworkerへ返す。この応答もモデル回数を消費する。繰り返す場合は部分報告へ進む。

一時的な取得失敗に対する既存の許可された再試行は、同じ操作の無意味な反復と区別する。ガード拒否・権限拒否・取消を迂回する再試行は追加しない。汎用検索に関する成功判定を天気等の特定語だけで実装せず、取得先固有の検査は既存adapterに残す。

### 5.3 再生fixture

取得本文とモデルの構造化応答を試験用fixtureで固定し、既存のtoolchain結合ハーネスへ渡す。途中失敗、修復応答、検索語の変更、最終報告までを再生する。呼出し数・順序・最終入力に含まれた根拠を検査し、余分な呼出しと未消費の応答を失敗にする。

最初は合成資料だけで実装する。liveで発見した事例は個人情報と秘密を除いた最小ケースへ変換して追加する。運用ログから生応答を常時収集する仕組みは追加しない。固定応答の再生成功と、実モデルが適切な探索を選べたことは別の検証結果にする。

## 6 会話履歴参照ツール

### 6.1 読む対象

正本は既存 `conversation` の保存済み原文である。Memoryのブックマーク、Worldの事実、会話の要約を履歴本文として混ぜない。保存済みかつ撤回されていない発言だけを返し、speaker、発言時刻、messageId、revision、digestを添える。Assistantの過去発言は「Assistantがそう述べた記録」であって、現在も正しい事実という保証ではない。

初期の探索範囲は、その依頼が属する会話とする。別会話を明示的に対象とする依頼は、ホストがアクセス可能性を確認して発行した会話参照だけを追加できる。モデルの入力したconversationIdで探索範囲を拡大しない。許可された範囲で見つからない結果を「全会話に存在しない」と回答しない。

Memory接続設定OFFでも通常の会話履歴を使う既存契約に合わせ、このツールは会話原文の参照として扱う。Memory保存・忘却の設定を変更せず、撤回済み原文を別の保存先から復元しない。

### 6.2 操作契約

| Tool | 入力 | 出力 |
| --- | --- | --- |
| `history.search` | 検索語、任意の日時範囲・speaker、許可済み会話参照、cursor、件数 | 候補の短い原文抜粋、message参照、時刻・speaker・版、続きcursor、検索範囲と走査完了状態 |
| `history.read` | message参照、前後の件数、任意の長文内cursor | 指定発言と前後の保存済み発言、提示view、長文の続きcursor、省略状態 |

「昨日の話」など語句の指定がない場合は日時を条件に最近の順で候補を返せるようにする。日時条件はホストのAsia/Tokyoで絶対時刻へ解決し、境界は開始を含み終了を含まない区間に統一する。SQLへ検索語を連結せず、文字列一致のワイルドカードをエスケープする。初版は厳密なキーワード検索とし、意味検索が成功したように表示しない。

候補は初期10件・最大20件、各抜粋最大300文字、一回の読取りは対象と前後を合わせ最大10発言・8 KiBとする。長い発言は途中で分け、読めなかった部分を明示する。履歴担当workerはtool操作最大4回、モデル最大7回（操作4回・報告1回・修復2回）を初期値とする。予算・期限はrootから引き継ぐ。

大きな会話での無制限走査を避け、一回に検査する発言数と本文量を上限化する。初期案は500発言・1 MiBの本文走査で、上限に達したら候補が0件でも続きcursorと `scanComplete: false` を返す。呼出し回数が尽きた場合は「確認した範囲では見つからなかった」と扱う。原文検索索引は最初から複製せず、計測で必要性が出た場合にだけconversation所有の派生索引として別途検討する。

SQLで全履歴を検索してから返却件数だけLIMITする実装では、走査上限を満たしたことにしない。先に保存順の対象batchと本文量を限定して検索する。長い単一発言は原文内位置もcursorへ保持して分割し、分割境界をまたぐ検索語の一致を落とさない。走査した範囲と、一致結果を返した範囲を分けて管理する。

### 6.3 順序とcursor

現在のconversationの `ordinal` はSQLite rowidであり、公開契約が永続ID・cursorへの利用を禁止している。この値をそのまま外へ出さない。

初版は、短命な検索セッションと不透明cursorをbackendで発行する。検索セッションはowner、許可会話、条件digest、会話revision、開始時の対象範囲、最後に検査したmessageIdに結び付ける。同じ会話revision内でのみ現行の保存順を使い、SQL内部でmessageIdから位置を解決する。messageId自体の辞書順や日時だけでページ順を決めない。

会話revisionが変わった場合は `history_cursor_stale` を返し、古い条件のページと新しい状態を混ぜない。初版は追記でもcursorを失効させる保守的な方式とし、取り直しは同じ予算内で最大1回。これにより訂正・撤回とページ取得の競合を単純化する。高頻度の追記と両立するsnapshot方式は今回の必須条件にしない。

cursorの期限はタスク期限と15分の短い方。backend再起動で失効する。失効後に古い本文を返すキャッシュは設けない。

進行中の依頼そのものを過去の証拠として検索しないよう、開始時に現在の入力messageIdを除く対象上限を固定する。検索・読取り・続き取得の全てで同じ上限を使う。会話revisionの変化を検出した場合は、対象上限だけを頼りに訂正前の本文を返さず、上記の失効処理へ進む。

### 6.4 回答への接続と採用

`capabilities` に履歴参照用のpackage/profile/SKILLを追加する。Coordinatorは「前に何と言ったか」「決めた日時を確認」などの依頼でこの能力を選べるようにする。Web調査の `researchInput`、URL、weather向け観測を履歴担当へ渡さず、package種別に対応する入力・context・報告検証を選択する。

履歴担当へWeb取得toolを発行しない。外部検索と履歴参照が両方必要な依頼の自動複合実行は後続とし、初版は一つの依頼で選んだ能力を完結させる。これにより会話本文を検索語として外部送信する経路を作らない。

履歴報告は、確認した発言と参照ID、確認した範囲、不足を含む。最終回答には「以前の発言」と分かる時刻・話者を渡す。Webの出典URL形式へ変換せず、画面では発言日時などのテキスト参照とする。履歴ジャンプUIは後続でよい。

取得時に固定した `messageId + revision + digest + viewId` を、報告受理時と最終回答採用の双方で `conversation.sourceInTransaction` により照合する。範囲内に該当なしという報告も、検索条件と確認範囲の会話revisionを検査する。訂正・撤回・権限変更・取消・期限切れがあれば古い報告を採用しない。再読取りが必要と返し、無制限に自動生成を繰り返さない。

履歴利用の回答は、この検証が終わるまで完成回答・音声へ公開しない。新たな利用記録には原文を複製せず、実行ID、発言参照、版、提示digestを残す。取得結果の本文は参照用一時領域だけに置き、無関係なログや新しいMemory台帳へ転記しない。

子が完了した後の採用検証metadataはWeb調査と同じく親ticketへ引き継ぐ。原文は親の採用transactionで再読取りできるため、一時viewの解放後に旧本文のコピーへ依存しない。採用後に原文が訂正・撤回された場合の過去回答の扱いは既存の会話・Memory契約を維持し、本機能だけで過去回答を自動書換えしない。

### 6.5 APIとCLI

Web・CLIはDBを直接読まず、認証付きAPIを使う。既存の全件取得APIは互換性を維持し、新しい検索・範囲取得APIを追加する。

| 新規API案 | 用途 |
| --- | --- |
| `POST /api/conversations/:id/history/search` | 条件とcursorをbodyで受け、限定された候補を返す |
| `POST /api/conversations/:id/history/read` | message参照と周辺範囲を受け、原文を返す |

POSTは検索語をURLへ載せないために使用し、会話内容を変更する操作にはしない。API利用者も会話のアクセス範囲を検証する。agentのowner参照とCLIの参照を交換して使えないよう、発行元とscopeを分ける。

CLIには `history-search` と `history-read` 相当の操作を追加する。実装時に既存CLIの命名規則へ合わせる。JSON出力には続きの取得に必要な参照を含め、人向け表示には範囲・省略・期限切れを示す。検索APIのbodyや原文をアクセスログへ記録しない。

## 7 失敗時の共通動作

| 条件 | 必須の動作 |
| --- | --- |
| 一時参照が失効した | `source_expired` 等の明示結果。読取り操作が裏でネットワーク取得を始めない |
| 他タスク・他会話の参照 | 拒否する。存在や本文を返さない |
| 本文内に操作指示・秘密の要求がある | 未信頼資料として扱う。読取り権限やtool一覧を変更しない |
| 同じURLを別版で取得した | 新しい参照を発行。古い引用を新しい本文へ付け替えない |
| 取得・履歴検索の結果が部分的 | `partial` と不足理由を返す。見つからないことと存在しないことを区別する |
| 引用番号・提示版が不正 | 報告拒否。残予算内で修復し、尽きたら理由付き終了 |
| 取消後に結果が届いた | 本文参照・報告・完成回答を新たに公開しない |
| backend再起動 | 未完了仕事は既存queueの復旧契約へ従い、一時参照の消失を明示する |
| 原文訂正・撤回後に履歴回答が完成した | 原文版検査で採用を止め、旧引用を表示・読み上げしない |

ログはrunId・jobId・requestIdと、操作種別、件数、byte量、回数、時間、失敗コードだけを使う。検索語、本文、会話原文、Provider生応答、認証情報は残さない。既存loggerの許可fieldを確認して実装する。

## 8 実装工程

工程は下記の順で進める。履歴の原文検索部分は本文保管部分に依存しないが、tool-runtimeとagent-runtimeの変更は契約を揃えてから接続する。

| 工程 | 実装内容 | 完了条件 |
| --- | --- | --- |
| P0 現状固定 | 最新差分と依存確認、既存試験、原文末尾・再検索・履歴訂正の合成シナリオ準備 | 現在できることと新機能で解消する失敗を記録。新tool schema、port、result種別を確定 |
| P1 本文保管 | 内部取得本文、results bufferの参照化、容量・TTL・owner管理 | プレビュー外の本文が保持され、公開結果とログに全文が漏れない。容量・取消・再起動試験が通る |
| P2 本文再読取り | find/read_saved、位置cursor、viewId、引用schemaの新revision | 中間・末尾の根拠を再fetchなしで読み、引用できる。古いviewの取り違えを拒否 |
| P3 探索制御 | 不足項目、操作指紋、外部/ローカル予算、finish予約、再生fixture | 最初の資料が期待外れでも別候補・再検索で到達。無意味な反復と予算超過が止まる |
| P4 履歴の公開操作 | conversationの検索・周辺取得、cursor、API/client/CLI | 範囲外・撤回済み発言を返さず、部分走査と続き取得を正確に表示 |
| P5 履歴能力の接続 | package/profile、モデル入力、履歴報告、採用port、親回答への結線 | モデルが履歴を調べて回答でき、生成中の訂正・撤回・取消では旧回答を採用しない |
| P6 統合受入 | 利用側domain・全体verify、live探索、必要時の音声機器受入 | fixtureとliveを別々に記録し、二機能の受入条件を満たす |

主なmigration候補はtoolの提示view metadata、操作指紋、予算内訳、履歴参照の採用metadataである。本文の永続コピー用tableは作らない。migrationは既存配列の末尾へ追加し、既存のschema・保存済みreportを読み続けられるようにする。

既存package/profile/SKILLのrevisionは上書きせず新revisionを追加する。旧reportには必要な互換読取りを残し、新しいview付き根拠と混ぜない。登録順・最新revisionの選択・learned routeの結び付けを同じ変更で検証する。

検索能力と履歴能力は別々に有効化できるよう、capabilitiesの登録・選択側で展開範囲を制御する。切り戻しは新能力の選択を停止し、新規参照を発行しない方式とする。進行中の新revisionタスクは取消または明示失敗にしてから無効化し、古いコードで黙って継続しない。適用済みmigrationと会話原文は削除しない。

## 9 受入シナリオ

| ID | 入力・条件 | 合格条件 |
| --- | --- | --- |
| R1 | 答えが資料の5,000文字目以降にだけある | fetch1回の後、保存本文から該当箇所を読み、正しい抜粋を根拠に回答 |
| R2 | 答えが12,000文字を超えた場所にある合成資料 | 新しい取得上限内なら読める。取得段階で省略した場合は未確認を明示 |
| R3 | 冒頭と末尾は無関係で、中間に必要情報がある | head/tailだけで終了せず、本文内検索で中間へ到達 |
| R4 | 最初の候補は別地域・別日付、次候補が目的に合う | 不一致を記録し、別候補を取得。最初の値を混ぜない |
| R5 | 初回検索に目的の資料がなく、検索語を変えると見つかる | 不足を反映して再検索し、残予算内で根拠付き回答 |
| R6 | 同じ検索・同じ読取りを繰り返すモデル応答 | 同一成功済み操作の再実行を止め、有限回で部分報告または失敗 |
| R7 | 範囲を変えた前後でexcerptIdが同じ | viewIdと本文版で区別し、誤った引用を拒否 |
| R8 | 期限・取消・容量不足・ガード拒否 | 権限を広げず、追加取得を勝手に行わず、原因と確認済み範囲を示す |
| H1 | 「先週決めた集合時刻」を複数発言から確認 | 候補検索→前後取得→speakerと日時を区別した回答 |
| H2 | 同時刻の発言、長い単一発言、疎な内部順序 | ページの重複・欠落がなく、長文の続きを取得できる |
| H3 | 一致0件だが走査上限に到達 | 全件不在と断定せず、未走査とcursorを返す |
| H4 | 検索後または生成中に原文を訂正・撤回 | 古いcursor・view・回答の採用を拒否 |
| H5 | 別会話・別ownerのmessage参照やcursorを渡す | 拒否し、本文を返さない |
| H6 | 撤回済み・未保存の下書き、過去の指示を含む本文 | 下書き・撤回は対象外。過去の指示を現在の操作権限にしない |
| H7 | 一部のみ確認して終了、または検索中に会話が変化 | 調査範囲を限定して報告し、取り直し回数を超えない |
| H8 | Memory OFFで明示的に会話履歴を確認 | 現行の会話参照契約で動作。Memoryの保存・設定を変更しない |

fixtureは外部通信・実credentialなしで通す。再生fixtureには期待する操作列と最終根拠を持たせ、引用検証やowner照合を意図的に外した場合に該当ケースが落ちることも確認する。性能は履歴240往復と、より大きな合成履歴で一回の返却量・走査量が上限内に留まることを検証する。今回、画面の描画速度を完了条件にしない。

liveでは、長い公開資料、初回候補の不一致、検索語変更の3種類を明示的に試す。到達率、外部取得数、ローカル読取り数、モデル回数、終了理由を記録する。固定応答が正しい列を返すfixtureだけで、実モデルがAgenticな検索をできるようになったとは判定しない。

## 10 検証コマンドと実施記録

各工程は所有domainの `bun run verify -- --domain <name>` と利用側domainの同コマンドを実行する。最終の対象は `web-research`、`conversation`、`capabilities`、`tool-runtime`、`agent-runtime`、`research-routes`、`dialogue`、`voice-dialogue`。Memory・Worldが使うconversation公開契約を変えた場合は、それぞれの利用側試験も実行する。

横断接続後は `bun run verify:all` を実行する。fixtureサーバーと試験用DBだけを使い、製品DB・通常会話で受入試験を行わない。CLIのAPI経由・JSON出力・cursor失効のプロセス試験を含める。liveは既存のtoolchain live経路に明示ケースを追加し、通常verifyから分離する。

結果は `spec/verification/research-and-history-tools/` に記録する。対象commitと差分、合成入力の版、コマンド・終了コード、fixture/live/実機器の区分、未完了事項を残す。本文・検索語・モデル生応答を通常ログへ追加しない。音声の挙動を変更した場合は既存の実マイク・ヘッドホン3往復と割込み受入を実施し、それまでは音声MVP完了を宣言しない。

| 工程 | 状態 | 検証結果 |
| --- | --- | --- |
| P0 | 完了 | 既存試験・差分・domain境界を確認し、契約と再生fixtureを固定 |
| P1 | 完了 | ガード後本文の参照保管、容量・期限・owner・再起動・公開量の試験 |
| P2 | 完了 | find/read_saved、原文位置、同じexcerpt番号の別view拒否、親採用までの検証 |
| P3 | 完了 | needs、操作指紋、有限予算、finish予約、不一致・再検索・反復の再生試験 |
| P4 | 完了 | 原文検索・前後と長文の部分取得、認証API/client/CLI、走査上限と不透明cursor |
| P5 | 完了 | Memory OFFで履歴能力を使用し、訂正・撤回・取消・再取得上限を結合試験 |
| P6 | fixture・全体検証完了、live再受入中 | 全体・利用側10domainは終了コード0。liveはSQLiteの保存済みURLで接続を確認。実モデルで判明した契約案内を修正し再受入中。実機器受入は未実施 |
