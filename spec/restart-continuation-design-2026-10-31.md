# 再起動をまたぐ仕事の継続 設計（案・合意待ち）

状態: 案。実装前に本書への合意が必要（新規の再開判断を導入するため）。

## 目的

離席・接続断・backend 再起動をまたいで、任された仕事を実施済み操作と未完了部分を区別して進める。現在の扱いは domain ごとに異なり、会話生成は中断のまま自動再開しない。本書は「何を再開し、何を再開しないか」の境界を固定する。

## 現在の仕組み（確認済み）

- queue は handler ごとに `recovery: "replay_safe" | "interrupt"` を宣言する。再起動時は `recoverRunning` が、取消要求済みを `outcome_unknown`、`replay_safe` かつ試行回数と期限の範囲内を retry、それ以外を `interrupted` にする（`api/domains/queue/service/runner.ts`）。
- `replay_safe` の例: タイマー満了、ブラウザのキャプチャ、計算、3D の一部。`interrupt` の例: 音楽・画像の生成、OCR 会話生成（dialogue の `generation-handler` と `toolchain-command` はいずれも `interrupt`）。
- shell の実行台帳は再起動後に未実行を取消、実行中を結果不明にし、自動再実行しない（`docs/shell.md`）。
- 会話の run は中断（`backend_restarted` / `backend_stopped`）として記録される（README「再起動時の扱い」）。

## 設計判断

### D1: 再開するのは「仕事」であって「発話」ではない

会話生成（発話の生成そのもの）は再開しない。理由は、生成の途中結果は音声再生と結び付いており、再生成すると二重発話と、実行済みツールの二重実行が起きるため。再開の対象は、run から切り離して台帳に残る仕事（TODO・担当の実行・キュージョブ）に限る。

### D2: 再開条件は handler の宣言を正本とする

新しい再開判断を足さない。各 handler が冪等性を保証できる場合だけ `replay_safe` を宣言する、という現行の規律を維持する。本書で変えるのは会話側の扱いだけで、queue の判断方式は変えない。

### D3: 会話は「中断の通知と再依頼の入口」を持つ

再起動後に中断した run がある会話では、次にその会話を開いたとき、中断した仕事の一覧（TODO の状態つき）を State に一行で示し、利用者が「続きをやって」と言えば通常の委任として再依頼できるようにする。自動で再依頼はしない。

## 変更範囲（合意後）

1. dialogue: 中断した run に紐付く未完了 TODO を、再起動後の最初の会話入力で State のホスト欄に示す。新しい再開エンジンは作らない。
2. 各 domain の handler: `replay_safe` にできるものが残っていないか棚卸しし、冪等性を試験で示せるものだけ宣言を変える。対象外の例: 外部への送信を伴うもの、課金が発生する生成。
3. shell: 現行どおり自動再実行しない（コマンドの二重実行を避けるため）。この判断は変えない。

## 試験

- queue の既存の recovery 試験に加え、対象 handler ごとに「再起動後に実施済み操作が二重実行されない」固定試験を足す。
- 会話側は、中断した TODO が State に示され、再依頼で通常の委任として進むことを dialogue の固定試験で確認する。
- 検証は `bun run verify -- --domain queue --domain dialogue` と、利用側 domain を含めて行う。

## 対象外

- 発話生成の自動再開、shell コマンドの自動再実行、外部送信の自動リトライ。
- 再開のための新しい優先順位やフォールバックの導入。
