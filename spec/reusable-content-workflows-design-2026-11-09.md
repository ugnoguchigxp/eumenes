# Eumenesアプリ開発と再利用できるワークフロー

2026-11-09。UI自由制作の公開入口を「Eumenesアプリ開発」に置き換える設計案。Web本文の修正と、保存・受付・既存Pipelineへの型付き接続は固定試験済み。実モデルの再計測では、接続完了後の生成時間と下書き・抽出結果の検査が残ることを確認した。 [実装・検証記録](verification/reusable-content-workflows-2026-11-09/README.md)

## 1. 目的と設計判断

自然文から、開き直して使える画面や定期的に更新される文書を作る。最初の受入対象は、日付を指定して開く上映一覧と、複数リポジトリの変更から毎日作る開発日誌。二つが同じ起動・実行・成果物採用の契約を通り、用途の違いを部品、入出力、起動方法、保存先で表現できることを確認する。

制作の公開入口は会話・ランチャーともに「Eumenesアプリ開発」に揃える。アプリは画面だけでも、ワークフローだけでも、両方の組み合わせでも保存できる。画面だけの説明ページや画面内で計算するツールもこの入口で作れる。定期日誌のように専用画面を持たないアプリは、同じ管理画面で設定と実行状況を確認できる。

制作時にLLMが用途と完了条件を読み取り、画面、入出力スキーマ、Pipelineの下書きを作る。利用者が確認した手順を保存し、実行時は同じ手順を使う。ページの探し方、抽出結果の判断、日誌の構成は、その回の資料を見た部品内のLLMが決める。道具を変える必要が生じたら、利用者が新しい版を確認する。

| 正本 | 保存する内容 | 変更する主体 |
| --- | --- | --- |
| ワークフロー定義 | 目的、固定入力、受け付ける入力の型、Pipeline、出力先、任意の基準点契約 | 利用者が確認した制作画面。保存時にホストが版とdigestを付ける |
| アプリ | アプリID、所有scope、表示名、編集用下書き、利用者が確認したアプリ版、画面とワークフローの対応 | `app-development` が所有する。スキーマ本体は `capabilities`、画面本体は `ui-compositions`、ワークフローの実行可能な定義と許可は `pipelines` が所有する |
| 実行許可 | 利用者scope、定義の版とdigest、部品・操作の版、接続の許可範囲、文書の保存先、有効状態 | ホストが利用者の確認操作から作る |
| 予約 | 起動時刻、間隔、取り逃した回の扱い、対象の定義IDと版 | 既存Scheduler。予定の設定はここを正本とする |
| 実行と成果物 | 今回の入力、根拠と成果物への参照、採用状態、前回から引き継ぐ基準点 | バックエンド。成果物は所有するdomainの公開操作で保存する |
| 画面定義 | 列、入力欄、レイアウト、ホストが許可したデータ参照と更新操作 | `ui-compositions` の確定版と既存のOpenUI検査・描画 |

初版で扱う出力は、表に渡すデータとライブラリに新規保存するMarkdown。起動は画面操作または固定間隔。Pipelineの手順と、ホストが行う成果物保存を別々に記録する。手順の完了だけで成果物を完成扱いにすると、日誌の保存失敗でコミット範囲を失うため。

## 2. 現行の再利用点と必要な変更

| 接続 | 現行でできること | 今回必要な変更 |
| --- | --- | --- |
| Pipelineの制作と実行 | 共同作業で確認した `request / steps / output` を、再生成せずに親実行へ渡せる。既存の検査、参照、順序、Queueを使う。 | 保存済み定義に基づく起動元を追加する。現行の確認済み定義の入口は共同編集セッションを検査するため、同じセッションIDを予約に保存する方法では再実行できない。 [現行の起動処理](../api/domains/agent-runtime/service/execution-pipeline.ts#L166) |
| 部品間の受け渡し | Pipelineは先行手順の確定結果とホスト発行の参照を次へ渡す。現行のカタログは完了結果の公開スキーマを持たず、通常の参照読み取りで渡る本文には上限がある。 | 登録部品に完了結果の型と読取口を足す。型付きデータや大きな差分は、要約やプレビュー文字列を再解釈せず、ホストが照合済みの参照から読み取る。 [部品カタログ](../api/application/pipelines/component-catalog.ts) · [参照検査](../api/application/toolchain/task-execution-sources.ts) |
| 予約 | 型付きの登録対象を、予約回の記録と同じwriter transactionでQueueへ受け付ける。既存の重複判定は直前の起動ジョブの状態を見る。予約レコードのscopeは現在 `default` 固定。対象payloadの更新操作はない。 | ワークフローの起動対象と、対象側の排他による受付保留を登録する。利用者の実行許可と予約IDの対応、成果物採用までの排他はワークフロー側が持つ。新版への切替は既存の取消・作成を同一transactionで呼ぶ。 [Schedulerの対象契約](../api/domains/scheduler/types/index.ts) · [重複と受付処理](../api/domains/scheduler/service/index.ts#L145) · [予約の作成](../api/domains/scheduler/service/index.ts#L351) |
| 制作物の保存 | UI自由制作は既存の専門担当セッションで画面定義を編集する。別の共同制作経路ではPipeline本文を検査・実行できる。 | Eumenesアプリ開発を専門担当セッションへ登録し、画面とワークフローを一つの版で確認する。実装済みの生成スキーマ・画面・定義の一括保存に、アプリ版と下書きの所有範囲を接続する。 [現行の制作bundle](../api/domains/capabilities/bundles/ui-compositions.bundle.json) · [ワークフローの保存接続](../api/application/pipelines/workflow-authoring.ts) |
| 表示 | UI自由制作が既存の表を生成・保存する。表の現行入力は固定の行または画面内の計算系列。制作定義では外部 `source` を拒否する。 | 新版の表と入力操作に、同じ画面に結び付けた型付きデータ参照を追加する。ホストが参照と操作を解決する。 [表の定義](../packages/artifact-ui/src/composition-contracts.ts#L549) · [制作側の検査](../api/domains/ui-compositions/contracts/index.ts#L98) |
| Web取得 | 保護付き本文取得、取得済み資料の参照、取得先と読む箇所のヒントの再利用がある。現行の本文抽出は記事内の `header` も除去する。 | 共通の本文抽出で記事内の見出しを保持する。その本文と出力スキーマを使い、`web.records` が根拠付きの行を返す。 [Web取得](../docs/web-research.md) · [取得手順キャッシュ](../docs/toolchain.md#L76) |
| Markdown保存 | 固定ID・同じ入力での受付、保存結果の照会、応答喪失時の読み戻しがある。現在の生成文書のホストはPursuitの出所を検査する。 | 生成文書の出所検査を、登録済みの所有元ごとに振り分ける。既存Pursuitとワークフローの許可をそれぞれ照合し、同じ保存操作に接続する。 [生成文書の公開操作](../api/domains/markdown/service/generated.ts) · [Pursuitの接続](../api/application/pursuit/document-port.ts) |

`app-development` が会話からの制作、アプリの版、確認と公開状態を所有する。本体側の `pipelines` がワークフロー定義・実行許可・受付・成果物採用を所有し、`agent-runtime` が従来どおり子処理の実行を所有する。Scheduler・Web取得・Git観測・Markdown・OpenUIとの結線はapplicationに置く。Pipeline配布物のJSON形式と実行器を使い、各部品は版付きbundleと登録adapterで追加する。既存のGit関連コードは開発作業の管理用で、この用途のGitHub列挙と読取専用コピーの更新は新しい能力として登録する。 [Pipeline取込設計](pipeline-p0-3-integration-2026-11-05.md) · [登録手順](../docs/toolchain-extension.md)

LLMに渡す制作指示には、利用可能な部品・型・保存先と、確認まで実行しない下書き操作を追加する。実行側には型付き資料の読取と処理範囲の報告契約を追加する。語句や個別用途で選択を固定する処理は追加しない。既存の公開操作で満たせない拡張は、生成スキーマと画面の確定版の保存、型付き結果の受け渡し、対象側の受付保留、成果物採用の進行管理に限定する。これらは下記の保存・排他・復旧条件を満たすための接続であり、新しいPipeline実行器は作らない。

## 3. 保存するJSONと型

以下は利用者が確認する定義本文。ホストが別途発行する定義ID、版、操作の許可、前回の実行データは含めない。部品名、スキーマ参照、接続先と保存先の参照は新しい登録例。既存参照、または§3.4の同一保存で登録される生成スキーマ参照だけを受け付ける。生成スキーマ本体と画面の下書きは定義本文とは別に保持し、確認対象全体のdigestに含める。

### 3.1 上映一覧

```json
{
  "version": 1,
  "trigger": "manual",
  "input": {
    "schemaRef": "schema:showtimes.input@1",
    "fixed": { "theater": "109シネマズ湘南" }
  },
  "pipeline": {
    "request": "指定劇場の指定日の上映一覧を作る",
    "steps": [
      {
        "id": "showtimes",
        "bundle": "web.records",
        "from": ["request"],
        "task": "対象日の公式一覧を読み、上映1回を1行にして出典を付ける",
        "result": "作品名、開始時刻、上映形式、出典を持つ指定日の上映一覧"
      }
    ],
    "output": { "from": ["showtimes"], "deliver": "上映一覧を返す" }
  },
  "publish": {
    "kind": "dataset",
    "from": "showtimes",
    "schemaRef": "schema:showtimes.rows@1"
  }
}
```

画面の更新操作は、定義のID・版、操作ID、`{ "date": "2026-11-09" }` を渡す。ホストは固定値に実行時の値を合わせ、劇場名と日付の全体を検証する。固定値と同名の実行時入力は拒否する。日付は指定劇場の現地日付として扱い、この例は日本時間。時刻が日をまたぐ表記は、公開ページの日付と表記を根拠に保持する。

日付欄は登録済みフォームの `type: "date"` を使い、`defaultDate: "today"` を指定すると、開いた時点のブラウザーの暦日が初期値になる。ホストが初期値を渡す場合はその値を使う。入力した日付は画面の更新後も保ち、リセットや開き直しで初期値を解決する。日付の送信形式は `YYYY-MM-DD` とする。「上映作品」の一覧側に、空の状態でも使える「作品リストを更新」を置く。押すと日付欄の選択を使ってWebから取得する。同じ日付で押し直した場合も再取得する。

上映データは `theater`、`date`、`rows` を持つ。各行は `title`、`startTime`、任意の `format`、本文の `evidenceRefs` を持つ。取得時刻とURLはホストが根拠参照から解決する。型が合うこと、各行の根拠があること、指定日の全件を確認できたことは別々に扱う。全件を照合できなければ部分結果として示し、掲載なしを確認できた場合に限って空の一覧を確定する。

上映画面は公式の作品名を見出しにし、その下に上映回を一件ずつ並べる。作品名にIMAXなどの付記がある場合は、その表記を見出しに残せる。画面の `bindings.sections` は `{ "path": [1], "rowsKey": "rows", "groupBy": "title", "itemKeys": ["startTime", "format"], "labels": { "format": { "2D": "通常" } } }` を指定し、対応する `grouped-list` に表示する。`path` は画面内の子要素の位置で、保存時に対象部品と出力フィールドを照合する。描画は指定された文字列キーの完全一致でまとめ、各グループの上映順を保つ。`labels` は表示にのみ適用する。上映データと公開済みの表の定義は同じ契約で読み込める。既存の上映アプリは同じアプリIDに画面を更新した版を保存する。

上映回を描画する際は、登録済みの `showtimes.rows@1` の日付と、先頭項目に割り当てた `startTime` を使う。時刻は横並びにし、幅に合わせて折り返す。全回で同じ形式は見出しの近くに一度だけ表示し、見出しの括弧内に同じ値があればその表記を使う。形式が異なる場合は各回に残す。日本時間の現在時刻から各セクションの次回を選び、「次回」として表示する。開始時刻に達すると次へ移り、選択日が未来の場合と残りの回がない場合は強調しない。深夜の24時台以降の表記は上映日からの時刻として比較する。描画時にのみこの表示を組み立て、保存済み定義と取得結果は従来のまま読み込む。

### 3.2 開発日誌

```json
{
  "version": 1,
  "trigger": "schedule",
  "input": {
    "schemaRef": "schema:dev-journal.input@1",
    "fixed": {
      "connectionRef": "connection:github-projects",
      "repositoryPrefix": "eumenes_"
    }
  },
  "pipeline": {
    "request": "対象リポジトリの前回からの変更を開発日誌にする",
    "steps": [
      {
        "id": "changes",
        "bundle": "git.changes",
        "from": ["request"],
        "task": "対象を列挙し、前回の基準コミットからの変更を収集する",
        "result": "リポジトリ別のコミット範囲、差分参照、取得状態、基準点候補"
      },
      {
        "id": "journal",
        "bundle": "content.markdown",
        "from": ["request", "changes"],
        "task": "関連する変更をまとめ、変更の意味と根拠を示す。取得できなかった範囲と、取得できても処理できなかった範囲を区別して記す",
        "result": "コミットを参照できる日誌のタイトル、Markdown本文、対象ごとの処理範囲"
      }
    ],
    "output": { "from": ["changes", "journal"], "deliver": "日誌と差分記録を返す" }
  },
  "checkpoint": { "from": "changes", "schemaRef": "domain:git-observation.cursors@1" },
  "publish": {
    "kind": "markdown",
    "from": "journal",
    "schemaRef": "schema:content.markdown-draft@1",
    "destinationRef": "destination:dev-journal"
  }
}
```

日次予約は既存Schedulerに起動対象を一つ追加する。以下は、利用者が日本時間9時を選び、予約の有効化を確認した後にホストがSchedulerへ渡すJSON。予約の形式は既存の `CreateSchedule` と同じで、定義IDと版はホストが解決する。

```json
{
  "requestId": "aa61160a-17d0-4c44-a1be-4b789cf03a4d",
  "target": {
    "kind": "workflow.run",
    "payload": { "definitionId": "dev-journal", "revision": 1 }
  },
  "schedule": {
    "type": "interval",
    "anchor": "2026-11-10T09:00:00+09:00",
    "intervalMs": 86400000
  },
  "misfirePolicy": "coalesce"
}
```

予定の起動時刻を日誌の日付に使い、差分の対象期間は最後に採用したコミットと今回取得したコミットで示す。これにより数日停止した場合でも、再開時に何日分を含んだかを区別できる。保存先の参照はホストが許可済みのDocling領域・フォルダへ解決し、ファイル名と保存IDは予約回に対応する固定値から作る。

### 3.3 スキーマと手順の検証

| 契約 | 受け渡す値 |
| --- | --- |
| `showtimes.input@1` | 劇場名と日付。日付の文字列に加えて暦日として有効かをホストで検査する |
| `showtimes.rows@1` | 劇場・日付・行・取得範囲。各行の時刻は掲載時の表記を保持し、表示用の並びは日付と時刻から決める |
| `dev-journal.input@1` | 接続参照と接頭辞。予約時刻と差分対象の基準点はホストが別に渡す |
| `git.changes` の結果 | 取得対象ごとの安定ID、追跡先、前回と今回のコミット、状態、読取可能な差分参照。ホストが発行する処理単位IDと、対応する基準点候補を含む |
| `git-observation.cursors@1` | 接続・リポジトリ・追跡ブランチごとの採用済みコミット。状態の版はホストが管理する |
| `content.markdown-draft@1` | タイトル、Markdown本文、本文で使った根拠参照、処理単位IDごとの `coverage`（`processed` / `unprocessed`、理由、根拠参照）。保存先、ファイル名、基準点の値はホストが解決する |

- 生成可能なフィールド定義は保存できる有限JSON Schemaで表し、既存の変換でZodにする。日付やGitの基準点など有限subsetでは表せない制約は、登録済みのdomainスキーマに置く。Zodのコードを定義JSONの中に書く必要はない。 [既存のスキーマ変換](../api/domains/capabilities/service/json-schema-subset.ts)
- 外側の定義は固定のZodスキーマで検証する。固定入力のキー、予約起動に必要な値、公開元の手順ID、型と保存先の組合せを照合する。`publish.from` と `checkpoint.from` は `pipeline.output.from` に含まれ、それぞれ指定した型を返す手順であることを保存時に確かめる。基準点を使う定義では、その候補の処理単位が公開元まで参照で渡り、公開元が対応するcoverageを返せることも検査する。Pipeline本体は既存checkerで検査する。
- 子部品の登録には、利用する実行入力の型、先行手順から受け取れる結果の型、返せる成果物の型、読み取り・作成の範囲を宣言する。最初の検査ではスキーマ参照の版まで照合する。汎用の `web.records` は、定義の出力先から渡された表スキーマを使う。型が合わない接続は確認画面で指摘する。
- 実行入力、前回の基準点、起動時刻は、ホストが今回の実行に結び付けて `from: ["request"]` に渡す。先行結果は手順IDから実体参照へ解決し、子部品の契約に必要な範囲を渡す。モデルの自然文や参照のプレビューから入力値・コミットID・根拠を復元することは拒否する。

既存の子実行の準備と結果採用に、ワークフロー対応部品の契約を解決する経路を追加する。登録済み操作へ型付き入力を渡し、完了した結果を既存Pipelineへ返す。定義中の `task` は、LLMを使う部品にだけ作業指示として渡す。Gitの対象、操作、資格情報は構造化入力と実行許可から決まる。長い本文や差分には範囲読取を用意し、読めた範囲と全体を区別する。

### 3.4 下書きから確認済みの制作物への保存

アプリの下書きは `version`、`title`、任意の `screen`、任意の `workflow`、生成する `schemas` を一組で持つ。`screen` はOpenUI定義と必要な入出力の対応、`workflow` は§3.1〜§3.3の定義。画面とワークフローの少なくとも一方を必須とする。画面内の説明や計算だけなら画面を保存し、表のデータをワークフローから出す場合は画面と対応付けが必須になる。日誌は専用画面を省略できる。現行のPipeline本文だけの共同制作とは別の版付き契約として登録する。

1. LLMは公開された部品・型・保存先を参照して下書きを作る。ホストは生成スキーマに所有scopeと定義IDに結び付く参照を割り当て、既存の有限subset変換、Pipeline checker、画面検査で確認前に検証する。下書きの参照は実行や一般の型解決には公開しない。
2. 確認画面には対象・入力欄・列・起動方法・接続範囲・保存先を示す。ホストは保存済みの下書き版と、アプリ全体のdigestを発行する。確認操作は下書き版・digest・操作IDを指定する。ホストはwriter内で現在の下書きを再読し、確認後の編集や部品の版の変更を検出したら保存を拒否する。
3. applicationが単一writer transactionで各domainの公開操作を呼ぶ。`capabilities` は生成スキーマを既存の保存形式と検査で登録し、`ui-compositions` は画面の確定版を保存する。`pipelines` はワークフローの確定版と許可を保存する。最後に `app-development` が各版・digestへの対応、アプリの公開版、操作の受付結果を保存する。画面だけのアプリではワークフロー定義と実行許可は発行しない。生成スキーマの登録口は型だけを受け付ける。参照の利用許可は所有scopeと対応付けから検査する。
4. どの保存が失敗しても全体をロールバックし、編集用下書きは残す。保存操作IDと同じdigestの再送は保存済みの組合せを返し、異なる内容は競合にする。確認済みの画面・型を同じ版のまま上書きしない。編集は新しい下書きと版を作り、新版が確定するまで既存の組合せを使う。

画面は保存済みの対応から定義ID・版、入力スキーマ、許可された更新操作とデータ参照を解決する。任意の外部 `source` を許可する変更にはしない。再読込・再起動後も同じ対応を読み、参照先が欠けるか失効していれば再確認理由を表示して実行を止める。予約の有効化は制作物の保存後に§5の別操作で行い、下書き保存だけでは起動しない。

### Webの取得手順

上映一覧の定義は「指定日の全上映回」という要件を保持する。取得URLや読む箇所のヒントは取得手順キャッシュ側で管理する。前回のURLを使うときも、指定日に該当する本文かを確認する。日付別ページのリンクを見つける判断はWeb担当が行う。取得済みデータの並べ替えやフィルタは画面内で行い、ページ取得と文章生成の呼び出しを増やさない。

上映一覧の `web.records` は、検索結果を番号付きで提示し、モデルが選んだ候補番号から取得URLを解決する。指定劇場の公式候補を保護付き取得で読めた時点で入口を記録する。入口に掲載リンクがある場合は、先にリンク一覧を番号付きで提示し、モデルが指定日の日別ページを選ぶ。日別ページを保護付き取得で読めた時点で取得先を記録し、その本文を抽出へ渡す。検索で日別ページに直接到達した場合は、本文から対象日と上映回の根拠を確認して日別ページとして記録する。アプリ版・手順・劇場に取得先をひも付け、日別ページは日付でも分ける。実行中の権限をwriterで確認して保存し、全件抽出の確定は別に行う。日別リンクの選択や抽出が期限切れでも、先に記録した取得先は次の更新に使える。

同じ日付の更新は保存済みの日別ページを再取得する。取得できないか本文から対象日を確認できなければ、そのURLを外し、保存済みの案内ページか検索から取得先を探す。別の日付では案内ページを入口にし、その日への掲載を確認する。記録するのは取得先のURLで、上映行と根拠は更新のたびに取得した本文から作る。同じ入力で更新中または失敗したときは、最新の実行状況と、その入力の最後に確認できた結果を画面に表示する。

#### 共通の本文抽出で記事内の見出しを保持する

先行検証では、湘南の公式HTMLから上映時刻を取得できたが、同じHTMLにあった27種類の作品見出しは保護済み本文からすべて欠落した。固定HTMLで作品名の囲いを `header` から `div` に変えると、作品名と時刻が両方残った。現行の `llm-fetch@0.1.4` が本文候補を選ぶ前に `header` を一律に取り除くためで、URLの発見やLLMの抽出指示を変更しても、削除された根拠は戻らない。 [再現と照合結果](verification/reusable-content-workflows-2026-11-09/README.md#観測結果)

1. `llm-fetch` の `selectHtmlContent` で、ページ共通の `header` と、記事・節の中にある見出し用の `header` を分ける。既存の除外対象を先に取り除き、残った `article` または `section` 内で見出し要素を持つ `header` を本文候補に残す。ページ共通のヘッダー、バナー、ナビゲーションに属するものは現行どおり除外する。本文の順序は、見出しから配下の時刻や項目へたどれるよう保持する。
2. 変更範囲を本文候補の選択に絞る。ネットワークの制限、原本の可視・非表示部分を含む検査、拒否判定、返却量の上限は既存の取得経路に従う。通常抽出と審査後の抽出の両方に同じ選択を適用する。固定HTMLで、同じ文書のページ共通ヘッダーは除外され、複数記事の見出しとそれぞれの時刻が原文の順で残ることを確認する。保持する見出しや非表示部分に命令が混入したケースも、既存の安全検査で拒否されることを確認する。 [現行の取得adapter](../api/domains/web-research/adapters/llm-fetch.ts)
3. 固定試験を通した修正版のコミットとパッケージを記録し、Eumenesは検証した版を固定して取り込む。取得結果の `provider` と既存のキャッシュキーに入る取得部品の版を揃える。旧版の保存済み結果は読める状態を保ち、新しい取得で旧版の本文をキャッシュヒットとして採用しないことを確認する。 [取得キャッシュのキー](../api/domains/web-research/service/cache.ts#L54) · [結果スキーマ](../api/domains/web-research/contracts/index.ts)

#### 本文から型付きの上映回を返す

`web.records` には、既存の保護済み本文と、その範囲を読み直せる参照を渡す。長い本文は、既存の範囲検索・読み取りの契約を使って、対象日付の見出しから次の日付までを確認する。対象範囲と行の対応はLLMが判断し、ホストは日付、型、根拠参照、読取範囲を照合する。日付の境界が曖昧、本文が打ち切られている、根拠が不足する場合は部分結果とし、全件扱いを避ける。チネチッタのように日付を変えても取得本文が同じ場合、URLの日付だけで本文の対象範囲を決めない。 [既存の本文範囲読み取り](../api/domains/web-research/service/saved-bodies.ts)

保護付き本文がMarkdownのリスト項目を複数行に分けた場合、字下げされた続きは同じ項目として渡し、元の区切りと本文範囲への参照を保持する。上映回の参照候補は時刻が書かれた行に絞り、本文に複数の見出しがある場合はその行を作品名の参照候補にする。見出しの直下に並ぶ時刻範囲もまとめて提示する。LLMは作品ごとに作品名の行、上映形式の根拠、開始時刻の参照を短いJSONで返す。同じ作品と形式の上映回に当たる時刻範囲を確認できれば、その見出しの範囲をまとめて選べる。ホストは選択された範囲の開始時刻を展開し、同じ階層の別見出しからの混入を拒否する。上映形式は元の区切りの中にある表記を保持し、表示名は画面側で適用する。

初版はこの共通経路を採用する。公開JSONのフィールドパスやサイト別CSSセレクタの追加は、修正後も構造を保持できない取得先があり、全件一致または時間に実測上の改善が出ると確認した場合に、取得手順側の別案として扱う。

### Gitの基準点

GitHub接続には読み取り可能な所有者・リポジトリ範囲を設定し、その中で毎回 `repositoryPrefix` を適用する。新しいリポジトリが対象になる条件も確認画面に表示する。コピーはサービス専用領域に置き、認証とGit実行はバックエンドが所有する。リポジトリ内のファイルやコミット文は資料として扱う。作業ツリーのコード実行やpushにつながる操作は、日誌の部品の契約外として実行時に拒否する。

基準点のキーは接続・リポジトリの安定ID・追跡ブランチ。初版は初回発見時の既定ブランチを追跡し、その時点で取得した先端コミットを「基準登録」として日誌に含める。初回に過去の全履歴を日誌化することは含めない。以後は前回採用したコミットと今回取得したコミットの間のコミット一覧と差分を記録する。更新後のコピーのHEADは取得状態であり、日誌に掲載済みの基準点は別の正本に保持する。

取得に失敗したリポジトリや、前回のコミットが今回の履歴につながらないリポジトリは、理由と前回の基準点を残す。履歴の書き換えや追跡先の切り替えには明示的な基準点の再設定が必要。列挙が途中で切れた場合も未確認の対象を記録し、削除済みとして扱わない。全件取得不能なら実行を失敗として表示する。取得できた対象があれば部分日誌として保存できるが、基準点の更新には次の処理範囲の確認も必要とする。

### 日誌の処理範囲と基準点の対応

Git部品は、リポジトリ・追跡ブランチ・前回と今回のコミットに結び付く処理単位IDをホストから発行する。初版は一つのリポジトリの今回範囲を一単位とし、同じリポジトリ内の一部だけを採用して基準点を途中まで進める処理は含めない。基準登録と変更なしも、本文で扱うべき明示的な単位にする。取得失敗の単位には取得状態と前回基準点を残し、未確定の今回コミットや採用候補を作らない。候補の値と差分参照は今回の実行に固定し、後続fetchのHEADから読み直さない。

日誌部品は入力の全処理単位について、一件ずつ `coverage` を返す。`processed` はその単位の資料を評価して本文に反映したこと、`unprocessed` は未処理または判断に必要な資料が不足したことを表す。要約・省略の妥当性はLLMが判断し、全コミットの逐語的な掲載は要求しない。読取やモデルの処理量上限で必要な資料を確認できなかった場合は `unprocessed` とし、理由と未処理範囲を本文にも記す。取得失敗の単位を処理済みにすることはできない。

ホストは処理単位の欠落・重複・未知ID、別実行の根拠参照、Git候補との不一致を拒否する。本文の語句から処理済み範囲を推測しない。採用対象は「Gitが取得範囲を確定した候補」と「日誌が `processed` とした単位」の共通部分に限り、文書の永続保存後に更新する。二つのリポジトリを取得して一方だけ日誌化できた場合、他方は前回の基準点を保持する。全単位が未処理でも状況を記した部分日誌は保存できるが、基準点は一件も進めない。処理量不足が続く場合は同じ再試行を重ねず、対象範囲や処理手順を見直した版の確認へ戻す。

## 5. 起動、権限、結果採用

### 制作と起動

1. §3.4の共同制作の下書きと確認を使い、対象、起動時刻、定期実行で使う接続、保存先を提示する。ホストは確認時の定義・schema・部品・画面の版を確定し、その組合せへの実行許可を保存する。確認済みの画面から手動実行でき、予約型は許可された利用者がSchedulerへ登録する。
2. 画面操作とSchedulerは同じ受付を呼ぶ。受付は起動元、定義の版、入力digest、今回のID、許可を保存する。手動は操作ID、予約は `occurrenceId` を同一受付の判定に使い、同じID・異なる内容は競合として扱う。状態を引き継ぐ仕事は同じ定義IDで一件ずつ実行する。読み取り専用の画面更新は入力単位で重複を判定する。
3. ホストが保存済みワークフロー用の実行元を発行し、既存Pipelineの検査・起動へ渡す。現行の会話・共同編集・Agencyの実行元は既存の検査経路を使う。新しい実行元の検査では、現在の保存レコードと権限を照合する。既存の実行台帳に必要な会話IDは制作時に結び付けた実在の会話を使い、表示先の関連付けに限る。受付、子部品の実行直前、結果採用時に同じ権限を再確認する。
4. 予約の開始時刻、停止、取り逃した回の集約はSchedulerが扱う。ワークフロー側の排他は起動ジョブの終了後も下記の解除条件まで保持する。部品の版や接続の許可が失効したら停止理由を表示する。変更した定義で予約を動かす場合は新しい版を確認し、下記の予約切替を行う。予定の停止と受付済み実行の取消は既存Schedulerと同様に別操作とする。

画面からは既存のArtifact操作経路に、定義の保存・手動起動・予約の有効化・実行照会・取消を登録する。照会は実行IDを使い、状態、成果物参照、再確認が必要な理由を返す。予約の有効化は、Schedulerの公開transaction操作での予約作成と、発行された予約ID・実行許可IDの対応付けを同一writer transactionで行う。汎用の `POST /api/schedules` からこの対象を直接作る操作は拒否する。予定時刻には登録済みの予約IDから対応を読み、対象payloadの定義ID・版と、対応する実行許可の利用者scopeを照合する。

基準点は同じ定義IDのうち、接続、対象条件、追跡設定、基準点スキーマの版が一致する定義間で引き継ぐ。対象範囲が変わる新版は、確認画面に基準登録から始める旨を表示する。結果は定義の版・今回の実行ID・保存時に使った状態の版に結び付け、同じ定義の編集と実行を混同しない。

### 排他中の予約と新版への切替

状態を引き継ぐ定義の排他は受付と同じtransactionで取得する。手動の別操作IDからの起動は、実行中のIDと理由を返して受け付けず、同じ操作IDの再送だけが既存の実行を返す。予約は定義単位の排他が残っていれば未受付のまま保留する。保留中は `nextDueAt` を進めず、予約回・ワークフロー実行・文書IDを発行済みとして保存しない。解放後の時刻でSchedulerが再判定し、初版の日誌の `coalesce` は取り逃した回を直近の一回へ集約する。日誌の日付はその予定時刻、対象範囲は最後に採用した基準点からとなる。

現行の対象受付で単に例外を投げると `target_failed` としてスキップされるため、`TargetDefinition` に任意の読み取り専用の受付可否検査を追加する。Schedulerは同じwriter transaction内で、既存の起動ジョブ重複判定より前にこれを呼ぶ。「保留」と安全な理由コードを返した場合は予約回を消費せず、既存の遅延再判定を使う。ワークフロー側は保存済みの排他から判定し、Schedulerは業務状態を直接解釈しない。検査を持たない既存対象の動作は変えない。これは受付ジョブ終了後にも続く排他を扱うための最小拡張であり、Queueの容量不足に偽装したり、用途名で分岐したりしない。

新版への切替は、確認済みの新版と旧予約の版を指定する一操作とする。applicationが同一writer transactionで旧予約を `cancelInTransaction` し、新版を対象とする予約を `createInTransaction` で作り、新予約IDと許可IDの対応を保存する。旧対応は新規受付不可として保持し、受付済み実行の照合に使う。新予約の作成失敗は旧予約の取消も戻す。操作IDと内容digestで再送を照合し、新旧予約の二重有効化を防ぐ。初版は有効な予約の切替を対象とし、停止中の予約は取消後に別途有効化する。

時刻・間隔を変えない切替では元のanchor・interval・misfirePolicyを引き継ぎ、新予約の初回時刻は既存の作成規則どおり切替時刻以降の境界とする。旧予約の未受付の取り逃しは引き継がない旨と、新しい初回時刻を確認画面に示す。受付済みの旧版実行は元の許可と版で継続し、切替だけで許可を失効させない。新版も同じ定義IDの排他を守り、起動時に互換な最新基準点を読み込む。取消・権限失効を利用者が別途指定した場合は、その旧版実行も停止する。

### 実行と確定

ワークフローの状態は受付済み、Pipeline実行中、成果物確定待ち、終端の順に管理する。成果物確定待ちには保存中と要確認を区別して記録する。実行中の子処理は既存の親実行から照会する。型に合う部分結果は、子処理としては引き渡し可能な確定結果にし、データの完全性を別フィールドで表す。これにより現行Pipelineの「確定した子結果だけを次に渡す」規則を使いながら、部分日誌を作れる。

| 出来事 | 成果物と状態の採用 |
| --- | --- |
| 表の出力が確定 | 所有scope、定義の版、入力、根拠を検証した結果を保存する。画面は選択中の入力と直近の操作に対応する結果だけを現在値として表示する。再読込時は同じ入力の最後の結果と取得時刻を読める |
| 日誌の作成が確定 | Markdown側の既存保存操作を、実行と結び付けた固定IDで受け付ける。下書き・coverage・Git候補を別々の不変参照で保存し、その対応を検査する。基準点の値はGitの結果だけから解決し、採用対象はcoverageとの共通部分に限る |
| 永続保存が確認できた | 保存済み文書の参照、実行の終端、日誌で処理済みの対象の基準点更新、排他解除を同一writer transactionで採用する。採用直前に、前回の基準点が今回の入力と一致することを確認する。不一致なら採用競合として終端し、基準点は更新しない |
| 保存を行わず終了、保存失敗が確定、競合 | 基準点を維持して失敗または競合として終端し、排他を解除する。一時保存だけで終了した結果も同様。送信済みか不明な保存はここへ分類せず要確認にする。次に許可された実行は最後に採用したコミットから取得する |
| 保存応答が失われた | 固定IDと内容digestで既存文書を照合する。保存確定まで同じ仕事の次回起動を抑え、確定できなければ要確認として残す。同じ予約回を別IDで作り直す操作は拒否する |
| 取消、期限切れ、権限失効 | 終端と排他解除を同じtransactionで保存し、遅れて返った結果や保存応答から基準点を進めない。送信済みの外部保存については確認できた状態を区別して表示し、既存文書の扱いは利用者の操作に委ねる |

保存状態を要確認にした場合は、同じ文書IDを既存の読取照合で再確認できるようにする。確定した保存を基準点へ採用できるのは実行許可が有効で、取消・期限切れで終端していない場合。終端済みの実行では文書の有無だけを表示する。次回を再開するときは、最後に採用した基準点から取得する。

### 進行管理と再起動時の復旧

`pipelines` は既存Queueに再実行可能な進行確認ジョブを登録する。受付レコード・排他・最初のジョブを同じtransactionで保存し、各進行段階の更新と次の確認ジョブの予約も一括で行う。待機中はQueueの実行可能時刻で間隔を空け、子処理の完了通知は確認を早める補助として使う。画面の照会やメモリ内の通知だけを進行の契機にしない。起動時には非終端レコードとジョブを照合し、欠けた確認ジョブを重複なく補う。

進行確認ジョブはLLMやGit処理を独自に再実行せず、親実行・Markdown保存の公開操作と保存済みの結果を照合する。親実行の開始はワークフロー実行IDに対応する固定の受付キー、Markdown保存は固定文書IDと凍結内容digestを使う。外部通信はwriter外で行い、採用時に権限・状態の版を再検査する。実行全体の期限はホストの実行・保存上限に基づき受付時に固定して表示し、復旧や再照合で延長しない。

| 停止した境界・状態 | 再開担当と処理 | 排他 |
| --- | --- | --- |
| 受付保存後、親実行の開始前 | 進行確認ジョブが固定キーで親を開始し、親IDとの対応も同じtransactionで保存する | 保持 |
| Pipeline実行中 | 既存agent-runtimeが子処理を管理し、進行確認ジョブが親の状態を照会する。親が失敗・取消・期限切れ・手順未完了のpartialで終端した場合は再生成せず、ワークフローも基準点を進めず終端する。データの部分性を持つcompleted結果は通常の採用検査へ進む | 非終端なら保持、終端なら解除 |
| Pipeline完了後、Markdown受付前 | 親の型付き結果を読み、凍結した下書き・coverage・Git候補と固定文書IDで保存を受け付ける。結果参照を再読できない場合は基準点を進めず失敗にする | 保持 |
| 保存受付後、応答確定前 | Markdown側の公開操作でQueueと保存台帳を照合する。中断済みジョブの未確定保存を正規化し、送信の可能性があれば要確認にする。同じ文書の再送信はせず、既存の読取照合へ進む | 保持 |
| 永続保存済み、基準点採用前 | 保存receiptとdigest、coverage、前回基準点、許可を再検査し、採用transactionを行う | 採用または失敗終端と同時に解除 |
| 要確認 | 既存の有限回の読取照合を行う。未確定なら要確認のまま表示し、次は利用者の再確認操作を待つ。期限監視と取消は継続する | 保存確定または終端まで保持 |
| 終端・採用済み | 再送・遅延結果は既存結果を返す。基準点更新や文書作成を繰り返さない | 解除済み |

採用済み判定と状態の版の照合で、確認ジョブの重複起動を無害にする。Markdownの中断状態の正規化と読取照合はMarkdown側が所有し、`pipelines` からその台帳を直接変更しない。取消後に外部保存が完了した場合、同じ予約回の別IDでの保存は行わないが、後続回には基準点未採用の範囲が再び含まれ得る。この場合は文書の存在と基準点未採用を分けて表示する。

実行ID、予約回ID、子処理ID、文書IDを相関させ、起動拒否、部分結果、保存要確認を画面から区別できるようにする。通常ログは安全なコードと識別子に限定し、本文・差分・認証情報は権限付きの業務データとして扱う。

## 6. 実装順と受入

上映一覧の実サイト受入は、本文修正、推論接続の確認、全件抽出、実画面の順に進める。保存・予約・Pipeline・成果物採用の共通基盤と開発日誌の固定試験は、Web取得の判定から切り離して進められる。実モデルを使う受入は、用途ごとにその推論経路が利用可能な条件で行う。

### 6.1 上映一覧の取得と推論を別々に判定する

1. **本文の欠落を修正する**。§4の固定HTMLで現行版の欠落と修正版での保持を比較する。見出しと時刻の対応、安全検査、本文の上限、旧キャッシュからの移行を検証してから、修正版で湘南と別映画館の公式本文を二日付ずつ取得する。LLMを呼ぶ前に、照合表にある日付・作品・時刻・形式の根拠が保護済み本文に残っているかを確認する。単語が本文のどこかに存在するだけでは合格にせず、同じ上映回の根拠として対応をたどれることを確かめる。
2. **推論経路を確認する**。本文取得とは別に、予定している実行経路・接続の役割・保存済み設定で、短い型付き入力から検証可能なJSONが返ることを確認する。先行試行では接続準備で期限を使い切ったため、接続準備、Queue待機、モデル処理を別に記録する。接続が準備完了に達しない場合はその段階の未達とし、条件が変わるまで全件抽出の再試行を保留する。短い診断は全件抽出の計測から分けて記録し、受入時の経過時間には、実際に発生した接続準備と待機も含める。 [前回の時間内訳](verification/reusable-content-workflows-2026-11-09/results.json)
3. **全件抽出を再測定する**。公式の対象URL・日付と照合表を事前に固定し、二映画館・二日付の各条件を3回測る。日付・作品・開始時刻・掲載された上映形式・根拠が一致し、欠落・重複・余分な行がなく、依頼受付から行データ確定まで各回60秒以内で合格とする。取得、待機、モデル処理、キャッシュの有無を分ける。公式一覧が更新されていたら新しい照合表とdigestを保存し、前回から変わった条件を明記する。未達なら取得本文、対象範囲の選択、抽出結果、時間のどこで失敗したかを判定し、同じ条件で試行を重ねる前に設計を見直す。

### 6.2 共通基盤を固定データで実装・検証する

1. **保存と型の契約を確定する**。共同制作の下書き、生成スキーマの登録、画面の確定版、制作物の対応、coverage、予約の受付保留、進行確認ジョブの公開契約を用意する。型・画面・定義・許可の各保存位置で失敗を注入し、一組の一部だけが公開されないことを確認する。確認後の編集、同じ操作IDで異なる内容、別scopeの型や画面参照は拒否する。既存の型・画面の保存と共同制作も回帰確認する。
2. **固定部品で保存・復旧まで結合する**。保存済み定義の起動元、既存Pipelineへの型付き参照、予約と手動の共通受付、Markdown保存と基準点採用を通す。異なるscope、失効版、直接の予約作成、型違い、捏造した参照を拒否し、同じID・同じ入力は既存の実行を返す。§5の復旧表の各境界で停止を注入し、画面を閉じたまま再開して進行または正しい終端へ到達することを確認する。保存応答喪失、ジョブの重複、取消、期限切れ、権限失効を含め、同じ予約回の文書が二重に作られず、保存成功時には一件を照合でき、基準点が二重更新されないことを確認する。
3. **排他と新版切替を確認する**。試験環境の時計を進め、起動ジョブが実行中の場合と、終了済みで成果物だけが未確定の場合の両方で次の予約時刻を越える。予約が `target_failed` や `overlap` へ落ちずに保留され、解放後は直近の一回へ集約されることを確認する。旧予約の取消後・新予約の作成前の失敗、切替の再送、旧版の実行中の切替、基準点の互換・非互換を確認し、二重予約と旧版結果による新版状態の上書きを防ぐ。受付可否検査を持たない既存対象の動作も確認する。
4. **制作の公開入口を切り替える**。画面だけ、画面とワークフロー、専用画面なしのワークフローを、新しい担当のセッションから作成・確認・再読込する。旧版入りのDBで旧履歴が新アプリの一覧に現れず、旧参照が安全に失敗し、旧フォーム回答と他のデータが維持されることを確認する。旧担当の新規起動と、旧タブからの保存の再送が受理されず、再起動後も新担当だけが能力検索・ランチャーに現れることを確認する。公開の切替はこれらの固定試験の後に行う。

### 6.3 利用者の操作から成果物までを確認する

1. **上映一覧**。自然文から型・画面・手順を作り、確認して保存し、再起動後にOpenUIを開き直す。同一作品の通常上映とIMAX、別の日付、当日回なし、取得漏れを固定本文で照合する。日付変更時に古い応答が新しい表示を上書きしないことを確認する。実サイトとの結合は§6.1の全件抽出と§6.2の通過後に行い、同じ条件で全件と根拠の一致、更新操作から表示確定まで60秒以内を確認する。固定データでの画面成功と実サイトでの受入は別に記録する。
2. **開発日誌**。§6.2を通過した共通基盤で、試験用の複数リポジトリによる初回基準登録、変更なし、追加対象、取得失敗、履歴の書き換えを再現する。二つとも取得できたが一方しか日誌化できないケース、差分の読取上限、全件未処理、coverageの欠落・重複・偽装も試す。保存後に処理済みの対象だけ基準点が進み、未処理分が次回に含まれることを確認する。自然文からの制作・予約有効化、試験用GitHubとDoclingへの保存まで通す。
3. **段階別に結果を記録する**。契約の部分試験、実際のQueue・writer・登録を使う結合試験、対象ファイルを指定したブラウザ試験の順に行う。`bun run verify -- --domain <name>` で `app-development`、`pipelines`、`agent-runtime`、`scheduler`、`tool-runtime`、`capabilities`、`collaboration`、`ui-compositions`、`web-research`、`markdown` と、新規Git観測domainを確認する。固定データ、実Web・実モデル、試験用GitHubとDoclingでの保存結果を別々に記録する。ブラウザ試験では画面の保存・再読込と更新操作も対象にする。 [検証手順](../docs/toolchain-extension-verification.md)

受入時には、二つの用途で異なるのが定義、型、登録部品、保存先であることを差分でも確認する。映画館やプロジェクト名を変えたときに製品コードの分岐が必要なら、契約のどこに用途固有の前提が入ったかを見直す。
