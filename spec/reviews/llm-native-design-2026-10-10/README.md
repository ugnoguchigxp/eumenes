# Eumenes の LLM Native 設計レビューと要件データの扱い

シナリオ固有の確認項目をデータとして保持し、共通の実行基盤が検証する構成を推奨する。意味の解釈はLLM、形式と参照の整合性・権限・取消の強制はコードが担う。新しい調査対象を追加するとき、製品のTypeScriptを変更せずに対応できることを受入条件にする。

2026年10月10日の作業ツリーを対象に、残存する問題を5件確認した。最優先は、保存した要件が実際のモデル入力へ届く経路の整備と、感情候補を語句で事前選別する処理の撤去である。天気・株価の専用処理3群は調査中に別の作業で削除されたため、残存件数に含めない。

レビューは実装の適合性に限定したtechnical/deep、agent profile、current評価。製品全体のTechnical Qualityの正式点数は保留、Project Potentialは対象外。LLM-Nativeの制約に関する2基準だけを評価し、全体の根拠カバー率は6.7%。点数から製品の品質やリリース可否を推定しない。問題の存在は再現とソース経路で確認したが、代替するモデルの精度・遅延は未評価。

## 残っている問題

### F01 保存したSKILLの本文がworkerへ届かない

優先度P1、影響Medium、確信High。

`api/domains/agent-runtime/service/context.ts:28` は必須profileとSKILLの存在・本文の有無を確認する。一方、生成するメッセージには共通policy、ツール、依頼、観測だけを入れ、依存定義の本文を含めていない。依存定義のhashはmanifestに入る。

再現では、SKILL本文を「締切時刻と料金を確認」から「定員と受付場所を確認」へ変えても、モデルに渡すメッセージは完全に同一だった。manifestは変化した。したがってSKILLを保存・改訂するだけでは、シナリオ固有の要件を動作に反映できない。

現在の共通policyで一般的な調査を進めること自体は可能で、旧planner指示の重複を除く意図も既存試験にある。ただし、要件をデータとして扱うための経路は別途必要である。旧SKILL全文を無条件でsystemへ戻す修正は避け、選択した要件データと版・出所・適用範囲を実行時入力に含める。共通の役割・権限規則は一か所に保持する。

受入条件: 要件AとBでモデル入力と要求される検証結果が変わり、同じ版は実行途中に書き換わらない。外部本文の指示は権限を変えない。必要な要件を文脈容量から黙って落とさない。

### F02 感情判定モデルの前に語句で候補を制限する

優先度P1、影響Medium、確信High。

`api/domains/delivery/service/evidence.ts:20` は喜び・共感・興味等を日本語の正規表現から判定する。`api/domains/delivery/service/index.ts:109` はその候補だけをモデルへ渡し、空ならモデルを呼ばずneutralへ戻す。通常の推論経路はfullCandidatesを指定していない。

再現では「おめでとうございます。」でモデルを1回呼びjoyになった。同じ祝福を表す「努力が実りましたね。心から祝福します。」ではモデル呼出し0回、`not-expressive`となった。これはモデルの能力によらず語彙表が表現可能な範囲を決めている。

選択可能な感情と意味の説明をデータとしてモデルに渡し、引用・否定・文脈も意味判断に含める。結果の列挙値、信頼度、期限、TTSに渡す数値の範囲検査は残す。感情からモーションや数値プリセットへの対応表は、表示・音声設定としてデータ化できる。

受入条件: 未登録の言い換えでも候補が消えない。引用、否定、慰め、祝福を評価用データで区別し、単語の追加で試験を通さない。モデル不在・失敗時のneutralは保持する。

### F03 タイマーの構造化結果を定型文に縮めてからLLMへ渡す

優先度P2、影響Medium、確信High。

`api/domains/dialogue/service/timer-phrase.ts:16` は口調を語尾置換で実装し、同ファイル`:73` は複数タイマーを件数だけの文章へ縮める。`api/domains/dialogue/service/index.ts:323` と`:383` はその文を`actionResult`として回答生成へ渡す。

残り120秒と300秒の2件は「タイマーが2件動いています」だけになった。このactionResult経路では各残り時間が失われる。別途渡されるsnapshotで補える場合はあるが、応答モデルが使う事実を文字列化で減らす必要はない。最終回答は既にLLMが生成しているため、定型文を最終回答として直送している、という指摘ではない。

操作receiptから公開してよい型付き結果を抽出し、件数・ラベル・状態・残り時間をデータで渡す。口調は既存のpersona指示へ集約する。結果の更新時点、取消、採用ticket検証は残す。

受入条件: 複数タイマーの名前と残り時間を質問したとき、回答生成へ必要な値が届く。口調変更のための語尾分岐を追加しない。操作は一度しか実行されない。

### F04 文字種で言語を推定して音声入力を拒否する

優先度P2、影響Medium、確信High。

`api/domains/voice-dialogue/service/asr-language.ts:24` の言語と文字種の表、`:56` の「中国語のみ」の文字表で言語許可を判定する。`api/domains/voice-dialogue/service/index.ts:352` が実際の拒否に使う。

再現では許可言語jaの「APIを確認してください」が拒否され、許可言語enのフランス語「Bonjour, comment allez-vous?」は通った。文字種の所属と発話の言語が一致しないためである。現ASRが検出言語を返さない制約はコメントに明記されているが、この推定を正しい言語検証として使うことはできない。

まずASRの言語指定・検出結果を利用できるか確認し、利用できなければ共通のモデル判定へ接続するか、文字種フィルタとして機能の意味を限定する。許可言語リストは設定データ、検出済み言語と許可リストの照合はコードに残す。混在言語・固有名詞・略語の扱いは評価データで決める。

受入条件: 日本語中の英字略語を誤拒否せず、同一文字種の別言語を許可済みと即断しない。判定不能を許可言語と同一視しない。

### F05 単語と句読点で音声の意味上の強調を決める

優先度P2、影響Low、確信High。

`api/domains/inference/service/speech-intonation.ts:7` と`:31` は「注意・警告・重要・必ず」や句読点で速度・高さ・抑揚を変える。再現では「特に注意する必要はありません。」にもnoticeの補正が掛かった。

ただし影響範囲は限定される。`api/domains/inference/service/execute.ts:247` は判定providerが利用できるとき、この補正を外す。主に自動抑揚が有効で判定provider不在等の経路で残る処理である。

既存の意味判定を共通経路として使い、モデル不在時は保存済みの音声設定を使う。数値のclamp、利用者設定、外部TTSへのパラメータ変換は保持する。音声プリセットはデータとして管理する。

受入条件: 否定文・引用文中の語句だけでは強調しない。provider不在時の挙動は一定で、シナリオ語彙に依存しない。

| `research-routes/service/keys.ts` | 鎌倉・静岡市・AAPLと有限文法だけを受理。横浜、MSFT、自然な言い換えはunsupported | 要件の適用判断をLLMと登録データへ移す際の回帰例 |

## 両立する仕組み

### 要件を扱う単位

最初に、実行ごとの「依頼契約」を共通の形式で作る。ユーザーの原文、対象・時点・条件、必要な出力、各条件の出所を保持する。既存の会話担当または調査担当の出力を拡張し、要件を作るだけの専用振分け役は追加しない。

再利用するシナリオは、版付きの要件データとして登録する。シナリオ名や項目名のたびにTypeScriptのunion、if、switch、validator関数を追加する構造にしない。たとえばイベント調査の「開催日時・料金・申込期限」は登録データの項目であり、共通workerの型にイベント専用フィールドを追加する必要はない。

| 内容 | 保持・判断する場所 | 例 |
| --- | --- | --- |
| 適用範囲と確認する意味 | 版付きデータをLLMが解釈 | 申込方法を聞かれた場合、受付期間と条件を確認 |
| 出力の型・必須項目・列挙値 | JSON Schema等のデータを共通検証器が検査 | 締切は日時、料金は数値と通貨、根拠は参照一覧 |
| 対象や時点との機械的な比較 | 構造化済みデータに共通演算を適用 | 対象ID一致、指定日と有効期間の比較 |
| 本文から値を取り出す意味判断 | LLM | 表や文章から期限・例外・対象を読み取る |
| 根拠が主張を支えるか | LLMによる意味検証 | 「受付開始」を「締切」と誤読していないか |
| 引用・参照・版の整合性 | コード | 同じ実行で提示した資料か、引用が存在するか |
| 権限・取消・予算・採用 | コード | 許可ツール、owner、cancelEpoch、期限、transaction |

JSONへ正規表現を移すだけでは、意味判断を語彙へ固定する性質は残る。データへ移す対象は「何を満たすか」であり、「この言い回しならこの答え」という代替実装を増殖させない。日時の計算や型検査のように明確な計算は、共通処理としてコードに残す。

### 検証結果もデータにする

各要件に対して、`満たした / 満たさない / 不明 / 適用外` と根拠参照を返す。たとえば料金が見つからなければ不明とし、要件自体を結果に合わせて削除しない。適用外には対象・条件に照らした理由が必要で、不明を合格へ丸めない。

共通検証器は、全要件への結果があるか、値がschemaに合うか、根拠が有効かを検査する。型や参照が正しくても意味の正しさは保証されないため、意味上の確認が必要な要件では元資料・凍結済みの要件・抽出値をモデルが照合する。必要な箇所だけを確認し、毎回別エージェントを増やす設計にはしない。

結果には利用した要件のID・revision・digest、request binding、資料の版、検証結果を結び付ける。既存の採用ticketと取消検証を利用する。hashの一致は改変検出であり、内容の真偽を証明するものではない。

### 外部から見つけたルールの扱い

Web本文にある応募条件や時刻表の適用条件は、出典付きの候補データとして抽出できる。ユーザーの依頼・登録済み要件・適用範囲と照合し、その実行に適用する条件を確定する。ユーザーの必須条件を弱めたり、外部本文をsystem命令に昇格させたりしない。

データには取得元、対象範囲、有効期間、版、確認状態を持たせる。取得時点の値と、再利用できる手順を分ける。保存済みの成功だけで将来の値を正しいと扱わず、現在の対象・時点・出典を再確認する。権限を増やすフィールドやJavaScript・shell等の実行文字列は受け付けない。

形式検査はJSON Schema等の既存形式に寄せる。項目間の比較が必要なら、実際に必要になった共通演算を小さく用意する。汎用性を理由に任意コードを実行できるルール言語を作らない。schemaやルールの深さ・件数・サイズも共通の上限で制御する。

### 既存機構を利用する範囲

`capabilities`には不変revision・hash・世代・依存閉包・失効検査、`agent-runtime`には一つのworkerループと根拠catalog、`tool-runtime`には権限付き実行、`inference`には制御用モデル呼出しがある。これらに要件データの受渡しと検証結果を接続する。

まず実行中だけの依頼契約を通し、再利用が必要な要件だけを版付き定義へ保存する。現在の`schemaKey`はTypeScriptに定義されたツール入力検査を選ぶ仕組みであり、任意のシナリオ出力schemaを登録する仕組みにはなっていない。ツールの固定I/O契約を保ちながら、シナリオ用の出力schemaを独立したデータとして追加する。

旧取得先学習のauthor/reviewer/registrationはsnapshotで撤去済みであるため、稼働中の共通機構として再利用できるとは見なさない。旧天気・株価分岐を復活させず、既存のrevision保存と制御推論の公開操作を利用する。

## 修正順と受入

| 順番 | 対象 | 完了条件 |

| 1 | F01と依頼契約 | データだけで要件を追加でき、モデル入力と検証結果へ届く。採用時に同じ版を確認できる |

最も重要な受入試験は、製品コードを凍結した状態で、既存のツールで取得・実行できる未対応シナリオを要件データだけで追加すること。モデルが要件を読み、型検査と意味検証を行い、根拠付き結果または不足を返せることを確認する。例としてイベントの申込条件、施設の利用条件、商品の対応条件を評価データに用いる。新しい外部プロトコルへの接続など実行能力そのものが不足する場合は、必要性を示したうえで共通のadapterを拡張する。

さらに、同義の言い換え・地名や商品名の変更・項目の追加・否定・例外条件・根拠不足・出典矛盾・外部本文中の権限要求・実行中の版更新と取消を試す。シナリオを増やすたびに製品TypeScriptの追加が必要なら、設計の受入は不合格。テストデータや期待される契約を固定することは、この制約に反しない。
