# 意図の判定で会話の文脈を分ける 設計（2026-10-29）

[local ハーネスの作り直しの計画](local-harness-rebuild-plan-2026-10-30.md)（2026-10-30）に置き換えた。§2.1 の `## Intent` も消した。以下は経緯として残す。

案・合意待ち（§2.1 だけ実施済み）。利用者指示（2026-10-29）:

- 「いきなり分類器に判断させるんじゃないのか。何のための分類機だ」
- 「tool利用ができないのでこうしてるのでは」
- 「tool利用時は会話の履歴をいれないとか、memoryのツール利用方法とかもいれず、subagentみたいにツール利用にフォーカスさせる。多少の会話はするけど。通常の会話時はむしろtoolチェーンの事を一切Contextに入れない」

ローカルの LLM（LFM）は、ツールを使うかどうかの判断も、ツールの引数を埋めることも苦手です（2026-10-29 の本番では `delegate` の `impact` を7回中0回しか書かず、予告も書かなかった）。そこで、ツールを使うかどうかは Ruri の意図判定が決めます。LLM には、その回の役目に要るものだけを渡します。

## 1 決めること

| # | 決めること |
| --- | --- |
| 1 | Ruri の判定で、その回の文脈を「会話」「ツール」「今の形」の3つから選ぶ（local ハーネスの、利用者の発言への回だけ）。知らせ（Host notice）の回、cloud ハーネスの回、判定のない回は今の形のまま |
| 2 | 会話の文脈には、担当（ツールチェーン）とツールのことを一切入れない。ツール定義も送らない |
| 3 | ツールの文脈は、サブエージェントのようにツール利用に絞る。会話の履歴・`## Memory`・記憶のツールは入れない。予告や短い返事は話す |
| 4 | 記憶の操作（読む・覚えて・忘れて）は、ツールではなく担当にする（[ローカル文脈の予算の設計書](local-context-budget-design-2026-10-29.md) §4.1 をここで実施）。ツールは `find_toolchain`・`delegate`・`work` の3本 |
| 5 | LFM が書かない `delegate` の予告は、ホストが補う（D8）。利用者の発言への回が返事なしで終わったら、ホストが決まった一言を話す（B） |

## 2 判定と文脈

| Ruri の判定 | ルート | 文脈 |
| --- | --- | --- |
| `chat`・`noise`・`incomplete` | `answer` | 会話の文脈（§3） |
| `request`（スコアが `searchScore` 以上） | `search` | ツールの文脈（§4）。最初の呼出しで担当探しを強制する（今と同じ） |
| `followup`、`request`（閾値未満）、判定なし（失敗・時間切れ） | `free` | 今の形（会話の履歴とツールの両方）。仕事への返事は、質問した会話とツールの両方が要る |

`answer` の今の実装（ツール定義を送り、`toolChoice: none`）は、§3 の「ツール定義を送らない」に置き換える。

### 2.1 判定を system に入れる（実施 2026-10-30）

利用者指示（2026-10-30）:「若干SystemContextの一部である結果を返すべき」「今ruriはtool利用か、そうじゃないかだけしか判断していません。５シナリオ要りません」

それまでは、判定はツールの出し方（`toolChoice`）と拒否だけで効かせていて、モデルの入力には何も書いていなかった。2026-10-30 朝の会話では、音楽の依頼（`request` 0.96 → `search`）でも、LFM は返事のない前の天気の依頼を探した（`find_toolchain` の `query` が「天気予報」）。判定の結果を、system の一部としてモデルに伝える。

| ルート | system の末尾に足す節 |
| --- | --- |
| `search` | `## Intent`<br>`- 利用者の今の発言は、担当への依頼です（意図の判定）。担当を探して、今の発言の内容を頼みます。` |
| `answer` | `## Intent`<br>`- 利用者の今の発言は、担当への依頼ではありません（意図の判定）。担当やツールは使わず、話して返します。` |
| `free`（`followup`・閾値未満・判定なし）、`shadow` | 足さない |

| 項目 | 決め |
| --- | --- |
| 位置 | system の最後（`## Results` の後）。判定は回ごとに変わるので、前に置くと system 全体のキャッシュが外れる。末尾なら、外れるのはそこから後（会話の履歴、テンプレートが system の後に置くならツール定義）だけ |
| 文の置き場 | `api/domains/dialogue/contexts/intent/search.context.toml`・`answer.context.toml` |
| 写しの検査 | 返事の写しの検査（`system_text_copied`）は、判定の節を含む system で行う。会話の記録の写しの除外（`copyFilter`）は、今と同じく判定を含まない system で行う |
| 範囲 | 判定が動く回だけ（local ハーネスの、利用者の発言への回）。cloud ハーネス、知らせ（Host notice）の回は今と同じ |

## 3 会話の文脈（`answer`）

| 部分 | 入れるか | 中身 |
| --- | --- | --- |
| system `## Role` | 入れる | 今と同じ |
| `## Speaking` | 入れる | 担当の語を含む行（「制作物や詳しい内容は担当への依頼と成果物に含め…」）を外した会話用の文 |
| `## Emotion` | 入れる | 今と同じ |
| `## Input` | 入れる | 今と同じ |
| `## Facts` | 入れる | 「今の外の状態を聞かれたら、担当に改めて頼みます」を「確かめていないことは、確かめていないと伝えます」にした会話用の文 |
| `## Toolchains`・`## Tools`・`## Results` | 入れない | |
| ツール定義 | 送らない | |
| `## Memory` | 本人の発言だけ | 出所が「本人の発言」の項目だけ（300 token まで）。推測（`agent_inferred`）と観察（傾向）は入れない。LFM は「（推測）」と付けても事実として使う（2026-10-29、「火曜の夜（22時頃）にぴたりの音楽を好む（推測）」から挨拶に毎回プレイリストの話をした）。2026-10-29 時点では有効な24件のうち本人の発言は1件 |
| 最近の会話 | 入れる | 今と同じ（発言と返事の文だけ） |
| `## State` | 一部 | 今・話題・決まったこと・未解決・関係する記録。仕事と提示中は入れない（番号とツールのための欄） |
| `## User` | 入れる | 今と同じ |

固定の部分の大きさは、概算で今の 5,108 token から約 2,300 token になる（system から `## Toolchains`・`## Tools`・`## Results` を外し、ツール定義を送らない）。

## 4 ツールの文脈（`search`）

| 部分 | 入れるか | 中身 |
| --- | --- | --- |
| system `## Role` | 入れる | 今と同じ |
| `## Speaking` | 入れる | 今と同じ（予告と短い返事を話す） |
| `## Emotion` | 入れない | |
| `## Input` | 入れる | 今と同じ |
| `## Facts` | 入れる | 今と同じ |
| `## Toolchains` | 入れる | 担当名の一覧の行を外す（「何ができるか」は会話の文脈では答えず、依頼としてここで探す） |
| `## Tools` | 入れる | `work` の行と「受け付けなかった呼出しは…」の行だけ。記憶の行と会話履歴の担当の行は外す |
| `## Results` | 入れない | |
| ツール定義 | `find_toolchain`・`delegate`・`work` | |
| `## Memory` | 入れない | 担当には、今と同じく記憶の参照（execution references）で渡る |
| 最近の会話 | 入れない | |
| `## State` | 入れる | 今・仕事・提示中（`target`・`a<n>` の解決に要る）に、直前の自分の返事を1行（「直前の返事: …」、200字まで。「それ」「さっきの」の解決のため）。話題・決まったこと・未解決・関係する記録は入れない |
| `## User` | 入れる | 今と同じ |
| 回の中のツールのやり取り | 入れる | 今と同じ |

固定の部分の大きさは、概算で約 3,000 token（system 約 2,000、ツール定義 3本 約 1,035）。

回が終わった後は、今と同じく、利用者の発言と自分の話した文（予告・返事）が会話の記録に残り、次の会話の文脈の最近の会話に入る。

## 5 接続とキャッシュ

3つの文脈は先頭が違う。どれも主会話の接続で送る。ツールの文脈は会話の履歴を持たないので、先頭が外れても再計算は約 3,000 token（LFM で 1 秒前後）で済む。会話の文脈は回ごとに後ろへ足すだけなので、これまでどおりキャッシュが効く。切り替えでキャッシュが崩れる（会話の文脈の最初の呼出しのキャッシュが毎回 0 になる）と測れたら、ツールの文脈を補助の接続に移す。

## 6 記憶を担当にする

[ローカル文脈の予算の設計書](local-context-budget-design-2026-10-29.md) §4.1 のとおり（`memory.recall`「記憶の確認」、`memory.request`「記憶の依頼」、即答型）。会話の文脈にはツールがないので、「覚えて」「忘れて」「前に何て言ったっけ」は `request` と判定されてツールの文脈で担当を探す。`memory` ツールは、cloud ハーネスを含めて削除する。

## 7 LFM 向けの補い

| # | 内容 |
| --- | --- |
| D8 | `delegate` の `execute` で予告が要る担当なのに予告が無いときは、拒否せず、ホストが決まった文で補う。文は dialogue の文脈に置く（「〈担当の名前〉に頼みました。終わったら画面でお知らせします。」）。モデルが書いた予告は今と同じく使う |
| B | 利用者の発言への回が、話す文なし・担当への引き渡しなしで終わったら、ホストが決まった一言を話して記録する（「うまくできませんでした。もう一度言ってもらえますか。」）。会話の文脈（`answer`）で何も言わなかった回は対象外（相づち不要の雑音・言いかけ） |

## 8 変えないもの

- cloud ハーネスの文脈（記憶のツールを担当にすることだけは両方）。
- 知らせ（Host notice）の回の文脈。
- `find_toolchain` を最初に呼ぶ手順（ツールの文脈では強制する）。
- 会話の記録と記憶の項目。

## 9 段階

| 段階 | 内容 |

| P2 | 3つの文脈を組み、判定で選ぶ（§2〜§5）。`answer` の今の実装を置き換える |

## 10 確認

| 確認 | 方法 |
| --- | --- |
| 会話の文脈に担当・ツールの語がない | dialogue の固定の試験（system・State・ツール定義に「担当」「find_toolchain」「delegate」「work」「t1」「a1」が出ない） |
| ツールの文脈に会話の履歴・`## Memory`・記憶のツールがない | dialogue の固定の試験 |
| 大きさ | 固定の試験で、会話の文脈の固定部分が約 2,500 token 以下、ツールの文脈が約 3,200 token 以下 |
| 判定が失敗したら今の形 | dialogue の固定の試験 |
| live | 再起動の後、利用者の合図で「こんばんは」「音楽を作って」「覚えておいて」を話し、`dialogue_intent_judgments` とログで、文脈と結果を確かめる |
