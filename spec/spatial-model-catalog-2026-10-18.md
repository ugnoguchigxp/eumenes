## 1. 方針

- **使用率は想定内。** CPU・GPU・メモリが活発に使われていても、それだけで色や動きの速さを変えない。
- **異常は「溜まり」と「出来事」で出す。** 溜まりは負荷平均の上昇、待ち時間の伸び、メモリ不足による停止など。出来事は強制終了、GPU のリセット、読み込みの失敗など。観測できない値や出来事を演出のために作らない。
- **溜まりは形の内部の光で示す。** Backend は入口側に光が残り、GPU は帯の光の進み方を抑える。どちらも待ち件数・最古待ち時間はラベルで示し、粒子を増減させない。
- **LARM ホストは持ち歩けない。** LARM に届かないときは、LARM 星系ごと表示から外す（§3、実装は §8 M5 の保留対象）。
- **外形は固定する。** モデル内の粒子のローカル座標を固定し、光の位相だけを進める。以下の「回る」「流れる」「満ちる」は明るさの移動を指す。形の回転・変形・噴出・花弁の開閉ではない。Scene の配置・公転とは分けて扱う。

## 2. 共通の状態表現と動き

| 状態 | 色 | 見え方 |
| --- | --- | --- |
| healthy（正常） | `#a8d6ff` 青白 | 基本の明るさ。activity に応じた穏やかな光 |
| pressure（負荷） | `#ffaf62` 橙 | 動きを増やさない。各モデルの定義に従い、流れを抑える・止める・光を残す |
| fault（障害） | `#ff6177` 赤 | 通常の流れを止め、idle 相当以下の弱い呼吸だけにする。観測された出来事の新規検出時だけ約1秒、柔らかく一度光らせる |
| disconnected（接続断） | `#756a8e` 暗い灰紫 | 光量を落とし、呼吸も明るさの移動も止める。外形は残す（LARM 星系の表示方針は §3） |
| unknown（未確認） | `#a99fd2` 淡い紫 | 光量をやや落とし、呼吸も明るさの移動も止める |
| stale（古い情報） | 元の色 | 通常の光量の45%にし、呼吸・移動・一度だけの光を止める |

| activity | 見え方 |
| --- | --- |
| idle | 外形の点はすべて見える。原則としてごく弱い呼吸だけ。容量や読み込み済みの席など、観測値の静的な明暗は残す |
| starting | 接続中・読み込み中という入力があるときだけ、形ごとの「満ちていく」光。完了を推測して点灯させない |
| working | 形ごとの光の波（packet）が流れる。速さは idle 用の基準周期に対して最大1.3倍、明るさの上乗せは最大10% |

- 各節の秒数は**制作時に見比べるための案**で、実装値や監視のしきい値ではない。特記がなければ idle の呼吸は約12秒周期。idle で波を流さない形でも、working の速さの上限を決める基準周期は持つ。
- 各モデルに示す「波の基準周期」は `motion.cyclesPerSecond = 1 / 基準秒数` に対応する。working で周期を短縮しても基準の `1 / 1.3` 倍までとし、使用率で加速しない。基準の速さのままでもよい。
- utilization は明るさの上乗せ（最大10%）にだけ使い、回転速度・点の大きさ・粒子数・外形に使わない。波・呼吸・utilization の上乗せは合算して10%以内とする。SSD の容量や LARM の席の点灯など、観測値を示す静的な明暗と活動の上乗せは区別する。
- 出来事による fault は10分間赤を残し、ラベルに理由と経過時間を出す（例:「OOM で強制終了（3分前）」）。同じ出来事を再取得しても光らせ直さない。10分が過ぎ、新しい問題がなければ通常の判定に戻る。出来事の識別・保持は取得側の設計事項（§8）。
- **状態は activity より優先する。** fault 中に working の波を出さない。pressure の扱いは各節に従う。stale なら元の health 色を残して停止し、disconnected・unknown も停止する。モデルは health を自分で判定しない。
- 端末の「動きを減らす」設定では、呼吸・明るさの移動・一度だけの光・値の変化時の補間を止める。静止座標と点ごとの一定の明るさ、最新の色・ラベルで示す。値の更新自体は可能。LARM の表示切替・カメラも即時にする。
- 取得していない値は未取得として扱い、0にしない。入力がなければ unknown。各節の動きはデータが取得できた場合の制作仕様であり、新しい観測 API の存在を意味しない。

## 3. 配置と採用一覧

```
            Eumenes 星系                         LARM 星系（届くときだけ）
    外環: サービス 6 体（r≈8.4）              中心: LARM 本体
    内環: ホスト 4 体（r≈3.7）                周回: LARM CPU / Unified Memory / GPU
    中心: 何も置かない（既存どおり）
```

- **Eumenes 星系（10体）**: backend が動く Mac と Eumenes の機能を表す。内環は `cpu`・`memory`・`ssd`・`backend`、外環は `llm`・`asr`・`tts`・`embedding`・`attitude`・`external`。
- **LARM 星系（4体）**: LARM が動くデスクトップ PC（Ryzen AI MAX+ 395、Linux）を表す。Eumenes 星系の横に置き、中心の `larm-core` の周囲に `larm-cpu`・`larm-memory`・`larm-gpu` を配置する。
- 合計14体。環内は各6体・4体を基準に間隔を取り直し、旧配置の空席を残さない。半径は配置案で、実際の見切れ・重なりを制作時に確認する。
- **LARM に届かないときの表示案**: LARM 星系を約2秒でフェードアウトし、カメラを Eumenes 星系に合わせ直す。復帰したらフェードインする。Eumenes 外環のサービスは消さず、各経路の実際の接続状態に従って残す。LARM を使う経路は接続断、cloud 経路はそれ自身の状態を示す。
- LARM の個別項目だけが unknown／stale の場合は、その形を止めて残す。LARM 星系全体が届かない場合との区別は取得側で行う（§8 M5）。

### 3.1 将来の拡張（ContextStill）

ContextStill をもう1つの星系として加える見込みがある（5〜8体）。今回の14体と合わせて19〜22体を想定し、配置には最大25体程度までの余地を持たせる。中身は今回決めない。

- 星系ごとにまとめ、星系数が変わったら並びからカメラの全体表示を合わせる。
- 届かない星系を消す扱いは、ContextStill にも使えるようにする。
- 曲線・直線・面の輪郭を使い分け、似た外形を増やしすぎない。将来の形にも、単色・固定座標・穏やかな光という共通条件を引き継ぐ。
- 各星系の中心には本体を表す形を置く。Eumenes 星系だけは既存どおり空にする。

## 4. モデル作成の共通条件（ChatGPT への依頼条件）

- 納品は採用14体の `<id>.bin` と `<id>.json`、計28ファイル。
  - `.bin` は Float32 little-endian、1点8値（32 bytes）。順序は `x, y, z, phase, group, seed, size, weight`。
  - 右手系・Z上。原点を中心に置き、外接半径で正規化できる大きさにする。
- 新規6体は各2,000〜2,600点を目安とする。既存8体は次の点数を維持する案を基準とし、作り直す場合の点数変更は制作時に明記する。
  - `cpu` 4,096、`memory` 1,917、`ssd` 1,908、`llm` 2,592、`asr` 2,463、`tts` 2,460、`embedding` 2,064、`attitude` 2,160。計19,660点。
  - 新規6体は計12,000〜15,600点。14体の合計は**31,660〜35,260点**、バイナリは1,013,120〜1,128,320 bytes（JSONを除く）。これは制作予算で、描画性能の検証結果ではない。
- `.json` の項目は既存形式を基本にする。
  - `id`、`label`、`kind`、`category`、`pointCount`、`stride`、`binary`、`bounds`、`normalizationRadius`、`attributes`、`coordinateSystem`。
  - `shape`: `name`・`description`・`topology`・`components`・`silhouette`・`label`。
  - `motion`: `type`・`phaseMeaning`・`groupMeaning`・`cyclesPerSecond`・`pulseWidth`・`baseBrightness`・`peakBrightness`・`maxDisplacement`・`rules`・`suggestion`。旧形式で motion が文字列のものも、制作時にはこの構造に整理する。
  - `maxDisplacement` は全モデルで `0`。既存メタデータに微小変位の許容値があっても、今回の制作では変位させない。明るさは同じ尺度で `peakBrightness <= baseBrightness * 1.10` とする。
- `group` は部位ごとの明るさの制御単位。数値と意味を `groupMeaning` に列挙する。以下の新規 group は制作案、既存形状は既存の部位区分を引き継ぐ。group を監視対象や色の区分と混同しない。
- `phase` は固定座標上の光の進行方向を0→1で表す。閉じた経路は剰余でつなぎ、分岐は group ごとの同じ方向に沿わせる。各節に記す位相・部位の関係をメタデータに含める。
- 全モデル共通の rules:
  - 光だけを動かし、粒子位置を時間で積分しない。外形・点数・size・seed は状態で変えない。
  - idle・活動0・接続断でも構造を示す点を残す。光の波がない部分も消さない。
  - health は形全体で1色。group ごとの色分けや状態を示す別色を足さない。
  - 時間は有界にして剰余で回す。§2 の停止条件と活動の上限を守る。
  - reduced motion は静止座標と点ごとの一定の明るさにする。
- 14体を並べても外形を識別できるようにする。透けた奥行きは粒子の密度と固定の weight で作り、面を塗るポリゴン・不透明な殻は納品形状に使わない。

次は `backend.json` の `motion` 部分だけの例。完成した JSON や既存 renderer がこの定義を解釈できるという保証ではない。完成時は §4 の基本項目・実際の bounds・点数などを併記する。

## 5. Eumenes 星系：内環（ホスト4体）

### 5.1 CPU（Mac）`cpu`

- **監視の意味・データ**: Mac の処理が追いついているか。macOS の負荷平均（1・5・15分）、論理コア数。使用率は utilization にだけ使う。
- **判定案（§8 M1）**: pressure は5分平均がコア数を超え、3回続けて上昇していること（1分 > 5分 > 15分）。fault は15分平均がコア数超。1分平均が5分平均を下回ったら回復とみなす。継続条件・回復と fault の優先関係は実装前に確定する。
- **形**: 既存の渦巻粒子銀河（4,096点）。group は主腕・副腕・円盤・中心・ハロー・明るい点。
- **group / phase**: 腕は中心→外側の弧長を0→1、円盤は周方向を0→1。中心・円盤・ハローはそれぞれ1・5・15分負荷の静的な明るさに対応させる。
- **アニメーション案**: idle は主腕・副腕の弱い呼吸と、観測負荷に応じた3領域の明暗。波の基準周期は16秒。将来 working 入力がある場合だけ円盤の周方向へ薄い光を巡らせる。現行のホスト activity は idle のため、使用率から working を作らない。負荷の明暗は「負荷 ÷ コア数」に上限を設け、変化を1〜2秒かけて移す。pressure は橙にして光を加速させない。fault は §2。starting の専用表現は設けない。

### 5.2 Memory（Mac）`memory`

- **監視の意味・データ**: Mac のメモリ不足による詰まり。macOS のメモリ圧迫レベル、圧縮・スワップの増え方。使用率は utilization にだけ使う。
- **判定案（§8 M2）**: warn または継続するスワップ書き出しで pressure、critical で fault。
- **形**: 既存の三軸編み格子（1,917点）。group は X方向・Y方向・Z方向・交点。
- **group / phase**: 各軸の格子線に沿って端→反対端を0→1とする。交点は到達時に弱く灯る固定の節点。
- **アニメーション案**: idle は格子全体の弱い呼吸。波の基準周期は12秒。working 入力がある場合だけ3方向を少しずらして光帯が通る。現行のホスト activity は idle で、確保・解放の個別イベントを観測したようには見せない。pressure は流れを止め、交点の光をわずかに残す。fault は §2。starting の専用表現は設けない。

### 5.3 SSD（Mac）`ssd`

- **監視の意味・データ**: データディレクトリのあるボリュームの空き。`statfs` の空き容量と総量。
- **判定（現行どおり）**: 空き10%未満で pressure、3%未満で fault。
- **形**: 既存の三層の四角い光棚（1,908点）。group は下層・中層・上層。
- **group / phase**: 容量の明暗を下→上へ割り当てる。phase は各層の高さと順序を0→1で表し、書き込み経路には使わない。
- **アニメーション案**: idle は弱い呼吸。容量の変化時だけ下層からの明暗境界を1〜2秒かけて更新する。working／starting 用の走る光は設けない。I/O のデータがないため読み書きを演出しない。pressure は橙で同じ容量表現を保つ。fault は §2。

### 5.4 Eumenes Backend `backend`

- **監視の意味・データ**: snapshot の取得可否（Web 側）、queue の待ち件数・実行中件数・最古待ち時間、プロセスの CPU 使用率（utilization のみ）。
- **判定**: 現行は snapshot が取れれば healthy、取れなければ disconnected。最古待ち時間が3回続けて伸びる場合の pressure は追加案（§8 M3）。独自の fault 条件は追加しない。
- **形**: **横向きの二重漏斗**。左右の広い開口を中央の細い腰でつなぐ。透けた粒子構造とし、手前・奥の輪郭で奥行きが分かるようにする。
- **group / phase（制作案）**: `0` 入口側漏斗、`1` 腰、`2` 出口側漏斗。ローカル X 軸の左→右を流れとし、入口 phase=0、腰=0.5、出口=1。位相は3部位で連続させる。
- **アニメーション案**: idle は全体の弱い呼吸。波の基準周期は12秒。working では広い入口→細い腰→広い出口の順に光が通る。実際に starting が与えられた場合だけ、同じ方向に一度ゆっくり満ちる。pressure では通過波を弱め、入口側に静かな光が残る。点を積み増したり腰を細くしたりしない。待ち件数・実行中件数・最古待ち時間はラベルに出す。disconnected・unknown・stale は全3部位を暗く残し、§2 に従って停止。fault 表示入力があれば §2 に従うが、Backend の fault 判定を新設する意味ではない。

## 6. Eumenes 星系：外環（サービス6体）

既存5体（LLM・ASR・TTS・Embedding・態度判定）は外形を維持する。現行の healthy / fault / disconnected / unknown 判定を変えず、pressure は使わない。idle は全形の弱い呼吸。fault では working の波を止めて §2 の弱さに戻す。disconnected・unknown・stale・reduced motion は呼吸も波も停止し、全形を残す。

### 6.1 既存5体のアニメーション

下記の基準周期はすべて制作案。starting の「灯る」は明るさの上乗せで、他の構造点を非表示にはしない。

| ID・形（点数） | group / phase | starting | working・波の基準周期 |
| --- | --- | --- | --- |
| `llm` LLM：三つ編みの結び目・トレフォイル（2,592） | group 0〜2 は3本の編み糸。共通の閉曲線の弧長が phase 0→1 | 結び目全体がゆっくり明るくなる | 約12秒で一周する短い光。半周遅れの淡い二つ目を添える。結び目をほどかない |
| `asr` ASR：音を集める椀（2,463） | group 0 緯線、1 経線、2 縁、3〜8 受け道6本。受け道は高い外端0→底1、椀は縁0.36→底1 | 縁の光が少しずつ満ちる | 約10秒で受け道を下り、底へ集まる。底の光を短く残して戻す。縁も常時見える |
| `tts` TTS：広がる波輪6本（2,460） | group 0〜5 は小→大の輪。第 k 輪（k=0〜5）の phase は k/6 | 最小の輪だけ弱く明滅 | 約10秒で小さい輪→大きい輪へ順次点灯。輪の径・位置は固定 |
| `embedding` Embedding：入れ子の八面体格子（2,064） | group 0 外側、1 中間、2 内側、3 座標の6半軸。各辺の中点0→両端1、半軸は原点0→外端1 | 内側の八面体の光が満ちる | 約12秒で辺の中点から頂点へ対称に進み、頂点に弱い光が残る。軸も原点から先端へ進む |
| `attitude` 態度判定：三枚の花弁（2,160） | group 0 上、1 右下、2 左下。各花弁の根元0→先端1 | 根元に弱い光が満ちる | 約12秒で根元→先端へ進む。3枚を周期の0・0.1・0.2だけずらす。花弁は開閉させない |

### 6.2 外部連携 `external`

- **監視の意味・対象**: Web 調査・天気・株価は `toolchain-history` の outcome／outcomeCode、Google アカウントは `google-accounts` の status。クラウド LLM 経路は LLM 側に含める。
- **判定案（§8 M4）**:
  - disconnected: ネットワーク断・名前解決失敗・時間切れなどで外に届かない、または Google の再認証が必要。
  - fault: 外は答えたが認証拒否・利用上限・応答形式違いなどのエラー。
  - healthy: 直近10分に成功。unknown: 直近10分に未使用。ただし Google は連携状態で常時判定。
  - 「見つからなかった」「聞き返した」「取り消した」は問題にせず、pressure は使わない。複数対象の状態の集約・理由コードの対応は実装前に確定する。
- **形**: **コスモス状の花**。中央の花芯を囲み、8枚の幅広い花弁が放射状に広がる。茎・葉は付けない。三枚花弁の態度判定とは、枚数・花芯・幅広い輪郭で区別する。
- **group / phase（制作案）**: `0` 花芯、`1〜8` 花弁。花芯は phase=0、各花弁は根元0→先端1。8枚は造形の区分で、8サービスや8種類の状態を意味しない。監視対象と花弁の個別対応は今回設けない。
- **アニメーション案**: idle は花芯と全花弁の弱い呼吸。波の基準周期は12秒。観測された実行中入力があるときだけ、花芯→花弁先端へ薄い光が伝播する。starting が実際に与えられれば根元からゆっくり満ちる。花弁の長さ・幅・開きは固定。fault は §2。Google 再認証などの原因はラベルで出し、対応が未定の花弁を恣意的に暗くしない。disconnected・unknown・stale は花芯と全花弁を残して停止する。

## 7. LARM 星系（4体・CPU/GPU共有メモリ）

下記の計測値・出来事は、LARM 側の API を別途設計・新設して取得する案（§8 M8）。1分ごとに取得し、合間の出来事を「前回以降の出来事」として受け取る想定。現時点で取得できる、または今回実装するという意味ではない。不達時の星系非表示は §3・§8 M5 に従う。

### 7.1 LARM 本体 `larm-core`

- **監視の意味・データ**: プロセスの稼働、読み込み済み／読み込み中のモデル、入れ替え回数、要求を断った回数、モデル置き場のディスク空き、再起動の出来事。
- **判定案**: 読み込み中は activity=starting。過剰なモデル入れ替え・混雑による要求拒否・ディスク空き10%未満で pressure。再起動・推論エンジン停止・モデル読み込み失敗・ディスク空き3%未満で fault。
- **形**: 密な小球の核と、その周囲に等間隔で並ぶ6つの席、席をつなぐ細い輪。
- **group / phase（制作案）**: `0` 核、`1〜6` 席、`7` 接続輪。各席は下0→上1、輪は周方向0→1。核は呼吸だけに使う。
- **アニメーション案**: idle は核の弱い呼吸と、読み込み済み数に応じた席の静的な明暗。空席も輪郭を残す。starting は実際に読み込み中の席だけ下→上へ満ちる。波の基準周期は16秒。working 入力があるときは接続輪に薄い光が一周する。席の切替は1〜2秒かけ、pressure でも点滅させず橙で示す。fault は §2。disconnected・unknown・stale は静止する。モデル数が6を超える場合の席への集約は未確定で、6モデル上限とは扱わない。

### 7.2 LARM CPU `larm-cpu`

- **監視の意味・データ**: `/proc/loadavg` の1・5・15分平均、論理コア数（32）、補助情報として CPU PSI（`/proc/pressure/cpu`）。CPU 使用率は utilization のみ。
- **判定案**: Mac CPU（§5.1）と同じ方向で、推論中の普段の負荷平均を live 実測してから基準を確定する。
- **形**: **クエーサー風の渦巻円盤・明るい核・上下二方向のジェット**。Mac CPU と渦の語彙を共通にし、上下の細長い光の構造で区別する。ジェットも最初から配置した固定点群。
- **group / phase（制作案）**: `0` 核、`1` 円盤内側、`2` 円盤中間、`3` 円盤外側、`4` 上ジェット、`5` 下ジェット。円盤は周方向0→1、両ジェットは核側0→先端1。1・5・15分負荷は円盤の内・中・外の静的な明暗に対応させる。
- **アニメーション案**: idle は核と円盤の弱い呼吸、負荷に応じた明暗。波の基準周期は16秒。working 入力があるときだけ、円盤を巡る光と核→両ジェット先端の光を同じ穏やかな周期で重ねる。ジェットの伸縮・噴出変形はしない。負荷は「負荷平均 ÷ 32」を上限付きの明暗に使う。pressure では加速せず橙、fault は §2。starting の専用表現は設けない。使用率や負荷から activity を捏造しない。

### 7.3 Unified Memory `larm-memory`

- **監視の意味・データ**: `/proc/meminfo` の `MemAvailable`・スワップ、`/sys/class/drm/card*/device/mem_info_vram_*` と `mem_info_gtt_*`、memory PSI、`/proc/vmstat` の `oom_kill`。
- **余裕の量の案**: `MemAvailable` ＋ GPU 専用領域の空き。GTT 使用分は `MemAvailable` から引かれているため二重に数えない。次のモデルが入るかは、モデルの大きさを知る LARM 側で判定する。
- **判定案**: `memory some avg60` の上昇、継続するスワップ書き出し、GTT上限90%超で pressure。OOM 強制終了・メモリ不足による読み込み失敗で fault。
- **形**: **D12ダイスを参照した正十二面体**。12枚の平らな五角面、30本の直線の稜線、20頂点を持つ。五角面の粒子は同一平面上に置き、稜線と奥の面が透けて見える密度にする。数字は付けない。面を球面へ膨らませない。
- **group / phase（制作案）**: `0〜29` 稜線、`30〜41` 五角面。共有稜線・頂点は重ねて密度を増やさず、所属を一意にする。固定の起点頂点から稜線ネットワークに沿う距離を0→1に正規化し、共有頂点で位相がつながるようにする。面の phase は境界の位相から内側へ補間する。
- **アニメーション案**: idle は弱い呼吸と、固定の weight による透明な奥行き。波の基準周期は14秒。working 入力があるときだけ稜線を伝わる光が隣の頂点へ広がり、面はごく弱く追随する。pressure では流れを止め、稜線と頂点の静かな明暗を残す。fault は §2。メモリの余裕・GTT・スワップは実測値のラベルで示し、12面を12領域の容量に見立てない。starting の専用表現は設けない。面数・角・稜線を変形させない。

### 7.4 GPU `larm-gpu`

- **監視の意味・データ**: 要求の待ち件数・最古待ち時間、生成速度（tokens/s）、初回応答時間、`gpu_busy_percent`（utilization のみ）、温度・クロック、GPUリセット・ring timeout・page fault のログ。
- **判定案**: 最古待ち時間が3回連続増加、生成速度が普段の半分以下、初回応答時間が普段の2倍以上、温度によるクロック低下で pressure。GPUリセット・ring timeout・page fault・ROCm/HIP実行エラーで fault。「普段」は live 実測後に決める。
- **形**: **半回転のひねりを持つ、一続きの幅広いメビウス帯**。幅方向にも粒子を置き、ひねりを立体として読めるようにする。固体の面ではなく透けた点群。
- **group / phase（制作案）**: `0` 帯の内寄りの粒子、`1` 境界線の粒子。ここで内寄りは帯の幅方向の中央付近を指し、表裏の区分ではない。phase は帯の中心線に沿う弧長0→1。継ぎ目では幅方向の向きが反転する形を保ち、同じ位置を二重に作らない。光帯は幅全体にかけ、周回の位相が継ぎ目で途切れないようにする。
- **アニメーション案**: idle は帯全体の弱い呼吸。波の基準周期は14秒。working では幅を持つ薄い光帯が一周し、固定されたひねりの立体感を見せる。pressure では光の進みを抑え、熱によるクロック低下なら流れを止める。待ち件数・時間・速度低下の理由はラベルで示す。fault は §2。disconnected・unknown・stale は帯を残して停止。starting が与えられた場合だけ同じ経路をゆっくり満たす。帯の幅・ひねり・粒子数を待ち件数で変えない。
