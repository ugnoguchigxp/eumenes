# 専門担当の終了失敗と再試行

2026年11月16日 · 実装済み、合成データで検証

専門担当の終了処理が、同じ条件では成功しないと確定した場合は、セッションを `closing` に置いたまま自動再試行を停止する。一時的な失敗は従来の毎分の再試行で回復させる。稼働環境への適用は別作業とする。

## 変更前の挙動

終了処理は、所有ドメインに作業の状態を問い合わせ、状態を取得できた場合に終了を依頼する。共同作業の状態取得には元発言の検証が含まれ、専門担当の期限切れと `closing` はどちらも拒否される。失敗時は作業の更新を巻き戻してセッションを `closing` にする。毎分の処理がこのセッションを再び選ぶため、経過時間で解消しない条件を繰り返し評価する。[終了処理](../api/domains/dialogue/service/specialist-core.ts) · [発言参照の検証](../api/domains/dialogue/service/specialist-source.ts) · [既知の再試行問題](tts-ack-latency-2026-11-15.md#p2-終了できない専門担当が同じ失敗を毎分再試行する)

## 再試行を止める条件

共同作業の状態取得で、保存済みの元発言への参照が対象セッションに属し、そのセッションの期限切れで実行権限を取得できないと確定したときに停止する。元発言を検証する dialogue の既存判定から型付きの理由を返し、共同作業の所有ドメインは状態取得時の失敗にその理由を引き継ぐ。複数の条件に該当する場合は、対象セッションへの紐付けを検証してから期限切れを判定する。

期限内の `closing` は、一時的な失敗の後にも発生する。その再試行には、所有ドメインが単一 writer 内で終了可否を調べる経路を使う。この経路は対象の作業とセッションの紐付け、元発言の有効性、子作業の所有権を確認し、作業中か、保存が必要かなど、終了に必要な状態だけを扱う。通常の実行権限と切り離し、発言や作業内容の取得、編集、子作業の起動、結果採用には使えない。終了可否の判断に必要な情報を取得できない場合は現在の検査に従って失敗を返し、再試行に回す。

| 観測した結果 | 処理 |
| --- | --- |
| 対象セッションの期限切れによって元発言の実行権限を取得できないと確定 | 終了試行を巻き戻し、再試行停止を保存する |
| `work_busy` など、条件が解消し得る失敗 | `closing` として保存し、次の定期処理で再試行する。期限内なら `closing` でも終了可否を調べられる |
| 理由の詳細がない `collaboration_source_invalid` や分類できない失敗 | 従来どおり再試行する。発言の欠落、忘却、所有者の不一致などは、この障害との同一性を推定しない |
| 終了処理が成功 | 所有ドメインの終了とセッションの `ended` を同じ書き込み処理で確定する |

判定には保存済みの紐付けと、失敗した検証段階を使う。汎用のエラーコード、試行回数、セッションIDだけでは停止を決めない。試行回数は観測用に保持する。一時障害を再試行している間に期限が来た場合は、その時点の条件を改めて検証する。通常のセッション終了、取消、忘却は、それぞれの既存の権限と所有ドメインの処理に従う。

## 保存と適用箇所

- セッションの四つの状態に加え、`closing` に限り内部の停止理由と停止時刻を持てるようにする。既存行の初期値は未設定とする。`closingReason` は元の終了要求を、停止理由は自動再試行を外した根拠を表す。
- 停止理由は、終了試行をセーブポイントまで巻き戻した後、単一 writer で保存する。保存時に `closing` と停止理由が一緒に確定する。作業の下書き、版、子作業への参照、操作記録は書き換えない。停止の警告は確定した状態遷移につき一度だけ、セッションID・固定の理由・試行回数を記録する。
- 毎分の処理と起動時の復旧処理は、停止理由が設定された行を除外する。新たな専門担当を開くときの期限切れ処理も、停止済みの行を再試行せず、既存の `specialist_closing` を返す。利用者が明示的に「閉じる」「破棄」を操作した場合は既存の権限・版・作業の検査に従う。自動で停止を解除する経路は設けない。
- 同じ会話で新たな専門担当を開けない影響は残る。再試行の停止で会話の利用制限を解除する場合は、保持中の作業の参照先と、新しい専門担当との競合時の扱いを別途決める。

## 検証と完了条件

1. **部分試験**。元発言の紐付けが有効で期限切れになった場合、期限内で `closing` の場合、別セッションの参照や理由不明の場合を区別する。終了試行の失敗後に作業に関する更新が巻き戻ること、停止理由の保存まで失敗した場合は停止の警告が出ないことを確認する。
2. **結合試験**。実 writer と共同作業のアダプターを使い、2件に相当する合成データで既存行の移行を確認する。停止後は複数回の定期処理、起動時復旧の呼び出し、同じ会話からの引き渡しを通しても、作業・試行回数・警告件数が増減しないことを確認する。一時的な失敗で期限内に `closing` へ移った共同作業は次回に再試行され、原因が解消すると終了する。取り消された処理の遅い結果が採用されないこと、保持中の作業にも既存の忘却が適用されることを確かめる。
3. **通し確認**。合成データで期限切れから停止までと、一時障害から終了までを確認する。既存の領域検証は `bun run verify -- --domain dialogue --domain collaboration` を使う。稼働環境への適用が許可された後は、対象2件の停止記録が各1件で、少なくとも定期処理2周期をまたいで試行回数が増えず、作業データも保持されていることを読み取り専用で確認する。

「受付拒否」は調べものの受付経路に由来し、この2件との因果関係は確認できていない。今回の完了条件は、終了処理の再試行と作業の保持に置く。

[結合試験](../api/application/collaboration/collaboration-close.test.ts)では、旧形式に相当する2件の作業保持、複数の定期処理と起動時復旧を通した停止、期限内の一時失敗からの終了を確認した。停止の警告は `dialogue.specialist_close_retry_stopped` に記録する。稼働中の2件は適用後に照合する。
