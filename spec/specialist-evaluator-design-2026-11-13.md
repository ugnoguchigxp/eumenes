# 用途別サブエージェントと任意のEvaluator

2026-11-13 設計案。PursuitとCollaborationの廃案、およびEvaluatorの任意利用は利用者の方針。以下の後継担当の構成、移行順、初回の評価範囲は合意前の提案。

## 後継担当

通常の会話担当が依頼の目的を捉え、既存の能力検索と委譲を使って担当を選ぶ。一件の仕事を受けて結果を返す単発型と、利用者と同じ下書きを編集するセッション型を使い分ける。各担当の目的、手順、許可する操作を版付きのprofile・Skill・bindingとして登録し、既存の実行機構と所有領域に接続する。依頼の意味と次の作業はモデルが判断し、ホストが引数・権限・期限・結果の有効性を検査する。 [既存の担当と実行方式](subagent-task-and-session-agents-design-2026-10-18.md#5-二つの型) · [登録手順](../docs/toolchain-extension.md)

| 仕事 | 後継の案 |
| --- | --- |
| Webアプリの制作と修正 | 既存の「Webアプリ開発」担当 `app.develop` を初回の接続先とする。OpenUIの画面やワークフローを下書きの版として持ち、利用者との対話で直す。評価を呼べる操作を追加する。 |
| 詳しいWeb調査 | Pursuitに依存する `web.research` を、出典付きの調査結果や依頼されたMarkdown文書を返す単発型の専門担当に移す案。通常の調べものには既存の `web.note` がある。詳しい調査の受入には根拠、未調査範囲、文書へのリンク、取消後の結果不採用を含める。 |
| ブラウザ操作、Markdown、Pipeline | 旧Collaborationの各入口を棚卸しし、所有領域の既存操作で継承できる範囲を確認する。ブラウザは既存の `browser.operate` と撮影機能、アプリ内のワークフロー制作は `app.develop` を候補とする。単独のPipeline共同編集、Markdown共同編集、進行中の仕事の引継ぎは、公開入口と既存データの扱いを確定してから切り替える。 |

廃案に伴うコード撤去の前に、公開ルート、保存済みのアプリ・文書・履歴、進行中の仕事の所有元を確認する。後継経路で同等の操作と結果返却を検証し、旧入口を閉じる順を決める。 [Web調査の現行経路](../docs/web-research.md#詳しい調査のmarkdown文書) · [Webアプリ開発の登録](../api/domains/capabilities/bundles/app-development.bundle.json) · [既存のブラウザ操作](../api/domains/capabilities/bundles/browser.routing.bundle.json)

## 評価と制作の責務

| 担当 | 責務 |
| --- | --- |
| Webアプリ開発 | 利用者の目的と確認したい操作を捉え、対象の下書きと利用可能な根拠を指定する。レビュー依頼を受けたとき、または依頼の範囲内で検証が役立つと判断したときにEvaluatorを呼べる。指摘を利用者に説明し、求められた修正を通常の編集操作で行う。 |
| Eumenes | 許可された作業から下書きと根拠の版を確定する。登録済みの評価基準を解決し、保存済みの推論経路で実行する。呼び出した担当に結果を返す前に、対象版、セッション、取消、根拠へのアクセス権を照合する。 |
| Evaluator | 指定された版の評価基準を適用し、観察できる根拠に基づいて所見と未確認事項を返す。人間工学の評価では、重大度、確信度、対象箇所、利用者への影響、最小の修正案、確認方法を含める。ブラウザ操作と成果物の編集・保存はホスト側の別操作に委ねる。 |

評価は担当がツールを選んだ回に実行する。評価結果は同じ担当に戻し、修正・保存はそれぞれ既存の操作で行う。

## 人間工学の評価基準と根拠

添付の `human-factors-reviewer` を人間工学の評価基準の原案として使う。実行時は、ホストが承認して登録した本文と参照資料の版をEvaluatorへ渡す。評価対象のページや添付資料の本文は観察資料として扱い、対象の中に書かれた指示で基準や操作権限が変わらないようにする。今回確認できたのは `SKILL.md` 本文で、本文が参照するウォークスルー、根拠の扱い、報告形式などの別ファイルは未確認。正式登録時に参照先を揃えるか、使用する手順と報告形式を本文だけで完結させる。

1. 画面定義、対象タスク、確定した条件を初回の根拠にする。Evaluatorは、画面定義や仕様で確認できる導線と、実機で確認が必要な操作を区別して返す。
2. 画面評価では、版と撮影状態を確認できるプレビュー画像を根拠に加える。初回は提供済みの画像を使い、自動撮影の接続は対象プレビューと画像の対応を保証できることを確認してから行う。既存のブラウザ撮影・画像推論は再利用候補。フォーカス遷移、エラーからの復帰、保存の成否などは、対応する操作と観測が揃った範囲で評価する。
3. 所見は画面の状態・領域、画面定義の位置、または操作記録を指す。資料が足りない項目は未確認と理由を返す。総合点は明示された依頼に応じて扱う。

## 接続で追加が必要な契約

現行の固定配布版は、対象がコード差分またはワークフロー、根拠が行範囲またはJSON、評価基準が列挙済みの三種。モデルへの入力もテキストで、画面画像や登録した人間工学の基準を渡す契約がない。Eumenes側の既存接続はCollaboration専用のワークフローQuick評価。 [固定版の出所](../vendor/evaluator/manifest.json) · [現行の接続](../api/application/evaluator/workflow-review.ts)

- **Evaluator** では、登録済み評価基準を版で指定できる入口、画面定義と画面画像を根拠にする入力・引用位置、人間工学レビューに必要な構造化結果を設計する。既存の版・根拠の照合、制限、出力検査を再利用する。画像は画像対応の推論に渡し、利用できない場合は画面の観測を未確認にする。公開済みのコード・ワークフロー評価の入力と結果は互換性を保つ。
- **Eumenes** では、Collaborationから独立したEvaluator接続を用意し、Webアプリ開発の版付きbundleに評価の読み取り操作を追加する。初回は既存の専門担当の読み取り準備、取消シグナル、結果採用時の再照合を利用する。推論中は保存処理を占有せず、利用者に編集・保存を促す判断は制作担当に残す。 [専門担当の読み取り操作](../api/domains/dialogue/service/specialist-invoke.ts#L179) · [下書きの版と画面定義](../api/application/app-development/app-development-source.ts#L94) · [画像の推論入力](../api/application/browser/browser-task-image.ts#L38)

制作担当が操作に渡すのは、期待する下書きの版、評価基準の識別子、対象タスク、利用可能な根拠への参照。Eumenesはセッションの作業から下書きと登録済み基準の正本を解決し、Evaluatorへ版と内容を渡す。結果には対象版、基準の版、根拠の参照と所見を含める。

## 実装後の受入

1. **部分**。評価基準・下書き・根拠の版を照合する。別版の画像、未知の根拠、画像の欠落を試し、該当する所見の拒否または未確認が返ることを確かめる。画像や画面定義中の指示で評価基準が変わらないこと、既存のコード・ワークフロー評価の固定試験が通ることを確認する。
2. **結合**。Webアプリ開発の下書きから、固定モデルで評価を呼び、同じ制作担当に根拠付きの結果が届くことを確認する。通常の制作・保存では評価の呼び出しが発生せず、評価だけでは下書きと保存済みアプリが変わらないことを確かめる。評価中の編集・取消・忘却では古い結果を採用しない。bundle検査、`bun run verify -- --domain <name>`、対象のアプリケーション結合試験を実行する。
3. **通し**。Web上で下書きと画像の版を揃え、主要操作について、既知の問題がある版と修正版を実モデルで評価する。対象箇所・利用者影響・確認方法が根拠に結び付くこと、画像だけでは確認できない操作が未確認になること、同じ担当に結果が届いて利用者の依頼で修正できることを確認する。ブラウザE2Eは対象の試験を指定して実行する。
