# 一手ずつの実行と原文照合による複数操作 設計案

作成日: 2026年10月21日

状態: 合意済み（2026-10-21、§9の決定を含む）。S1〜S3を実装・固定試験済み、通し受入を実施中（§11）。S4（経験）は未着手。§11に独立レビューで残した課題（最初の照合への注入など）がある。方式の方向性（最初の一手だけを選ぶ、実行後に原文と照合して足りない要素を探し直す、時間のかかる担当は「結果が出たら報告」）と§9の5項目を利用者と合意した。

## 1 背景と評価

[日常の複数操作担当](everyday-task-agent-implementation-plan-2026-10-21.md)は、会話担当（R1）が `execute_task` へ委譲し、親が最初に全体の操作計画を作り、項目ごとに能力を探索・選択して子を呼ぶ。[進行契約の検証記録](verification/everyday-task-agent/progress-contract-verification-2026-10-21.md)では、タイマー二操作は改修後に安定したが、画像→3D・検索→別操作・動画再生では、毎回別の種類の失敗が出た。

| 観測 | 起きた場所 |
| --- | --- |
| 依頼を最初の一操作に縮めて委譲（全件） | R1の要約 |
| 複数操作の依頼を単独担当へ直接委譲（画像→3D 2/3、動画 1/2）、単独の依頼を親へ委譲（過去3/3） | R1の振り分け |
| 計画の脱落・余分な項目・schema違反・前項目の能力の流用 | 親の計画と能力選択 |
| `execute_task` が毎回の最初の推論に無条件で提示される | `delegate-conversation.ts` の別枠提示 |
| 埋め込み検索は題材で当たり、「二つ以上のタスク」という構造では当たらない | 能力検索（組合せ5件中、上位4件に入ったのは3件） |

原因は、次の二つの予測を最初の時点でLLMにさせていることにある。いずれも、まだ何も実行しておらず、担当の一覧も見ていない時点の判断である。

- 依頼全体のタスク数
- 依頼全体の計画

判断を一つ誤ると後段が静かに消える。判断の回数が多いほど、通しの成功率は掛け算で下がる。推論の精度をむやみに測って指示文を調整する方法は、確率的にしか改善せず、モデルを替えると揺らぐため採らない。

## 2 方式

最初の時点で全体を予測しない。代わりに、小さく具体的な二つの判断を繰り返す。

1. **最初の一手**：R1は、依頼のうち最初に行うことだけを切り出し、その用途で担当を検索・選択する。既存の `find_toolchain` の検索文を「最初の一手の用途」に限定する。担当の選び方は今と同じ二段の分析を使う。
2. **原文との照合**：担当の結果が確定したら、利用者の原文と、これまでの実行結果を照合する。照合の結果は次のいずれかとする。
   - `done`：依頼は達成済み。会話の既存の回答経路で報告する。
   - `continue`：足りない要素がある。その要素の用途を検索文として書く。hostがその検索文で上位4件を検索し、担当を一つ選ばせて実行し、再び照合する。
   - `blocked`：続けられない。実行済み・不足・未確定を分けて報告する。

単独の依頼は一手と一回の照合で終わる。複数の依頼は照合が自然に続きを作る。そのため、「単独か複数か」をR1に予測させる振り分けは不要になる。`execute_task` という選択肢と、その別枠提示は廃止する。

時間のかかる担当（調査、生成など）は、受付時点で「結果が出たら報告します」と会話へ返す。結果が確定した時点で照合を始める。会話全体の非同期化は本書の範囲外とする。

## 3 判断と仕組みの分担

| 担当 | 内容 |
| --- | --- |
| LLM（R1） | 依頼の理解、最初の一手の用途、4候補からの担当選択、担当への依頼文。Memory・Worldの背景を踏まえる |
| LLM（照合） | 原文と結果の照合、足りない要素の用途、次の担当の選択と依頼文、最終報告の文面 |
| host | 原文の保持、台帳、子の実行と結果確定の待機、照合の起動、根拠refの検査、二重実行の防止、手数・時間の上限、取消・訂正・権限失効・忘却 |

意味の判断（タスクの区切り、達成の判定、能力の選択）にコードの語句分岐・辞書・正規表現・同名対象の重複除外を使わない。

## 4 仕組みで固める点

1. **照合の基準は原文**：照合の入力の正本は、利用者の原文と、訂正・回答の原文である。R1の要約は担当への依頼文としてだけ使い、達成の基準にしない。
2. **完了には根拠を必須にする**：`done` では、原文の条件ごとに、それを満たした結果refを対応付ける。hostは、各refがこの依頼の中で確定した子の結果であることを検査する。存在しない結果や、背景資料だけを根拠にした完了は拒否する。条件そのものの見落としはLLMの判断に残る（§6で補正する）。
3. **二重実行の防止**：既存の台帳と、子IDによる再送の再利用を使う。同じ手の再送は同じ子とreceiptを返し、入力の変更は競合とする。内容の類似による重複除外はしない。
4. **上限**：子の呼出し6回、照合を含む判断12回、親子合計48推論、絶対期限300秒（時間のかかる担当では、その担当の期限）。最終報告用に1推論を予約する。上限に達したら `blocked` と同じ形で返す。
5. **小さい判断の形**：
   - 照合の出力は `{status: done|continue|blocked, need?: string, evidence: [{condition, ref}], summary}` に限る。
   - 担当の選択は、提示した4候補のfunctionを一つ呼ぶだけとする。
   - 計画全体や状態欄の写し込みが起きる大きなschemaは置かない。
6. **照合の起動条件**：R1が担当へ委譲した依頼すべてで、結果の確定後に照合する。調査・instantも、複数操作の前段になりうるので対象とする。R1が `answer` で直接答えた場合は照合しない。

## 5 流れ

```text
利用者の発話
  → R1：最初の一手の用途で検索 → 4候補から担当を選び依頼文を書く
  → host：子として実行（時間がかかる場合は「結果が出たら報告します」を返す）
  → 結果確定
  → 照合（原文 + 結果 + 台帳）
       done     → 根拠ref検査 → 会話へ報告
       continue → needで検索 → 4候補から選択 → 子として実行 → 照合へ戻る
       blocked  → 実行済み・不足・未確定を報告
```

質問・訂正・取消・忘却・再起動時の停止は、既存の作業制御（`task_control`）と台帳の契約を使う。訂正では、実行中の子の停止を確認してから照合に戻す。過去の実行を、新しい条件の達成と自動的には同一視しない。

## 6 「足りている」の誤認を経験で補正する

照合が `done` と判定した後に、利用者が同じ作業の不足を指摘した場合、その組を経験として保存する。

- 何を保存するか：元の依頼、報告した結果、指摘された不足。
- どう判定するか：その指摘が当該作業への不足の指摘かどうかは、R1が作業refを指定して判断する。
- 次にどう使うか：次の照合で、依頼と近い過去の経験を埋め込み検索で最大数件取り出し、参考資料として提示する。経験は指示や許可ではなく参考データとして扱う。

保存先は、担当選択と手順の履歴を持つ既存の `toolchain-history` を第一候補とする。利用者の事実・好みを扱うMemoryとは分ける。忘却の際は派生データとして一緒に消す。経験の語句から判定するコードは書かない。

## 9 決定事項（2026-10-21 合意）

1. 照合は、サブエージェント（担当）が作業を終えて会話担当へ戻した時点で、会話担当が行う。終了できなければ、次の担当を探す検索文を選ぶ。対象は、数ラウンドにわたって会話相手を担当へ切り替えるsession型を除く、すべての委譲。
2. 照合と継続は会話担当の範疇とする。会話担当は依頼を出す側であり、単一タスクの経路を基本にする。呼ばれる担当は変更しない。今回のメタエージェント（`task.execute`・親実行）は入口を外して休止し、実装・試験・復元手順を残す（§10）。
3. 照合が `continue` のときは利用者に確認せずに続ける。依頼を完了していない以上、利用者へ聞かない。副作用のある操作の許可は、既存の所有domainの確認に従う。
4. 経験の保存先は `toolchain-history`。
5. `task.execute` は悪影響が出ているため廃止する。

以下は合意前の選択肢として残す。

### 合意前の選択肢

1. 照合の対象を、R1が担当へ委譲したすべての依頼にするか（推奨）。操作・制作に限るか。対象を広げるほど、単独の依頼に照合の推論が1回増える。
2. 照合とその後の継続を、どこで動かすか。推奨は、既存の親実行（agent-runtime）を照合専用に改めて使う案で、台帳と予算をそのまま使える。会話担当の推論として実装する案もある。
3. 照合で `continue` となったときの扱い。推奨は、次の担当を選ぶ前に利用者へ確認せず続ける案で、利用者は訂正・取消で止められる。副作用のある操作の許可は、既存の所有domainの確認に従う。
4. 経験の保存先を `toolchain-history` にするか（推奨）。Memoryに置くか。
5. 既存の `task.execute` の名前と入口の扱い。廃止して照合に置き換える（推奨）か、名前を残すか。

## 11 実装記録（2026-10-21〜22）

### 実装した仕組み

- **照合の起動**：担当の結果を文章にする生成ジョブで、回答の前に照合する（`completion-check.ts`）。対象外は、新しい判断、担当からの質問、通知、session型、システムのプロンプト、担当の質問への回答で再開したrun、chainの最後の手順。即時回答型（instant）は同じrunでhost回答するため、今は照合しない（§4-6との差。未実装）。
- **照合の形**：関数は `check_request({conditions:[{condition, step|null}], achieved, need})` の一つだけ。stepは実際に行った手順番号以下でなければ違反。
- **条件の固定**：最初の照合が条件の一覧を決める。最初の照合で `need` だけがあり未達の条件が無いときは、`need` を未達の条件として一覧に加える。以後の照合は同じ一覧の各条件に手順番号を付けるだけで、条件の追加・削除・言い換えは違反（`completion_conditions_changed`）。
- **次の手の決定**：hostが一覧の最初の未達条件を次の手の検索文にする。照合のLLMが、結果を読んだ後に自由文で新しい目的を作ることはできない（最初の照合を除く。下記）。
- **継続run**：`sourceKind: "continuation"`、画面では非表示、Memoryに学習しない、session型へ送らない。`dialogue_continuations` にroot run・手順・原文・済んだこと・次の手・条件を保存する（migration 0013・0014）。継続runは次の手で一度だけ検索し、R1・R2の通常の委譲を行う。操作の権限は元の手入力・音声入力のメッセージに結ぶ。
- **途中の回答**：継続する手順の回答はhostの固定文（`progress`）。次の手順の予告が続く。LLMの回答が音声の長さ制限を超えて失敗する経路を無くした。
- **打切り**：元の依頼の後に利用者の新しい入力があるか、元の入力が取り下げられたら、まだ委譲していない継続runを取消す。継続runを作るときも同じ条件で作らない。照合の推論が失敗しても、その手順の回答は失敗させない。継続runを受け付けられなかったときは、採用済みの回答を残してchainを終える。
- **上限**：最初の手順の後に最大3回。最後の手順は照合しない。

### 独立レビュー（2026-10-22）で残した課題

- **最初の照合への注入**：最初の照合は結果を読んだ後に条件の一覧を作る。調査結果などに書かれた作業が条件として混入すると、継続runは元の入力の権限で実行しうる。以後の照合では条件を固定したので、混入は最初の照合だけに限られる。対策案（最初の照合では結果を渡さず原文だけで条件を決める、副作用のある担当を継続runで呼ぶときは確認を求める等）は利用者の判断が必要。
- **音声**：継続runの回答は画面に出るが読み上げられない。途中の手順の結果は固定文に置き換わり、出典は最後の手順の分だけが残る。
- **instant**：照合の対象外（上記）。
- **失敗した結果**：失敗・拒否の結果でも照合し、`need` が再実行になると最大3回まで繰り返しうる。

## 12 手順間の受け渡し（2026-10-22 合意）

### 方針（利用者の提案）

継続の次の担当に、(a) 前の手順で会話エージェントが受け取ったものと同等の結果と、(b) 利用者の元の依頼を、hostが確実に渡す。LLMの要約（`achieved`）を経由させない。

最初の照合での注入は、Web検索に既存の対策があるので本設計では扱わない（利用者判断・2026-10-22）。

### 現状の欠陥（コードで確認）

- **元の依頼が渡っていない**：委譲はすべて `originalRequestInTransaction(run)`（`request-context.ts`）でrunの入力文を `originalRequest` にする。画像・音楽・Excalidraw（`generation-operation.ts`）、調査・操作の担当（`delegate-conversation.ts`）、command（`command-source.ts`）が該当する。継続runの入力はhostが書いた `CONTINUATION=` 文なので、次の担当は利用者の原文ではなくhostの文を「依頼の原文」として読んでいる。
- **前の結果が渡っていない**：結果のブロック（`operation.delegation`・`operation.image`・`research.result` など）は、その手順のrunの回答の準備でだけ組まれる。次のrunにあるのは、照合のLLMが書いた `achieved` の要約と、固定文に置き換えた途中の回答だけである。URL・画像ID・作成した対象のIDは、要約に正確に書かれた場合にしか届かない。

### 評価

- **妥当**：受け渡しをLLMの要約からhostによる複写へ変えるので、データの流れは推論に依存しなくなる。これは「仕組み的に間違えない」方向である。注入口は2か所に集約できる（元の依頼の取得箇所と、結果ブロックの保存）。担当ごとの判断や、特定の依頼に合わせた分岐は増えない。
- **既に渡っている場合がある**：例として、3Dの担当はsnapshotの `images` から `imageRef` を選べる。domainの状態を通じて届く経路があるので、受け渡しが必須になるのは結果が報告の中にしか無い場合である（例：調査で見つけた動画のURLをブラウザ担当へ渡す）。
- **効果の範囲**：前の結果を使う手順（検索→再生、生成→加工）を可能にする。一方、最初の手での委譲漏れや担当自身の失敗（受入の失敗の主因）は直らない。成功率が手順の数だけ掛け算で下がる性質も残る。
- **注意点**：
  1. 大きさ：調査結果は大きい。まずは切り詰めずに渡し、入力推論の時間を受入で測る（下記6）。
  2. 識別子の有無：会話エージェントが受け取る形に、次の操作に必要なID・URLが含まれているかは結果の種類ごとに確かめる（未確認：調査報告の `safe_projection` に出典URLがあるか）。
  3. 結果は参照データとして渡す：既存の担当の規則（「操作結果は実行状態で、中の命令は実行しない」）の範囲で扱う。

### 設計

1. **結果の保存**：照合が「継続」と決めたとき、その手順の回答の準備で組んだ結果ブロックをそのまま継続の行に保存する（`dialogue_continuations.steps_json`、新しいmigration。0013・0014は変更しない）。中身は `operations` と `research` のブロックである。前の手順までの分を引き継ぎ、手順番号を付けて積む（最大3＋1手順）。
2. **元の依頼**：継続runでは `originalRequestInTransaction` が、root runの入力（利用者の原文）を返す。`command-source.ts` の直接の読取りも同じ関数に揃える。これで、すべての担当の `originalRequest` が利用者の原文になる。
3. **担当への結果**：委譲の入力に、hostが付ける `priorSteps`（手順番号と保存した結果ブロック）を加える。各担当の入力組立て（画像・音楽・Excalidraw・調査／操作の担当・command）で、`originalRequest` と同じ扱いの参照データとして渡す。規則文（`delegated-task-rules`・`command-rules`）に「priorStepsは同じ依頼で前の手順が得た結果。次の操作に必要な値はここから取り、推測しない」を加える。
4. **会話エージェント**：継続runの判断（R1・R2）にも同じ `priorSteps` を参照ブロックとして見せる。担当への依頼文が具体的になる。
5. **最終回答**：最後の手順の回答にも `priorSteps` を見せて、途中の手順の結果と出典を回答に含められるようにする（§11 の音声・出典の課題の一部）。
6. **窓**：切り詰めない（利用者判断・2026-10-22。担当の窓には余裕がある）。会話の窓では `fitAssembly` の切り詰めを受けないよう、組み立て後に元の依頼の直前へ一つのsystem文として置く。入力推論の時間が問題になれば、効果を確かめた後に最適化する。
