# 一手ずつの実行と原文照合による複数操作 設計案

作成日: 2026年10月21日

状態: 案・合意待ち。方式の方向性（最初の一手だけを選ぶ、実行後に原文と照合して足りない要素を探し直す、時間のかかる担当は「結果が出たら報告」）は2026-10-21に利用者と合意。本書の詳細（§9の決定事項）は未合意で、実装は未着手。

## 1 背景と評価

[日常の複数操作担当](everyday-task-agent-implementation-plan-2026-10-21.md)は、会話担当（R1）が `execute_task` へ委譲し、親が最初に全体の操作計画を作り、項目ごとに能力を探索・選択して子を呼ぶ。[進行契約の検証記録](verification/everyday-task-agent/progress-contract-verification-2026-10-21.md)では、タイマー二操作は改修後に安定したが、画像→3D・検索→別操作・動画再生では、毎回別の種類の失敗が出た。

| 観測 | 起きた場所 |
| --- | --- |
| 依頼を最初の一操作に縮めて委譲（全件） | R1の要約 |
| 複数操作の依頼を単独担当へ直接委譲（画像→3D 2/3、動画 1/2）、単独の依頼を親へ委譲（過去3/3） | R1の振り分け |
| 計画の脱落・余分な項目・schema違反・前項目の能力の流用 | 親の計画と能力選択 |
| `execute_task` が毎回の最初の推論に無条件で提示される | `delegate-conversation.ts` の別枠提示 |
| 埋め込み検索は題材で当たり、「二つ以上のタスク」という構造では当たらない | 能力検索（組合せ5件中、上位4件に入ったのは3件） |

原因は、次の二つの予測を最初の時点でLLMにさせていることにある。いずれも、まだ何も実行しておらず、担当の一覧も見ていない時点の判断である。

- 依頼全体のタスク数
- 依頼全体の計画

判断を一つ誤ると後段が静かに消える。判断の回数が多いほど、通しの成功率は掛け算で下がる。推論の精度をむやみに測って指示文を調整する方法は、確率的にしか改善せず、モデルを替えると揺らぐため採らない。

## 2 方式

最初の時点で全体を予測しない。代わりに、小さく具体的な二つの判断を繰り返す。

1. **最初の一手**：R1は、依頼のうち最初に行うことだけを切り出し、その用途で担当を検索・選択する。既存の `find_toolchain` の検索文を「最初の一手の用途」に限定する。担当の選び方は今と同じ二段の分析を使う。
2. **原文との照合**：担当の結果が確定したら、利用者の原文と、これまでの実行結果を照合する。照合の結果は次のいずれかとする。
   - `done`：依頼は達成済み。会話の既存の回答経路で報告する。
   - `continue`：足りない要素がある。その要素の用途を検索文として書く。hostがその検索文で上位4件を検索し、担当を一つ選ばせて実行し、再び照合する。
   - `blocked`：続けられない。実行済み・不足・未確定を分けて報告する。

単独の依頼は一手と一回の照合で終わる。複数の依頼は照合が自然に続きを作る。そのため、「単独か複数か」をR1に予測させる振り分けは不要になる。`execute_task` という選択肢と、その別枠提示は廃止する。

時間のかかる担当（調査、生成など）は、受付時点で「結果が出たら報告します」と会話へ返す。結果が確定した時点で照合を始める。会話全体の非同期化は本書の範囲外とする。

## 3 判断と仕組みの分担

| 担当 | 内容 |
| --- | --- |
| LLM（R1） | 依頼の理解、最初の一手の用途、4候補からの担当選択、担当への依頼文。Memory・Worldの背景を踏まえる |
| LLM（照合） | 原文と結果の照合、足りない要素の用途、次の担当の選択と依頼文、最終報告の文面 |
| host | 原文の保持、台帳、子の実行と結果確定の待機、照合の起動、根拠refの検査、二重実行の防止、手数・時間の上限、取消・訂正・権限失効・忘却 |

意味の判断（タスクの区切り、達成の判定、能力の選択）にコードの語句分岐・辞書・正規表現・同名対象の重複除外を使わない。

## 4 仕組みで固める点

1. **照合の基準は原文**：照合の入力の正本は、利用者の原文と、訂正・回答の原文である。R1の要約は担当への依頼文としてだけ使い、達成の基準にしない。
2. **完了には根拠を必須にする**：`done` では、原文の条件ごとに、それを満たした結果refを対応付ける。hostは、各refがこの依頼の中で確定した子の結果であることを検査する。存在しない結果や、背景資料だけを根拠にした完了は拒否する。条件そのものの見落としはLLMの判断に残る（§6で補正する）。
3. **二重実行の防止**：既存の台帳と、子IDによる再送の再利用を使う。同じ手の再送は同じ子とreceiptを返し、入力の変更は競合とする。内容の類似による重複除外はしない。
4. **上限**：子の呼出し6回、照合を含む判断12回、親子合計48推論、絶対期限300秒（時間のかかる担当では、その担当の期限）。最終報告用に1推論を予約する。上限に達したら `blocked` と同じ形で返す。
5. **小さい判断の形**：
   - 照合の出力は `{status: done|continue|blocked, need?: string, evidence: [{condition, ref}], summary}` に限る。
   - 担当の選択は、提示した4候補のfunctionを一つ呼ぶだけとする。
   - 計画全体や状態欄の写し込みが起きる大きなschemaは置かない。
6. **照合の起動条件**：R1が担当へ委譲した依頼すべてで、結果の確定後に照合する。調査・instantも、複数操作の前段になりうるので対象とする。R1が `answer` で直接答えた場合は照合しない。

## 5 流れ

```text
利用者の発話
  → R1：最初の一手の用途で検索 → 4候補から担当を選び依頼文を書く
  → host：子として実行（時間がかかる場合は「結果が出たら報告します」を返す）
  → 結果確定
  → 照合（原文 + 結果 + 台帳）
       done     → 根拠ref検査 → 会話へ報告
       continue → needで検索 → 4候補から選択 → 子として実行 → 照合へ戻る
       blocked  → 実行済み・不足・未確定を報告
```

質問・訂正・取消・忘却・再起動時の停止は、既存の作業制御（`task_control`）と台帳の契約を使う。訂正では、実行中の子の停止を確認してから照合に戻す。過去の実行を、新しい条件の達成と自動的には同一視しない。

## 6 「足りている」の誤認を経験で補正する

照合が `done` と判定した後に、利用者が同じ作業の不足を指摘した場合、その組を経験として保存する。

- 何を保存するか：元の依頼、報告した結果、指摘された不足。
- どう判定するか：その指摘が当該作業への不足の指摘かどうかは、R1が作業refを指定して判断する。
- 次にどう使うか：次の照合で、依頼と近い過去の経験を埋め込み検索で最大数件取り出し、参考資料として提示する。経験は指示や許可ではなく参考データとして扱う。

保存先は、担当選択と手順の履歴を持つ既存の `toolchain-history` を第一候補とする。利用者の事実・好みを扱うMemoryとは分ける。忘却の際は派生データとして一緒に消す。経験の語句から判定するコードは書かない。

## 7 既存実装の扱い

| 対象 | 扱い |
| --- | --- |
| 台帳、子の実行、再送の再利用、予算、取消、訂正、権限失効、忘却、再起動時の停止 | 再利用する |
| 子への結果の受渡し、所有domainへの公開操作の接続（research / command / instant / 生成 / browser） | 再利用する |
| `set_plan`・計画の表示・計画の改訂条件・`stepRef` の計画項目 | 廃止する。子IDと台帳の手順で置き換える |
| R1の `execute_task` の別枠提示と、検索からの除外 | 廃止する |
| 親の `find_toolchain` の自由な呼出し | 照合の `continue.need` による検索に置き換える |
| bundle `task.execute`（skill / package / toolchain） | 新revisionで照合の契約へ改める。旧revisionは書き換えない |

置き換えた後の旧コードと旧試験は残さない。

## 9 合意が必要な決定事項

1. 照合の対象を、R1が担当へ委譲したすべての依頼にするか（推奨）。操作・制作に限るか。対象を広げるほど、単独の依頼に照合の推論が1回増える。
2. 照合とその後の継続を、どこで動かすか。推奨は、既存の親実行（agent-runtime）を照合専用に改めて使う案で、台帳と予算をそのまま使える。会話担当の推論として実装する案もある。
3. 照合で `continue` となったときの扱い。推奨は、次の担当を選ぶ前に利用者へ確認せず続ける案で、利用者は訂正・取消で止められる。副作用のある操作の許可は、既存の所有domainの確認に従う。
4. 経験の保存先を `toolchain-history` にするか（推奨）。Memoryに置くか。
5. 既存の `task.execute` の名前と入口の扱い。廃止して照合に置き換える（推奨）か、名前を残すか。
