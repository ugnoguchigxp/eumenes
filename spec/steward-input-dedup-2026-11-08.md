# 記憶担当の入力の重複削減

2026-11-08。利用者が許可した「Eumenes側の入力の重複削減を実装し、変更前後のトークン消費と記憶品質を比較し、明確な改善だけ採用する」作業。

## 対象と根拠

Stewardの`messages.ts`は指示と`OUTPUT_SCHEMA`を独立入力のsystem、または共有会話入力のtask末尾へ書く。全stepは`executeControl`にも同じinstructions/outputSchemaを渡す。Inferenceの`operationOutputMessages`が、後続systemを落とす実装でも読めるよう同じ契約を最初のsystemへ追加する。このため指示とschemaが二重になる。共通機構側の説明・schemaの提示とproviderの構造化出力は必要なので維持し、Steward側の重複だけを外す。

本文の参照化は現行の会話入力が短縮・結合されるため今回行わない。記憶本文・出来事・引用・origin・期間・coverage・出力schema・provider設定・権限・単一writer・忘却・旧結果の拒否は変えない。core/hostパッケージ、DB schema、再推論抑制、サーバー起動/再起動、実記憶操作は対象外。他作業の差分を保持する。

## 実施順と採用条件

1. 変更前の対象ソースを保存し、現行の部分試験を確認する。
2. 出来事・記憶からの保存、訂正、否定、期間/条件、他者との区別、明示依頼、忘却を含む合成ケースと期待値、比較回数を最初のモデル実行前に固定する。既存のprepare/parse/applyとLARM/Inferenceを再利用する。
3. Stewardが渡す入力はdataだけとし、指示とschemaの唯一の追加元を既存Inferenceにする。公開された推論契約は変更しない。
4. 部分→結合→影響domainのverify。共通Inferenceを通した最終入力で、共有/独立両経路の先頭に指示とschemaが一つあり、本文等が欠落しないことを検査する。
5. 保存済みLARM設定をbackendの読取専用操作で参照し、隔離した合成データで旧新を交互に実行する。プロセス内の既存live runnerを利用し、サーバーは起動しない。実モデルのusageを記録し、入力/出力/キャッシュ/合計/遅延と品質を別集計する。raw credentialsや製品データは保存しない。
6. 凍結した各問の品質を弱めず、新版の新規意味失敗0、危険な誤保存/誤訂正/誤忘却0、旧版以上の合格数、実usageで入力と合計tokenが減ることを採用条件とする。品質失敗時は再生成で置換しない。通信失敗やusage欠落を成功扱いしない。実測で確証がなければ製品差分を戻し、試験と記録だけ残す。遅延は観測値として報告し、短い試験で実会話の高速化を断定しない。

正常な長時間推論を時間だけで再起動しない。3ラウンド、または同一失敗の証拠なし反復時は進め方を評価し、現在の会話へ判断を通知する。

## 結果

候補を実装し、12ケース×旧新の24応答を比較した。入力は69,683→36,079 token（48.22%減）、入出力合計は71,879→38,180 token（46.88%減）。ただし固定チェックの合格数は10/12→9/12で、候補だけ訂正が失敗した。引用を`今は`から原文にない`前は`へ変えたため既存の引用検査が更新を拒否し、古い記憶が残った。受入条件に従い、候補の製品コードと関連する試験変更はすべて開始時の内容へ戻した。

一例一観測のため、削減が常に訂正失敗を起こすとは断定しない。一方、この比較では品質維持が示せず、再生成や期待値変更によって採用を正当化しない。採否と原記録は[比較報告](verification/steward-input-dedup-2026-11-08/README.md)に保存した。
