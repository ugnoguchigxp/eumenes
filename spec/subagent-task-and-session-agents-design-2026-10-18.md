## 1 背景と目的

### 1.1 2026-10-18 の実機の事象

UI自由制作で、1回目の制作は画面に出た。しかし、そのまま続けた修正の依頼が効かず、毎回同じ画面が返った。DB とログで確かめた経過は次のとおり。

| 時刻（JST） | 発言 | run | 結果 |
| --- | --- | --- | --- |
| 15:11 | 「ecサイトのデモuiを考えてください」 | c5df4a8d | 反映が3回拒否され、4回目で版1が反映された。その後の返答の推論が契約違反で2回失敗し、run は failed になった |
| 15:14 | 「カートの中はいらないかな」 | ae54e5e4 | 4秒後の次の発言で cancelled になった |
| 15:14 | 「いるとしても相当ひどいですね」 | d4b832a3 | 定義の全文を出し直したが、版1と同一だった。receipt は `unchanged` なのに「反映しました」と答えた |
| 15:16 | 「何も変わってないですね」 | 93bb0d6c | 同じく `unchanged` で、同じ返答だった |

原因は次の4つである（根拠は `ui_composition_receipts` と各 run のログ）。

1. **記憶が欠ける。** 専門担当の履歴（`sessionHistory`）には、完了して回答のある run しか入らない。そのため、最初の依頼（failed）と「カートの中はいらない」（cancelled）は、専門担当に一度も渡っていない。
2. **全文を書き直す方式である。** 小さな修正でも定義全体を再生成させるので、出力が長くて遅く、写すだけで何も変えない誤りが起きる。
3. **「変更なし」を成功と返している。** `answerContext` が `applied: true, unchanged: true` を返すので、モデルは「反映しました」と言ってしまう。
4. **反映できたのにターン全体が失敗になる。** 作業は反映済みなのに、最後の返答が契約違反だと run を failed にする（D10 の問題）。

### 1.2 一般化した課題

UI自由制作のように、利用者と一緒に何ラウンドも編集を重ねる作業は今後増える。対象は次のように多様である。

- 一つの構造化文書を直す。UI定義の JSON、設定、図（Excalidraw のシーン）、表など。
- 外部の道具を使いながら成果物を育てる。Web で調べて表やプランを作る、画像を生成して画面に入れる、など。
- 一回の依頼で完結する操作や調査。タイマー、Kanban、Web検索など。

ところが、今の実行方式は次の状態にある。

- 型ごとに別々に作られている。command、research、session、instant、旧形式の plan→generate の2段（§3）。
- 「単発で終わるもの」と「一緒に作業を続けるもの」が、仕様として区別されていない。
- 協働型（session）は UI自由制作の都合に寄っていて、記憶・編集・道具の扱いが共通部品になっていない。

本書は、次の三つを共通の仕様として定める。

- サブエージェントを **単発型（task）** と **協働型（session）** の二つの型に整理する。
- 両方が使う **エージェント核** を一つにする。
- 協働型の対象を **作業領域（workspace）** として抽象化し、コーディングエージェントと同じように「読んで、部分を書き換える」編集を、ホストの共通機能にする。

## 3 現状の棚卸し

| 実行方式 | 入口 | 推論の回数 | ツール | 状態・記憶 | 結果の採用 |
| --- | --- | --- | --- | --- | --- |
| command | `toolchain-command.ts:138` | 1回（ループなし、修復なし） | binding の tools を `TOOLS=` で提示し、`parseInvocation` で検証する | 1回の呼び出しは無状態。質問の往復は command interactions（最大3問）が持つ | settle で agent-runtime の action ルートを通して実行する。回答文は会話側の2ラウンド目が書く |
| research（agent-runtime） | `agent-runtime/service/start-task.ts:11` | 1ステップ1推論のループ（web 12・history/world 7・quick 5） | executionRef をホストが発行し、分類別の予算を持つ（search 2・read 3 など） | `agent_tasks` のカウンタ、vault（900秒）、EvidenceCatalog | AnswerTicket の digest を照合して採用する |
| instant | `instant-answer.ts:22` | 0回（会話のR1の引数で実行する） | 1つ | なし | adapter の回答文をそのまま使う |
| 旧形式（excalidraw・image・music） | `generation-operation.ts:99-200` | plan 1回 → generate/open ジョブ | domain ごとの zod 契約 | domain ごと | domain ごと |
| session（専門担当） | `specialist-turn.ts` | 1ターン最大6回（invoke の結果を次の推論へ渡す） | binding の tools。作業は host が固定する | 作業の現在値（`current`）と、完了した run だけの履歴 | 操作ごとに writer transaction で実行する。返答はモデルが書く |
| coding（Codex） | `packages/coding-runner` | 外部 CLI の中で完結する | 外部 | 外部スレッド | Kanban・codex-tasks |

共通しているのは次の点である。

- LARM の `captureControl`/`executeControl` と、zod の出力契約。
- 1ジョブ1推論を、キュー駆動で settle する形。
- ツールはホストが発行した ref で指し、モデルに id を作らせない。
- 採用は receipt・digest・epoch の照合で確定する。

一方、次の点は型ごとにばらばらである。

- 記憶の持ち方。
- 失敗とやり直しの数え方（専門担当はターンに1回、agent-runtime はタスクに1回）。
- 早く終える手段。
- 作業対象を部分的に編集する手段。これはどの型にも無い。

## 4 設計の原則

1. **型は二つだけにする。** 単発型と協働型。instant はエージェントではない（推論しない）ので型に含めない。
2. **核は一つにする。** 文脈の並び、出力契約、ツール実行、予算、失敗の扱いは、両方の型で同じ部品を使う。違うのは、ライフサイクル（いつ始まり、いつ終わるか）と、記憶・作業領域の有無だけ。
3. **音声が先にある。** 返答は短い。変更の中身は画面で見せる（差分の表示）。1ターンはできるだけ1回の推論で終える。
4. **コーディングエージェントのように直す。** 現在の版を読み、必要な部分だけを書き換え、ホストが検証してから新しい版にする。全文を出し直すのは、新規作成と全面的な作り直しのときだけ。
5. **記憶はホストが持つ。** 何を頼まれ、何をして、どうなったかをセッション記録に残し、毎ターン決まった形で渡す。失敗・中断も記録から消さない。
6. **権限・検証・版の確定はホストが行う。** モデルの出力は提案であり、検証を通ったものだけが版になる。保存（確定）は、作業領域ごとに決めた確認を経る。
7. **domain の判断は domain に置く。** 作業文書の正規化・補正・検証は、所有する domain が実装する。ホストは汎用の編集手順を提供する。下位の domain は上位の domain を参照しない。

## 5 二つの型

### 5.1 単発型（task）

- **始まり:** 通常担当が依頼文（brief）を作って渡す。会話の相手は通常担当のまま。
- **処理:** エージェント核のループで、ツールを使って結果を作る。利用者に問い返すのは interactions（質問の往復）だけ。
- **終わり:** 結果（projection）を返したら終わる。回答文は通常担当が書く（今の2ラウンド目）。
- **記憶:** 依頼文と、そのタスク内のツール結果だけを持つ。タスクをまたいだ記憶は持たない。続けて頼まれた場合、通常担当は前回の結果の ref を新しい依頼文に付けて渡す（`previousResultRef`）。
- **該当するもの:** command（タイマー・Kanban・設定の単発操作など）、research（Web・会話履歴・World）、image・music の一回生成。

### 5.2 協働型（session）

- **始まり:** 通常担当が会話の相手を引き継がせる。引き継ぐのは、依頼の原文、通常担当の依頼文、対象（保存済みの作品・設定など）。ホストが作業領域を開く。
- **処理:** 利用者の発言ごとにターンを回す。各ターンで、作業領域を読み、編集し、短く答える。
- **終わり:** 保存して閉じる、会話に戻る（未保存なら保留）、破棄、期限切れ、のいずれか。今のセッション状態（active・suspended・closing・ended）を使う。
- **記憶:** セッション記録と作業領域の版の履歴を持つ（§8）。
- **該当するもの:** UI自由制作。今後の候補は、Excalidraw の対話編集、設定の対話編集、表やプランの作成、画像の反復編集。

### 5.3 型の選び方（登録者向けの基準）

| 問い | はい → | いいえ → |
| --- | --- | --- |
| 利用者が結果を見て、続けて直すことが普通か | 協働型 | 単発型 |
| 成果物が、版を重ねて育つものか（画面・文書・設定の下書き） | 協働型 | 単発型 |
| 一回の操作・調査で完結し、結果を通常担当が話せばよいか | 単発型 | 協働型 |

同じ domain が両方を持ってもよい。例えば、画像の一回生成は単発型で、「もう少し明るく」と反復する編集は協働型にする。型は binding の `execution` で決める（`command` は単発型、`session` は協働型）。

## 6 エージェント核

### 6.1 文脈の並び（D7 を採用する）

[リファクタリング計画 §3.5](conversation-subagent-llm-refactoring-plan-2026-10-17.md) の並びを、両方の型の共通部品にする。置き場所は `api/domains/inference` の contracts。

| 順 | role | 内容 |
| --- | --- | --- |
| 1 | system | 役割（profile）、SKILL、共通規則、出力契約、TOOLS。ホストが固定した文だけ |
| 2 | user（参考資料の囲み） | 協働型では、セッション記録の要約（§8.2）と、作業領域の現在の版（§7.3）。単発型では、それまでのツール結果。時刻 |
| 3 | user（囲みなし） | 現在の依頼。利用者の原文。委譲の依頼文と原文が違えば両方を入れ、原文を優先する |

1ターンの中の2回目以降の推論では、`assistant（前回の出力）` と `user（囲み: TOOL_RESULT）` を末尾に追記する。先頭部分は変えない。プロバイダーのセッション継続（`sessionRole: "subagent"`）とキャッシュを保つためである。

### 6.2 出力契約

今の専門担当の契約（一つの平らなオブジェクトと `action`）を引き継ぐ。そのうえで、両方の型を同じ形にそろえる。ネイティブの tool calling は使わない（A2）。LARM のローカルモデルと、今の control 契約・修復の仕組みをそのまま使えるからである。

| action | 単発型 | 協働型 | 意味 |
| --- | --- | --- | --- |
| `invoke` | ○ | ○ | TOOLS の一つを実行する。`reply` を付けられる（§6.3） |
| `reply` | ×（代わりに `finish`） | ○ | 利用者への短い返答・質問。ターンを終える |
| `finish` | ○ | × | 単発型の結果を返して終える（今の research の `finish{report}`、command の結果） |
| `clarify` | ○ | × | 単発型が利用者に一つ問う（今の command の clarify） |
| `return` | × | ○ | 担当を離れて通常担当へ戻す |
| `discard` | × | ○ | 利用者が明示したときだけ、未保存の作業を捨てる |

型ごとに使える action の集合を、出力 schema の enum で絞る。例は action ごとに一つだけ書く（今の方式のまま）。

### 6.3 早く終える仕組み（`reply` 付きの invoke）

一回推論の設計（S3）の `endTurn` を、モデル側の契約として一般化する。

- 協働型の `invoke` には、任意で `reply`（短い返答、今の `text` と同じ制約）を付けられる。
- ホストは操作を実行し、**成功したら** `reply` を返答としてターンを終える。返答のための推論はしない。
- **失敗したら** `reply` を捨て、結果を次の推論へ渡す（§6.5 のやり直し規則に従う）。
- adapter は従来どおり、結果に `endTurn: { reply }` を付けてホスト側からターンを終わらせることもできる。固定文で終えたい拒否などに使う。両方ある場合は adapter が優先する。
- 単発型の `invoke` に `finish` 相当を付けることはしない。単発型は結果の採用に照合が要るからである。

これで「1ターン1推論」が普通になる。UI自由制作の修正（部分編集＋一言の返答）は1回の推論で終わる。

### 6.4 予算と打ち切り

binding の `agent.turn`（§10）で、ツールチェーンごとに決める。既定値は今の値に合わせる。

| 項目 | 協働型の既定 | 単発型の既定 | 備考 |
| --- | --- | --- | --- |
| 1ターン（1タスク）の推論の上限 | 4 | 型ごとの今の値（command 1・research 5〜12） | 今の専門担当の6を下げる。`reply` 付き invoke で、ほとんど1〜2回で終わる |
| 拒否後のやり直し | 1 | 今の値 | ツールごとに上書きできる（§7.4、A4） |
| 出力契約の修復 | 推論ごとに1回（D3 の a） | 同左 | 修復も推論の上限に数える |
| 時間 | `timeLimits`（設計済み） | 同左 | 変更しない |

上限に達したときの扱い（D11 の a）は次のとおり。

- 残りの推論回数を、状態値として毎回渡す（`callsLeft`）。
- 最後の1回で `invoke` が来たら、契約違反として扱う。ただし `reply` 付きの invoke は、成功すればターンが終わるので許す。

### 6.5 失敗の扱い

| 事象 | 扱い |
| --- | --- |
| 操作は成功し、その後の返答だけが契約違反 | D10 の a。run は完了にする。画面には作業状況（receipt）を出し、読み上げは「〈ラベル〉を更新しました」のような**ホストの定型文**にする（A14）。セッション記録には「返答なし」と残す |
| 操作が拒否され、やり直しの上限を超えた | ホストの固定文で終える（例:「直せませんでした。〈短い理由〉」）。理由はエラーコードから決める。案（作れなかった内容）は作業領域の「反映できなかった案」に残す（§7.6） |
| 出力契約の修復も失敗 | run は failed にする。ただし、セッション記録には依頼と「失敗」を残す（§8） |
| 取消（割り込み・利用者の取消） | run は cancelled にする。発言はセッション記録に残す（§8.4） |

## 7 作業領域（workspace）

### 7.1 種類

| 種類 | 例 | 編集の手段 |
| --- | --- | --- |
| 作業文書（document） | UI定義 JSON、設定の下書き、Excalidraw のシーン、Markdown の文章、表（JSON） | ホスト共通の文書ツール（§7.3）。編集はテキストの置換 |
| 資産（asset） | 生成した画像・音楽・検索結果のメモ | 生成・取得のツールが作る。作業文書から id で参照する |
| 外部状態（external） | Kanban のカード、タイマー | domain の操作だけで変える。作業領域としての版は持たない（単発型が普通） |

協働型の作業領域は、作業文書を一つ以上と、資産の置き場を持てる。最初は「作業文書1つ＋資産」に限る（A3）。UI自由制作は `definition.json` 1つになる。

既存の `DomainAdapter.describe().documents`（設定画面の文書の項目登録）とは別の概念である。名前の衝突を避けるため、ref の種類は `workspace:` を新設する。設定の文書を協働型で編集するときは、設定 domain がその文書を作業文書として公開する（§11）。

### 7.2 作業文書の契約（domain が実装する）

`SessionWorkAdapter` に、作業文書の口を足す。

```ts
interface WorkDocumentPort {
  /** 作業文書の宣言。path は表示名、mediaType は application/json など。 */
  describe(): { path: string; mediaType: string; maxBytes: number; schemaRef: string };
  /** 版の正規テキスト。キー順を schema 順に固定し、JSON はインデント2で整形する。決定的であること。 */
  readInTransaction(tx, workRef): { revision: number; title: string; text: string } ;
  /** テキストを値に読み、補正（fixer、任意）し、厳密に検証する。版は作らない。 */
  checkText(text: string): { ok: true; value: unknown; fixes: string[] } | { ok: false; issues: Issue[] };
  /** 検証済みの値を新しい版にする。baseRevision が違えば revision_conflict。同じ値なら no_change。 */
  commitInTransaction(tx, workRef, input: {
    baseRevision: number; title?: string; value: unknown; origin: AdapterOrigin; note: VersionNote;
  }): { revision: number } ;
}
```

- **正規化は domain の責任である。** 同じ値からは必ず同じテキストを作る。同じ正規テキストを、画面の「ソース」表示とモデルへの入力の両方で使う。
- **補正（fixer）は任意である。** UI自由制作は、一回推論の設計 §4 の `fixDefinition` を使う。
- **検証の指摘（Issue）は、位置（JSON Pointer と行・列）と規則名だけにする。** 入力値は含めない（今の `repairHint` と同じ）。
- **`VersionNote` は、版ごとの短い記録である。** 依頼の run、操作の種類（create・edit・write・undo・user_edit）、編集の件数、補正の記録を持つ。セッション記録（§8）と画面の版の履歴に使う。

### 7.3 ホスト共通の文書ツール

作業文書を持つ協働型には、ホストが次のツールを自動で提示する。binding の tools に書く必要はない（A5）。

| ツール | 入力 | 動作 |
| --- | --- | --- |
| `doc.edit` | `{baseRevision, title?, edits: [{old, new}] (1〜32件), reply?}` | 正規テキストに置換を順に当てる。結果を `checkText` → `commitInTransaction` |
| `doc.write` | `{baseRevision, title, text, reply?}` | 全文を置き換える。新規作成と、利用者が全面的な作り直しを求めたときだけ使う（A6） |
| `doc.view` | `{fromLine?, toLine?}` | 文書が大きく、文脈に全文を入れないときだけ提示する（§8.2） |

`doc.edit` の規則（コーディングエージェントの Edit／MultiEdit と同じ考え方）は次のとおり。

- `old` は、その時点のテキストにちょうど1回現れなければならない。0回なら `edit_not_found{index}`、2回以上なら `edit_ambiguous{index, count}`。一意にするのはモデルの責任で、前後の行を含めればよい。
- 編集は配列の順に、前の編集を当てた結果へ当てる。途中で一つでも失敗したら、全体を当てない（原子的）。
- 一致は完全一致だけにする。空白やインデントの違いを吸収する曖昧な一致は入れない（新しいフォールバックになるため。A7）。
- 当てた結果が今の版と同じなら `no_change` を返し、版を作らない。`no_change` は成功ではない（§7.5）。
- `baseRevision` が今の版と違えば `revision_conflict`。画面での Undo や手直しが割り込んだ場合である。結果には最新の版番号を返す。
- 結果がJSONとして読めなければ `document_parse_failed{line, column}`。検証で拒否されれば `document_invalid{issues}`（最大8件）。

TOOL_RESULT は次の形に統一する。

```json
{"ok": true, "revision": 3, "fixes": ["alias:card->info-card"], "changedLines": [12, 40]}
{"ok": false, "error": "edit_not_found", "index": 1}
```

### 7.4 拒否後のやり直し（ツールごと）

| ツール | やり直しの既定 | 理由 |
| --- | --- | --- |
| `doc.edit` | 1回 | 出力が短く（数十〜数百トークン）、失敗の理由がはっきりしている（見つからない・一意でない）ので、直すのが安い |
| `doc.write` | 0回 | 出力が長い。一回推論の設計に従い、作り直しは利用者との対話で行う |
| domain の操作 | binding で指定（既定1回） | 今の SKILL の「二度まで」は1回に下げる |

### 7.5 結果が何も変わらないとき

`no_change` は失敗として扱う。

- 協働型では、やり直しをせずに、ホストの固定文でターンを終える。例:「変更点が分かりませんでした。どこを変えますか。」（A8）
- 理由は、2026-10-18 の事象のように、依頼が曖昧で何を変えるか分からないときに起きるからである。作り直しても同じ結果になりやすい。

### 7.6 反映できなかった案

一回推論の設計 §3.2 の「直近の反映できなかった案」を、作業文書の共通機能にする。

- `doc.write` が検証で拒否されたら、そのテキストと指摘を、作業領域の「反映できなかった案」に1件だけ残す。
- `doc.edit` の拒否では残さない。元の版が残っているからである。
- 次の依頼のとき、セッション記録の要約に「反映できなかった案があり、指摘は〜」と載せる。S6 の (b) にあたる。
- 利用者が画面でその案を直して反映する経路は、§7.7 と同じにする。

### 7.7 画面からの編集との関係

- 画面の Undo・Redo・保存・破棄は、今の画面操作のまま扱う。版が動いたことは、セッション記録に `screen_action` として残す。
- 利用者がソース表示で JSON を手で直す操作を、作業文書の口（`checkText` → `commitInTransaction`、origin は ui）で受ける（S6 の (c)、A13）。モデルの編集と同じ検証を通る。
- 次のターンの専門担当には、「版4は利用者が手で編集した」と記録で伝わる。

### 7.8 変更の見せ方

音声では短く答え、中身は画面で見せる。

- 制作画面に「直前の変更」を出す。前の版と今の版の正規テキストの差分を、ソース表示で強調する。
- プレビューで変わった部品を一時的に縁取るかどうかは、各 artifact が決める。
- 差分は版の正規テキストから画面側で計算するので、新しい保存項目は要らない。

## 8 記憶（協働型）

### 8.1 セッション記録

dialogue domain に、セッション記録の表 `dialogue_specialist_events` を新設する（A9）。run とメッセージから履歴を組み立て直す今の方式（完了した run だけ）をやめる。

| kind | 中身（小さく保つ） |
| --- | --- |
| `handover` | 通常担当の依頼文、依頼の原文、対象の ref |
| `user_utterance` | 発言のメッセージ id。本文はメッセージ表にある |
| `agent_reply` | 返答のメッセージ id |
| `tool_call` | ツール id と要約。`doc.edit` は編集の件数と変わった行。`doc.write` は文字数と digest。本文の全文は持たない |
| `tool_result` | ok・エラーコード・版番号 |
| `version` | 版番号、`VersionNote` |
| `turn_failed` | エラーコード |
| `turn_cancelled` | 理由（`superseded`：次の発言による、`user_cancel`、`returned`） |
| `screen_action` | undo・redo・save・discard・retarget・user_edit |
| `async_completed` | 非同期ツールの完了（§9.4） |

- 書き込みは、各 run の settle と、画面操作と同じ transaction で行う。取消後の古い結果は書かない（今の採用の照合に従う）。
- ログ（JSONL）には書かない。会話本文はメッセージ表、それ以外は短いコードだけである。

### 8.2 毎ターンの文脈の組み立て

参考資料の囲み（§6.1 の2）を次の順で組み立てる。

1. **引き継ぎ:** 依頼の原文と依頼文（`handover`）。最初のターンが失敗しても必ず残る。
2. **これまでの経過:** セッション記録から、ホストが決定的に作る。LLMで要約しない（A10）。

   ```
   v1 ← 「ecサイトのデモuiを考えてください」 doc.write 成功（返答の推論は失敗）
   ×  「カートの中はいらないかな」（次の発言で中断）
   v1 ← 「いるとしても相当ひどいですね」 doc.edit 変更なし
   ```

3. **最近の会話:** 直近 N ターン（既定12）の発言と返答の本文。失敗・中断したターンの発言も入れ、注記を付ける。
4. **作業領域の現在の版:** 版番号、タイトル、正規テキスト。
   - 32 KiB 以下なら全文を入れる。
   - それを超えたら、構造の目次（上位の部品と行番号）だけを入れ、`doc.view` を提示する。
5. **反映できなかった案:** あれば、その指摘（§7.6）。
6. **状態値:** `callsLeft`、`dirty`、`savedRef`、`viewing`、時刻。

最近の会話の予算（今の 192 KiB）を超えたら、古いターンから本文を落とす。「これまでの経過」の行は残す。経過の行は1件80字程度なので、200ターンでも 16 KiB に収まる。

### 8.3 割り込み・中断された発言（D5）

音声では、一つの依頼が二つの発言に分かれ、前の発言が取り消されることがある（今回の「カートの中はいらないかな」→「いるとしても相当ひどいですね」）。

- 次の発言で取り消された発言（`superseded`）は、次のターンの「現在の依頼」に直前の発言として含める。例:「（直前の発言、中断）カートの中はいらないかな」+「いるとしても相当ひどいですね」。原文の順のまま並べ、どちらを優先するかはモデルが読む（A11）。
- 利用者の明示の取消（`user_cancel`）は含めない。経過に「取消」として残すだけにする。
- 専門担当から戻るときに後ろに詰まっていた発言は、D5 の a（発言順のまま通常担当へ届ける）とする。画面から戻るときも同じにする。

### 8.4 単発型の記憶

単発型はセッション記録を持たない。会話の記憶は通常担当が持つ。続けて頼まれたら、通常担当が前回の結果の ref を依頼文に付ける（§5.1）。research の evidence など、タスク内の状態は今の `agent_tasks` のまま持つ。

## 9 ツールの種類と権限

### 9.1 ツールの分類

| 分類 | 例 | 提示のされ方 | 副作用の段階 |
| --- | --- | --- | --- |
| 作業文書ツール | `doc.edit`・`doc.write`・`doc.view` | 作業文書があればホストが自動で提示する | draft（作業領域の版だけ） |
| domain の操作 | `ui-compositions.submit`、設定の項目検証 | binding の tools | 操作の `effect` に従う |
| 共有ツール | Web検索、画像生成、会話履歴の検索 | binding の `agent.sharedTools`（§9.3） | none または asset |
| 対話の制御 | reply・return・discard・clarify・finish | 出力契約の action | なし |

### 9.2 副作用の段階と確認

| 段階 | 意味 | 確認 |
| --- | --- | --- |
| none | 読むだけ（検索・閲覧） | 不要 |
| draft | 作業領域の版を進めるだけ。Undo できる | 不要 |
| asset | 資産を作る（生成画像など）。作業領域に属し、保存されなければ消える | 不要 |
| commit | 保存済みの成果物・設定を変える | 画面のボタン、または利用者の明示の音声確認（A12） |
| irreversible | 外部への送信・削除 | 単発型の今の承認の流れに従う。協働型からは使わせない |

モデルは commit 以上の操作を直接持たない。協働型の保存は、今と同じく画面のボタンで行う。

### 9.3 共有ツール（協働型から他の能力を使う）

協働型が作業の途中で、Web で調べる、画像を作る、などを必要とする場合がある。通常担当へ戻らずに使えるようにする（A15）。

- binding の `agent.sharedTools` に、使ってよい単発型ツールチェーン（またはその中の tool）を列挙する。例: `{"toolchainId": "web.search", "as": "web_search"}`。
- 実行の流れは次のとおり。
  1. 協働型が `invoke`（tool は `as` の名前）で依頼文を渡す。
  2. ホストが、その単発型を子タスクとして起動する。
  3. 単発型の結果の projection（主張と出典、資産の id）が TOOL_RESULT になる。
- 子タスクの推論と時間は、協働型のターンの予算に数える。
- 子タスクに会話の記憶は渡さない。依頼文だけである。
- 資産（画像など）は作業領域の資産置き場に入り、作業文書から id で参照できる。UI自由制作では、画像の参照（imageSpec）に `asset` の種類を足す（P3）。

### 9.4 時間のかかるツール（非同期）

画像生成（数十秒〜）や詳しい調査（数分）は、音声のターンの中で待つと長すぎる。

- 共有ツールに `async: true` を指定できるようにする。
- 非同期のツールは、起動したらすぐに `{ok: true, pending: jobId}` を返す。協働型は「画像を作っています」と `reply` してターンを終える。
- 完了したら、ホストが `async_completed` をセッション記録に書く。セッションが active で手が空いていれば、**ホスト起点のターン**を一つ起こす（A16）。そのターンの「現在の依頼」は、完了の通知（ホストの定型の資料）である。協働型は結果を作業文書に入れ、短く知らせる。
- 利用者のターンが進行中なら、そのターンが終わった後に起こす。セッションが保留中・終了済みなら起こさず、再開時の経過に載せる。

### 9.5 Codex 等の外部コーディングエージェントとの関係

Kanban の Codex 実行は、外部の CLI に任せる別系統である。本書の対象外とする。ただし、作業文書ツールの考え方（読む → 部分置換 → 検証 → 版）は同じなので、`doc.edit` の失敗コードと結果の形は、Codex の差分適用と比べられる形にしておく。

## 10 登録の形（binding）

session binding に `agent` を足す。command binding にも、単発型に関係する項目だけを足す。どちらも任意の項目で、無ければ今の動作になる。

```json
{
  "kind": "binding",
  "id": "ui.studio",
  "revision": 4,
  "execution": "session",
  "adapterRef": "adapter:ui-compositions",
  "availabilityRef": "availability:ui-compositions",
  "tools": [
    { "toolRevisionId": "tool:ui.submit@1", "operationId": "ui-compositions.submit", "inputSchemaRef": "builtin:uiSubmitRequest" }
  ],
  "artifactRevisionId": "artifact:ui.studio@4",
  "session": { "targetSchemaRef": "builtin:uiCompositionTarget" },
  "timeLimits": { "runMs": 1200000, "turnMs": 900000, "inferenceMs": 600000 },
  "agent": {
    "workspace": { "documentRef": "workspace:ui-compositions.definition@1", "inlineBytes": 32768 },
    "turn": { "maxModelCalls": 4, "retries": { "doc.edit": 1, "doc.write": 0, "default": 1 } },
    "memory": { "recentTurns": 12, "recentBytes": 196608 },
    "sharedTools": []
  }
}
```

- `workspace.documentRef` は、adapter の `describe().workspaces`（新設）にある宣言を指す。bundle の検証で存在を確かめる。
- `sharedTools` の各要素は `{toolchainId, as, async?}`。登録時に、その toolchain が単発型として有効であることを確かめる。
- `doc.*` を持つときは、`ui-compositions.draft.apply` を tools から外す（§12）。
- 版の規則は今のとおり。binding・artifact・toolchain の revision を上げ、既存の revision の JSON は変えない。

## 12 UI自由制作への適用

前回の調査で挙げた E1〜E5 と、一回推論の設計の S1〜S6 は、本書の仕組みで次のように扱う。

| 項目 | 扱い |
| --- | --- |
| E1 編集の指定方法 | `doc.edit`（正規テキストの文字列置換）。JSON Pointer は使わない |
| E2 全文の反映 | `doc.write` は新規作成と「全面的に作り直して」のときだけに使う。SKILL に書く |
| E3 変更なし | `no_change` は失敗。固定文で聞き返す（§7.5） |
| E4 履歴 | セッション記録（§8）。失敗・中断も残す |
| E5 一回推論の設計との関係 | 統合する。S3 の `endTurn` は §6.3 の `reply` 付き invoke と adapter の `endTurn` になる |
| S1 出力契約の修復 | 推論ごとに1回（D3 の a）。推論の上限に数える |
| S2 補正で部品を捨てたことを伝える | `fixes` に捨てた記録があれば、ホストが返答に一文を足す |
| S6 反映できなかった案 | (a)(b)(c) を入れる（§7.6・§7.7）。(d)（強制反映）と (e)（コピー・ダウンロード）は入れない |

UI自由制作で変えるものは次のとおり。

- adapter に作業文書の口（§7.2）を実装する。正規化は schema 順のキー・インデント2。補正は `fixDefinition`、検証は `validatedDefinition`。
- `answerContext` の `unchanged` を `no_change` の拒否に変える。
- SKILL を書き換える（skill@7）。
  - 「最初の依頼は `doc.write`。修正は `doc.edit` で、依頼の部分だけを置換する」。
  - 「`old` には前後の行を含めて一意にする」。
  - 「成功したら `reply` で一言」。
  - 「失敗したら、理由を読み、一度だけ直す」。
  - 「完全な定義を渡す（差分は受け付けない）」の規則を消す。
- ソース表示を正規テキストにそろえ、直前の差分を強調する。ソース表示の手直しを受ける（A13）。
- 版を上げる。binding `ui.studio@4`、artifact `ui.studio@4`、package・toolchain の revision。

1ターンの推論の量の見込み（2026-10-18 の実測、出力1トークン約16ms）は次のとおり。

- 今: 全文の再生成で約750トークン（約12秒）、返答の推論で約16秒。合計約28〜45秒。
- 変更後: 部分編集は約50〜200トークン（1〜3秒）。返答の推論は無い。入力の処理（約12秒）は残るので、約15秒前後になる。

## 14 試験と受入

- **核:** 文脈の並び（囲みのない user は現在の依頼だけ）。`reply` 付き invoke の成功で1推論で終わること、失敗で次の推論へ進むこと。`callsLeft` と最後の1回の扱い。修復の数え方。
- **作業文書:** 置換の一意性（0回・2回以上）、原子性、順序、`no_change`、`revision_conflict`、解析失敗の位置、検証の指摘、補正の記録。正規化の決定性（同じ値は同じテキスト）。既存の fixture（U1〜U8）を正規化して、補正なしで通ること。
- **記憶:** 失敗したターン・中断したターン・画面の操作が、次のターンの経過に出ること。`superseded` の発言が次の依頼に含まれ、`user_cancel` は含まれないこと。予算を超えたとき、経過の行が残ること。2026-10-18 の4ターンを fixture として再現し、3ターン目の入力に最初の依頼と「カートの中はいらない」が含まれること。
- **UI自由制作:** 修正の依頼が `doc.edit` 1回で反映されること。音声の依頼で読み上げまで完了すること（`specialist-voice.test.ts`）。E2E の台本（`ui-compositions.spec.ts`・`ui-composition-parts.spec.ts`）を部分編集に合わせる。
- **live・実機:** 実モデルで「作る → 3回直す」を音声で通す。各修正が1推論で終わり、前の修正が保たれることを確かめる。fixture・live・実機の結果は分けて記録する。
