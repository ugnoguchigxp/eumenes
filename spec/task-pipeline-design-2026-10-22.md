# タスクパイプライン 設計

- 日付: 2026-10-22
- 状態: 合意済み（2026-10-22、§11 は推奨どおり）。実装の契約は §13
- 関連: [step-and-check-multi-operation-design-2026-10-21.md](step-and-check-multi-operation-design-2026-10-21.md)（一手ずつ照合する方式。本書の受け皿）、[subagent-task-and-session-agents-design-2026-10-18.md](subagent-task-and-session-agents-design-2026-10-18.md)（単発型・協働型、作業文書と `doc.edit`/`doc.write`）、[docs/toolchain-extension.md](../docs/toolchain-extension.md)

## 1 背景と目的

3タスク横断（`pasta`：調べる→タイマー→曲）の実モデル受入は 0/3 でした。一手ずつ照合する方式では、次の三つが毎回揺れます。

- 何をどの順で行うか。
- 前の結果をどう渡すか。文章の結果から値を取り出す処理（「8〜9分」→ `minutes=8`）も含みます。
- いつ完了とするか。

利用者の提案（2026-10-22）により、決まった手順を固い定義（データ）としてまとめ、担当の検索で引き当てられるようにします。LLM の仕事は次の三つに絞ります。

1. どの手順を使うかを選ぶ。
2. 入力の値を当てはめる。
3. 各ステップを、既存の単タスクのサブエージェントとして実行する。

順番、受け渡し、合格の判定は、仕組み側が定義どおりに行います。

3つ以上の担当を使う手順は、新しい機能ドメイン `pipelines` にまとめます。定義は利用者と LLM が対話して作り、画面（Artifact）で流れを目で確かめながら、試験もします。

### 1.1 以前に却下した案との違い

「よくある組み合わせを1つのツールチェーンにする」案は、組み合わせをコードに固定するので却下しました。本書の定義はデータです。作る、試す、版で公開する、という流れをすべて利用者側で行います。コードに入るのは、汎用の実行部と検査だけです。

## 2 合意済みの決定（2026-10-22）

| # | 決定 |
| --- | --- |
| D1 | 定義は JSON で保存します。表示するときは整形して（インデント2、キー順は schema 順）見せます。YAML は使いません |
| D2 | 最初の版は、一直線に並んだステップだけにします。分岐と並列は後の段階にします |
| D3 | 編集の画面は Artifact で出します。その画面で、どの言い方なら担当の検索に拾われやすいかも確かめられるようにします |
| D4 | 定義は、LLM が作業文書（JSON のテキスト）を編集して作ります。UI自由制作と同じく、対話しながら埋めていきます。人もエディタで直接編集できます |
| D5 | 依頼が定義の一部としか合わないとき（例：3ステップのうち2つだけ頼まれた）は、パイプラインを使いません。今の、一手ずつ照合する方式で処理します |

## 3 全体像

```text
発話
 → 担当の検索（公開済みのパイプラインも候補カードとして出る）
 → R1 がパイプラインを選び、入力を埋める（各入力に、依頼の原文からの引用を付ける）
 → 仕組み側の検査：schema、引用が原文にあること
 → パイプラインの実行（アプリケーション層が1ステップずつ進める）
      step: toolchain  既存の担当へ、ひな形から作った依頼文で委譲する。終わるまで待つ
      step: extract    宣言した変数から、型つきで値を取り出す（LLM が出し、仕組み側が検証する）
      各ステップの後に合格条件を確かめる。不合格なら止める
 → 結果のまとめ（最終回答のひな形と、各ステップの結果ref）
 → 既存の完了の照合（パイプライン全体を1手として扱う。足りない条件があれば今の方式で続ける）
```

## 4 定義の形式（`pipeline.json`）

```json
{
  "formatVersion": 1,
  "id": "cook-timer-music",
  "title": "茹で時間を調べてタイマーと曲",
  "summary": "食材の標準的な茹で時間を調べ、その時間のタイマーを掛け、待つ間の曲を作る",
  "useWhen": ["パスタを茹でる時間を調べてタイマーを掛けて、曲も流して"],
  "avoidWhen": ["時間が決まっているタイマーだけの依頼"],
  "inputs": {
    "food": { "type": "string", "description": "茹でる食材", "required": true },
    "mood": { "type": "string", "description": "曲の雰囲気", "required": false, "default": "落ち着いた" }
  },
  "steps": [
    {
      "id": "research",
      "kind": "toolchain",
      "toolchain": "web.guided",
      "request": "${inputs.food}の標準的な茹で時間を調べてください",
      "outputs": { "report": "result.report" },
      "accept": { "state": "completed" }
    },
    {
      "id": "minutes",
      "kind": "extract",
      "from": ["${steps.research.report}"],
      "instruction": "標準的な茹で時間を分で。幅があれば短い方",
      "schema": { "type": "integer", "minimum": 1, "maximum": 120 }
    },
    {
      "id": "timer",
      "kind": "toolchain",
      "toolchain": "timers",
      "request": "${steps.minutes.value}分のタイマーを掛けてください",
      "outputs": { "timerId": "refs.timer" },
      "accept": { "state": "completed", "outputs": ["timerId"] }
    },
    {
      "id": "music",
      "kind": "toolchain",
      "toolchain": "music",
      "request": "${inputs.mood}な曲を作ってください",
      "outputs": { "songId": "refs.song" },
      "accept": { "state": "completed", "outputs": ["songId"] }
    }
  ],
  "answer": "${inputs.food}は約${steps.minutes.value}分です。タイマーを掛け、曲を作りました。",
  "tests": [
    {
      "utterance": "ペンネを茹でる時間を調べてタイマーして、明るい曲も作って",
      "inputs": { "food": "ペンネ", "mood": "明るい" },
      "stepResults": { "research": { "result": { "report": "ペンネの茹で時間は11〜12分が目安" } } },
      "expect": { "steps.minutes.value": 11 }
    }
  ]
}
```

### 4.1 項目

| 項目 | 内容 |
| --- | --- |
| `id`・`title`・`summary`・`useWhen`・`avoidWhen` | 担当の検索に使います。今の bundle の profile と同じ項目で、同じ索引に入れます |
| `inputs` | 型つきの入力です。型は string・integer・number・boolean・enum。R1 が埋めます |
| `steps[].kind=toolchain` | `toolchain` は公開済みのツールチェーンの id です。`request` は委譲する依頼文のひな形です。`outputs` は、結果のどの値を変数にするかを書きます。指す先は、受け渡しの記録（`PriorStep`）に入る値と ref です |
| `steps[].kind=extract` | `from` の変数から、`schema` の形の値を一つ取り出します。LLM が出し、仕組み側が schema で検証します。自由な文章を次のステップへ流さないための専用ステップです |
| `steps[].accept` | 合格条件です。状態（completed）、エラーが無いこと、指定した出力があり型に合うこと。意味の判定は書きません |
| `answer` | 最終回答のひな形です。無い場合は、各ステップの結果から会話LLMが短くまとめます |
| `tests` | 試験の事例です。発話、期待する入力、ステップの偽の結果、期待する変数の値を書きます（§8） |

### 4.2 変数

- 参照は `${inputs.x}`・`${steps.<id>.<output>}`・`${steps.<id>.value}`（extract の値）だけです。式や関数は持ちません。
- 実行1回ごとの変数と成果物の参照（タイマーID・曲ID・画像ID など）を、実行記録として保存します（§6）。
- 各ステップのサブエージェントが受け取るのは、ひな形に埋め込まれた値と、宣言された変数だけです。成果物の ref は、今の受け渡しの記録（`handoffValues`）の形で渡します。
- サブエージェントから共有データを書き換える口（§11 Q2）は、最初の版では `outputs` と `extract` に限ります。

## 5 選択と入力の当てはめ

- 公開済みのパイプラインの版は、ツールチェーンの候補として、担当の検索の索引に入ります。検索の文は、今の「最初の作業の用途」ではなく、依頼の全体で引けるようにします。本書は `summary`・`useWhen` を、依頼全体を表す文で書きます。
- 候補カードには、入力の schema と、ステップの短い一覧（例：「調べる→タイマー→曲」）を載せます。即時型の担当の引数と同じ形で、R1 がパイプラインの関数を呼びます。
- 各入力に `requestQuote`（依頼の原文からの引用）を付けます。仕組み側は、引用が利用者の発話の中に文字どおりあることだけを確かめます。既定値があり、利用者が触れていない入力は、引用無しで構いません。意味の一致は判定しません。
- 一部しか合わない依頼（D5）は使わない、という規則は、候補カードと R1 の文脈に書きます。判断は LLM に任せ、コードで発話を分類しません。

## 6 置き場所と実行

### 6.1 ドメインの分担

| 層 | 置くもの |
| --- | --- |
| `api/domains/pipelines`（新設） | 定義の契約（zod）、静的な検査（§7）、版の保存（既存の版は書き換えません）、実行記録（変数・ステップの状態・成果物のref）、ひな形の展開、domain の試験 |
| `agent-runtime`（実行の進行） | パイプラインの実行です。休止中の task 型が持つ親実行（`agent_executions`）の基盤を、手順が決まったモードで使います。子の呼び出し、ジョブの待ち、取消、締め切り、会話への結果の通知は、今の基盤のままです（§13.4） |
| `api/application/toolchain` | 公開（定義から bundle を作って登録）、候補カードへの入力の付与、実行基盤への口（port）の実装。複数ドメインへの保存は、一つの書き込み処理（transaction）でまとめます |
| capabilities | 公開した版を、担当の検索の索引とツールチェーンの登録へ入れます。公開の操作は、アプリケーション層の一つの書き込み処理で行います |

下位のドメインは上位を参照しません。`pipelines` は、capabilities や各担当のドメインを直接 import しません。担当の存在の確認は、検査のときに口（port）で受け取ります。

### 6.2 実行の型

ツールチェーンの実行の型に `pipeline` を足します（§11 Q1）。今の型は instant・command・session・task です。パイプラインの1回の実行は、今の継続の仕組みの1手として台帳に載ります。取消、予算、run の締め切りは、今の仕組みを使います。

### 6.3 ステップの進め方

1. ひな形を展開します。参照する変数が無い場合は、そこで止めます（検査で防ぐので、通常は起きません）。
2. `toolchain` のステップは、今の継続の手と同じ委譲の経路で担当へ渡します。依頼文は展開したひな形にします。利用者の原文は、参考資料として添えます。
3. 時間のかかる担当（3D・曲・画像）は、ジョブが終わる状態になるまで、仕組み側が待ちます。待つ間、会話には「進行中」と返し、終わったら次のステップへ進めます。
4. 合格条件を確かめます。不合格なら、パイプラインを止めます。そこまでの結果と、止まったステップと理由を会話に返します。自動のやり直しは、各担当の中の今のやり直しだけにします。
5. `extract` は、推論1回で、schema つきの値を出させます。検証に失敗したら、修復を1回だけ行います（今の構造補正と同じ）。それでも失敗したら止めます。

### 6.4 完了の照合との関係

- パイプラインの各ステップの合格は、§6.3 の機械的な判定だけで決めます。ステップごとに `check_request` は呼びません。
- 全体が終わったら、今の完了の照合を1回行います。パイプライン全体を1手として扱います。依頼にパイプライン外の条件があれば、今の方式で続けます。

## 7 静的な検査（保存と公開の前）

次の点を、機械的に確かめます。

- schema に合っていること。
- 変数の参照が切れていないこと。前のステップか `inputs` にあることを確かめます。
- `extract` の `schema` と、参照する側の型が合うこと。
- `toolchain` が公開済みで、使える状態であること。
- `id` が重ならないこと。
- ステップの数の上限（最初は8）。
- `tests` の事例が schema に合うこと。

指摘は、位置（JSON Pointer と行・列）と規則の名前だけにします。UI自由制作の作業文書と同じ扱いです。

## 8 作る・試す基盤

### 8.1 作り方（D4）

- 協働型の専門担当 `pipeline.studio` を、bundle で登録します。作業文書は `pipeline.json` 1つです。編集は、ホスト共通の `doc.edit`・`doc.write` で行います。設計は、サブエージェントの二つの型の §7 のとおりです。
- 正規テキストは、インデント2、schema 順のキーです。画面の表示と、モデルへの入力の両方で同じテキストを使います（D1）。
- 人が画面で直接編集した結果も、同じ作業文書の新しい版になります（`user_edit`）。
- 公開は、利用者が画面のボタンを押したときだけ行います。公開するたびに、パイプラインの新しい版ができます。

### 8.2 編集画面（Artifact、D3）

| 区画 | 内容 |
| --- | --- |
| ソース | 整形した JSON のエディタです。人も編集できます。直前の変更を強調します |
| 流れ | ステップを順に並べた図です。変数のつながり（どのステップの出力がどこで使われるか）を線で示します。検査の指摘は、該当のステップに出します |
| 検索の確認 | 言い方を入力すると、担当の検索で、このパイプライン（下書きも可）が何位で、どれくらいの近さで出るかを、他の候補と並べて示します。`useWhen` などの、どの項目が効いたかも示します |
| 選択の試験 | 発話を入れると、実際の R1 で選択と入力の当てはめだけを行います。担当は実行しません。選ばれたか、入力と引用が期待どおりかを示します |
| 試験運転 | 偽の結果での運転（`tests` の `stepResults` を使い、担当は動かしません）と、実モデルでの運転です。実モデルでの運転は副作用があるので、開始前に確認します |

検索の確認は、公開前の下書きを索引に入れずに点数を出します。今の索引の点数の付け方と同じ計算を、下書きの文にも当てます。

## 9 試験

- **固定試験（domain）**：検査の各規則、ひな形の展開、版の保存（上書きしないこと）、実行記録。
- **固定試験（アプリケーション）**：偽の担当で、1本の通し、途中の不合格による停止、extract の検証失敗と修復、取消、時間のかかるジョブの待ち、パイプライン後の完了の照合。
- **実モデル（live）**：手順を2〜3本、手で書きます（`pasta` 型、画像→3D→曲 など）。似ているが同じではない依頼で、選択、入力、通しの結果を測ります。live 検証の仕組み（`scripts/task-execution-live.ts`）に組を足します。
- fixture、live、実機器の結果は分けて記録します。

## 11 要合意事項

| # | 問い | 推奨 |
| --- | --- | --- |
| Q1 | 実行の型 `pipeline` を新設するか、task 型の一種にするか | 新設します。task 型は LLM が次の一手を決める型で、性質が逆だからです |
| Q2 | サブエージェントが、宣言された共有の変数を書き換える専用ツール（例：`vars.set`）を持つか | 最初の版は持ちません。`outputs` と `extract` で足りるか、P1 の live で見て決めます |
| Q3 | パイプラインの後に、今の完了の照合を1回行うか（§6.4） | 行います。パイプライン外の条件を拾うためです |
| Q4 | ステップが失敗したときの扱い | 最初の版は止めるだけにします。それまでの結果と理由を返し、自動の続行や代わりの手順は入れません |
| Q5 | パイプラインのステップから、別のパイプラインを呼ぶか | 呼びません（P3 以降に検討） |
| Q6 | 定義の保存先 | `pipelines` ドメインの SQLite です。版ごとに JSON を保存します。見本を bundle で配るのは後回しにします |
| Q7 | P1 で手で書く手順 | `pasta`（調べる→タイマー→曲）と、画像→3D→曲の2本です |

## 12 対象外

- 分岐、並列、繰り返し（P3）。
- 発話の分類をコードで行うこと。選択、入力の当てはめ、一部しか合わないかの判断は、LLM に任せます。
- 既存の版の書き換え。

## 13 実装の契約（2026-10-22）

[ツールチェーンの登録と拡張](../docs/toolchain-extension.md)と skill `data-driven-toolchain` の手順に合わせます。パイプラインは、データドリブン形式のツールチェーンの一種として登録します。

### 13.1 binding（`execution:"pipeline"`）

```json
{
  "kind": "binding", "id": "pipeline.cook-timer-music", "revision": 1,
  "execution": "pipeline",
  "adapterRef": "adapter:pipelines@1", "availabilityRef": "availability:pipelines@1",
  "tools": [],
  "timeLimits": { "runMs": 1800000, "turnMs": 900000, "inferenceMs": 600000 },
  "pipeline": { "...": "§4 の定義（formatVersion 1）" }
}
```

- 定義は binding の中に持ちます。binding は版で保存され、既存の版は書き換えられないので、パイプラインの版は binding の版です。
- 定義の schema（zod）は `pipelines` ドメインに置き、capabilities の binding の契約はそれを参照します。`pipelines` は他のドメインを参照しません。
- 画面（artifact）は持ちません（instant・task と同じ）。package は tool を持ちません（task と同じ）。
- `runMs` は親実行の締め切りです。ステップごとの締め切りは、各担当の binding の `timeLimits` に従います。

### 13.2 公開（定義 → bundle）

- 公開すると、`pipelines` の定義から、profile・package・toolchain・binding の新しい版を持つ bundle を作り、`importBundleInTransaction` で登録します。id は `pipeline.<定義のid>`、関数名は `pipeline_<定義のid>`（`-` は `_`）です。
- toolchain の `summary`・`useWhen`・`avoidWhen`・`examples`（3件以上が必須。`tests[].utterance` と `useWhen` から作ります）は、定義の検索用の項目から作ります。担当の検索の索引（全文と埋め込み）には、他のツールチェーンと同じ経路で入ります。
- 公開の前に、§7 の検査を通します。担当の存在は、公開済みのツールチェーンの一覧で確かめます。
- 入口は API（`POST /api/pipelines/publish`、認証・Origin 検査あり）です。P2 の画面の「公開」ボタンも同じ操作を使います。

### 13.3 候補カードと選択

- アプリケーション層は、`execution:"pipeline"` の候補カードに `pipeline`（入力の JSON Schema、入力の検査、ステップの一覧）を付けます。即時型の `instant` と同じ方法です。
- R1 の関数の引数は、分析の項目、`announcement`、各入力 `<名前>`、引用 `<名前>_quote`（平坦）です。
- 検査に通った呼び出しは `next:"pipeline"` になり、予告を回答として返します。採用の書き込み処理の中で、親実行をパイプラインのモードで始めます。

### 13.4 実行（agent-runtime の親実行）

- `ParentState.pipeline` に、凍結した定義、入力、各ステップの値、進み位置を持ちます。親の判断の推論（`executionStep`）は使いません。
- `toolchain` のステップは、`startChild` で、その時点で公開中のツールチェーンの版へ子として渡します。依頼文は展開したひな形です。即時型の担当には `arguments` のひな形を展開して渡します。前のステップの結果 ref を子の参照に入れます。
- 子が終わったら（`adoptChild`）、合格条件を確かめます。合格なら次のステップへ、不合格なら `pipeline_step_failed` で止めます。子の質問（waiting_input）は、今の基盤どおり、会話への質問になります。
- `extract` は、専用のキューの処理（`PIPELINE_EXTRACT`）で、推論1回、関数1つ（`extract_value`、呼び出しを強制、出力の上限つき）で行います。schema の検証に失敗したら、修復を1回だけ行います。
- 全部終わったら、`answer` のひな形を展開した文を結果の要約にして、`completed` で終えます。会話には、今の `task_result` の通知で届きます。
- 依頼の訂正（amend）は、パイプラインでは受け付けません（`pipeline_amend_unsupported`）。状態の確認、質問への回答、取消は、今の `task_control` で行います。
- 親実行の可用性は、task 型の binding（休止中）ではなく、そのパイプラインの binding が公開中であることで判定します。

### 13.5 完了の照合（Q3）

- パイプラインの `task_result` の通知に答える run では、親実行の元の依頼を原文として、今の完了の照合を1回行います。ステップの結果は、照合の1手分の結果として渡します。足りない条件があれば、今の続きの方式で進めます。

### 13.6 作る基盤（P2）

- `pipeline.studio`：協働型の bundle です（session binding、`agent.workspace` は `workspace:pipelines.definition@1`）。package は tool を持たず、文書ツールだけを使います。
- adapter `adapter:pipelines@1` は、作業文書の口（正規化・検査・版の保存）と、画面の source・action を実装します。下書きは `pipelines` ドメインの SQLite に版で保存します。
- artifact `pipeline.studio@1` の view `pipeline-studio`（DesignSystem 部品）が、ソース・流れ・検査・検索の確認・選択の試験・試験運転を表示します。操作は、ソースの反映、公開、検索の確認、選択の試験、試験運転（偽の結果）です。実モデルでの運転は、確認のうえで会話から依頼します。
