# Eumenes テスト環境移行計画

作成日: 2026年10月14日  
状態: 評価用の計画案。移行実装は未着手。  
対象: ローカル検証、CI、fixtureによる結合試験、実接続評価の運用。

Eumenesの既存の `verify` を拡張し、変更に必要な検証を選択し、その選択理由と実行結果を追跡できる環境へ段階的に移行する。最初に試験の選択漏れと無駄な再実行を減らし、その後に再現試験、不変条件の試験、LLMによる変更専用テスト生成を追加する。

最初の実装単位は、検査順序の改善、試験の実行経路の棚卸し、実行履歴の保存、変更影響に基づく検証計画の表示までとする。既存テストの大量削除、テストランナーの全面統一、CIの検証範囲の縮小は含めない。

## 1 目的と成功の定義

解決する課題は、コードベースの拡大に伴う「どの試験を実行するか判断しにくい」「結果が出るまで長い」「別の編集で検証結果が無効になる」「不具合を同じ条件で再現しにくい」の四点である。

移行の成功は、テスト本数の減少ではなく、次の条件で判断する。

- 変更から必要な試験を選べ、選択と除外の理由を確認できる。
- 必須契約の試験と、変更によって壊れる利用側の試験を取りこぼさない。
- 結果を検証対象のソース、依存物、実行環境に結び付け、別の状態の合格と混同しない。
- 同条件で比較したとき、変更から有効な検証結果までの時間と、無効化による再実行が減る。
- fixtureの合格、LLM等への実接続評価、実機器受入を別の証拠として扱う。

速度改善と選択漏れ防止を別々に評価する。短時間で終わっても、選択範囲の妥当性を確認できなければ移行完了とはしない。

## 3 設計方針と変更範囲

### 3.1 既存機構を正本にする

domainの所有パスと依存関係は `scripts/domains.ts`、境界の検査は既存のboundary検査、試験の実行は既存のBun・Vitest・Playwright設定を使う。同じ依存関係を別の手書き台帳に複製しない。

試験の列挙と実行計画は既存構成から導出する。API結合試験、共通UI、動的bundle登録など、導出できない対応だけ補足する。補足情報は試験名やユーザーの語句による推測ではなく、所有・公開契約・登録adapterの接続関係を表す。

### 3.2 LLMと実行コードの役割を分ける

LLMは変更意図、仕様上のリスク、故障仮説、追加の試験を判断する。コードはファイル差分、依存関係、契約、実行、状態、資源制限、証拠の整合を管理する。

依存グラフと必須契約から選ばれた試験は、LLMの「低リスク」という判断だけでは省略しない。LLMが使えなくても必要な決定的検証は実行でき、LLMによる追加探索の未実施は明示する。語句辞書や固定シナリオ分岐で意味判断を代替しない。

### 3.3 検証を三つの用途に分ける

| 用途 | 実行する内容 | 合格が示す範囲 |
| --- | --- | --- |
| 開発中の局所検証 | 静的検査、変更箇所と利用側の関連試験 | 選択した範囲の契約と動作 |
| 変更を採用するための検証 | 関連する結合試験、配布物の契約、必要なReplay・ブラウザ試験 | 固定した変更と環境での結合動作 |
| 全体監査と外部環境の評価 | 全体の決定的試験、必要な実接続評価、実機器受入 | 全体または外部環境を含む明示した範囲 |

移行初期は現在のCIを維持する。局所検証の成功だけでCI全体の成功を代替しない。実接続評価と実機器受入は用途別の結果を保持し、音声MVPの完成条件である実機器の3往復受入を変更しない。

### 3.4 初期移行に含めないもの

- Nx等への全面移行、BunとVitestの統一、独立したVerification Engineの構築。
- MLによる失敗予測、共有リモートキャッシュ、全リポジトリの常時横断検証。
- 既存の恒久テストの大量削除、期待値や制限時間の緩和による高速化。
- 製品の業務仕様、DBスキーマ、認証方式の変更。
- 実運用の会話本文、音声、認証情報、Providerの生応答の収集・ログ化。

## 4 移行段階

段階0 → 段階1 → 段階2を基本順序とする。段階3は段階0の計測で対象を選び、段階1以降に小さく開始できる。段階4は段階2・3の証拠管理と隔離を利用する。

### 段階0 試験の実行経路と計測を整える

**実施内容**

1. 試験ファイルと実行設定を照合し、domain、application、infrastructure、client、DesignSystem、scripts、acceptance、browserの実行経路を確認する。
2. DesignSystemなど、収集した試験を実行先へ渡していない箇所を修正する。acceptanceの判定器試験と、実LLMを使う受入runを別に扱う。
3. 全体検証では各パッケージの静的検査を長い試験より前に実行する。既存の型検査範囲を狭めない。
4. 実行ごとの結果を保存し、`latest.json` は既存利用者向けの入口として維持する。成功時の証拠もCIで保存する。
5. 固定した入力と同じ環境条件で、時間、失敗、無効化、再実行を計測する。初回install・buildと試験実行時間を分ける。

**完了条件**

- 発見したすべての試験に実行経路か明示した除外理由がある。未登録を黙って成功にしない。
- 除外は既存の実接続・実機器区分等に基づき、失敗する試験を隠すために追加しない。
- 必要な静的検査の失敗を、長い試験の実行前に検出できる。
- 成功・失敗・中断・未実行・入力変更による無効化を識別できる。
- 後続の改善を比較できる基準値が残る。

### 段階1 変更から検証計画を作る

最初は選択結果を表示するだけのモードを実装する。出力には変更一覧、対象試験、選択理由、必須契約、追加評価、影響不明の範囲を含める。以下のオプション名は案であり、現行CLIで利用可能とは扱わない。

```sh
bun run verify -- --affected --base <比較基準のref> --plan
```

**選択の契約**

- 比較基準を必須情報として記録する。ローカルでは基準からのcommit差分に加え、staged・unstaged・未追跡の対象ファイルを含める。CIではPRの基準や検証対象commitを明示する。
- 削除・改名は変更前後の所有関係を使う。基準refや変更前のグラフが取得できない場合は、影響不明として範囲を広げる。
- 変更domainから利用側へ逆向きに辿り、該当するAPI・Web・試験依存を確認する。初期版はdomain単位の保守的な選択とする。
- `api/application` の組み立て、client、共通UI、動的bundle、設定、migration、vendor更新を考慮する。静的importだけで完全とはみなさない。
- 公開契約・所有・接続関係が不明な変更は、該当する広い試験集合へ戻す。決定的試験の範囲を確定できなければ `verify:all` 相当へ戻す。
- ブラウザE2Eは選択したファイルを明示する。対応関係が不明なら計画を未解決とし、既存規則に反して無指定の全件E2Eを起動しない。
- prompt・schema・ツール定義の変更は、固定応答のfixtureだけでは判断品質を検証できないことを計画に表示する。

**検証方法と完了条件**

新規・削除・改名・未追跡、共通基盤、test-only依存、動的登録、vendor、設定の変更fixtureで選択結果を確認する。結合では実際のランナーへ渡す試験集合と計画を照合する。代表的な過去変更は同一入力で全体検証と比較する。

計画生成の初期完了条件は、代表fixtureの期待範囲を満たし、影響不明を明示できること。CIの縮小条件は別に段階2で定める。

### 段階2 入力の固定と選択実行を導入する

ローカルの未コミット変更も含め、検証対象を独立したディレクトリへ固定して実行する。新しい作業ブランチの作成は必要としない。未追跡・削除・改名・実行権限・必要な資産を含めた入力manifestを作り、取り込み中の変更を検出したら不完全なsnapshotとして終了する。

製品DB、秘密、ローカル設定ファイルをまとめてコピーしない。依存物はlockfileと配布物digestで一致を確認する。出力先、試験DB、ポート、書き込み可能なキャッシュを実行ごとに分離する。生成物もsnapshot内の入力から作る。

最初は実行の直列性を維持する。現在のlockを外して並列化するのは、DB・port・環境変数・build出力・レポートの競合がないことを確認した後とする。snapshot準備の時間も含めて効果を測る。

合格結果はsnapshotの証拠であり、その後の作業ツリー全体の合格ではない。変更採用時に対象digestとの一致を確認する。初期版では試験結果の自動キャッシュ再利用を行わず、履歴の保存に留める。

**比較運用と切替条件**

1. 現行の全体CIを残したまま、同じ入力で自動選択の計画・結果を比較する。
2. 暫定の評価期間を20変更とし、変更分類の偏りを確認する。20件すべてが小さなUI変更なら、共通基盤等の判断材料にはしない。
3. 全体試験で検出した失敗を選択側が見落とした場合、原因を分類して選択関係を修正する。既知の回帰と限定的な故障注入でも検出力を確認する。全件成功した20変更だけでは見逃しがない証明にならない。
4. 対象外の既存失敗は担当と影響を記録し、無断で修正・除外しない。それによって完走できない範囲は未評価とする。
5. 代表変更と既知の回帰で未解決の選択漏れがなく、無効化率・総所要時間が改善し、検証入力を追跡できた時点でCI縮小案を評価する。

Linux・macOS双方の証拠を維持する。全体監査の頻度、必須CI、変更採用・公開前に必要な結果は、評価結果に基づく切替判断として定める。それまでは現在のCIを変更しない。切替後に選択漏れや入力識別の不備が見つかれば、自動選択による省略を停止して全体検証へ戻す。

### 段階3 再現試験と契約試験を充実させる

**Replayの試行**

Queue・dialogue・voice-dialogueの既存fixtureを使い、開始、取消、遅延応答、期限到達、再起動を明示的なイベント列として与える。時刻だけでなく、応答の解放順序・乱数・識別子・初期状態も固定する。起動待ち等は、理由のない固定sleepではなく観測可能な状態で待つ。

初期対象は少数の取消・遅延結果・復旧ケースとする。各domainの業務契約と試験は当該domainに置き、複数domainの配線の確認だけapplicationで行う。実運用ログは本文やProvider応答を含まないため、そのまま再生データに転用できる前提を置かない。最初は合成fixtureを使う。

Replayの合格は、固定した外部応答を受けた制御の合格である。LLMが適切なツールを選ぶか、適切な情報を抽出するかは別の実接続評価で確認する。旧版との差分も、既存バグや意図した変更を含み得るため、差があるだけで不具合と判定しない。

**不変条件の試験**

既存契約を正本として、取消後の結果不採用、権限、二重副作用防止、忘却後の非再出現を、生成した入力と操作順序で確認する。単純な大量ランダム入力ではなく、事前条件と状態遷移を持つ試験を優先する。失敗seed・イベント列・最小化した再現例を保存する。fast-check等の採用は、小さい試行でBunとの適合と保守負担を確認して決める。

**配布パッケージの契約**

Memory・WorldModelの既存manifest・digest検査に、Eumenes側の利用契約試験を結び付ける。配布物digest、契約版、ホスト側試験の版を結果に残す。ホストが上流の内部試験を複製するのではなく、実際に使う公開操作・失効・migration等を確認する。上流の変更や公開手順の変更は、本計画だけでは実施対象にしない。

**完了条件**

同一fixtureの再実行で同じ契約違反を再現でき、既存の競合・復旧の回帰例を検出すること。実際のプロセス停止、タイマー、ブラウザ、機器でしか確認できない境界の試験は残す。実時間試験を削る場合は代替できる範囲と残す接続試験を示す。

### 段階4 JiTTestを追加探索として試行する

JiTTestは変更ごとに故障仮説とテストを生成する方式である。既存の必須試験を置き換える権限は持たせず、当初は変更採用を自動阻止しない参考結果として扱う。

入力は変更前後のコード、利用者要求、公開契約、凍結した評価基準、既存試験の証拠とする。LLMは故障仮説と試験候補を作る。実行hostは隔離、実行時間、モデル呼出し数、費用、許可された操作を制御する。予算切れや生成器の失敗は「不具合なし」にしない。

既存のcoding環境とfixtureを使う小規模な運用試行を先に行い、専用エージェント製品は作らない。将来Eumenesのツールチェーンとして提供する場合に限り、bundleと登録adapterによる既存の拡張手順に従う。

生成した試験は仕様に照らして確認し、意図した変更への誤報を除く。既知の不具合や隔離した変異コードに対して検出力を確認する。変更前後の差分は補助証拠とし、旧版を常に正解と扱わない。

一般的な失敗候補は一時成果物として保管期限を設ける。本当の不具合と確認できたものは、再現入力と恒久的な回帰試験を残す。評価指標は真の不具合数、誤報の確認時間、再現率、追加時間、費用とし、生成テスト数を成果指標にしない。

## 5 実行証拠の最小契約

新しい大規模な証拠DBは導入せず、既存のJSONレポートを拡張する。実行ごとの保存先を設け、`latest.json` との互換性を保つ。

| 情報 | 必要な内容 |
| --- | --- |
| 入力 | 基準commit、未コミット変更を含む入力digest、対象ファイルmanifest、lockfile、vendor digest |
| 実行条件 | OS、architecture、runtime・runner版、検査設定、試験・fixture版、seed、秘密を含まない環境条件 |
| 計画 | 対象試験、選択根拠、必須契約、除外理由、未解決範囲、LLM追加提案の有無 |
| 結果 | 各stepの状態と時間、実行した試験、失敗分類、再実行、停止理由、入力の有効性 |
| 実接続評価 | fixtureと区別した実行種別、実行時に取得したサービス識別情報、評価基準版、予算と使用量 |

必須項目が未実行・無効・判定不能なら、その範囲を合格にしない。失敗分類が不明な場合は未確定を許し、製品不具合や環境障害へ無理に割り当てない。

liveは保存済みLARM接続をbackendのsettings読み取り専用操作から参照し、テスト接続先は設定APIで保存する。モデル・profile名はコードやファイル名に固定しない。秘密やProviderの生応答をレポートに含めない。通常の運用ログと、合成fixtureを使う試験成果物の保存先・内容を区別する。

## 6 実装単位と検証

| 単位 | 主な変更候補 | 検証と完了条件 |
| --- | --- | --- |
| A 試験棚卸しと実行先 | `scripts/test-domain.ts`、既存runner設定 | 部分: 列挙と振分け。結合: DesignSystem・acceptance等の実行経路。通し: 選んだdomainで実際に期待した試験が動く |
| B 実行順序と履歴 | `scripts/verify.ts`、レポート、CIの証拠保存 | 部分: 状態・report契約。結合: 静的検査失敗時に長い試験へ進まない。通し: 完走・中断・無効化を正しく保存 |
| C 検証計画の生成 | `scripts/domains.ts`を読む選択処理、application等の対応情報 | 部分: 変更fixture。結合: 計画と実行引数の一致。通し: 過去変更の対象選択と全体検証の比較 |
| D 固定入力での実行 | `scripts/verification-inputs.ts`周辺、隔離実行 | 部分: 削除・改名・未追跡・実行権限・資産の保持。結合: DB・port・出力分離。通し: 元の作業ツリー編集と検証対象を混同しない |
| E 契約と再現性の試行 | Queue等の既存fixtureと各domain試験 | 部分: 時計・イベント列。結合: 取消と遅延結果。通し: 永続化・復旧を含む契約 |
| F JiTTest試行 | 既存のcoding環境と検証成果物 | 部分: 候補・予算・判定。結合: 隔離実行。通し: 既知の不具合の検出と誤報分類 |

最初の実装範囲はA・B・Cの計画表示まで。D以降は、先行段階の測定結果とレビューを反映して詳細化する。

既存コマンドによる検証は、`bun run verify -- --domain <name>` と必要な利用側domainを用いる。検証基盤自体の変更は、対象のscript試験から始め、代表domainで結合確認し、固定入力で `bun run verify:all` まで確認する。ブラウザ変更がある場合のみ対象ファイルを明示してE2Eを実行する。CIではflakyを合格としない既存方針を維持する。

通し検証を省略する場合は、その理由と未確認範囲を記録する。担当外の失敗は証拠を報告し、要件や期待値を弱めて通さない。

## 7 評価指標と停止条件

| 指標 | 評価方法 |
| --- | --- |
| 選択漏れ | 同一入力の全体試験で検出した失敗のうち、選択側が検出できなかったもの。原因別に記録 |
| 検出力 | 既知の回帰・限定的な故障注入を検出できるか。全成功の比較だけに依存しない |
| フィードバック時間 | 準備時間を含む、変更から最初の有効な結果まで。変更分類ごとの中央値と分布を比較 |
| 検証総コスト | 重複実行、snapshot作成、install、build、無効化、実接続費用を含める |
| 安定性 | 同じ入力での結果の揺れ、再試行のみ成功した試験、環境起因の失敗 |
| 保守負担 | 対応表・fixture・生成テストの更新量と、誤報の確認時間 |

暫定目標は、代表的な変更群で検証総時間の中央値を30％減らし、評価対象で未解決の選択漏れを残さないこととする。30％は達成済みの数値でも性能保証でもなく、段階0の基準値を見て評価開始前に確定する。比較対象は実際の現行手順とし、元々domain検証だけでよい変更を全体検証と比較して改善率を水増ししない。

同じ目的の「仮説・実施・結果確認」が3ラウンド続いた場合、または新しい根拠のない反復が起きた場合は、最新計画・完了条件・残作業を見直す。正常に進行する長時間処理を経過時間だけで再起動しない。検証対象を途中で編集して結果を無効にしない。

CI縮小後に選択漏れが出た場合は縮小を戻す。隔離実行が不安定なら入力変更検出付きの既存実行へ戻す。ReplayやJiTTestの費用・保守負担が効果を上回る場合は対象拡張を停止する。いずれも既存の検証基準を維持する。

## 8 採用判断が必要な事項

| 論点 | 現時点の案 | 判断に必要な根拠 |
| --- | --- | --- |
| application・bundle・共通UIの対応情報 | 既存構成から導出し、不足だけ補足 | 代表変更での選択漏れと対応情報の更新負担 |
| snapshotの作成方法 | ブランチを増やさない独立ディレクトリ | 未コミット変更の忠実性、準備時間、依存物の再現性 |
| CI縮小と全体監査の頻度 | 比較運用中は現状維持 | 変更分類ごとの結果、OS差、既知回帰の検出 |
| fast-check等の追加 | 小さな不変条件の試行で判断 | 現行runtimeとの適合、失敗例の縮小、保守負担 |
| Replayの共通化範囲 | 各domainのfixtureを優先 | 複数箇所に実際に生じた重複と共通契約 |
| LLM追加探索の費用上限 | 試行前に時間・呼出し数・費用を固定 | 使用可能な実行環境と実測費用 |
| 実行証拠の保持期間 | 失敗再現例は恒久化、一般実行は期限付き | 保存容量と調査に必要な期間 |
