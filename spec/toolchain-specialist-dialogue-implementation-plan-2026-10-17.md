# ツールチェーン専門担当との対話編集 実装計画

作成日: 2026-10-17

改訂: 外部レビューと同日の追加指示を反映。会話からの復帰、生成中のUndo禁止、専門担当でのWorld／Memory不使用、保存ボタンによる明示保存を追加。再レビューで、保留からの再開、生成中の範囲、範囲外発言の配送後の扱いを補完。

状態: 実装・固定試験済み（2026-10-17）。ブラウザE2E、実モデル受入、実機器受入は未実施。実施記録は§15。

対応するツールチェーンの専門エージェントへ会話相手を切り替え、成果物を対話で作成・修正する共通機構を追加する。初回適用はUI自由制作とする。最初の依頼から大枠を作り、その後の部分修正・全面変更、編集確定前のUndo／Redo、保存、通常会話への復帰を接続する。

## 1 目的と確定した要件

2026-10-17の利用者との合意を実装の基準とする。

- UI自由制作の一回生成型フローを廃止し、専門担当と会話して作る方式へ置き換える。初回の会話で初稿を生成することは、この廃止対象に含めない。
- 専門担当への切替はUI制作専用にせず、対応を登録したツールチェーンで利用できる共通機構にする。非対応のツールチェーンも存在する。
- 専門担当への切替後は、同じ会話欄でその担当と直接対話する。毎ターンの依頼整理・担当選択・返答の書き直しを通常会話エージェントへ戻さない。
- 最初の依頼で大枠を作る。続く依頼から部分修正か全面変更かを担当LLMが判断する。
- 作品ごとの制作会話の永続復元や、途中案を蓄積する履歴機能は作らない。編集確定前にはUndo／Redoを提供する。
- UI自由制作のArtifactに、過去の保存作品を見る機能と現在のUIを保存する機能を設ける。作品タイトルはAIが選ぶ。
- 現在のArtifactのプレビューをメインコンテンツにする。既存のデスクトップ／モバイル表示切替は残す。
- 制作画面の主表示を「プレビュー／ソース」で切り替え、表示中のOpenUI定義JSONを読取専用で確認できるようにする（2026-10-17の試用後の指示で、別Artifact方式から変更）。
- 履歴から保存作品を開いている間も「新規作成」で閲覧を解除し、編集中の案または空の状態へ戻れるようにする。
- 保存してArtifactを閉じると通常会話エージェントへ戻る。保存作品を閲覧中に修正を依頼すると、通常会話エージェントが切替を伝えて専門担当へ引き継ぐ。
- 「会話エージェントに戻って」という発言でも通常担当へ戻れる。テキストと音声で同じ公開操作を使う。
- 生成中はUndoを実行できず、ボタンもDisabledにする。Redoも同じ制限に揃える。
- 専門担当はWorld／Memoryを参照・更新しない。制作対話を自動取り込みの対象にしない。
- 確定保存は利用者が保存ボタンを押したときだけ行う。自動保存やAIによる保存はしない。「破棄」ボタンを常設し、試作を保存せず捨てられるようにする。
- 初期版は保存済みの担当設定を使う。モデル・接続を後から変更しても成果物の形式と保存先は維持する。

今回の実装範囲は共通機構とUI自由制作への接続まで。他の全ツールチェーンの移行、新しいモデル接続、任意コードを実行するWebサイト制作基盤、外部公開機能は含めない。別ツールチェーンでも通ることは試験用adapterで確認する。

## 3 利用者の操作と状態遷移

| 場面 | 会話相手 | Artifactと処理 |
| --- | --- | --- |
| 通常会話 | 通常担当 | 制作依頼から利用可能な専門担当を選ぶ |
| 新規制作への切替 | 専門担当へ交代 | 切替成立後に通知し、UI自由制作を開いて初稿を作る |
| 制作中の対話 | 専門担当 | 説明・必要な質問・部分修正・全面変更を直接扱う |
| 保存ボタン | 現在の担当を維持 | 現在案を保存し、その状態を次の編集の基準にする |
| 保存後に閉じる | 通常担当へ復帰 | 未保存変更がないことを確認して作業を終了する |
| 「会話エージェントに戻って」 | 通常担当へ復帰 | 未保存案があれば期限内だけ一時保留する。保存も破棄も強制しない |
| 破棄ボタンまたは明確な破棄依頼 | 通常担当へ復帰 | 生成を失効させて未保存案を破棄する。保存作品は残す |
| 保存作品の閲覧 | 通常担当 | 履歴から作品を開く。閲覧だけでは切り替えない |
| 閲覧作品の修正依頼 | 専門担当へ交代 | 保存内容と今回の依頼から、新たな編集を始める |

「アンケートUIを基本とし、4〜5問の問いで選択肢もRadioボタンの簡易的な物」は、生成されるアンケートが4〜5問であるという依頼として扱う。制作条件を4〜5問尋ねる固定ウィザードは設けない。低リスクの未指定事項は担当が仮置きして初稿を出し、成果物を作れないほどの不足だけを確認する。

閉じる操作では保存しない。未保存の状態でタブの閉じる操作をした場合は「破棄して閉じる／編集を続ける」を選べるようにし、保存したい場合は制作画面の保存ボタンを使う。常設の破棄ボタンは利用者の明示操作として、保存を勧める確認を挟まず破棄する。生成中は直前の正常案を表示し、破棄・終了が成立したら進行中の生成を失効させる。他のArtifactを閉じるだけでは専門対話を終了しない。

初期版は一つの会話で同時に一つの専門担当を有効にし、保留を含めて一つの作業だけを持つ。一時保留は現在案とUndo列を元の期限まで残すだけで、保存作品・過去案の履歴・再起動後の復元を増やさない。編集中に過去作品一覧を開くだけでは編集対象を変更しない。別作品への編集切替時の確認は§4.4のhost応答に基づく。

## 4 共通の担当切替

### 4.1 登録契約

既存のcommand bindingは変更せず、継続対話用の版付きbinding契約を追加する。作業名は `execution: "session"` とし、実際の型名はP0で確定する。bindingのunion、bundle検査、公開catalog、runtime解決、Webの契約まで同時に拡張する。未知の実行方式は拒否する。

新しいbindingは、専門担当のpackage、登録adapter、利用可能な操作、対象を読むquery、Artifact、継続対話の可用性を宣言する。会話側へ公開するcardにも対応可否を載せる。packageのprofile・Skill・toolsは既存の版固定と依存閉包で取得する。

Undo／Redo・保存・破棄は各domainの登録操作とする。保存はUIの保存ボタン専用にし、専門担当のtoolsには公開しない。通常担当への返却・保留・再開・終了は共通の登録操作とし、担当と画面から同じ契約を使う。専門対話に対応するだけで、外部操作の取消や履歴復元まで提供すると見なさない。

### 4.2 引継ぎと入力先

通常会話LLMが公開されたツールチェーンを選び、hostが対応可否、対象の所有者と存在、公開版を検査して専門対話を開始する。明示的な担当切替UIからも同じ公開操作を呼ぶ。文字列検出で担当を選ばない。

通常担当が受け取る閲覧コンテキストは、hostが発行したArtifact・作品参照と短い表示情報に限る。切替操作に含まれる参照をサーバー側で再検査し、現在表示中という理由だけで任意IDへのアクセスを許可しない。対象が不明な場合はLLMが確認する。

切替通知は「サブエージェントに切り替えます」などの短い表示とする。hostの切替成功を根拠に表示し、失敗したのに担当名だけが変わる状態を作らない。

専門対話中の各発言は、入力受付で宛先を固定し、通常担当の生成・routing・回答書換えを省略して専門担当へ渡す。既存dialogueの受付、queue、進捗、取消、回答採用を再利用する。会話を扱うコードを通ることと、通常会話LLMを呼ぶことを区別する。

### 4.3 管理する最小状態

dialogueが現在の専門対話を所有する。概念上、以下を保持する。

| 情報 | 用途 |
| --- | --- |
| sessionId、conversationId、所有scope | 操作と返答の宛先を固定する |
| toolchain／package／binding／artifactのrevision | 開始時の担当契約を固定する |
| adapterRef、作業参照、保存対象参照 | domainの編集状態へ接続する |
| sessionRevision、epoch、activeRunId | 重複、切替、取消、遅延結果を検査する |
| 開いているArtifactのinstance参照 | 終了対象のタブを識別する。権限の根拠にはしない |
| active／suspended／closing／ended、expiresAt、終了理由 | 入力可否と終了・回収を管理する。期限の正本はdialogueのみ |

会話本文は既存conversation保存を再利用し、必要な担当識別・session参照を付けて編集中の発言を抽出する。作品ごとに別の永続会話を新設しない。再編集には保存成果物と今回の依頼を使い、終了したsessionの履歴復元を前提にしない。通常会話へ戻った後のコンテキストには作業結果の短い記録を残し、UI定義全文を渡さない。

専門担当の一ターンは「返答・質問で待つ」または「登録操作を実行し、その結果を確認して返答する」を扱う。質問・返答の後は推論を終了し、ユーザー待ちをrunningのまま維持しない。確認質問の表示・回答schemaは既存interactionを利用できる部分だけ再利用し、既存の質問数上限を制作全体の対話回数に転用しない。

一ターンの処理には期限・呼出し上限を設ける。初期案は120秒・モデル呼出し最大6回・構造修復最大1回とし、P0の容量確認で確定する。質問待ち時間は含めない。モデルの意味評価を独立した反復工程として追加しない。

### 4.4 会話と音声からの復帰と対象切替

専門担当が呼べる返却操作は、利用者の依頼を根拠に通常担当へ宛先を戻す。利用者が「会話エージェントに戻って」と依頼した場合、未保存案があっても保存・破棄の回答を待たずに戻る。hostは未保存案を `suspended` にし、生成中の処理を取消・失効させる。未保存変更がなければ終了する。Artifactは保留表示で残せる。保留中も明示的な保存・破棄ボタンを利用できるが、AIによる変更は再開成立後に限る。保留中に保存ボタンが成功して未保存変更がなくなった場合は、その作業を終了し、Artifactを保存作品の閲覧表示へ移す。

保留した作業の再開は、通常の切替と同じ公開操作で行う。通常担当が同じ対象への編集を依頼した場合や、利用者が保留表示の「編集を再開」を押した場合に、hostは保留中の作業と対象・所有scope・期限を照合する。一致すれば新しい作業を作らずに `active` へ戻し、epochを進める。保留中の作業は会話ごとに一つなので、同じ対象への新規編集を二重に開始しない。対象が異なる場合は下記の `needs_resolution` に従う。保留表示のArtifactを閉じる操作は、未保存時のタブ閉鎖と同じ確認に従い、確認なしに破棄しない。

専門担当の範囲外の依頼を受けた場合も、LLMがその意味を判断して返却操作を選べる。hostは元発言の参照と未処理の依頼を保存し、復帰成功後に通常担当へ一度だけ配送する。復帰命令だけなら新たな通常担当の推論を開始しない。別の依頼を伴うときだけ実行し、同じ発言の再送で二重実行しない。発言の語句で分岐する処理は追加しない。

「やめる」のように生成停止・破棄・担当復帰のどれかが曖昧な場合は、進行中処理を止めて現在案を維持し、専門担当が必要な確認を一度行う。明確な破棄依頼なら保存せず破棄して戻る。音声も同じ確認・返却・取消操作を使い、画面のタブを操作できないことを退出の阻害要因にしない。

別作品・別担当への切替要求をhostが受けたとき、既存の未保存作業があれば `needs_resolution` と現在の作業参照・版・選べる操作を返す。新しい担当はまだ起動せず、対象を変更しない。現在応答する担当が、その応答に基づき「破棄して切り替える／現在の編集を続ける」を確認する。保存したい場合は保存ボタンを案内する。音声の明確な選択も同じ操作へ渡す。保存ボタンの成功または破棄の確認後に、保留した切替要求を一度だけ再検査・実行する。確認後に作業の版が変わっていれば再確認し、古い選択で新しい案を捨てない。

### 4.5 期限と終了の所有者

期限の正本はdialogueの `expiresAt` に一本化する。初期案の無操作24時間はこの期限を指し、ui-compositionsには独立した期限判定・自動破棄timerを持たせない。その作業への利用者の発言受付、採用された明示編集操作、保留からの再開で期限を更新する。poll、表示切替、LLMの途中出力、保留中の通常会話は延長理由にしない。既に期限切れの作業を新しい発言で延命せず、各ターンの実行期限もsession期限を超えない。

applicationの既存[lifecycle機構](../api/application/server-lifecycles.ts)に定期回収を登録する。dialogueの公開操作で期限切れと回収待ちの候補を列挙し、applicationが同じwriter transactionで「所有domainの破棄、jobの失効、dialogueの終了、宛先の復帰」を行う。取得・入力・結果採用の各入口でも現在時刻と期限を検査するため、定期回収の実行前でも期限切れの案は更新・保存・採用できない。初期の回収間隔は60秒を候補としてP0で確定し、ブラウザ接続がなくても実行する。起動時も同じ終了処理を使い、通常運転中の回収と別の破棄実装を作らない。

所有domainの破棄に失敗したらtransaction全体をrollbackし、domain側だけ残したまま `ended` にしない。失敗を安全な分類で記録し、別transactionで `closing` と回収待ちを記録して操作を閉じる。期限切れ・権限失効時はこの記録にも失敗しても入口のguardが利用を拒否する。次の定期回収で同じ冪等な終了操作を再試行する。回収失敗を完了扱いせず、重複実行を防ぎ、繰り返す失敗は監視可能な状態で残す。外部processの停止はcommit後に行い、停止が遅れても失効済みの結果を採用しない。

| 現在状態 | 契機 | 成功後 | 失敗・待機時 |
| --- | --- | --- | --- |
| なし | 専門対話の開始 | active、対象とepochを確定 | 通常担当のまま。半端な作業を残さない |
| active | 生成・編集・保存ボタン | active、確定した版だけ更新 | 現在案を維持し失敗を表示。通常担当へ勝手に戻さない |
| active | 通常担当への返却 | dirtyならsuspended、cleanならended | 宛先と作業を一体でrollbackし、切替成功と表示しない |
| suspended | 同じ作業の再開 | active、新epoch | 期限・権限・対象不一致を拒否し、現在案を上書きしない |
| suspended | 保存ボタン | ended、作業削除、保存作品の閲覧表示 | suspendedを維持し失敗を表示。下書きは残す |
| active／suspended | 別対象の編集要求 | cleanなら終了と新対象開始 | dirtyならneeds_resolution。確認は状態の付随情報として保持 |
| active／suspended | 明示破棄・clean状態で閉じる | ended、通常担当、作業削除 | closing、操作停止、回収待ち。保存作品は維持 |
| active／suspended | 期限切れ・再起動・権限失効 | ended、理由を保持、作業削除 | closingまたは期限guardによる拒否、回収を再試行 |
| closing | 定期回収 | ended | closingを維持し失敗を記録 |
| ended | 同じ終了操作の再送 | 元のreceiptを返す | 新しい入力・生成結果・再開は拒否 |

### 4.6 通常文脈とWorldとMemoryからの分離

専門担当に渡す情報は、今回の依頼、編集中の会話、現在の成果物、利用者が指定した資料、登録された担当指示・操作とhostの作業状態に限定する。World／Memoryの参照ツール・更新ツールを公開せず、長期記憶、作業要約、recall、Worldの候補提示、記憶由来の追加文脈も合成しない。

会話表示用の保存と、通常担当の文脈・自動学習への利用を分ける。dialogueが受理時に専門対話のmetadataを確定し、conversationが保持する。通常担当の[context compiler](../api/domains/dialogue/service/context-compiler.ts)、routing用履歴、topicTexts、要約・recallの入口では、専門対話の生発言を対象外にする。memoryが無効な場合の直近履歴fallbackも同じ条件を使う。専門対話が大量にあるため直前の通常会話が履歴枠から押し出されないよう、対象を絞ってから件数・容量制限を適用する。

dialogueのrun終了処理から専門対話をMemoryのexchangeへ登録せず、World／Memoryの自動抽出・要約・索引化の対象にしない。conversationの変更outboxを参照するWorld側も、公開されたmetadataで対象を除外し、変更一覧と本文の直接参照の両方を検査する。除外イベントを読み飛ばしてもcursorを進める。既存の `scheduled_prompt` や「忘却」の意味へ便宜的に置き換えず、取り込み可否の明示的な契約を追加する。既存の通常会話の参照・学習方針は変えない。

通常担当へ戻す短い作業記録は、対象参照、保存／破棄／保留の状態、確定receiptを含む引継ぎデータとしてdialogueが渡す。UI定義や制作の全文は含めず、World／Memoryへ自動登録しない。範囲外依頼を返却する際は、元発言に紐づく未処理の依頼だけを通常ターンとして扱い、専門対話全体を再分類しない。配送したその発言は、以後の通常文脈・自動取り込みでは通常会話の発言として扱う。この配送記録はdialogueが確定し、同じ発言の再送では再配送しない。

## 5 UI自由制作の作業状態と保存

### 5.1 保存作品と一時作業の分離

`ui-compositions` が保存作品と編集中のUIを所有する。保存作品は従来の作品IDを維持し、title、現在の表示定義、フォーム定義、保存revisionを正本とする。新規作品は最初の明示保存で作品一覧へ加える。

編集中だけ、基準となる保存revision、現在案、Undo／Redoのsnapshot列とcursor、draftRevision、generation、進行中のjobを一時作業領域に保持する。暫定実装方針はbackendのSQLiteを正本とし、WebはAPIから投影する。transactionと世代検査を既存の単一writerに揃えるためであり、途中案の永続アーカイブは提供しない。

保存時はUndo／Redo列を新しい確定状態にまとめる。終了・破棄時は一時案とsnapshot列を削除し、再送・遅延結果を拒否するための最小receiptと失効情報だけを既存の保持方針に沿って残す。ページ再読込みは有効な作業状態を再取得できる。初期版ではbackend再起動をまたぐ編集復元は提供せず、起動時に旧作業を失効・回収して保存作品から再開する。通常の再読込みとbackend再起動を混同しない。

一時領域の件数・合計bytesはP0で定める。初期案はUndo対象50変更。無操作期限は§4.5のdialogueの期限に従う。表示定義には既存の16 KiB制限を維持し、フォーム・会話・snapshot全体の上限は別に検査する。容量超過時は現在案を保持し、制限を表示する。黙ってUndo履歴を削らない。SQLiteへの一時書込みは確定保存ではなく、保存作品一覧には出さない。

### 5.2 UndoとRedo

- 検証と採用が成功した一回のAI変更を一単位とする。初稿は空の案にUndoできる。タイトルも画面全体と同じsnapshotに含める。
- 利用者がタイトル変更を依頼した場合も通常の下書き変更として扱い、Undo／Redoの対象にする。
- 部分修正も全面変更もsnapshot単位で戻す。失敗・取消・説明だけの応答ではUndo列を増やさない。
- Undo後に新しい変更を採用するとRedo側を破棄する。新しい変更が失敗した場合はRedo側を保持する。
- Undo／RedoはLLMを呼ばず、登録されたdomain操作として処理する。フォームの回答入力と、設計を戻す操作は分離する。
- 「生成中」は、専門担当のターンの受付から終了まで（`activeRunId` がある間）を指す。「下書きへ反映」操作を呼ぶ前の推論中も含める。担当が読んだ現在案と反映時点の案がずれないようにするため。
- queuedを含む生成中はUndo／RedoのボタンをDisabledにする。会話・音声・APIからの要求もhostが `generation_in_progress` で拒否し、生成取消を兼ねさせない。先に明示的な生成停止を確定するか、生成が終わってから実行する。拒否ではcursor・generation・現在案を変えない。開始とUndoが競合した場合は同じwriter内で状態を再検査する。
- Undo／Redo、新しい変更指示、破棄ではgenerationを進める。古い生成結果の採用には、sessionのepoch、draftRevision、generation、receiptの全てが一致することを要求する。
- 次の担当入力にはUndo後の現在案を渡す。会話中に残る過去の「変更しました」を現在の画面より優先しない。

### 5.3 保存と終了

保存は利用者の保存ボタン操作だけで受け付ける。生成成功、担当復帰、タブ閉鎖、期限切れ、AIの保存宣言では保存しない。会話で保存を求められた場合も保存ボタンを案内し、LLM用toolsには保存操作を出さない。hostもUI actionのoriginと登録された保存actionを検査し、会話originの保存を拒否する。

保存は `{requestId, sessionId, expectedDraftRevision, expectedSavedRevision}` に相当する契約で、hostに保持した現在案を確定する。クライアントから送られた完成JSONをそのまま正本として保存しない。

同じ操作の再送は既存receiptを返し、同じIDで異なる入力を拒否する。他タブ等が保存作品を更新していた場合は競合を返して下書きを残す。自動上書き・自動再送はしない。保存の成否不明は照会で確定する。

生成中は保存操作を無効にし、完了または取消後の現在案を保存する。保存処理中は新たな編集を受け付けず、成功後に基準revisionとUndo列を更新する。

保存と閉じるは独立した操作にする。保存ボタンの成功後、未保存変更がない状態で閉じると、application層の一つのwriter transaction内でdomainの一時作業終了とdialogueの終了公開操作を呼ぶ。保存に失敗したら下書きを残し、閉じる処理を続けない。終了確認後にWebがタブを閉じ、通常担当へ戻す。タブ閉鎖前に通信が切れても、再取得した終了状態から表示を一致させる。

破棄ボタンは常設し、生成中も利用できる。明示破棄では生成を失効させ、一時案・Undo列を削除して通常担当へ戻す。新規の試作なら作品を一件も保存せず終了し、既存作品の編集中なら保存版を維持する。保存transaction処理中だけは破棄を無効にし、保存の成否不明時もreceipt照会で結果を確定してから破棄を受け付ける。

## 6 専門担当の指示と画面表現

UI制作担当には、役割、初稿を出す方針、修正対象を現在案から読むこと、明示条件を維持すること、必要な場合だけ質問すること、保存とプレビュー更新の区別をprofile／Skillへ記載する。元依頼、会話、現在案、参照画像は入力データとして分離する。画像中の文を命令として扱わない。

通常担当への復帰依頼、担当範囲外の依頼、取消と破棄の区別、未保存の別対象切替を共通Skillへ記載する。保存操作は選択肢としてモデルへ公開せず、World／Memoryも利用可能情報に含めない。

担当が現在案を読んで構成を生成し、登録された「下書きへ反映」操作へ提出する経路にする。旧 `ui.compose.request` を呼んで別の一回生成担当へ依頼し直す構成は採用しない。候補はhostでschema・参照・世代を検査してから反映し、返答は保存・反映receiptに基づかせる。途中の説明文や未検証JSONを操作として実行しない。

初期版の更新方式は、安定した項目IDを保持した完全な構成案の置換とする。LLMが変更箇所を判断し、hostは形式を検査する。JSON Patch等の独自編集言語は追加しない。部分修正で不要な箇所が変わらないことは実モデル受入で確認する。

生成できる構成は既存のDesignSystem・OpenUIから広げる。UI制作向けに許可する部品だけのcatalogを渡し、設定・認証・端末等の登録viewを自由に配置できる権限は与えない。

初期版で必要な表現は、見出し・説明、情報カード、Radioを含むフォーム、セクションごとのまとまり、余白・幅・文字の強弱・配色の登録トークン、狭幅時の配置。既存layoutが子layoutを許さない点も含め、P0で表現例を契約化する。必要な場合は深さ・ノード数を制限した構成へ拡張し、既存viewの意味を変更しない。任意HTML／CSS／JavaScript、任意URL、任意API呼出しは生成定義へ持たせない。

プレビュー内のフォーム操作は試用として扱い、編集中の回答を保存作品の回答へ記録しない。既存の保存作品に対する回答送信契約は維持し、保存revisionと項目の整合を引き続き検査する。設計のUndoで実際の回答送信を取り消すことはしない。

## 7 モデル接続

初期版は保存済み `subagent.resourceId` の選択を利用し、未指定時は既存のサブエージェント経路に従う。実際の生成まで同じ選択を使い、旧maintenance controlのLARM固定に戻さない。

dialogueで受理した各ターンの認可・期限を根に、既存 `captureControlInTransaction` のrouteと推論receipt検査を利用する。開始・返答・更新が同じ根の権限下にあることを確認する。作品保存はLLMの完了文ではなく保存操作のreceiptで判断する。

会話履歴と成果物はEumenes側を正本とする。Provider固有のsession継続は最適化として扱い、対応していない接続でも現在案と編集中の必要な文脈を再提示して動くようにする。モデル変更は次のターンから適用し、実行中のモデルは変更しない。Providerのsessionは切り離し、製品の作業参照は維持する。

モデル名・profile名をコード、条件分岐、既定値、ファイル名へ固定しない。利用不可や画像入力非対応は明示し、別モデルへの無断変更で成功扱いしない。既存のcontrol出力上限で構成案が収まるか測定し、不足する場合だけ担当単位の上限指定を共通推論へ追加する。全機能の上限を一律に引き上げない。

P0では小さな初稿、代表的な部分修正、16 KiB境界に近い構成について、指示・会話・現在案を含む入力量、フォーム等を含む出力量、実行時間、未指定箇所の維持を測る。bytesをtoken数と同一視しない。出力枠だけが不足するなら測定を根拠に担当単位の上限を追加し、時間超過や意図しない改変が残るなら単純な上限増加で解決扱いにしない。必要な代表画面を維持できる範囲で生成用schemaの冗長さ・容量上限を見直し、保存済み作品の読取り上限を下げない。要件を保てない場合はP0未完了として更新方式の再設計を提案する。要件や試験期待値を下げて通さず、独自差分言語も無断で追加しない。

## 8 Artifactと会話画面

UI自由制作のArtifactは、現在のプレビューをメインコンテンツとし、生成したUIを見て操作できる領域を中心にする。AIが付けたタイトル、作品履歴への入口、保存、常設の破棄、通常会話へ戻る操作、Undo／Redo、必要な進捗・失敗表示はその周囲にコンパクトに配置する。従来の「作る／プレビュー」というタブ切替、制作条件フォーム、デモの一回生成ボタン、編集画面へ戻る操作は廃止する。プレビュー自体は維持する。

生成中は保存・Undo・RedoをDisabledとし、生成停止・破棄・通常担当への復帰を利用できる。保留中は「未保存・一時保留」と期限を表示する。未保存案について「保存ボタンを押すまで作品には保存されません。サーバーの再起動や期限切れで破棄されます」と簡潔に案内する。再接続で失効が判明した場合は、通常担当へ戻り、未保存案の破棄と保存版が残っていることを表示する。単なるページ再読込みを再起動と扱わない。

既存のデスクトップ／モバイル切替をプレビューの表示操作として残す。同じUI定義を表示幅に応じて確認する機能とし、切替のたびに生成・保存・担当変更は行わない。表示モードの変更は作品の編集やUndo／Redoの一単位に数えず、未保存状態と試用中のフォーム入力を維持する。編集中の更新やUndo／Redoでも選択中の表示モードを維持する。保存作品の閲覧時にも利用でき、狭いArtifact幅でも切替操作と内容へアクセスできるようにする。

履歴は保存作品の一覧とし、制作途中の案・失敗した新規案は掲載しない。既存の作品一覧と認証済みsource取得を再利用する。タイトルと選択操作を中心にし、作品本文や制作条件が一覧を占有しないようにする。

会話欄は現在の担当を常時表示し、切替時にも入力欄・添付・進捗の基本操作を維持する。送信時に会話の宛先epochを固定する。切替直前に入力された発言や添付を、別の作品・別担当へ黙って送らない。古い宛先の送信は再確認できる状態に戻す。

音声入力・読み上げが有効な場合も同じdialogueの宛先と採用検査へ接続する。専門担当の返答を読み上げるために通常担当のLLMを追加で呼ばない。音声実機器の受入はブラウザfixtureと分けて記録する。

### 8.1 OpenUI定義JSONの確認

制作画面の主表示に「プレビュー／ソース」の切替を置く。ソースは、プレビューが表示しているものと同じ検証済みOpenUI定義JSON（編集中は採用済みの現在案、閲覧中はその保存版）を整形して読取専用で示し、「編集中／保存済み」とrevisionを併記する。切替は表示状態だけで、生成・保存・Undo履歴・担当を変えず、更新やUndo／Redoをまたいで維持する。未採用のモデル出力やコンパイル後のOpenUI Langは表示しない。JSONの直接編集・再投入は対象外。確認のためのLLM呼出しや別の取得は行わず、制作画面のsourceの定義を使う。

当初の別Artifact（`artifact:ui.definition@1`）方式は、試用で開けなかったことと切替の方が自然との指示により廃止した。登録済みの旧revisionはDBに残り、launcherを持たないため表示されない。

保存作品の閲覧中は「新規作成」を表示し、閲覧を解除して編集中の案、無ければ空の状態へ戻す。

| dialogue | 担当切替・返却・保留・再開の公開操作、唯一の期限と終了状態、専門ターン、直接返答、通常文脈・routing・topicTextsとMemory exchangeへの混入防止 |

| inference | 保存済み担当経路の利用。必要な場合のみ出力予算・Provider session接続の拡張 |

| ui-compositions | 一時作業、構成案の検証・採用、Undo／Redo、明示保存、一覧、旧生成処理の置換 |
| application | dialogueと所有domainの公開portを接続し、終了・作業破棄・宛先復帰を同じwriter transactionで実行。既存lifecycleで期限切れと回収待ちを処理 |
| artifact-ui／design-system | 制作画面の簡素化、許可された構成表現、編集操作・状態表示、読取専用のOpenUI設定JSON表示 |
| Web workspace／client | 担当表示、入力先、対象作品、閉じる制御、型付きAPI、再取得、プレビュー／ソース切替と新規作成への復帰 |
| voice-dialogue | 同じ宛先への接続確認と、必要な境界修正のみ |

下位domainからdialogueへの参照を追加しない。UI制作は作品の意味と保存を所有し、dialogueは会話相手と発言の配送を所有する。共通層へUI制作専用の語句分岐や保存SQLを持ち込まない。既存Web下書きstoreをそのまま第二の正本にせず、編集状態は所有domainのAPIへ一本化する。

新しいAPI・型・DB列の名前はP0で実コードに合わせて確定する。既存のdialogue送信・進捗・取消APIとtoolchain action APIを優先し、sessionの取得・開始・終了に足りない契約だけを追加する。既存の認証・origin検査を維持する。

## 10 移行と旧方式の廃止

新規migrationは名前付きで依存を宣言する。旧migration、公開済みprofile／Skill／tool／package／binding／Artifactの本文・hashは変更しない。新しい入出力は新schemaとして登録し、旧版も参照するvalidatorを上書きしない。

既存の正常な保存作品はID・タイトル・定義・回答との関係を維持して移行する。過去の失敗・取消行は破壊的に削除せず、新しい保存作品一覧の対象から区別する。旧生成中jobは新版採用前に排出または取消・失効し、旧結果が新しい保存状態を上書きしないようにする。

新revisionを有効化した後は、旧一回生成の公開操作、制作フォーム、デモ、旧生成handlerへの新規投入を無効にする。旧版の読取りとreceipt照会は維持する。旧ジョブの終端を確認してから不要な実行コード・試験fixtureを撤去する。単に古いUIを隠すだけで廃止完了にしない。

移行試験はfresh DB、旧版seed済みDB、既存作品と回答を含むDB、二度目のseedで行う。問題時は新規専門対話を非公開にし、保存作品の読取りを維持する。廃案となった一回生成経路を自動で再公開しない。

## 11 実装順と完了条件

各段階で実装と回帰試験を揃えてから検証する。部分→結合→通し→実モデルの順を守り、前提が未完了な通し試験を繰り返さない。

| 段階 | 必要作業と依存 | 完了条件 |
| --- | --- | --- |
| P0 契約の確定 | 現行試験の基準取得、session binding、公開操作、既定の状態遷移の詳細、容量・期限、構成表現を確定 | 出力・時間・未指定箇所の維持を測定し、予算不足時の対処まで確定。入出力と所有先を推測せず実装できる |
| P1 共通の直接対話 | P0後。登録、切替、専門ターン、直接返答、質問待ち、会話・音声からの返却、期限回収、文脈とWorld／Memoryの分離、client契約 | 別の試験用adapterで複数往復・復帰・回収失敗が通る。通常LLMを毎回呼ばず、World／Memoryを使わない |
| P2 UI制作の編集状態 | P0後。一時作業、snapshot、Undo／Redo、保存競合、構成契約、移行 | 保存作品を変えずに編集でき、保存時だけ確定する。失敗・取消・遅延結果で破壊しない |
| P3 専門担当と画面の接続 | P1・P2後。新版bundle、指示、担当モデル、候補採用、プレビュー主体のArtifact、保存・破棄、表示モード切替、プレビュー／ソース切替、閲覧から再委任 | 初稿→修正→Undo／Redo→保存ボタン→閉じる→履歴→再編集と、未保存破棄・通常担当への返却を固定モデルで通す。両表示モードとソース表示が同じ案を示す |
| P4 移行と回帰 | P3後。旧公開経路・UI・handlerを閉じ、既存作品・非対応toolchain・音声との結合確認 | 旧生成入口が残らず、既存作品を開ける。対象domainと利用側gateが成功 |
| P5 実モデル受入 | P4後。保存済み設定を用いて自然言語の生成・改訂を観測 | 代表依頼と別題材で要件を満たし、モデル・条件・結果をfixtureと分けて記録 |

P0〜P5の必要作業はすべて未着手。今回の完了条件は、この計画書の作成、参照確認、索引への登録までである。

## 12 検証計画

### 12.1 固定試験と結合試験

| 対象 | 必須の確認 |
| --- | --- |
| 登録 | commandとの併存、非対応の拒否、旧revision不変、session参照・schema・adapterの不整合拒否 |
| 直接対話 | 初回引継ぎの依頼が欠けない、専門担当への3往復、説明だけの応答、質問待ち、通常担当の呼出し回数 |
| 対象と権限 | 閲覧作品を正しく引継ぐ、未発行参照や他scopeを拒否、保存中の切替、複数タブの宛先競合 |
| 編集 | 初稿、部分修正、全面変更、タイトル変更、Undo／Redo、Undo後の分岐、説明・失敗時に履歴を増やさない、生成中（反映前の推論中を含む）のボタンDisabledとAPI／会話からの拒否 |
| 採用 | 取消・新指示・Undo・終了・期限・権限失効後に古い結果を採用しない |
| 保存と破棄 | 保存ボタンのorigin限定、AI・会話からの保存拒否、自動保存なし、新規・更新、revision競合、再送と成否不明の照会、未保存の試作を作品追加なしで破棄、保存版は不変 |
| 復帰と切替 | テキスト／音声の「会話エージェントに戻って」、dirtyは保留・cleanは終了、保留からの再開（通常担当経由・再開ボタン）で作業を二重作成しない、保留中の保存成功で終了、保留表示を閉じる時の確認、範囲外依頼の一度だけの配送、別対象でneeds_resolution、確認待ち中の版変更、別Artifact閉鎖は維持 |
| 期限と回収 | 唯一のexpiresAt、通常運転中の回収、pollで期限延長しない、破棄失敗で終了もrollback、closingから冪等再試行、期限直後・再起動後の採用拒否と利用者表示 |
| 文脈と記憶 | 専門担当へのWorld／Memory入力・ツール・更新がない、通常文脈・routing・topicTexts・memory無効時fallbackから専門発言を除外、exchange・outbox取り込みと直接source参照を拒否、除外時cursor前進 |
| 構成 | 未許可view・source・action、過大入力を拒否、狭幅・キーボード・Radio操作、試用と回答保存の分離 |
| プレビュー | メインコンテンツとして表示、デスクトップ／モバイル切替の維持、切替で同じ定義・未保存状態・試用入力を保持、再生成や保存やUndo履歴追加をしない、更新・Undo／Redoでも表示モードを維持、保存作品の閲覧時にも利用可能 |
| ソース表示 | 初期はプレビュー、切替で同じ定義のJSONを表示、現在案・保存版の表示とrevision一致、Undo／Redo・保存への追従、切替で担当や下書きを変えない、閲覧中の新規作成で空の状態または編集中の案へ戻る |
| 移行 | 既存作品・回答の維持、旧生成中の排出、新規一回生成の拒否、seed冪等性 |
| モデル | 保存設定の採用、次ターンのモデル変更、能力不足・接続失敗、Provider sessionなしの継続 |
| 他のツールチェーン | 別の試験用adapterでも同じ共通経路を使える。非対応の既存commandは動作を維持 |

### 12.2 実モデルの受入

少なくとも次の独立した系列を用意する。期待値はモデル入力へ含めない。

1. 4〜5問・Radio中心の簡単なアンケートを初稿で作る。単一選択として操作でき、不要な名前入力や自由記述を足さない。
2. 同じ作品へ「3問目だけ変更」「もっと柔らかい雰囲気」を順に依頼する。変更対象と維持条件を確認し、Undo／Redoで画面・タイトル・項目が戻ることを確認する。
3. 同じ編集から全面的な作り直しを依頼する。別作品へ勝手に保存せず、保存するまでは旧保存作品を保つ。
4. 保存して閉じ、通常会話に戻る。履歴から作品を閲覧し、修正依頼で対象を正しく引き継ぐ。以前の制作会話を復元せず続けられる。
5. 別題材の案内画面・情報カードを作り、アンケート専用分岐なしで構成できることを確認する。
6. 制作中に通常担当へ戻るよう依頼し、未保存案を一時保留して復帰する。別の話題を伴う場合は通常担当へ一度だけ届くこと、専門担当がWorld／Memoryを使わないことを観測する。
7. 思いつきの新規UIを作って破棄する。保存ボタンを押さなければ作品一覧に追加されない。音声でも通常担当への復帰と明確な破棄ができ、音声の保存依頼だけでは保存しない。

同じ目的の試行は3ラウンドで俯瞰評価し、新しい証拠がない反復を止める。モデル能力不足と、構成定義で表現できない問題と、接続・採用失敗を区別する。固定モデルの成功だけで自然言語理解の受入完了としない。モデルを変えて比較する場合は別条件の結果として記録する。

実モデル検証でサーバー起動・停止・再起動が必要なら、実施前に明示許可を得る。保存済みLARM設定はbackendのsettings公開読取から確認し、製品DB・秘密をコピーしない。設定変更や新モデル契約はこの計画書作成では行わない。実マイク・スピーカーでの担当切替と3往復は独立した実機器受入として扱い、それを通すまで音声対応の完成とは宣言しない。

## 13 完了判定と作業記録

完了にはP0〜P5の条件、段階別検証、旧方式の廃止、最終差分確認が必要。差分では担当外の変更、例の語句・対象への依存、LLMの意味判断を代替する条件分岐が増えていないか確認する。専用処理が必要なら共通機構の不足と根拠を記録する。

検証中は入力となるコード・文書を編集しない。担当外の失敗は証拠と影響を報告し、勝手に修正しない。通常ログには本文・画像・設定・秘密・Provider生応答を出さず、runId、jobId、requestId、session参照、世代、状態、許可されたエラー分類で追跡する。

実施記録には段階、入力条件、変更・登録revision、確認結果、失敗地点、残作業、次の続行条件を残す。実装済み、固定試験済み、実モデル受入済み、実機器受入済みを区別する。サーバーの長時間処理は進捗がある限り経過時間だけで再起動しない。
