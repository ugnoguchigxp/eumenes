# 文字・音声の返答を句ごとに先行合成し、順に再生する

2026-11-15。利用者が「この設計で実装を進めてください」と承認。実装・固定試験は完了。利用者による再起動後、Webの文字入力1件と音声入力の実測で先行合成・順序付き再生を確認した。実環境では再生終了報告の到着待ちなどが残り、遅延改善と実機器3往復の受入は完了扱いにしない。検証記録は [句ごとの先行合成と順番待ち再生](verification/tts-async-clause-playback-2026-11-15.md)。

## 利用者の要求

「句読点まで確定したならその時点で非同期でTTS生成に回す」「再生していなければすぐ再生し、すでに再生していたら終了まで待つ」。対象は利用者確認済みの「文字・音声の両方」。

完了条件は、入力方法にかかわらず、回答全体の確定や前の句の再生完了を合成開始の前提にしないこと。再生は元の文章順に1つずつ行い、取消・失効後の未再生音声を残さないこと。

## 既存機構と観測

- `voice-dialogue/service/respond.ts` は音声入力の返答を `subscribeAnswerStream` で受け取り、`SpeechSentences` で区切って `synthesis.ts` へ渡している。全文採用前に合成する固定試験がある。
- `synthesis.ts` は待機中の本文と生成済み音声を分けて保持し、生成済み音声を最大3件に制限する。再生待ちの間も次の句を合成できる。
- Webの `chunk-player.ts` は公開された音声を先に取得し、`AudioController.play(..., {waitForPrevious:true})` で直前の音声が終わるまで再生を待つ。取得済みの音声を次の音声より先に並べるので、取得完了順では話さない。
- 文字入力の自動読み上げは `automatic.ts` が `run.status === completed` を待ち、`replay.ts` を開始する。backendのspeech claimとreplay本文検査も完成済み回答を前提にしている。表示SSEを早めるだけでは、この待ちはなくならない。
- 抑揚は `delivery/service/index.ts` の既存LLM判断を使う。`inference/service/execute.ts` のTTS実行は既存の1本のレーンであり、句の抑揚判断と合成を含む。別ボイスへの代替や同時TTS要求の増加は行わない。

直近の音声入力run `f49b3c3c-b9f1-4e0d-aa2e-36749a99af97` の1句目は、12:50:38.586にTTS処理を開始し、回答の生成終了12:50:40.895より前に動いていた。抑揚判断は4,606msでtimeoutとなり、音声合成の呼出しは約732ms、最初の音声公開は12:50:44.069だった。全文待ち以外の待ちもあるという証拠であり、TTS本体がすべての遅延の原因とは扱わない。1回の観測を一般的な性能値とはしない。

変更前の固定試験はbackend 4ファイル20件、Web 3ファイル29件が成功。記録は `verification-reports/tts-async-20261115/`。

## 方針

既存の句分割・読み上げ用本文・TTS実行レーン・再生キューを再利用する。文字入力については、完成済み回答のreplayとは別に、実行中の回答に結び付く音声の購読口を追加する。音声入力のレコードを偽造したり、同じ利用者発言を再送して別の回答を作ったりしない。

文字の流れと音の流れは次のように重なる。

1. 現在の生成から「最初の句、」が届く。既存の読み上げ用整形と句分割を行い、すぐ合成待ちへ入れる。
2. LLMが続きの文章を生成する間に、最初の句の抑揚判断・TTSを進める。
3. 最初の音声が用意でき、出力が空いていれば再生する。再生中も次の句を合成・取得する。
4. 次の音声が先に届いても、前の音声の終了を待ってから再生する。
5. 回答終了時は句読点のない末尾を1度だけ処理する。既に読み上げた句を完成済み回答の自動replayで再生しない。

「句が確定」は文章の境界が分かったことを意味し、回答全体の採用完了ではない。生成中に話した音は取り戻せないため、取消後は未再生分を破棄し、すでに再生された区間だけ既存の配達記録の扱いに従う。これは音声入力で既に採用している契約を文字入力にも適用する変更となる。

## 実装範囲

### 共通の句処理

`createSpeechSynthesis` の既存処理から、句分割・待機本文・生成済み最大3件・再生報告・取消・終了待ちを、voice-dialogue内の共通処理として切り出す。TTSの呼出しと採用の検査・保存を呼出し元から渡せる範囲に留め、汎用ジョブ基盤は新設しない。

音声入力は現在のDBのvoice turnと推論のreceiptを引き続き使う。文字入力はrunと生成IDに結び付いた一時的な音声出力を使う。両方とも既存のTTS実行レーンを経由するため、Providerへ送るTTSは1件ずつのまま。音声生成とブラウザー再生は独立して進める。

既存の `SpeechSentences` と `spokenPrefix` を使う。URL・未完のMarkdownリンク・小数など、まだ境界が確定していない箇所は保留する。句の意味、感情、適切な声を語句の辞書や独自分岐で決めない。

### 文字入力の音声購読

voice-dialogueに次の2つの操作を追加する。通常の認証・同じ再生画面の検査を通す。

| 操作 | 役割 |
| --- | --- |
| `POST /api/voice/runs/:runId/speech` | screen IDを受け、対象runの音声を一度だけ確保し、進捗・音声をSSEで購読する |
| `POST /api/voice/runs/:runId/speech/:sessionId/played` | 再生した生成ID・句番号・実際に音を出したかを報告し、生成済みの待機枠を解放する |

音声購読は `subscribeAnswerStream` を使い、本文・生成ID・取消signalをbackendから取得する。ブラウザーから渡された任意の文字列を、未確定回答の正当な本文として扱わない。既存replayの「完成済み回答の句だけを許可する」検査は緩めない。

SSEは開始情報、生成IDの切替、音声の用意完了、生成終了、失敗を通知する。音声は句番号・本文・表示に必要なdeliveryとともに送る。WAVはbase64で搬送し、最大音声サイズを既存の音声上限に合わせる。生成済み最大3件の上限で先読み量を制限する。受領しただけでは再生済みにせず、再生終了の報告で枠を解放する。

生成が終わっても、再生待ちがある間は購読を維持する。すべての句が再生・失敗処理を終えたら閉じる。接続切断、画面の所有権喪失、取消、失敗、期限切れでは購読と待機中の合成を終了する。一時状態はメモリだけに保持し、既存と同程度の件数・寿命上限を設ける。プロセス再起動後に途中音声を自動復元しない。

### 重複・順序・取消

- 文字入力の先行読み上げも、従来と同じ `run:<runId>:answer` の確保を使う。実行中runの確保を許可するのは新しい購読操作だけとし、既存の完成済みreplayへの入口は変えない。
- 音声入力に既に所有されているrun、発話者でない担当、再生する画面でない利用者からの要求は従来どおり拒否する。
- 句の識別はrun・生成ID・句番号で行う。再生成時は旧生成の合成・再生待ち・遅い結果を破棄する。
- Webでは音声の取得・準備と、実際の再生開始を分ける。別の句が再生中でも次の音声を取得できるが、同じ出力から同時に2つの発話を流さない。既存の通知との待合せも維持する。
- 新しい本文のSSE購読は音声側で行い、文字のdeltaごとにworkspace全体を再描画しない。
- 停止・mute・音声入力による中断・画面切替では、再生中だけでなく合成中・取得済み未再生の音声も止める。
- TTS失敗の句を再試行したり別の声へ差し替えたりせず、既存の失敗処理を使う。音声失敗を会話本文の失敗に変えない。

## 今回変更しないこと

LLMによる抑揚の判断方式と時間制限、声の設定、TTSの同時実行上限、モデル・profileの選択、画面の所有権、本文の採用条件、DBスキーマは変更しない。backendやCLIから音を鳴らさない。

抑揚判断の待ちは独立して記録する。この判断を省略する、短時間で打ち切る、別の判断方式に変える場合は、声の振る舞いを変える別の設計判断として扱う。今回の先行合成だけで、Providerや抑揚判断そのものが高速化するとは説明しない。

## 作業順と検証

1. 共通の句処理を切り出し、音声入力の既存試験を維持する。
2. 文字入力の購読・確保・生成の寿命・再生報告を結合する。
3. Webで音声の先読みと順序付き再生を接続し、完成時の二重読み上げを防ぐ。
4. 部分→結合→消音ブラウザーの順で確認する。
5. `bun run verify -- --domain dialogue --domain voice-dialogue --domain audio --domain inference` を実行する。既存の検査阻害が残る場合は、現行ファイルの固定コピーと対象検査の結果を分けて記録する。
6. 実装・試験がすべて揃った後に再起動の許可を確認し、稼働環境への反映と利用者のブラウザーでの受入へ進む。固定試験と実機器の結果を混同しない。

| 観点 | 完了条件 |
| --- | --- |
| 生成開始 | 句読点の前は送らず、句の境界が来た後、回答全体を未完了に保ったままTTS処理が始まる |
| 非同期 | 1句目の再生中に2句目の合成が進む。後続本文の受信も止めない |
| 再生 | 最初の音声は準備・出力条件が揃ったら再生する。2句目は1句目が終わるまで再生しない |
| 順序 | 取得結果が逆順でも文章順に再生し、同時に鳴らさない |
| 末尾 | 最後の句読点なし部分を処理し、完成通知で既に処理した句を重複させない |
| 取消・失敗 | 抑揚判断中、合成中、取得中、再生中の各段階で止め、後から届く旧音声を再生しない |
| 再生成 | 旧生成の未再生分を捨て、新しい生成だけを対象にする |
| 複数画面 | 同じ回答を2画面が生成・再生しない |
| 権限 | 他の画面、別run、別生成、音声入力が所有するrun、未承認本文を受け付けない |
| 記録 | 再生済み報告の到着順が逆でも聞いた順を保ち、未再生分を聞いた扱いにしない |

計測は「句を受け取る→合成処理開始→抑揚判断終了→音声完成→ブラウザー取得→再生開始→終了」を分ける。本文、WAV、設定、認証情報、Providerの生応答を運用ログへ出さない。
