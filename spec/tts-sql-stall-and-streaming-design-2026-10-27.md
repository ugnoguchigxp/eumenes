# TTSの停止原因と本文ストリーミングの変更案

## 状態と目的

2026-10-27。活動表示SQLの修正は実装・固定試験済み。本番DBへの適用と実機器の受入は未実施。本文ストリーミングは、利用者が「その方針で実装してください。LLMの生成途中からTTSに流して、取消時は未再生分を破棄するようにしてください」と合意した方針に従って実装した。検証の状態は末尾に記録する。

利用者からの依頼は、句の間の不自然な待ち時間を調べ、まずEumenesで停止を起こしているSQLを直すこと。その後、LLMの生成文字列をTTSへ直接流すという方向が示された。

## 特定した停止原因と修正

`GET /api/steward/activity?conversationId=main` が、`steward/repository/activity.ts` の `lastClosedUnits` を呼ぶ。このSQLはslotごとの最後の終了unitと、そのjobの判定を取得する。従来の索引では会話全体の履歴を相関副問合せで繰り返し検索し、並べ替えていた。

これは活動表示用のSQLだが、backendのメインスレッドを同期的に占有するため、同じプロセスの音声応答や他のHTTP処理も待たせる。Webの活動表示は共通の更新通知に伴って再取得される。

既存の[活動表示設計](memory-activity-indicator-design-2026-10-25.md)の結果と判断方式を保ち、次の索引だけを追加した。SQL本文、LLM指示、TTSの方式は変更していない。

- `steward_decision(conversation_id, job_id)`
- `steward_unit(conversation_id, slot, closed_at)`。終了したunitだけを含む部分索引。

登録は `steward/0006-activity-indexes`。既存の `0005-drop-episode` がunit表を再作成するため、その後に適用する。さらに試したstep用索引には改善が見られず、採用しなかった。

## 変更前の本文ストリーミング

`dialogue/service/generation-stream.ts` の `createAnswerStream` はLLMのdeltaを受け取るが、最初のdeltaの計測と出力量の検査だけを行い、本文を公開しない。`dialogue/service/progress.ts` は回答の採用transactionが終わった後にDBから本文を取り出す。従って、現在はLLM生成とTTS合成を本文について重ねられない。

一方、`voice-dialogue/service/synthesis.ts` の合成待ち本文と生成済み音声は、すでにメモリ上の配列とMapで運ばれている。SQLをメッセージキューとして追加する必要はない。推論の追跡、設定、取消、回答履歴の保存に使うSQLとは役割が異なる。

## 合意した変更方針

LLMから受け取った回答本文のdeltaを、生成attemptの寿命に結びついたメモリ上の購読へ渡し、既存のTTS入力処理へ直結する。本文をSQLへ保存して読み直すことと、回答全文の完成を、合成開始の前提にしない。

1. `createAnswerStream` から生成attemptを識別できる本文deltaを通知する。ツール呼出し・内部推論・別attemptの本文を混ぜない。通常の履歴公開は既存の採用transactionで行う。
2. voice側はその通知を既存の `SpeechSentences` と `createSpeech` へ渡す。トークン1個ごとに別のTTS要求を送るのではなく、現在の合成APIが受け取れる単位にまとめる。表情判定など既存のLLM判断はこの変更だけでは除去しない。
3. 既存の取消とstale判定で、そのattemptの購読・合成・未再生音声を終了する。取消後の遅い結果は公開しない。生成中にすでに再生された音声は取り戻せないため、「回答全文が採用されるまで発声しない」という現行方針は変更になる。中断した本文を別attemptの続きとして使わない。
4. 完了時は既存の採用結果と送信済み本文の一致を確認し、末尾をflushする。接続の再開時に生成途中の本文をDBから復元して再生しない。

この提案は全文の採用待ちをなくす。句ごとの合成時間が音声の再生時間を上回る問題は別に測定する。LLMの文字列を逐次渡すことだけで、LARMが一つの要求へ文字列を追送できるとは扱わない。

## 実装後の完了条件とLARMへの確認範囲

- 部分：deltaの順序と本文の保持、attemptの分離、末尾flush、取消、遅い結果の破棄、完了時の重複防止を試験する。
- 結合：最初の本文区間が届いた時点で、LLMの生成完了前にTTS要求が始まることを確認する。取消されたattemptの未再生音声を公開しない。
- 通し：サーバー操作の許可がある状態で、同じ発話による修正前後の最初の音声までの時間と句間の無音を比較する。実機器で3往復確認するまで受入完了とはしない。
- LARMへの確認事項：発見済みTTSサービスが単発の全文入力とWAV応答だけでなく、文字列の追加入力・音声の逐次出力・取消をどの契約で提供するか。逐次出力があっても文字列の追加入力とは区別する。Eumenesの活動表示SQLの修正にLARMの変更は不要。

## 本文ストリーミングの実装

`dialogue/service/answer-streams.ts` のメモリ上の通知を、既存のgeneration handlerとprogressの寿命管理へ接続した。生成ごとに識別子と取消signalを持ち、現在の本文prefixだけを保持する。deltaの通知処理にSQLはない。SSEと保存済み履歴は従来どおり採用済み本文だけを公開する。音声会話のresponderは別のbackend購読から本文を受け、既存の句分割・表情判定・合成を生成中に開始する。

取消・参照情報の失効・生成失敗ではsignalを合成処理へ伝え、待機本文と未再生音声をその場で消す。遅い音声結果も公開しない。生成の置換では旧signalを失効させ、別の生成の本文を継ぎ足さない。生成完了時は送信済み本文とのprefix整合を確認して末尾をflushし、合成を重複しない。生成完了前に全区間が再生済みの場合も、採用後に既存の「聞いた」記録を確定する。

既存の引継ぎ案内は、すでに流した前置きの後へ追加してから再生確認を待つ。案内を本文の前へ差し込んだり、前置きの再生だけで引継ぎを始めたりしない。LARMへの合成要求は引き続き句単位で、文字列追加入力APIの導入ではない。通常の読み上げの語句・意味判断を専用分岐へ移していない。

## コードレビューと改善（2026-10-27）

利用者の「コードレビューをしてください。改善点がなくなるまで改善してください」に従い、今回のSQL索引と本文ストリーミングの差分、取消・再生記録・購読解除をレビューした。次の8件を再現して修正した。業務の意味判断やLLM指示、新しいフォールバックは追加していない。

| 指摘 | 再現した問題 | 修正 |
| --- | --- | --- |
| 取消と再生報告の競合 | 先に書込み予約された再生報告があっても「聞いていない」と記録された | 音声状態の参照を保持し、取消の書込み確定後に再生済み部分を読む |
| 最後の再生報告と取消の競合 | 再生完了が先に確定しても、その後に部分再生の記録が追加された | 取消の更新が成功した場合だけ取消の配達記録を書く |
| 再生報告の到着順 | 非同期の報告が逆順に届くと、聞いた本文が逆順になった | 再生済み区間にindexを保持して音声の順で記録する |
| 保存失敗後の再報告 | SQL文・COMMITの失敗後もメモリ上から音声が消え、再報告で完了できなかった | transactionの確定後にだけメモリ上のキューを進める |
| 生成開始時の文脈読取り失敗 | 初期化の例外が通知側に吸収され、音声の失敗として扱われなかった | 初期化を音声側の例外処理に含め、合成と未再生分を終了する |
| 購読の二重解除 | 古い解除関数を再度呼ぶと新しい購読まで消えた | 解除対象の購読集合が現在のものと一致する場合だけ取り除く |
| 初回通知の例外 | 初回通知で例外になると解除関数を返せず、購読が残った | 初回通知に失敗した購読を除去してから例外を伝える |
| 取消後の遅い通信エラー | 音声取得や再生報告の遅いエラーが、後から始めた再生を止め得た | その再生キューが現在も有効な場合だけエラーを通知する |
