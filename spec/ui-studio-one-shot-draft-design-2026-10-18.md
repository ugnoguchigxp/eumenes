# UI自由制作 一回推論の下書きと定義の補正 設計

作成日: 2026-10-18

状態: 設計案・合意待ち。要合意事項はS1〜S6（§6）。

関連: [専門担当との対話編集](toolchain-specialist-dialogue-implementation-plan-2026-10-17.md)、[表現力拡張](ui-studio-expressive-parts-implementation-plan-2026-10-17.md)

## 1 背景と目的

2026-10-18の実機確認では、次の経過で失敗した。

- 依頼: 「若者向けの運動会のランディングページ」を音声で依頼した。
- 専門担当のモデルが定義を書いた。1回の推論に約50秒かかった。
- 定義は2回続けて検証で拒否された（`ui_definition_invalid`）。
- 3回目の推論の途中で、専門担当の1ターン全体の上限（120秒）に達し、`specialist_turn_timeout`で終わった。
- 利用者からは、LLMが2分以上応答しないように見えた。

現在の方式では、反映が拒否されると、理由を専門担当へ返して作り直させる（最大6回のモデル呼出し）。反映に成功しても、利用者への返答を書くためにもう1回推論する。1回の推論が長いローカルモデルでは、作り直しが重なると応答が無いように見え、上限にも達する。

利用者の方針（2026-10-18）:

- 初稿は1回の推論で作る。
- 定義の小さな誤りは、ホストが補正（fixer）してから検証する。
- 補正しても検証を通らなければ「表示できない」と伝えて終える。通れば、その版を画面に反映する。
- 自動の作り直しはしない。直すのは利用者との対話（二人三脚）で行うと割り切る。

## 2 現行の仕組み

| 段 | 現行 | 根拠 |
| --- | --- | --- |
| 出力の文法 | 専門担当の出力（行動のJSON）全体に、`jsonrepair`による一度の文法修復をかける。修復で中身の並びが変わるものは拒否する | `api/infrastructure/llm-json.ts` |
| 出力の契約 | 行動の形が契約に合わないと、1回だけ修正のための推論（repair）を行う | `dialogue/service/specialist-turn.ts` |
| 定義の検証 | `validatedDefinition`で厳密に検証する（部品の許可リスト、サイズ、schema、意味の検証）。補正はしない | `ui-compositions/contracts` |
| 拒否後 | 理由（位置と規則名）を専門担当へ返し、次の推論で作り直させる | `specialist-turn.ts`の`invoke` |
| 返答 | 反映結果を受けて、もう1回の推論で返答を書く | 同上 |

## 3 新しい流れ（UI自由制作の下書き反映）

1. 専門担当は、1回の推論で`ui.draft.apply`を呼ぶ。引数は次の3つ。
   - `title`
   - `definition`
   - `reply`（新設。利用者に伝える短い一言。置いた仮定など。200字まで）
2. ホストが`definition`を補正する（§4）。
3. ホストが補正後の定義を、従来どおり厳密に検証する。
4. 検証を通れば、下書きに反映してターンを終える。
   - 返答は`reply`を使う。`reply`が無ければ「〈タイトル〉を下書きに反映しました。」。
   - 補正で部品を省いた場合は、「表示できない部分を省きました。」を一文添える。
   - 返答のための2回目の推論はしない。
5. 補正しても通らなければ、画面（プレビュー）には反映せずにターンを終える。
   - 返答は固定文。「画面に表示できませんでした。作った案はソースで確認できます。」
   - 作り直しの推論はしない。
   - 拒否の手がかり（位置と規則名）はログの`repairHint`に残す（記録済み）。
   - 作った案のJSONは捨てずに出力する（§3.2）。

### 3.2 反映できなかった案の出力

反映できなかった案も、JSONとして利用者に見せる（2026-10-18の利用者の指示）。

- 作品（work）に「直近の反映できなかった案」を1件だけ持つ。中身は次の5つ。
  - タイトル
  - 補正後の定義のJSON（整形済み）
  - 補正の記録（`fixes`）
  - 検証の指摘（位置と規則名の一覧）
  - 作った時刻
- 次の反映が成功したら消す。作品を保存・破棄しても消す。サイズの上限は64 KiB。
- 下書きの版（Undo・Redoの履歴）には入れない。プレビューは直前の成功した版のまま。
- 制作画面の「ソース」表示に、「反映できなかった案」として整形JSONと検証の指摘を並べて出す。プレビューには出さない。
- 扱いの選択肢は要合意事項S6で議論する。

質問への回答や、作業を返して通常担当へ戻る行動は従来どおり。初稿に限らず、修正の依頼でも同じ流れになる（各依頼につき1回の推論で反映する）。

### 3.1 共通機構への入れ方

専門担当の対話は、UI自由制作以外のツールチェーンも使う共通機構。UIのためだけに分岐を足さない。

- adapterの操作結果に、任意の`endTurn: { reply: string }`を加える。返ったら、専門担当のターンはその返答で終える（次の推論をしない）。
- 操作が拒否されたときも、adapterがエラーの代わりに`endTurn`（固定文）を返せる。返したら同じく終える。
- `endTurn`を返さない操作は、従来どおり結果を次の推論へ渡す。

UI自由制作のadapterは、`ui-compositions.draft.apply`で常に`endTurn`を返す。undo・redo・保存などの画面操作は変えない。

## 4 定義の補正（fixer）

artifact-uiに`composition-fixer.ts`を置き、`@eumenes/artifact-ui/composition-checks`から公開する。出力は`fixDefinition(raw) → { definition, fixes: FixCode[] }`。

原則:

- 決定的で、同じ入力からは同じ結果を出す。
- 内容を創作しない。直せないものは捨てる。
- 何をしたかを`fixes`に残す。
- 補正の後は、必ず従来どおりの厳密な検証を通す。fixerは検証の代わりではない。

| 分類 | 補正 |
| --- | --- |
| 文法 | `definition`がJSON文字列で渡された場合は、既存の`decodeLlmJson`（`jsonrepair`込み）で読む。外側の` ```json `や前後の説明は既存どおり外す |
| 外形 | 一番外側がlayoutでない部品、または部品の配列なら、縦並びのlayoutで包む。`{"definition": …}`のような二重包みは中身を取り出す |
| 余分な項目 | `source`と、設定画面専用の項目（`tabs`の配列・`headerChildren`・`draftSource`・`headerLayout`）を消す。各部品のschemaに無い項目を消す |
| 部品名 | よくある別名を正規の名前に直す（`heading`・`title`・`text`・`paragraph` → `text-block`、`card` → `info-card`、`img` → `image`など）。表を持って限定する。それ以外の未知の部品はその部品を捨てる |
| 文字数・件数 | 上限を超える文字列は末尾を切って「…」を付ける。配列の件数（childrenは48、選択肢など）は上限で切る |
| 列挙値 | 許されない値は、任意項目なら消す。必須項目は既定値にする（`direction`はstack、グラフの`kind`はbarなど） |
| 画像 | URLの指定、目録に無いテーマ、不正なseedは、`placeholder`（neutral、altは保持）に置き換える |
| 状態 | 入れ子のlayoutにある`model`は、名前が衝突しなければ一番外側へ移す。入力部品の`bind`先が無ければ、型に合う状態を既定値で足す（numberは0とviewのmin・max、textは空、booleanはfalse） |
| 式 | 構文が壊れた式や、未知の名前・関数を使う式は直せない。その式を持つ部品を捨てる |
| 上限 | `form`は2つ目以降を捨てる。6階層を超えるlayoutは中身を親へ上げる。240部品・96 KiBを超える分は末尾の部品から捨てる |
| 空になった | 捨てた結果、表示できる部品が残らなければ補正の失敗とする |

補正後の定義は、整形して保存・表示する（キーの順序をschemaの順に揃え、ソース表示ではインデント2の整形JSON）。開発者向けに、JSONファイルを補正・検証・整形して表示するスクリプト`scripts/ui-definition-fix.ts`も用意する（補正内容と検証結果を出す）。

## 5 SKILLと契約の変更

- `uiDraftApply`に`reply`（任意、200字）を加える。
- SKILLを改める。
  - 「反映は1回で決める。失敗したら作り直さず、ホストが利用者へ伝える」。
  - 「`reply`に、置いた仮定と作ったものを短く書く」。
  - 「反映が失敗したら同じターンで再提出（二度まで）」の規則を消す。
  - 版を上げる（skill@6、package@6、toolchain@8）。
- 初稿の大きさは制限しない（2026-10-18の利用者の指示で、出力は24kトークン、定義は96 KiBまで緩和済み）。

## 6 要合意事項

| ID | 論点 | 推奨 |
| --- | --- | --- |
| S1 | 行動のJSON自体が契約に合わない（下書き以前に、行動の形が読めない）ときの修正推論（repair）を残すか | 残さない。文法修復（`jsonrepair`）でも読めなければ、§3の5と同じ固定文で終える。1回の推論で終わることを優先する |
| S2 | 補正で部品を捨てたことを返答で伝えるか | 伝える。一文だけ（§3の4） |
| S3 | 共通機構への入れ方 | §3.1の`endTurn`。UI専用の分岐は作らない |
| S4 | 時間の上限 | 変えない。1回の推論で終わるので、1ターン120秒・run 3分に収まる見込み。収まらない実測が出たら別途 |
| S5 | 初稿の大きさの目安 | 決定済み：目安を設けない（出力24kトークン・定義96 KiBまで緩和） |
| S6 | 反映できなかった案のJSONの扱い（§3.2） | 議論する。候補は(a)〜(e)。(a)と(b)は最低限として入れ、(c)〜(e)は議論の結果で決める |

S6の候補:

- (a) ソース表示で見せるだけ（読み取り専用。検証の指摘を並べる）。
- (b) 次の修正の依頼で、専門担当にその案と検証の指摘を渡す。例えば「さっきの案のグラフを直して」で、失敗した案を土台に直せるようにする。1回の推論の原則は保つ。
- (c) 利用者がソース表示でJSONを編集し、「この案を反映」で検証にかける（画面上の手直し）。
- (d) 「この案を反映」で、表示できない部品だけを省いて強制的に反映する（fixerより強い削除）。
- (e) コピーやダウンロードで持ち出し、外部のエディタやLLMで直して貼り戻す。

## 7 試験と受入

- fixer: 分類ごとの補正の試験。決定性、捨てたものの記録、補正後の厳密な検証、空になる場合の失敗。既存のfixture（U1〜U8）とSKILLの例が補正なしでそのまま通ること（補正は壊れたものだけに効く）。
- 専門担当のターン: 1回の推論で反映して終わること。補正しても失敗する場合は推論が1回で、固定文で終わること。`endTurn`を返さない操作は従来どおり。音声の依頼でも読み上げまで完了すること（`specialist-voice.test.ts`を拡張）。
- E2E: 既存の`ui-compositions.spec.ts`と`ui-composition-parts.spec.ts`の台本を1回推論に合わせ、全件passを確かめる。
- 実機: 利用者が音声で依頼し、1回の推論で反映されるか、失敗時に固定文がすぐ返るかを確かめる。
