## 実装した変更

| 対象 | 変更と維持した境界 |
| --- | --- |
| 旧接続の復旧 | 接続状態GETの410だけを失効へ変換し、旧leaseを貸出対象から外して既存の確保処理へ進める。同時要求は既存のconnectingへまとめ、利用中の処理を待って解放する。生成POSTの410や認証拒否を一括再送しない |
| 取消と終了 | 復旧中の取消・終了で遅れて返った接続を採用せず解放する。既存のlifetime・利用数管理と採用ゲートを使用する |
| streamの診断 | 共通readerが固定の終了分類、終端の有無、届いていた許可済みの計数を通知する。失敗時もtimingへ残すが、不完全出力の拒否と外向きエラーは維持する |
| 補助接続の診断 | 内部の物理処理がmainでも、論理的なauxiliary/subagentをログへ保持する。1回限りの寿命契約は変更しない |
| 集計の完全性 | 接続終了・logger排出後に集計し、各呼出しの計数・timingの不足や重複、boot/config混在を検出する |
| cacheの受入 | 正式入力数、資料内の値の読取り、全段階の実行、再利用数を検査する。通常配置と先頭systemの対照を分離し、不合格は終了コード1とする |
| 初期判断の比較 | runnerに同一接続／短命接続の対照と、依頼・背景・候補の差分を追加する。製品の接続方式や判断方式は切り替えない |

主な実装は`api/domains/larm/service/{refresh,lease-manager,index,llm-timing}.ts`、`api/infrastructure/{chat-stream,logger}.ts`、`scripts/response-decision/`。意味判断の語句分岐、固定返答、slot制御、接続pool、常駐判断接続、新しいフォールバックは追加していない。

## 初期判断の接続比較

native出力を固定し、同じ入力・同じ13486 byteの送信形を再利用した。物理接続だけをrunner内で変え、論理的な段はauxiliaryの初期判断のままとした。

| 条件 | 初回のcache / prefill | 再送のcache / prefill | 判断全体 |
| --- | --- | --- | --- |
| 同一接続を保持 | 0 / 3,444.413 ms | 2,933 / 24.146 ms、2,933 / 24.059 ms | 7,628・3,800・10,402 ms |
| 毎回新規の補助接続 | 0 / 3,708.369 ms | 全件0 / 3,671.642・3,804.866 ms | 7,184・7,977・8,048 ms |

同一接続の3回目は初回出力がnative操作を返さず、上限1回の修正が入った。表の24.059 msはその要求の初回呼出しであり、修正は575 token再評価・899.029 msのprefillを要した。合計7呼出し、6判断すべて期待判断に一致。修正を除外して速さを主張しない。

この条件では、同一接続の維持で初期判断の入力再読込みを減らせる。一方、キャッシュヒットしても初回呼出し全体に約3.8〜4.4秒を要し、出力形式の修正も残る。常駐化だけで応答全体が解決するとは判定しない。

追加の差分比較は8判断すべて成功、修正0件。

| --- | --- | ---: |
| 基準 | 2,937 / 0 / 3,486.438 ms | 0 |
| 依頼だけ変更 | 2,943 / 2,421 / 686.642 ms | 0 |

背景を追加したのに正式量が700 token減っている。現行の組立ては背景をuserとして置き、その後に判断指示のsystemを置く。先に確認した後方system欠落と整合するが、この試験だけで落ちた内容を全て特定したとはしない。この条件は同じ情報を保持した速度比較として無効とする。候補差分では同一接続でもcache 0になり、接続だけでなく実際のprefixも改善の条件となる。

## 正式約14000 tokenの対照試験

先頭system＋userの2メッセージを使い、資料末尾の値を答えさせた。JSON schemaには正解値を埋め込まず、資料の読取りを別に検査した。出力上限512 token。各形式は校正1件＋シナリオ10件の全11件成功、可視性・正式量・再利用・記録の完全性が合格した。

| 形式 | 正式入力token | 即時再送cache / prefill / 要求全体 | 補助4件後cache / prefill / 要求全体 |
| --- | ---: | --- | --- |
| テキスト | 13,956 | 13,952 / 53.346 ms / 6,334 ms | 13,952 / 25.460 ms / 2,240 ms |
| JSON | 13,962 | 13,958 / 27.721 ms / 2,684 ms | 13,958 / 25.784 ms / 2,683 ms |

テキストのcache 0の初回はprefill 25,505.832 ms・要求全体32,435 ms、JSONは19,052.628 ms・22,553 msだった。テキストでは即時再送でも要求全体に6.334秒かかり、prefill以外の変動がある。これらの差からProviderのqueue時間等を断定しない。短い固定応答の測定であり、通常会話の速度改善ではない。

user差分・背景差分でも約13,440 tokenを再利用した。全段の記録に欠測・revision混在はなかった。

## 通常配置は不合格を確認

新しい資料読取りと正式量の検査を使い、通常配置を1回確認した。終了コード1。10要求中9要求は生成として成功したが、mainの6要求はすべて資料内の値の読取りに失敗した。

- 基準・即時再送・背景追加・元の要求・補助4件後は正式2,682 token。user差分は2,688 token。
- 補助4件後のcacheは2,678、prefillは22.848 ms。可視な短い入力だけの再利用であり、約14,000 tokenの受入にはしない。
- `auxiliary_3`は`chat_stream_incomplete`。今回追加した診断では`finishReason=length`、`streamFailure=output_limit`だった。今回の1件は上限到達と判別できたが、過去の同名エラーの原因まで遡って断定しない。上限128 tokenは変更していない。
- 残る補助3要求は生成成功だが、数字だけという試験の期待には一致しなかった。本文は保存せず、原因は未確定。期待値の緩和は行っていない。
- 正式計数・timingは全10件でそろい、`coverageComplete=true`、`revisionComparable=true`。受入は`visible=false`・`formalSize=false`・`retained=true`となり、不合格を検出した。
