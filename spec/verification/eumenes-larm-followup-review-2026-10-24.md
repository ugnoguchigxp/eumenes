# LARM接続復旧と応答遅延の改修レビュー

2026-10-24。対象は[接続復旧と応答遅延の修正](eumenes-larm-followup-2026-10-24.md)の差分。接続寿命・取消・終了、診断の安全性、比較runnerの記録と合否判定を確認し、見つかった問題を修正した。最終の再レビューでは、この差分の範囲に未解決の指摘はない。

## 指摘と修正

| 指摘 | 影響 | 修正と確認 |
| --- | --- | --- |
| 最後の利用者と復旧処理が同じleaseを解放する | 1回の退役でDELETEを2回送る。競合や不要な待ちにつながる | lease単位で解放のPromiseを共有し、確認済みの解放は再送しない。失敗時だけ次の既存cleanupが再試行できる。正常・一度失敗・body取消失敗・body取消待機を回帰試験化 |
| 重複した呼出しIDを別の測定として数える | 同じ計測を二重に使って完全と判定できる | 重複IDを拒否。成功行と失敗timingの食い違いも拒否する |
| 結果行のない計測を除外してしまう | 対応しない計数・timingや失われたsubjectIdがあっても、記録が完全と見える | 未対応・未帰属の計測を検出し、比較不能にする。途中の1要求だけの表示は、そのsubjectIdのログに絞る |
| cache試験が段階の存在だけを検査する | 補助4要求より前の結果を「補助4件後」として受け入れ得る | 段階の件数・順序・roleを確認し、重複・順序違いを拒否する。再利用tokenは正式入力数以下の安全な整数を要求 |
| 背景更新で確認する正解値が変わらない | 新しい背景を読まなくても正解になる | 背景の正解値を別の値に変え、元へ戻した要求も独立して照合する。通常配置と2メッセージ対照へ適用。JSONはvalueだけのobject、テキストは指定値との一致を確認する |
| 後続のusageで既知の計数を失う | 分割フレームで届いたprompt数などが診断から消える | 有効な計数を項目ごとに保持。生のusageや未知の値を診断へ渡さず、不完全出力の採用判定は維持する |
| 後続finishフレームで拒否理由を取り違える | 観測済みcontent filterを出力上限と記録し得る | 最初に観測した打切り理由を保持する。元の例外・取消と未完了出力の拒否は変えない |
| runnerが新しいsignalで失敗理由を分類する | 自分の締切超過を通常の通信タイムアウトと記録する | 実際の試行のsignalを共有し、期限切れ・取消も失敗件数と全条件失敗の停止判定へ含める |
| 偶数標本の中央値が上側の中央値になる | 比較の中央値が通常の定義と異なる | 中央2値の平均へ修正。p95はnearest-rankを維持し、空・奇数・偶数の試験を追加 |

解放の共有は同一leaseのcleanupに限定した。常駐接続・pool・追加の生成再送・新しい優先順位は追加していない。診断用のbody取消が待機または失敗しても、確認済みの解放を取り消したり再確保を待たせたりしない。

## レビューと検証の経過

最初の回帰試験で二重DELETE、重複行による誤った完全判定、分割usageの欠落、拒否理由の誤分類、未対応計測の見落としを再現した。更新される正解値を扱えないfixtureも確認し、修正後に通過した。テスト期待値を緩めず、古い値・余分なJSON項目・段階の順序違いは不合格のままとした。

| 検証 | 結果 |
| --- | --- |
| 最終の接続・stream・診断・logger・公開API・runner試験 | 63件成功、失敗0 |
| runner単体試験 | 14件成功。上記63件と重複するため合算しない |
| 比較runnerのfake実行 | 4条件×3方式×2接続条件の24判断が期待どおり。fixture確認だけで、live採用には使わない |

最初のdomain検証は全工程が通過したが、並行作業によるソース更新を検出して`invalidated`になった。これを合格とは扱わず、条件を固定し直して上記の成功を確認した。対象159ファイルは、その無効になった検証中も変更されていなかった。途中の全体型検査で確認した別作業の試験ファイルのエラーには手を加えていない。

domain検証成功後の変更は、runnerの未対応計測検知と途中表示の絞込みだけ。製品コードは変更せず、runnerの最終試験・全体型検査・実ログの再集計で確認した。無関係なdomainまで同じ試験を反復していない。
