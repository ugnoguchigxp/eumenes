確認できた不足は次のとおり。

1. **実目標用の参照先・検査が未接続。** 登録済み作業先は依然としてサンプルのREADMEとCLIだけ。本家のLive2D実装を読む・検証する対象が提示されていない。背景色の設定自体は `web/src/domains/avatar/background.ts` と `HiyoriViewControls.tsx` に存在し、`docs/avatar.md`、`spec/avatar-view-adjustment-2026-11-07.md`にも実装・検証記録がある。まず現在の実装と元の達成条件を照合する必要があり、新たな編集許可の要求だけでは不十分だった。ここから実目標の達成済みを自動で確定した事実はない。
2. **目標の質問が自発配送されない。** `goal-permission.ts` の `list_goals` は未回答の質問を返すが、`goal-report-delivery.ts` は完了報告だけを配送する。既存の開発監督の質問通知も目標起点では除外される。質問への返答を実行先へ戻す処理はあるが、最初の提示がなく、本人に質問が届かないまま待機し得る。これは設計の「追加許可を既存質問に結び付けて一度求める」を満たしていない。
3. **読取ポリシーの適用に不整合がある。** 許可省略の登録で唯一のローカル作業先がWeb調査より常に優先されるため、目標に無関係なサンプル作業先でも公開調査の選択肢がなくなる。改訂後は旧版の編集許可を失効させる一方、新版へ適用できる読取ポリシーを発行していない。専用runnerの選択も作業先が1件のときだけであり、実案件を単純に2件目として追加するだけでは解消しない。
4. **実担当の質問待ちが同じ目標の他条件を止める。** 担当からの質問でcurrentWorkIdを保持してneeds_userになった経路では、その目標の判断全体が再開対象から外れる。別の目標へ実行枠を返す処理はあるが、同じ目標の独立した未達条件を先に進める設計を満たしていない。
5. **利用経路を含む受入が不足。** 通常の音声認識から共通会話・目標ツールへ入る実装経路はある。リアルタイム音声は既存の委任を選択したときに共通会話へ入る。どちらも今回の実モデル受入はテキスト入力で、実音声の目標登録・質問提示・返答・同一目標再開までを受け入れた結果ではない。

残作業の完了条件は、実目標に対応する参照先と検査を接続し、既存成果を先に確認できること、必要な質問が自発的に一度届いて同じ質問IDの返答で再開すること、上記の読取許可・独立部分の待機を修正すること、実目標と実際の利用経路で追加の催促なしの進行を検証すること。README受入の成功だけで、この実運用の完了を宣言しない。
