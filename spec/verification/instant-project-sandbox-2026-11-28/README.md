# Instant Project Sandbox P0 検証記録

2026-11-28 JST。第6稿のP0事前検証を完了した。使い捨てのGitリポジトリ、検査プロセス、SQLiteと、許可を得たループバック配信で確認した。製品サーバーと製品DBは操作していない。

## 1. 従来方式のディスク基準値

macOS 27.2.1（arm64）、Bun 1.4.4、APFS。試行ごとに独立したスパースディスクイメージを用意した。同一ロックを持つ二つの比較用フォルダに `bun install --frozen-lockfile --backend=clonefile --ignore-scripts` を順に実行し、ボリュームの空きブロック数の差を計測した。依存はReact、three.js、cannon-es、型定義、TypeScript、Vite。Bunのキャッシュは両フォルダで同じボリュームに置いた。各条件3回。測定には事前取得済みロックを使い、インストール時に実行ファイルのビルドや開発サーバーの起動は行っていない。

| 条件 | 1件目の実ディスク増分の中央値 | 2件目の増分の中央値（最小–最大） | 2件の合計増分の中央値 | 2件目のインストール時間の中央値 |
| --- | --- | --- | --- | --- |
| 初回はキャッシュなし | 109.43 MiB | 1.16 MiB（1.13–1.19） | 110.55 MiB | 82 ms |
| キャッシュあり | 1.39 MiB | 0.99 MiB（0.97–1.37） | 2.46 MiB | 77 ms |

キャッシュがある場合の値は、キャッシュ自体の占有を既に含めた時点との差。比較用フォルダからインストールを省いた場合のストレージ・時間削減余地は、この機器で同じ依存とclonefileを使う限り小さい。Works専用の実行環境はCoreの追跡対象とDB領域から分離するため、共有構成自体の準備・保持に必要な容量もP4で計上する。これ以上の節約を前提に範囲を広げず、既存のP0で、待機プロセスの解放と制作手順の簡略化が成立する境界を確かめる。共有構成との差、アプリの表示時間、メモリの差は未測定。

## 2. 分離ビルドと型検査

- 作業フォルダとは別にインストールした共有依存で、React・three.js・cannon-esを含むTSXをビルドし、型検査した。共有依存と型検査の解決先を渡し、作品フォルダに `node_modules` は生成されなかった。型エラーだけを加えると型検査は失敗し、プレビュー相当のビルドは通った。
- `sandbox-exec` で既定の読取りを拒否した初期プロファイルでは、Bunはdyldの起動段階で終了した。ルートディレクトリ自体とOS実行用ファイルへの読取りを追加し、起動前に一つのプロファイルを適用する方式で復旧した。この状態で、別領域のテストデータの読取り、入力と共有依存への書込み、TCP接続をOSが拒否し、出力専用領域への書込みは通った。
- 作品フォルダに試験用のpreloadと環境ファイルがある状態で起動しても、信頼済みの設定を使った起動処理は読み込まなかった。作品側の `tsconfig` の `paths` は分離ビルドに使われなかった。マクロ指定は入力検査の時点で失敗し、実行を示す試験用の印は生じなかった。

共有環境を保存したロックから別の場所に復元し、二つのTSX入力でそれぞれバンドルのSHA-256が一致した。別の共有環境にだけzodを追加した後と、外側に置いたCore模擬ツリーの依存宣言・ロック・React実体を更新した後も、二つのハッシュは一致した。型検査には、Coreで採用済みのCanvas同梱TypeScriptコンパイラーを隔離用の一時領域へ配置して使った。

現行の `createCheckSandbox` に隔離を重ねると、macOSが後からの適用を拒否した。単一プロファイルの試験では、現行の登録照合と終了・入力証跡を再利用して `typecheck` と `build` を実行した。未登録の引数を拒否し、型エラーTS2322では両方とも終了コード3、検査中に記録対象の入力が変わると合格扱いにならなかった。共有型は検査から読め、共有環境や作品への書込みは拒否された。TypeScript Language ServiceでもGit除外の設定からReact・three.js・`OrbitControls` の定義へ到達できた。実Claude Code、Codexの画面およびClaudeの読取りツールからの固定版参照は製品接続後に確認する。

## 4. 実ループバック配信

利用者の明示許可を受け、製品とは別の試験用HTTPサーバーを起動した。各試行でIPv4の `127.0.0.1` に一つだけリスナーを開き、動的な同一ポートで `localhost`（親画面）、`p-a.localhost`、`p-b.localhost`（作品）を配信した。HTTP応答はPlaywrightで差し替えていない。許可外のHostは421、GET以外は405。すべての試行で停止後にTCP接続が拒否され、`lsof` でも試験ポートに待受がないことを確認した。

| 試験ブラウザー | 同一ポートでの表示、素材、保存領域の分離 | 作業中のAを親から停止し、Bを操作 |
| --- | --- | --- |
| この機器に導入済みのGoogle Chrome 158（ヘッドレス、サイト分離の追加フラグなし） | 合格 | 合格 |
| Playwright Headless Shell 149（サイト分離の追加フラグなし） | 合格 | **不合格**。Aの処理が終わるまで親が停止操作を完了できなかった |
| Playwright Headless Shell 149（`--site-per-process` 明示） | 合格 | 合格 |

作品ごとに `localStorage`・IndexedDB・BroadcastChannelを分離できた。静的なJSON・CSSの読込み、選んだフレームだけへの画像転送、作品から親画面と本体模擬APIへのアクセス拒否、Service Worker登録時にスクリプト取得前に拒否することも確認した。初版の対応範囲は今回合格したmacOSのChrome構成。Playwright Headless Shellの受入ではサイト分離を明示する。P1では製品の起動前チェックと実画面で再確認する。

## 5. 追加の固定応答

- **画像の直接受付と作品参照。** 現行の画像入力スキーマを再利用したin-memory DBで、作品IDと操作IDを一意にし、`image.generate` だけを登録した。再送やリビルドで同じ実行と期限を保持し、作品ごとの取消、同一操作の入力の不一致、期限切れと許可失効を検出した。明示参照、未表示の作品名、同名の候補、移設後の旧世代も判別できた。 [固定応答のコード](interfaces-probe.ts)
- **依存の承認。** 固定メタデータで、公開から7日未満またはインストール用スクリプトのある依存を拒否した。登録世代を変更した後の承認、同一承認の再送を拒否し、承認を受けた作品だけが新しい固定版で同一の仕事IDを使うことを確かめた。製品ではRegistry・配布処理と接続して確認する。 [承認の固定応答](dependency-probe.ts)
- **収集と監視。** `.env` とルート外リンクを除外し、個別16 MiB、ファイル数、合計の上限で入力を拒否した。一つのプロセスで2作品を監視し、100 msでAの連続保存をまとめてAだけを更新した。閉じると監視と待機タイマーは0になった。初期上限は1,024ファイル、個別16 MiB、合計64 MiB。読取り中にファイルやディレクトリが置き換わる場合はP1で確認する。 [収集・監視の試験](source-probe.ts)
