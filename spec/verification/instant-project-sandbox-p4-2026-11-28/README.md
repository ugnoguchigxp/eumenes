# Works P4の試験導入と計測

2026-11-28 JST。製品サーバーを使わず、macOS arm64と消音したGoogle Chromeで確認した。

## 既存作品の試験導入

既存のL-Lang World ClockのGitルートに暫定の入口と共有環境を登録し、作品のファイルとGitの状態を試験前後で照合した。Worksは従来のHTMLとサーバーを棚卸しに表示した。元の画面は追加のDOM要素と生成されたWebAssembly・capability JSONの配信を必要とするため、この作品の正式移行は見送った。

試験登録を解除し、元のデモ配信処理を同じリポジトリから読み込んでループバックで開いた。ChromeでWasmの初期化と時計の表示を確認した。Gitルート・共通ディレクトリ・HEAD・インデックス・リモート・作業ツリーの状態と、入口・HTML・サーバー・依存宣言・ロックを比較した。

対応するブラウザー作品の固定例は、ChromeのWorks画面から試験登録した。未コミットの編集を含む表示と、不足依存・版差の棚卸しを確認した。試験中のClaude Codeによる編集を拒否し、Chromeで登録解除した。作品側に生成設定、依存、ロックの変更を残さず、登録・配信・監視を解除した。 [試験導入結果](trial-result.json)

## ディスク実消費

同じ版のReact・three.js・cannon-es・TypeScriptを使った。従来構成には個別のViteを含む。APFSの独立したイメージごとにBun 1.4.4のclonefile方式を使い、空キャッシュと準備済みキャッシュを各3回測った。数値は中央値と範囲で、MBは100万バイト。従来構成はインストールの実消費を測り、共有方式は固定版・キャッシュ・作品別の本番ビルド出力を含む。

| キャッシュ状態と作品数 | 個別インストール MB | Works共有 MB |
| --- | ---: | ---: |
| 空、0件 | 0 | 74.61（74.59–74.67） |
| 空、1件 | 106.91（106.86–106.95） | 75.33（75.29–75.35） |
| 空、2件 | 107.85（107.82–107.90） | 76.06（76.02–76.08） |
| 準備済み、0件の増分 | 0 | 1.38（1.34–1.39） |
| 準備済み、1件の増分 | 1.31（1.31–1.33） | 2.12（2.07–2.13） |
| 準備済み、2件の増分 | 2.46（2.45–2.48） | 2.85（2.80–2.86） |

空から2件を始めると約31.8 MB少なかった。準備済みキャッシュから共有の固定版も準備する場合、2件の増分は約0.39 MB多かった。固定版まで準備済みなら、そこから2件分のビルドを追加した増分は約1.47 MB。個別インストールもAPFSのクローンを使うため、共有方式の効果は開始条件によって異なる。

空キャッシュで追加依存を含む版3.1を導入して旧版を保持した時点は77.23 MB。次の版3.2を導入して最古の版3.0を削除した時点は77.00 MB。準備済みキャッシュの場合は同じ順で4.02 MB、3.79 MBだった。それぞれ依存の異なる固定版を導入し、掃除後も直近2版を保持した。 [APFSの計測値](disk-result.json)

## プロセス、待機メモリ、操作待ち時間

同じ二作品のTypeScript/Reactソースを使用した。macOSのfootprintコマンドで物理メモリを採り、Worksは事前にビルドした本体Webを配信する隔離ホストからの増分を求めた。計測用Webのビルドは別プロセスで行った。Chromeのプロセスは別欄で計測した。LARMはメモリ比較から外し、P3の実環境試験に記録した。各条件3回の中央値で、範囲は記録の各試行から確認できる。

個別方式の初回表示には作品ごとのBunインストールを含む。Worksの初回表示は共有環境の準備後に、登録から表示までを測った。Worksは保存時にビルド・型検査を行ってページを読み直す。Viteは起動済みサーバーでHMRを行う。WorksのChromeは表示を閉じた後も本体のタブを開いており、Viteは作品タブを閉じた。Worksの開閉によるChromeの差は、この測定条件で約11〜21 MBだった。

個別方式は二件同時に開く間、Viteが二つ常駐した。二件目だけを起動して表示した場合の中央値は149〜152 MBだった。Worksはホストプロセス一つに作品用の共通プレビュー待受を持ち、作品別のサーバーが生じなかった。監視数は0、1、2、閉じた後0と推移した。ビルド・型検査中にサンプルした物理メモリのピークは、ホスト込みの中央値で395〜423 MB。二件を閉じた時点でビルダーの子プロセスと待ち行列は0だった。 [プロセス・メモリ・待ち時間の全試行](runtime-result.json)

別の通し試験で、会話からAlpha、続けてBetaを指定した。実Claude Codeが二件を順に編集し、どちらも型検査とビルドに合格してChromeで表示された。待機中の二つの実ランナーはそれぞれ54.2 MBと50.3 MB。作品を閉じ、各ランナーの60秒の待機期限と追加の照会3回を経て、両ランナー・監視・ビルダー・待ち行列は0件だった。この試験のホストには会話試験とWebビルドも含まれるため、ホストの前後値は隔離した比較表と分けて記録した。 [実Claude Codeの計測](native-result.json)

同じ機器で複数の軽量なブラウザー試作を続ける場合、作品別サーバーを持たない効果を確認できた。保存直後の表示が重要な既存作品や専用サーバーを持つ作品では、従来の起動方法を併用できる。この計測からフレームを保持する運用への変更は採用しない。
