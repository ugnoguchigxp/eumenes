# LARM新版での再検証

2026-10-24。対象: 利用者からの再検証依頼。前回の切替前の記録は[larm-revalidation-2026-10-24.md](larm-revalidation-2026-10-24.md)。

## 判定

**検証した条件では、補助処理によってmainのKVキャッシュが失われる問題は解消している。** 正式計数で約14,000 tokenの対照入力を使い、通常テキスト・JSONのストリームとも、補助4要求後も末尾4 token以外を再利用した。prefillは約26 ms、要求全体は約2秒だった。

一方、**会話履歴の後ろにあるsystemの情報欠落は残る**。通常のContextWindow配置では推定約14,000 tokenに対して正式計数が2,682 tokenとなり、この配置の14,000 token保持受入は成立しない。短い初期判断の疎通も6.46〜7.20秒を要した。キャッシュ保持の改善から、製品の応答遅延全体が解消したとは判定しない。

## 対象と手順

保存済みLARM接続先をbackendのsettings domainの読取り専用操作で取得した。開始・終了時のhealthはHTTP 200 / status=ok。配備対象は一致し、各試験の正式計数メタデータも同じbootEpoch/configRevisionだった。

- releaseCommit: `082b0bbdbb89caf3e3592b5254d6dbdb362317c9`
- bootEpoch: `epoch-b01f6115-9e41-4ce7-867b-79ed2062a5f9`
- configRevision: `1cbcb01cb336ee90ab617a6ef9f8cd8521cf926db302891b7e9e72d159d95e78`
- Eumenesの基準commit: `0fa17b5b6cefe8718a8bde37e7d21b3f1734b974`

warnログ確認後、部分的なrole可視性、LARM接続経由のキャッシュ試験、初期判断の疎通の順に実施した。対象ソース・試験・設定537ファイルのハッシュを開始時に保存し、終了時の変更0件を確認した。既存のTODO UI・monitoring・background等の別作業差分は保持した。

製品コード・設定の変更、製品サーバー・LARM・Providerの停止・起動・再起動、他consumerの接続解放、別チャットへの送信は行っていない。独立した検証用接続は終了時に解放した。入力は合成データとし、会話本文・認証情報・Provider生応答は記録していない。

## 3. 通常配置の合成試験: 14,000 token受入は不成立、補助1件失敗

`scripts/response-decision/cache.ts`は9要求中8成功、`auxiliary_1`が`chat_stream_incomplete`で失敗し、終了コード1。出力上限128 tokenだが、上限が失敗原因かどうかは未確定。上記512 tokenの対照試験成功だけで、この失敗の原因を断定しない。

通常配置のmainは全て正式2,682 tokenだった。初回cache 0 / prefill 3,022.901 ms、即時再送cache 2,678 / 26.503 ms、補助4要求後cache 2,678 / 22.507 ms。背景を追加しても正式計数は変わらない。これは可視な2,682 tokenの再利用確認であり、通常配置で約14,000 tokenを保持できたという証拠にはしない。

## 4. 初期判断の疎通: 6/6成功、6.46〜7.20秒

`scripts/response-decision/bench.ts --run --smoke`で雑談・一般知識の2ケースを既存3方式で実行した。6/6 qualityPassed、全件1呼出し、修正呼出し0。ツールの実アクションや製品の会話保存は行っていない。

| 方式 | 成功/実行 | 時間 ms |
| --- | ---: | ---: |
| native-legacy | 2/2 | 7,056〜7,139 |
| schema-legacy | 2/2 | 6,463〜6,900 |
| schema-stable | 2/2 | 6,768〜7,195 |

全件cache 0、正式入力2,700〜2,940 token、prefill 3,410〜3,723 ms。独立した短命のauxiliary接続を使うこの試験では、初期判断の入力再読込みが残っている。キャッシュを保持できることと、実際の初期判断でヒットすることは別に確認する必要がある。

2ケースの疎通から方式間の優劣や本番採用は判定しない。role互換性が未解決のため、全ケース・反復・holdoutによる採用比較は行っていない。これは最終回答・音声を含めた製品全体の通し計測でもない。

## 5. 配備前の接続を保持した製品プロセスの注意点

稼働中Eumenesのログには、旧bootEpochの接続への制御要求がHTTP 410になった記録がある。今回の新規検証接続は新版で成功している。一方、既存の`lease-manager.ts`の再接続条件には410が含まれず、既存試験`token-count-diagnostics.test.ts`の「a control-plane 410 identifies the old claim without changing lifecycle recovery」も、410後に旧接続IDを保持して`larm_control_410`を返す挙動を検証している。この試験は1成功（18 assertion）。

製品の読取り専用`/api/inference/status`はHTTP 200 / readyだったが、状態表示だけでは接続復旧・会話成功を証明できない。製品プロセスから新しい会話を送る通し検証は今回実施していない。製品の再接続・再起動や410回復仕様の変更は行っていない。
