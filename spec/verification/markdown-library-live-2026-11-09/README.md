# LARM文書ライブラリ拡張の本番受入

2026-11-09 JST。設定済みLARMはGET/PUT/PATCH/POST/DELETEを公開し、稼働中のEumenesも拡張一覧、フォルダー、移動、コピー、削除、一括操作を有効と判定した。Docling本体は事前確認時に停止状態だった。[結果](results.json)

専用フォルダーに検証文書を作成し、Eumenesの公開APIから空フォルダー作成、単件の移動・タイトル変更・コピー・削除、一括移動・コピー・削除、配下を含むフォルダー移動・コピー・削除を確認した。元文書のIDを保持し、コピーは別IDを採用した。BOM、CRLF、末尾空白、日本語、装飾と取込原文を含むMarkdown・Plate復元データは読戻しで一致した。削除した検証文書は404を返した。

古いETagではEumenesがLARMへの変更要求より前に409 `revision_conflict` を返す。最初の検証スクリプトはLARMの412を想定して中断したが、入口での競合拒否をコードと応答で確認し、同じ文書が変わっていないことを照合して残りの試験を進めた。競合要求の再送は行っていない。

実画面のMarkdown Artifact @4では、保存済み検証文書を開けた。ゴミ箱アイコンで削除対象を確認してキャンセルし、別の検証文書を画面の「移動」から親フォルダーへ移動して読戻した。既存9文書のID、パス、タイトル、ETag、本文・復元データのdigestは一致した。[削除確認](delete-confirmation.jpg)、[移動後の一覧](move-readback.jpg)

再起動前の稼働画面では、最新のドラッグ移動と一覧フォーカスが未反映だった。

検証専用のフォルダーと配下をAPIで削除し、開いた検証用workspaceも削除されたことを確認した。最終一覧は元の9文書と一致し、Docling本体は引き続き停止状態だった。

利用者の再起動後、新しい検証用文書をフォルダー行へドラッグし、移動先を入力済みの確認画面から移動した。移動先で文書を開き、一覧への切り替えでその行へのフォーカスを確認した。親フォルダーを表示してから作業用一覧経由で同じ文書を開き直した場合も、保存先のフォルダーに戻り、該当行が強調・フォーカスされた。チェック選択は0件だった。[再起動後の一覧](focus-after-restart.jpg)

APIで移動後のID・パス・Markdown・Plate復元データを照合した。新しい検証用フォルダーも配下ごと削除し、元の9文書とDoclingの停止状態を再確認した。
