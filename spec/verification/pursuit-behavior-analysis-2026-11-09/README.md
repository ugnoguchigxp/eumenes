分析日: 2026-11-09。対象は11月8日の四件。新しい調査は走らせず、既存公開APIと保管済みログを照合した。製品コード・設定・サーバーを変更していない。

検索を一件ずつ実行する構造はある。ただし、長時間化を検索の繰返しだけで説明することはできない。完了した技術比較は検索が一回だけで、本文取得三回も開始約2分17秒までに終わっていた。その後に43回のモデル呼出しと順番待ちがあり、通知までさらに約21分39秒かかった。

## 一番大きな手掛かり：取得が終わってからの時間

前回の技術比較では、最後の外部本文取得が開始後136.858秒に終了した。依頼→通知は1,435.402秒で、残りは1,298.544秒。

- その後のPursuitモデル呼出し: **43回、876.736秒（約14分37秒）**。
- その後の実行待機: **403.926秒（約6分44秒）**。
- Webの再検索・追加取得: **0回**。

したがって、このケースの遅さの主な観測対象は、取得後に続くモデル呼出しと実行待機である。検索の一括化だけでこの約21分39秒を解消できる、という根拠はない。

ただし、前回版にはモデル呼出しの目的ログがなく、この43回を「再読何回・下書き更新何回・最終検証何回」とは分けられない。それらが全て不要だったとも判定していない。

## 実装から確認できることと、未検証の仮説

既存のツールは`web_lookup(query: string)`、`web_read(url: string)`で、それぞれ一つのクエリ、一つのURLを受ける。Pursuitの提案契約も`tool`と`inputJson`が一組であり、複数の独立操作を一回の提案で返す欄はない。共通の推論実行枠は1、Web取得枠は6だが、対象四件では一調査内のWeb並列実行は観測されなかった。

このため「次の一手を選ぶ→操作一件→結果を見てまた次を選ぶ」という細かい往復が、時間を積み上げる構造だと考えられる。検索・URL読取りをまとめる案には検討価値があるが、独立性や品質を保てるかの比較は未実施。一定の回数や時間へ強制的に短縮する案、意味判断を語句で置き換える案を今回実装していない。

根拠となる実装: `api/domains/pursuit/service/tools.ts:18`、`node_modules/eumenes-pursuit/dist/domains/generation/prompts.js:37`、`api/domains/pursuit/service/core.ts`、`api/application/server-core.ts:92`。取り込まれた設計は[既存設計](../../pursuit-web-research-integration-2026-11-06.md)。

次に分析の優先度が高いのは、取得後の43回のモデル呼出しで、何の操作が選ばれ、どの新しい根拠や報告更新につながったかである。独立した最終検証は、その必要性と役割を保ったまま別に評価する。

- [照合用イベント](source-events.jsonl): 関連IDで抽出した運用項目。会話本文・モデルの生応答・設定・認証情報を含まない。
- [検証結果](validation.json): 過去の使用量集計・件数・ID一意性・区間・入力hashとの照合。

`input_tokens_total`にはキャッシュ分を含む。通常入力・キャッシュ入力・出力を三分割したい場合は`input_tokens_uncached`、`input_tokens_cached`、`output_tokens`を使う。156の関連推論試行すべてを使用量APIのIDと照合し、キャッシュ内訳も取得した。時系列のモデル行はそのうちPursuit本体131試行だけで、関連Agencyや記憶整理25試行を混ぜていない。

CSVの空欄・JSONのnullは不明を示し、0回・0秒とは異なる。外部Webの時間はqueue.settledのdurationMs、モデルの時間は保存usageのended-startedであり、記録層が異なる。前回の本文URLや検索結果の詳細の一部は既存公開APIで期限切れ／取得不可になっており、当時保存した最新二件のWeb取得スナップショットと、保管済み運用ログを優先した。期限切れの本文を新しく取り直して過去の証拠に置き換えていない。
