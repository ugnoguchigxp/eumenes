# HTTPキャッシュにおける `Cache-Control: max-age` と `no-cache` の違い

`max-age` は指定秒数の間、応答を新鮮なものとして再利用できる期間を定めます。`no-cache` は保存を禁じる指示ではなく、保存した応答を再利用する前にオリジンサーバーで検証するよう求める指示です。

## 対象と情報の日付

2026年11月15日時点のHTTPキャッシュ仕様を、指定されたRFC 9111（2022年6月公開）に基づいて整理します。ここでの説明は、主にサーバーが応答に付ける `Cache-Control` を対象とします。

## 背景：キャッシュと「新鮮さ」

HTTPキャッシュは、以前の応答を保存し、後続リクエストに再利用して通信量や待ち時間を減らします。保存済み応答が「新鮮（fresh）」なら、キャッシュはオリジンサーバーへ問い合わせずに再利用できます。新鮮さの期間を過ぎた応答は「古い（stale）」状態です。

キャッシュの現在の経過時間（`current_age`）が新鮮さの期間（`freshness_lifetime`）を超えているかで判断します。経過時間には、応答の `Age` なども反映されます。したがって `max-age=60` は、必ずしも受信した瞬間から60秒使えるという意味ではありません。

## それぞれの働き

### `max-age=N`

応答の年齢が N 秒を超えたら、その応答を古いと扱うよう指示します。期間内は、ほかの再利用条件も満たしていれば、キャッシュはオリジンサーバーに確認せず応答を返せます。

```http
Cache-Control: max-age=60
```

この例では、新鮮さが続くのは応答の年齢が60秒を超えるまでです。期限後、キャッシュは通常、保存済み応答を検証してから再利用するか、新しい応答を取得します。検証には `ETag` と `If-None-Match`、または `Last-Modified` と `If-Modified-Since` などが使われます。

### `no-cache`

引数なしの応答ディレクティブは、応答をキャッシュに保存すること自体は禁じません。保存した応答を別のリクエストに使う前に、オリジンサーバーへ転送して検証し、成功した場合に限って再利用するよう指定します。

```http
Cache-Control: no-cache
```

保存済み内容が変わっていなければ、オリジンサーバーは `304 Not Modified` を返せます。キャッシュは保存済み本文を使い続けられるため、毎回本文全体を転送する必要はありません。ただし検証のための通信は発生します。

## 主な違い

| 指示 | 保存 | 検証なしで再利用 | オリジンサーバーへの確認 |
|---|---|---|---|
| `max-age=60` | 条件を満たせば可能 | 60秒の新鮮さ期間中は可能 | 期限内は通常不要 |
| `no-cache` | 可能 | 不可 | 再利用の前に必要 |

## 具体的な使い分け

- **一定時間、変更の反映が多少遅れてもよいコンテンツ**：`max-age=300` のように、新鮮さの期間を設けます。期間内の再利用によって負荷や待ち時間を減らせます。
- **利用のたびに最新状態を確認したいが、本文の再転送は減らしたいコンテンツ**：`no-cache` を使い、検証に `ETag` などを利用します。
- **保存自体を避けたい場合**：`no-cache` ではなく `no-store` を検討します。RFC 9111では `no-store` は、キャッシュがリクエストや応答を保存しないよう指定する別のディレクティブです。

なお、リクエスト側に付ける `Cache-Control: no-cache` は、クライアントが保存済み応答を検証なしで使わないよう求める指示です。仕様上、リクエストディレクティブはキャッシュへの助言であり、キャッシュが実装して従うことは必須ではありません。応答側の `no-cache` とは適用される側が異なります。

## 注意点

- `no-cache` は「キャッシュ禁止」ではありません。保存させない指定は `no-store` です。
- `max-age` は、指定期間を超えた応答を即座に破棄する指示ではありません。キャッシュは検証して再利用できる場合があります。
- `max-age` と `no-cache` のように指示が競合する場合、RFC 9111はより制限の強い指示に従うよう求めています。
