# 応答開始遅延のレビューと実測

調査開始: 2026-10-13、実測終了: 2026-10-14 00:01 JST。対象: Eumenesの会話・ASR・LLM・TTS経路。

## 結論

体感の遅れは一律の200〜400msでは説明できない。今回の合成音声を使った3回のAPI測定では、**ASR後の入力判定LLMが5.71〜5.81秒**を占め、音声アップロード開始から最初の音声データ取得まで10.71〜10.99秒かかった。入力判定は認識された言語、前の発話との継続関係、回答可能な状態かを一度に判断する既存処理である。

添付報告の「生成後の態度判定が689〜819ms」という観測は否定しない。ただし今回、初回の1.419秒のうち接続準備が1.373秒、準備済みの要求では判定全体が25〜32msだった。**態度モデルそのものの高速化より、入力判定の短縮と接続準備・本文確定の依存関係の見直しを優先する。**

OpenAI・Claudeとの同条件比較は行っていない。モデル、prompt、出力制約、履歴の異なる経路の所要時間差から、Eumenes固有の追加遅延や他製品との差を断定しない。

## 範囲・完了条件

目的は、遅延の場所をレビューと計測で特定し、以後の改善を評価できるログと再計測手段を残すこと。既存のPinoと相関ID、LARM adapter、settings読み取り専用操作、各domainのAPIを再利用した。

実施順は、既存ログ・指示・実行経路の確認→部分試験の基準値保存→時間境界の計測追加→部分・結合試験→実接続測定→全体検証・差分点検。推論の意味判断、プロンプト、モデル選択、採用条件、言語や権限の検証、DBスキーマ、製品設定は変更していない。改善案の実装と、実マイク・スピーカーの受入は今回の完了条件に含めない。

## 測定結果

### サービスのadapter経路

保存済みLARM接続をbackendのsettings domainで読み、同一クライアント接続を保持してTTS→ASR→LLMを3巡した。TTS入力は固定した日本語短文、ASR入力はその合成音声。LLMは固定した短問、出力上限128 token。音声・本文は保存していない。

| 観測 | 初回 | 2回目 | 3回目 |
| --- | ---: | ---: | ---: |
| TTS要求→WAV取得 | 989ms | 205ms | 233ms |
| ASR要求→認識結果取得 | 333ms | 285ms | 287ms |
| LLM要求→最初の本文 | 1,475ms | 1,170ms | 1,163ms |
| LLM全体 | 1,547ms | 1,252ms | 1,240ms |
| 正式token計数 | 26ms | 17ms | 30ms |
| 生成送信→最初の本文 | 1,439ms | 1,150ms | 1,129ms |

最初のTTSの接続準備は738ms。再利用時のProvider準備は1ms未満。LLMは各巡回でTTS/ASRの後なので、初回LLMも既に接続済みである。「cold model」と呼べる条件は制御していない。TTS値は音声全体の受信完了であり、最初の可聴音ではない。ASR認識内容の精度評価はこの時間測定とは別である。

根拠: [adapter結果](adapter-result.json)、[adapter運用ログ](adapter-backend.jsonl)。各3件のみであり、P95や通常利用の分布は算出しない。

### 隔離backendの会話API経路

一時DB・一時キー領域・一時ログを使用し、接続設定を設定APIに保存した。cloud fallbackは無効、toolchainは無効。テキストは新規会話3件、音声は同じ隔離環境のmain会話に合成音声で3回入力。通常Webと同じdeferred音声入力を使い、`input_ready`を確認してcommitした。ブラウザの無音判定・録音・実音響再生は含まない。状態取得は25ms間隔なので、音声取得までの値にはその観測待ちが最大約1周期分加わる。最初の音声チャンクを取得後、セッションを停止した。

| 観測 | 1回目 | 2回目 | 3回目 |
| --- | ---: | ---: | ---: |
| テキスト送信→SSEの最初の本文 | 2,709ms | 2,490ms | 2,909ms |
| テキスト送信→完了確認 | 5,708ms | 5,754ms | 6,177ms |
| 音声送信→最初の音声データ取得 | 10,966ms | 10,711ms | 10,992ms |
| 音声: ASR処理 | 360ms | 348ms | 336ms |
| 音声: ASR後の入力判定 | **5,764ms** | **5,710ms** | **5,814ms** |
| 音声: 回答LLM adapter全体 | 4,422ms | 4,230ms | 4,383ms |
| 音声: 回答後の態度判定 | 32ms | 30ms | 28ms |
| 音声: 合成開始→最初のチャンク公開 | 345ms | 325ms | 385ms |

音声の入力判定は全体の約53%。その補助接続準備は21〜34msで、約5.7秒の大半は生成要求の応答待ちだった。API測定全6回答の `dialogue.body_policy` はstreamedであり、この標本では本文保留は発生していない。

テキスト初回だけ態度判定1,419ms（うちProvider準備1,373ms）。2・3回目は27ms・25msだった。token計数は主回答21〜43ms、音声入力判定38〜40ms。これらは入力判定5.7秒に比べ小さい。

根拠: [API結果](api-result.json)、[ID別の区間一覧](api-summary.json)、[API運用ログ](api-backend.jsonl)。adapter試験は短いuser messageだけ、会話APIは製品system prompt付き・出力制約も異なる。両者の差を「アプリ処理に1秒かかる」と解釈してはいけない。

### 添付調査との照合

指定されたrun `03eb3f2e-7e16-4a0b-86b1-a44a17f73099` の候補取得346ms、LLM本文TTFT4,165ms、交換完了7,579ms、態度判定819msを既存ログで再確認した。態度判定区間中に音声用接続準備437msがある。既存ログだけではそのrunの本文保留有無は不明。

## コードレビューと改善案

### P1: ASR後の入力判定を短縮する

[recognize.ts](../../../api/domains/voice-dialogue/service/recognize.ts) はASR完了後に `executeControl` を待ち、許可言語・信頼度・入力状態が確定してから回答へ進む。実測5.71〜5.81秒、送信サイズ4.8〜5.1KB、補助接続準備21〜34ms。

まず既存の [transcript-language](../../../api/domains/voice-dialogue/prompts/transcript-language.md) と [transcript-assessment](../../../api/domains/voice-dialogue/prompts/transcript-assessment.md)、JSON schema、共通control実行経路を使って比較する。重複する説明・schema提示を精査し、同じ意味と検証項目を保った短い指示を試す。既存の入力判定をまとめた構成を崩してLLM往復を増やさない。公開Profileで利用可能な低遅延モデルへのcontrol専用ルーティングも候補だが、対応capabilityと品質の確認を先に行う。

評価は独立発話・継続・途中・曖昧・多言語・略語を含む固定セットで行い、言語許可、readiness/relation、誤結合率、完了前の早答え、取消を比較する。語句分岐や文字種による代替判断、信頼度閾値の緩和は採用しない。暫定の実験目標は判定を1秒以内に近づけること。仮に達成できれば約4.7秒の短縮余地だが、達成可能性・品質は未検証。

### P1: 回答全文確定と発声開始の関係を見直す

[respond.ts](../../../api/domains/voice-dialogue/service/respond.ts) は `waitForTerminal` と本文採用を待ってから合成を開始する。今回の音声回答では最初の本文から生成完了まで約1.73〜1.74秒あった。この区間がTTS開始前に丸ごと直列に入る。

低リスクな第一案は、本文の正当性を検査した時点と、態度・音声付随情報の完了を分ける設計の検討。部分発声を導入するなら、発声済み文の採用・訂正・取消・World/Memory失効を扱う契約が必要である。現行の保留条件を単純に外す案は不可。今回のwarm態度判定は数十msなので、態度判定だけを外しても秒単位の改善にはならない。

### P1: 接続準備を応答後の必須待ちにしない

[larm/service/index.ts](../../../api/domains/larm/service/index.ts) はLLM単独の接続から音声・態度Providerを必要に応じて準備する。今回、初回TTSで738ms、初回回答後の態度判定で1,373msの準備待ちが発生した。

音声セッション開始など、音声利用が確定したタイミングで既存 `prepareVoice` を先行する案を比較する。全起動時に全Providerを無条件確保しない。接続数・他セッションの待ち・idle解放・取消を維持し、warm状態では不要な処理を増やさない。準備時間が短縮ではなく前に移るだけの可能性があるため、利用者の開始操作から最初の音声までで効果を判定する。

### P2: 本文保留を実利用で集計する

[generation-handler.ts](../../../api/domains/dialogue/service/generation-handler.ts) はMemory/World/担当結果やrecallがある場合、採用検証前に本文を公開しない。添付報告が指摘する構造は現行コードでも確認した。今回は新規会話・tools無効で6回答すべてstreamed。実利用で `body_policy` のheld率と `first_delta`→保存確定の時間を測ってから優先順位を決める。保持を必要とする安全条件は維持する。

### P2: live音声の次チャンク取得・decodeを先行する

[voice-dialogue/hooks/index.ts](../../../web/src/domains/voice-dialogue/hooks/index.ts) では、前チャンクの再生終了→played通知と再取得の完了→次の音声取得→decodeの順になる。ネットワーク往復とdecodeがチャンク間の無音に加わる。テキスト回答の自動読上げは別のreplay経路で、既に次の合成要求を先行しているため、両者を混同しない。

既存の最大3チャンク保持と再生順を維持して、1チャンク先の取得・decodeだけを先行する案。新たな先行結果も世代・取消・権限失効で破棄する。追加した `audio_fetch` / `audio_decode` / `playback_scheduled` と実音響測定で、無音の短縮と割込み回帰を確認する。今回はチャンク間の実音響時間を測っていないので効果量は未確定。

### P2: 音声終端・LLM送信待ちを別々に評価する

[voice-activity.ts](../../../web/src/domains/audio/controller/voice-activity.ts) の既定無音判定は1,500ms。今回のAPI試験はその後から測っており、この1.5秒を含まない。値だけ短くすると途中発話が増えて入力判定の要求も増えうる。無音区間で区切る処理と、LLMが発話の意味的な完了を決める役割を分けて維持する。

主回答の送信後TTFTは今回の会話APIで約2.38〜2.85秒。LARM内のqueue/prefill/decode内訳は観測できない。まず同じclaim・同じbody・同じ出力上限で経路比較し、LARM側が内部時刻を返せる場合に照合する。正式token計数は17〜43msだったため、契約を省略して高速化する根拠はない。
