# 記憶入力の重複削減：反復比較

2026-11-08。**旧版と候補を各60回比較した。LLMの揺らぎは両方にあるが、候補の品質維持を確認できず、不採用。製品コードは旧版のまま。**

同日、利用者との確認により今回の改修を見送る判断を確定した。追加の実装・再評価は予定せず、比較コードと証跡を保存する。再検討の条件は[計画書の最終判断](../../steward-input-repeat-2026-11-08.md#最終判断利用者確認済み)に記載した。

## 実施条件

前回失敗した訂正の入力、初期の「朝は紅茶が好き」という記憶、出力schema、指示文、保存済みLARM設定を固定した。前回保存した旧版と候補の入力構築コードを読み込み、既存Inferenceの出力契約を加えた実送信入力を比較した。前回24件の送信入力を同じhashで再現できることを実行前に確認した。

各対の実行順を交互に反転し、ABBAの順序を均衡させた。各variantは先行30回・後行30回。毎回独立の合成SQLiteストアとforget journalを使い、実際のStewardのparse/applyとMemoryの保存結果を検査した。実ユーザーのデータは使用していない。

まず各20回を行い、予定した中間条件で差を確定できなかったため各60回へ拡張した。120生成すべての応答・実usage・保存後Stateを取得した。意味失敗の引き直しや結果の選別はしていない。source hash・設定hash・provider識別hashとdataの同一性を照合し、各variantの送信入力hashもそれぞれ一つだった。新規120問題ではなく、一つの問題の条件付き反復である。

製品コードを候補へ切り替えず、保存済みrendererで旧新を作った。出力IDは補正せず、原JSONを既存parserへ通した。fixtureの位置別aliasは初期の合成データ作成だけに使った。原JSON・失敗・usageは`results.json`に保存した。

| --- | ---: | ---: |
| 完了した生成 | 60 | 60 |
| 固定チェックで訂正が反映された件数 | 57 | 50 |
| 訂正が反映されなかった件数 | 3 | 10 |

固定チェックは記憶数・本文・旧値の消失を確認するもので、polarityを確認していなかった。したがって57/60と50/60を、意味まで正しい成功数として扱わない。120件を保存後のStateと照合し、すべての固有の提案群を点検したところ、「朝は緑茶が好き」という本文に`polarity: negated`が付いた誤更新が旧版7件・候補14件あった。原集計とラベルは変更せず、`semantic-review.json`へ別集計した。本文が同じでも否定が逆なら、正しい訂正ではない。

候補の不正引用2件のうち1件は、前回と同じく`今は`を原文にない`前は`に変え、引用検査で拒否されて古い記憶が残った。もう1件は正しい更新に余計な不正引用の更新を重ねたもので、正しい更新だけが残った。最終Stateが正しいことと、提案に問題がないことを分けて記録した。

旧版の未反映3件と、候補の未反映のうち9件は、更新自体を提案しない出力だった。候補の残る未反映1件は不正引用による拒否だった。

## 揺らぎと入力変更の切り分け

- **同じ入力でも揺らぐことは確認できた。** 旧版にも候補にも成功と失敗があり、raw出力は旧版5種類、候補14種類だった。候補は常に失敗するわけではなく、前回の1件だけで決定的な回帰とは言えない。
- **入力変更による影響がないとも言えない。** 失敗は旧版3/60、候補10/60。片側Fisher正確検定はp=0.037399、両側p=0.074799。2回の予定された判定に各0.025を割り当てた事前基準では、入力変更との関連を確定する閾値に届かない。有意差がないことを同等性の証明にはしない。
- **元の引用誤りだけでは、原因を一つに絞れない。** 不正引用試行0/60対2/60の片側p=0.247899。観測数が少なく、この引用誤り自体が重複削減によって増えたと断定する根拠は不足している。
- **意味の品質維持は確認できなかった。** 別点検でも候補の正しい訂正は36/60で旧版50/60を下回った。これは原集計を都合よく変更した検定ではなく、保存結果の意味の監査として報告する。追加点検を事前登録済みの主要指標と読み替えない。

順序別でも、先行時の未反映は旧版1/30・候補4/30、後行時は旧版2/30・候補6/30だった。先行/後行だけでは観測差を説明できない。一方、同じprovider識別でもバックエンドのcacheや他の利用による影響があり、完全な独立試行・定常な分布は保証できない。p値は診断の補助であり、厳密な因果関係の証明や別モデルへの一般化には使わない。

手法：[Fisher正確検定の定義](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.fisher_exact.html)。集計関数は公開例の試験を通し、Python標準ライブラリの独立計算でも同じp値になることを確認した。

## 採否と検証

**不採用。** 訂正段階で候補の失敗数と不正引用の頻度が旧版を上回ったため、予定した条件に従い他11ケースの追加比較へは進まなかった。予定最大186生成に対し、実施は120生成。品質維持が確認できていない状態で候補を適用しない。製品コードは最初から最後まで旧版のままであり、サーバーの再起動・実記憶の変更・他チャットへの送信・commitは行っていない。

集計関数の試験と、引用拒否・保存・訂正・依頼等の既存部分試験は計25件成功。型検査成功。終了後に全source hash不変、製品3ファイルが前回開始時の旧版と一致することを照合した。今回は製品コードの変更を採用していないため、全アプリのverifyや通しの実会話試験は繰り返していない。実モデルの比較は隔離した実Memoryへparse/applyを通した範囲であり、実アプリ全体・クラウド・独立した人間評価の証明とは区別する。

主な記録：`manifest.json`、`results.json`、`summary.json`、`analysis.json`、`semantic-groups.json`、`semantic-review.json`、`independent-stat-check.json`、`final-tests.log`、`final-integrity.json`。前回の記録は変更せず残した。今後の比較では、今回見つかったpolarityを含む期待値を新しい試験の実行前に固定する必要がある。
