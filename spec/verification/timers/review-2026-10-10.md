# タイマー実装のコードレビュー（2026-10-10）

対象は `spec/timer-artifact-implementation-plan-2026-10-09.md` に対応するタイマー実装。開始・照会・取消のツールチェーン、永続化と期限処理、時計、終了通知を確認し、下記を修正した。既存の並行変更は保持した。live および実機器の受入完了を示す記録ではない。

## 発見した問題と修正

| 優先度 | 発見した問題 | 修正後の動作 |
| --- | --- | --- |
| P1 | タイマー用Skillが判断前のcoordinator入力になく、取消対象のID・版番号も与えられていなかった | 判断前に必須Skillとprofileを固定し、現在のタイマー候補を渡す。取消・ID付き照会は渡した候補と照合し、Skillの失効も再確認する |
| P1 | 通知のpollが pending → claimed を受け取るとeffectのcleanupが再生を中断した | 再生attemptの寿命をqueryのpending配列から切り離し、所有するclaimの再取得では止めない。StrictModeのeffect再実行でも維持する |
| P1 | 再生失敗後にpending専用silenceを使い、claimed通知を確定できなかった | 所有するclaimをblocked/mutedとしてackし、playedは実際の再生完了後だけ記録する |
| P1 | 不変の開始receiptだけを回答に使い、回答前の取消・期限到達を反映できなかった | action ledger、所有者、receipt digestを照合し、現在のタイマー状態を再取得する。取消済みを開始成功として採用せず、破損receiptの本文も配信しない |
| P2 | origin tokenは文字列の一致だけで、保存された人間の依頼と結び付いていなかった | 生存するmanual/voiceの会話run、coordinatorの所有者・取消epochを照合し、conversationIdとmessageIdも保存する |
| P2 | RTT計測を通信完了後に始めており、時計の通信補正がほぼ0だった | リクエストの前後で単調時刻を計測する。復帰・再接続・期限到達後はAPIで状態を確認し、取消のissuedAtもサーバー推定時刻を使う |
| P2 | 通知音が別AudioContextを作り、音量・出力先・mute・音声処理を無視していた | 出力を再利用し、音声セッションがあれば同じcontrollerを使う。設定、入力中、応答中、再生中を考慮し、通知音とその出力の余韻はマイク入力から除外する |
| P2 | silent/played通知が表示から消え、停止できなかった。claimed通知の停止もpending専用操作だった | dismissまで表示を保持し、現在のtimer revisionで通知を停止する。音を出せなかった通知も画面から停止できる |
| P2 | clientの壁時計で鮮度を判断し、最初の通知ページしか取得しなかった | serverNowとclaimの期限で判断し、通知のページを取得する。鮮度を超えたclaimの再送と別clientによるackの再送も拒否する |
| P2 | 時計の表示対象は手入力で送った単一runだけで、音声開始・連続送信・再読み込みで欠落した | 複数runの保存receiptを監視し、音声runも対象にする。保存済みactiveタイマーを復元し、同じ画面で閉じたタブはpollで開き直さない |
| P2 | 再dispatch時のqueue_fullが通知claim回収・保存期限処理までrollbackさせた | タイマーごとにSAVEPOINTで再dispatchし、容量待ちのタイマーが他の回収処理を止めない。変更のないmaintenanceは明示publishしない |
| P2 | 狭い時計領域で8桁の時刻がはみ出す可能性があった | DigitalClockのheroサイズを8桁でも収まる比率に変更し、DesignSystemを再buildした |

タイマー候補は全active（最大32件）と直近の未停止通知8件に絞り、本文・過去の会話・不要なタイマー履歴をcoordinatorへ増やさない。アーティファクトの参照は保存済みreceipt/APIのtimerIdから作る。

## 確認結果

- レビュー開始時のタイマーbackend＋ツールチェーン: 17件成功。
- 修正後のタイマーbackend＋ツールチェーン: 24件成功。会話経由の照会・取消、架空origin、回答準備後の取消、破損receipt、鮮度境界のclaim、他clientのack、queue_full時のclaim回収を含む。
- 関連backendの横断試験: 140件成功（queue_full回収試験追加前の実行）。
- Web全体のVitest: 38ファイル・153件成功。
- `verify --domain agent-runtime` と `verify --domain tool-runtime` は成功。`verify --domain audio` は21件の試験を含め成功。
- `verify --domain timers` は成功した実行あり。その後の実行でもformat・lint・typecheck・domain試験は成功したが、並行変更により最終source hash検査が停止した。
- 全体typecheckと `git diff --check` は成功。
- DesignSystem buildは成功。
- browser: 3ケース成功（時計の2ケースと通知の1ケースは別実行）。90秒の会話から時計表示、375px幅での24時間表示・再読込み・取消、保存した8秒タイマーが期限に達して時計のタブを閉じても通知が残り「通知を停止」で消えることを確認。

## 全体検証の未完了

`verify:all` はタイマー以外の並行変更である `api/domains/world/repository/extraction.ts` と `api/domains/world/service/lifecycle-adapter.ts` のformatで停止した。

独立して実行したbackend全体試験は596成功・27失敗・1skip（23 import/起動エラーを含む）。実行中にworldの構文が変わり、開発サーバーとloggerの受入試験などが失敗した。その後の全体typecheckは成功したが、この実行を全体検証成功とは扱わない。最新のdialogue domain試験もworldのforget/extraction経路で5件失敗し、`world_host_extract_event` のテーブル不在等を報告した。これらをタイマーの修正結果に混ぜて成功扱いにしない。

実LARMでのタイマーroute選択、実時間での期限遅延、実マイクと出力機器の3往復、複数の実ブラウザー/機器間の通知音の受入は未実施。fixtureの音声ゲート試験やbrowserの通知表示は実機器受入の代わりではない。
