# Web検索後の報告失敗の調査と改修

2026-10-10。検索から本文取得、調査担当の報告、会話への採用までを対象に調べた。既存のWorld・画面・通知などの並行変更はこの改修の対象に含めない。

## 確認した原因

製品の運用ログでは、08:09:36 JSTに検索候補5件、08:09:41に本文1件を取得していた。その後、08:09:55と08:10:11の報告を `invalid_evidence / quote_mismatch` で拒否していた。検索要求そのものの失敗と、検索後の報告失敗を分けて確認した。

製品DBをコピーしない隔離backendでも、次の挙動を再現した。

| ケース | 改修前の観測 |
| --- | --- |
| 今日の鎌倉の天気・最高気温 | 検索5件と3ページの取得に成功したが、報告の引用不一致で失敗。76.9秒 |
| 明日の鎌倉の天気・最高気温 | 検索5件と1ページの取得後、モデルの1試行が30秒の期限に達して失敗。48.2秒 |
| Bun公式資料のテストコマンド | 初回検索の5秒timeout後に再検索成功。本文はguardの `PATTERN_DETECTED` で拒否。検索要約の引用に基づく部分的な回答は保存された |

途中の実Web試験では、引用不一致を解消しても当日の数値が回答に届かなかった。`workerContext` が20,000 bytesの容量を超えると古い資料を丸ごと除去し、先に取得したtenki.jpの予報が最後に読んだ動的ページのナビゲーションに置き換わっていた。公開ページを別途取得し、tenki.jp本文の先頭約1,350文字に当日と翌日の予報が存在することも確認した。

さらに、検索2回・読取り3回を使い切った後もモデルが検索を要求し、修正試行でも許可されていないtoolを要求して終了するケースを観測した。

稼働中の既存会話でも試したところ、通常の検索経路で「予報が掲載されている」ことだけを報告し、未読候補が残っていても終了するケースがあった。また、調査担当が10月10日の鎌倉の晴れ・最高26℃を本文から報告しているのに、会話の回答は「対象日が不明なため取得できません」となった。主LLMの入力は新しい調査報告→過去の会話→現在の質問という順序で、古い失敗が最新報告より後ろに置かれていた。

## 実装

- 取得済みの表示本文を、原文に完全一致する300文字以下の抜粋へ分ける。モデルは `sourceId` と `excerptId` を選び、ホストが引用文を確定する。保存・公開API・メインへの投影は既存のReport形式を維持する。従来形式の引用は完全一致検査を維持する。
- 架空の出典・抜粋、提示範囲外の抜粋、引用文による参照の上書きを拒否する。引用や本文をメインへ転送しない。拒否ログは固定の `unknown_excerpt` と契約項目名だけを残す。
- 20,000 bytesの資料予算では検索要約を先に短くし、複数の読取本文へ容量を配分する。既存の本文4,800文字、資料20,000 bytes、全体65,536 bytesの上限を増やさない。短縮した資料は `truncated` として扱う。
- 取得操作を5回使った後は許可toolを空にし、出力契約と指示の双方をfinishに揃える。本文未確認の検索要約を使う条件も、本文取得失敗または読取り予算終了に限定して説明する。
- 日本時間の今日と翌日を別々に渡し、短期予報を優先する。依頼項目が不足し取得予算が残る場合は、別候補の本文で補うよう指示する。
- 許可された本文読取りtoolと未読の検索候補がある場合、具体的な読取り例を渡す。既取得URLの再読では表示範囲が増えないことも伝える。天気の報告不足はweb-research内で判定し、通常検索で未読候補と取得枠が残る場合は既存の1回の修正枠で再取得へ進む。取得手順の保存経路には既存の正本検証を適用し、この追加判定を重ねない。
- 主LLMへ渡す現在の報告を、過去の会話の後、現在の質問の直前へ移す。要約にある対象日を、原文非転送やpartialだけを理由に未確認と扱わないよう指示する。過去の会話は保持する。

Web取得のguard、DNS/redirect検査、所有者・取消・期限・採用検査は省略しない。参照番号の検証は主張の意味の正しさまで証明するものではなく、元の完全一致検査と同じく根拠の実在を検査する。
