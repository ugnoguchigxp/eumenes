# ASR後の入力判定：高速化候補の比較（2026-10-14）

**安全条件を維持した高速化は未達。本体への変更は採用していない。** 同じモデル・入力・設定で短縮は観測できたが、短い出力形式では未完入力や判定不能な入力を通す回帰が発生した。`transcript-language.ts` と `transcript-assessment.md` は着手時へ戻し、差分がないことを確認した。条件や期待値を緩めて採用していない。

前回の[応答速度調査](../response-latency-2026-10-13/README.md)で約5.7秒だった、ASR後の言語・継続関係・回答開始可否のLLM判定が対象。目的は、その判断をLLMに残し、許可言語、3つのconfidence、8秒期限、不正出力の拒否、receipt採用・取消・stale検査を保った短縮を確認すること。ASR/VAD/TTS、モデル変更、DB・公開APIの変更は対象外とした。

## 同条件比較

保存済みsettings domainの読取り専用操作と既存LARM adapterを使用。実測モデルは全試行 `ornith-1.5-strix-lean`。JSON出力、temperature 0、maxOutputTokens 512、exact context、8秒期限を固定した。各ペアのユーザー入力・previousText・conversation・languageCodesは同一で、順序をAB/BA交互にした。設定の変更を検知したら測定を停止する。

主会話を実行しない測定用の親接続まで確保すると補助接続の準備中に期限へ達したため、比較本体では、補助adapter内部と同じ短命接続を1要求ずつ作成・解放した。本文を生成する主会話は併走させていない。これはcontrol adapterの測定であり、inferenceの保存処理や接続解放時間、実際の音声入力全体の測定ではない。製品の接続方式は変更していない。

最初の12種類は通常質問、未完断片、継続、話題変更、短い返答、略語、外国語・混在言語、曖昧入力、本文・履歴内の判定指示。最後に、指示明確化へ未使用だった4種類を加え、16種類×前後×2回を測定した。合成した転記文だけを使い、実際の会話・音声・認証情報・設定値を結果へ保存していない。

以下の短縮幅は、両版とも応答を取得できた同一入力ペアの「変更前 − 候補」の中央値。期限超過を速い応答として数えず、別に残した。bootstrap区間は成功ペアのみに対する参考値で、母集団全体の速度保証ではない。試行間の外部負荷は制御できないため、異なる行の絶対時間を直接比較しない。

## 安全性と計測の限界

最後の候補は、意味を特定できない `…` に `identified / ja / confidence 0.95 / ready / readinessConfidence 0.8` を返した。既存のhost検査では回答開始条件を満たしてしまう。元の版は同じ入力をundeterminedとして止めた。この誤採用は、コードに特定文字の検出を加えて隠すべきものではない。

最後の32回ずつの実行で、変更前は21回応答・11回期限超過、候補は25回応答・7回期限超過。成功した応答だけの中央値は4,442→4,072 ms、平均は4,936→4,623 msだった。候補の新しい誤採用は2回。全期待条件を満たした数は10/32→18/32だが、これを安全性の向上とは扱わない。判定不能や低信頼度で保守的に止めた応答も、事前に定義した厳しい期待値に届かなければ不合格のまま記録している。

元の版にも、続きの発話をindependentとする、話題変更をcontinuationとする、confidenceが不足する、といった課題がある。候補側の新しい誤採用を、元の版の課題を理由に許容していない。

接続準備が約3.8秒かかる例と、準備・token計数が約70 msで終わった後にHTTP応答待ちだけで約7.9秒かかる例を確認した。HTTP応答待ちには提供側の待ち行列・入力処理・生成が含まれ、今回のクライアントログだけでは分解できない。別機能の実LLM試験と時間帯が重なった記録を読み取り、完了後という条件変更を根拠に再測定したが、その後も期限超過は再発した。並行試験だけが原因とは断定しない。

候補不採用が確定した後、本体を先に復元した。最後の比較は、起動時に固定したmessages・schema・parserを持つプロセスで最後まで記録したもので、復元後の製品の速度を示すものではない。

## 残した変更と検証

- [比較runner](../../../scripts/voice-assessment-latency-live.ts)と[16種類の評価入力](../../../scripts/voice-assessment-cases.ts)。入力同一性・保存設定の一致を検査し、3回連続の実行失敗で停止。割込み時は要求を中止し自分の接続を解放する。現状は本体を戻しているので、`--run` は `candidate_identical_to_baseline` で送信前に止まる。将来の候補を実装して比較するためのrunnerである。
- [host回帰試験](../../../api/domains/voice-dialogue/test/settings-integration.test.ts)：言語・継続関係・回答可否それぞれのconfidence不足、および許可外言語で回答を開始しない4ケースを追加。
- [schema/data境界の試験](../../../api/domains/voice-dialogue/test/transcript-language.test.ts)：不足・余分な項目、不正な状態・言語・confidence、未完JSON、上限超過の拒否と、本文・履歴をJSONデータとして渡すことを追加。
- [音声API測定runner](../../../scripts/response-latency-api-live.ts)：input_ready到達時間を記録し、入力判定がエラーでdraftに戻ったときは90秒待ち続けない。
- 復元後のvoice-dialogue検証：backend **71件**、Web **42件**成功。型・整形・lintを含むdomain gate成功。[ログ](verify-preserved-voice-dialogue.log)
- 復元後のworkspace型検査は1,330ファイルで成功。比較runnerが本体とbaselineの同一性を検知して、送信前に停止することも確認した。[記録](noop-guard.log)
- 全体gateは途中の候補でbackend等1,953件成功・2件skipまで進み、担当外の `TimerWorkspace.test.tsx` 2箇所の型エラーで停止した。[ログ](verify-all-final.log)。担当外は修正していない。最終状態の全体gate成功とは扱わない。
- 本体候補が意味判断の受入を通らないため、新形式での音声API通し試験・実機器受入は実施していない。判定の回帰を残したまま次段階へ進めない。

高速化そのものの完了条件は満たしていない。次に必要なのは、元の出力契約を維持した状態で、LARM提供側の同時実行待ち・入力処理・生成を分けた計測と、他処理の影響を把握できる実行枠での比較である。接続の別名化だけで演算資源が分離されるとは限らない。今回のデータを根拠に、期限を延ばす、信頼度の閾値を下げる、文字列パターンで意味判断を代替するといった変更は行わない。
