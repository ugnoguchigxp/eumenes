# 天気の即時回答ツールチェーン

作成日: 2026-10-18

状態: 2026-10-18 利用者合意（§6 決着）。実装・fixture済み（binding `execution:"instant"`、`api/application/weather/`）。回答文は末尾に発表時刻「（5時発表）」を付ける。実機で「鎌倉の天気」が「横浜は…」と答えたため、§7 で地名の解決を host 側へ移した（利用者合意 2026-10-18、revision 2、実装・fixture済み、実APIで鎌倉・横浜・札幌・大阪の回答を確認。実LLMの引数は未確認）。§3 の `area` 列挙と `primary_area.xml` は §7 で置き換え。

関連: [会話の初動 §8（削除済み。正本は会話エージェントのContextWindow仕様）](context-window-spec-2026-10-24.md)、[ツールチェーンの登録と拡張](../docs/toolchain-extension.md)、[調査失敗時の返答](research-failure-reply-and-readahead-2026-10-17.md)。

## 1. 背景

天気の依頼は、R1 → 一時回答 → Web調査サブエージェント（検索・本文取得・報告）→ 会話エージェントの回答で、回答まで約57秒かかる（run `180ade55-9423-40fa-ba74-cb1c4e735136`）。答えの形が決まっているのに、汎用の調査手順を通っているため。

## 2. 使う API（2026-10-18 確認）

- `GET https://weather.tsukumijima.net/api/forecast/city/{cityId}`。横浜（140010）で 200、約0.56秒。
- 応答: `title`（例「神奈川県 横浜 の天気」）、`publicTime`（+09:00）、`publishingOffice`、`forecasts`（今日・明日・明後日。`telop`、`temperature.max/min.celsius`、`chanceOfRain` の6時間ごと）、`description`、`location`、`copyright`。
- 地域は一次細分区域142件（`https://weather.tsukumijima.net/primary_area.xml`）。市区町村の単位ではない（例: 鎌倉は「神奈川県 横浜」）。
- 気象庁のデータを個人が運営する互換APIで配信している。公式サービスではない。

## 3. 流れ

| 段階 | LLM | 内容 |
| --- | --- | --- |
| 候補検索 | なし | 既存（§8）。天気の依頼で天気担当が候補に入る |
| R1 | 1回 | 天気担当の関数を呼ぶ。引数は共通の kind/freshness/impact/approved に加え、`area`（一次細分区域のラベルの列挙、例「神奈川県 横浜」）と `day`（`today`/`tomorrow`/`day_after`）。**`announcement` は持たない** |
| 取得 | なし | host が `area` を cityId に解決し API を呼ぶ |
| 回答 | なし（§6 Q1） | host が取得結果から回答文を作り、通常の確定回答として保存・配信する |

- 一時回答は出さない。R2 も呼ばない。回答まで R1 の1回分（推定7〜8秒。区域の列挙が R1 の入力に加わるのは天気担当が候補にある時だけ）。
- 区域一覧は `primary_area.xml` から取得してキャッシュし、列挙と cityId の対応を作る（固定のハードコードはしない。取得できない時は天気担当を候補に出さない）。
- 3日より先、時刻別、現在の気温など API にない依頼は、R1 が天気担当を選ばず既存の Web 調査を選ぶよう、天気担当の useWhen/avoidWhen（登録定義）で示す。

## 4. API 障害時（利用者方針）

API が失敗（ネットワーク・タイムアウト・非200・形式不正）したら、同じ run で既存の Web 調査（`web.search`）へ切り替える。依頼は元の発言をそのまま渡す。切り替え時の一時回答は §6 Q2。調査が失敗したら既存どおり「失敗しました。」。切替は API 障害のときだけで、天気担当の結果が気に入らない等の理由では切り替えない。

## 5. 登録と変更範囲（見込み）

- データドリブン形式（bundle＋登録adapter）で `weather.forecast` を追加。手順は `docs/toolchain-extension.md`・`docs/toolchain-extension-verification.md`。
- R1 の関数定義に、登録定義が宣言した引数（`area`・`day`）を載せ、`announcement` を要求しない「即時回答」型の binding が必要。§8 の R1 は「担当関数は announcement 必須、依頼引数は R2」なので、この型を追加する（会話の判断方式は変えない。担当の登録定義で型を宣言する）。
- 回答文の組み立て、区域一覧のキャッシュ、API 呼び出しは adapter 側。dialogue に天気の語句分岐を書かない。

## 7. 改訂: 地名を host が解決する（2026-10-18、revision 2）

### 7.1 問題

実機で「鎌倉の明日の天気」に「明日（10/19）の横浜は…」と答えた。予報は正しい（鎌倉は気象庁の「神奈川県 東部」、API の区域名は「横浜」）が、言っていない地名で答えるので誤りに見える。R1 に142区域の列挙から選ばせ、回答文に API の区域名を入れていたため。

### 7.2 変更

- **対応表:** 気象庁 `https://www.jma.go.jp/bosai/common/const/area.json`（約262KB、市町村1,805件 class20s → class15s → 一次細分区域 class10s）を起動時に取得してメモリに持ち、一日一回読み直す（従来の区域一覧と同じ扱い。利用者選択 (a)）。class10 のコード142件は天気 API の city id と一致する（2026-10-18 確認）ので、`primary_area.xml` は読まない。取得できない間は天気担当を候補に出さない。
- **R1 の引数:** `area` の列挙をやめ、`place`（依頼の地名をそのまま。市区町村・地域・区域・都道府県のどれでもよい）、`prefecture`（その地名がある都道府県。LLM が知識で埋める。同名の市町村の区別に使う）、`day`（従来どおり）。`choiceField` は持たない。
- **解決（host、LLMなし）:** 地名と表の名前を、末尾の「市・町・村・区・都・府・県」を除いて比べる。
  1. 市区町村（class20。「横浜市北部」のような分割名は「横浜市」としても照合）
  2. 地域・区域（class15「三浦半島」、class10「東部」）
  3. 都道府県（県庁所在地を含む区域）
  同じ段で複数見つかれば `prefecture` に合うものを選び、なお複数なら表の先頭。見つからなければ従来の取得失敗と同じく `web.search` へ切り替える。都道府県名と県庁所在地の47行は固定の表で持つ（地名の事実で、変わらない）。
- **回答文:** 解決した地名を主語にし、区域は注記にする。例「明日（10/19）の鎌倉市は曇時々晴、最高26℃・最低19℃、降水確率は最大20%です（神奈川県東部の予報・5時発表）。」区域名は「都道府県＋class10名」。
- **登録:** 入力 schema を新キー `weatherPlace` とし、skill・tool・package・toolchain・binding を revision 2 にする（profile は revision 1 のまま）。旧キー `weatherForecast` と revision 1 の定義は bundle と code から削除する（DB の旧 revision はデータとして残る）。
- R1 の入力から142区域の列挙が消える。
